## Context

A sandbox holds a forge credential, and how far that credential reaches decides what a prompt-injected agent could touch. By default the credential proxy (DL-034) adds a credential only to requests for the session's own repositories. Sometimes a person wants more: an interactive session that moves between repositories, or one that clones a sibling repository it did not start with. The credentials differ in reach. A user's own personal token or Forgejo token reaches whatever that user gave it; the deployment's GitHub App and shared Forgejo token reach whatever the administrator installed them on (DL-042).

A stored token (a GitHub personal token, or a Forgejo, Gitea or GitLab token) is handed over as it is. spov cannot mint a narrower one and cannot read back what the user created it with. Without a visible statement, a person could hand an agent a token for every repository they own and never learn that they did. A stored token can also fail to see a repository at all, and then the failure should come before a sandbox exists and cost money.

## Decision

### Git access: `repos` or `all`

A launch has a git access setting, `repos` or `all`, applying for the whole life of the session.

- `repos`, the default, is the proxy's per-repository rule.
- `all` has three effects. Every platform the caller holds a credential for gets one, including platforms the session cloned nothing from. The proxy adds the credential for any repository on those hosts; a stored token still faces the proxy's endpoint allowlist, and an App token its narrower permissions. A GitHub App token is minted without a repository list, still with `git.SandboxPermissions` (`GitHub.IssueWideToken`, through `git.IssueFor`). A GitHub platform is configured for one account's installation, so this is one token for that installation. Tokens stay in the sidecar either way.

The value comes from the first match of:

1. a launch flag or form field: `spov fly --git-access`, `spov jobs create --git-access`, or the job form on `/jobs/new` (its default is empty and left out of the request);
2. the CLI config: `sandbox.git_access` for `spov fly` and `sandbox.job_git_access` for jobs, sent with the request as a preference (`git_access_preferred`);
3. the caller's stored default, `default_git_access` for interactive sessions and `default_job_git_access` for jobs, set on the Settings page through `PATCH /api/v1/me` (an empty value clears it);
4. `repos`.

A job never takes the interactive default, because an unattended job is where narrowing matters most and a preference chosen for convenience should not widen it unnoticed.

### The deployment's consent for `all`

`SPOV_GIT_ALLOW_ALL` (`git.allow_all`), off by default, lets `all` apply to the deployment's own credentials: the GitHub App and a shared Forgejo, Gitea or GitLab token. A user's own credential can always use `all`. A platform with no recorded tier counts as the deployment's. A local server sets the switch itself, since every credential there is the user's (`Service.mayReachAll`).

When `all` cannot apply, what happens depends on where it came from:

- If a flag or form field named it, the launch is refused with a 422 before anything exists. The message names every platform that cannot have `all` and says to store a personal token or ask an admin. A queued job whose owner's tier changed before it launched fails the same way.
- If it came from config or a stored default, those platforms get `repos`, and the launch log and the session page say so.

A flag is refused and a preference is downgraded because the fallback is the safer setting and is named. A saved default, or a config file shared across projects, must not make every launch fail.

### What `all` gives up

With `repos`, a prompt-injected agent can reach only the session's repositories through the credential. With `all`, one sandbox holds a credential for everything that token reaches, so an injected agent can reach other repositories too. A person who steers the session across repositories and chose `all` accepts that for that session. For a credential belonging to the deployment, the risk is deployment-wide: one sandbox would hold a token for the whole installation. That is the administrator's to accept, which is why the switch exists. A personal token's reach was its owner's own choice when they created it. A user who has both a personal token and the organisation's App uses the token; under `repos` its GraphQL reach is wider than the App's would be, and the session page shows it.

### Renewal and recreation follow the recorded access

`store.Session.Credentials` records, per platform, the access it got. Re-mints (`recordedSelections`, with `IssueWideToken` for `all`) and recreated sidecars use that recorded access, checked again against the consent rule. A platform whose credential has since become the deployment's, because the user deleted their own token, is minted for the session's repositories again, and the record is changed to `repos` so the page stops claiming every repository. A token already in the sidecar keeps its reach until it lapses (an App token within the hour) or the session ends. A job sandbox adopted after a restart has its access worked out again from the tiers at adoption, since its launch recorded nothing for it. A Forgejo the session selected nothing from takes its base path from the platform's configured URL (DL-021).

### The launch checks that a stored token can see each repository

Before any sandbox exists, `git.Bootstrap` asks the forge, through `git.RepoChecker`, whether a stored token can see each repository it is to clone, and refuses the launch when the forge says it cannot.

- It applies to a token the proxy hands over as it is, for each selected repository and whatever the git access, since the same token clones them under `all`. A GitHub App token needs no check: minting it narrowed to a repository it cannot reach already fails. The repositories are asked about at once, each bounded by 5 seconds (`repoCheckTimeout`).
- The request is the forge's read of one repository: `GET /repos/{owner}/{name}`, or GitLab's `GET /projects/{path}`. A 404 is the refusal; on Forgejo and Gitea a 403 is too. On GitHub a 403 is not, since GitHub answers a rate limit with one, and on GitLab only a 404 is, since it answers a project it hides with one. A public repository the token can read passes.
- Any other answer, or none, lets the launch go on. An unreachable forge API is not a reason to refuse a launch whose clone may still work.
- The error names the credential and the repository and says to give that credential access to it, for example "the github credential this launch uses cannot see acme/app, so it cannot be cloned; give that credential access to it".

The check is about reach, not write access. A public repository the token can read but not push to still launches; the repository picker's note on a fine-grained token says so (DL-042).

### The session page names the credential

`SessionView.credentials` (`SandboxCredentialView`) names, per platform, the credential's kind, where it is held, the forge, the access it got and whose tier it came from. The kinds are `renewed` (a GitHub App token, narrowed to the repositories and renewed while the session is in use) and `stored` (a stored token, whose reach is whatever it was created with). The launch records the kind from `git.Renewable`, because the tier alone cannot tell an App from a personal token. Every bootstrapped platform issues some token, so there is no third kind. The holder is `proxy` or `sandbox`, and absent when not recorded.

The view carries nothing about the token itself, not a prefix or a hash, because that would invite comparing tokens. The web wording is `credentialLine` and `credentialTag` in `web/src/lib/format.ts`: the tag shows the kind, whose it is, and where it departs from the usual case (every repository, or inside the sandbox), and the full sentence is on demand. It says "these repositories" or "every repository this token reaches" according to the access. For a job, the session page, not the launch log, is where this is visible.

Settings tells a person, under a forge token, how to scope it (`forgeTokenAdvice`), that spov cannot check what it reaches, and that every sandbox on that platform uses it. For Forgejo that is "Specific repositories" with the `write:repository` and `write:issue` scopes (`tea` reads a repository's labels when it opens a pull request), for Gitea the same two scopes, for GitHub a fine-grained token limited to specific repositories, and for GitLab the `api` scope with a short expiry, noting that it reaches every project its account can. The launch log notes once per platform with a stored token where it went (the proxy, or the sandbox as it is) and that spov cannot check its reach (`noteStoredTokens`), so `spov fly` prints it; for a job, the session page is where it is seen.

## Rationale

Narrowing protects against a prompt-injected agent reaching repositories it had no reason to touch, and it is the default. A person who knows a session will span repositories would otherwise have to list every one at launch. A setting lets them choose that knowingly, and a separate job default keeps unattended work narrow.

The deployment decides for its own credentials because under the organisation's App a user can already start a session on any repository the App covers; the switch does not limit what a user may do, only how far a hijacked agent can reach from one session.

Asking the forge before launch costs one read per repository. Without it, a launch with a personal token that cannot see the repository would create a sandbox, the clone would get a 403 and the sandbox would exit, and spov could report only that the sandbox never became ready. The SDK gives a sandbox no stdout or stderr after it terminates, so the clone's own message cannot be read back, and keeping the entrypoint alive to report it would hold a sandbox open for every failed clone.

Alternatives rejected for narrowing a stored token: a Forgejo OAuth application, whose scopes cannot be limited to repositories and so reaches further than a well-scoped stored token; refusing an unscoped token, which is impossible because the scope cannot be read; and a per-repository SSH deploy key for each job, which covers git over SSH only, not the API calls `tea` and a pull request need, and needs SSH egress. The credential proxy narrows a stored token instead.

## Consequences

- An App token is minted for the whole installation when `all` is both asked for and allowed, so narrowing is the default rather than a rule.
- A launch with a stored token makes one forge read per repository more. A launch on a repository the token cannot see fails at once with a reason and costs nothing.
- `SessionRequest`, the profile and its `PATCH` body, the generated API client, the Settings page, the job form and both CLI commands carry the setting.
- Guards: `internal/server/gitaccess_test.go`, `internal/credproxy/policy_test.go` and `internal/session/credproxy_test.go` cover the setting and the proxy; `TestALaunchRefusesARepositoryItsTokenCannotSee` covers the check; `TestFlySaysWhatTheSandboxHolds` covers the credential line.

## Known gaps

- spov cannot read back what scope a stored token was created with, so the page and Settings can say only what the token is, not what it reaches.
- A stored GitHub or GitLab token still reaches whatever its account can through GraphQL, which names no repository; the session page says so for those tokens.
- The launch check is reach, not write access, and runs only for the repositories the launch selected, not for the extra platforms `all` adds.
