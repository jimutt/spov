## Context

DL-027 bounds the export (bundle plus working-tree archive, as packed) at 32 MiB and the seed bundle at 16 MiB, and DL-101 judges a sync job over 32 MiB as `over_limit`. DL-126 bounds what a landing brings into the checkout at 1 GiB of git objects and 256 MiB for any one blob (inflated sizes, from `cat-file --batch-check`), and bounds the unpacked working tree by the export's 32 MiB, checked while it unpacks. With the export streamed (DL-176), the 32 MiB is no longer what the server can afford to hold, and it is low enough that an ordinary session (a dataset, a build directory that is not ignored, an added binary) hits it on exit.

## Decision

**The bounds are the landing's.** A sync-back may bring in what DL-126 lets land, measured the way the landing measures it:

- **objects**: the commits since the base add at most `MaxSyncIncomingBytes` (1 GiB) of objects, none larger than `MaxSyncIncomingBlobBytes` (256 MiB), counted from `git rev-list --objects base..HEAD` through `git cat-file --batch-check` (sizes read without inflating);
- **working tree**: the changed and untracked files to pack total at most 1 GiB by their `lstat` sizes, none over 256 MiB.

The export script checks both in its `archive` and `inspect` modes before it packs anything (DL-176), so a refusal costs seconds and nothing crosses the network. The landing's own checks stay as they are and are the backstop, with one change: the working tree's total and per-file bounds move from `unpackWorktreeTar`, which runs as files are written, to `archivePaths`, which reads the tar headers before `boundIncomingObjects` and the fast-forward, so a refusal there also comes before anything lands (DL-126's rule). The in-unpack check stays as a second backstop at the same values.

**The transport bound** is `MaxSyncExportBytes`, now 1 GiB of packed bytes (bundle plus gzipped archive). Packing never makes the parts larger than what they pack beyond a few headers, so an export within the landing bounds is within it; it exists so the server and the CLI can refuse a stream that is not what the script would write. The server allows it plus `MaxSyncMetaBytes` (1 MiB, the metadata's own bound, which the script also checks before it writes) plus 1 MiB of tar framing and keep-alive entries; the CLI checks the declared parts against it (DL-178). The deprecated JSON routes keep 32 MiB of packed bytes under `MaxSyncJSONExportBytes`, and the script's `export` mode keeps that bound.

**The refusal names what is large.** Over a bound, the script's message gives the measure and its limit, then up to five of the largest paths among the files to pack and the blobs the new commits add, each with its size, and says to add generated output to `.gitignore` or remove the files before syncing. It reaches the user through the server's failed-export answer unchanged, and the CLI prints it as it does a failed sync-back today, with the session left running.

**Sync jobs follow.** `InspectSync` reports the two measures, and DL-101's gate 2 (`judgeSync`) sets `over_limit` on either, saying which one ("the commits add N MiB, over the 1 GiB a sync can take"; "the changed files are N MiB…"; "a.bin is 300 MiB, over the 256 MiB one file may be"), so a `passed` sync job is one a current client can apply. The job's deliverable keeps `Size` as the larger of the two measures.

**The seed keeps 16 MiB** (`MaxSyncBundleBytes`), carried in the create request as today. Its refusal says what would help, per case:

- unpushed commits on a remote of a configured platform: push the branch first (as today);
- a checkout with no remote, sending its whole history: add a remote on a configured forge and push;
- a remote whose host matches no configured platform, or whose platform has no credential: configure the platform or add its credential, after which only the unpushed commits are sent;
- a transcript resume's `sync_bundle` (DL-098) over the bound: the same wording as the launch that would have sent it.

## Rationale

The user meets whichever bound is checked first, so the first check must be the one that decides. Measuring the landing's own quantities in the sandbox, before packing, means the transfer never refuses what the landing would accept, and never carries for half an hour what the landing will then refuse; it also avoids compressing a tree only to throw it away. 1 GiB and 256 MiB are DL-126's numbers for what may reach the user's disk, now applied to both commits and uncommitted files alike.

The seed stays bounded because it waits in the server's memory through a launch and in Postgres for a queued job (DL-100); streaming it needs a launch phase of its own. It fails at launch, before any work, with a remedy, which is the cheaper place to fail.

## Consequences

- A sandbox's `/tmp` holds up to the packed export while it streams, and the user's machine needs room for the spool, the fetched objects and the unpacked files at once (DL-178).
- A sync job whose changes are between 32 MiB and 1 GiB now passes gate 2 where it failed before, and needs a current CLI to apply (the JSON route's refusal says so).
- The script's measuring is cheap but not free: a `git status` and a `cat-file --batch-check` over the new objects, which the `inspect` mode already ran.
- DL-130's `maxExportOutput` stays for the JSON routes only.
