## Context

A hosted deployment serves many people. If the server held one Forgejo token, one GitHub credential and one set of model keys, every user would push as the administrator with the administrator's keys. An organisation typically installs one GitHub App and wants every agent session to use it, since asking each user to register an App is unreasonable. A solo user or a contractor may have only their own personal access token. Both levels have to be possible, and a session has to act with the same identity for its whole life.

Forgejo, Gitea and GitLab have nothing like an App, so their two levels are a shared account's token and the user's own token (DL-041).

## Decision

### Two tiers per platform

Every credential a sandbox receives for a platform resolves from one of two tiers. On the wire they are `user` and `org`; the CLI config calls them `personal` and `shared`.

| Platform | Organisation (the deployment) | Personal (the user's own) |
|---|---|---|
| GitHub | an App: `SPOV_GITHUB_APP_ID` with `SPOV_GITHUB_APP_PRIVATE_KEY`, or one an admin stored in Settings; the installation is found from the platform's account | a fine-grained personal access token (a classic one is accepted), used by `git.GitHubPAT` |
| Forgejo, Gitea, GitLab (per host) | a shared account's token in `SPOV_PLATFORM_TOKEN_<NAME>`, named after the platform | the user's own token |
| Model providers | the provider variables in the deployment's environment | the same variable names, stored per user, overriding per provider |

One configured platform entry serves both tiers. On GitHub the credential's shape tells them apart: a JSON object is an App, and a token with a GitHub prefix is a personal token (`LooksLikeGitHubPAT`). Resolution runs on the server, per user and per platform, at launch and when repositories are listed. A user stores their own credential with `spov credentials add` or in Settings (DL-008 covers sealing, rotation and the credential routes). A local server has one user whose tier is the keyring and the environment, always present.

A personal GitHub token is held as-is: spov did not mint it, cannot narrow it and cannot revoke it, so `TokenScope` reports `PerRepo: false`. The sandbox proxy still narrows what it may do (DL-034).

### Resolution and the recorded tier

A launch picks one tier per platform.

1. The CLI's user config may set `platforms[].prefer: personal | shared`. This is read from the user file only, since a project file may not set `platforms`. `spov fly` and `spov jobs create` send it as `credential_preference: {<platform>: "shared"}`. The browser sends none, which means personal-first.
2. The server tries the preferred tier and uses the other only when the preferred one holds no credential. With neither, the platform is listed as unavailable with the reason and how to add a credential. When the other tier is used, the launch prints no note; the session page's credential tag ("the organisation's" or "your own", `credentialTag`) says which was used.
3. The preference is stored on the session's request, so a queued job resolves it when it launches. The tier chosen is stored on each `store.SessionCredential` (`withTiers`). The credential itself is never stored on the session.
4. Token renewal, sidecar recreation, adoption of a sandbox after a restart, the git-access check and gate 2 resolve the recorded tier only (`TierPolicy.Only`, built by `policyOf`), re-authorised against current policy (`mayReachAll`, the allowlist). If the recorded tier's credential is gone, the step fails as unavailable: renewal stops and gate 2 reports the check unverified. It never substitutes the other tier. A credential row with no recorded tier resolves personal-first. `Deps.UserForge` takes a `TierPolicy` (`Prefer` from the request, `Only` from the record), and gate 2's `jobs.ForgeFor` takes the job's session (DL-050, DL-021).

An unreadable credential in a tier ends resolution with an error; it never falls through to the other tier. A stored personal credential that cannot be decrypted resolves to `TierNone` with a message to store it again, because falling through would hide a lost key behind the deployment's access. An unreadable personal provider key is withheld rather than replaced by the deployment's, since that would bill the deployment for work meant for the user's own account.

Only unreadability is detected at resolution. A readable credential that does not work is used and fails later: a revoked App key fails when the token is minted, and a revoked personal token fails at clone. The tier decides which repositories and which identity a sandbox acts with. Switching it silently mid-life could push as someone else or verify against a set the launch never had.

With the App set in the environment, storing or removing one in Settings is refused with a 409; the two never apply to the same platform.

### The organisation's App in the database

An admin can store the shared GitHub App from Settings instead of the environment. The `org_credentials` table (hosted only) holds, per organisation and platform, the App ID, the account whose installation is used and the installation ID in the clear, and the private key sealed with AES-GCM under `SPOV_CREDENTIAL_KEY` (`_OLD` during rotation). Its AAD is `auth.OrgCredentialAAD`, which starts with a byte no organisation ID starts with, so a user's row can never be opened as an organisation's or the reverse. Losing the key makes the stored App unrecoverable, and an admin stores it again. A local server keeps keyring credentials and has no such table.

- **Verified before storing.** `git.GitHub.Check` signs an App JWT, finds the account's installation, reads its permissions, and mints, uses and revokes one token to list the repositories it reaches. A failing step is refused with the step named and nothing is stored. The check records the installation ID so later mints skip discovery.
- **The environment wins.** When `SPOV_GITHUB_APP_ID` and `SPOV_GITHUB_APP_PRIVATE_KEY` are both set, or the platform's `SPOV_PLATFORM_TOKEN_<NAME>` is, the organisation tier is the environment's. One variable of the pair alone is no App and is ignored. A stored App is then not read, and the API refuses changes with a 409 saying so. The two are never merged, so there is one answer to which App is in use.
- **A short cache.** `server.OrgApps` keeps each decrypted App, or the fact that there is none, for at most 30 seconds per organisation and platform on each replica. The replica that changed it drops its copy at once. `hostedCredentials.orgToken` reads the environment, then the stored row. A row that cannot be opened ends resolution (the launch is told to ask an admin) and the admin page shows it with Replace and Remove; a store that cannot answer says so.
- **Rotation and removal apply from the next mint.** A running session keeps its token until it expires, at most an hour. Its renewal mints from the new App and fails visibly if that App does not reach the session's repositories. Removing the App makes the organisation tier absent from then on.

### The admin routes and the Organisation section

`GET /api/v1/org/github`, `PUT /api/v1/org/github/{platform}` and `DELETE /api/v1/org/github/{platform}` (`registerOrgGitHub`) are admin-only.

- `GET` returns the status and never the key. Each App is checked live and the result is kept for a minute (`OrgCheckTTL`). The status gives the source (`environment`, `stored` or none), the App ID, account and installation ID, the permissions the installation grants and which of those sandboxes ask for (`git.SandboxPermissions`) it lacks, the repository count and the first 20 names, when it was last verified, and who stored it and when. The response also carries the organisation's latest ten `admin_events`, which the Settings section lists. It answers whether the App works and what it reaches without exposing the secret.
- `PUT {app_id, private_key, account?}` checks and stores. The account defaults to the platform's configured account; with neither, the request is refused. `DELETE` removes. Both write the row and an `admin_events` row (`github_app.stored`, `github_app.removed`: who, what and when, with the App ID and account, never the key) in one transaction, after taking the organisation's admin lock and re-checking admin (`requireLiveAdmin`). The audit trail answers who changed it without a log line that could carry the secret.
- A platform that is not configured answers 404, as does `DELETE` when no App is stored; the environment setting the App answers 409 to `PUT` and `DELETE`; and a local server answers 501. A GitHub platform is configured for one account, so there is one installation per platform and no setup flow beyond this form.

The Organisation section on `/settings` appears only for an admin. It shows the status, a form to store or replace (the key field is write-only and cleared after submit), and Remove behind a second press (`ConfirmAct`). When the environment sets the App it shows the status and where it is configured, with no form. Its logic is in `web/src/lib/orgsettings.ts`; the component holds markup (DL-062).

### The repository listing names the tier

`GET /api/v1/repos` reads each tier a caller has on each platform through that tier's own credential (`Deps.UserRepos`, `hostedCredentials.reposByTier`) and marks each repository with the tiers that reach it (`via: ["user", "org"]`). It also reports each platform's tier for the caller's launch: personal-first for the browser, or under the preference the CLI sends (`?prefer_shared=<platforms>`). A platform neither tier has a credential for says how to add one. A listing failure in one tier is a warning naming that tier and never hides the other tier's repositories.

- The browser's picker shows a repository its tier cannot reach disabled, with the reason, for example that only the organisation's credential reaches it and a browser launch uses your own (`repoUnreachable`). A platform with no credential for the browser's launch gives that platform's reason.
- The CLI's picker keeps only what its launch's tier reaches and says per platform how many it left out and which `prefer` would reach them (`reachableFromHere`; DL-028).
- The session page names the tier in each platform's credential tag.

A reader should not find out at clone time that the credential in use cannot reach a repository. The cost is up to two forge calls per platform, made on demand and never polled.

### A fine-grained token's public repositories

A fine-grained GitHub token can read any public repository, so `/user/repos` lists them, and a launch on one clones and then fails at push. A public repository that the personal tier reaches through a fine-grained token is therefore listed and marked `RepoView.maybe_read_only`. A private repository in that listing was granted to the token and is not marked. A classic token and the organisation's App mark nothing.

The browser shows a marked repository with the note "Public: your token can read it, and can push only if you gave it this repository" (`repoReadNote`). The CLI shows "public, push only if your token was given it" (`repoDetail`). Both show it only when the launch resolves to the personal tier: through the organisation's credential the mark is dropped, since the mark is about the personal token, and the organisation's credential reaches the repository with its own access. The mark is a hedge, not a check. GitHub's `permissions` object on `/user/repos` and on `/repos/{owner}/{repo}` is the account's role, not the token's grant, so nothing in the API says which repositories the token may push to. spov does not probe write access: GitHub offers no read-only probe and a trial push writes to the repository. Hiding public repositories would hide ones the person did grant; listing them unmarked offers launches that end in a failed push. The mark comes from the token's prefix (`IsFineGrainedGitHubPAT`).

### Who may use what

Under the organisation's App, any user on the allowlist can start a session on any repository the App is installed on. The allowlist (DL-007) and the App's installation scope together are the boundary, and there are no per-repository grants. A shared Forgejo or Gitea token is managed by a person and cannot be revoked by spov, so rotating it is an admin's job.

`docs/github-access.md` is the reader's account. It keeps four things apart: signing in to spov, which gives no repository access; the organisation's App and its lifecycle; the allowlist; and a sandbox's git access (DL-043). `deploy/README.md` links to it and says how to move from the environment to stored configuration.

## Rationale

An organisation installs one App by nature, and the personal tier keeps a solo user or a contractor with their own token working. Personal-first is the least surprising default: if a person gave spov their token, their sessions use it. The CLI's `prefer: shared` is for a person who wants the organisation's identity regardless.

Recording the tier means a long-lived session cannot change identity under its user. Keeping the environment authoritative when it sets an App gives one answer to which App is in use. A separate table and AAD keep the shared secret out of every per-user code path, and verifying first means a stored App is one that worked.

## Measurements

A fine-grained GitHub token granted a few private repositories also listed many public ones: every public repository its account can read. The `permissions` object GitHub returned for them reported the account's role, not the token's grant. This was measured against the live GitHub API during the combined-scenario run (DL-022).

## Consequences

- Hosted credential resolution is one `hostedCredentials` assembly behind the `server.Credentials` interface; a local server's is the keyring and environment.
- `spov credentials` says which platforms prefer the shared credential.
- The listing for a fine-grained token stays long; marked repositories are told apart, not removed.
- `TestARecordedTierIsTheOnlyOne` and `TestALaunchRecordsItsTierAndGateTwoFollowsIt` guard the recorded tier. `TestAnAdminStoresACheckedApp` and `TestAStoredAppOpensOnlyWhereItWasSealed` guard the stored App. `TestAFineGrainedTokensPublicRepositoriesAreMarked` guards the mark.

## Known gaps

- The mark on a fine-grained token's public repositories is not applied to an organisation-tier fine-grained token set in the environment (`SPOV_PLATFORM_TOKEN_<NAME>`), because the merged listing cannot say which tier's token caused it. It is not applied to a local server's listing either, which has one tier and reads it through the forge.
- A readable but non-working credential is not detected at resolution, only when it is first used.
- The launch's reach check on a personal token (DL-043) asks about visibility, not write access.
