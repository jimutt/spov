## Context

spov clones from, pushes to and opens change requests on four kinds of forge: GitHub, Forgejo, Gitea and GitLab. They differ in how a person gives spov access. A Forgejo, Gitea or GitLab user creates a token and spov stores it. Forgejo's `POST /users/{u}/tokens` accepts only password Basic auth (plus `X-FORGEJO-OTP` under two-factor authentication), so spov cannot mint a token from another token without holding the account password, which is a far larger trust ask than a scoped token. GitHub is different: a GitHub App lets spov mint short-lived installation tokens, narrowed to the repositories of one session, and revoke them. GitHub fine-grained personal access tokens cannot be created through the API.

Repositories also differ in shape. On every forge but GitLab a repository is `owner/name`; GitLab projects live in nested groups (`group/sub/project`) and must not be flattened.

## Decision

### One interface, two credential flows

`git.Platform` is the one interface behind every forge. Besides `ListRepos`, `IssueSandboxToken`, `TokenScope` and `FindPullRequest` it carries `Name`, `Host` and `Kind`, and platforms may add the optional capabilities `RepoChecker` (can this credential see a repository), `Inspect` (describe the token) and, on GitLab, `ProjectIDs`. The difference between the flows is carried by two things only. `Token.Revoke` is optional, nil for a token spov did not create. `Platform.TokenScope` says what a token grants: for a stored token (Forgejo, Gitea, GitLab) it is an unverified description of what the user was asked to configure, because spov cannot read a token's scoping back through the API; for a GitHub App it is `PerRepo: true`, a verified property of what spov itself requested.

- **Forgejo, Gitea and GitLab** use a stored token. `IssueSandboxToken` returns the stored secret unchanged and refuses an empty repository selection. The git username is the configured account for Forgejo and Gitea and `oauth2` for GitLab, and `Revoke` is nil: the token belongs to the user, outlives the sandbox, and is rotated or narrowed on the forge. Forgejo supports repository scoping at token creation (`CreateAccessTokenOption` takes `repositories: [{owner, name}]`), so the user is asked to create the token with "Specific repositories", `write:repository` and `write:issue`. On GitLab it is a personal access token with the `api` scope.
- **GitHub** uses an App. `git.GitHub` mints an installation token narrowed to the session's repositories (a `repositories` array of bare names, plus a `permissions` object capped at what the installation was granted) and revokes it at teardown through `Token.Revoke`. How the personal-token tier and the organisation's App are chosen is DL-042; how a sandbox's token is limited to the session's repositories or widened is DL-043; how it is renewed while the session is in use is DL-021. Where the proxy sidecar runs, it holds the token and the sandbox holds a placeholder (DL-034).

### Clones and workspace directories

`git.Bootstrap` returns each repository's clone with a credential-free HTTPS URL; a non-https clone URL is refused. The sandbox authenticates through a per-host git credential store (`writeGitCredentials`). An embedded token would be printed by `git remote -v` to anything running in the sandbox and would stop `tea` matching a repository to its login.

A repository is cloned to `/workspace/<name>`. When two repositories share a name, `uniqueDir` falls back to `<owner>-<name>` and then `<platform>-<owner>-<name>`, with slashes in a namespace replaced by `-`. Owner and name come from a remote API and become directory names, so `CheckRepoPath` and a directory check run where they are turned into one: no separators, traversal components, leading dashes, whitespace or control characters.

`Bootstrap` returns its revoke function even when it fails partway, so a platform that mints can always release what it created. Revocation runs at most once however many times it is called, because a deferred revoke plus an explicit one on an error path is normal and a real platform rejects a second attempt. `RedactURL` removes the credential from one URL structurally with `net/url`; `RedactAll` scrubs free text such as git output, where a remote is often named more than once and a single positional cut would leave the second credential exposed.

### The kinds

A platform's kind is one of `github`, `forgejo`, `gitea` and `gitlab`, and the string is the same in the config (`config.PlatformKind`), `git.Platform.Kind()`, the proxy, `opencode.CLIForKind` and the API, whose forge fields document all four. `git.Kinds` lists them.

- `forgejo` and `gitea` share one adapter (the Forgejo SDK, which talks to both), `tea` and one proxy policy. They differ in name, credential key and tested status; neither is the base of the other. `kind: forgejo` pointed at a Gitea server works and is only misnamed.
- `gitlab` is an adapter over GitLab's REST API v4 written on `net/http`; the handful of calls it makes do not justify the official client's size.
- `base_url` defaults to github.com for `github` and gitlab.com for `gitlab`; `forgejo` and `gitea` require it.
- Hosted credential keys are `github`, `forgejo:<host>`, `gitea:<host>` and `gitlab:<host>`. `CanonicalPlatform` accepts exactly these and provider keys.
- Every place that branches on a kind uses an exhaustive switch where an unknown kind gets nothing: no credential, no CLI, no policy. Nothing falls through to GitHub's behaviour. The kinds live in `internal/git`; `credproxy` cannot import `git` and keeps its own constants.

### Repository paths

A `git.Repo` keeps two fields, `{Owner, Name}`, and `Owner` is the whole namespace path. `Owner + "/" + Name` is the slug used wherever a repository is named or matched: the CLI flag, the plugin's `spov_pull_request`, the proxy's repository list, deliverable keys and the web. Only `gitlab` accepts a slash in `Owner`; every other kind needs exactly one segment, and every kind refuses empty, `.` and `..` segments.

- A path is split at its last slash (`git.SplitPath`), which is unambiguous because a project name has no slash. Cutting at the first slash is wrong for a nested namespace.
- Every segment uses letters, digits, `.`, `_` and `-`, and may not start with `-` (`git.CheckRepoPath`). The config, `--repo` (`parseRepoFlag`), the server's selection and the bootstrap all check it.
- Two fields keep every store row, API view and test shape: `Owner` already holds a string in `sessions.request` and `job_deliverables`, so no schema change was needed. `recordedPullRequests`, `uniqueDir`, `parseRepoFlag`, the clone base path and the proxy's git matcher all handle a nested owner.
- GitLab's numeric project IDs are not a repository's identity in spov. The proxy gets them from the launch (`git.ProjectIDs`); how it matches a nested path is DL-034.

### The GitHub App client

`git.GitHub` is a stdlib-only client with no JWT library and no SDK. An App JWT is RS256 over two base64url JSON objects, which `crypto/rsa`, `crypto/x509` and `encoding/json` produce directly. `appJWT` backdates `iat` by 60 seconds for clock drift and sets `exp` nine minutes ahead (GitHub rejects more than ten). Both PKCS#1 and PKCS#8 private keys parse, and a wrong key is rejected. `iss` may be the App ID or the client ID (GitHub recommends the client ID) and spov accepts whichever was stored.

The client uses these endpoints:

- Discovery, with the JWT: `GET /users/{u}/installation` and `/orgs/{o}/installation`, both tried because spov is not told whether the account is a user or an organisation. A platform needs a configured account or an installation ID. A 2xx response with no id counts as a miss, so an unexpected shape from the first endpoint does not stop the second being tried. A configured `installation_id` skips discovery. The result is cached in memory per process, not written back, and the cache lock is held across the lookup so concurrent callers do not each spend the same requests on GitHub's rate limit.
- `POST /app/installations/{id}/access_tokens` mints a token that lasts exactly one hour (not configurable). Mint-time narrowing takes a `repositories` array and a `permissions` object, both strict subsets of the installation's grants. spov sends only `repositories`, not `repository_ids`, and the permissions it asks for are `git.SandboxPermissions` capped at what the installation holds (read with the JWT from `GET /app/installations/{id}`).
- `DELETE /installation/token`, authenticated with the token itself, revokes it early.
- `GET /installation/repositories` needs the installation token and returns an object with a `repositories` array.
- Git over HTTPS needs the username `x-access-token`. GitHub has no refresh mechanism; the only remedy for expiry is minting again with the private key.

The credential is a JSON object holding the App ID or client ID, the private key and an optional installation ID (`ParseGitHubCredential`; its errors never quote the value). A local server's keyring holds it under `platform:<name>`; a hosted server takes it from the environment or the organisation's stored App (DL-042).

### Why the App private key stays out of the sandbox

The agent can read every secret its sandbox holds, so the damage a leak does is bounded by the token's scope. A one-hour token narrowed to the session's repositories is a bounded loss. The App private key is not: it grants permanent, self-renewing access to every repository the App is installed on and cannot be revoked by ending the session. It stays on the server, and the sidecar holds only the minted token. Two other designs were rejected: a credential helper that calls back to the user's machine (there is no channel, and one would have to stay open for the session's life), and capping GitHub sessions at an hour. Expiry is what makes holding a token tolerable; the server re-mints while a session is in use (DL-021). At rest the private key is a more valuable secret than a Forgejo token and is sealed like every stored credential (DL-008).

### The credential check

`spov credentials add`, the Settings page and the server check a stored token before storing it, with `git.Inspect`. The check reads the token's own user, and on GitLab its scopes and expiry, and says which of three things it found.

- Forgejo and Gitea: `GET /api/v1/user` gives `verified_as`, and `/api/v1/version` gives the server version shown on the line after `spov credentials add`. A token limited to specific repositories may lack `read:user`, so a 403 there is not a refusal: `verified_as` falls back to the configured `account` and the repository listing decides.
- GitLab: `GET /api/v4/personal_access_tokens/self` gives scopes and expiry. It is read first because `/user` needs a read scope; then `/user` gives the user and `/version` the version. A token without the `api` scope is refused with the scopes it has, because `glab` and merge requests need it.
- In the token check only, a 401 is a bad or expired token (`ErrBadToken`), a 403 a missing permission (`ErrMissingPermission`) and a 404 an unsupported server (`ErrUnsupportedServer`), each with the forge's own message. Elsewhere, in the listing and in gate 2, a 404 is a missing project. There is no version table: a GitLab older than 15.5 has no `personal_access_tokens/self` and answers that 404.
- The check runs before the repository listing, so a token missing a scope is refused for that rather than for an empty listing. A token that then reaches no repositories is refused too, with a note to scope it to the ones wanted.
- The user, scopes and expiry are stored with the credential (`user_credentials.scopes` and `expires_at`, migration `00026_credential_facts`) and shown where it is listed: `spov credentials` on a hosted server, the line after `spov credentials add`, and Settings. A local server's keyring holds only the secret, so locally the facts appear only on the add line. spov never renews or narrows a stored token. A GitHub PAT keeps its own check (DL-042).

### Which forges are tested

spov is tested end to end on github.com, Codefloe (Forgejo) and gitlab.com (GitLab), and `docs/forges.md` is the reader's page: the kinds, what each needs from a token, what the proxy allows, and the tested matrix with each forge's status and measured versions. End to end means the credential check, repository listing and selection, clone, push, the forge CLI opening a change request, gate 2 (DL-050) and the proxy's refusals, in a real sandbox. Codeberg, gitea.com, self-hosted Forgejo and Gitea, and self-managed GitLab are documented as expected to work and untested. A claim of support rests on a run, and the matrix records which runs happened so the claim can grow without being re-argued.

### The Forgejo family on real servers

The suite runs real Forgejo and Gitea servers, because a fake would test spov against a guess of the API. `scripts/forge-test-server.sh start forgejo|gitea <dir>` starts Forgejo 17.0.1 or Gitea 28.3.0 on 127.0.0.1 over HTTPS with a throwaway certificate and SQLite, and makes an admin user and token with the forge's own command line. A launch clones only over https, so the forge must serve TLS. With Docker the script runs the release's official image; without it (the CI runner has none) it runs the release binary, checked against a sha256 committed in the script. It writes an env file the suite reads (`SPOV_TEST_FORGEJO_ENV`, `SPOV_TEST_GITEA_ENV`).

`TestScenario4` (`internal/cli`, in CI's Postgres job when the env files are set) runs once per forge it is given, with no external account needed. Through the admin's API it makes a member with their own token, two private repositories of theirs (one with an open pull request) and another user's private repository. Against the scenario server with that forge configured it then asserts:

- a token the forge refuses is not stored, and the member's is, verified as them;
- the repository listing shows their two repositories and not the other user's;
- a launch on the other user's repository fails before any sandbox exists (DL-043);
- gate 2 asking the forge verifies the open pull request with its real number and URL and marks a branch without one missing;
- no secret reaches a response or the log.

The same harness runs the rest of the combined scenarios (DL-022). The real-sandbox round for the family (clone, push, `tea` and the proxy's refusals) is `TestIntegrationScenarioForgejo`, against a Forgejo whose address a sandbox can reach.

## Rationale

A kind names the product a person configured, which is also the product whose API and CLI spov must speak. Sharing the Forgejo adapter with Gitea reflects today's APIs, checked by the matrix; it is not a promise. The exhaustive switch stops a new kind inheriting another's credential rules by accident, which the proxy's `allows` would do if it sent every non-Forgejo kind down the GitHub path.

One interface with two flows keeps the real asymmetry visible instead of hiding it: a stored token is user-managed, repository-scoped by the user, and unrevocable by spov, while an App token is minted by spov, narrowed, short-lived and revocable. The interface needed no change to take the second flow.

The App client avoids `go-github` and `ghinstallation`: go-github ships a new major version every three to four weeks, each a distinct import path, and ghinstallation pins its own go-github major, so using both compiles two copies of the SDK into the binary. For a JWT and a handful of endpoints that is a poor trade, and it is the reasoning that keeps the Modal SDK behind `internal/sandbox`.

Keeping `{Owner, Name}` and storing the full namespace in `Owner` is what GitLab and the user actually name, while every row and view keeps its shape. Refusing a nested owner on the other kinds keeps their two-segment API calls correct. The credential check exists because a person adding a token wants to know that it works and for whom, and a token that will stop in a week should say so before a job fails on it.

## Measurements

### Forgejo token behaviour (Forgejo 16.0.3 on Codefloe)

- `CreateAccessTokenOption` takes `repositories: [{owner, name}]`, so per-repository scoping exists. The Go SDK `forgejo/v3` v3.0.0 does not expose the field.
- `POST /users/{u}/tokens` accepts only password Basic auth. Codefloe answered "auth method not allowed" to a token header and to a token used as the password. Minting needs the account password, so spov does not mint.
- spov cannot read a token's scoping back through the API, so there is nothing to revoke and nothing to verify.

### GitHub App against a real App (integration tests)

A real GitHub App installed on an account with many repositories:

- A token minted for one repository saw 1 of the installation's many repositories, so `TokenScope`'s `PerRepo: true` is a verified fact.
- After `DELETE /installation/token` the token answers `401 Bad credentials`.
- The stdlib-signed RS256 JWT with backdated `iat` and nine-minute `exp` is accepted for listing, minting and revoking.
- Minting takes about 250 to 860 ms. A configured `installation_id` and discovery both work.
- The stored credential file the README describes parses, mints a narrowed token, and lets git clone a private repository through the credential store, with `git remote -v` showing a credential-free URL.

Re-run: `go test -tags integration ./internal/git/ -run 'TestIntegrationGitHub'`, with `SPOV_TEST_GITHUB_APP_ID`, `SPOV_TEST_GITHUB_KEY_FILE` and `SPOV_TEST_GITHUB_ACCOUNT` set.

### Forgejo and Gitea on real servers

- Both accept any username with a token as the password, on the API and over git. The username is ignored. The forge authenticates by the token alone, so a shared `account` name on a Forgejo platform grants nothing; each user's access is exactly their own token's scope.
- Both create and list pull requests with a `write:repository` token. `tea pr create` also reads the repository's labels, which need the issue scope, so `write:repository` alone cannot open a pull request with `tea` and `write:repository` plus `write:issue` can. That is the recommended scope in `docs/forges.md`, the Settings page (`forgeTokenAdvice`) and the forge's scope text.
- Versions in use: Forgejo 17.0.1 and Gitea 28.3.0. The real-sandbox round ran against Forgejo 17.0.1 in a Modal sandbox behind a TLS tunnel.

Re-run: `scripts/forge-test-server.sh start forgejo <dir>` (and `gitea`), then `SPOV_TEST_FORGEJO_ENV=<dir>/env SPOV_TEST_GITEA_ENV=<dir>/env SPOV_TEST_DATABASE_URL=... go test -tags integration ./internal/cli/ -run TestScenario4`. The sandbox round is `go test -tags integration ./internal/sandbox/ -run TestIntegrationScenarioForgejo`.

### GitLab on gitlab.com

- S-GL1: `glab` 1.120.0 and git through the real credential proxy against gitlab.com passed (2026-10-24). The measured calls fit the proxy's allowlist, and members, merge, approve, delete and an unselected project went without the credential. It runs locally and needs no Modal. Re-run: `SPOV_TEST_GLAB=/path/to/glab go test -tags integration ./internal/credproxy/ -run SGL1 -v`.
- S-GL2: a `pr` job on gitlab.com in a sandbox, against a subgroup project, verified merge request !1 (2026-10-24). It has no test function of its own, so no re-run command is recorded.

## Consequences

- Adding a fifth forge means a new case in every switch, and the compiler does not enforce it. `TestEveryKindIsDecidedWhereTheCLIBranchesOnIt` checks the CLI and server sites for each of `git.Kinds`; `TestGiteaSharesForgejosPolicyAndAnUnknownKindGetsNothing` checks the proxy's side, and `TestARecordedRequestInASubgroupKeepsItsWholePath` guards the last-slash split.
- A stored Forgejo, Gitea or GitLab token is long-lived and user-managed. Rotating it or changing which repositories it reaches happens on the forge, and a new token has to be stored. In exchange spov never handles an account password and has no minting step to fail.
- A GitHub App needs creating once, which is more friction than a pasted token and a better security position.
- A bump of either test forge's version changes the script's version and both of its checksums. The CI job downloads the two binaries on each run.
- A self-managed GitLab on a private network is unreachable through the proxy, which dials public addresses only.

## Known gaps

- Two GitHub API behaviours are undocumented and unverified: whether sending both `repositories` and `repository_ids` is an error (spov sends only `repositories`), and whether installation tokens also expire from inactivity. Neither affects the design.
- The recommended Forgejo and Gitea scopes are advice. spov cannot read a stored token's scoping back, so it cannot check that the user followed it.
- The GitLab round on gitlab.com has no re-run command for S-GL2.
- Codeberg, gitea.com, self-hosted Forgejo and Gitea, and self-managed GitLab are untested.
