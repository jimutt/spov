## Context

A sandbox is given git credentials but, unless spov sets one, no git identity. With `user.name` and `user.email` unset, git guesses an author from the machine (`root@<container hostname>`), and every commit and pull request made in a session is attributed to that guess instead of to the person who launched it.

The credential is not the identity. A GitHub App installation token authenticates as the App, so pushing works and the commit is still authored by whatever git decided. The failure is silent: the work lands and is misattributed.

## Decision

spov resolves a git author at launch and configures it in the sandbox. The entrypoint runs `git config --global user.name` and `git config --global user.email` (`writeGitIdentity`), and a half that is empty is not written.

### Resolution

`git.ResolveIdentity` layers an explicit identity over a list of fallbacks, field by field and in order. Configuring only an email does not discard a detected name. A fallback is consulted only while a field is still missing, so a source that costs a database read or a subprocess is not paid for once the answer is complete. Resolution happens in two places.

On the client (`Env.gitIdentity`, which the CLI runs because only it can read the user's git configuration), first match wins per field:

1. `--git-name` and `--git-email`;
2. `git.name` and `git.email` in the spov config, or `SPOV_GIT_NAME` and `SPOV_GIT_EMAIL`;
3. the local `git config --get user.name` and `user.email`.

The result travels in the launch request. On the server (`Service.launch`), the request's identity is the explicit one and the fallbacks are, in order:

1. the launching user's profile, `users.git_name` and `users.git_email`, which is filled from the sign-in identity when the user first signs in (the name falls back to the login when the provider gives none) and edited on the Settings page through `PATCH /api/v1/me`;
2. the server's own configured `git.name` and `git.email`.

Name and email are resolved independently, so half an identity in the profile gives a mixed author: the profile's name with the server's email, say. Having one half is a real configuration, and half an identity is better than none, since git needs both only at commit time. A browser launch carries no client identity, so it takes the profile. A CLI launch carries what the client resolved, and the profile fills only the fields the client could not. A store that cannot answer the profile read is not a launch failure; the identity falls through to the server's configuration.

### Reading the local identity

`LocalIdentityIn` runs `git config --get` and does not parse `~/.gitconfig`. git resolves system, global, per-worktree and `includeIf` rules in a precedence order spov should not reimplement; a naive file read would give the wrong answer to anyone who splits work and personal identities by directory. The command runs in spov's working directory, which decides whether an `includeIf.gitdir` rule applies. Since `gitdir` matches a repository's location, such a split takes effect only when spov is launched from inside a repository; from a bare directory the unconditional identity is used, as git itself would.

Exit status 1 means the key is unset and is the ordinary case. Exit status 128 means git ran and objected, typically a malformed config file. That is reported with git's own message, which names the file and line, and is never read as "no identity", since that would send the user to set a value in the very file git refuses to read. A machine with no `git` in `PATH` yields no identity without an error.

### A missing identity warns

If name or email is still empty after the client's resolution, `spov fly` and `spov jobs create` warn (`identityWarning`), naming only what is missing and the three ways to set it: `git config --global`, the `git.name` and `git.email` config keys, or `--git-name` and `--git-email`. The launch proceeds. The warning reads only what the client resolved, so on a server whose profile or configuration supplies the missing half it can appear although the sandbox gets a complete author. A `git` that fails on a malformed config is also a deferred warning at launch, not an error. Git will refuse to commit until an identity exists, but that refusal belongs in the sandbox where it can be fixed, and a launch that refuses to start would take away read-only sessions. `spov config show` includes the git section only when a name, an email or `allow_all` is configured (`shownGit`), so it does not imply an identity spov does not have.

## Rationale

Misattribution is silent: nothing fails, so nobody notices until a commit shows up authored by `root@<container hostname>`. Layering flags over config over local detection matches how the rest of spov resolves settings, so there is nothing new to learn, and detection means it works with no setup at all, which was the broken case. Shelling out to `git` is the only way to honour `includeIf`. Warning rather than failing keeps a sandbox that cannot commit launchable, and that is still useful.

In hosted mode the profile rung makes commits authored as the human who launched the session, whichever credential pushes them. The server's own configured identity is the last resort, so a hosted deployment does not author everything as one administrator.

## Consequences

- Commits from a sandbox are attributed to the person who launched it, which is what a reviewer looking at the history expects.
- The identity is written into the sandbox, so an email address the user keeps out of public commits reaches a remote machine. It is their own git identity and would appear in any commit they pushed, and the config keys let them use a different one, a noreply address for instance.
- A machine without `git` loses auto-detection. That degrades to the warning, and the config keys still work.
- The identity is fixed for the session. A session mixing repositories that want different identities needs `git config user.email` inside the sandbox, as it would locally.
- The guards are `TestResolveIdentityLayersHalvesIndependently`, `TestResolveIdentitySkipsDetectionWhenComplete`, `TestLocalIdentityReportsABrokenConfig`, `TestLocalIdentityUnsetIsNotAnError`, `TestLocalIdentityInHonoursTheDirectory`, `TestGitIdentityPrecedence`, `TestServerIdentityFillsWhatTheClientLacks`, `TestEntrypointWritesTheGitIdentity` and `TestEntrypointOmitsAnEmptyIdentity`.
