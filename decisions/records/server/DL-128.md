## Context

DL-007's allowlist is keyed on an e-mail address, matched against the GitHub account's primary, verified address. That address is often a personal one the administrator does not know: they add `bob@company.com`, Bob is refused, and neither of them sees why until Bob reads the refusal page. DL-007 also lists as a gap that a user whose primary address changes at GitHub becomes a new user, losing their credentials, sessions and settings.

GitHub is the only sign-in, so the natural name for a person is their GitHub account. A login can be renamed, and a released name can be registered by somebody else, so a login alone is not an identity; GitHub's numeric account ID is. A mistyped login is also more dangerous than a mistyped address: it most likely names another real person.

## Decision

This amends DL-007. Everything it says that is not restated here stands: the cache and its refresh, the admin API's guards, the seed's once-only rule, and the allowlist as the only source of admin rights.

### Two kinds of entry

An allowlist entry is one of:

- **an address** (`bob@company.com`), as today: it admits the account whose primary, verified address it is, checked at each login;
- **a GitHub account**, written `@login` (`@bob`): it admits one GitHub account, identified by its numeric ID.

A person is allowed when any entry covers them, and is an administrator when any entry that covers them is an admin entry.

### An account entry is resolved when it is added

Adding `@bob` makes the server ask GitHub for that login (`GET /users/{login}`, unauthenticated) and store the account's numeric ID, its login as GitHub spells it, and its display name. The entry is keyed on the ID. There is no unresolved account entry:

- a login GitHub does not know is refused with a 422 that says so;
- an organisation account (GitHub's `type` is not `User`) is refused with a 422;
- GitHub unreachable or rate-limited is a 502 that says to try again, and nothing is stored.

When a user row already records that login's ID, the row is used and GitHub is not asked. The stored login and name are labels only, refreshed from the profile whenever that account signs in; a rename at GitHub never changes who the entry admits.

The response carries the resolved name and login, so the administrator sees whom they admitted.

### A user is a GitHub account

`auth.GitHubIdentity` gains the numeric `ID`, read from the `GET /user` the login already makes. `users` gains `github_id` (nullable, unique per organisation when set).

At sign-in the allowlist is asked with both the account's ID and its address. The user row is then found by `github_id`, and only when none has it, by address among rows with no `github_id` yet, which is how every user from before this change is bound at their next login. A row found by ID has its address updated to the current primary one. So:

- a user whose address changes keeps the same row whenever an entry still covers them;
- a user covered only by an address entry whose address changed is refused at their next login, as today, but returns to the same row once an administrator adds the new address or the account;
- an address already recorded on a row bound to a different GitHub account never moves and is never shared: a login that would need it is refused, with a page that says the address belongs to another account on this server.

The per-request check (`CookieAuthenticator`, `TokenAuthenticator`, the device flow's approval) asks the cached allowlist with the user's `github_id` and address, in place of the address alone.

### Storage and API

`allowlist_entries` gains `github_id`, `github_login` and `github_name`; an entry has an address or an ID, never both, and each is unique per organisation. The memory store follows.

- `PUT /api/v1/allowlist/{entry}` and `DELETE /api/v1/allowlist/{entry}` take an address or `@login` in the path. For an account entry that already exists, the path's login is matched against the stored one without asking GitHub, case-insensitively.
- `AllowlistEntryView` gains `kind` (`email` or `github`), `github_login`, `github_id` and `name`; `email` is empty on an account entry. It also gains `last_login_at`, set when a user the entry covers has signed in, which is what tells an administrator that an entry has never been used.
- Deleting an entry ends the browser sessions of each user it covered whom no other entry still covers (`Login.RevokeSessions` takes the users, not an address).
- The last-admin guard counts admin entries as before. "Your own entry" for the self-demotion and self-deletion guards is any entry that covers the caller, and the change is refused only when no other admin entry would still cover them.

### The seed file

A line of `SPOV_ALLOWLIST_FILE` may be `@login` or `@login admin`. Account lines are resolved at the import, before the transaction that writes them. One that cannot be resolved makes the file unusable, on DL-007's terms: fatal on a first boot, a warning on a re-seed.

### The refusal page

A refused login names both the account and the address (`@bob (bob@personal.example)`), so the person can tell an administrator either one.

## Rationale

- Resolving at add time means an entry never rests on a name that can change hands, and a typo is caught by the name shown back or by GitHub not knowing the login, before anyone is admitted.
- Keeping address entries exactly as they are needs no migration of meaning: a deployment that allows by company address keeps the rule "this address, verified by GitHub".
- Finding the user by account ID closes DL-007's "new address, new user" gap without making an address entry admit an address nobody allowed.
- The unauthenticated lookup needs no stored token and no new scope. Its limit of 60 an hour per address is far above how often anyone is added, and when it is hit the add is refused cleanly instead of being stored half-made.

## Consequences

- The server makes one outbound call to GitHub when an account entry is added, and at a first boot whose seed file names accounts.
- The sign-in keeps the scope `read:user user:email`; nothing new is asked of users.
- Allowing a whole organisation or team, and a second sign-in through OIDC, are not part of this. Both would be further entry kinds or identity sources on the same two tables.
- `docs/server.md` and `deploy/README.md` describe both kinds and recommend the account form.
