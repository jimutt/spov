## Context

DL-007's allowlist is keyed on an e-mail address, matched against the GitHub account's primary, verified address. That address is often a personal one the administrator does not know: they add `bob@company.com`, Bob is refused, and neither of them sees why until Bob reads the refusal page. DL-007 also lists as a gap that a user whose primary address changes at GitHub becomes a new user, losing their credentials, sessions and settings.

GitHub is the only sign-in, so the natural name for a person is their GitHub account. A login can be renamed, and a released name can be registered by somebody else, so a login alone is not an identity; GitHub's numeric account ID is. A mistyped login is also more dangerous than a mistyped address: it most likely names another real person.

## Decision

This amends DL-007 and DL-132. Everything they say that is not restated here stands: the cache and its refresh, the admin API's guards, the seed's once-only rule, the allowlist as the only source of admin rights, and every off-boarding step.

### Two kinds of entry

An allowlist entry is one of:

- **an address** (`bob@company.com`), as today: it admits the account whose primary, verified address it is, checked at each login;
- **a GitHub account**, written `@login` (`@bob`): it admits one GitHub account, identified by its numeric ID.

A person is allowed when any entry covers them, and is an administrator when any entry that covers them is an admin entry.

### An account entry is resolved when it is added

Adding `@bob` makes the server ask GitHub for that login and store the account's numeric ID, its login as GitHub spells it, and its display name. The entry is keyed on the ID. There is no unresolved account entry:

- a login GitHub does not know is refused with a 422 that says so ("GitHub knows no account named @bob");
- an organisation account (GitHub's `type` is not `User`) is refused with a 422;
- GitHub unreachable is a 502 that says to try again, and a 403 or 429 from GitHub (its rate limit) a 502 that says to try again later; nothing is stored either way.

The path's login is matched, case-insensitively and without asking GitHub, against the stored logins of the account entries; a PUT or DELETE of an existing entry by `@login` needs no lookup. A PUT that would create an entry always asks GitHub and stores the ID GitHub returns; a login recorded on a user row is never used to resolve a new entry, because a removed member who renamed away leaves the old login there and someone else may have registered it since. Two entries can carry the same login after a rename, because a label is refreshed only at its account's sign-in; an entry is then never guessed between, and the request is a 409 that names each entry by its `id:` form and display name and says to use that form. The stored login and name are labels only, refreshed from the profile whenever that account signs in; a rename at GitHub never changes who the entry admits.

The lookup is one unauthenticated `GET /users/{login}` on the API root the sign-in reads (`auth.GitHubUserAPI`; the login is github.com only). Before any request the login must have GitHub's shape: 1 to 39 letters, digits or single hyphens, not starting or ending with a hyphen (`auth.ParseGitHubLogin`), so its text can only name one path segment. The request has a 10 second deadline, follows no redirect to another scheme or host, and reads at most 64 KiB of the answer; an answer whose `id` or `login` is missing or out of shape is treated as GitHub unreachable. A display name has its control and format characters removed and is cut to 255 characters. The lookup is a seam, `Deps.GitHubAccounts` (an `auth.AccountLookup`): `spov serve` sets `auth.GitHubAccounts.Lookup`, every test a fake. Nothing caches or retries it, and it is not behind the repository listing's cache. An allowlist request is an ordinary API request under DL-133's per-user limits. The caller's own entries are read from the store before GitHub is asked, so a non-admin, another organisation's admin or a removed admin makes the server ask GitHub nothing.

The response carries the resolved name and login, so the administrator sees whom they admitted.

### A user is a GitHub account

`auth.GitHubIdentity` gains the numeric `ID`, read from the `GET /user` the login already makes. A `/user` answer without an ID, or whose login is not of a login's shape, fails the sign-in. `users` gains `github_id` (nullable, unique per organisation when set). It is written only when a row is created and by `UserStore.BindGithub`, which sets it on a row that has none and never changes it after; `UserStore.Update` keeps it.

At sign-in the allowlist is asked with both the account's ID and its address. The user row is then found by `github_id`, and only when none has it, by address among rows with no `github_id` yet, which is how every user from before this change is bound at their next login. That bind happens only when an address entry of the organisation covers the address at that moment, read from the store in the bind's own transaction under the allowlist's lock (`CountAdmins`), never from the cache: only an address entry admits a row by its address (DL-007), and an account entry alone would hand an earlier user's credentials, history and CLI tokens to whoever holds that address at GitHub now. Without one, the row is not bound and no second row is made for the address; the sign-in is refused with a page that says the address is recorded for an earlier user of this server, and that an administrator can connect the account to it by adding the address as an entry. A row found by ID has its address updated to the current primary one. So:

- a user whose address changes keeps the same row whenever an entry still covers them;
- a user covered only by an address entry whose address changed is refused at their next login, as today, but returns to the same row once an administrator adds the new address or the account;
- an address already recorded on another row (bound to a different GitHub account, or to no account while the signing-in account has a row of its own) never moves and is never shared: a login that would need it is refused, with a page that says the address belongs to another account on this server. The unique index on the address is the backstop for a race.

The per-request check (`CookieAuthenticator`, `TokenAuthenticator`, and through the cookie the device flow's approval) asks the cached allowlist with the user row's `github_id` and address, in place of the address alone, and the principal carries the `github_id`. A row with no `github_id` yet is covered only by an address entry: an account entry cannot admit it, and its CLI tokens keep working only while an address entry covers it. One browser sign-in binds it.

### Storage and API

`allowlist_entries` gains `github_id`, `github_login` and `github_name`; an entry has an address or an ID, never both, and each is unique per organisation (a check constraint and two partial unique indexes in place of the old primary key). The memory store follows.

- `PUT /api/v1/allowlist/{entry}` and `DELETE /api/v1/allowlist/{entry}` take an address, `@login`, or `id:<github_id>` in the path. A leading `@` is an account by login; `id:` and digits only an account entry by its numeric ID, anything else after `id:` being a 422; anything else must be an address. The `@` and the `:` may be percent-encoded. The `id:` form never asks GitHub: a PUT changes an existing entry and keeps its labels, and creating one by ID is a 422 that says to add it by `@login`. A client addresses an existing account entry by `id:`, since two entries can carry one stale login. An account entry is resolved before the transaction that writes it, so the allowlist's lock is never held across a call to GitHub.
- `AllowlistEntryView` gains `kind` (`email` or `github`), `github_login`, `github_id` and `name`; `email` is empty on an account entry. `name` is the account's display name, or on an address entry the name of the user it covers. It also gains `last_login_at`, the newest `users.last_login_at` among the users the entry covers, which tells an administrator that an entry has never been used, `you`, whether the entry covers the caller, and `also_covered_by`, the other entries (as a path names them) that cover a user this one covers, so a client can say that removing it ends nothing of theirs, and `unbound`, true on an address entry that covers a user row with no `github_id` yet. An account entry cannot admit such a row, so removing that address entry off-boards the person even when their account has an entry; the flag lets a client say so. An address entry covers the user row with that address, an account entry the row bound to its ID. `last_login_at` is already written at each completed browser sign-in; a device-flow approval needs a browser session, so it adds nothing, and no request writes it.
- Deleting an entry ends the browser sessions of each user it covered whom no other entry still covers (`Login.RevokeSessions` takes the users, not an address).
- The last-admin guard counts admin entries as before. "Your own entry" for the self-demotion and self-deletion guards is any entry that covers the caller, read from the store inside the transaction after `CountAdmins`, and the change is refused only when no other admin entry would still cover them. The caller's live admin check (`requireLiveAdmin`) passes when any of those entries is an admin entry.

### Off-boarding with two kinds of entry

DL-132 off-boards the person whose address a delete removes. With two kinds of entry, a delete off-boards each user the removed entry covered whom no other entry still covers, the same rule as ending browser sessions. Whether another entry covers them is decided inside the delete's transaction, after the entry is gone. A person covered by both an address entry and an account entry loses nothing when one is removed, and everything when the second goes. The audit row and the answer name the user as `@login (address)` when the row is bound to an account, else by the address.

The retry stays: a delete naming an address, `@login` or `id:<github_id>` that matches no entry, but matches a user row (by address, by the login recorded on a row with a `github_id`, or by that `github_id`) whom no entry covers, runs the off-boarding again and answers 204. It is a 404 ("is not on the allowlist") when it matches neither an entry nor such a user, and a 409 when the login is on more than one such row. A delete never off-boards a user an entry still covers, and reads only the caller's organisation.

### The seed file

A line of `SPOV_ALLOWLIST_FILE` may be `@login` or `@login admin`. Account lines are resolved at the import, before the transaction that writes them, by the same rule as the API: a line whose login exactly one existing entry carries (on a re-seed) is that entry, and any line that would create an entry asks GitHub, never a user row's login. All of a file's lookups share one deadline of 30 seconds, so an unreachable GitHub cannot hold a server at boot. One that cannot be resolved in that time, or that GitHub refuses, makes the file unusable, on DL-007's terms: fatal on a first boot, a warning on a re-seed. The admin count is read once before the file, so a deployment that has an administrator reads no file and asks GitHub nothing, and again under the lock inside the transaction, so a seeder that lost the race writes nothing. Two lines that resolve to one account take the widest privilege, as a repeated address does.

### The refusal page

A refused login names both the account and the address (`@bob (bob@personal.example)`), so the person can tell an administrator either one. The page is an `html/template`, and a login is printed only once it has a login's shape.

## Rationale

- Resolving at add time means an entry never rests on a name that can change hands, and a typo is caught by the name shown back or by GitHub not knowing the login, before anyone is admitted.
- Keeping address entries exactly as they are needs no migration of meaning: a deployment that allows by company address keeps the rule "this address, verified by GitHub".
- Finding the user by account ID closes DL-007's "new address, new user" gap without making an address entry admit an address nobody allowed.
- The unauthenticated lookup needs no stored token and no new scope. Its limit of 60 an hour per address is far above how often anyone is added, and when it is hit the add is refused cleanly instead of being stored half-made.
- Matching a path against stored labels first keeps a change of admin rights or a removal working while GitHub is down. The `id:` form reaches every entry whatever its label, which is what a client sends for a row it already shows.
- Binding an earlier row only under an address entry keeps DL-007's rule that an address is admitted only when it was allowed; the account entry admits the account, not whatever an earlier user left at that address.
- Off-boarding only those no other entry covers keeps "removing one of two entries" from ending the work of someone who is still allowed in.

## Consequences

- The server makes one outbound call to GitHub when an account entry is added, and at a first boot whose seed file names accounts.
- The sign-in keeps the scope `read:user user:email`; nothing new is asked of users.
- Allowing a whole organisation or team, and a second sign-in through OIDC, are not part of this. Both would be further entry kinds or identity sources on the same two tables.
- `docs/server.md`, `docs/security.md` and `deploy/README.md` describe both kinds and recommend the account form.
- A login label goes stale until its account signs in. Two stale labels on one login are a 409 for `@login`; the `id:` form reaches each.
- A user row from before this change is bound only to an account that signs in with its address as the verified primary one while an address entry allows that address. An account admitted by an account entry alone is refused until an administrator adds the address. An account that already has a row of its own and comes to hold that address is refused, and the address stays with the old row.
- Moving a person to the account form before they have signed in once since this change off-boards them when the address entry goes, since only the address entry admits their unbound row. The list marks such an entry (`unbound`), and the docs say to switch only after they have signed in.
