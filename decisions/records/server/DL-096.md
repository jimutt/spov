## Context

A sandbox's environment holds only what spov sets: `PATH`, `HOME`, the add-ons' variables (DL-033), the proxy's settings (DL-034), the routed credentials' placeholders (DL-072) and the provider keys (DL-036). A project often needs ordinary settings as well: `NODE_ENV`, a test database URL, a locale, a feature flag, an OpenCode log level. Nothing in the config, the CLI or the API sets one; the only way is a file committed to the repository, such as a `mise.toml` with an `[env]` section, which reaches only what mise runs.

Secrets already have their own mechanism: a routed credential, which the proxy sidecar holds and sets only where its route covers a request (DL-072). This decision is for values that are not secret.

## Decision

### Where the variables come from

- **`sandbox.env`**, a map of name to value, in the user file and in a project file (`.spov.yaml`). Maps merge key by key across the layers (DL-026), so a project file adds to or overrides the user file's entries one name at a time. A value that is the empty string is kept as an empty variable; there is no way to unset a lower layer's entry other than overriding it. There is no `SPOV_*` variable for it, as for every map and list key.
- **`--env KEY=VALUE`**, repeatable, on `spov fly` and `spov jobs create`. Each one sets that name over the merged config. A later `--env` for the same name wins. `KEY=` sets an empty value; an argument with no `=` is refused.
- **One setting for sessions and jobs.** A job gets `sandbox.env` as an interactive session does. There is no `job_env`: the variables describe how the project runs, not how far an unattended agent is trusted, which is what `job_credentials` (DL-075) and `job_git_access` (DL-043) are for.
- **The server's own `sandbox.env`** is the base: a request's variables are merged over it by name. A browser launch sends none (DL-061), so it gets the server's. On a local server the CLI and the server read the same user file, so the two agree.

### Where they go

- The CLI sends the merged map as `env` on `POST /api/v1/sessions` and `POST /api/v1/jobs`. The server checks it (DL-097) and refuses a request it does not accept with a 422 that names the variable and the rule.
- The resolved map, the server's base included, is stored on the session in the clear (`store.Session.Env`; a `sessions.env` column in Postgres, and the journal's session record on a local server, DL-091).
- It is set in the main container's plain environment (`sandbox.Spec.Env`, through `opencode.EnvConfig.User`), never the Modal Secret, which holds only credentials (DL-036). Every process sees it: the entrypoint, OpenCode and a `sandbox exec`. The proxy sidecar does not get it.
- A resumed session's new sandbox gets the stored map again, whether it boots a snapshot or a transcript resume (DL-087, DL-088). A recreated sidecar is unaffected.
- `SessionView.env` carries the map, so `spov ls --json` and every session endpoint show it, and a job's view shows its session's. The session page lists it in the sidebar behind an (i), as a fact about the session (DL-057).

### Not now

An account default in the browser's settings, and an `env` field on the browser's launch forms. Both can follow the default-model pattern later (DL-062, DL-061).

## Rationale

- A map that merges by name lets a project add its own variables without repeating the user's, which a replaced list would force.
- Storing and showing the values in the clear is honest about what they are. A value that should not be shown is a secret, and secrets go through a routed credential.
- Setting them in the plain environment, not the Secret, keeps them out of the Secret's redaction for the same reason, and keeps the Secret's contents exactly the credentials.

## Consequences

- A project file can set environment variables for every session on its repository, the way it can set add-ons. A repository someone else wrote can therefore set them too; DL-097's refused names keep it from changing how spov's own setup, OpenCode's authentication or its configuration behave, and the agent can already set anything in its own shell.
- A value someone mistakes for harmless is visible to anyone who can read the session, in Modal's control plane and in the database. The docs say so and point to routed credentials.
- The API gains a field on two requests and on the session view, which the generated client follows (DL-005).
