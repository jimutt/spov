## Context

The server has two clients: the Go CLI and a TypeScript web app. It streams progress, first launch steps and then job logs and transcripts. A generated spec keeps the web client from drifting from the server. Huma derives the OpenAPI 3.1 document from the Go request and response types that have to exist anyway, and on its standard-library adapter it adds no third-party module to the build (verified by building). Other options were `net/http` with chi, ConnectRPC and oapi-codegen. Typed RPC clients do not give browsers streaming, and generating the spec from handwritten handlers or the other way round would add a second source of truth.

## Decision

### The server

The API is Huma v2 (`github.com/danielgtaylor/huma/v2`, pinned in `go.mod`) on the `humago` adapter over `http.ServeMux`. There is no other router. Streaming is SSE through `huma/v2/sse`, typed into the spec. The API has no WebSockets. The only WebSocket in the system is OpenCode's terminal, which goes through the loopback proxy. If Huma stalled, plain `net/http` handlers on the same mux would replace it. It is a small project, and its exposure is bounded to the HTTP edge.

Everything versioned lives under `/api/v1/`. A breaking change means `/api/v2/` and never a silent change to v1. The resource groups are sessions (create, list, get, delete, connect, events, log, messages, interrupt, model, permissions, forms, sync export, and a stream of session states), jobs, repositories, models, the caller's own account (`me`, credentials, tokens, web sessions, usage, the OpenCode connection), users and the allowlist, and the organisation's GitHub App. The document is the authoritative list.

`spov serve openapi [--3.0]` prints the document without binding a port. The document is the contract. A change to a Go request or response type that changes it shows as a reviewable diff in `docs/api/openapi.yaml`.

### Creating and following a launch

`POST /api/v1/sessions` returns 202 with `{id}` at once, and the launch runs on the server, detached from the request (`context.WithoutCancel`, bounded by the launch timeout, 5 minutes by default). A launch takes seconds to minutes, and a held-open POST would time out behind any proxy. The server runs the real `session.Launcher`, including its loopback proxy, because that proxy is how a launch proves the path to the sandbox. Once the sandbox is healthy it closes the proxy (`Session.CloseProxy`) and keeps the handle, the password and the token revoker in memory as caches. A session this process did not launch is terminated through the provider by sandbox ID (see DL-003).

`GET /api/v1/sessions/{ref}/events` is SSE with `step`, `ready` and `error` events. It replays from the start for a session that is still starting, and a finished session yields its single terminal event. A stream on a replica that did not run the launch polls the store instead.

Listings are served from the store and not from Modal, because the SDK's list costs 1 + 2N RPCs (see DL-004).

### Errors

Errors are RFC 9457 `application/problem+json`, Huma's default. `toHumaError` maps domain errors explicitly:

- an unknown session or sandbox is 404;
- a stopped session, or one that is not running when the call needs it, is 409 with the problem type `session-stopped`;
- a name already in use is 409;
- an invalid request is 422;
- a concurrency quota or the connect-token limit is 429;
- a missing password, or any other provider failure, is 502 with the provider's message passed through the credential filter, never carrying a credential;
- a deadline is 504.

A handler that already chose its answer keeps it.

The credential filter, `internal/redact` (`Error`, `Text`), is applied to every message that crosses the API boundary or is stored. It replaces URL userinfo, token-bearing query parameters, `Bearer` and `Basic` credentials, the prefixes of Modal and GitHub tokens, `password: value`-style pairs (keeping the label) and any long opaque string, because a leaked credential costs more than a terse message. It is its own package so that the server and the job supervisor share one filter (see DL-046).

### Protected by construction

`Handler` serves everything under `/api/v1/` behind the browser guard and authentication. A package-local `register(api, op, handler)` helper is the only way an operation joins the API. It refuses at startup any operation outside that prefix and stamps `op.Security` on every operation inside it. Whether a path is protected is therefore decided in one place, and the document and the enforcement cannot disagree. `TestOpenAPIDocumentsSecurityOnEveryOperation` and `TestEveryDocumentedPathIsUnderThePrefix` check it.

Only the health endpoints (`/livez`, `/readyz`, `/startupz`), the login and device flows, the OpenCode pin and the web app's static files are reachable without a credential (see DL-006 and DL-007). `/docs`, `/openapi.json`, `/openapi.yaml` and `/schemas/*` are served by Huma behind the guard and authentication, because they describe the API's shape and that is reconnaissance for anyone who can reach the port (`TestAuthenticationAndGuardOrder`).

A session owned by another user reads as 404 and not 403, so its existence is not the caller's to learn. Admins see and control everything in the organisation.

### Limits

`http.MaxBytesReader` caps every request body at 1 MiB. Session creation, which may carry a base64-encoded checkout bundle, is capped at 24 MiB (`maxBodyBytesFor`; see DL-027). `ReadHeaderTimeout` is 10 s. There is no `WriteTimeout`, because SSE streams are long-lived and the API has no other long response.

### The Go client

The CLI uses a thin handwritten package, `internal/server/client`, against the server's own types. Generating a Go client from the spec would add a toolchain for little gain. A change to a view or request is a compile error on both sides.

### The generated TypeScript client

The web client is generated from the 3.1 document by `openapi-typescript` 7.13.0 (types only, no runtime) with `openapi-fetch` 0.17.0 as the typed `fetch` wrapper. Both are pinned devDependencies, run through `bun run gen:types` and never `bunx`, which would fetch whatever is latest. The 3.1 document is the input directly. The `--3.0` downgrade produced byte-identical TypeScript and stays only as an escape hatch (`Server.OpenAPI`).

`docs/api/openapi.yaml` (from `go run -buildvcs=false ./cmd/spov serve openapi`) and `web/src/lib/api/types.ts` are committed, marked `linguist-generated`, produced by `scripts/gen-api-client.sh` and never edited by hand. CI's web job and `scripts/check.sh` regenerate both and fail on a `git diff`. The script dumps the document through a temporary file beside the destination, so a compile error cannot leave an empty spec in the tree.

`info.version` is the fixed `server.APIVersion` (`v1`) and never the build version. A build stamp would change the document on every commit and fail the gate every time. `-buildvcs=false` stays in the script so a stamp cannot creep back in through `debug.ReadBuildInfo`. `TestTheDocumentCarriesNoBuildIdentity` and `TestTheDocumentIsDeterministic` guard this, the second from a separate process because map ordering shows only there.

A view must not expose an internal store type, and no event type uses `time.Duration`, which the document describes as nanoseconds. `UserView.quota_override` is a `QuotaOverrideView`, declared as `type QuotaOverrideView QuotaInput` so Huma names the schema after it. It has `QuotaInput`'s optional shape with duration strings, because an override records which fields an admin pinned. What the API reports is then what `PATCH /api/v1/users/{id}` accepts (`TestEveryOverrideFieldSurvivesTheRoundTrip`).

### The hand-written SSE transport

`web/src/lib/api/sse.ts` reads SSE with `fetch` and a `ReadableStream`, not `EventSource`. `EventSource` cannot tell a 401 from a dropped connection, and its automatic reconnect cannot be turned off. A generated SSE client does not fit spov's events: the one checked types the stream as the spec's array envelope while its runtime yields one bare payload at a time with the `event:` name dropped, and spov's event kinds are discriminated only by that name. The transport mirrors `internal/server/client/follow.go`:

- It reopens once from the beginning when the connection breaks. It reports the reset through an `onRestart` callback and not a synthetic event, which would have to be added to the generated union by hand. The second failure surfaces to the page. There is no poll fallback.
- A non-200 answer is final, and so is an oversized event (`MaxEventBytes`, 1 MiB, like the Go client). The bound applies to the retained incomplete frame and not the whole read buffer, so a single read that carries many good frames is not refused.
- Event names live in a table keyed by the generated union (`Record<LaunchEvent['event'], ...>`), so a renamed or dropped name fails `astro check`. A name the server adds is absent from the table and skipped.
- Frames split on a blank line in any of SSE's three line endings, with the incomplete tail kept in the buffer. Normalising the buffer first would misread a chunk boundary inside a CRLF. Decoding uses a `TextDecoder` with `stream: true` and not `TextDecoderStream`, which does not typecheck against `pipeThrough` here and would still need care for multi-byte characters split across chunks.
- A `ref` is checked against path normalisation. `encodeURIComponent` leaves `..` alone, so `/sessions/../events` would resolve to `/api/v1/events` with the caller's credentials. The client builds the URL and compares its normalised pathname with what it built, and refuses a mismatch. A `/` inside a ref is percent-encoded and stays one segment, which the server answers with 404.

`client.ts` resolves its base against `location.origin`, because `openapi-fetch` builds a `Request` before it calls `fetch` and a relative URL has nothing to resolve against outside a document, which is every test. The redirect to the login page on a 401 is not in the transport. It is page-level middleware.

## Rationale

- A derived spec means the web client cannot drift from the server, and nothing is hand-maintained.
- No added dependency on the standard-library adapter keeps the dependency list short.
- 202 plus SSE suits a launch that takes seconds to minutes, and the same shape serves jobs.
- Types-only generation is the smallest thing that removes drift. The types are the hard part, and `openapi-typescript` renders Huma's `oneOf` as a discriminated union that narrows under `--strict`. The hand-written transport is one small file.
- Committing the spec and the types makes an API change reviewable in one diff and gives the web build no Go dependency.

## Measurements

- Huma on `humago` adds no third-party module to the build (checked by building).
- `openapi-fetch` is 17 KB with one types-only dependency.
- The `--3.0` downgrade of the document gives byte-identical TypeScript to the 3.1 input. Re-run with `scripts/gen-api-client.sh`.
- The generator `@hey-api/openapi-ts` vendors about 2,100 lines of runtime, and its generated SSE types and its runtime disagree (shown by a typecheck against the real spec).
- The gate was verified in both directions. A clean tree regenerates byte-identically, and adding one field to `UserView` made both artifacts differ. Renaming an event kind in the table fails `astro check`, and dropping a field from `overrideView` fails the round-trip test.
- The single `typescript` pin (5.9.3) satisfies `astro check` and `openapi-typescript` 7.13.0 together, so no isolated generator was needed.

## Consequences

- Changing the API without regenerating fails CI.
- The one `typescript` pin serves two tools, so raising it breaks the generator before anything visible.
- `docs/api/openapi.yaml` and `web/src/lib/api/types.ts` are build outputs of the Go types. The editable TypeScript is `client.ts` and `sse.ts`.
- `/docs` is a surface of its own. The guard and authentication cover it.
