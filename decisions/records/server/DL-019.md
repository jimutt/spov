## Context

The web app lets a person talk to an agent that is running in a sandbox. Reads of a session come from the store and never touch the sandbox (see DL-018). A message is different: it is a write, made once per human act, and it has to reach the sandbox's OpenCode.

The browser could reach the sandbox itself, because `POST /api/v1/sessions/{ref}/connect` hands a caller an edge URL, a connect token and the OpenCode Basic password. It does not, for three reasons. The password would sit in browser memory and show in every devtools network pane. The server could not refuse a send on the job's state (see DL-052), because it would not know the send happened. And the recorder could not be nudged to read it. CSRF protection is not among the reasons: that is `BrowserGuard`'s job (see DL-061).

OpenCode's prompt route takes a `delivery`: `steer` or `queue`. What each does was measured in spike S-Q1 (below), and the measurements decide the default.

## Decision

The server relays messages. There is one operation, `POST /api/v1/sessions/{ref}/messages` with `{conversation, text, delivery, after, id}`, which pairs with the `GET` that reads messages. Interrupting a turn is a separate endpoint, because it cannot be separated from the job-row change that stops it stranding a job (see DL-053). There is no CLI command to send a message: an attached CLI already talks to the sandbox, and `internal/server/client` has the call only as the API's Go surface, with its own test.

This is a third category of sandbox call beside the recorder's reads and a job's lifecycle writes: once per human act, never per viewer and never on a timer. The code lives in `steer.go`, not in `sandboxio.go`, which is the recorder's alone. Only `steer.go` may address the sandbox's prompt route, because that route makes a `user` inbox item (`TestOnlyAHumansOwnWordsReachThePromptEndpoint`).

### Deliveries

- **`steer`** is the default and what the browser sends. The message is read at the agent's next step, once the step or tool call running now has finished. Nothing running is stopped.
- **`queue`** is read when the whole turn ends, before any continuation. It is API only.

An omitted `delivery` is `steer`. Both apply to interactive sessions and to jobs. To have a message read at once, the person sends it and then interrupts, which resumes it (see DL-053); there is no combined delivery. A job refuses a message in the states where it would be enqueued and not delivered: `blocked`, `queued`, `provisioning`, `delivering` and the terminal states (`jobRefusesAMessage`). `TestEveryJobStateIsDecided` makes a new job state fail until it is placed. What a delivered message does to a job, including the `after` choice (`continue` or `handover`) that rides in the prompt's `metadata.spov.after`, is in DL-052.

Steer is the default because a job's turn lasts as long as the agent keeps calling tools, so "after the turn" can mean half an hour. With `queue` as the default, a message sent between two `sleep 30` calls would not be read until the person interrupted. `steer` waits only for the running step, a tool boundary, and cuts nothing off.

### Each send

The request is checked in this order, all before anything reaches the sandbox, so a refused caller spends no mint:

1. **Text** is trimmed, must be non-empty and at most `MaxMessageBytes` (the same bound as a job's goal). `delivery` and `after` are validated against their enums.
2. **`id`** is optional. If present it must start with `msg_`, be at most 128 bytes and use letters, digits, `_` and `-`. The browser mints the id so that it is both the idempotency key and the key its optimistic echo reconciles on; asking the server for one would cost a round trip before the echo could render. The id becomes a primary key in the sandbox and the recorder's key for the row, so a caller does not get to choose arbitrary text for it. The id the sandbox echoes back (`promptedID`) is held to the same check and falls back to the caller's. The `msg_` prefix is written in Go and in the browser (`TestTheMessageIDPrefixMatchesTheBrowser`).
3. **Ownership** is `Service.Get`, which is organisation-scoped: a caller who does not own the session gets 404.
4. **The session is running** and has a sandbox. This comes before the limits so that repeated sends to a dead session cannot use up the limit of one about to be revived.
5. **The job's state** (`steerableJob`), for a session that has a job.
6. **The conversation** (`steerInto`) must belong to the session, checked against the store's rows, because OpenCode ids are unique only within a session. It may be omitted only when there is nothing to choose: exactly one recorded conversation resolves to it, and several refuse with the count. Choosing the oldest, as the job path does for a job's opening goal, would be a guess that puts a person's message in front of an agent they were not talking to. The conversation is `PathEscape`d into the sandbox URL, because the recorder wrote it from the sandbox's own frames and the sandbox chooses that string. `setConversationModel` has the same exposure.
7. **The two limits** (below).

The prompt is sent with `resume: true` and `delivery` explicit. `resume` is explicit for clarity; the default already schedules execution. A steering call resets the sandbox's idle clock, which is intended: a session nobody is talking to still idles out.

POST `/prompt` returns once the item is durably admitted, not once the model has read it.

### Steering's own limits

A steering call does not mint a connection per message. `Service.Connect` issues a Modal connect token that lives 24 hours and cannot be revoked, and the per-session mint budget is shared with the recorder, which needs it to redial (see DL-030). Steering uses the server's cached connection, so a send usually reaches no mint transaction and the durable mint limit does not bound it. Steering therefore needs a ceiling of its own, and the rule is that steering must reach its limit before the recorder does. There are two limits.

- **`MessagesPerMinute` (6)** is in memory, per replica, on the shape of `attemptLimiter` without its lockout. It is abuse control only: with N replicas the effective ceiling is N times 6, so it cannot bound the shared budget. A refused send records nothing, so hammering a full window does not push its expiry out.
- **`RecordingMintReserve` (3)** protects the recorder. `mintBudgetLeft` reads the durable `Mint` rows every replica shares and refuses while a send could take the session's remaining budget below the reserve. A send costs at most `MintsPerSteer` (2) mints, because `withConnection` mints on a cache miss and again if the sandbox refuses the credential it was given. The budget is `MintsPerMinute` (10) per organisation and session, so a send is refused once the session has spent more than 5 of them in the last minute. The reserve is three because `RecorderBackoff` allows three redials to begin within a minute; `TestTheReserveIsSizedForWhatASendCanCost` derives the minimum from it.

The check reads and does not reserve, so a mint can land between the read and the send. The error is at most one mint, not a whole budget. A failed read of the count is returned as an error, neither a refusal nor a pass: failing open would spend the budget the reserve protects, and refusing would blame the caller for spov's own outage. The check takes the caller's own sentinel error, because a send and a stop (see DL-053) both spend from this budget and need different wording. A send over either limit answers 429 (`ErrTooManyMessages`); `ErrNoConversation` and `ErrJobNotSteerable` answer 409.

### The audit marker and the recorder

After a send, the server writes the spov-sourced event `spov.session.steered` (`MarkerSteered`) with the sender, the message id and whether it was queued or handed a job over. It is the only attribution: the inbox item is typed `user` and names nobody, with connection reuse a mint row does not say who wrote, and an organisation admin can reach another user's session through `Service.Get`. `store.Event.Validate` refuses the name from a sandbox, and the job state machine ignores it.

It is written after the send, because an action that did not happen must not be recorded. A failure to write it only warns: failing the request after delivery would invite a retry that sends the message twice, and the sandbox dedupes on the id while spov's own side effects do not. The cost is that an audit record can be lost. It is written on a detached context, so a caller who hangs up right after the send cannot choose whether their own action is recorded. `ctxBoundConversations` in the tests is what makes that check meaningful, because the in-memory store ignores its context. The marker is spov's own row and does not count as evidence that a recorder was listening earlier (`TestASteeringMarkerIsNotEvidenceOfAnEarlierRecorder`; see DL-017).

A send then nudges the recorder with `OnStart`, best-effort and effective only on the leader, since the recorder runs only under leader election. The recorder's poll remains the mechanism. Without a nudge a message could sit in the sandbox's store and not in spov's, and on a job the supervisor derives a steer from the stored event.

### The message id in the log

`MessageView` and `LogEvent` carry the message id, which the browser's echo reconciles on. The stored half reads it from the stored message. The live half is `storedMessage`, which re-derives it from the event's `Raw` at `data.inboxID`, and only for `session.inbox.enqueued` and, from the sandbox, `delivered` and `cancelled` (`namesAMessage`). It must not search for `id`, which is the event's own `evt_…` id, nor for `assistantMessageID` or `source.messageID`, which name other messages. That the enqueued id and the stored message id are one id space is OpenCode's behaviour (`SessionInbox.reconcile` looks in both tables). S-LS1's `steerMessageIDFor` compares them when the message store holds the item.

### A message's status, and cancelling it

A person's message has a status derived from stored events, never from the sandbox: queued from its enqueue, processed from `delivered`, cancelled from `cancelled`, and not processed when the session or job ended with none of them. `storedInbox` adds the `delivery` and `after` of an enqueued user item to the log, so the browser's `messageStatuses` in `timeline.ts` can build the list; how it draws them is in DL-059. Reading the sandbox's inbox per viewer would be the read that DL-018 forbids, and the store is the only source that survives a reload and agrees across viewers.

`DELETE /api/v1/sessions/{ref}/messages/{id}` (`CancelMessage`) relays OpenCode's inbox DELETE. It is a per-act write like a send, with the same authorisation, a running session, connection reuse, conversation rule and limits, taking from the same per-session message ceiling. Like a send it writes an audit marker, `spov.session.message.cancelled`, and nudges the recorder. OpenCode answers 204 whether or not the item was still pending, so the response says only that the request was sent, and the outcome is read from the stored `cancelled` or `delivered` event. Only a person's own message can be cancelled: the id must be a stored `user` enqueue of the session (`isPersonsMessage`), so a caller cannot drop spov's queued continuation. Moving a queued message to `steer`, and editing or reordering one, are not offered.

### The first message creates the conversation

An interactive session started in the browser has no conversation until someone speaks, and an attached TUI makes its own. When a session that has no job has no recorded conversation, `Steer` creates one on the first send (`firstConversation`, through `createConversation` as the job path does), in the session's landing directory, records the row, sets the session's model, and then sends. Doing it at launch would make a conversation the person may never use. A job's conversation is the job path's, and a message to a job with none recorded is refused with `ErrNoConversation`, which otherwise remains only for cancelling a message.

Concurrent first sends on one replica are serialised per session (`keyedLocks`, `firstSends`) and the store row is checked again inside, so they create one conversation. `withConnection` may run the closure twice after a refused credential, and the second run reuses the conversation the first created, recorded or not.

## Rationale

- A send is a write whose rate is how fast someone types, so it does not bring back the polling problem that the read rule exists to prevent.
- Putting the message through the server is what lets the server refuse it on a job's state, attribute it, bound its cost and nudge the recorder. None of these is possible from the browser.
- One endpoint with explicit defaults avoids a second creation path with a second validation order.

## Measurements

- **S-Q1, OpenCode's inbox**, measured on the local binary with a scripted fake model, no plugin, no sandbox and no key. Eleven results:
  1. A `queue` item is not seen mid-turn. The model first sees it after its final reply and it runs inside the same execution: `session.inbox.delivered`, a model step that answers it, then `session.execution.succeeded`. No `succeeded` comes between the turn and the queued item.
  2. A `steer` item reaches the model at its next step and does not stop the running step or tool.
  3. Steer goes before queue. A synthetic with no `delivery` resolves to `steer`, and a synthetic with `delivery: "queue"` is ordered with queued user items by arrival.
  4. Every pending queued item runs in one go, in arrival order, each answered by its own step, all before `succeeded` (measured with two items).
  5. An interrupt parks queued items, whether `resume` is true or false. They stay in `GET /inbox` while the session is idle (6 s measured) and run after the item that starts the next execution. `resume=true` resumes only pending steer items.
  6. `PATCH /inbox/{id}` to `steer` wakes a parked item and raises `session.inbox.delivery.changed`.
  7. `DELETE /inbox/{id}` raises a durable `session.inbox.cancelled`, and a second DELETE of the same id is a silent 204. A `queue` item sent with `resume: false` on an idle session stays pending, and the next `resume: true` send drains both, oldest first.
  8. A prompt's `metadata` is kept on the `session.inbox.enqueued` item (`item.payload.metadata`) and on the stored message.
  9. `enqueued`, `delivered`, `cancelled` and `delivery.changed` are all durable.
  10. A plugin's context has `session.interrupt` but nothing that reads or changes the inbox.
  11. A `steer` item sent while a long step runs stays pending until that step ends, and an interrupt with `resume=true` delivers it at once in a new execution.

  Measured on OpenCode 2.0.22. Re-run: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SQ1 -v`; nothing billable is created. Re-run it on every OpenCode bump. Results 1, 4 and 5 are what takeover, interrupt and the completion signal rest on (see DL-052, DL-053, DL-048).
- **S-LS1, the steering surface** on the pinned build: the routes are spelled as read, the `delivery` enum is `[steer, queue]`, `POST /prompt` echoes the caller's `msg_` id in `{"data":{"id","sessionID","timeCreated","type":"user","payload":{"text"},"delivery":"steer"}}`, and an omitted `delivery` resolves to `steer`. Re-run: `go test -tags integration ./internal/sandbox/ -run SLS1 -v` (`TestIntegrationSLS1SteeringSurface`), which creates one billable sandbox and terminates it. A mismatch in the response shape would show as "no echo ever appears", which looks like a UI bug, so it is measured.
- **Limits:** `MessagesPerMinute` 6 per replica; `MintsPerMinute` 10 per organisation and session (durable); `MintsPerSteer` 2; `RecordingMintReserve` 3. Re-run: `go test ./internal/server/ -run TestTheReserveIsSizedForWhatASendCanCost`.

## Consequences

- New inbox routes need entries in `contract.Used` when spov calls them, and OpenCode ignores an unknown query parameter, so only the contract check catches a rename (see DL-035).
- The generated client and `docs/api/openapi.yaml` change with the endpoint (`scripts/gen-api-client.sh`).
- This endpoint is correct for jobs only together with the state refusals above and the takeover rules in DL-052.

## Known gaps

- A job whose conversation row failed to write (`jobConversation` only warns) cannot be steered until the recorder writes the row.
- Two replicas racing on the first message of an interactive session can create two conversations. The next send then names the ambiguity, and the second conversation stays empty.
