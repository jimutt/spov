## Context

spov holds git platform tokens, GitHub App keys, model provider keys and the CLI's own token for a hosted server. Where those live depends on who reads them. A local server runs as the user and reads the user's machine. A hosted server reads its database and its environment, and never the machine of the person who is talking to it. A credential stored on the wrong side is silently useless.

## Decision

### Local: the OS keyring with a file fallback

The local store is `zalando/go-keyring` behind a 2 s timeout (`credentials.DefaultTimeout`). The interface is `Get`, `Set`, `Delete` and `Name`. It cannot enumerate its keys, because the OS keyring cannot, so local listings probe known names.

Keys are namespaced `<kind>:<id>`: `platform:<name>`, `provider:<ENV_VAR>` and `server:<host>`. The `server:` key holds the CLI token for a hosted server (see DL-006). The kinds keep the flat keyring key space readable.

When the keyring times out or fails, spov falls back to `credentials.json` in its config directory, with mode `0600`. The first write there prints a warning that names the file and says the secrets are stored unencrypted. `spov config show` reports the backend in use.

- **What the file protects and what it does not.** The `0600` mode, and a `0700` directory, keep other local accounts from reading the secrets. It does not protect against any process running as the same user, against backups that copy the file, or against an unencrypted disk. Encrypting the file was rejected, since a key derived from the machine would sit next to the ciphertext and protect against nobody that the file mode does not already exclude, and a passphrase would have to be typed on every launch. The warning tells the user where the secrets are.
- **Backend choice.** The backend is chosen once per process by probing the keyring on first use, because a hanging keyring costs the full timeout and paying it per call would make the CLI unusable. A "not found" answer counts as a working keyring.
- **Demotion.** The probe only reads. A keyring that reads but cannot write, such as a locked keychain, would leave the user on a broken backend for the whole process. So a failed write on the primary demotes to the fallback once, and later reads follow.
- **Timeouts.** A timed-out write has an unknown outcome and not a failed one. The call keeps running and may complete later, leaving a copy in the keyring that spov has decided not to use. `ErrTimeout`'s message says so. The wrapper deliberately lets a hung call's goroutine leak, since a blocked D-Bus call cannot be cancelled and the buffered channel lets it exit whenever it returns.
- **The file store.** It refuses to read a file wider than `0600`, writes atomically through a temporary file that is `chmod`ed before the secrets are written, and tightens a containing directory that predates spov and is looser.
- **Modal.** Modal credentials come from Modal's own sources (`~/.modal.toml`, `MODAL_TOKEN_*`). There is no spov path to store a Modal token.

### Hosted: sealed rows in the database

A hosted server stores user credentials in `user_credentials`, one row per user and platform, sealed with AES-256-GCM under a 32-byte key from `SPOV_CREDENTIAL_KEY` (base64). A server without the key stores nothing: storing or removing a credential answers 501 saying so, and the listing reports `enabled: false`, so that "no credentials" is not read as "mine are missing" (see DL-042 for which tier a launch uses).

- **Nonce and AAD.** Each write draws a fresh random 12-byte nonce. The additional authenticated data is `org_id\0user_id\0platform` (`CredentialAAD`), so a row copied into another user's name fails to open and does not decrypt into their session. The organisation's own credentials use a different AAD that starts with a byte no organisation ID starts with, so an organisation row can never be opened as a user's or the reverse.
- **Key versions.** A key's version is derived from the key, not from where it was configured: the first four bytes of SHA-256 over the key, masked to 31 bits. A key always opens what it sealed, however it is presented later, and the order of the two variables cannot matter. A scheme where the current key is "version 2" and the retiring one "version 1" fails silently at the first rotation, because the new key takes version 2 and every existing row becomes unreadable.
- **Rotation.** Set the new key as `SPOV_CREDENTIAL_KEY` and the previous one as `SPOV_CREDENTIAL_KEY_OLD`. Old rows stay readable and are rewritten under the new key when their owner next stores them. There is no command that re-encrypts every row, so the old key stays configured until nothing references it. `SPOV_CREDENTIAL_KEY_OLD` alone is refused, because it would seal new data under the key being retired.
- **A credential that will not open is not a miss.** It resolves to "re-add it" and never falls through to the organisation's credential, which would hide a lost key behind the deployment's own access. An unreadable model provider key is withheld, not replaced by the deployment's, so the deployment is not billed for work the user meant for their own account.
- **Plaintext** exists only in memory while a launch or listing runs. Values are never returned, never logged and never recorded on a session row.
- **API.** `PUT /api/v1/me/credentials/{platform}` with `{token}` verifies the token against the platform and stores it. `GET` returns presence, who the token is, its scopes and its expiry, and never the value. `DELETE` removes it, and removing a credential that is not there succeeds. Every endpoint canonicalises the platform name before it touches the store (hosts lower-cased, provider variables upper-cased), so `remove forgejo:EXAMPLE.COM` removes the row that `forgejo:example.com` created. Without that, the remove would report success and leave a live credential behind. Verification is in DL-041.

### One verb for accounts, one for secrets

`spov login` and `spov logout` sign in to accounts: the configured spov server (see DL-006), and `spov login opencode` for the OpenCode Console connection (see DL-015). Any other name is refused with the `spov credentials` command that handles it. `--name` and `--no-browser` stay on `login`.

`spov credentials` lists the stored credentials by name and never by value (`list` and `ls` are aliases). `spov credentials add <name>` stores one, and `spov credentials remove <name>` removes one. The command tree is in DL-023.

The name is one positional argument, shared by `add`, the listing and `remove`:

- a platform: `github`, or `forgejo:<host>`;
- a provider key: a name ending in `_API_KEY` in any case, any other all-uppercase variable, or `provider:<VAR>`;
- anything else is a platform. With a local server a platform may also be named as it is in config, and that name wins over the uppercase rule (a platform called `GH`). `github` and `forgejo:<host>` find the configured platform of that kind or host, so one name works in both modes. When several platforms answer to one name, spov refuses and lists their config names.

Flags carry only what a kind needs: `--app-id`, `--key-file` and `--installation-id` for a local GitHub App, `--token` to skip the prompt, and `--no-verify` locally. A hosted server takes a GitHub token for `github`, refuses the App flags and `--no-verify`, and always verifies.

### Where a secret goes

A credential is stored where the server the CLI talks to reads it, and `Env.hostedServer` decides: a configured server URL means hosted, never a flag. With a local server the secret goes into this machine's store, which the local server reads. With a hosted server it goes to that server, for the caller's own sessions. A hosted server never reads this machine's store. Every `add` and `remove` says where it acted. A hosted server without `SPOV_CREDENTIAL_KEY` refuses. An operator's own credentials for a hosted deployment come from its environment and not from a CLI.

Listings follow the same rule. A hosted listing shows what the server holds, and a provider key by its bare variable. A local listing shows which known names this machine's store holds: the configured platforms and the provider variables in the catalogue (`prep.ProviderKeyEnvs`), each probed with `Get`. A key stored under another variable is not listed, and the listing says so. A platform is shown by its config name with the hosted name beside it, such as `forge  (forgejo:forge.example.com)`. The OpenCode line stays last. The listing shows presence only, never a secret or a prefix of one, because a prefix invites itself into a pasted output.

### Verifying before storing

A credential is verified before it is stored, so a wrong token fails at `add` and not halfway through creating a billable sandbox. Locally this builds the platform and lists its repositories. `--no-verify` skips the listing, but the Forgejo constructor still contacts the server, and the help says the credential is stored unchecked. Provider keys are not verified, because there is no cheap check that fits every provider. A GitHub App key is read from a path (`--key-file`), never pasted or given as a flag value, which keeps it out of scrollback, shell history and `ps`. Forgejo tokens come from `--token` or a prompt without echo. A stored provider key fills a gap, since at launch the environment wins over the store.

A rejecting server is the one place that quotes the credential back. Forgejo answers a bad token with `access token does not exist [sha: <token>]`, and the SDK passes it through. Verification errors are therefore scrubbed at that boundary, in the CLI and again on the server, which holds the secret and whose 422 travels through proxies and access logs. Private keys are removed by pattern (anything between `-----BEGIN ... PRIVATE KEY-----` and its `END`, whatever its encoding), because a server echoing a JSON body escapes the newlines and a value match would miss the key. A literal value is replaced only when it is at least eight characters (`minRedactableSecret`), because a one-character credential would rewrite unrelated words. Verification errors do not wrap their cause with `%w`, so `Unwrap` cannot carry the unredacted text out. Nothing inspects them with `errors.Is`.

Verification narrows the window without closing it: a token can be revoked later.

## Rationale

- The OS keyring is the right default on macOS, Windows and desktop Linux. On Linux systems without a D-Bus secret service (headless installs, some virtualised environments) go-keyring can hang or fail, and the timeout wrapper turns either into a graceful fallback.
- A command name should say what it acts on: an account that is signed in to, or a secret that is stored. Having the location follow the server removes a choice that had one useful answer.
- A server-held key keeps a database dump useless without the deployment's secret store, at the cost of one more secret to manage.

## Measurements

- The keyring timeout is 2 s (`credentials.DefaultTimeout`). On a Linux system without a secret service, the keyring was measured failing in about 5 ms with `org.freedesktop.secrets was not provided by any .service files` and the file fallback is used. The wrapper stays because the documented failure mode elsewhere is a hang.
- Verification was run against a real GitHub App and a real Forgejo. The Forgejo token echo and the escaped-newline key leak described above were observed there.

## Consequences

- Losing `SPOV_CREDENTIAL_KEY` makes stored user credentials unrecoverable. Users enter them again.
- Two code paths exist for the local store (keyring and file), and tests cover both.
- Guard tests: `TestLocalCredentialsTakeTheServersNames`, `TestTheConfiguredServerDecidesWhereACredentialGoes`, `TestOpenRejectsAnotherUsersRow`, `TestRotation`, `TestKeyVersionIsStable`, `TestVerificationErrorDoesNotEchoTheToken`, `TestPutWithoutAKeyIs501`.

## Known gaps

- No command re-encrypts every row after a key change.
- The local listing cannot show a provider key stored under a variable the catalogue does not know.
