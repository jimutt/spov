## Context

A hosted server deploys from `deploy/Dockerfile` (DL-010), but no image is published: every operator builds their own. The examples (compose, Kamal, Kubernetes) name an image they cannot pull.

## Decision

- The release workflow builds `deploy/Dockerfile` for `linux/amd64` and `linux/arm64` with buildx, after the release check, and pushes `ghcr.io/jimutt/spov:<version>`. A release that is not a prerelease also moves `:latest`; the examples never use it.
- The image is signed with cosign keyless signing by its digest, and gets a build provenance attestation pushed to the registry.
- The image's build stamps the version, commit and date, as goreleaser does.
- The Kubernetes manifests name `ghcr.io/jimutt/spov:<version>@sha256:<digest>`, and the deploy README says how to read a release's digest (the workflow prints it as a notice) and verify it (`cosign verify`, `gh attestation verify oci://…`). Compose and Kamal keep building from `deploy/Dockerfile`, since that is how a change is proved before it is released; the README says how to point Compose at a release.
- `deploy/Dockerfile`'s web and Go stages run on the builder's platform and the Go stage cross-compiles (`GOOS=$TARGETOS GOARCH=$TARGETARCH`), so the arm64 image needs no emulation. The platform arguments are declared without defaults, because a default overrides BuildKit's value: measured on 2026-11-06, a default made the arm64 image hold an x86-64 binary. The credential proxy stays linux/amd64, which is where sidecars run. A local `docker buildx build --platform linux/amd64,linux/arm64` produced an aarch64 and an x86-64 binary.
- Pushing uses the workflow's own `GITHUB_TOKEN` (`packages: write`), and the package is public once the maintainer marks it so.

## Rationale

A published image removes the build step from every deployment and lets an operator verify what they run. Pinning by digest means a moved tag can never change a running deployment.

## Consequences

- `deploy/` examples change from a locally built image to the published one.
