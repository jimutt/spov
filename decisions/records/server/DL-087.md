## Context

A session whose sandbox has ended is `stopped` or `failed`, and today that is final: the only way on is a new session, which starts from a fresh clone and an empty conversation. Snapshot resume and transcript resume (control-plane.md §2.11.1) were agreed in August 2026 and descoped until the exit snapshot (DL-084) and the conversation import (S-TR1) made both workable.

The choice discussed on 2026-11-06 was between a new session linked to its parent and the same session reopened. Reopening keeps one URL, one listing entry and one transcript for the whole piece of work.

## Decision

`POST /api/v1/sessions/{ref}/resume` reopens a session. Its body is `{timeout?, message?}`, and it answers with the session's view.

**Finding a stopped session.** `{ref}` is an ID, or a name. A name resolves to the live session that holds it, else to the caller's newest stopped or failed session with that name. This amends DL-018's known gap, where a name resolves among live sessions only. `GET /sessions/{ref}`, `spov attach` and `spov resume` resolve the same way.

**Who and what.** Only the session's owner may resume it. An admin may not, since the session would run on the owner's credentials. A session is resumable when all of these hold:

- the server keeps its sessions in Postgres (DL-084);
- it is `stopped` or `failed`;
- it belongs to no job (a job's session is refused with 409);
- it has a run that reached `running` (DL-085). A session that failed at launch is refused, and its owner launches a new one.

A deliberately stopped session is resumable like one that idled out or timed out.

**Refusals before anything starts.** Everything that can be checked before a sandbox exists is checked synchronously, and a refusal leaves the session `stopped` or `failed` as it was, with its snapshot untouched:

- the session quota, under the same advisory lock as a launch (DL-009);
- the timeout (below);
- the first message (below);
- a snapshot still being taken (DL-088).

A recorded credential tier that has gone (DL-042) is found by the launch path, as at a first launch: the run fails with the launch's error, never switching tier, and the session stays resumable, since an earlier run ran.

**The name.** When a live session now holds the name, the session resumes under the first free name of `<name>-2`, `<name>-3`, and so on. The rename is written with the resume, the view carries the new name, and the log's resume marker names both.

**The state.** The resume moves the session from `stopped` or `failed` to `starting` in one conditional write, so two resumes of one session cannot both start. That write clears `StoppedAt`, `Error` and `SandboxID`, and inserts the next run (DL-085), so the reconciler sees a launch in flight (`launchInFlight`, DL-004) until the run records its sandbox. The sandbox is named `<name>-run<N>` from the second run on, which avoids waiting on a just-terminated sandbox's name, and is tagged with its run (DL-084). The reconciler adopts a sandbox only when its name and run tags match the session's current run. That amends DL-004.

From there the launch path runs as for a new session: `running` once OpenCode answers, or `failed` with its error. Its lifecycle writes go through the launcher, as a launch's do.

**The settings.** The resumed sandbox gets the recorded request: repositories, model, egress preset, add-ons, git access, routed credentials, landing and idle timeout. Only the timeout may be set again:

- `timeout` defaults to the timeout the session was launched with. If `max_timeout` has since been lowered below it, the default is cut to the limit;
- an explicit `timeout` over `max_timeout` is refused with 422, as at launch (DL-009);
- the idle timeout stays as launched, cut to the timeout.

A model switched while the session ran comes back with its conversation: OpenCode keeps it in its own store, which a snapshot restores, and in each conversation's `Session.Info`, which a transcript resume imports (DL-089). The server sets nothing.

**Credentials.** Every platform resolves again through the tier the launch recorded (`policyOf`, DL-042), and the tokens are minted then. The OpenCode Console grant goes through `freshConsoleToken` under its lock, and `SetOpenCodeGrant` records the generation, as at launch (DL-015). Routed credentials are resolved again for the recorded names (DL-075). One that has since gone is left out and noted as at launch (`MarkerRoutedLeftOut`), and the session view lists what this run attached.

**The CA.** Every run makes a new CA, kept as a launch's is (`keepProxyCA`, DL-034) and deleted when the run's session stops. No process survives a snapshot, and the stored CA would have been deleted at the stop and would have lapsed (`CAValidity`, 26 h). The entrypoint installs it in place of the old one (DL-088).

**The log.** The resume writes `spov.session.resumed` with the run's number, how it resumed (`snapshot` or `transcript`, DL-088 and DL-089) and any rename. The page draws it as a seam. The recorder attaches to the new sandbox through its `Wake` nudge (DL-017).

**A first message.** `message` carries the browser-minted `id` and the text, and passes DL-019's checks when the resume is asked: the text bound, the `msg_` prefix, and the conversation rule. With several conversations the message must name one (`conversation`), and is refused otherwise. With one, it goes there, and with none, into a new conversation once the session runs. The message is stored on the new run (`session_runs.first_message`), so another replica that finishes the launch, or a restart, still delivers it. It is delivered through `steer.go` as a steer with its own id once the session is `running` and its conversation is attached, and it writes `spov.session.steered` as any steer does. A repeat with the same id is dropped. If the resume fails, the message is not sent, and the failure says so.

## Rationale

Reopening keeps the reader's thread intact. The run table (DL-085) carries what a second row would have, so the listing, the recorder and the reconciler can still ask about one sandbox at a time.

Settings as launched keep resume a continuation, not a relaunch. Changing the repositories or the add-ons would need a fresh image and fresh clones, which the snapshot cannot give. The model can still be switched in the running session as before (DL-014).

Minting again under the recorded tier follows DL-042 exactly as a recreated sidecar or a renewal does, and nothing secret survives in the snapshot to be reused (DL-084). Refusing before anything starts keeps a refused resume from spending a run, or the snapshot choice it would have made.

Resuming under a new name, rather than refusing, keeps a resume from depending on what the person launched since. The first message lives with the run so that "Resume and send" survives the browser tab closing while the sandbox boots.

## Consequences

- `stopped` and `failed` stop being terminal for an interactive session. The state stream, the attach wait and the page must allow `stopped` to `starting` (DL-090).
- A resume costs a quota slot and a sandbox, like a launch.
- The launch metrics count a resume with a closed-set `kind` label (`launch` or `resume`).
