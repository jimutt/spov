## Context

A session whose sandbox has ended is `stopped` or `failed`, and today that is final: the only way on is a new session, which starts from a fresh clone and an empty conversation. Snapshot resume and transcript resume (control-plane.md §2.11.1) were agreed in August 2026 and descoped until the exit snapshot (DL-084) and the conversation import (S-TR1) made both workable.

The choice discussed on 2026-11-06 was between a new session linked to its parent and the same session reopened. Reopening keeps one URL, one listing entry and one transcript for the whole piece of work.

## Decision

`POST /api/v1/sessions/{ref}/resume` reopens a session. Its body is `{max_duration?, message?}`, and it answers with the session's view.

**Who and what.** Only the session's owner may resume it. An admin may not, since the session would run on the owner's credentials. A session is resumable when:

- it is `stopped` or `failed`;
- it belongs to no job (a job's session is refused with 409);
- it has at least one run that reached `running` (DL-085). A session that failed at launch is refused, and its owner launches a new one.

A deliberately stopped session is resumable like one that idled out or timed out.

**The state.** The resume moves the session from `stopped` or `failed` to `starting` in one conditional write, so two resumes of one session cannot both start. It clears `StoppedAt` and `Error`, and inserts the next run (DL-085). From there the launch path runs as for a new session: `running` once OpenCode answers, or `failed` with its error. The session quota is checked first, under the same advisory lock as a launch, and counts the session as live from that write (DL-009). A refusal leaves the session as it was.

**The settings.** The resumed sandbox gets the recorded request: repositories, model, egress preset, add-ons, git access, routed credentials and landing. Only the duration may be set again. `max_duration` defaults to the duration the session was launched with and is cut to `max_timeout`, as at launch. A model switched while the session ran is read back from its log, as the page reads it (`session.model.selected`).

**Credentials.** Every platform resolves again through the tier the launch recorded (`policyOf`, DL-042), and the tokens are minted then. A tier that has gone fails the resume, never switches. Routed credentials are resolved again for the recorded names (DL-075). One that has since gone is left out and noted as at launch (`MarkerRoutedLeftOut`), and the session view lists what this run attached. The proxy sidecar reuses the CA kept in `session_proxy_cas` when it covers the hosts, and only otherwise makes and installs a new one: the same rule as a recreated sidecar (DL-034).

**The log.** The resume writes `spov.session.resumed` with the run's number and how it resumed (`snapshot` or `transcript`, DL-088 and DL-089). The page draws it as a seam. The recorder attaches to the new sandbox through its `Wake` nudge (DL-017), and the gap marker compares against the conversations the store already holds.

**A first message.** `message`, when given, is delivered as a steer (DL-019) once the session is `running` and its conversation is attached. It goes into the session's newest conversation, or a new one when it has none. If the resume fails, the message is not sent, and the failure says so.

## Rationale

Reopening keeps the reader's thread intact. The run table (DL-085) carries what a second row would have, so the listing, the recorder and the reconciler can still ask about one sandbox at a time.

Settings as launched keep resume a continuation, not a relaunch. Changing the repositories or the add-ons would need a fresh image and fresh clones, which the snapshot cannot give. The model can still be switched in the running session as before (DL-014).

Minting again under the recorded tier, with the recorded routed credentials resolved again, follows DL-042 and DL-075 exactly as a recreated sidecar or a renewal does. Nothing about the old sandbox's credentials survives in the snapshot to be reused (DL-084).

The first message lives on the server so that a "Resume and send" survives the browser tab closing while the sandbox boots.

## Consequences

- `stopped` and `failed` stop being terminal for an interactive session. A reader of a session's state must allow `stopped` to `starting`: the session-state stream, the attach wait (DL-025) and `ls`'s live set (DL-012) all re-read it.
- The reconciler adopts a resumed session's sandbox by its session and run tags, and sweeps a run whose session was resumed again.
- A resume costs a quota slot and a sandbox, like a launch.
