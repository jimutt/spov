## Context

A CLI token comes from the device flow, which needs a browser session, and lasts 90 days (DL-006). A service account (DL-140) has no browser session, and a CI secret that lapses every 90 days stops a pipeline without warning.

## Decision

An administrator issues and revokes a service account's tokens. The routes are tagged `admin` and answer 501 on a local server.

- `POST /api/v1/service-accounts/{name}/tokens` with a `name` (a label, required, at most 64 characters) and either `expires_in_days` (1 to 1095; 365 when neither is given) or `no_expiry: true`. The answer carries the token once; the server keeps its hash, as for every token. It is a `spov_pat_` token in DL-006's format, held in the same table.
- `GET /api/v1/service-accounts/{name}/tokens` lists each token's id, label, creation time, last use, expiry and issuer, never the token. The issuer is recorded on the token row (`api_tokens.issued_by`, set only by this route) and shown as the admin's user id with their `@login` or address as a label.
- `DELETE /api/v1/service-accounts/{name}/tokens/{id}` revokes one.
- An account holds at most 10 usable tokens; an eleventh is a 409.
- Issuing and revoking each write an `admin_events` row (`service_account.token.created`, `.revoked`) with the token's id and label.

The account itself can list and revoke its tokens through `/api/v1/me/tokens`, as a user can, and cannot issue one; its own revoke writes the same `service_account.token.revoked` row, with the account as actor. A device flow cannot issue a token for a service account.

Removing an admin from the allowlist does not revoke the service tokens they issued: that would stop every pipeline they set up. DL-132's off-boarding counts the usable ones in its `allowlist.offboarded` row and names their accounts in a warning, and the listing shows who issued each, so they can be rotated.

## Rationale

- Issuing through an admin route is the only way that needs no sign-in, and it puts every CI credential in the audit trail.
- A year by default with an explicit `no_expiry` keeps a forgotten token from living for ever unless someone chose that.
- Two usable tokens at once is what a rotation needs (issue, switch the secret, revoke); ten leaves room for several workflows.

## Consequences

- Nothing warns before a token expires; the listing shows the date.
- A removed admin who kept a copy of a service token they issued can use it until it is revoked or expires. Whoever removes an admin rotates the tokens the off-boarding names: issue a new one, switch the pipeline's secret, revoke the old one.
- Deleting the account revokes all of them (DL-140, through `Service.Offboard`).
- The token routes join `adminOnly`, and a test shows an expired, a revoked and a disabled account's token each answer 401.
- The create answer carries `Cache-Control: no-store`. A label is trimmed and may hold no control characters. Revoking a token already revoked, or another account's, is a 404, as the listing no longer shows it. A deleted account takes no new token (409).
- A device code approved for a row that is not a person's issues nothing: the exchange answers `access_denied` and the code is deleted.
- The off-boarding's count of issued tokens is not one of its steps: a failure to read it is a warning and changes neither the steps nor the answer.
