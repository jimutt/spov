## Context

A security review (findings D-05 and D-10) found two ways for one allowlisted user to spend what everyone shares.

Image builds. With add-ons and `apt` (DL-033), every distinct valid selection is a new image variant, built on Modal on its first launch at the operator's cost (DL-016). A request may name 16 add-ons and 32 packages, so a loop of launches with a new package name each time builds without end, and the image registry grows by one image a build. The two build slots (`DefaultMaxVariantBuilds`) belong to the whole server process, so one user can hold both and every other user's first launch of a new variant is refused with "too many image builds in progress".

The repository listing. `GET /api/v1/repos` reads each tier's forge on every request (DL-042). Under the organisation's GitHub App that is the installation's rate limit, which launches, token renewals and gate 2 share, so one user listing in a loop can make every other user's launches and pull request checks fail until the hour resets.

## Decision

### Image build limits

Both limits apply on a shared (hosted) server only. A local server has one user on their own Modal account, and five new variants a day would get in the way of someone trying add-ons, so its builder is unlimited. `spov serve` sets `VariantBuilder.PerOwnerLimits` to true unless it runs as the CLI's own local server, and the zero value is unlimited. The repository listing cache below is a shared server's too: a local server (`Deps.Local`) reads the forge on every listing, because its CLI writes credentials to the keyring without telling the server, and it has no organisation App to protect.

| Limit | Value | When hit |
|---|---|---|
| Image builds running per user | 1 | The launch waits for its turn |
| New image variants per user | 5 in any 24 hours | The launch, or the session or job create, is refused with a 429 that says when the next one is allowed |

- A user is the session's owner (`attributionUser`). Admins are not exempt on a hosted server. The two global build slots stay, and a launch past them is refused as before (DL-016).
- Only a build this user's request actually starts counts. A variant that already exists, in the image registry or in Modal and whoever built it, never counts and never waits. A launch that joins a build already running for the same image name, started by anyone, neither counts nor waits. A build that fails still counts. A rebuild of a pruned image counts, since it starts a build.
- A launch that needs a build while the user already has one running waits for it, bounded by the launch's own limit (`config.DefaultLaunchTimeout`, a job's `ProvisionTimeout`), and then builds, unless the image has appeared meanwhile. It says "waiting for your earlier image build to finish" in its progress.
- A background rebuild spov starts itself, the one `pickVariant` starts while a launch boots the newest recorded build (`VariantBuilder.Start`), counts against the user whose launch caused it. It does not wait: when the user already has a build running, or has no new build left in the window, it is skipped silently and the next launch asks again, as for a build past the global bound.
- The refusal is made before any session, job, sandbox or build exists. `Service.refuseBuildOverLimit` runs in `Create` and `CreateJob` after the other request checks, and refuses only a request whose launch would build its image on the launch path: the exact image is not published and no older build of the request exists (`needsLaunchBuild`, which mirrors `pickVariant` without recording anything). It answers `ErrQuotaExceeded`, so the API maps it to 429 and `QuotaRefused` counts it as `image_builds`. The message names the limit and the time the next build is allowed. The CLI and the browser forms show a problem's `detail`, so the words reach the person unchanged.
- The launch checks the limit again where the build starts (`VariantBuilder.start`), because the create's check is advisory: two creates can pass together. A launch refused there fails with the same message, before any token is minted or sandbox created. A resume that needs a build is checked only there.
- `spov serve image build`, the operator's command, does not go through the launcher's builder and is not limited. A `VariantBuilder` call with no owner is not limited, and neither is any call when `PerOwnerLimits` is false.
- The counts are in memory, per replica, keyed by user ID, with an injectable clock (`VariantBuilder.Now`). The limits are fixed constants (`DefaultMaxRunningPerOwner`, `DefaultMaxNewPerOwner`, `DefaultOwnerWindow`); configuration keys for them are not built.

### The repository listing cache

- `GET /api/v1/repos` keeps each listing for 60 seconds (`RepoListTTL`), per organisation, user and tier, in memory on each replica. `Deps.UserRepos` now lists one tier (`RepoListing`), so the user's tier and the organisation's tier are cached apart and a user who has changed only one reads only that one. A listing through the forge a request resolved to (local mode, or no tiered listing configured) is keyed by the tiers that resolution chose.
- An error from the forge is not cached. A listing marked `Failed`, with a credential that could not be read or a platform whose forge failed, is served once and not kept. A plain listing that carries a warning is not kept either, since a warning there may be a failure.
- The cache holds at most `RepoListMaxEntries` (1024) entries. Past that, expired entries go first and then the oldest.
- Concurrent misses of one key make one read (`repoCache.load`, a `singleflight.Group` per key). The read runs apart from the request that started it, bounded by `repoListTimeout` (2 minutes), so one caller hanging up neither cancels it nor hands its error to the others; a caller whose context ends stops waiting.
- Storing a user's credential, or removing one that was there (`PUT` and `DELETE /api/v1/me/credentials/{platform}`), drops that user's own-tier and plain entries, never their organisation-tier entry, which their own credentials do not reach (`ForgetOwnRepoListings`). A delete that found nothing drops nothing. Off-boarding (DL-132) drops every entry of the user (`ForgetRepoListings`). An admin storing or removing the organisation's App (`/api/v1/org/github/{platform}`) drops every entry of the organisation, since the organisation's tier is in each user's listing. The routed credential handlers do not matter and do not.
- The launch-time repository check (`git.RepoChecker`, DL-043) and gate 2 (DL-050) are not behind this cache.

## Rationale

- The values are the ones the maintainer accepted for a first public deployment: a person who is building something real needs one build at a time and a handful of new images a day, and a loop needs far more.
- Counting at the point a build starts, and not at create or in the registry, is what makes "an existing variant never counts" true without a second source of truth: a launch whose image exists never reaches the build, and one that joins a running build never starts one.
- Waiting in the launch, not refusing, for the per-user running limit fits the launch's shape: it is already a wait of minutes for a build, with a bound of its own. A background build does not wait, because a wait would hold a detached goroutine for a user who did not ask for it.
- The create-time check exists so the person is told at once, with a 429 and a time, instead of being given a session that fails; the build-time check exists because the create cannot be exact.
- Caching per tier keeps each credential's listing separate, so a user who changes only their own token does not make the organisation's App be read again, which is the rate limit that is being protected.
- A cache keyed by user does not stop many users from each reading the organisation's tier once a minute. It bounds one user, as the finding asks. A cache shared across users would bound the installation but would show a user a listing built through the organisation's credential for someone else, which is the same listing, so it is a possible later step.

## Consequences

- The counts and the cache are per replica and are lost on restart. With N replicas a user can start up to N times the limit in a day and cause up to N forge reads a minute per tier. A shared counter in the store would remove that, at the cost of a table and a query on the launch path. The record does not build it.
- The cost of a variant is still the operator's. An operator who does not want users to trigger builds sets `modal.build_on_demand: false` and prebuilds with `spov serve image build`; `deploy/README.md` says so.
- A user who reaches the limit still launches on any image that exists. A new variant of an old request, whose newest build exists, launches on that build and only loses the background update.
- A launch that waited for the user's earlier build and then finds its own image published (built by someone else meanwhile) does not build.
- A listing can be up to 60 seconds behind a repository created or removed on the forge. A credential change shows at once on the replica that served it, and on any other within 60 seconds, since each replica keeps its own cache and only the one that served the change drops its entries.
- A listing in flight while a credential changes can store its result after the drop and serve it for up to a minute. The window is one request.
- `Deps.UserRepos` changed shape: it takes a tier and returns a `RepoListing`, and `server.CombineRepoListings` joins the tiers as the handler does. The CLI's `hostedCredentials.reposOfTier` replaces `reposByTier`; DL-042's wording naming `reposByTier` is stale and this record says what replaced it.
- A local server is never limited, so a person running their own server can build as many variants as they like at their own cost.
