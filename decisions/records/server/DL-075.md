## Context

A routed credential (DL-072) is useless if it has to be asked for every time: an opt-in that is easy to forget pushes people to `open` egress and pasted tokens (decided 2026-11-05). But a session in a repository someone else wrote should not reach every registry the user can, and a project file must not be able to say where credentials go (DL-026). Jobs run unattended and already keep a git-access default of their own (`sandbox.job_git_access`, DL-043).

## Decision

### What a launch attaches

At launch the server resolves the caller's candidates: their own routed credentials and the organisation's (DL-074). When a personal and an organisation credential share a host, the personal one is the candidate for that host and the organisation's is left out for this session. Two personal credentials sharing a host are refused at launch, naming both, because neither tier can decide between them; the user narrows to one.

Then the attached set is:

1. **The launch's own list,** when it names one (`--credentials a,b`, `credentials` in the request): exactly those, asked-only ones included. An unknown name refuses the launch. `--no-credentials` (`credentials: []`) attaches none.
2. **Otherwise the default:** every candidate whose attach mode is `always` (an `asked` credential attaches only by name, step 1),
3. **narrowed by the configuration's list** when it has one: `sandbox.credentials` (and, for a job, `sandbox.job_credentials`) in the user or project file, a list of names or `none`. It keeps only the named candidates that the default already had. It never adds an `asked` credential and never adds one the caller does not hold, so a project file can only take access away. A name it gives that the caller does not hold is ignored with a note in the launch's progress, because a project file is shared and its names may be someone else's.

The CLI sends the configuration's list as `credentials_preferred`, and the server applies step 3 to it. The request's `credentials` (step 1) is set only by a launch flag, the job form or the API. The browser's forms send neither, so a browser launch gets the default.

### Jobs

`sandbox.job_credentials` is a job's own narrowing, as `sandbox.job_git_access` is for git access. A job never takes `sandbox.credentials`. When it is unset, a job gets the default (step 2) with no narrowing. `spov jobs create --credentials` and `--no-credentials` set step 1.

### Recorded on the session

The attached set is recorded on the session (`session_routed_credentials`: name, tier, hosts, paths, scheme, preset), never the secret. A recreated sidecar resolves each recorded credential again in its recorded tier (DL-034's recreation, DL-042's rule that a recorded tier is the only one). A credential removed since is left out of the recreated sidecar with a note in the session's log; it is never replaced by another tier's credential of the same name. A recorded credential whose route changed since keeps its recorded route for this session.

### Needs

A project file may list the hosts it needs: `sandbox.needs: [npm.acme.com]`. The CLI sends them with the launch. When no attached credential covers a needed host, the launch's progress and the session log say so, naming the host. That is a note, not a refusal: the host may be public, or the user may mean to launch without it.

## Rationale

The default is everything because forgetting is the common failure, and a forgotten credential looks like a broken registry, which people fix with `open` egress and a pasted token. Narrowing by the credential (`asked`), the configuration and the launch covers the cases where everything is too much: a credential that should reach only some repositories, a repository someone else wrote, a one-off launch.

A project file only narrows. It may name credentials, but naming one never attaches it, so DL-026's rule that a project file cannot say where credentials go still holds. The launch's own list may attach an `asked` credential, because the launch is the user's own act.

Personal-first on a shared host follows DL-042. Refusing two personal credentials on one host follows DL-034's one credential per host: the proxy picks by host, and a first match would be an accident.

## Consequences

- A user with a routed credential and no configuration sends it to every session. The session page says which credentials a session holds (DL-077).
- A job on a repository the user knows less well can be narrowed in one place, `sandbox.job_credentials: none`.
- Tests: `TestEveryCandidateAttachesByDefault`, `TestAProjectFileCanOnlyNarrowCredentials`, `TestAnAskedCredentialAttachesOnlyByName`, `TestAJobTakesItsOwnCredentialDefault`, `TestAPersonalCredentialTakesASharedHost`, `TestARecreatedSidecarFollowsTheRecordedCredentials`, `TestANeededHostWithoutACredentialIsNoted`.
