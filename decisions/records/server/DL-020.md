## Context

An agent can stop and ask: a permission request before a tool runs, or a question form from its built-in `question` tool. A person watching in the browser needs to see the ask, answer it, and see afterwards how it was settled. The requirement is that replies remain owner-authorised, auditable writes that cannot accidentally grant wider authority than the request in front of the reader.

OpenCode's permission reply takes `once`, `always` or `reject`. `always` saves the permission for the project, so it outlives the request it answers.

What the pinned OpenCode build does with asks was measured in spike S-F1 (see Measurements). The measurement that shapes the design is that the build's listing routes for pending permissions answer 400, so a pending ask cannot be read from the sandbox.

## Decision

### A pending ask is read from the stored log

The recorder keeps the five ask frames by name (`ephemeralNames`: `permission.asked`, `permission.replied`, `form.created`, `form.replied`, `form.cancelled`), the non-durable frames it stores anyway (see DL-017). The log carries what a page needs as `LogEvent.ask` (`storedAsk`): the request or form id, a permission's action, resources and tool call, a form's title and fields, a reply's decision and a form's answer. It is set only on the sandbox's own ephemeral frames, whose rows say `source: "ephemeral"`. A form field's link survives only as an absolute http or https address (`webURL`).

The browser derives each ask's status in `askStates` (`web/src/lib/asks.ts`) from the log it already holds:

- a permission is pending from its `asked` until its `replied`, and a form from its `created` until its `replied` or `cancelled`;
- either is also settled, as unanswered, when a turn of its conversation ends after it (`session.execution.succeeded`, `failed` or `interrupted`);
- either still pending once the session has ended reads as unanswered.

A turn ending settles a permission because an interrupt drops a pending permission with no reply frame, and a reply to it then answers 404. The supervisor applies the same rule to a job (`unansweredAsks`; see DL-054).

Nothing may depend on listing pending permissions. A job cannot ask questions: `PermissionsForKind` denies the `question` tool, so a job parks only on a permission (see DL-040).

### Answering goes through the server

Answering is a per-act write like a message (see DL-019): the same authorisation, connection reuse, mint budget, per-session rate limit and conversation rule, and the session must be running. An ask id carries the prefix OpenCode gives it (`per_` for a permission, `frm_` for a form) and is held to a message id's length and character set.

- `POST /api/v1/sessions/{ref}/permissions/{id}` takes `{decision: "once" | "reject", message?}`. `always` is refused as an invalid request (422). A saved permission is wider authority than the request in front of the reader, and refusing it server-side keeps that from depending on the browser. The message travels only with a reject, where OpenCode hands it to the model, and is bounded like a message; a message with an allow is refused. The way to save a permission for good is `spov attach`, through OpenCode's own TUI.
- `POST /api/v1/sessions/{ref}/forms/{id}` takes `{answer}` keyed by the form's field keys, and `DELETE` on the same path dismisses the form. Each value must be OpenCode's `Form.Value` (a string, number, boolean or list of strings) and the whole answer is bounded like a message. Whether it fits the form is the sandbox's to say.
- **The id must be a stored ask of this session.** `askOf` finds a `permission.asked` or `form.created` event with that id (`FindEvent`), checks that it came from the sandbox's ephemeral source and that the id inside the frame matches, and takes the conversation from the stored row, never from the caller. An unknown id is a 404 worded as "no such request" (`ErrNoSuchAsk`). The server never relays an id it has not seen asked (`TestOnlyAStoredAskCanBeAnswered`).
- **A job's run must be live.** An answer to a job that is queued, provisioning, delivering or finished is refused as a message is (`jobRefusesAMessage`), except that a blocked job is the one to answer. An allow in the other states would run a tool while the job is being judged.
- **Each act leaves an audit marker** naming who acted and what they decided, never the answer's words: `spov.session.permission.replied`, `spov.session.form.answered`, `spov.session.form.dismissed`. The page hides them with the other audit markers. A failure to write one only warns.
- The outcome is read from the stored `permission.replied`, `form.replied` or `form.cancelled`. The reply's own 204 says only that the sandbox took it. The routes answer 202.
- On a job, an accepted permission answer also writes `spov.job.answered` (`jobs.MarkerAnswered`), which the supervisor reads as the release of a blocked job (see DL-054).
- `contract.Used` holds the two reply routes and the form DELETE (see DL-035).

### The card in the transcript

A pending ask is drawn where the agent asked, as a card the reader acts on (`AskCard.svelte`). It is its own block in `blocksOf`, so a folded run never hides it, and it sits under the tool call it belongs to. The frames that settle it are read into its status and are not drawn. The composer's status bar says "Waiting on your answer" while an ask is pending (`composerStatus`), as the cue when the card is scrolled out of view (see DL-059).

- A **permission card** names the action and its resources in monospace. It offers Allow once and Reject; Reject opens an optional message to the agent. There is no "always". The reject message is not in `permission.replied`; it shows on the tool call's failed line.
- A **question card** renders the form schema: each question with its header, options as radio buttons (single) or checkboxes (`multiselect`), a free-text "Other" when the field allows `custom`, and booleans, numbers and external links. It has Submit and Dismiss. The answer is keyed by field key, and the field logic is in `asks.ts` (tested in `asks.test.ts`). A field type the page does not draw says to answer with `spov attach`. A hidden field, or one whose `when` does not hold, is neither drawn nor sent.
- A **settled card** collapses to one line: "Allowed once", "Rejected", "Answered: Blue, No" or "Dismissed". A pending ask on a session that has ended reads "Not answered". One answered "always" from an attached TUI says so.
- An answer in flight disables the card and shows "Sending…". A refusal shows the problem and restores the card. A taken answer says "Sent. Waiting for the session to confirm." until the log settles it.
- What the sandbox writes is data. An external field's link is drawn as a link only for an absolute http or https address. Blocks are keyed by position, and a draft or answer has no prototype for a field's key to reach.

## Rationale

- The listing routes are broken at the pin, and a per-viewer read of the sandbox is what DL-018 rules out in any case. The ephemeral frames carry what the page needs: what is asked, of which tool call, and with which options.
- Replies are the writes most able to widen what an agent may do, so they are bound to an ask the server has seen, to a live run, and to a recorded actor.
- The ask belongs where the agent stopped, beside the tool call it holds up.

## Measurements

Spike S-F1 ran against OpenCode 2.0.22, the local binary with a scripted fake model and a plugin that makes `glob` ask; no sandbox and no key. Re-run: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SF1Asks -v`, and `-run SF1Tools` for the tool half (`TestIntegrationSF1Asks`, `TestIntegrationSF1Tools` in `queue_spike_integration_test.go`). Re-run it on an OpenCode bump.

1. A permission ask raises `permission.asked`, ephemeral, with `data.id` (`per_…`), `action`, `resources`, `save`, `metadata` and `source` (the tool call). `POST /api/session/:id/permission/:requestID/reply` takes `{decision: once | always | reject, message?}`, answers 204 and raises `permission.replied` (`requestID`, `reply`), also ephemeral.
2. Allowed once, the tool runs and the execution reaches `succeeded`.
3. Rejected with a message, the tool fails with `error.type: "permission.rejected"` and the message as `error.message`. The model receives both and the execution continues to `succeeded`. A reject is a `permission.rejected` with no interrupt, which gate 3 still reads as a refusal (see DL-050).
4. `GET /api/session/:id/permission` and `GET …/permission/:id` answer 400. OpenCode fails its own response validation on `metadata.path`.
5. The built-in `question` tool (`{questions: [{question, header, options: [{label, description}], multiple}]}`) raises ephemeral `form.created` with a form id (`frm_…`), `title`, `metadata: {kind: "question", tool: {messageID, id}}`, and fields `q0`, `q1`, … each a `string` (single choice, `custom: true`) or a `multiselect`. The form is under `data.form`.
6. `POST /api/session/:id/form/:formID/reply` takes `{answer: {q0: "Blue", q1: ["No"]}}`, keyed by field key; an index key is refused as `FormInvalidAnswerError`. It raises `form.replied` (`id`, `answer`), and the tool succeeds with a sentence naming each answer.
7. `DELETE /api/session/:id/form/:formID` dismisses a form and raises `form.cancelled`. The tool fails as aborted ("The user dismissed this question") and the execution ends `interrupted` with reason `shutdown`.
8. An interrupted turn settles asks unevenly (`PermissionInterrupted`, `QuestionInterrupted`): a pending form gets `form.cancelled`, but a pending permission is dropped with no frame, and a reply to it answers 404 `PermissionNotFoundError`.

## Consequences

- A change to OpenCode's ask frames shows up first as a card that never appears or never settles, so the S-F1 re-run is the check on a bump.
- `TestProjectionAgainstRealSandboxFrames` holds captured frames of all five ask frames, checks that each is kept by name, and checks that an ephemeral delta is still dropped.
- A blocked job's resume note does not name `spov attach` for a permission the page can answer.
- `sessiondetail.svelte.test.ts` tests only the wiring; the field logic is tested in `asks.test.ts` and the card in `askcard.svelte.test.ts`.
