## Context

OpenCode Go (a subscription that serves a set of open models) and OpenCode Zen (pay-as-you-go credit) are reached through an OpenCode Console account. Their key is not one of the provider keys in spov's catalogue (DL-013), so without a sign-in neither can be used from a spov session. The console recommends its own sign-in, `opencode auth login opencode` in OpenCode 2, over a pasted key.

Measured at OpenCode 2.0.21 and 2.0.22 (2026-10-03), by tracing the binary and then running the same flow from a script:

- The sign-in is an OAuth device flow at `https://opencode.ai/console/auth/device/code` with client ID `opencode-cli` and `supports_org_scope: true`. The device code lasts 600 s and the token endpoint is polled every 5 s.
- After the user approves in a browser, `/auth/device/token` answers `access_token`, `refresh_token`, `expires_in`, `org_id` and `token_type`. Both tokens are opaque strings. The access token lasts 30 days (`expires_in` 2,592,000 s). OpenCode keeps the result in the `credential` table of its own `opencode.db` and refreshes it when less than 5 minutes remain.
- Polling the token endpoint is not fully reliable: one of three sign-ins got `server_error` about 4 minutes in, and the other two worked on the first approval.
- The same access token opens the console's other APIs (`/api/user`, `/api/orgs`, `/api/v2/config`, web search), so it is an account credential, not only a spending one.
- A refresh (`grant_type=refresh_token` at `/auth/device/token`) returns a new access token (again 30 days) and a new refresh token. The previous access token stops working at once (`/api/user` answered 401 straight after). Sending the previous refresh token again is answered `invalid_grant` and revokes the whole grant: the newest access token answered 401 and the newest refresh token was refused too. A refresh therefore ends the token in use, and two holders refreshing one grant revoke it.
- The public Go endpoint `https://opencode.ai/zen/go/v1` refuses the OAuth token ("Invalid API key", in either `Authorization` or `x-api-key`, with or without an org header). The console config does not point there: `GET /console/api/v2/config` with the token as a bearer returns both providers, with their models served from `https://opencode.ai/inference/go/openai/v1` and `.../inference/go/anthropic/v1` for Go and `/inference/{openai,anthropic,google}/v1` for Zen, an `x-opencode-org-id` header, and a key template `{env:OPENCODE_CONSOLE_TOKEN}` that is not a secret.
- The gateway accepts the token as a bearer on both formats (the Anthropic-format path also accepts `x-api-key`; the OpenAI-format path only a bearer). A bogus bearer gets 401 "Invalid credential" and none gets "Go requires a credential". Every request needs an `x-opencode-session` header ("MissingSessionID" otherwise). A workspace privacy setting can make the gateway answer "requires Global regions".
- OpenCode 2.0.21 treats `OPENCODE_API_KEY` as a console connection: in an empty home with the token in that variable it loaded the console config, listed all of Go's models at the `/inference` URLs and answered a prompt on `opencode-go/glm-5.3-flash` for $0.0005. With only a placeholder in the variable and no proxy it activated both providers too. In that local run the test model used its shell tool unprompted, and the token ended up in a saved shell output and in OpenCode's database. A sandbox holding only a placeholder would have exposed nothing, which is why it must hold only a placeholder.

## Decision

### The server runs the sign-in and holds the grant

The spov server runs the device flow for a user and holds the resulting grant as that user's OpenCode credential. It never reads the grant of the user's own OpenCode.

1. `POST /api/v1/me/opencode/connect` starts a flow and returns the verification URL, the user code and an attempt ID. `GET /api/v1/me/opencode/connect/{id}` reports the attempt and polls the console once when a poll is due. `GET /api/v1/me/opencode` shows the connection and also advances a pending attempt, so an approval is collected even if the CLI or the tab that started it has gone. `DELETE /api/v1/me/opencode` forgets the connection. The attempt is stored, so any replica can answer for it. The grant never passes through the CLI or the browser, so a hosted and a local server behave the same.
2. A poll runs under the user's lock (below), so a CLI and a browser asking about one attempt never both spend its device code. The poll is detached from the request, so one that spends the device code still stores the grant it got.
3. There are two ways in, both calling the same endpoints: `spov login opencode` (a positional name, so it cannot collide with a configured platform; `spov logout opencode` disconnects) and the Settings page's "Connect OpenCode" section (DL-062). `spov credentials add OPENCODE_API_KEY` stores a pasted console key as the fallback, and also covers a deployment that exports one key for everyone.
4. The grant (access token, refresh token, expiry, org ID, a generation number and a needs-reconnect flag) and the attempt in progress are two slots. A hosted server keeps them as sealed rows `opencode:grant` and `opencode:attempt` in the credential store (`SealedConsoleStore`); a local server keeps them in the machine's credential store (`LocalConsoleStore`). The credential listing leaves them out and `CanonicalPlatform` refuses them, so the generic credential API can neither read, write nor delete them (DL-008). No endpoint answers with a token or the device code. A hosted server without `SPOV_CREDENTIAL_KEY` answers 501 to the sign-in endpoints.
5. The console's verification link must be on the console's own origin, or the sign-in does not start.
6. spov's own console calls (the device flow and refreshes) send a `spov/<version>` user agent, so the console can tell spov's sign-ins from OpenCode's own. A sandbox's model requests are OpenCode's own and keep its user agent.
7. A connected grant counts as the user holding `OPENCODE_API_KEY` for `have_key` and for the model check, even when its access token has lapsed, since a launch refreshes it. When a user has both a grant and a stored key, the grant is used; a grant that cannot be used leaves the stored key in place. `GET /api/v1/models` marks `sign_in: "opencode"` on the OpenCode providers, and only where a session would be given the sign-in (`consoleCarried`) (DL-013). A grant the console refused gets its own refusal, "reconnect OpenCode", apart from the missing-key one.
8. Disconnecting deletes the grant's tokens and keeps its generation number, so a later sign-in is newer than anything a live session holds. The console has no revocation endpoint that spov knows of, so the grant stays valid until it expires or the user ends it in the console, and Settings says so.
9. A failed attempt (an expired device code, a denial, a console error) ends the attempt and the user starts again. A `server_error`, a `temporarily_unavailable` or a 5xx while polling is retried up to five times before it ends the attempt. `slow_down` widens the polling interval by 5 s and does not end the attempt.
10. The prep pass (DL-047) does not use the grant: its calls are made by the control plane with its own provider keys, not by an agent harness.

### A grant is refreshed only at launch, by one holder

A launch that carries the grant refreshes it first if its access token would expire before the session's timeout plus one hour (`ConsoleRefreshMargin`). Nothing refreshes on a timer, so an idle grant is left alone; with 30-day tokens a user refreshes about once a month. Only `freshConsoleToken` refreshes, and nothing imports a grant from the user's own OpenCode.

1. The refresh takes a per-user lock: a transaction-scoped Postgres advisory lock in hosted mode (`CredentialStore.Lock`, inside `Store.Tx`), and an in-process mutex locally. It then reads the grant again, because another launch may have refreshed it while this one waited, and uses it without refreshing when it is now new enough. Two launches never send the same refresh token.
2. The new grant is stored before it is used. The locked section runs detached from the launch with its own time limit, so a launch deleted or timed out mid-refresh still stores the grant the console has already rotated. If the refresh succeeds and the write fails, the grant is lost, since the old tokens are dead: the launch fails and asks the user to connect again. A launch never proceeds on a token it could not store.
3. A refresh answered `invalid_grant` marks the grant as needing a new sign-in. Launches that need it are refused with "reconnect OpenCode", worded like the missing-key refusal. Live sessions keep their token until it expires or the next refresh. Any other refresh failure leaves the grant alone: the launch continues on the current token if it is still usable, with a note, and without one otherwise.
4. After a refresh, the server writes the new access token into the sidecar of each of the user's live sessions that hold the grant, in the background so the launch does not wait. The write is `spov-proxy set-key OPENCODE_API_KEY` with the token on stdin (`credproxy.SetKeyCommand`), under the session's renewal lock, which a sidecar's recreation also takes. The proxy rereads its file when a key changes, and `set-key` and the forge's `set-token` take a file lock in the sidecar so writes from two replicas take turns. Between the refresh and the write those sessions' model calls get 401.
5. Each session records the grant generation its sidecar holds (`sessions.opencode_grant`, written only by `SetOpenCodeGrant`). The once-a-minute renewal pass (`RunRenewals`) writes the token into any session that is behind. A write that failed is not retried for 10 minutes (`pushBackoff`), because every write is an exec and an exec resets the sandbox's idle clock (DL-021). A sidecar that holds no OpenCode key records 0 instead of being retried. A recreated sidecar gets the current token and records its generation. A sandbox launched without the sidecar holds the token in its environment, which cannot be replaced: it records none and keeps its token until it expires.

### The token stays in the proxy

The main container holds a placeholder `OPENCODE_API_KEY`. The sidecar sets the user's real OpenCode credential as a bearer on `opencode.ai`, and only on a short list of paths (DL-034).

- The catalogue has two providers, `opencode-go` and `opencode` (Zen), both keyed on `OPENCODE_API_KEY` (`prep.OpenCodeKeyEnv`) with API host `opencode.ai`, a bearer header and the path list `openCodeAPI`. The proxy holds one entry per key variable, so its refusal of two entries on one host holds, and the catalogue test requires providers that share a variable to share its API.
- OpenCode loads the console config itself, through the sidecar, and sends its model requests to the `/inference` gateway the config names. spov writes no provider config of its own for these providers and never hands OpenCode a console connection directly, which would put the real token in OpenCode's database inside the sandbox.
- The credential is the user's grant if they have one, otherwise a stored or deployment `OPENCODE_API_KEY`. The sidecar gets the current access token at launch and later ones as above. A server without the proxy leaves the grant out, says so in the launch log, and refuses an OpenCode model that would need it, because unlike a provider key the token opens the user's console account and the main container is where the agent reads.
- Unlike other providers, `opencode.ai` has a path list, because this token also opens the console account. The proxy removes the client's credential headers from every request on that host and sets `Authorization: Bearer` only on:
  - `GET /console/api/v2/config`, so OpenCode can load its providers (a path entry may name a method, and this one names GET);
  - `/inference/` and everything under it, the model gateway;
  - `/zen/`, Zen's public API, which neither a sign-in nor a pasted key has been seen to use and which is kept in case OpenCode falls back to it;
  - `/console/api/websearch`, which OpenCode's web search tool calls with the same token.

  A path ending in `/` is a prefix; any other matches exactly; a path with percent-encoding, a dot segment or an empty segment matches nothing. Every other path on the host, such as `/console/api/user` or billing, gets no credential. A new console path used by OpenCode shows up as a 401 on that feature, which fails closed.
- Everything else is the provider-key rule: response scrubbing, unread event streams, sidecar recreation and the launch log's list of held keys. OpenCode's own user agent and `x-opencode-session` are left alone, and a gateway refusal such as the regions one reaches the user unchanged.

## Rationale

Reusing the sign-in of the user's own OpenCode would remove one click, but a grant cannot be shared: each refresh replaces the refresh token and ends the previous access token at once, and reusing an old refresh token revokes the whole grant, so spov and the user's OpenCode would sign each other out. Reading another program's database would also tie spov to a schema that changed twice within OpenCode 2. The server runs the flow because it already holds every credential a session uses and must be the only holder that refreshes this one. A flow in the CLI would hand the grant to a process that then has to give it away. A device flow beats a key for the user: the console recommends it, and someone already signed in to opencode.ai approves with one click, where a key means opening the console, creating a key and pasting it.

Refreshing at launch and not on a timer follows from the rotation. Every refresh breaks the token live sessions are using, so the fewer refreshes the better. A user's sessions all use the one token and a hosted server can run more than one replica. A launch is the only moment a token has to last for a known span, and a timer would keep refreshing grants nobody uses, each refresh meaning a write into every live sidecar. The GitHub token renewal pattern (DL-021) does not fit, because a GitHub re-mint leaves the old token valid. The lock plus a re-read is cheaper than recovering from a revoked grant, the user's only OpenCode credential in spov. Pushing the token into live sidecars, instead of letting them fail (the write path already exists for GitHub tokens), spares a session started an hour earlier a model call that fails for no reason the user can see. The write costs little: it happens about once a month per user, for that user's live sessions only.

The path list differs from other providers because a provider key is only a spending credential, where inference is both the risk and the purpose, while this token also opens the account. Limiting it to the config, the gateway and web search keeps an agent from reading or changing the account through the proxy, and OpenCode still works. A bearer is used on every path because the gateway accepts it on both formats, and the client's `x-api-key` is removed like every client credential, so one header covers all. Letting OpenCode load the console config, instead of copying its gateway, headers and model formats into spov, avoids drift: the console can change all three.

## Measurements

Measured at OpenCode 2.0.21 and 2.0.22 on 2026-10-03; the first bullets of Context are measurements too.

- End to end through the sidecar with a real sign-in (2.0.22): the launch took 4 s. The main container held only a placeholder in `OPENCODE_API_KEY`, and the real token was in no file or process environment under `/root`, `/etc`, `/workspace`, `/tmp` or `/proc`. OpenCode loaded the console config through the proxy and its `opencode-go` models pointed at `/inference/go/openai/v1` and `/inference/go/anthropic/v1`. From the main container, with the placeholder as a bearer, `/console/api/v2/config` answered 200 (the proxy set the token) and `/console/api/user` answered 401 (it did not). `opencode-go/glm-5.3-flash` answered a prompt in 2 s.
- After a refresh ended the token a live sidecar held, `spov-proxy set-key OPENCODE_API_KEY` gave it the new one, and the next prompt answered in 5 s, with no restart of OpenCode or the proxy.
- A pasted console API key works the same way. From outside a sandbox, `GET /console/api/v2/config` with the key as a bearer answered 200 with the same two providers and the same `/inference` base URLs and key template, and a call on `/inference/go/openai/v1` answered 200 in 0.8 s. Through the end-to-end test with the config path limited to GET, the launch took 5 s, the main container held only the placeholder, the config answered 200, `/console/api/user` answered 401 and `opencode-go/glm-5.3-flash` answered in 7 s. A pasted key never goes to `zen/go/v1`, so `/zen/` is not needed for it either.
- Route check with the main container's own egress closed (the per-provider proxy spike): for both `opencode-go` and `opencode`, the first call was `GET opencode.ai/console/api/v2/config`, sent through the sidecar with the proxy's invalid bearer and answered 401, 1 s after the prompt. The other providers passed.
- Gateway answers with a bearer: `glm-5.3-flash` and `minimax-m2.7` answered 200, and `deepseek-v4-flash` answered "requires Global regions". The sign-in's config listed 29 Go models, 26 of them served from the OpenAI-format path and 3 from the Anthropic-format one, and 81 for Zen; a pasted key's config listed the same two providers (81 and 29 models).
- The console config the sign-in received carried no `websearch` entry, so `/console/api/websearch` is unexercised.
- Without a real token the per-provider proxy spike still shows the route. Re-run the end-to-end check (`TestIntegrationOpenCodeConsoleThroughTheProxy`) on an OpenCode bump: `SPOV_CONSOLE_SPIKE=1 go test -tags integration ./internal/session/ -run OpenCodeConsole -v`. It needs a person to approve the sign-in at the URL it logs, uses a little of the account's allowance, and revokes the grant at the end. With `SPOV_CONSOLE_KEY_FILE=<file>` naming a file that holds a console API key it launches with that key and skips the refresh. The route check: `go test -tags integration ./internal/sandbox/ -run SKModelCallsThroughTheProxy`.
- Locking: `TestConcurrentLaunchesRefreshOnce` has six concurrent launches refresh once, `console.Fake` enforces rotation and reuse detection, and `TestACredentialLockSerialisesRefreshes` checks the advisory lock against real Postgres.

## Consequences

- Any user with a console sign-in or key can run Go and Zen models in a session. Without either, OpenCode's free Zen models (key `public`) are unchanged.
- A grant lives on the server for up to 30 days at a time and can open the user's console account, so it is sealed like other credentials and kept out of the sandbox. The sign-in adds three endpoints and a credential kind, so the generated API client is regenerated (DL-005).
- A refresh briefly breaks the user's other live sessions until the write reaches them, usually within one pass. A model call that fails in that window is retried by OpenCode or fails that turn.
- The pattern assumes refresh tokens stay single-use with reuse detection, as measured. If the console relaxes that, the lock stays correct.
- A new OpenCode release can change which console paths it calls; the route check above is re-run on a bump.

## Known gaps

- spov signs in as OpenCode's own client, `opencode-cli` (one constant, `console.ClientID`), because it has no client ID of its own registered, and registering one is the console owner's step. The sessions run OpenCode, so OpenCode's ID describes the traffic honestly until there is a better one. A client ID for spov is wanted from OpenCode. A grant is refreshed with the client ID it was issued to, so a switch later means each user connects once more.
- spov depends on the gateway path the console config names (`/inference/...`), and its stability is unconfirmed. If the console moves it, OpenCode follows the config and the proxy's `/inference/` rule needs a new path.
- The grant's refresh-token lifetime is not known, so a grant left unused long enough may expire and the user connects again.
- The console has no revocation endpoint that spov knows of, so disconnecting forgets the grant on the server without ending it at the console.
