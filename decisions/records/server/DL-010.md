## Context

A hosted server is a long-running service that several people use through a browser and the CLI. It runs as one or more replicas and talks to Modal with a credential of its own. The decisions that are expensive to reverse are the shape of the origin (cookies, CORS, OAuth redirects) and where secrets come from.

## Decision

### Image and files

The image is `CGO_ENABLED=0 go build -trimpath -ldflags "-s -w"` of `cmd/spov`, on `gcr.io/distroless/static-debian13:nonroot`, pinned by digest when deployed. The entrypoint is `/spov` and the default command is `serve`, so a Kubernetes `args:` reads as the whole invocation. Distroless static carries CA certificates, tzdata and a nonroot user, which `scratch` lacks. Nothing in the stack needs cgo. One image serves the API, runs `serve migrate`, and serves the built web app, which is embedded in the binary (see DL-055). Bun is a build-stage tool only.

The deployment files are in `deploy/`: `Dockerfile`, `compose.yaml` (Postgres 18 and the server, with `SPOV_MIGRATE_ON_START=true`), `kamal/` and `k8s/` (Deployment, Service, a migrate Job and a Secret template). Kubernetes manifests are plain YAML, and Helm is not adopted. Migrations run before the new version serves. The Kamal pre-deploy hook runs `kamal app exec ... -- serve migrate up`, and the Job does the same on Kubernetes, so a bad migration fails the deploy and does not crash-loop replicas that migrate at start (see DL-003). The hook needs its executable bit set with `git update-index --chmod=+x`.

Kamal is run from the repository root with `-c deploy/kamal/config/deploy.yml`, which keeps one build context, the same as `docker build -f deploy/Dockerfile .`. The config names its hooks and secrets under `deploy/kamal/.kamal/`. The secrets file is gitignored and kept out of the image's build context. The pre-deploy hook passes the same config path to `kamal app exec`, so a hook that calls `kamal` must name the config itself (`TestKamalRunsFromTheRepositoryRoot`).

### Single origin

The web app and the API share one hostname. `/api/*`, `/livez`, `/readyz`, `/startupz`, `/login`, `/oauth/*` and `/device` belong to the server, and everything else is the web app's. As a result cookies are `SameSite=Lax; HttpOnly`, and `Secure` whenever the public URL is https (the server warns when it is not), no CORS configuration exists, and a separate web origin is ruled out. The standard library's `CrossOriginProtection` works with no trusted origins.

The browser guard's `Host` check accepts the host of `SPOV_PUBLIC_URL` (see DL-006). That is the one externally visible origin, and it is also the base of the OAuth redirect. A server that is its own origin, which is every loopback listener, needs none, and the guard uses the listen address. A wrong `SPOV_PUBLIC_URL` fails login visibly and does not weaken the guard. A malformed one is refused at startup. The GitHub OAuth app and GitHub App need the public URL at registration, so a staging deployment needs its own.

### Listen address

A hosted `spov serve` listens on `--listen`, then `SPOV_LISTEN`, then `127.0.0.1:8080` (`DefaultListen`). Binding every interface is the deployment's explicit choice. `compose.yaml`, `kamal/config/deploy.yml` and `k8s/deployment.yaml` each set `SPOV_LISTEN=:8080` (`TestTheDeploymentFilesBindEveryInterface`). A server that is reachable from the network should be so because someone said so. A bare host running `spov serve` with a database and no `SPOV_LISTEN` stays unreachable and is not exposed, while a container that forgets the variable fails visibly at its health check. A container run without `SPOV_LISTEN` or `--listen` is unreachable from outside its network namespace, and the deployment guide says so.

### Configuration

Hosted configuration is the environment: `SPOV_LISTEN`, `SPOV_PUBLIC_URL` (required behind a proxy), `SPOV_DATABASE_URL`, `SPOV_SERVER_TOKEN`, `SPOV_CREDENTIAL_KEY`, `SPOV_GITHUB_OAUTH_CLIENT_ID` and `_SECRET`, `SPOV_GITHUB_APP_*`, `SPOV_ALLOWLIST_FILE`, `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET`, `MODAL_ENVIRONMENT`, and model provider keys. The server reads the user config file and the environment, never a project file. The config file carries sandbox defaults (`sandbox.*`, `opencode.*`, `platforms.*`) and has no field for a secret. An administrator can also store the organisation's GitHub App sealed in the database, and the environment wins when it sets one (see DL-042).

A hosted server refuses to start without the credential proxy embedded in its binary, unless `SPOV_TOKENS_IN_SANDBOX=1` is set, in which case every sandbox holds its tokens and keys (see DL-034).

### Health

`/livez` answers 200 whenever the process can answer, and never touches Postgres or Modal. A liveness probe that depends on the database turns a database blip into a restart storm. `/readyz` needs the store to answer within 2 s and migrations to be at head. `/startupz` runs the same checks with a 10 s budget for an orchestrator's startup probe. Kamal's `proxy.healthcheck.path` is `/readyz`. All three are unauthenticated and outside `/api/v1/`. A failing probe logs its reason and returns a bare status, because a connection error names the database host and user (`TestLivenessNeverTouchesTheStore`, `TestReadinessFailsWhenTheStoreDoes`).

### Shutdown

On SIGTERM or SIGINT a hosted server drains in this order within a 20 s budget (`ShutdownBudget`, below Kubernetes' 30 s default and Kamal's drain timeout): stop accepting and shut the HTTP server down, stop the reconciler and release its lock, close the Modal client, stop the job queue, close the database pool. Launches in flight are not awaited. They continue in the sandbox, and the orphan sweep finishes them from another replica (see DL-004). A client following a launch stream reopens it and then polls (see DL-005). A local server uses a shorter sequence.

### The Modal credential

`NewModalProvider` takes an explicit `sandbox.ModalCredentials{TokenID, TokenSecret, Environment}` and builds the client with `modal.NewClientWithOptions` and a `MaxThrottleWait` of 30 s. The CLI reads ambient Modal config (`~/.modal.toml`, `MODAL_TOKEN_*`) in one place and passes the values in, so the provider never reads ambient config. There is one `*modal.Client` per process behind an accessor, so a rotated credential can replace it.

The credential is a workspace API token minted for the deployment, and not reused from a developer's machine. The deployment runs in its own Modal environment (`MODAL_ENVIRONMENT`, for example `spov-hosted`), not the default one. The reaper terminates any `spov=1` sandbox past its deadline (see DL-004), and a separate environment keeps it away from a sandbox that someone launched from their own machine.

What this protects and what it does not: a Modal API token carries full workspace privilege and belongs to one account. The dedicated environment limits what the reaper and the deployment reach, but it does not limit what the token can do. That is acceptable for one operator, who already holds that access. A deployment shared by several operators should use a scoped service identity instead. Swapping is a change of credential and needs no code change, since `ModalCredentials` is the same either way. Revoking the token also breaks a local spov that uses the same token until a new one is minted. Rotation is mint, deploy, revoke the old one.

The image must set `HOME`. `NewClientWithOptions` fails with `$HOME is not defined` before it reads explicit credentials, because it resolves its config path through `os.UserHomeDir`, and distroless `nonroot` sets none. Any path serves, including one that does not exist, because a missing config file is treated as empty. The Dockerfile sets `HOME` to a directory inside the image.

Every replica counts toward Modal's 200 operations per second workspace limit, so the reconciler runs on one leader.

### Upgrades

From the first public release until v1, each breaking change ships with release notes and migration guidance. A new build migrates the database forward with `spov serve migrate up`. The first public release needs its own upgrade note, written against that release's schema and API. A same-version restart is what every deploy does, and restart recovery alone is not proof that an upgrade is safe, so upgrade cases are exercised separately from restarts.

## Rationale

- One origin removes a class of configuration (CORS, `SameSite=None`).
- A migration hook before the new containers serve fails a bad migration early, where startup migration would crash-loop replicas.
- Secrets that come only from the environment cannot end up in a config file that is committed or mounted by mistake.

## Measurements

- `modal.NewClientWithOptions` with explicit credentials in a container fails with `$HOME is not defined` before it reads them. Any `HOME` path works, a missing `~/.modal.toml` is treated as empty, and distroless `nonroot` sets no `HOME`.
- Modal's workspace limit of 200 operations per second bounds the useful replica count when each replica lists sandboxes.

## Consequences

- `SPOV_PUBLIC_URL` matters for cookies, OAuth callbacks and the browser guard. A proxy in front of the server must pass the `Host` header through.
- A deployment that wants the web app on its own origin cannot have it.
