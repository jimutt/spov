## Context

Deploying the published image with Kamal failed: the image carried no
`service` label and Kamal refuses an image without one, so no published
tag could ever deploy. The release workflow now labels it (`service=spov`,
first present in v0.2.1), but the guides still describe building from
source as the only Kamal path and never name the prebuilt option.

Separately, setting up a single-operator server required reading code:
nothing says the deployment can run with no organisation credential (a
personal token stored after the first login is tried first), that an
`SPOV_PLATFORM_TOKEN_<NAME>` variable attaches only to a platform
declared in the server's user file and is otherwise ignored, or how that
user file reaches a container. The Kamal template mounts no user file
and offers no Postgres, so a single host needs both invented. The OAuth
scopes (`read:user`, `user:email`) and the fact that the device flow is
spov's own, with nothing to enable on GitHub, are also code-only.

## Decision

### The prebuilt image is the documented Kamal path

The Kamal section of `deploy/README.md` names running a published
release: `kamal deploy -c deploy/kamal/config/deploy.yml --skip-push
--version <version>`, which pulls instead of building. Tags are release
versions (`0.2.1`), `:latest` follows the newest non-prerelease, and the
`service=spov` label the check needs is on every image from v0.2.1;
older tags are refused by Kamal, not by the server. Building from source
stays for proving a change before it is released, and the template keeps
its builder section, so `TestKamalRunsFromTheRepositoryRoot` is
unchanged.

### The templates ship the user file

`deploy/server-config.yaml` is the server's user file, mounted by the
Compose template and embedded as a ConfigMap by the Kubernetes one (the
manifests' plain-YAML rule forces that duplication, and the two copies
must be kept in step). Kamal mounts it from `/etc/spov/server-config.yaml`
on the host, placed there with `scp` before the first deploy: Kamal does
not sync relative volume sources, and the remote docker resolves them
against the SSH session's working directory (creating a missing one as a
directory) instead of the repository. It declares the `github` platform,
with `git.allow_all` and `sandbox.regions` shown for the single-operator
case. It documents the rule the code enforces: an organisation token
variable names a platform here, and a variable with no platform here does
nothing. Fill in the account and deploy.

### One operator needs no organisation credential

The Credentials section gains the single-operator path: configure OAuth,
log in, store a personal token in Settings or with `spov credentials add`;
the deployment tier is only a fallback, and omitting it is a supported
shape rather than a missing step.

### Login prerequisites are stated, not inferred

Browser login names the scopes spov requests itself (`read:user`,
`user:email`), why `user:email` is required rather than convenient (a
private address is only in `/user/emails`, and the login identity is the
primary verified one), and that the device flow is spov's own
authorization server with nothing to enable on GitHub.

## Rationale

- The release workflow already publishes, signs and attests the image;
  the guides should send single-host deploys there instead of
  re-documenting a build everyone repeats.
- A commented accessory is documentation that cannot drift from the
  template, unlike a README snippet someone edits. The user file ships
  tracked and mounted, so a deploy needs no second file from outside —
  except the Kubernetes ConfigMap copy, which the manifests' plain-YAML
  rule forces to duplicate and the record calls out.
- Every inferred rule above cost a debugging session; each is now one
  paragraph where the operator looks first.

## Consequences

- Kamal deploys of tags older than v0.2.1 fail at the label check with
  Kamal's own error. That is the documented floor, not a regression:
  those tags never deployed.
- A deployment that sets an org token variable without declaring the
  platform still silently ignores it; the shipped file is where the rule
  is written down, and no startup warning is added.
- `deploy/server-config.yaml` and the Kubernetes ConfigMap duplicate each
  other; a change to one must be mirrored in the other.
