## Context

DL-072 defines a routed credential. A user needs one way to store theirs in both modes, as `spov credentials add` already stores forge tokens and provider keys (DL-008). The route is not secret, but it decides where the secret is sent, so it needs the same integrity as the secret. The local keyring cannot enumerate its keys, so a local listing cannot find a routed credential by probing known names.

## Decision

### The command

`spov credentials add <name>` stores a routed credential when it is given a route, and only then:

- `--host <host>` (repeatable), with one scheme: `--bearer`, `--basic <username>` or `--header <name>`; `--path <prefix>` (repeatable) narrows it.
- or `--preset <npm|maven|nuget|pypi>` with the preset's own options (DL-076). A preset fills in the scheme and the hosts.
- `--attach asked` marks it to attach only when a launch names it (DL-075). The default is `always`.
- The secret comes from a prompt without echo, or `--secret-file <path>` (`-` for standard input). It never comes from a flag value, which would leave it in shell history and `ps`.

`spov credentials remove <name>` and the listing take the same name. A routed credential's canonical key is `route:<name>`. A bare name is accepted when it cannot mean anything else. A name that DL-008's parser would read as a platform or a provider key (a configured platform's name, `github`, anything with a `:`, anything ending in `_API_KEY` or all uppercase) is refused at `add` and must be given as `route:<name>` elsewhere. The listing shows each routed credential by name with its hosts, paths, scheme, preset, attach mode and where it is stored, never the secret or a prefix of it.

There is no verification. No check fits every service, and a preset's check would need the registry's own API. The command says the credential is stored unchecked.

`spov credentials add` decides where the credential goes by `Env.hostedServer`, as for every other credential (DL-008).

### Hosted

The server stores it in `user_credentials` under the platform key `route:<name>`, with the route in a new `route` column (JSON, in the clear, so a listing can show it without opening the secret). The secret is sealed as other user credentials are (AES-256-GCM under `SPOV_CREDENTIAL_KEY`), and the AAD binds the route as well as the owner: `CredentialAAD(org, user, "route:<name>")` followed by the route's canonical encoding (`RouteAAD`). A row whose route was changed in the database no longer opens, so a write to the database alone cannot redirect the secret to another host.

The API is `GET /api/v1/me/routed-credentials`, `PUT /api/v1/me/routed-credentials/{name}` with `{secret, route}`, and `DELETE /api/v1/me/routed-credentials/{name}`. It answers 501 without a credential key, as the credential endpoints do. A user holds at most 32 routed credentials. A `PUT` replaces the route and the secret together, never one alone. Settings lists them and offers remove; adding one from the browser is a later change.

### Local

The secret goes into the keyring (or the `credentials.json` fallback) under `route:<name>`. The route goes into `routes.json` in the local server's state directory, beside `server.json` and `variants.json`, mode `0600` and written atomically. The index is what a local listing reads, so routed credentials are listed although the keyring cannot enumerate. A row in the index whose secret is missing from the store is listed as missing, and a launch leaves it out with a note.

### Read at launch

A launch reads the routed credentials as they are then, from the store or the keyring and the index. A local server needs no restart after `add`, unlike a provider key (`keyAdvice`, DL-013).

## Rationale

One command for both modes keeps DL-008's rule that where a credential goes is decided by the configured server, never by a flag. Requiring a route to make a routed credential means no existing `add` changes meaning.

Binding the route into the AAD matters because the route is the part that decides where the secret goes. A database write that changed only the host would otherwise send a user's registry token to an attacker's host on the next launch, without touching the ciphertext.

An index file locally is what the plan called for: the route is not secret, the keyring cannot list, and the local server already keeps its state files in that directory.

## Consequences

- `spov credentials` lists three kinds: platforms, provider keys and routed credentials.
- A database restored without its `route` column contents fails to open those rows, and the user adds them again.
- Tests: `TestARoutedCredentialIsSealedWithItsRoute`, `TestAChangedRouteDoesNotOpen`, `TestALocalRoutedCredentialIsListedFromTheIndex`, `TestARoutedCredentialNameCannotShadowAPlatform`.
