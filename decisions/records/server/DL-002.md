## Context

spov has a hosted mode, where a central server orchestrates sandboxes for its users, and a local mode, where nothing is installed besides the CLI. Two code paths would drift apart. An in-process library, a child process running the same binary and a required docker-compose setup were compared. Only the child process keeps a single code path without imposing Docker on a CLI user.

## Decision

The CLI always speaks HTTP to a spov server. It never calls `session.Launcher` or `sandbox.Provider`. Local and hosted mode differ in three things only: the base URL, how the server was started and the authenticator. The local path is the hosted path with a different URL.

`internal/cli` imports `internal/server/client`, which is hand-written against the server's own types, so a change to a view or request is a compile error on both sides. The provider and `internal/session` are reached only from `spov serve`.

### `spov serve`

`spov serve` assembles the server from the same configuration and credential store the CLI uses. Flags are `--listen`, `--local` and `--state-file`. A hosted server listens on `127.0.0.1:8080` unless `--listen` or `SPOV_LISTEN` says otherwise. The default is loopback because binding every interface is the deployment's explicit choice: a container sets `SPOV_LISTEN=:8080`, and a bare host that forgets it stays unreachable instead of exposed (see DL-010). Clients authenticate with the bearer token in `SPOV_SERVER_TOKEN`, which the server reads from its own environment, and a hosted server refuses to start without it. `spov serve openapi [--3.0]` prints the API document.

A server reads the user file and the environment only (`Env.ServerConfig`, `config.LoadUser`), never a project file (see DL-026).

`--local` means: listen on an ephemeral loopback port (`127.0.0.1:0` unless `--listen` says otherwise; the CLI's spawn passes none), use the memory store, use a generated token (32 random bytes, base64url) and exit when idle. It reads the Modal credential and the git platform tokens from the places the CLI reads them. Its token is its own and never the environment's.

### Which server a command talks to

First match wins:

1. `--server <url>`.
2. `SPOV_SERVER`.
3. `server.url` in the user's config file. A project file cannot set it.
4. A running local server named by the state file.
5. A new `spov serve --local`, spawned as a child, whose state file the CLI then waits for.

The token for steps 1 to 3 is `SPOV_SERVER_TOKEN`, or the token `spov login` stored for that host. It is never an argument. `spov fly --server https://spov.example.com` is the whole difference between local and hosted for a user.

### The state file

The local server writes `$XDG_STATE_HOME/spov/server.json` (default `~/.local/state/spov/server.json`) once it is listening. The write is atomic (temporary file, then rename) with mode `0600`. The fields are `pid`, `url`, `token`, `version` and `started_at`. The state directory is made `0700` even when it already existed, because a writable directory would let another user replace the file.

The CLI treats the file as live only when all of these hold:

- `url` is `http`, names a loopback address or `localhost`, and has no userinfo. The file is trusted for its token and not for where to send it, so a file another process managed to write cannot point the CLI and its token at a host of its choosing.
- `pid` is running.
- `version` equals the CLI's own.
- `GET /api/v1/me` with the token answers 200 within 500 ms.

Otherwise it deletes the file and spawns. The token never appears in argv, logs or error text. The probe also avoids trusting a stale pid.

### The version gate

`version` is the full `internal/version` string, so two development builds from different commits differ. When the file's version differs from the CLI's, the CLI sends SIGTERM to that pid (on Windows it kills the process), waits up to 5 s for it to go, and spawns a fresh server whether or not it did. A wedged old server keeps its own ephemeral port and harms nothing. The check comes before the probe, so a server of another build is never talked to. Two builds of spov never talk to each other.

### Spawning

The CLI runs `os.Executable() serve --local --state-file <path>`, detached from the terminal (`Setsid`, no stdio). The child runs in the state directory, so it never reads the project file of the repository the CLI was run in. The child's stderr is appended to `$XDG_STATE_HOME/spov/server.log` (mode `0600`, truncated at the next spawn once it passes 1 MiB). The CLI waits up to 5 s for a state file that validates. Failure messages name the log, because the terminal is about to belong to OpenCode.

Ready means reconciled: the local server runs one reconciliation before it writes the state file. A CLI that spawned it to attach to or stop a session a previous server launched therefore does not see a 404 for a sandbox that is running.

### Idle exit

The local server exits after 60 s (`IdleExit`) with no request in flight and no session in `starting`. An open SSE stream counts as a request in flight. It removes its own state file (only one that still names its pid) before it drains the listener, so a CLI that reads the file during shutdown spawns a replacement and does not find a server that answers its probe and refuses its next call. Kept sandboxes (`--keep`) do not hold the server open. Their Modal tags are their durable record, and the next server finds them by tag.

### Outliving the server

A transport failure (no answer, as opposed to a problem the server sent) makes the CLI resolve a server again, which spawns one if needed. A `connect` whose server has gone resolves a server again and asks by name, and `Env.deleteSession` retries by name after a 404 by ID, because the new server adopts the session under a new ID. A TUI session continues when the local server exits, since its heartbeat goes to the sandbox, and the next call re-resolves a server automatically.

### Signals and lifetime

The spawned server is in its own session, so Ctrl-C in the terminal never reaches it. A launch in flight survives the CLI being interrupted, and it is the CLI's `DELETE` that cancels it. A failure after the server accepted the launch prints the stop hint, since the sandbox may be running. SIGTERM to the server's pid runs the same orderly shutdown.

Ending a session when the TUI exits is the CLI calling `DELETE /api/v1/sessions/{id}`. The server never terminates a sandbox on its own for this.

### The commands as HTTP flows

- `spov fly` builds a `SessionRequest` and posts it. The launch flow itself is in DL-024.
- `spov attach <ref>` reads `GET /sessions/{ref}` and connects, then takes the same tail as `fly`. It does not recover passwords. A stopped session is refused before any connection, and by name it is not found, since names resolve among live sessions only. Waiting for a session that is still starting is in DL-025.
- `spov ls` reads `GET /sessions`. Sandboxes the reconciler has not yet adopted appear within 30 s. Paging is in DL-012.
- `spov stop <ref> [--all]` sends `DELETE /sessions/{ref}`. `--all` lists the live sessions and deletes each, continuing past failures.
- The repository picker reads `GET /repos` (see DL-028). `--repo platform:owner/name` needs no platform in the client's config, because the server may know one the client does not. An unqualified `owner/name` needs exactly one configured platform.

The request carries only what the client chose. That is sizing, timeouts, placement and the egress preset from config, an image only when one is configured explicitly (so a hosted server's default is not overridden), and the git identity the client resolved from flags, config and its own git config. The server's configured identity fills only the halves left empty. `egress_extra_domains` is a server-side key, added to whatever preset a request names. `SessionView` carries the effective image, sandbox and egress, so the summary after a launch (timeout, idle timeout, hourly cost) comes from the server.

Warnings that only the server can make, such as an expiring GitHub token or a missing model provider key, reach the terminal as `note` events. Per-platform listing failures travel in the `GET /repos` response as `warnings`.

A session the server reports ready, but which this machine's proxy cannot reach, is left running with a summary and a stop hint. The server has just proved the sandbox healthy, so a local failure is no evidence against it, and attaching again is the cheap retry.

## Rationale

- One code path means a bug reproduces in both modes or in neither.
- A child process needs nothing installed, and idle exit leaves nothing running. The version gate leaves no orphan after an upgrade.
- The state file plus the probe avoids a second server racing the first and a reused pid.

## Measurements

A manual end-to-end run against real Modal covered: `spov serve openapi`; `/api/v1/me` answering 401 without and 200 with the token; a full `fly` with the launch view fed by the stream; `fly --keep`, then `ls`, `attach`, `attach --web` and `stop`; a server restart that re-adopted a kept session; and Ctrl-C during a launch. It left nothing running at Modal.

The run also showed a defect the tests had not covered. In a kept-session run the sandbox exists at Modal for the whole health wait while the session row has no sandbox ID, and a reconcile in that window adopted the sandbox a second time under its own ID. A running sandbox whose name belongs to a live `starting` session is left to that launch (`Reconciler.launchInFlight`). `TestReconcileLeavesALaunchInFlightUnadopted` and `TestReconcileLeavesAHostedLaunchInFlightUnadopted` guard it.

The time bounds are: 30 s for the CLI's health check through its own proxy, 5 s for a spawned server's state file, 5 s for an old server to exit after SIGTERM, 500 ms for the liveness probe, and 60 s of idleness.

## Consequences

- `spov serve` is a supported, documented command surface and not an implementation detail.
- Two spov processes exist during a local session. If the server dies mid-session the TUI continues, and the next call re-resolves a server.
- The spawn budget and the version gate are failure modes of `spov fly`, and both print specific messages.
- CLI tests run the real API in-process (`httptest`), assembled by the same `serverDeps` that `spov serve` uses, with the fake provider and fake platform behind it. A test that reaches the real `Env.spawn` execs the test binary as `serve --local`, so `TestMain` in `fixture_test.go` makes that child exit. Fixtures set `Env.Spawn` or `Env.Client` instead of relying on that guard.
- Guard tests: `TestLocalClientRefusesANonLoopbackStateFile`, `TestLocalClientStopsAServerOfAnotherBuild`, `TestStateFileIsPrivateAndAtomic`, `TestServeLocalExitsWhenIdle`, `TestServeLocalStaysUpWhileASessionStarts`, `TestServeLocalReconcilesBeforeAnnouncing`, `TestSpawnArgsCarryNoSecret`.
