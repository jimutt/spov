## Context

`Service.Connect` counts a session's recent mints and records a new one in one store transaction, against `MintsPerMinute` (DL-003, DL-030). The memory store's mutex makes the count exact. In Postgres, `pgMints.CountSince` is a plain `count(*)` under READ COMMITTED, and the `LockSession` query in `internal/store/postgres/queries/queries.sql` (`select … for update` on the session row) is never called. Two connects for one session on different replicas can both count below the limit and both insert.

## Decision

`SessionStore.Lock` holds a session's row until the enclosing transaction ends: in Postgres it is `LockSession` (`select … for no key update`, so it blocks other writers of the row but not inserts that only reference it), and in memory it only checks that the session exists, since a memory `Tx` already holds the store's lock. `Service.Connect` takes it before counting, so the count and the insert are one step on every replica.

`TestTheMintLimitHoldsAcrossReplicas` (real Postgres, `go test -tags integration ./internal/store/postgres/ -run MintLimit`) runs eight racers against a limit of one, with a pause between count and insert. With the lock exactly one mint is recorded; with the lock taken out, all eight are.

## Consequences

Concurrent connects for one session serialise on its row, which they already do in memory. The limit stops being approximate under several replicas.
