## Context

Every user is a GitHub account that signed in (DL-128), and a CLI token is issued by the device flow for 90 days and is valid only while an allowlist entry covers its user (DL-006, DL-007). A CI workflow that starts jobs therefore holds a person's token: the jobs are that person's, they count against that person's quota, and they stop when the person is removed (DL-132) or the token lapses.

## Decision

A hosted server has **service accounts**: users an administrator creates, that never sign in.

- **The row.** `users.kind` is `person` (the default) or `service`, and `users.disabled_at` is set when a service account is deleted. A service account has a name matching `^[a-z][a-z0-9-]{1,30}[a-z0-9]$`, unique among the organisation's service accounts, and the row's address is `<name>@service.invalid`. It has no `github_id` and is never bound: `upsertUser` refuses a sign-in whose address matches a service row, and the allowlist routes refuse an address entry under `service.invalid`. An organisation holds at most 100.
- **Authentication.** Only a bearer token authenticates one (tokens are DL-141). `TokenAuthenticator` allows a `service` row while `disabled_at` is unset and does not consult the allowlist for it. Its principal is never an admin and carries `Service: true`. No cookie session and no device approval can name one.
- **What it may do.** Everything a non-admin user may: create and read its own sessions and jobs, store its own credentials and routed credentials, read its own tokens. The per-user request limits (DL-133), the build limits (DL-134) and the two quotas (DL-045) apply to it as to a user, with the same defaults; an admin changes its quota through `PATCH /api/v1/users/{id}`, and `GET /api/v1/users` lists it with `kind`.
- **Its forge credential** is a stored token: the account stores it itself, with its own spov token, through the existing credential routes (`spov credentials add` with `SPOV_SERVER` and `SPOV_SERVER_TOKEN` set). No route writes a credential on another account's behalf. A service account has no GitHub App of its own; a launch may still prefer the organisation's (`credential_preference`, DL-042).
- **The admin routes**, tagged `admin` and 501 on a local server:
  - `POST /api/v1/service-accounts` with `name` and optional `git_name`, `git_email` (the commit author, defaulting to the name and the row's address);
  - `GET /api/v1/service-accounts`, each with its name, id, author, creation time, token count and last use;
  - `PATCH /api/v1/service-accounts/{name}` for the author;
  - `DELETE /api/v1/service-accounts/{name}`, which sets `disabled_at` and writes the `admin_events` row in one transaction and then runs `Service.Offboard` on the row. A failed step answers 500 naming what is left, and the same delete retries it, as DL-132's does. The name stays taken and the history is kept.
  Each write records an `admin_events` row (`service_account.created`, `.updated`, `.deleted`) with no secret.
- **Admins and its work.** An admin reads, steers, interrupts and cancels a service account's sessions and jobs through the existing owner-or-admin rule (`Principal.CanAccess`, DL-006); nothing is added for that.
- **No page and no command.** The routes are documented with `curl` examples in `deploy/README.md`, as the allowlist's were before DL-129.

## Rationale

- A row in `users` gives a service account everything that is keyed on a user (ownership, quotas, credentials, limits, off-boarding, the tenant wall) without a second kind of owner anywhere.
- `.invalid` is reserved and no forge verifies an address under it, and the two refusals make the row unreachable by sign-in even so.
- A stored token per account gives each agent its own forge identity through code that exists. A GitHub App per account would need its own sealing, renewal and tier beside the organisation's (DL-042, DL-021), which is a separate decision if it is ever needed.
- The account storing its own credential keeps the credential routes' rule that a secret is written only by its owner.

## Consequences

- A stored token is not renewed by spov (DL-041), so a service account's forge token is rotated by whoever runs the pipeline.
- A leaked service token can do what the account can, including replacing its stored credential; it cannot read one back, reach another user's work or administer anything.
- The new operations join `adminOnly` in `tenantisolation_test.go`, `newTenantWorld` gains a service account with a job, and a test shows a disabled account's token is refused, a sign-in cannot take a service row, and a service principal is refused every admin route.
- Migration 00040 adds the two columns.
