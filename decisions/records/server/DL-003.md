## Context

A hosted spov server runs as several replicas behind a load balancer, and any of them may receive any request. A replica may also die in the middle of a launch. Local mode has to run with no database and persist nothing. The Modal Go SDK discards `SandboxInfo` when it lists sandboxes, so a listing costs 1 + 2N RPCs for N sandboxes (see Measurements). A server therefore cannot list Modal on each request.

## Decision

### Any replica can serve any request

No request depends on process memory that another replica lacks. What a request needs is in Postgres, in the sandbox itself, or derivable from configuration. A sticky-session load balancer is neither required nor assumed. Leadership exists only for background work (see DL-004).

In practice:

- **Handle.** Any replica gets a `sandbox.Handle` from `Provider.FromID(sandbox_id)`. The handle held by the launching replica is a cache, not a requirement.
- **Password.** `connect` takes the session password from a per-replica in-memory cache keyed by session ID. It is a bounded LRU of 1,000 entries (`DefaultPasswordCacheSize`), cleared when the session stops. The launch fills it on the replica that ran it. On any other replica, or after an eviction or restart, one exec in the sandbox (`printenv OPENCODE_PASSWORD`) recovers it on first need. A failed recovery answers 502 `password unavailable` and never a made-up value. The password is never written to the database. The sandbox is the durable holder, so recovery on demand makes every replica equal without persisting a secret. The cost is one extra exec per session per replica that serves it. The connect flow is in DL-030.
- **Terminate.** `DELETE` terminates by sandbox ID through the provider. It is the only path, and the reconciler uses it for adopted sessions. Git tokens are revoked by re-deriving them: GitHub App tokens last an hour and expire by themselves, with a best-effort revocation through the recorded installation ID, and stored Forgejo tokens are never spov's to revoke. The launching replica's in-memory revoker is used when it is present and skipped otherwise.
- **Cancellation is durable.** A launch is cancellable only while the store holds no sandbox for it. Once there is one, `DELETE` takes the terminate path, because cancelling then would set a flag the launch has already passed and the delete would report success while the sandbox kept billing. The flag is `sessions.cancel_requested_at`. `Service.Delete` sets it with an update conditional on `state = 'starting'`, and `commitLaunch` reads it under `SELECT ... FOR UPDATE` in the same transaction that records the launch as running, so a cancel and a commit exclude each other across replicas. A flag in the launching process's memory fails in exactly this way: a `DELETE` that lands on another replica during the window before the sandbox exists marks the row stopped, and the launching replica, reading its own empty map, writes it back as running with a live sandbox. The caller is told the session is gone while it bills.
- **Orphaned launches.** A launch is a `starting` row plus a goroutine on one replica. If that replica dies, the elected leader's sweep resolves the row once it is older than `LaunchTimeout` plus a minute (see DL-004). A mid-launch restart therefore costs at most that long in `starting`, and the CLI's `Follow` polls through it.
- **Launch events from another replica.** A launch's step log is per-replica memory. A `GET /sessions/{id}/events` that reaches a replica that did not launch answers with a `step` snapshot (`starting sandbox`) and then reads the store every 2 s (`StorePollInterval`) until the session is terminal, so `Follow` sees a valid stream from any replica (`Server.streamFromStore`). A `stopped` session ends that stream as a failure (`terminalEvent`), which is what the client's own polling fallback concludes, so a stream and a poll never disagree about one session. A stopped session right after create means the launch was deleted. Postgres `LISTEN/NOTIFY` fan-out of launch steps is not implemented. The conversation recorder keeps a session's conversation in the store (see DL-017).
- **Mint limit.** The rolling-minute limit on connect tokens (`MintsPerMinute`, 10 per session) counts and records the mint in one store transaction (`Service.Connect`). The memory store's mutex makes that exact. Under Postgres the count takes no row lock, so the limit is exact only for requests that do not overlap (see Known gaps).

### The Store interface

`internal/store.Store` is the schema: it is the only door to persistent state, and the sub-stores are `Sessions`, `Mints`, `Users`, `Tokens`, `DeviceCodes`, `Credentials`, `OrgCredentials`, `AdminEvents`, `Allowlist`, `Conversations` and `Jobs`, plus `Tx` and `Ping`. `Tx` runs a function atomically where the backend can. The memory store serialises transactions with a mutex so the semantics hold there too, and it fails loudly on a call back into the outer store, a retained store or a nested `Tx`.

Rules every implementation follows:

1. **`OrgID` on every entity and every request-path query.** Handlers call `Get(ctx, orgID, id)` and `List(ctx, orgID, filter)`. The reconciler's `BySandbox` and `ListLive` cross orgs, because the provider's listing has no org, and handlers never call them. Role-based access later adds rows and not a migration of every table.
2. **IDs are ULIDs** generated by the server (`github.com/oklog/ulid/v2`), sortable by creation time. Session names are unique per org among `starting` and `running` sessions. Postgres enforces this with a partial unique index on `(org_id, name) where state in ('starting','running')`, which holds under concurrent creates from two replicas in a way application checks cannot.
3. **The memory store is honest.** One contract suite (`store/storetest`) runs against the memory store always and against Postgres when `SPOV_TEST_DATABASE_URL` is set. Postgres tests run in a per-test schema that the suite creates and drops, so they parallelise. A query the memory store cannot answer is not added to the interface, so local mode cannot diverge silently.
4. **Secrets are never stored in plain.** No password, token or Modal credential is in an entity. Stored credentials are sealed (see DL-008).
5. **`Session.Request` records what was asked for** (repositories, landing, image, the sandbox resource shape and the egress preset name) and holds no credential and no provider type.
6. **Adopted sessions** have no `OwnerID` beyond the `user` tag. In hosted mode the reconciler assigns them to a system owner and an admin reassigns them.

Local mode persists nothing. Interactive sessions store nothing, and Modal tags are the record that survives a restart. A SQLite store for local mode was rejected, because it would fork the schema under sqlc for a mode that needs only live state. Local mode holds one fixed `local` user.

### The Postgres store

`internal/store/postgres` implements `Store` with pgx v5 and sqlc-generated queries (`sql_package: pgx/v5`, `emit_json_tags: false`). The generated code is committed, and CI runs `sqlc diff`. There is no ORM. sqlc cannot express an optional filter, so `pgSessions.List` with its filters is hand-written pgx, the one exception.

The target is PostgreSQL 18. The schema uses nothing newer than 16, the documented minimum.

Schema conventions: every table has `org_id`, `created_at` and `updated_at`; IDs are ULIDs stored as `text`; `orgs` has a single `default` row, so more orgs are rows and not a migration; `sessions.request` and `clones` are `jsonb`; `state` is `text` with a check constraint. The web-login session table belongs to `scs/pgxstore` (renamed `web_sessions`) and is not in `Store`.

### Migrations

Migrations are goose SQL files embedded in the binary. `spov serve migrate up|down|status` applies them through a throwaway `database/sql` handle (`pgx/v5/stdlib`) with `goose.NewProvider` and `WithSessionLocker(lock.NewPostgresSessionLocker())`, so concurrent attempts are safe. The binary applies them itself because a distroless image has no shell.

The server never migrates at start, so a deployment can run migration as a step that fails the deploy before any new container serves. The exception is `SPOV_MIGRATE_ON_START=true`, meant for compose and development, which `spov serve --local` refuses. `AtHead` reports whether the applied version equals the embedded head, and `/readyz` reads it. The database is configured only by `SPOV_DATABASE_URL`, never by a config file, and `--local` never opens one. The job-lifecycle tests in `internal/server` use the database as they find it and do not migrate, so a stale test schema shows up as a missing column; run `spov serve migrate up` first.

## Rationale

- One interface and one contract suite make the local and hosted paths answer the same questions the same way.
- A partial unique index is worth more than application-level name checks when two replicas create at once.
- Terminate-by-ID makes one path for launched and adopted sessions.
- Polling the store for events from a non-launching replica is a few lines and correct.

## Measurements

Listing Modal sandboxes through the SDK costs 1 + 2N RPCs for N sandboxes.

A spike checked the Postgres behaviour the design assumes against a real database: the advisory lock, per-test schema isolation, the partial unique index and that a second `SELECT ... FOR UPDATE` on a row blocks until the first transaction commits. All behaved as assumed with PostgreSQL 18.6, pgx v5.10.0, sqlc v1.31.1, goose v3.27.3 and ulid v2.1.2. Re-run it, and the store contract against Postgres, with:

```sh
export SPOV_TEST_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:5433/spov?sslmode=disable
go test -tags integration ./internal/store/ -run Phase2 -v
go test -tags integration ./internal/store/postgres/
```

CI installs the distribution's `postgresql` package and starts the cluster with `pg_ctlcluster`, because its runner has no container runtime, so a `services:` block cannot start a database. That took about 25 s with PostgreSQL 18.6.

Guard tests: `TestConnectWorksFromAReplicaThatDidNotLaunch`, `TestConnectReportsAnUnrecoverablePasswordAsBadGateway`, `TestDeleteWorksFromAReplicaThatDidNotLaunch`, `TestDeleteFromAnotherReplicaDoesNotResurrect`, `TestEventsPollTheStoreForALaunchRunningElsewhere`, `TestEventsFromAReplicaThatDidNotLaunchEndWithTheDerivedOutcome`, `TestDeleteAfterALaunchCommitsTerminatesTheSandbox` and the `TestPasswordCache...` tests.

## Consequences

- The password costs one exec per session per replica, which is negligible against Modal's request limits.
- The contract suite is how the interface grows. A new sub-store needs a memory implementation and suite coverage.
- Mid-launch server restarts leave a session in `starting` for up to the launch timeout plus a minute.
- A migration is a deploy step. A server started against an older schema fails with missing columns until `spov serve migrate up` has run.

## Known gaps

- The Postgres mint count takes no lock on the session row. Two connects for one session that reach different replicas at the same moment can each count below the limit and both record a mint, so the limit can be exceeded by the number of overlapping requests. The `LockSession` query exists in `queries.sql` and nothing calls it.
- Launch steps are visible individually only on the replica that ran the launch. Other replicas report one snapshot step and then the outcome.
