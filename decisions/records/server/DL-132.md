## Context

DL-007 made a removal from the allowlist lock the person out on their next request and delete their browser sessions. Nothing else went with them. The security review (finding A-02, M1) showed what stayed: their running sandboxes and unfinished jobs kept running, so a `/connect` answer saved before the removal kept a shell, the session's repositories and the deployment's model keys until the sandbox's own timeout; their queued jobs still launched; their CLI tokens were refused but not revoked, so they worked again if the address was re-added; and their stored forge tokens, provider keys, routed credentials and OpenCode sign-in stayed in the database.

## Decision

`DELETE /api/v1/allowlist/{email}` off-boards the person whose address it removes. In order:

1. The entry is removed in its transaction, under the same checks as before (`requireAllowlist`, then `CountAdmins` and `requireLiveAdmin` inside the transaction, `guardLastAdmin` for an admin entry). That locks the person out first.
2. Their browser sessions are ended (`Login.RevokeSessions`), as DL-007 says. A failure there is still a warning, not a failed delete.
3. `Service.Offboard` (`internal/server/offboard.go`) then runs every one of these steps, each even if an earlier one failed:
   - cancels each of their unfinished jobs (states `store.JobCounts`) with `Service.CancelJob`, which stops the job's session by the path its state calls for. A job that finished in the meantime is skipped;
   - stops each of their sessions still live (`store.LiveStates`) with `deleteFor`, which terminates the sandbox. This includes a held sync job's session, which is live with a finished job and which `DeleteSession` refuses. A session whose job is still unfinished is left out, because its cancel failed and stopping the session alone would leave the job to run; that failure is already reported;
   - revokes every CLI token of theirs that is not yet revoked (`TokenStore.ListByUser`, `Revoke`), so re-adding the address does not revive one;
   - deletes every row of `CredentialStore.ListByUser`: forge tokens, provider keys, routed credentials (`route:<name>`) and the OpenCode sign-in rows (`opencode:grant`, `opencode:attempt`). No cache keyed by user serves a credential after its row is gone, so there is none to drop;
   - writes one `admin_events` row, action `allowlist.offboarded` (`AdminMemberOffboarded`), actor the admin, detail the address and the counts (jobs cancelled, sessions stopped, CLI tokens revoked, credentials deleted) and, when a step failed, what is left. Never a secret or a credential's name.

The acting admin is the principal for every step (`Principal.CanAccess` lets an admin act on another's session), so a cancelled job's note names them.

A person who never signed in has no user row (`Users().ByEmail` is not found): only the entry is removed, and nothing is audited.

If any step failed, the request answers 500 through huma, saying that the address is removed, what is left (for example "3 stored credentials not deleted"), what was done, and that sending the same delete again retries. Each failure's detail goes to the server's warning log, redacted.

A delete of an address that is not on the allowlist, but whose user row exists, runs the off-boarding steps again and answers 204. That is the retry. With no entry and no user row it stays a 404 ("is not on the allowlist"). The admin checks apply on both paths.

The person's history is kept: the user row, past sessions, transcripts, reports and snapshots.

Local mode has no allowlist, so nothing changes there.

## Rationale

- Removing a person is the one moment an admin says they should have nothing left. Doing it in the same call means there is no second list of things to remember, and no window in which a saved connection outlives the decision.
- The entry goes first and alone in its transaction, so the lockout never waits on a sandbox or a forge. The later steps touch sandboxes and several tables and cannot share one transaction, so each is allowed to fail on its own and the call says what is left.
- Retrying through the same delete, rather than a separate endpoint, keeps the admin's action the same whether the first attempt finished or not. A user row is what says there was someone to off-board, so an address that was never used still answers 404 and a mistyped one is still caught.
- Revoking tokens, not only refusing them, makes re-adding an address a fresh start rather than a restoration.
- Deleting credentials, not keeping them for a possible return, is the smaller risk: a returning person adds them again in a minute, while a kept forge token is a standing secret of someone who has left.

## Consequences

- The OpenCode sign-in is deleted from spov but not revoked at OpenCode. The grant stays valid there until it expires or the person ends it in OpenCode's console.
- A device code approved in the ten minutes before the removal can still issue a CLI token afterwards. That token is refused while the address is off the allowlist. A further delete of the address revokes it, so an admin re-adding the address should send one first.
- Other replicas refresh their cached allowlist within ten seconds (DL-007). A launch one of them accepts in that window can start after the off-boarding listed the person's sessions; a repeated delete ends it.
- A removal now terminates sandboxes and cancels jobs. An admin who removes the wrong address loses that person's running work, though not their history.
- The audit trail now records removals of people who had signed in. Removals of addresses that were never used are not audited, as before.
