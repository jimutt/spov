## Context

With add-ons (DL-033), every combination of add-ons and apt packages a project asks for is its own image. An operator prebuilding each combination would make add-ons unusable locally, where the user is the operator. Once a variant is named after the exact versions it installs, every upstream patch release also makes the current name one nobody has built, and building it on the launch path would cost the first launch after each release 25 s to 1.5 min. Quick boots are the point of variant images.

Every image spov publishes stays in the Modal workspace until it is deleted: each OpenCode pin's base image, each spov build's credential-proxy image, each variant, and one variant per patch release a request has used. Nothing deletes them unless spov does. Images persist until deleted, and spov assumes nothing about what their storage costs; pruning bounds an otherwise unbounded accumulation and keeps the workspace legible.

Deleting an image has a measured, unobvious effect (see Measurements): the published name keeps resolving, `HasImage` keeps answering true, and a new sandbox from the name fails. So Modal's name lookup cannot be the authority on whether an image exists.

## Decision

### The registry

spov keeps a registry of every image it publishes (base, proxy and variant): its name, the Modal image ID, its kind, a variant's request key and resolved versions, when it was published, when a launch last used it, and when pruning deleted it (`store.Image`). A launch updates the last-used time at most once an hour per image in a server process, so a busy deployment does not write on every launch.

- A server on Postgres keeps it in the `images` table (`ImageStore`), shared by every replica. Any other server (a local one) keeps it in the state file `variants.json` beside `server.json`, written atomically under an advisory file lock so the `spov serve image` commands and a running local server do not lose each other's writes, and read at start-up. A local server exits after a minute with nothing to do (`IdleExit`), so the records must outlive the process. A missing or unreadable file means no records, never a failed launch. A server that finds no state directory has no registry at all, and its launches boot the variant their request names.
- The registry, not Modal's name lookup, says whether an image exists. A pruned entry is kept and marked deleted. A launch, `EnsureImage` or `spov serve image build` that needs a deleted name rebuilds and republishes it, through `BuildImage` and never `EnsureImage`, whose lookup would say the name exists. A name that is not in the registry is looked up in Modal, and one Modal has is entered.
- The credential-proxy image `spov-proxy-<hash>` is registered and pruned like the others. The filesystem snapshot behind it is baked with `NoExpiryTTL`, because snapshots otherwise expire after 30 days (DL-034). A proxy image is baked again by the first launch that needs it.
- A registry can be wrong when two deployments share a Modal environment, such as a local and a hosted server: one prunes an image the other still records. A launch whose sandbox create fails because its image is gone (`ImageNotFoundError`, `imageGone`) marks the entry deleted, says so, and the next launch rebuilds it. A base image is the operator's to rebuild, and the error names `spov serve image build`. `spov serve image build --rebuild` publishes a name again whatever any registry says.

### Which image a launch boots

`Service.pickVariant` decides, for a request with add-ons or apt packages, and a job's launch follows the same rules. The variant is derived again at launch from this server's current recipe, not from the name stored at create, because a queued job can wait through a deploy that changes the pin or the toolchain. Add-ons the server does not offer fail the launch with a plain message.

1. The exact image, built from the resolved versions, is registered and not deleted: boot it.
2. The exact image is not in the registry but Modal has it: enter it in the registry and boot it.
3. Otherwise, look for an older build of the same request: the newest registered build under the request key (the variant named with its versions as written), or, with nothing registered, the image named by the request as written if it exists, entered with its versions as written. Boot it at once and record that build's versions on the session (`Booted`). When `build_on_demand` is on, start the exact build in the background (`VariantBuilder.Start`, rebuilding if the exact name was pruned) and say so in the launch's progress. No background build starts when a partial version did not resolve (it would build the request as written), nor when the resolver's answer is older than the recorded build's version, as a replica with a lagging cache can give (`worthBuilding`). A build that would pass the bounds below is skipped silently, and the next launch tries again. An image that Modal has and the registry lacks counts as an older build, so a lost registry does not force a rebuild.
4. With no usable image at all, build the exact one on the launch path. If `build_on_demand` is off, or the exact name was pruned and this server does not build on demand, the launch fails with a message naming the exact `spov serve image build --addons ... --apt ...` command.

With `build_on_demand` off, a launch stays on the newest recorded build. `spov serve image build --addons ...` resolves, builds the exact image, records it and prints the resolved versions, which is how an operator moves a deployment to a new patch. A finished build is recorded as the newest for its request whether it ran in the background or on a launch path (`VariantBuilder.OnBuilt`). A failed build is logged and not recorded, so the older build stays in use.

### Building on demand

A launch whose add-on variant is missing builds it, then continues; the base image is never built by a launch.

- The build reuses the cached base layers and adds only the variant's own layers (DL-032). A variant's name hashes its recipe to 32 hex characters, and the recipe pins resolved versions, so the name follows the exact release. A short hash would let a caller who chooses packages with `sandbox.apt` search for a recipe whose name collides with another variant's.
- At most one build runs per image name in a server process, so concurrent launches wait for the same build. At most two different builds run at once (`DefaultMaxVariantBuilds`); a launch past that is refused with `ErrTooManyBuilds` and not queued, so no caller can stack up detached builds. Two replicas that build at once publish the same recipe under the same name.
- The build runs before any token is minted, so a failed build leaves nothing to revoke. It is detached from the launch under its own 30-minute bound (`DefaultVariantBuildTimeout`). A launch that reaches its own five-minute limit (`config.DefaultLaunchTimeout`) fails with "still building, ready for a later launch", and the build carries on and publishes. The launch timeout is not stretched, because the reconciler judges a starting session by it (DL-003). A job's launch has the same bound (`jobs.ProvisionTimeout`, five minutes): a build that outlasts it fails the job with "still building", and a resubmitted job finds the image.
- The launch reports a progress note before its first step, naming the image and its add-ons and saying it is a one-time build.
- A failed build fails the launch with the build's error and is not remembered. The next launch tries again.
- `modal.build_on_demand` (default true; `SPOV_MODAL_BUILD_ON_DEMAND`) lets an operator turn on-demand building off. A hosted operator might, because `sandbox.apt` lets any caller trigger a build: with it on, any caller can trigger up to two builds at a time; off keeps image contents to what the operator has built. When it is off, a missing variant refuses the launch with a `sandbox.ImageNotFoundError` naming the exact build command. A missing sidecar image is reported as itself.
- The base image stays an operator step: `spov serve image build` (DL-032). A missing or pruned base, with no add-ons and no apt packages, refuses the launch and names the command, because a missing base means the deployment's pin was never prepared and the operator should see that.
- A custom `sandbox.image` bypasses all of this and takes no add-ons.
- Builds count against the Modal workspace, outside the session quota (DL-009).

### Pruning

An image is deleted when it has gone unused for long enough. The defaults are fixed constants (`ReplacedVariantRetention` and the others in `imageprune.go`); configuration keys for them are not built.

| Image | Deleted when unused for |
|---|---|
| a variant a newer build of the same request replaced | 7 days |
| the newest variant of a request, only while `build_on_demand` is on | 30 days |
| a base image of any pin but the current one, or a variant built on one | 30 days |
| a proxy image of any binary but the current one | 7 days |

The current pin's base image and the current proxy image are never deleted. Neither is any image a live session was created from or asked for (`Booted.Image`, `Request.Image`), whatever its age: a running sandbox survives a delete, but a recreated sidecar needs its proxy image. An unfinished job is covered by the same rule, since a queued job has no image yet and resolves at launch, and a running job's session is live. The newest variant of a request is kept while `build_on_demand` is off, because only an operator can rebuild it.

- `Prunable` picks the entries and says why (`PruneCandidate`). Pruning marks an image deleted in the registry before it deletes it in Modal: one marked but not deleted is only rebuilt, while one deleted but not marked would fail launches. Each mark and delete carries on past a cancelled prune, bounded at a minute, and one that fails is reported while the rest go on.
- The replica that runs the reconciler prunes once a day (`RunImagePrune`). It checks at start and then hourly whether a day has passed since the last prune, which is stored with the registry and written before the prune runs, so a prune that keeps failing is not retried hourly. A local server runs the same check at start-up, so it prunes at most once a day.
- `spov serve image prune` runs it on demand; `--dry-run` lists what it would delete. Run beside a local server it cannot see that server's sessions, but every retention outlasts a sandbox's 24-hour limit, so an image a live sandbox was created from is never stale enough to go. It takes the current pin and proxy image from its own build and configuration, so it is run from the deployed build.
- Images that are not in the registry are not pruned automatically: the SDK cannot list a workspace's images. Those a launch still uses are entered when it does and are pruned from then on. An operator can delete the rest in Modal's console.

## Rationale

Building at launch makes add-ons usable without an operator per combination. Recipes are curated and deterministic, so a build on demand is the same build an operator would run, and layer reuse limits a variant build to its own add-ons. Using the newest registered build while the exact one builds in the background keeps launches fast, at the cost that one launch can run a patch or two behind what it asked for. Keying the record on the name with versions as written reuses what the server can already compute, and turns images already in Modal into records when a launch first uses them, with no migration step.

The store is where a hosted server keeps what must survive restarts and be shared between replicas. A local server's memory store does not survive its own idle exit, so it uses the state file.

Staleness, not a fixed count, decides pruning: it keeps what people use and lets go of what they stopped using, so a replaced patch goes quickly and a whole request only after a month without use. Keeping deleted entries is what makes pruning safe, because Modal keeps answering for a deleted name. Pruning runs where the reconciler runs, as renewals and sidecar checks do, so one replica does the work.

## Measurements

- Variant build durations on cached base layers: one add-on 34 to 43 s, two about 70 s, all eight about 3 min, so a typical first launch fits the five-minute launch limit. A recipe whose layers are all cached publishes in seconds: the base published in 1 s, and a first launch of the all-add-on variant, building included, took 7 s. When the base layers of a new pin are not cached, because the operator never built that base, a variant build builds the whole chain, about 1.5 min more. Re-run: `go test -tags integration ./internal/session/ -run 'AnAddonVariant|CredentialProxy'`.
- Image delete behaviour (Go SDK 0.10.0, `Images.Delete`, measured 2026-10-04): the delete took 125 ms, and a second delete of the same ID returned no error. A sandbox already running from the image kept working. The published name still resolved to the deleted ID and `HasImage` said true, and a new sandbox from it failed with `NotFound: image … not found`. The same recipe rebuilt in 2.1 s under a new ID, and publishing it made the name work again. The SDK says a delete removes only the final image, not its intermediate layers. Re-run: `go test -tags integration ./internal/sandbox/ -run TestIntegrationImageDeleteSpike`.

## Consequences

- A project's first launch with a new combination is slower, unless an older build of it exists. A request unused for a month builds again on its next launch (25 s to 1.5 min); a replaced patch is never needed again unless someone pins it exactly.
- A session can run older patches than the newest even though it asked for a moving version. The session records which it got.
- A background build uses Modal compute of its own, at most once per request per patch release.
- A local server with a lost state file starts with no records: its next launch finds an exact image, finds the image named as written, or builds on the launch path.
- The guards are `variantpick_test.go` (the order above) and `TestPrunableFollowsTheRetentions`.

## Known gaps

- Intermediate layers stay after a delete, and whether Modal collects them is undocumented, so a delete may free less than the image's size.
- The retention periods are fixed defaults.
- Images that are not in the registry and that no launch has used are not pruned automatically.
