## Context

Local mode has one user, and the operating-system account is its boundary. Hosted mode has browser logins, an allowlist, server-side sessions and CLI tokens. Handlers must see the same thing in both modes, so none of them branches on mode. A local server is also a loopback listener that a web page in the user's browser can address.

The CLI reaches a hosted server from SSH sessions, containers and CI, where a loopback OAuth callback cannot work. The device authorization grant (RFC 8628) degrades to printing a code. A single grant is about 300 lines and a table. The Go OAuth provider frameworks are either pre-1.0 or full identity providers, so spov implements the grant itself, with `golang.org/x/oauth2`'s device client on the CLI side. PKCE belongs to the authorization-code grant. The device flow's defences are the entropy of the user code, rate limiting and showing what is being approved.

## Decision

### The Principal and the authenticators

A request carries one `auth.Principal` in its context: `UserID`, `OrgID`, `Email`, `Admin`, and `TokenID` when a stored CLI token authenticated it. Handlers read it with `auth.From(ctx)`. They never see the credential and never branch on mode. The middleware runs the configured `Authenticator` and answers 401 `problem+json` otherwise.

`Authenticate` returns the principal, `ErrUnauthenticated` when the request carries no usable credential, or another error when a credential is present but wrong. The second kind is logged and never echoed. A `Chain` tries authenticators in order and stops at the first principal or definite rejection, so only `ErrUnauthenticated` moves on to the next one.

- **Local** (`LocalAuthenticator`): `Authorization: Bearer <token>`, compared with `subtle.ConstantTimeCompare` against the token in the state file (see DL-002). Success is the fixed principal `{local, local, "", Admin: true}`. Any other credential form is rejected, and so is a request with more than one `Authorization` header, because a front proxy and the server could otherwise read different ones. The token exists so that "same operating-system user" is enforced by the state file's mode `0600`, not by "it is loopback". Another user on a shared machine can reach the port but not the file.
- **Hosted:** when browser login is configured the chain is the session cookie, then `spov_pat_` tokens, then the single shared bearer from `SPOV_SERVER_TOKEN`; without it the shared bearer is the only credential and the device flow is not served. The cookie authenticator is in DL-007. The shared bearer resolves to the `local` principal, which is an admin in the `local` organisation, so it is a full-access credential for whoever holds it. A hosted server refuses to start without one.
- **`StaticAuthenticator`** exists for tests.

Authorisation: a principal sees and controls the sessions it owns, and an admin sees and controls all of them. Every store query takes the principal's `OrgID`. Local mode is a single admin tenant, but the user and organisation columns are filled anyway, so the schema and the queries are the same in both modes.

Tokens, cookies and `Authorization` values are never logged. A rejected credential logs the remote address and the reason, never the credential.

### The browser guard

The browser guard wraps every listener, local included, and runs before authentication:

- `Host` must be the server's own address. Any loopback spelling of the listen port is accepted (`localhost`, `127.0.0.1`, `::1`). In hosted mode the host of `SPOV_PUBLIC_URL` is accepted too, because behind a proxy the `Host` header names it.
- `Sec-Fetch-Site`, when present, must be `same-origin` or `none`.
- `Origin`, when present, must name this server over http or https. `null` is another site.

Go's `http.CrossOriginProtection` does the `Origin` against `Host` comparison. spov's own `Sec-Fetch-Site` check runs ahead of it, because `CrossOriginProtection` exempts safe methods and spov's rule does not. A missing header is allowed, since Go clients, including the spov CLI, send neither.

The guard has one exemption: a `GET` to a registered path may be a top-level cross-site navigation, which is how the browser returns from the OAuth provider to the callback. Only the `Host` check still applies there. The exemption also skips the `Origin` check, which a browser does not send on a top-level `GET` navigation anyway. The route has to carry its own CSRF defence (see DL-007).

What it protects: a page in another tab cannot reach the local API by scanning ports. That page cannot read the token, but it could still cause requests, and `DELETE` is one of them. What it does not protect: a same-origin attacker, or any process that can read the token. The token is the credential. The same guard covers `/docs`, the schemas and the device approval page.

The approval page uses a cookie-only authenticator (`Deps.BrowserAuth`). Browsers' `EventSource` cannot set headers, so the web app reads SSE with `fetch` (see DL-005).

### The device flow

spov is its own authorization server. The GitHub login is how a human proves who they are on the approval page, and the device flow is how a CLI gets a spov token from that human.

`POST /device/code` and `POST /device/token` are unauthenticated by construction, because a CLI that is polling for a token has no credential yet. They sit outside `/api/v1/`.

`POST /device/code` returns `{device_code, user_code, verification_uri, verification_uri_complete, expires_in: 600, interval: 5}`.

- `device_code` is 32 random bytes, base64url, stored as a sha256 hash.
- `user_code` is 8 characters from `BCDFGHJKLMNPQRSTVWXZ`, written `XXXX-XXXX` (20^8, about 2.6 x 10^10 values), unique among unexpired codes.
- `client_id` is the fixed string `spov-cli`. Another value is refused with `invalid_client`.
- The interval is a field on the server so a test can lower it. The real client waits a full interval before its first poll, so 5 s is a floor on a login the user has already approved. It is kept so that shorter intervals do not multiply polling by every waiting CLI.

`GET /device`, the approval page, is behind login and behind a browser session specifically. It authenticates with the cookie-only authenticator, and the handler independently refuses any principal that carries a `TokenID`. Otherwise a CLI token could approve a device flow. A stolen token could then mint fresh 90-day replacements for itself indefinitely, its expiry would mean nothing, and revoking it would evict nobody. The shared bearer cannot approve either. An anonymous visitor is redirected to `/login?next=/device` and not answered 401, which `auth.Optional` allows: it resolves a principal when there is one and serves the handler either way.

A submitted code that resolves shows a confirmation step naming what is being approved: the token name (`<hostname> · spov <version>`, sent by the CLI), the server, the user, and Approve and Deny. Approving is a second deliberate submit, so a link cannot grant access in one click. Opening the approval link from `verification_uri_complete` fills the code field in for the person.

The approval rate limit is per user and not per address, because the identity is known behind login and a shared address would punish bystanders. Five wrong codes in 10 minutes lock that user out for 15 minutes. A wrong code never reveals whether it exists. The counter is cleared only by a completed approval and never by a code that merely resolves. Because `/device/code` is unauthenticated, an attacker could otherwise start a flow of their own, submit its code, and reset the lockout between batches of guesses.

`POST /device/token` answers with RFC 8628 responses: `authorization_pending`, `slow_down` (polled faster than the interval, after which the server raises that code's interval by 5 s), `expired_token`, `access_denied`, and on approval `{access_token, token_type: "bearer"}` exactly once. The device code is deleted afterwards.

A device code is created in the `default` organisation and takes the approving user's organisation at approval, and both stores write the new `org_id` (`UpdateDeviceCode`). A CLI token and that user's browser session are therefore the same principal in the same organisation.

`Device.Sweep` deletes expired device codes every 10 minutes and once at start. A row is otherwise deleted only on exchange or denial, so every abandoned flow would leak a row for ever and keep its user code reserved.

### The token

A token is `spov_pat_`, then 32 random bytes in base62, then a 6-character base62 CRC32 of that random part. The server rejects a bad prefix or checksum before any database access. A fixed prefix and checksum let secret scanners match precisely, and the format is fixed because changing a token format after issuance is painful. The token is stored only as `sha256(token)` in `api_tokens`, with a name, `last_used_at` (written at most once a minute), `expires_at` and `revoked_at`. The lifetime is one constant, 90 days (`DefaultTokenLifetime`). There is no `--expires` and no administrator-set maximum. The token is shown once, in the CLI, and never on a web page. An opaque token is revoked with one row update, where a signed token would need a denylist lookup on every request anyway.

`TokenAuthenticator` takes `Authorization: Bearer spov_pat_...`, looks up the hash, checks the token is neither revoked nor expired, loads the user, re-checks the allowlist, and returns the principal with `TokenID` set. Any other bearer form is `ErrUnauthenticated`. A well-formed token that is unknown stops the chain. Local mode wires only `LocalAuthenticator`, so a local state-file token never reaches it.

`GET /api/v1/me/tokens` lists id, name, creation, last use and expiry, and never the hash or the token. `DELETE /api/v1/me/tokens/{id|current}` revokes one. Another user's token ID is 404 and not 403, so it does not confirm that the ID exists. `current` resolves through `Principal.TokenID`, so from a browser cookie it is 404. A token is a principal of its user, with no narrower scope.

### The CLI side

`spov login --server URL` (or the resolved server) runs the device flow with `x/oauth2`'s `DeviceAuth` and `DeviceAccessToken`. It prints the URL and the code, opens a browser when there is one, and stores the token in the credential store under `server:<host>` (see DL-008). `ServerKey` includes the scheme for plain http, so `http://host` and `https://host` are different entries and a token minted for a plaintext server is never sent to the TLS one. `spov logout` revokes the token on the server (`DELETE /api/v1/me/tokens/current`) and then deletes it locally. If the revoke fails, it still deletes locally and warns. `spov whoami` prints `GET /api/v1/me`. With no `--server` and no configured `server.url`, `spov login` explains that local mode needs no login.

For a non-loopback server the token comes from `SPOV_SERVER_TOKEN` and otherwise from the credential store entry for the host. A 401 prints `run spov login --server ...`.

## Rationale

- One principal removes the branches on mode that would otherwise creep into handlers.
- The device flow suits a tool whose audience is headless first.
- Fixing the token format now avoids a painful change later.
- CLI tokens and web sessions stay separate, since their lifetimes, revocation and storage differ. One `Chain` resolves either to the same principal.

## Measurements

- **`x/oauth2` auth style.** With `Endpoint.AuthStyle` unset the client probes: it sends `client_id` in the `Authorization` header and retries in the body on any error. That doubles every poll and replaces the server's error with the retry's, so `access_denied` never reaches the caller and the login hangs until the code expires. `oauth2.AuthStyleInParams` fixes it (`TestDeviceConfigSetsAuthStyleInParams`). A spike checked `x/oauth2`'s device client against a hand-rolled server (happy path, denial, expiry, `slow_down`, the token checksum, user-code entropy and this probe). Re-run: `go test -tags integration ./internal/server/ -run Phase2Device -v`, `go test ./internal/cli/ -run Login` and `go test ./internal/server/ -run TestDeviceFlowIssuesAWorkingToken`.
- **Lockout reset.** When a code that merely resolved cleared the attempt counter, 20 consecutive wrong guesses produced no lockout. Only a completed approval clears it (`TestTheLockoutCannotBeResetByASelfIssuedCode`, `TestACompletedApprovalClearsTheAttemptCounter`).
- **Token approval.** A CLI token approving a device flow was reproduced and is refused (`TestACLITokenCannotApproveADeviceFlow`, `TestTheSharedBearerCannotApproveADeviceFlow`).
- **Client wait.** The real `x/oauth2` client waits at least one whole-second interval before its first poll. The server's tests therefore post the grant directly (`deviceFixture.accessToken`, `deviceFixture.poll`). Only `TestDeviceFlowIssuesAWorkingToken` and the CLI's login tests use the real client, on purpose, as the evidence that the endpoints work with it.

## Consequences

- A stolen token is a user's full access until it is revoked or expires. Scoped tokens do not exist.
- The shared bearer stays wired in hosted mode and is a full administrator credential. Deployments that use browser login and CLI tokens can treat it as a break-glass credential and keep its value private.
- The browser guard refuses a request with a foreign `Host`, so a hosted server behind a proxy must set `SPOV_PUBLIC_URL` (see DL-010).

## Known gaps

- Rate limits and lockouts are in memory per replica. With N replicas the budget is N times the stated one, and every deploy resets it. That is acceptable against a 20^8 space, and it is to be revisited if the allowlist widens.
- An administrator cannot list or revoke another user's tokens.
- The approval page's only anti-phishing signal is the token name, which the requesting client chooses. A device-code phish, where an attacker starts a flow and sends their user code to a victim, is defended by the confirmation step and by the page being unreachable from another site. Nothing lets the victim tell the code they just generated from one they were sent. Showing the requesting client's IP address on the confirmation step is the obvious next control and is not built.
