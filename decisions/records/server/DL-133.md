## Context

The November 2026 security review (findings M2 and M3) found no rate limit anywhere in the server. Anonymous `GET /login` and `POST /device/code` each write a row (a `web_sessions` row with a 15-minute life, a `device_codes` row with a 10-minute life) with no bound per address or in total, and three signed-in paths read every `web_sessions` row. A signed-in user could open thousands of event streams, each reading the store every two seconds, or send any number of concurrent requests and creates. The `http.Server` set only `ReadHeaderTimeout`, so a body could be sent a byte at a time and an idle keep-alive connection was never closed. huma also gives every operation with a body its own five-second read deadline by default, which is too short for a 24 MiB sync bundle on a slow link.

## Decision

The server enforces fixed request limits. They are constants in `internal/server/limits.go`, checked by `TestTheDefaultLimitsAreTheDecidedValues`; `Deps.Limits` replaces them only in a test, with its own clock. The only new setting is `server.trusted_proxies`.

Every limit is in memory and per replica. A rate is a token bucket. Unless noted, a refused request is a 429 with `Retry-After` in whole seconds (at least 1) and an RFC 9457 problem whose detail names the limit; the CLI prints that detail.

Anonymous sign-in, keyed by client address:

| Limit | Value | When hit |
|---|---|---|
| Sign-ins started (`GET /login` and `POST /device/code`, one bucket for both), per client address | 30 a minute, burst 30 | 429; on the browser route the login error page, on the device route `{"error": "slow_down", "error_description": ...}` |
| The same, per client network (an IPv4 /24 or an IPv6 /48) | 300 a minute, burst 300 | as above, the message naming the network |
| Polls of `POST /device/token`, per client address | 120 a minute, burst 120 | 429 with `{"error": "slow_down"}`, which x/oauth2's device client answers by polling 5 s slower |
| The same, per client network | 1,200 a minute, burst 1,200 | as above |
| Browser logins started on this replica | 10,000 within `FlowLifetime` (15 min) | 503 with `Retry-After`; on the device route `temporarily_unavailable` |
| Device codes started on this replica | 10,000 within `DeviceCodeLifetime` (10 min) | 503 with `Retry-After` |
| Places one client network holds in each of those two caps | 500 | 429 with `Retry-After` until that network's oldest start leaves the window; on the device route `slow_down` |

The two caps are a sliding count of the starts this replica admitted within the row's life, with no store query, so the rows one replica can create are bounded at any time. A start counts when it is admitted, whether or not it then writes a row (a `GET /login` from a browser already signed in counts). The limits are checked in order: the address's bucket, the network's bucket, the network's share of the cap, the cap. A start refused by a bucket does not take a place in the cap, and one the network's bucket refuses gets its address's token back. A start refused by the share or the cap has spent its tokens. Each cap keeps, beside its count, each network's own starts within the window; a network is dropped once its last start leaves, so that map never holds more entries than the cap. A refused `GET /login` never reaches the handler, so scs commits no session row for it.

The sign-in limits run behind the browser guard, inside the handler it wraps for the login and device routes. A request the guard refuses (a wrong `Host`, a cross-site `Sec-Fetch-Site` or `Origin`) is answered 403 before any limit sees it, and spends neither a token nor a place.

Signed-in users, keyed by the principal's org and user ID (the shared `SPOV_SERVER_TOKEN` principal is one user), on every request under `/api/v1/`:

| Limit | Value | When hit |
|---|---|---|
| API requests | 600 a minute, burst 100 | 429 |
| Session creates, job creates and session resumes (`create-session`, `create-job`, `resume-session`), on top of the request bucket | 20 a minute, burst 20 | 429 |
| Open event streams | 20 | 429 on the next, `Retry-After: 10` |
| Requests in progress, streams not counted | 32 | 429, `Retry-After: 1` |
| Request body on a route that takes no bundle | 1 MiB | 413 |

The body limits were already `MaxBodyBytes` (1 MiB) and `MaxSessionBodyBytes` (24 MiB on session create, job create and session resume, DL-027, DL-098, DL-100), applied through `http.MaxBytesReader` and huma's per-operation limit. They stay. A body whose declared length is over its route's limit is now refused with 413 before any of it is read, on every route including the device flow's open endpoints, whose form parse answered 400 before.

Which routes are streams and which are creates is read off the API document at startup (`routeClasses`): a stream is an operation registered through `registerSSE`, a create is one of the three operation IDs, matched by the mux pattern humago registers each operation under. The per-user limits are middleware between authentication and the mux, in `Server.Handler`; the anonymous ones run in `Handler` behind the browser guard and before the login and device routes.

Not limited: `/livez`, `/readyz`, `/startupz`, `/opencode-pin.json`, the web app's static files, the device approval page (which has its own per-user attempt limit, DL-006) and the Prometheus listener.

The client address is the connection's peer, unless the peer is inside `server.trusted_proxies`. From a trusted peer it is the right-most `X-Forwarded-For` entry, across every such header, that is not itself trusted; an entry that does not parse ends the walk at the last good address, and when every entry is trusted the left-most one is used. The header is never read from any other peer. The first request per process from an untrusted peer that carries the header logs one warning naming the setting. An IPv6 client is counted by its /64 for the per-address limits, and its network is its /48; an IPv4 client's network is its /24. A peer address that does not parse is its own address and network. The sign-in limits are the only reader of this address; cookies, redirects and the browser guard never read a forwarded header.

`server.trusted_proxies` is a list of addresses and CIDR ranges, empty by default. Like every list (DL-026), it is set in the user file only, not through `SPOV_*`; `spov config show` shows it under `server`. An entry that is neither an address nor a range, or a range with host bits set, fails config validation and so refuses to start the server.

Timeouts: `ReadHeaderTimeout` stays 10 s, and `IdleTimeout` is 2 minutes. There is still no `WriteTimeout` and no server-wide `ReadTimeout`. A request with a body gets a read deadline of 30 s, or 5 minutes on the three bundle routes, set per request with `http.ResponseController.SetReadDeadline`. A request with no body, which every stream is, gets none. huma's own five-second per-operation deadline is overridden by a huma middleware (`keepReadDeadline`) that ignores huma's setting of a deadline and passes its clearing through; net/http clears the deadline itself once a body has been read. A body that misses its deadline fails the request (408 from huma).

Refusals are counted in `spov_requests_limited_total{limit}`, with `limit` from a closed set: `sign_in_rate` and `device_poll_rate` (an address's or a network's bucket), `sign_in_cap`, `device_code_cap`, `sign_in_share` and `device_code_share` (a network at its share of a cap), `requests`, `creates`, `streams`, `in_flight`.

Bucket sets do not grow without bound. Once a minute a set drops every bucket that has refilled to its burst, which holds nothing a new one would not. A set holds at most 100,000 keys; past that, new keys share one overflow bucket until a sweep makes room. Counts drop a key at zero.

The browser opens a live stream (`live.ts`) refused with a 429 once more after its `Retry-After`, bounded to between 1 s and 60 s, and treats a second 429 as it treats any refusal: final, so a page over its stream limit does not reopen in a loop, and the page shows the server's detail for a refused stream as it does for a refused request (`describeProblem`). A stream that opens earns its next 429 one more retry; the wait is not a gap, since the log stream resumes from its cursor. Every other non-200 on a stream open stays final, and the launch stream (`sse.ts`) is unchanged. The CLI's device login prints the server's description when a sign-in start is refused.

The CLI's waits, `spov jobs wait` and the wait in `spov attach` (DL-103, DL-025), treat a 429 from any of their reads as the server saying when to come back: they sleep for its `Retry-After` (`client.Error.RetryAfter`, read in seconds or as a date), at least the wait's poll interval and at most 60 s, print one line saying so, and read again. A 429 is not a failed read and counts toward no retry limit; the wait's own timeout and Ctrl-C still end it.

## Rationale

Limits in memory need no schema, no store round trip on the hot path and no coordination, and they fail open on a restart rather than locking anyone out. Per replica is the same trade DL-006 made for the approval limit. A hand-written bucket is about 40 lines; `golang.org/x/time/rate` is not in the module graph, and its limiter has no key set or eviction anyway.

A sliding count of starts is a bound on rows without reading the tables, and without trusting the sweep's timing: whatever the address mix, a replica admits at most 10,000 starts per row lifetime. The per-address buckets keep one client from taking all of that.

Reading `X-Forwarded-For` only from a configured proxy keeps the review's property that no forwarded header is trusted by default. Taking the right-most untrusted entry, rather than the left-most, means a client that writes its own header cannot choose the address it is counted under. Keying IPv6 by /64 is because one subscriber usually holds a whole /64, so a per-address key would give them 2^64 buckets.

Classifying routes from the API document means a new stream is counted as one without a list to keep in step. A per-request read deadline, rather than a server-wide `ReadTimeout`, lets the bundle routes have five minutes while every other route has 30 s, and leaves bodiless streams alone. Overriding huma's five-second default is what makes the bundle routes' five minutes real: before this decision a 24 MiB bundle had five seconds.

## Consequences

- Limits are per replica: N replicas allow N times as much, and a restart or deploy resets every count.
- The sign-in caps bound the rows each replica creates, not the rows in the database; N replicas can hold N times 10,000 sign-ins in progress. The review's other half of M2 (`Iterate` reading every `web_sessions` row) is not addressed here.
- One network cannot fill a sign-in cap: at 300 starts a minute and 500 places it gets a 429 of its own while everyone else signs in. A distributed source spread over 20 or more networks can still fill a cap and hold every sign-in on the replica at 503 until its starts leave the window, and holding it costs about 11 requests a second. Not storing a row at the start of a browser sign-in (carrying the flow's state in a signed cookie) would remove the browser cap altogether; that is left as later work.
- Many clients behind one carrier-grade NAT or one corporate /24 share a network's 300 starts a minute and its 500 places.
- A cross-site page cannot spend the sign-in limits with its visitors' addresses, since the guard refuses those requests first.
- A CLI wait under sustained 429s keeps waiting rather than failing; only its timeout or Ctrl-C ends it.
- Behind a reverse proxy, until `server.trusted_proxies` names it, every client shares the proxy's address for the per-address limits, and one busy address can use up everyone's sign-ins. The warning and `docs/server.md` say so.
- A trusted range that covers clients lets those clients choose their address. The docs say to name only the proxies.
- 20 live views per user is about ten browser tabs (a session page holds one or two streams) or terminals following a session. A page over the limit shows the refusal and must be reloaded.
- The per-user limits run after authentication, so an authentication lookup still happens for every request, including one that is then refused.
- `TestTheLogStreamsGzippedEventByEvent` and the five-minute reopen in `live.ts` are unchanged; `TestAStreamOutlivesTheReadDeadline` guards that a stream is not cut by a read deadline.
