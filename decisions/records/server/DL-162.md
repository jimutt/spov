## Context

The per-user concurrency limits are the bound on what one person can start on a hosted server, and a deployment that configures nothing gets the built-in pair (DL-009). That pair was three sessions and two jobs. It leaves little room to keep a few interactive sessions open while a small queue of autonomous work runs, and both numbers are well short of the point where a handful more sandboxes would stop being a rounding error against the other limits.

## Decision

The built-in defaults are five concurrent sessions and four unfinished jobs:

- `DefaultQuotas` in `internal/server/quota.go` holds five sessions and four jobs.
- `config.Defaults` in `internal/config/defaults.go` holds the same pair, so a server started without a `quotas` block carries them into `Deps.Quotas`.
- Jobs stay below sessions. The two limits are counted apart, so a person may run five interactive sessions and, in addition, four unfinished jobs. The lower job number is the spend choice DL-009 makes, not a share of the session limit.
- Nothing else changes: a zero field still means the built-in default and never "no limit", org defaults still come from `quotas` or `SPOV_QUOTAS_*`, and a per-user override still applies field by field over them.
- The limit meters need no change. `LimitMeter.svelte` draws one tick per unit up to 24, so these limits and any larger configured one stay a bounded summary line (DL-060). `limitmeter.svelte.test.ts` pins the cap and the real count beside it.
- The places that word a spend bound in terms of the old job default (DL-049, DL-101) now count from four.

`TestTheDefaultConcurrencyLimitsAreTheDecidedValues` pins both layers and checks that the config defaults agree with `DefaultQuotas`.

## Rationale

Five interactive sessions suit a person working across several checkouts and pages, and four jobs let a small batch run overnight without a create being refused for want of one slot. The shape of DL-009 is kept: sessions and jobs are counted apart, jobs stay a minority of the session allowance because a job runs unattended, and the wall clock and the job slot remain the spend bound.

A deployment that preferred the old numbers sets `max_concurrent_sessions: 3` and `max_concurrent_jobs: 2`; the change is only to what an unconfigured server does.

## Consequences

- An unconfigured deployment allows up to five session sandboxes and, counted apart, four job sandboxes per user, instead of three and two. That is still a small, bounded number, but it is more spend a single person can start before anything else stops them.
- Existing org configuration and per-user overrides are untouched, so a deployment that set either keeps it.
- A larger configured limit does not widen the sessions page's summary line: the meter renders at most 24 ticks and names the real count beside them.
