## Context

DL-159 stores, per session, the variants each model offers in that session's sandbox. The composer needs them, and the model switch (`POST /sessions/{ref}/model`, which already takes `provider/model#variant`) must not send a mode the model does not accept.

## Decision

- `GET /api/v1/sessions/{ref}/model-variants` (`session-model-variants`, `Cache-Control: no-store`) answers from the store, never the sandbox: `{read: bool, models: {"provider/model": ["low", "high", ...]}}`, `read` false and `models` an empty object while nothing is stored for the session's current sandbox. It is a `byRef` route in the tenant-isolation sweep (owner or admin, anyone else 404), and the owner's world in `newTenantWorld` holds stored variants with a marker.
- The switch accepts a `#variant` only when the session's stored list for its current sandbox names that variant for that model (`checkVariant`, after the launch's own model checks). Otherwise it answers 422: "<variant> is not a reasoning mode <provider/model> offers in this session", followed by "; it offers low, high, max" (the ones it does offer, in order), "; it offers none", or "; this session has not listed its models' reasoning modes yet" when nothing is stored for the current sandbox. A reference without a variant is unchanged: it selects the model's default.
- A launch's own model (`--model x#variant`, the profile's default) is not checked against this list, as before (DL-013, DL-014): there is no sandbox yet to ask.

## Rationale

The list a reader is offered and the list the switch accepts are one stored list, so a mode offered can always be chosen and nothing else can. A route of its own keeps a list of some tens of KB out of every session read and listing.

## Consequences

- A client that sent a hand-written `#variant` to the switch is now refused unless the sandbox offers it.
- Nothing is offered or accepted before the recorder's first attach to a run.
