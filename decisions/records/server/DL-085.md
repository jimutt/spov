## Context

A resumed session keeps its row and gets a new sandbox (DL-087), so a session has several sandboxes over its life. Today a lot keys on the session's own fields, and each assumes one sandbox per session:

- `store.Session` holds one `SandboxID` and one `Booted` image;
- usage bills a session from `CreatedAt` to `StoppedAt` (`billableWithin`, DL-009), so a session resumed a day later would be billed for the day it was stopped;
- the lifetime metric, the page's "Running for" and the listing's ages read the same two times;
- the connection and password caches are keyed by session (DL-030);
- the recorder gives up on a session for good after its retry budget (`abandoned`, DL-017).

The exit snapshot of each sandbox (DL-084) is ready seconds after the sandbox ends. It can be fetched later from the sandbox ID alone, so a server that restarted can still collect it.

## Decision

**Runs.** A new table, `session_runs`, has one row per sandbox a session had, numbered from 1, for interactive and job sessions alike. The memory store carries the same records. Each row holds:

- `sandbox_id`, `booted` (the image name it was recorded against, and the snapshot ID when it booted from one), `opencode` (the OpenCode version it ran);
- `started_at`, `running_at` (when it first reached `running`, empty if it never did) and `ended_at`;
- `origin`: `launch`, `snapshot` or `transcript`;
- `snapshot`: the exit snapshot's image ID once it is kept;
- `snapshot_state`: `none` (created without one), `pending`, `kept`, `failed` or `deleted`;
- `snapshot_at`: when the snapshot was kept.

`store.Session.SandboxID` and `Booted` stay the current run's, for the code that reads them today. A launch writes run 1 in the transaction that records the sandbox, and each resume writes the next run (DL-087).

A run ends when its session is marked `stopped` or `failed`, or when the reconciler reaps its sandbox (DL-004). `ended_at` is set in the same write as the state change. When the reconciler's listing-miss rule moves a `stopped` session back to `running` (DL-004), it clears the current run's `ended_at` and puts a `pending` snapshot state back to its create-time value. That amends DL-004.

The migration backfills run 1 for live sessions only. A session that had stopped before this change has no runs and is not resumable.

**Collection.** `Service.CollectSnapshots` runs once a minute where the reconciler runs. It calls `Provider.ExitSnapshot` for every `pending` run whose sandbox has ended: at most 8 at a time, each waiting at most 30 s, the whole pass bounded by 50 s. The resume path may also collect a pending run's snapshot itself (DL-088).

- A kept snapshot is written to the run.
- A run still pending 30 minutes after it ended, or one whose snapshot Modal reports failed, is marked `failed`, and the session can be resumed from the transcript (DL-089).
- A run that never reached `running` has its snapshot deleted as soon as it is kept, since it holds no work.

Nothing on a read path calls Modal for this (DL-018).

**Times.** Every reader of how long a session ran reads its runs, in one batched read per listing (never one per session):

- `billableWithin` sums each run's stretch between `started_at` and `ended_at` (now for the live run) inside the window. A session with no runs is billed from its own times, as before. This amends DL-009.
- `spov_session_lifetime_seconds` is recorded per run, with a closed-set `origin` label.
- The session page's "Running for" and "Stopped after", and the listing's ages, read the current run.

`StoppedAt` keeps the last run's end.

**Per-run state.** The connection and password caches are keyed by session and sandbox ID. A hit whose sandbox is not the session's current one is a miss. This amends DL-030. The recorder's retry budget and its abandonment are per run, so a session the recorder gave up on is recorded again when it resumes. This amends DL-017.

**Metrics.** `spov_snapshot_collections_total{outcome}`, where outcome is `kept`, `failed`, `none` or `deleted_unused`. Each gets a row in `docs/metrics.md` (DL-011).

## Rationale

A run per sandbox is what "reopen the same session" needs underneath. The reconciler, the recorder and the cost each ask about one sandbox at a time, and the row answers for the current one while the runs keep the history.

Snapshots live on the run rather than in DL-016's image registry: registry entries are keyed by an image name, and an exit snapshot has only an ID. The registry's rule is kept, though. The store says whether a snapshot exists, not Modal, and a run marked `deleted` is never booted.

Collecting after the end, by sandbox ID, from where the reconciler runs means a restart or a replica change loses nothing. The 30-minute limit covers a snapshot Modal never finishes without leaving it pending forever.

Caches and budgets keyed only by session would carry one sandbox's state into the next. A replica that missed the stop would steer through a dead connection, and a recorder that once gave up would never record again.

## Consequences

- A migration adds `session_runs`.
- `Fake` gains exit snapshots, so the collection and the resume paths are tested without Modal.
- Usage for a resumed session counts only the time a sandbox ran.
