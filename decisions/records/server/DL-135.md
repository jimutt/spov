## Context

The security review of 2026-11 listed a group of Low findings in the server and the credential proxy. None of them is exploitable on its own, but each is a gap that a second mistake would turn into one. This record gathers the fixes, one sentence each, with the decision each one amends. The finding numbers are the review's.

## Decision

Each of these now holds.

**Browser guard (A-05, amends DL-006 and DL-010).** An `Origin` that names the public host must carry the public URL's scheme (`BrowserGuard.RequirePublicScheme`), so `http://spov.example.com` is refused on an https deployment. The listen address and loopback names keep accepting either scheme, since an operator's port forward and the Vite dev proxy are plain http. With no public URL (local mode) nothing is required of the scheme.

**Session cookie (A-06, amends DL-007).** A Secure cookie is named `__Host-spov_session`, which a browser refuses when it was set by a sibling subdomain or with a Domain or another Path. On plain http the cookie keeps the name `spov_session`, because the prefix requires Secure. Everyone signs in once more after the change.

**Unexpected store errors (A-11, amends DL-005).** An error that is not one of the store's own sentinels and whose text begins "store: " at any depth of wrapping is answered with a 500 and the fixed message "internal error (reference NNNN); the detail is in the server log". The detail, redacted, goes to the process log under that reference. The same holds for the error event of a stream. A store call that ran out of time (a pool acquire or a dial, which wraps `context.DeadlineExceeded`) keeps its 504, with the fixed message "timed out (reference NNNN); the detail is in the server log"; a timeout that is not the store's keeps its redacted text. A store error that fails a launch is stored as the session's error, and sent as the launch stream's failure, as the fixed message, and the store error a job's provisioning returns becomes the job's error as the same message (`hideStoreError`, which still unwraps to the cause). Every other mapping in `toHumaError` is unchanged, so a deliberate message (a quota, a name in use, a refused model, a provider's error) reaches the client as before.

**Shared token strength (D-14, amends DL-006 and DL-002).** A hosted server refuses to start when `SPOV_SERVER_TOKEN` has fewer than 32 characters, and the error says `openssl rand -hex 32`. The local server's generated token is not affected.

**Response scrub (B-05, amends DL-034).** The scrub of a credentialed response also covers each secret's JSON form with escaped slashes (PHP's `\/`), its JSON string form, and its URL query and path escapes. A `206` response is refused unless it is one of the pass-through kinds (git packs, `application/octet-stream`, a provider's event stream), since a part of a body can cut a secret in two. The headers of informational (1xx) responses to a credentialed request are dropped; the status still reaches the client, so `100 Continue` works.

**Merge refusal (B-06, amends DL-034).** A pull request's merge is refused for any case of `merge` in the path, and with a `;parameter` after it, for GitHub, Forgejo and Gitea.

**Forgejo and Gitea query credentials (B-07, amends DL-034).** A request to a Forgejo or Gitea host whose query names `sudo`, `token` or `access_token`, in any case, split on `&` or `;`, gets no credential, as a GitLab request naming its own credential parameters already did. Forgejo, Gitea and GitLab read the same names from a form body, so a request to one of their hosts with any `Content-Type` header naming `application/x-www-form-urlencoded` or a `multipart/` type gets no credential either, whatever its path or method (`carriesForm`). The body is not read. No request on an allowed endpoint needs a form: tea, glab and the forges' API clients send JSON, git and LFS send their own types, and the form uploads these forges take (release assets, project uploads, issue attachments through tea, package publishes) are on paths or methods the policy already refuses. A forge write that sends a form on an allowed path reaches the forge with no credential and is answered 401.

**Where a re-mint is written (B-08, amends DL-034 and DL-021).** The `proxy` tag decides only when it says `1`. Without it, a renewal writes into the main container only when the session's recorded holder for that platform is the sandbox; a recorded holder of the proxy, or an unrecorded one (an adopted job sandbox) on a deployment that runs the proxy, fails the renewal before a token is minted (`ErrProxyUnknown`). An unrecorded holder on a deployment with no proxy keeps the main container.

**GitLab tokens in redaction (B-10, amends DL-005).** `internal/redact` matches GitLab's token prefixes (`glpat-`, `gldt-`, `glrt-`, `glrtr-`, `glcbt-`, `glptt-`, `gloas-`, `glft-`, `glimt-`, `glagent-`, `glsoat-`, `glffct-`, `glwt-`).

**Deliverable URLs (C-08, amends DL-051).** A forge's pull request URL is stored only when it is https, or http for a forge configured with http, on the forge's own host with no user information (`git.OwnURL`, applied by every platform's `FindPullRequest`); otherwise the pull request is kept with no URL. A job view serves only an http or https address with a host, whatever an older row holds. The web already draws a verified pull request with no URL as plain text and counts it in the list.

**Report names (C-11, amends DL-051 and DL-063).** A top-level Markdown file is collected as a report only when `jobs.SafeEntryName` accepts it: valid UTF-8 of at most 255 bytes, no empty or dot segment, and no backslash, colon or control character. `WriteReportBundle` applies the same check to every entry and refuses the bundle otherwise. A colon is refused because Windows reads `name:stream` as another file.

**Panics in background goroutines (D-13, amends DL-003, DL-017 and DL-018).** `internal/safego` runs a goroutine with a recover that logs the value and the stack through the server's warning log. `safego.Loop` runs a loop again after a panic, after a wait that doubles from 1 s to 1 min. `spov serve` runs the reconciler, the job sweep, the renewal, sidecar, prune, snapshot and metrics loops, the recorder, the allowlist refresh, the device-code sweep and the idle watcher under it. The launch and resume goroutines, the state and log feeds, the recorder's captures and frame readers, snapshot collection, the OpenCode grant push and a variant image build run under `safego.Do`. A recorder capture that panics gives its session up for that sandbox, as a spent redial budget does (DL-017): it is marked abandoned before the capture is forgotten, so the next poll does not attach again, and `spov.recorder.stopped` is written once with a note (`Recorder.giveUpAfterPanic`; `TestACaptureThatPanicsIsGivenUpLikeOneOutOfRedials`). A panicked launch or resume ends as a failed one does (`launchPanicked`, deferred in the goroutine): when the row is still starting it is marked failed (or stopped, when a delete asked for it) with the error "internal error (reference NNNN); the detail is in the server log", its run is ended, and the launch stream ends with `Launch failed`, status 500 and that detail; a row that already committed running keeps it and the stream ends ready. The panic then reaches `safego.Do`, which logs it with its stack. A sandbox a panicked launch had already created, before committing, is not terminated by this path, since the failure path it mirrors terminates none; it runs until its own sandbox timeout at most. A job's launch runs on the supervisor's worker, which River recovers. Request handlers are not wrapped; net/http recovers them, and River recovers its workers.

**Exec deadlines (amends DL-021, DL-025, DL-027, DL-034 and DL-101).** Every call of `Handle.Exec`, `ExecInput`, `ExecBounded` (DL-130) and `SidecarExecInput` runs under a deadline its caller sets: the seed 10 min, the sync export 10 min, the sync inspection 5 min, the password read 30 s, the recreated sidecar's CA install 1 min, the OpenCode grant write 30 s, the proxy binary write into the bake sandbox 5 min, and a token re-mint inside `renewTimeout`. `sandbox.Fake` answers `ErrExecNoDeadline` to an exec whose context has none, so a new caller without one fails its test. The Modal handle adds `DefaultExecTimeout` (15 min) under any exec that arrives with no deadline.

## Rationale

Each change is the smallest one that closes its finding and keeps the existing behaviour for everything else. The two places that could have been broader were left narrow on purpose. The browser guard keeps loopback origins on a hosted server, because an operator reaching a pod through a port forward is a supported use and a loopback origin cannot be set by a page on another site. The store-error rule keys on the store's own message prefix and its sentinels instead of turning every unmapped error into a 500, because provider and forge errors are deliberate, redacted and useful to the person who launched the session.

## Consequences

- Every browser session ends once, as the cookie's name changes on an https deployment.
- A hosted deployment with a short `SPOV_SERVER_TOKEN` fails to start until it is replaced. The CI probe and the test fixtures use a long one.
- A request through the proxy that asks for a byte range gets a 502 unless it is a git or binary transfer, and one whose Forgejo query names `token` or `sudo` reaches the forge without a credential.
- A job's sandbox adopted after a restart on a proxied deployment can no longer have its token renewed into the main container; it fails and is noted, as a proxied sandbox whose sidecar died does.
- A report named with a colon or a backslash is not collected. Nothing else about a report changes.
- A recovered panic is logged only. There is no metric, so an operator finds one by its log line. A panicked launch is counted as a failed launch in the launch metric.
- `spov ls` and the session page show a launch that failed on the store as "internal error (reference NNNN)"; the operator reads the cause in the server log under that reference.
- Not verified here: that GitHub, Forgejo and Gitea route `MERGE` as they route `merge` (the refusal does not depend on it), and the browser's behaviour with the `__Host-` prefix on a live deployment.
