## Context

Operators want to know whether work is progressing, where it fails and whether cleanup keeps up. spov has health endpoints, logs, usage estimates and the stored job and session state, and no metrics. Operators differ in what they run. Self-hosters mostly scrape Prometheus. Teams on managed observability expect OTLP push, which reaches Grafana Cloud, Datadog, Honeycomb or a collector, and Prometheus 3 can receive it too.

A hosted spov runs several replicas against one database (see DL-003). Some measurements are events that one process observes, such as an API request it served, a launch it ran or a job it delivered. Others describe shared state, such as how many jobs are queued. If every replica reported shared state, a sum across replicas would multiply it. If a scrape queried the database, scraping more often would mean more load. A retried delivery must not count as two completed jobs, and a scrape must never reach a sandbox.

Metric labels are also the easiest place to leak data or blow up cardinality. A goal, a report, a token, a URL, a repository name or any organisation, user, job or session ID as a label value would be both.

## Decision

### Instrumenting and exporting

Metrics are instrumented once with the OpenTelemetry Go SDK. `internal/telemetry` builds the `MeterProvider` and owns every instrument. A `depguard` rule in `.golangci.yml` allows the OpenTelemetry SDK, its exporters and the Prometheus client only there. Everything else records through typed methods on a nil-safe `*telemetry.Metrics`. A nil `Metrics` records nothing, which is what every test that does not care gets.

Two exporters are each turned on separately, and both can run at once:

- **Prometheus.** `metrics.prometheus_listen` in the server's config (`SPOV_METRICS_PROMETHEUS_LISTEN`) starts a separate HTTP listener that serves only `GET /metrics`. It is never on the public API port. The operator picks the address, such as `127.0.0.1:9464` or a private network. `spov serve` prints the listener's address when it starts.
- **OTLP.** It is on when `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` or `OTEL_EXPORTER_OTLP_ENDPOINT` is set. The transport is OTLP over HTTP (`http/protobuf`), configured by the exporter's own standard `OTEL_*` variables (headers, timeout, TLS, `OTEL_METRIC_EXPORT_INTERVAL`), which it reads from the process environment. spov adds no keys of its own. gRPC is not offered, because collectors and managed backends accept HTTP and a second exporter is not needed. An `OTEL_EXPORTER_OTLP_PROTOCOL` that names anything else is warned about at startup.

Nothing configured means nothing exported: the meter provider has no reader and recording costs next to nothing. `spov serve --local`, the server the CLI spawns, never exports, whatever is configured.

Export never affects work. A listener that cannot bind is a warning and is skipped, so a metrics port conflict cannot take the control plane down. A failed OTLP push goes to OpenTelemetry's global error handler, which spov points at its own warnings at most once every 15 minutes, so an unreachable collector cannot flood the log. Any later failure in setup closes the listener again and the server runs without metrics.

Every series carries the resource attributes `service.name=spov` (fixed, so `OTEL_SERVICE_NAME` does not rename it and dashboards can rely on it), `service.version` (the build) and `service.instance.id` (random per process, so replicas' series stay apart). OpenTelemetry's `autoexport` package was not used. When `OTEL_METRICS_EXPORTER` is unset its default is OTLP to localhost, which would need special-casing to keep "unset means none", and it adds the contrib module.

An unauthenticated `/metrics` protects nothing by itself. It is served on its own listener and never on the public API port. It carries operational counts with closed labels and no identifiers or content. Anyone who can reach the address can read the deployment's load and failure counts. That is acceptable because the operator binds the listener to loopback or a private network, and an operator who cannot do that must put an authenticating proxy in front of it. `docs/configuration.md` and `deploy/README.md` document the listener and the OTLP variables.

### Events are counted where the store accepted them

Counters and histograms are recorded by the process that observed the event and carry its `service.instance.id`, so summing across replicas is correct. An ending is recorded only after the store's move succeeds, so the state machine is the deduplication:

- A job's outcome is recorded after the move into a terminal state (`Supervisor.movedTo`). A move refused as an invalid transition, because another pass or replica already made it, records nothing. Queue delay is recorded where this call wrote `queued -> provisioning`.
- A session's stop goes through `Sessions().MarkStopped`, a conditional write that only one caller wins. A `Delete` racing the reconciler, or two `Delete` calls, count one stop. It is a conditional update in Postgres and part of the store contract. A stop is attributed to a job's session by `Jobs().BySession`, one read per stop, never by session name.
- Launch outcomes are recorded where the launch writes its result.

A redelivered queue attempt or a retried pass therefore cannot count an ending twice. One exception is left alone: a session that the reconciler marks ended after a transient listing miss, and then resurrects, counts its real stop again.

### Shared state is measured once

Jobs and sessions by state, and the age of the oldest queued job, are reported only by the replica that holds the reconciler lock (see DL-004). `Service.RunMetricsSnapshot` runs inside the leader loop and reads the cross-organisation `Jobs().ListLive` and `Sessions().ListLive` on its own 30 s tick. A session counts as a job's when an unfinished job names it. The observable gauges report the cached snapshot. A replica that is not leading reports none, and a replica that loses the lock stops reporting. The gap is up to one tick when leadership moves. A dashboard must not sum these gauges by `service.instance.id`, because there is only one series, and `docs/metrics.md` says so per metric.

A scrape does no work. It reads only the in-memory snapshot and the instruments, never queries the store or the provider, and never reaches a sandbox (see DL-018). If the two live listings become too heavy for a 30 s tick, an aggregate count by state is the next step.

### A closed catalogue

Every instrument is a method on `telemetry.Metrics`. Each label is a typed enum fixed in code (`store.JobKind`, `store.JobState`, `EndedBy`, `LaunchStep`, `Termination` and so on). No method takes a free string label, and inside each method a value outside its list is recorded as `other`, so a conversion from an arbitrary string cannot widen a label. The one exception is the API route, which is the Huma operation ID, a closed set defined by the server's own registrations, and never the request path. A stream (an SSE operation) is counted but not timed, since its duration says nothing about latency.

Forbidden as labels, always: any ID, name, goal, report, prompt, model output, token, URL, path, repository, e-mail address or error text. Errors are classified into the enums and never quoted. Typed labels make a leak a compile error, and a closed catalogue bounds cardinality by code and not by traffic.

The catalogue is the fixed `spov_`-prefixed set in `docs/metrics.md`, which lists each metric under its Prometheus name with its type, labels and values, whether it is per process or shared, and what to watch it for. Names use OpenTelemetry units (seconds, `{request}`, `1`). The families are:

- **API:** requests and request duration by operation, and quota refusals by limit (sessions, jobs, size, duration).
- **Jobs:** the shared job gauge and oldest queued age, job endings (kind, outcome, ended by), queue delay, clock used, delivery duration, verdict gates and judged deliverables.
- **Sessions:** the shared session gauge, launches by failed step (`setup`, `tokens`, `sandbox`, `server` or `none`), launch duration, lifetime (the basis for estimated billable time) and terminations by reason (`stopped`, `ended`, `reaped`, `failed`).
- **Background work:** reconciler runs and duration, supervisor passes, recorder gaps and reconnects, git token renewals, credential proxy recoveries and image builds.
- **Build:** `spov_build_info`.

`TestEveryMetricIsDocumented` records every instrument through the real Prometheus exporter and fails when a metric is missing from the document, when the document lists one that does not exist, or when the label keys differ. `TestTheDashboardQueriesDocumentedMetrics` fails when the dashboard queries an undocumented metric. Other tests read recorded values through `internal/telemetry/telemetrytest`.

### The dashboard

`deploy/grafana/spov-dashboard.json` is an importable Grafana dashboard over the Prometheus names, in three rows: work progressing, failures and cleanup health. `deploy/README.md` points to it.

## Rationale

- The instrumentation is the costly part, and with OpenTelemetry it is written once. Supporting both exporters is a config switch and some documentation, not two implementations.
- Prometheus on its own listener is what a self-hoster's scrape config expects, and keeping it off the public port means a hosted server does not publish operational counts to the internet.
- Confining shared state to the lock holder reuses a guarantee that already exists, that one replica does deployment-wide work. It also gives one unambiguous series where every dashboard would otherwise have to deduplicate.
- Counting at the store's accepted move means the metric agrees with the rows by construction.

## Consequences

- Adding a metric means a method, a documentation entry and, where useful, a panel. The test enforces the first two.
- Renaming a metric breaks operators' dashboards, so a rename after the first public release needs a release note.
- Model token and cost metering, alert rules, and client or sidecar telemetry are not part of the catalogue.
- Guard tests are `TestTheServerRecordsRequestsLaunchesStopsAndRefusals`, `TestACancelIsCountedOnce`, `TestTheSnapshotIsSharedStateWhileLeading`, `TestAJudgedEndingIsCountedOnce` and `TestAStreamIsCountedButNotTimed`.

## Known gaps

- The shared gauges can be missing for up to one refresh when leadership moves, or briefly reported by both the old and the new holder.
