## Context

People and service accounts manage schedules from the browser (DL-195) and the CLI (DL-196). A schedule creates jobs as its owner, so who may see or change one is as sensitive as who may see a job.

## Decision

- Routes, all tagged `schedules`, on a hosted server only (a local one answers 501):
  - `POST /api/v1/schedules` (`create-schedule`): name, cadence, zone and the job request; 201 with the view.
  - `GET /api/v1/schedules` (`list-schedules`): the caller's own, newest first, paged like jobs (DL-012); an admin passes `?all=true` for the org's.
  - `GET /api/v1/schedules/{ref}` (`get-schedule`): by name or id, with its history.
  - `PATCH /api/v1/schedules/{ref}` (`update-schedule`): any of name, cadence, zone, job request; checked again as at create (DL-191).
  - `POST /api/v1/schedules/{ref}/pause` and `/resume`; `DELETE /api/v1/schedules/{ref}`.
  - `POST /api/v1/schedules/{ref}/run` (`run-schedule`): fires now (DL-192), answering 202 with the job's id, 409 when the previous run is still going, 429 at the job limit, 422 with the create's refusal and a 500 with a reference for a fault, by the error's own kind. Its slot is the current minute, so a second run within the same minute answers with that minute's job. An admin's run of another person's schedule runs as the owner and writes an `admin_events` row (`schedule.run`) naming the schedule, its owner and the job, never the request.
- `{ref}` is the caller's own name for a schedule, else an id (`Service.GetSchedule`), reached by its owner or an admin like `Service.GetJob`: anyone else gets 404, never 403 (DL-006). A name is 1 to 63 lower-case letters, digits, dots, dashes or underscores, starting with a letter or digit (`scheduleNameRE`); one the owner holds already is a 409. Only the owner may change a schedule's job (an admin's change is a 422), checked as theirs; an admin may read by id, pause, resume, run and delete. A change of cadence or zone moves the next run from now, and a resume does too, clearing the failures, and is refused while the owner may no longer sign in. Every write applies only its own fields to the row read again and locked in a transaction (`changeSchedule`), so a fire's or an off-boarding's change made meanwhile is kept. Every route joins `tenantisolation_test.go`'s tables (`byRef` for the `{ref}` routes, `ownNamespace` for the listing, `creations` for create), and the owner's world in `newTenantWorld` holds a schedule with a marker.
- The view (`ScheduleView`) carries the stored job request, cadence, zone, state, paused reason, `next_run_at`, the next three slots (`next_runs`) for the form's preview, the failure count and the history, and never anything secret; the request holds no credential.
- A job fired by a schedule carries `schedule: {id, name}` on `JobView` (DL-195), resolved with one read per distinct schedule on a page (`scheduleNames`); the name is empty once the schedule is deleted.
- None of the routes is one of DL-133's counted creates, which are exactly the routes that take a bundle: run now is bounded by the job limit, as every fire is, and a save starts nothing.

## Rationale

Walling schedules the way jobs are walled reuses the guards that already protect jobs, and the sweep catches a route that leaks. Answering "run now" synchronously lets a person try a schedule before trusting its cadence.

## Consequences

- The tenant sweep's world, the OpenAPI document and the generated client grow by one resource.
