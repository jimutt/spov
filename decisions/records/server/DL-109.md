## Context

A hosted session (`spov-20261107-203158`) became unmessageable: every
send from the browser failed with 422 `this session has 2 conversations;
name one`. The store held two conversation rows. The first was the
person's own, opened by their first message. The second was a subagent
the agent itself spawned mid-session (a code-review Task run, nine
messages over ninety seconds), which the recorder recorded as a second
conversation of the session — by design, since DL-017 keeps one row per
sandbox OpenCode session.

DL-019 deliberately refuses an unnamed send when several conversations
exist rather than guess between them. That rule predates agents that
fork their own sessions, and its known gap only contemplates the
cross-replica first-message race. The web UI, the CLI and every other
client name no conversation, so the rule bricks the whole session the
moment an agent works the way agents work: interrupt, model switch and
resume-with-message fail through the same check, and the 422 names no
remedy the client could act on.

## Decision

### Unnamed resolves to the oldest

`steerInto` with no conversation named returns the oldest row, which
`ListConversations` already lists first on both stores. The person's
own conversation is always the oldest: `firstConversation` and
`jobConversation` open it for them on their first message, and anything
later is the agent's own (DL-045) or the stray second half of a
first-message race (DL-019). Naming a conversation still names it, and
naming one the session does not have is still refused.

`firstConversation` resolves a row that landed between the caller's
list and its own the same way, instead of refusing: the race it guards
against is the one case that creates two primaries, and the oldest is
the sane half there too.

### The API names the default

The `conversation` field on every steer-shaped request (send,
interrupt, cancel, model switch) now documents the default — omitted,
the session's oldest — instead of calling the field required. The
regenerated OpenAPI document and web client carry the same wording.

## Rationale

- The evidence supports one behaviour, not two: DL-025 already decided
  oldest-first for jobs and `attach` opens the oldest for the same
  reason. A rule that steers jobs to the oldest but refuses interactive
  sends would be two behaviours where the evidence supports one.
- A subagent's conversation is never what the person was talking to,
  but the fix does not need to identify subagents to route correctly:
  children are created after their parent by construction, so oldest
  already excludes them. Tracking parentage (OpenCode's `parentID`,
  `session.created`) stays future work for transcript fidelity, not a
  prerequisite for steering.
- Transcript resumes reuse the same OpenCode ids on import (DL-089),
  so the oldest survives a resume and keeps meaning the person's own.

## Consequences

- The DL-019 known gap about the first-message race stays valid, but
  its sting is gone: the second conversation stays empty and unnamed
  sends now reach the first.
- A caller that named no conversation and read the 422 as "pick one"
  now silently steers into the oldest; no client named none and read
  the count, since none could act on it.
- `TestSeveralConversationsMustBeNamed` becomes
  `TestSeveralConversationsSteerToTheOldestUnnamed`, and the interrupt
  test asserts the oldest rather than a refusal.
