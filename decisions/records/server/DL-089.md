## Context

Some stopped sessions have no usable snapshot:

- it was pruned or expired (DL-086), or Modal failed to take it (DL-085);
- snapshots are off, or the session ran without the proxy (DL-084);
- the deployment's OpenCode pin has moved since (DL-088).

The store still holds every conversation: each message whole in `store.Message.Raw` (DL-069), and each conversation's ID and title.

Spike S-TR1 (`internal/server/transcriptimport_integration_test.go`, 2026-11-05, local, pinned 2.0.22) used `POST /api/experimental/session/import`, which takes `{info, messages}`. Here `messages` is the list `GET /message` returns, which is what `Raw` holds, and `info` is a `Session.Info`. A conversation rebuilt from the stored messages in a fresh OpenCode kept its ID and every message, and on the next turn the model was sent the old history. S-TR1 used the real `Session.Info`, which the store does not keep today.

## Decision

**The sandbox.** A transcript resume boots a fresh sandbox:

- its image is the variant for the recorded add-ons at the deployment's current pin, picked and built as at launch (`pickVariant`, DL-016);
- its repositories are cloned as the launch cloned them: the same repositories at the same requested refs, with the same landing. Branches the agent pushed are not checked out;
- it gets `ExitSnapshot` under DL-084's rule.

**The import.** Once OpenCode answers, and before the session is `running`, each conversation of the session is imported in creation order. It is sent with its stored `Session.Info` and every stored message's `Raw`, oldest first, through `withConnection` (DL-030). An import that fails is noted in the log as `spov.session.import.failed` with the conversation's ID, and the resume carries on: the transcript is still in the store and on the page, but the agent will not see it. The import keeps each conversation's ID, so the recorder continues the same conversation rows.

**What the recorder keeps.** At attach, the recorder reads each conversation's `Session.Info` once (`GET /api/session/{id}`) and stores it whole as `conversations.info`, as it keeps messages whole. That is one read per conversation per attach, never on a timer (DL-018). A conversation recorded before this change has no info. For it the server builds one from what the store has (ID, title, directory, creation time), which S-TR1 must measure before implementation relies on it.

**The agent is told.** The generated `AGENTS.md` gets a section saying the session was resumed from its transcript: the workspace is a fresh clone, and uncommitted changes, installed packages and files the earlier runs wrote are gone.

**The contract.** The import endpoint goes into `contract.Used`, with a wrapped fake (DL-035). S-TR1 joins the OpenCode-bump checks:

```
SPOV_PROBE=1 go test -tags integration ./internal/server/ -run STR1 -v
```

## Rationale

The transcript is what spov always has, so this path makes every interactive session resumable, whatever happened to its sandbox. Cloning as at launch is the only state spov can rebuild faithfully, and saying so (DL-090) is better than guessing which pushed branch the agent meant.

Importing before `running` means a first message (DL-087) never reaches a conversation that is still empty. Keeping the info whole at attach costs one read the recorder can take while it is connected anyway.

## Consequences

- A migration adds `conversations.info`.
- The import endpoint is experimental in OpenCode, and the contract check and S-TR1 are its guards on a bump. If it goes away, transcript resume still gives a fresh sandbox with the old transcript readable on the page, and the import failure is noted.
- How large a conversation the import takes is unmeasured. Implementation measures it with the long-conversation fixture behind `TestIntegrationMeasureLongConversations` (DL-070).
