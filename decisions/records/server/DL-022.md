## Context

Several features cut across the workstreams: the organisation's shared GitHub App and the tier a launch records, mixed report sets, blocked jobs and takeover, coordinated pull requests, and restarts in the middle of a job. Each is covered piece by piece by unit tests against fakes of the store. That shows each piece works. It does not show that the pieces compose through the wiring `spov serve` ships, on a real database, or that a page tells the reader the truth. Readiness is judged per criterion, not by the existence of a feature.

## Decision

### Three layers, and the layer is named

A scenario is validated in three layers. Each acceptance criterion is carried by one of them, the status table of the scenario's evidence document names which, and a criterion carried by the automated suite says so and names the test. It is not claimed as exercised by hand.

1. **An automated control-plane suite** (`TestScenarioN` in `internal/cli`, behind the `integration` tag, in CI's Postgres job). It builds a server with the functions `spov serve` uses (`serverDeps`, `wireLogin`, `wireCredentials` and, for jobs, `wireJobs`) on a fresh real Postgres database, against a fake GitHub (`scenarioGitHub`) and a fake sandbox provider. `scenarioGitHub` checks an App's JWT signature against the App's live keys, so a wrong or deleted key fails as it would on GitHub, and it answers a repository only to a credential that reaches it. The periodic passes (renewal, sidecar checks) are called directly, a clock the test moves drives everything, and a restart is a second server on the same database. The suite must have teeth: a deliberately broken tier rule must fail it, at the step of `TestScenario5` labelled 5.19. Each suite gets a fresh database of its own, dropped afterwards, and two seeded users, an admin and a member. It runs with `SPOV_TEST_DATABASE_URL` set and is skipped without it: `go test -tags integration ./internal/cli/ -run 'TestScenario'`.
2. **A browser journey** run with Playwright, against a local hosted-mode server and real Modal sandboxes. It covers what only a real OpenCode and the pages show.
3. **A short real-forge check** on a dedicated test account: a dedicated test GitHub App, a fine-grained token and a few private test repositories. After it the rest runs unattended. It covers git through the real proxy, one real renewal and one real sidecar recreation, gate 2 against GitHub, and a clone that fails with the wrong credential.

A step that needs something only an operator can do (deleting an App key, revoking a token on GitHub) stays in the automated layer, where the fake does it. The automated layer proves wiring and tier rules against a GitHub that behaves as the real one where spov relies on it. What it cannot prove (the real GitHub's answers, git through the proxy, the pages) belongs to layers 2 and 3. The sandbox and model cost of those layers is accepted release work, and each run cleans up what it creates.

Each scenario keeps one evidence document: the build (commit and version), the deployment, the date, a numbered script another person can repeat, one row per acceptance criterion marked pass, fail or not-run with the layer that carries it, and one dated section per run. A later run appends a section and never rewrites an earlier one, so a failed row stays on record. Secrets, tokens and private-key material are never pasted into evidence; credential rows are described by kind and tier only. `scripts/scenarios/secret-scan.sh` looks for any of the scenario's secrets in a server log, saved responses and CLI output, and for anything shaped like a private key or a forge or provider token. It names which secret appeared where without printing it. `scripts/scenarios/hosted-local.sh` starts the local hosted-mode server for layers 2 and 3, with its own Postgres container, the credential proxy and a dedicated Modal environment, reading secrets from files kept outside the repository. Any secret found in a response or log is a release blocker.

### Users and helpers, never product changes

Users are seeded, not signed in through GitHub. `TestIntegrationScenarioSeedUsers` (run by `scripts/scenarios/hosted-local.sh seed`) creates an admin and a non-admin in the server's own database, each with a CLI token and a browser session made through the server's own session manager. Steps the product offers no way to cause use test-only helpers behind the integration tag. The product does not gain a way to force a renewal, kill a sidecar or sign in without GitHub. `TestIntegrationScenarioKillSidecar` terminates one session's proxy sidecar through the Modal SDK so the reconciler can recreate it. It needs the sandbox's ID in `SPOV_SCENARIO_KILL_SIDECAR` and a dedicated Modal environment in `MODAL_ENVIRONMENT`, and it touches only a spov sandbox with a `proxy` tag whose sidecar has never been recreated, since a second death ends the session.

### The harness

- Every suite starts its clock about three hours behind the real one (`newScenarioServer`). The store stamps an event's `created_at` with its own clock, and `inUse` compares that with mint times taken from the scenario's clock, so once a session has an event it stays in use. The suite therefore cannot catch an idle-renewal regression; the unit guards do (see DL-021).
- Wiring added to `spov serve` belongs in `serverDeps`, `wireLogin`, `wireCredentials`, `wireJobs` or `newReconciler`, or the suite stops testing it. Gate 2 is the one call the suite rebuilds, and `TestGateTwoIsWiredToTheJobOwnersForge` guards that wiring.
- Job suites (`TestScenario1`, `2`, `6`, `7`) share `wireJobs`, the supervisor wiring `runServe` uses, with a queue that only records. A suite calls `Supervisor.Run` per pass. `jobOpenCode` is the job sandbox's OpenCode as an httptest server wrapped in `contract.Checked`, so each request is checked against the pinned build's contract (see DL-035). It serves `/api/fs/list` and `/api/fs/read` for `/workspace/out` and the plugin's evidence and outcome files from whatever a step put there. Frames are written to the store as the recorder would. `hold` makes a read wait, which is how a delivery is cut off partway.
- `withJobs` sets the Postgres store's clock to the scenario's, because the wall-clock ledger is stamped with the store's clock and judged on the supervisor's.
- `restart` stops the server, calls `sandbox.Fake.Reattach` (which models a new process's handles; the old server's `Close` detaches them), boots a new server on the same database and runs one reconciler pass, as a booting `spov serve` does. `withJobs` must be called again afterwards for the new store's clock.
- `boot` starts the Prometheus listener as `spov serve` does, so each process's own counts can be scraped (see DL-011).

### What each suite covers

**Shared App lifecycle and the recorded tier (`TestScenario5`).** On a hosted deployment:

- An admin storing a deliberately broken key or ID is refused and nothing is stored. A real one is stored, and the status view names the installation, the repositories it reaches and any missing permission.
- A replacement key of the same App applies to new launches at once. A running session keeps its token until it expires, and its next renewal mints from the replacement.
- A non-admin can neither read nor change the organisation's settings, and no private-key material appears in any response, page, log or CLI output.
- A credential that is present but does not work fails and never substitutes the other tier. Only an unreadable credential is detected when a tier is resolved. A readable one that does not work is used and fails later: an App whose key was revoked fails when spov mints its token, and a revoked personal token fails at clone. Neither falls through to the other tier (see DL-042).
- With the stored App removed, a launch on a repository only the App reached is refused when the user holds no credential. When they hold a stored token that cannot see the repository, the launch is refused before any sandbox exists (see DL-043). A personal-first launch on a repository the user's token reaches works.
- With the App set in the environment, the status shows its source as the environment, and storing or removing one in Settings is refused with 409. The environment and a stored App never apply to the same platform.
- Every administrative change leaves an audit row without a secret.
- Once a launch records a tier, renewal, sidecar recreation, adoption after a restart and gate 2 use that tier only. After a restart the sessions keep their tier and token. A renewal mints from the recorded tier with the replacement key. A killed sidecar is recreated holding the recorded tier's token. Gate 2 verifies through the recorded tier on a repository only it can see. With the recorded tier's credential removed, a renewal stops, gate 2 reports unverified (never succeeding through the other tier, even where the other tier could see the repository), a recreated sidecar is never handed the other tier's token, and no secret appears in the errors (`TestARecordedTierIsTheOnlyOne`, `TestALaunchRecordsItsTierAndGateTwoFollowsIt`). A failed renewal is also noted in the session's log (see DL-021).
- The browser lists which tier reaches each repository, a git access of `all` on the App is refused when asked for and falls back when only preferred (see DL-043), and the CLI's preference takes the App.

In the real check the timeline is: launch with a shared-first preference and confirm the recorded tiers; restart the control plane once every job in the run is running (a job still provisioning takes the adoption path, which marks its token due at once and moves its renewal); wait for one renewal in real time; only then kill the sidecar and observe its recreation, which mints a new token and moves that session's next renewal; let the job open its change request and confirm gate 2; then remove the recorded tier's credential with further sessions live, timed so one renewal and one gate 2 fall after the removal. Removal is organisation-wide, so the run orders its sessions around one removal and restores the App afterwards. Page views and metric scrapes must not extend a sandbox's life.

**Mixed report sets (`TestScenario2`).** Several reports and their images collected give gate 2 passed. A mixed set (one unreadable, one over 10 MiB, one that lost an image) is judged partial, with each member's fault in its detail. A listing that fails leaves gate 2 unverified, never failed, and the job not succeeding. A declared `unfinished` is partial. A failed check fails a job whether its reports are verified or partial. A passing check with no verified report fails. After the sandbox is terminated, and after a server restart, each collected report is read from `GET /jobs/{id}/file` and a report with images downloads as its bundle (see DL-051, DL-050). The browser run uses two short report jobs: one asked for two reports and linking a missing image shows "Succeeded, partly", gate 2's detail and the preview after the sandbox has ended, and one with a check that exits 1 is shown failed with its reports still readable. No forge is involved, so there is no real-forge layer.

**Blocked jobs and takeover (`TestScenario6`).** At the pin a job does not ask: its plugin decides every permission and the `question` tool is denied on every job kind, so a job reaches `blocked` only if its permission hook failed to install (see DL-040, DL-045). Forms are therefore not applicable to jobs and are proven on an interactive session. The suite writes a `permission.asked` frame in the measured shape. It asserts that the blocked job's wall clock keeps counting; that a message to it is refused with 409; that `always` is refused; that CLI attach treats it as joinable; that a second open request keeps it blocked after the first is answered; that allow-once releases it to `running` and releases the plugin's loop; that a handover message delivered to a running job steers it and stops the clock, and Resume continues with what was left; that a continue message leaves it running and counting; and that after parking, answering, steering and resuming the job ends at its wall clock having used exactly its allowance, so no answer or resume added time (see DL-049, DL-052, DL-054). A permission answer's reach is the person's own: allow-once covers the one call asked, and `always` is refused, so a job's launch-time policy is never widened for later calls. The browser run shows "Paused for you" while steered and the remaining time after the resume.

**Coordinated pull requests (`TestScenario1`).** One `pr` job over two repositories, against `scenarioGitHub`'s pull requests. Attach waits while the job is queued and joins it once it runs. A continue message is read without pausing it and its clock keeps counting. Three takeovers and resumes with twenty steered minutes each add no time. A correction enqueued before the agent completes keeps the job running until the message is delivered; the plugin's half of that deferral is `TestCompletionWaitsForAQueuedMessage`, and the suite proves the control plane's half, which is that the job is not concluded while a message waits and the verdict reads the last declaration and the full inventory. Final evidence of two pull requests in one repository, a supporting one recorded after a deferred completion, one recorded twice, one in a repository the job was not given, and a failed check then a passing one is judged as three verified pull requests and a passed check, each looked up with a token for its own repository alone, with exactly the running time on its clock. A three-repository job that records one pull request is a full success and its sandbox token reaches all three. A recorded pull request that delivery closes is missing, and the job is a partial success. A recorded pull request is an evidence line named `opencode.DeliverableEvent`. A late correction cannot be timed in a real run, which is why the suite exists; the real run only shows that GitHub answers as the fake does. A pull request merged before the job ended is verified. A recorded pull request the agent withdrew after a person wrote is left out of the set, and one withdrawn without such a message is judged as recorded (see DL-051). Every suite ends by scanning its responses and the server log for the scenario's secrets.

**Restarts during work and delivery (`TestScenario7`).** One report job is restarted onto a new server process, over the same database and sandboxes, in each state a restart can meet it in:

- running: it runs on, and the minutes across the restart count once;
- steered: it stays paused, and Resume on the new process releases the loop once and adds no time;
- blocked: it stays blocked and counting, and an answer on the new process releases it;
- past its allowance while the server was down: the first pass on the new process bounds it, with one wall-clock marker;
- delivering, cut off partway (`hold` on the second report read, then the pass's context cancelled): the next process finishes it, reads each report once, stores each once, stops the run once and writes one evidence, collection and verdict.

The ending, its gates and its deliverables are counted once, by the process that wrote the ending, and a redelivery on that or a later process counts nothing. After a restart, reading a running job's API views, live streams and pages, and scraping the metrics, sends nothing to its sandbox (see DL-018). Restart recovery alone is not proof that an upgrade is safe; what is promised across upgrades is in DL-010.

**Forgejo and Gitea (`TestScenario4`)** runs on the same harness against real servers (see DL-041).

## Rationale

- Per-slice tests against fakes cannot show that the shipped wiring composes. Building the suite from `spov serve`'s own functions makes it test what ships, and extracting `wireJobs` from `runServe` exists so job suites do the same.
- A fake GitHub that verifies signatures and reach is what makes a tier rule testable. A rule that falls through to the other tier must fail the suite.
- The automated layer can cut a delivery off at a chosen point and time a late correction, which a real run cannot do. The real layers show what only a real OpenCode, proxy and GitHub show.
- Naming the layer per criterion stops a unit test being counted as a manual pass.

## Measurements

- **Sidecar recreation.** A sidecar that exited by itself was measured in spike S-I4 (see DL-034). A terminated sidecar, recreated under the same name, was first measured by a combined-scenario run: the reconciler recreates it, and a recreation mints a new token. Re-run: `SPOV_SCENARIO_KILL_SIDECAR=<sandbox-id> MODAL_ENVIRONMENT=<environment> go test -tags integration ./internal/sandbox/ -run ScenarioKillSidecar -v`. This needs Modal and creates billable sandboxes.
- **Renewal timing.** An App token lasts one hour and `RenewWithin` is 15 minutes, so a renewal falls about 45 minutes after the mint while the session is in use.
- **Idle timeout under observation.** An interactive session with a short idle timeout, whose page was kept open and reloaded and whose API views and metrics were read every 20 seconds, still ended at its idle timeout. Viewing and scraping do not extend a sandbox's lifetime. Re-run the suite half with `go test -tags integration ./internal/cli/ -run TestScenario7` (Postgres).

## Consequences

- The suites are the regression gate for cross-cutting behaviour. A change to `spov serve`'s wiring that is not made in the functions the harness calls leaves the suite testing something else.
- Real-forge and real-sandbox runs are release work with a cost, and they use dedicated test accounts, a dedicated Modal environment and repositories created for the purpose.
- The scenario helpers are tools behind opt-in variables and the integration tag, not tests of spov.
