## Context

Everything that shapes a sandbox beyond its repositories (egress, routed credentials, variables, add-ons, git access) comes from config files and flags that only the CLI reads. A browser launch gets the defaults: every `always` routed credential, the server's egress, no add-ons. A person who works across several projects wants a different set per project, and in particular wants some credentials kept out of the others. Locally that is done with project files and `--credentials`; the browser has nothing.

A named bundle picked at launch, called a **sandbox template** ("template" where the context is clear). "Environment" was rejected because `sandbox.env` and `--env` already mean variables, "profile" is the account's defaults, and "preset" is the egress presets and the registry presets. Templates are personal only, are not bound to repositories, and a launch that names none behaves as today.

## Decision

### What a template holds

A template has a name, an optional description (at most 200 characters), and any of these settings. A setting left out is not part of the template.

- `egress`: a preset name (`open`, `install`, `agent`), and `egress_extra_domains` (at most 16). Extra domains need a preset in the same template, and not `open`.
- `credentials`: a list of at least one routed credential name, or `no_credentials`. Left out, the launch's default applies (DL-075). An empty list is refused at write: attaching none is said with `no_credentials`, never with a list that a later step could read as "not set". A name stands for whichever credential of that name the caller's candidates hold at launch (their own before the organisation's, DL-075), so one re-stored later under the same name is what attaches.
- `env`: variables, name to value, under `opencode.CheckUserEnv`'s rules (DL-097).
- `addons` and `apt`.

An empty `env`, `addons`, `apt` or `egress_extra_domains` is the same as leaving it out, and is stored that way.
- `git_access`: `repos` or `all`.

It holds no secret, no repository, no model, no image, no landing, no name for the session and no timeout. The model stays the profile's default and the launch's field (DL-014).

The name follows a routed credential's rule (DL-072): lowercase letters, digits and `-`, starting with a letter, at most 40 characters, unique per user. `none` is refused, as it is for a credential. A user holds at most 32 templates.

### Checked when written

A write runs each setting through the check a launch request gets (`validateRequest`'s rules for egress, extra domains, variables, add-ons, apt and git access) and answers 422 with the same text. It does so by building a request that holds only what the template sets and checking that (`checkTemplate`), so the deployment's own defaults count: a deployment that boots its own image refuses a template with add-ons at the write. A credential name is checked for its shape only: whether the caller holds it is asked at launch (DL-120), because a credential can be added or removed after the template is written. The listing names, per template, the credentials it lists that the caller does not hold now (`missing_credentials`).

### API

- `GET /api/v1/me/templates`: every template of the caller, by name, each with `missing_credentials` and `updated_at`.
- `GET /api/v1/me/templates/{name}`: one of them, in the same shape; 404 when there is none.
- `PUT /api/v1/me/templates/{name}` with the settings: creates or replaces the whole template.
- `DELETE /api/v1/me/templates/{name}`: succeeds when there is nothing to remove.

### Storage

`store.TemplateStore` (`List`, `Get`, `Put`, `Delete`, keyed by organisation, user and name) with the settings as one JSON document. It is a dependency of its own (`Deps.Templates`), as `Deps.RoutedCredentials` and the image registry are, not part of `store.Store`, so the memory store's index and journal rules do not come into it. Every endpoint answers 501 when it is nil.

- Hosted: a `sandbox_templates` table (`org_id`, `user_id`, `name`, `settings`, timestamps), unique on the three keys, in the clear.
- Local: `templates.json` (versioned, mode `0600`, written atomically) in the local server's state directory beside `routes.json` and `variants.json`, so templates outlive the idle local server. It holds the one local principal's templates, as `routes.json` holds their routes.

A template is never shared: no organisation tier, no admin route, no read of another user's.

## Rationale

A template is the stored form of what a `sandbox:` block in a config file says, kept where both clients can reach it. Leaving a setting out, rather than storing a default, lets a template say only what it is for (a credentials-only template changes nothing else) and lets the server's own defaults keep moving under it. Checking at write with the launch's own rules means a template that saves is one a launch will not refuse for its shape; credentials are the exception because they have a life of their own.

Personal only keeps this out of the admin surface and the tier rules (DL-042, DL-074). An organisation's shared credentials can still be named in a personal template.

## Consequences

- A new dependency with two implementations to keep in step (Postgres and the local file), tested against one shared set of cases.
- A template can go stale: a credential it names is removed, or an add-on stops being offered. The listing shows the first; a launch refuses on either (DL-120).
