## Context

DL-027's export, and DL-102's for a sync job, answer one JSON object carrying the bundle and the working-tree archive in base64. The server reads the exec's whole output, decodes it, encodes it again and sends it, so it holds the export several times over, and the export is capped at 32 MiB to keep that small. A user whose session adds a large file or a generated tree that is not ignored learns about the cap at the worst moment, on exit, after the work is done. DL-175 gives the server a way to pass an exec's output on without holding it.

## Decision

**Routes.** Two new operations stream the export as an archive:

- `POST /api/v1/sessions/{ref}/sync-archive` (`export-session-sync-archive`), with `ExportSync`'s checks: a running single-repository session that is not a job's.
- `POST /api/v1/jobs/{id}/sync-archive` (`export-job-sync-archive`), with `ExportJobSync`'s checks and DL-102's 409s.

They are per-act sandbox reads, as the JSON export routes are (DL-018), registered through huma with a `huma.StreamResponse` and documented as `application/x-tar`. Both join `byRef` in the tenant sweep. DL-133's per-user limits count them as ordinary requests (one in-flight place each for the length of the transfer), not as event streams, so a refusal never speaks of live views.

**The archive.** The answer is `200`, `Content-Type: application/x-tar`, `Cache-Control: no-store`, chunked, never gzipped (the contents already are). It is an uncompressed POSIX tar of regular files, in this order:

1. `spov-sync.json`, at most `git.MaxSyncMetaBytes` (1 MiB): `{"format": 1, "branch", "base_commit", "head_commit", "deleted": [...], "commits", "files", "object_bytes", "worktree_bytes", "bundle": bool, "worktree": bool}`. `object_bytes` and `worktree_bytes` are DL-177's measures, taken before anything is packed.
2. Any number of zero-length `spov-sync-keepalive` entries, written every 10 seconds while the script packs, so that bytes keep flowing through a proxy that times out an idle response.
3. `state.bundle`, when `bundle` is true.
4. `worktree.tar.gz`, when `worktree` is true.
5. `spov-sync-end.json`: `{"bundle_bytes", "worktree_bytes"}`, the packed sizes. Its presence is how the client knows the archive is whole (DL-178).

The bundle and the worktree archive are what the JSON export carries today, unchanged (DL-027's script, the same `base..HEAD` range and `git status --untracked-files=all` selection). The export script gains an `archive` mode beside `export` and `inspect`: it measures, refuses there with nothing on stdout when DL-177's bounds or the metadata bound are exceeded, writes the metadata, then packs each part into its directory and writes it.

**Failure before and after the first byte.**

- The server runs the script with `ExecStream` (DL-175) into a writer that sends the status and headers, and flushes, on its first write, which comes after the measuring (seconds, not the packing). An exec that ends without writing (the script refused, the repository is missing) is answered as `ExportSync` answers a failed export today: a 502 with the redacted detail, which for a refusal is the script's reason.
- Once a byte is sent, any failure (a non-zero exit, more than `MaxSyncExportBytes + MaxSyncMetaBytes + 1 MiB` of stdout, the sandbox gone, the deadline) aborts the response with `panic(http.ErrAbortHandler)`, so the chunked body ends without its terminator (an HTTP/2 stream is reset) and the client sees a broken stream, never an archive that ends cleanly. `internal/server` has no recovering middleware in front of the routes, and none may be added that swallows this panic. The abort is logged with the session and the cause.

**An abandoned export is stopped.** The script works in one directory per sandbox, `/tmp/spov-sync-archive`, with its process group's id in a `pid` file. A new archive run kills the group a previous run left (a client that went away, a retry) and clears the directory before it starts. It runs under `timeout -s TERM` set to the exec's remaining deadline, and removes its directory on exit, on TERM included.

**Time.** The archive's exec runs under `ArchiveTimeout`, 45 minutes: 1 GiB at 4 Mbit/s, the slowest connection the plan serves, is about 36 minutes, plus the packing. The figures DL-175's test measures are recorded there; a slower connection gets the deadline's abort and the retry message (DL-178).

**Behind a proxy.** A hosted server streams this answer for minutes. `deploy/kamal/config/deploy.yml` sets `proxy.buffering.responses: false` and `proxy.response_timeout: 3600`, and `deploy/README.md` says what an ingress in front of spov needs (no response buffering, a read timeout over 10 seconds of idle and a response timeout over `ArchiveTimeout`), with the nginx ingress annotations for the Kubernetes example. A deploy's drain (25 seconds) cuts an archive in flight; the client retries.

**The JSON routes stay.** `POST /sessions/{ref}/sync-export` and `/jobs/{id}/sync-export` keep their shape and their 32 MiB bound (`git.MaxSyncJSONExportBytes`) for clients from before this change, and are marked deprecated in the document. Their over-bound refusal adds that a newer spov syncs up to 1 GiB. A later minor release removes them in a decision of its own.

## Rationale

A tar is the plainest container that streams and names its parts: Python's `tarfile` writes it in stream mode in the sandbox, Go's `archive/tar` reads it on the CLI, and neither needs a framing of spov's own. The metadata goes first so the CLI knows what to expect and every refusal is decided before the first byte; the end entry goes last so a cut-off stream can never look complete. A tar header needs its entry's size, so each part is packed before it is sent, and the keep-alive entries cover that gap.

Measuring before packing means every refusal the script can make reaches the user as an ordinary API error with its reason. Only a failure in transit, which has no better channel once the status is sent, becomes a broken stream.

New routes rather than content negotiation on the old ones keep each operation's response one documented type.

## Consequences

- DL-027's export is no longer bounded by what the server can hold, and the server holds one copy buffer of it at a time.
- The server holds the request's goroutine and its exec for the length of a transfer; the in-flight limit and `ArchiveTimeout` bound how many and how long.
- `measureRequests` records nothing for an aborted archive; the server's log line is its only trace.
- Two operations of the same act exist until the JSON ones are removed; both read the sandbox through the same script.
