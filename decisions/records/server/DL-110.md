## Context

Nothing in spov knows that one OpenCode session is another's child. The recorder (DL-017) keeps one `conversations` row per OpenCode session in the sandbox, and a subagent the agent spawns is just a second row. Every consumer then has to guess which row is "the person's":

- the browser draws every conversation on one timeline (DL-058), so a subagent's task prompt, a `user` item in its own inbox, is drawn as the reader's message and the subagent's replies as the agent's own;
- steering, `attach` and the interrupt resolve an unnamed conversation to the oldest (DL-109, DL-025), which is right only while "oldest by `created_at`" means "the person's". `created_at` is when spov first saw the row, so two conversations first seen in one catch-up batch have no reliable order (DL-025 says so).

OpenCode does record the link. `Session.Info` has an optional `parentID` (the pinned contract's `Session.Info`), and `GET /api/session` already lists children: it takes a `parentID` filter whose `null` value means "roots only", which is what it does *not* do by default. The recorder already stores each listed session's `Info` whole (DL-089), but only the catch-up read supplies it. A conversation first seen through a live frame is upserted with no `Info` (`Recorder.conversation`), so its parent is unknown until the next catch-up.

DL-109 deliberately left parentage as "future work for transcript fidelity". This is that work.

## Decision

### Parent is a column, filled before the child's first frame is stored

`store.Conversation` gains `ParentOpenCodeID` (the parent's `ses_…` id, empty for a root). `UpsertConversation` keeps a non-empty value over an empty one, as it does for `Title` and `Info`. The recorder sets it from the `parentID` of the session's `Info`, in two places:

- `catchUp`, from the listing it already reads;
- `conversationWith`, when a frame names a session it has not stored a row for: it reads that one session (`GET /api/session/{id}`) once, before the row is upserted, so no event of a child is stored while its parentage is unknown. One read per new conversation, never on a timer, and never from a read path, so DL-018's rules for the recorder as the only sandbox reader hold (`TestTheRecorderNeverReadsOnATimer`, `TestNoReadPathTouchesTheSandbox`).

If that read fails, the row is stored with no parent and the next catch-up fills it in. A conversation with no recorded parent is a root; the only cost of a failed read is the pre-DL-110 drawing until the next catch-up.

Parentage is a column and not a parse of `Info` at read time, because list previews (DL-115) and the supervisor (DL-114) must exclude children inside a store query or a cheap set, and `Info` is an opaque blob that only an import reads. The memory store's journal records the new field, so `JournalFormat` is bumped (DL-091, DL-092), and the Postgres store gets a migration adding a nullable `parent_opencode_id`.

### The wire says it

`ConversationView` gains `parent` (the parent's OpenCode id, omitted for a root), beside `id` and `title`. `LogEvent.session` already names the conversation of every frame, so with `parent` a client can classify any message or event without a second request. The generated OpenAPI document and client follow (DL-005).

### An unnamed send goes to the oldest root

DL-109's rule becomes: an unnamed conversation resolves to the oldest conversation *with no parent*, then, when every row has one (or the roots are not yet known), to the oldest. Naming a conversation still names it, and naming a child is allowed by the API but is not offered by any client. This amends DL-109 and DL-025's "oldest" wherever the oldest is used to mean the person's (`steerInto`, `firstConversation`, `jobConversation`, `attach`'s `openingConversation`): they share one helper, `store.Primary(convs)`, so they cannot disagree.

### Resume keeps the link

A transcript resume imports conversations oldest first (DL-089), and OpenCode's import requires a child's parent to exist already. The oldest-first order puts a parent before its children by construction, since a child is created by a running parent, and the stored `Info` carries `parentID`, so the import keeps the link. This is stated here because the import is the one place a child with a missing parent is refused rather than drawn, and the first implementation step checks it against a real import (spike S-SA2, below).

## Rationale

- The parent is the one authoritative signal. Heuristics (the oldest, "created while a tool call was running", "the prompt looks like a task") each fail in a case the plan has already found: simultaneous first sight, background subagents that outlive their call, plugin-created children with no task tool at all.
- A column over a parse keeps every "exclude children" question a plain predicate, and keeps `Info` for the one consumer that needs it whole.
- Fetching at first sight, before the first event is stored, makes parentage a precondition of any child frame being readable, so no reader has a window in which it can mistake a child for a root.
- One helper for "the person's conversation" removes four copies of "the oldest".

## Consequences

- A migration, a store contract addition (`storetest` gets a parentage case for both stores) and a `JournalFormat` bump.
- The recorder makes one extra sandbox read per new conversation. A session that spawns many subagents makes that many reads, bounded by `MaxConversations` (32).
- Until S-SA1 measures it, which frames and fields carry parentage on the live stream is not known; the plan reads `Info` because it is in the pinned OpenAPI contract, and treats any frame field as an optimisation to take only if the spike shows one.
- `GET /api/v1/sessions/{ref}/messages` gains a field. An older client ignores it and keeps today's drawing.

## Measurements still to take

Spike **S-SA1**, local and keyless like the other `SPOV_PROBE` spikes: run the pinned OpenCode with a fake model that calls the `subagent` tool, and record (1) the tool's name and the frames of a call, and whether any carries the child's session id; (2) whether the child's frames arrive on the same event stream with `session` set; (3) whether the child emits `session.execution.*` frames; (4) the `type` of the child's first inbox item (`user` or `synthetic`) and whether it is enqueued in the child's own session; (5) whether `session.created` carries `parentID`; (6) a background subagent that outlives its call. Spike **S-SA2** imports a stored parent and child into a fresh sandbox.
