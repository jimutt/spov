## Context

The long-conversation measurements of 2026-11-05 (DL-070) found two costs outside the browser.

1. **The memory store scanned every row.** Every local server uses it. `PutEvents` checked each new event against every stored event (`eventStored`), and `ListEvents`, `LastEvent`, `FindEvent`, `LastSeqs` and `LastEventExcept` each walked every event of every session; `PutMessages` walked every message for each one it wrote. Recording a long session was quadratic, and the log stream calls `ListEvents` on every store poll. Every transaction also copied the whole conversations, messages and events maps so it could roll back, and the job supervisor opens one on each follow pass whose cursor moved: 43 ms per one-event transaction at 147k events. Seeding a 10k-message session's 147k events had not finished after 120 s, and 74k events had taken over ten minutes, where Postgres took 34 s.
2. **Nothing was compressed.** Opening a 10k-message session downloaded 17.1 MB of messages and 69.0 MB of log.

## Decision

**The memory store keeps three indexes** beside its maps: each session's event IDs in Pos order, the stored OpenCode sequences per conversation, and each message's ID by conversation and OpenCode ID. Writes add to them. The session reads take that session's events: `ListEvents` binary-searches the cursor, and the `Last*` reads walk back from the newest. A transaction's view shares them, as it shares the maps.

**A transaction journals its conversation writes** instead of copying those three maps: each write to a conversation, message or event, and its index entries, records how to undo itself, and a rollback runs the journal newest first. The smaller maps (sessions, jobs and the rest) are still copied. The 147k events now go in in 200 ms, one more event plus a follow read costs 2 µs, and so does a one-event transaction.

**Two reads are gzipped**, a session's transcript (`GET …/sessions/{ref}/messages`) and its log stream (`GET …/sessions/{ref}/log`), when the request accepts gzip with a weight above zero (`withCompression`). The wrapper decides when the handler writes its header or first flushes, and only for a JSON or event-stream body. Its `Flush` flushes the compressor before the connection, so each server-sent event leaves when it is sent. Level 1 (`BestSpeed`); a compressor costs about a megabyte even then, so they are pooled. On the 10k session's payloads at those settings, the transcript goes from 17.1 MB to 7.2 MB and the log from 69.0 MB to 18.7 MB, flushed per event. The browser and the Go client both decompress on their own.

## Rationale

Only those two reads are compressed because of BREACH: a compressed response holding a secret beside text an attacker influences can leak the secret through its size over many requests. Their text is not redacted: it is what the agent and the person wrote, and can hold anything a run printed. They are safe on other terms:

1. They hold no spov credential (no cookie, bearer or CSRF token).
2. Text in them changes only when a run or a person writes it, not on an attacker's request.
3. The browser guard refuses cross-site requests, so a hostile page cannot repeat the request.

Everything else, including the device flow, tokens, credentials and `/connect`, is sent as it is. Compressing in a reverse proxy instead was rejected: a local server has none, and a proxy that buffers to compress would hold the log stream back.

## Consequences

- A new read path on the memory store must use the indexes, or a long session makes it a scan again. A new way of writing a conversation, message or event must update the indexes and journal its undo.
- A new heavy read joins `compressedReads` only on the same three terms.
- `ListMessages` and `LastMessages` still walk every message in the memory store; at 10k messages that is well under a millisecond, so they are left.
- A proxy in front of a hosted server sees `Content-Encoding: gzip` on those two reads and must pass it through, not compress it again.
