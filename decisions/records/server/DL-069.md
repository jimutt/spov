## Context

`Recorder.readMessages` (`internal/server/recorder.go`) read `/api/session/{id}/message` with no `limit`, `order` or `cursor`, although the pinned build's operation takes all three (DL-017, DL-035). The document says only that an omitted limit returns "its default page size".

Spike S-MP1 (`TestIntegrationSMP1MessagePaging`, measured 2026-11-05 against 2.0.22 on this machine with a fake model) filled one conversation with 70 turns, 211 messages:

1. A read with no parameters returns 50 messages, the newest first. So the recorder stored only a conversation's newest 50. A turn end usually overlapped the previous read, but a catch-up after a restart or a late attach, and any turn that produced more than 50 messages, lost everything older for good.
2. `limit` must be 1 to 200; anything else answers 400.
3. Messages are ordered by `time.created`, which OpenCode sets when it receives the message, not by id. A prompt whose id was stamped ten minutes back still sorted as the newest message, so spov's browser-minted ids (DL-059) cannot land in the middle of the list.
4. Following `next` from `order=asc` or `order=desc` returns every message once, in order. The last page still carries a `next`, which leads to an empty page.
5. A cursor keeps the first page's order, and a cursor sent with `order` answers 400 ("Cursor cannot be combined with order"), as does a forged cursor.

## Decision

A read of a conversation asks for `limit=50&order=desc`, then follows `next` with `limit` and `cursor` only. Each page is upserted as it arrives. The read stops at:

1. a page shorter than 50 (the end, since the last page still has a cursor),
2. a page with no `next`,
3. a page that changed nothing in the store: `PutMessages` reports the rows it inserted or actually updated, in both stores (`storetest`), and a page counting none ends the read,
4. a page that is not JSON, with a warning: a page past `MaxSandboxReadBytes` arrives cut short, and older pages would otherwise be lost in silence, or
5. `MaxMessagePages` (200) pages, with a warning. The count comes from the sandbox.

The page size is OpenCode's own default, so no page is larger than the single read was.

The rule is the same for every read. A conversation the store has never held is read back to its first message. A catch-up after a restart or a redial reads what was missed plus one page the store already holds, and so does a turn end. `Final` reads one page per conversation when the live span kept up, so its 10 s budget is not spent on history already stored. The extra page re-stores a message that changed after it was stored, such as a reply read during a catch-up, when later messages pushed it off the first page.

The contract check already covers the parameters: `contract.CheckRequest` matches each query parameter against the document, so a renamed one fails the fakes. It cannot check the range of `limit`, which the document types as a string; the spike does.

## Consequences

- A long conversation is stored whole after a restart, and the verdict's conduct gate (DL-050) and the transcript's recovery from `messages` (DL-048) see all of it.
- A catch-up costs the pages that were missed, not the whole conversation, so a long session's redial does not hold the frame queue (`RecorderBufferBytes`) open while it re-reads its history.
- Newest first means a read cut short by `FinalReadTimeout` or the page bound keeps the end of the conversation.
- A message that changes more than one unchanged page behind the newest message is not stored again. Nothing measured changes a message after its turn ends.
- If OpenCode ever returned a message differently on each read, every page would count as changed and each read would run to the conversation's start or the page bound: slower, never lossy.
- S-MP1 is re-run on an OpenCode bump: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SMP1 -v` (no Modal, no key). It asserts each of the five facts above.
