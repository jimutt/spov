## Context

A hosted server with many users needs limits on what each of them can start. Modal does not provide per-user limits that spov can use, so the server enforces them. The only point that is both cheap and before money is spent is the create call, before anything is provisioned.

## Decision

### The limits

Quotas are checked in session and job creation before `Provider.Create`. Each user has these limits, with these defaults:

| Limit | Default | Notes |
|---|---|---|
| `max_concurrent_sessions` | 3 | starting and running sessions the user owns |
| `max_concurrent_jobs` | 2 | unfinished jobs, counted apart from sessions |
| `max_timeout` | 8 h | hard-capped at 12 h, the sandbox maximum |
| `max_cpu` | 4 | |
| `max_memory_mib` | 16384 | |
| `max_job_duration` | 4 h | the longest wall clock one job may ask for (see DL-049) |

A request above `max_timeout`, `max_cpu` or `max_memory_mib` is refused with 422 that names each limit it exceeds. It is not clamped. A create that would exceed a concurrency limit is refused with 429, because the request is well formed and would succeed for someone else or after a session ends. A job's sandbox timeout is derived from its clock and cut to `max_timeout`, and the job request's own timeout is not used.

The burst ceilings count as well. Modal bills `max(requested, actual)`, so `cpu_limit` and `memory_limit_mib` are compared as `max(request, ceiling)`. Checking only the request would let 1 CPU with a `cpu_limit` of 64 bypass the quota.

Org defaults come from the `quotas` config section, or `SPOV_QUOTAS_*` in the environment (plural, matching the section name that the environment-key derivation reads). A zero field means the built-in default and never "no limit", because an unbounded default is how a hosted server gets a surprise bill. A per-user override is a `quota` JSON column on `users`, which an admin edits with `PATCH /api/v1/users/{id}`. An override replaces any subset of fields, is applied over the defaults, and is capped again at the hard ceiling. `GET /api/v1/me` reports the effective quota as `quota`, which is what the web app's limit meters read (see DL-060). Admins are subject to quotas too, with a higher override if they need one. A quota change takes effect on the next create. A running session is never ended by a quota change, only by the age rule below.

### Counting under concurrency

A transaction alone does not make a concurrency limit a limit. `count(*)` takes no row locks, so under READ COMMITTED every transaction that counts before any of them inserts finds room. `CountLive` therefore takes `pg_advisory_xact_lock(hashtext(org), hashtext(owner))` first when it runs inside a transaction, which serialises one user's creates. The lock releases with the transaction, so there is no unlock to leak on an error path.

Sessions and jobs are separate limits, because a queue of jobs must never lock a person out of their interactive tooling, and a person opening sessions must not stall the queue.

- **Sessions.** The session count is `starting` plus `running` sessions the user owns. It excludes the session of an unfinished job, decided by the job's state and not merely by the existence of a job row. A terminal job stops counting against the job limit, and a session still running under one, such as after a failed terminate that left a billing sandbox, falls back to the session limit, where an unowned live sandbox belongs.
- **Jobs.** The job count takes its own advisory lock, keyed on the owner prefixed with `job:`, so a user's job create and session create do not wait on each other. It counts with `JobState.Counts()`, which includes `queued`, and not `Live()`, which excludes it. Counting with `Live()` would let a caller queue any number of jobs against the limit. `store.JobCounts` is the same set as a list for SQL, and `TestJobCountsAgreesWithTheCountsMethod` keeps the two in step.

Lock mistakes show only against real Postgres, because the memory store serialises on one mutex.

### Attribution

Every sandbox is tagged `user=<user id>` and `org=<org id>`. The keys are bare and not `spov.user`, because `OwnedTags` filters on `user` and `spov`, and renaming them would orphan running sandboxes from `spov ls` and `spov stop`. The user tag is the ULID in hosted mode and `local` in local mode. `BuildTags` takes a `TagSet` struct.

The reconciler uses the tags to return an adopted sandbox to its owner and count it against their quota (see DL-004). It accepts the user tag only when it is a ULID or the local principal. A sandbox carrying an operating-system username would otherwise be adopted under an owner that does not exist and attribute someone else's session. An organisation ID is not a ULID, since a hosted login puts everyone in `default`, so the organisation tag is accepted when it names an organisation this server serves. Applying the ULID check to it would reject every real organisation.

### Cost

Cost is an estimate: the session's resources times its elapsed wall-clock time, summed per user for the calendar month in `GET /api/v1/me/usage` as `running_hours`, `estimated_cost` and `sessions`, with `estimated: true`. The rates are approximate per-CPU-hour and per-GiB-hour figures in `internal/sandbox`. It is labelled estimated, and a floor, wherever it is shown. Actual billing can exceed it, since Modal bills the larger of the request and actual use. There is no billing sidecar, no separate environment per tenant and no hard spend cap.

### The age backstop

The reconciler's leader terminates any spov sandbox older than the organisation's `max_timeout` plus one hour, whatever the store says (see DL-004). Modal's own sandbox timeout is the last resort.

## Rationale

- Enforcing at create is the only point that is both cheap and before money is spent.
- Refusing and not clamping tells the person which limit they hit.
- Separate session and job limits stop the two kinds of use from starving each other.
- A ULID tag survives a change of username and is the one stable key for attribution across the users table and Modal's listing.

## Measurements

Without the advisory lock, eight concurrent creates all passed a limit of one (PostgreSQL 18, READ COMMITTED). The integration tests hold every racer open past its count to force that interleaving, since it is otherwise rare enough to pass by luck. Re-run:

```sh
export SPOV_TEST_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:5433/spov?sslmode=disable
go test -tags integration ./internal/store/postgres/ -run Quota
```

`TestConcurrencyQuotaIsALimitNotASuggestion`, `TestJobConcurrencyQuotaIsALimitNotASuggestion` and `TestJobAndSessionQuotasDoNotSerialiseOnEachOther` cover the session lock, the job lock and the fact that the two do not collide. The unit tests are `TestQuotaBoundsTheBurstCeilings`, `TestConcurrencyQuotaCountsOnlyLiveSessions` and `TestLaunchTagsTheOwnerAndOrg`.

## Consequences

- Actual Modal billing can exceed the estimate, and the label says so.
- A running session outlives a lowered quota until the age rule ends it.
- A new count that depends on job or session state must use the same predicates as the quota, or the limits and the meters disagree.
