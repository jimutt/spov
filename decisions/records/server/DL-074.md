## Context

An organisation's private registry usually has one shared read token, which every member's sessions should get without each member storing it. DL-042 already gives the organisation a tier of its own for the GitHub App, stored by an admin in `org_credentials`. Routed credentials (DL-072) need the same tier.

## Decision

- An organisation's routed credentials are an admin's to define. They live in `org_credentials` under the key `route:<name>`, with the route in the clear in the row's `meta` column, which already holds what may be shown about an organisation credential, and the secret sealed under `auth.OrgCredentialAAD` followed by the route's canonical encoding (`routedcred.AAD`, DL-073; `SealedOrgRoutedCredentials`). A user's row can never be opened as the organisation's or the reverse, and a changed route does not open. `OrgCredentialStore.List` reads them.
- The admin API is `GET /api/v1/org/routed-credentials`, `PUT /api/v1/org/routed-credentials/{name}` with `{secret, route}`, and `DELETE /api/v1/org/routed-credentials/{name}`. A write takes the organisation's admin lock and re-checks admin (`requireLiveAdmin`), then writes the row and an `admin_events` row (`routed_credential.stored`, `routed_credential.removed`, with the name and the route, never the secret) in one transaction, as the GitHub App's routes do.
- `spov credentials add <name> --org` stores one through that API, and `spov credentials remove <name> --org` removes one. Both are refused locally, before the secret is read: a local server has no organisation tier, and a local user's own credentials already reach every local session. A hosted listing ends with the organisation's routed credentials, and `--json` adds `org_routed_credentials`.
- Settings shows the organisation's routed credentials to every member (name and route, under the member's own), and an admin also gets Delete. A member sees which shared credentials their sessions get without seeing a secret. The read is `GET /api/v1/org/routed-credentials`, open to every member; the writes need an admin, 403 otherwise, and every endpoint answers 501 where there is no organisation tier.
- An organisation holds at most 64 routed credentials.
- There is no environment form. An operator who wants a shared credential at deployment stores it through the admin API once.
- When a member's own routed credential and an organisation's route a common host, the member's wins for that session, as a personal forge credential does (DL-042's personal-first order). Resolution is DL-075.

## Rationale

The organisation tier is the common case for a private registry: one read token, minted once by whoever administers the registry. Defining it per member would push every member to copy one secret by hand. An admin's write is audited as the App's is, because an organisation credential reaches every member's sandbox.

No environment form, because a route is data an admin edits, and an environment form would need a restart and a parser for a list of structured values. The App has one because a deployment may need it before anyone can sign in.

## Consequences

- Removing an organisation credential takes it out of every later launch at once. A running session keeps what its sidecar holds until it ends, as it does for any credential.
- Tests: `TestAnAdminStoresAnOrgRoutedCredentialAndItIsAudited`, `TestAMemberCannotStoreAnOrgRoutedCredential`, `TestAnOrgRoutedCredentialOpensOnlyAsTheOrganisations`, `TestALaunchAttachesTheOrganisationsRoutedCredential`, `TestAnOrgRoutedCredentialNeedsAHostedServer`, and the store conformance case for `List`.
