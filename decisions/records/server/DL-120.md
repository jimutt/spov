## Context

DL-119 defines a sandbox template. This record says what a launch does with one.

## Decision

### The field

`SessionRequest` and `JobRequest` gain `template`, a template's name. The server reads the caller's template at create. A name the caller does not hold is a 422 before any row exists. A launch with no `template` is exactly today's.

### Order

For each setting a template can hold, the launch's value is the first of:

1. the request's own field, when it is set;
2. the template's, when the template holds that setting;
3. what applied before this record: a saved preference the CLI sent, the profile's default, the server's default.

In detail:

- **Egress.** The request's `egress` replaces the template's preset and its extra domains together. A request that sends only `egress_extra_domains` adds them to the template's preset in place of the template's own list.
- **Add-ons and apt.** A list in the request replaces the template's list, as a later config layer replaces an earlier one (DL-026). The server's own `sandbox.addons` and `sandbox.apt` stay the base under either.
- **Variables.** They merge by name: the server's own `sandbox.env`, then the template's, then the request's (this adds a layer to DL-096's order). The merged set is checked as a request's is.
- **Git access.** A template's `git_access` ranks above a saved preference (`git_access_preferred`) and the profile's default, and is itself treated as a preference: where `all` is not allowed on the deployment's credential (DL-043's `mayReachAll`), the launch falls back to `repos` and says so. Only the request's own `git_access` is refused there. This adds a rung to DL-043's order.
- **Routed credentials.** A template's `credentials` list is the launch's own list in DL-075's step 1: exactly those, `asked` ones included; `no_credentials` attaches none. The request's own `credentials` or `no_credentials` replaces it. The configuration's narrowing (`credentials_preferred`, DL-075's step 3) is then applied to a template's list as well, keeping only the names in both, so a project file can still only take access away. A template that leaves credentials out leaves DL-075 as it was.

### Refusals

A template's setting that can no longer be met refuses the launch with a 422 that names the template and the setting: a credential the caller does not hold, an add-on no longer offered, a variable the rules now refuse. It is never dropped silently, because the person chose the template for what it attaches.

Everything a launch already refuses still applies to the resolved request: add-ons on an image spov did not build, routed credentials without the proxy (DL-077), two attached credentials on one host (DL-075).

### Recorded

The resolved settings are written into the session's stored request as if the launch had sent them, with the template's name beside them (`store.SessionRequest.Template`, `SessionView.template`). Nothing later reads the template again: a resume, a recreated sidecar and a job's provisioning use the stored request. Editing or deleting a template changes no existing session.

The launch's progress names the template once, with what it set.

### Jobs

A job takes a template the same way, through `jobSessionRequest`. A template's `git_access` applies to a job that names the template; a job still never takes the interactive profile default. A `sync` job may name one.

## Rationale

"The request's field wins" is one rule the server can apply without knowing which client sent the request. Treating a template's credential list as the launch's own list is the point of the feature: a credential marked `asked` is attached only where a template (or a flag) names it, which is how a person keeps a credential out of their other projects.

Git access from a template is a preference because the template is written once and used on launches whose credential tier differs; refusing a launch for a setting written weeks ago would be a surprise, and falling back to the narrower access is safe.

Recording the resolved values, not a reference, keeps a session reproducible and keeps resume (DL-087) and sidecar recreation (DL-034) away from a store read that could now answer differently.

## Consequences

- A request field that is set always wins, so a client must send a covered field only when its user set it. The browser already does. The CLI must not send built-in defaults for the covered fields when a template is named (DL-122).
- Removing a routed credential can break launches from a template that lists it. The refusal says which.

## Implementation notes

- Resolve in one function (`applyTemplate`) called by `CreateSession` and `jobSessionRequest` before `validateRequest`, so the resolved request is checked once, as a whole.
- Tests: each setting's order (request over template over preference and default); variables merge by name; a template's list attaches an `asked` credential and a narrowing still removes one; `all` from a template falls back with a note where a request's is refused; a missing credential refuses and names the template; a resume after the template was deleted launches with the recorded settings; the session view carries the template's name.
