## Context

A transcript that lives only in the sandbox is only as durable as the sandbox: a terminated or timed-out session keeps its row in the store and loses its conversation. Everything the control plane shows about a session's conversation therefore comes from rows spov wrote while the session ran.

Reading a sandbox has a price. A plain HTTP request to a sandbox resets Modal's idle clock and a held-open stream does not (DL-018), so anything that polls a sandbox keeps it billing. A recorder has to be reading whenever a session runs, whether or not anyone is watching, and still must not read on a timer.

OpenCode's event stream (`/api/event`) is volatile: it replays nothing, so a frame sent while nothing listens is gone for good. Its messages (`/api/session/{id}/message`) can be read whole at any time. Frames that belong to OpenCode's durable log carry `durable: {aggregateID, seq, version}`, where `aggregateID` is the OpenCode session (`ses_…`) and `seq` is its position in that session's log. A durable log starts at sequence 1 per aggregate. A message carries `id` (`msg_…`), `type` (`user` or `assistant`) and `time.created` in epoch milliseconds. The experimental durable-log endpoint (`/api/experimental/session/:id/log`) is a watermark oracle, so the conversation is captured from the volatile stream and reconciled from `/message`.

## Decision

### Rows in the store

An OpenCode session inside a sandbox is a conversation, what it holds is messages, and what happened around them is events. `Store.Conversations()` returns a `ConversationStore`. A sandbox may hold several conversations.

- `Conversation`: spov's id, org, session, OpenCode's id (`ses_…`), a title and times. `UpsertConversation` keys on (session, OpenCode id) and keeps the existing id and creation time. A conversation first seen in a frame is upserted with an empty title, which the next `/message` read fills.
- `Message`: OpenCode's id (`msg_…`), role, the text with reasoning parts dropped, the time OpenCode gave it, and the message as received (`Raw`), which the verdict's conduct gate reads for tool parts (DL-050). The raw form never goes over the API: it is untrusted sandbox JSON and `MessageView` carries what the browser needs.
- `Event`: a `Source`, a `Seq`, a `Pos`, a name, text, a time and the raw frame. The sources are `opencode` (a durable frame, `Seq` is the durable sequence), `spov` (a marker the recorder or the supervisor writes: no conversation, no sequence) and `ephemeral` (below). A name in `spov.` may only be carried by a spov event, so a page can draw such a row as spov's voice and a sandbox cannot claim it (`ErrInvalidEvent`).
- The interface also has the reads the other components need: `LastMessages` (the list page's last message per session in one query), `LastEvent` and `LastEventExcept`, `FindEvent`, and `LastSeqs` (below).

Writes are idempotent by structure, so the recorder need not remember what it wrote. Conversations are unique on (session, OpenCode id), messages on (conversation, OpenCode id), and events carry a partial unique index on (conversation, seq) where the source is `opencode`. A recorder that attaches twice, a `/message` read repeated after a break and a frame delivered again each write the same rows once. The ephemeral source has a nullable `seq`: NULLs are distinct in a unique index, so seq-less rows are neither deduplicated against each other nor against the durable log, and a spov marker is stored with a NULL sequence too.

Every row carries `org_id` and `session_id`, with composite foreign keys (a conversation to its session, a message or event to its conversation, all on delete cascade), so a row cannot disagree with its parent and be listed under the wrong session. A null conversation id (a spov marker) satisfies the key. A batch lands whole or not at all: Postgres writes it in one transaction, and the memory store checks every row before writing any. An event with a zero time, or an OpenCode event without a conversation or sequence, is refused with `ErrInvalidEvent` by both stores. The shared `storetest` suite runs both implementations.

`Pos` is assigned by the store and strictly increases, so a reader holds it as a cursor (`ListEvents(after)`). ULIDs are not monotonic within a millisecond, so a tail that resumed by id could skip a row. `Pos` is a valid cursor only with one writer per session, which the recorder is: Postgres assigns identity values at insert and does not roll them back, so two transactions writing one session could commit out of order and a reader past the higher position would miss the lower. The memory store cannot reproduce that, so no contract test guards it and the recorder's design is the guard.

The raw frame is kept (one frame is bounded by `MaxLogFrameBytes`, 1 MiB) so a projection fixed later re-projects without a sandbox. Several OpenCode shapes on this path are inferred rather than documented, and two inferred ones have proved wrong. Not stored: reasoning parts, ephemeral frames other than those named below (deltas and status would fill the busiest table), and anything of spov's own credentials. The conversation is the owner's content, readable by whoever may read the session; `Service.Get`'s access check is the only gate.

### Ephemeral frames kept by name

Frames without a `durable` marker are not stored, except five kept under `SourceEphemeral`, matched by exact name (`ephemeralNames`): `permission.asked`, `permission.replied`, `form.created`, `form.replied` and `form.cancelled`. They tell the supervisor a job is parked and answered, and the page derives a pending ask from them (DL-020). They are matched by exact name, never by suffix, because the sandbox chooses names and a suffix rule would let a frame it invents drive a job's state machine. An ephemeral event needs a conversation and no sequence.

### One recorder, run where the reconciler runs

There is one `Recorder` per process. It is started by the same leader runner as the reconciler, so under Postgres exactly one replica records and in local mode the one process does. Its state is one goroutine per running session, rebuildable from the store and the sandbox; nothing in it is authoritative. It acts as the principal `auth.Recorder(orgID)` (`UserID` `auth.RecorderID`, admin), so `Connect` records its mints under that id, and it goes through `Service.Get` and the mint transaction like a person. A span uses a cached server-side connection when there is one (`connectReusing`), so a redial usually costs no mint. One mint per span serves the stream and every read of that span, so a catch-up over several conversations is several reads and no further mints. Mints count against `MintsPerMinute` (10) per session, a budget `spov attach` shares.

`Run` syncs on start and every `ReconcileInterval` (30 s, plus up to a fifth in jitter): it starts a capture for every running session with a sandbox that nothing is recording, and cancels captures of sessions that have left `running`.

A nudge starts a capture sooner, and the poll stays as the backstop. `Recorder.Wake(session)` starts a capture for one session at once if nothing records it. It is wired in two places:

- The supervisor calls it when it opens a job, before the goal goes out (`Supervisor.Wake`). A job posts its goal about `FollowInterval` (10 s) after provisioning, so without the nudge the recorder attaches between 0 and about 36 s after the agent starts and, on a short job, after the run is over.
- `Service.OnStart` is wired to it. A launch calls it where it commits `running` with a sandbox id, not where the sandbox becomes reachable: `Sync` skips a session that is not both, so an earlier nudge would find nothing to attach to, and a launch cancelled while starting never nudges. It is also called after each act that writes into a running session (a steering message, an interrupt, a model switch, an answered ask, a cancelled message), so a session that is not yet recorded is picked up at once (`Wake` returns early on a session it already holds).

`Wake` is safe for a session already recorded, does not block (the capture dials on its own goroutine) and does nothing before `Run` has started. A nil `Wake` or `OnStart` is a working configuration (local mode, tests). The nudge is an optimisation, never the mechanism: the poll still finds an interactive session no supervisor opens, a replica that did not run the launch (captures are per process), and a nudge lost to a restart or a failed capture. The poll must not be weakened on the strength of the nudges. `TestServeWiresTheRecorderToTheService` finds every exported `On*` function field on `Service` by reflection and fails until `serve.go` sets it, since an unwired seam compiles, passes every unit test and never fires.

### A capture reads the sandbox only when the sandbox did something

Every request the recorder makes is caused by an event in the sandbox or by its own attach, never by the clock (`TestTheRecorderNeverReadsOnATimer` counts every mint, dial and read through an attach, a hundred frames, a turn end, a quiet spell and a break). A span is one attach and its stream:

1. **Attach.** Record `t0`, the time the stream opens. Dial `/api/event` and buffer its frames in a queue. Then read the last stored durable sequence of each of the session's conversations (`LastSeqs`), read `/api/session`, read `/message` of every conversation once (the catch-up, at most `MaxConversations`, 32) and upsert. Then drain the buffer. Opening the stream before the read makes the seam between them empty. A conversation that cannot be read is skipped with a warning; a store write failure ends the span.
2. **Streaming.** A durable frame becomes a row keyed on `durable.seq`, dated by the frame's own `created` (the recorder's clock as the fallback), with the raw JSON kept. A durable frame without a sequence cannot be keyed and is dropped, with one warning per span. A frame claiming a name in spov's namespace is dropped with one warning. A message comes only from `/message`, keyed on its id; one without an id is skipped.
3. **A turn ends.** On `session.execution.succeeded`, `.failed` or `.interrupted`, that conversation's `/message` is read once and upserted. A turn is caused by a person or a job, so this read is one the sandbox's user already paid for in activity. It is the one place the design leans on an event name; if OpenCode renames them, messages fall back to the catch-up on a break and a delete only, and `events` still holds everything. `TestRealFramesBecomeRows` and the captured-frame tests are where a rename would show.
4. **A break.** When the stream ends, the recorder re-reads the session row. If the session has left `running`, the capture ends and writes nothing: the stream ended because the session did, which is not a gap. If it still runs (or the row cannot be read, which counts as a break so a flapping store does not restart captures with a fresh budget every 30 s), the recorder redials after 5, 10, 20, 40 and 80 s (`RecorderBackoff`): `RecorderRedials` = 5 redials in total over the session's life while this process leads. After the fifth it writes `spov.recorder.stopped` with the last error and stops (`TestABreakIsBoundedAndMarked`). The bound is deliberate: an unbounded redial against a dead event endpoint with a live process would be a heartbeat nobody owns, and a redial is a plain request. The budget is per session life, not per break; a new leader term starts the count afresh, which is the escape hatch. A successful redial re-runs the attach, judged like any other.
5. **A failed write** (`PutEvents` or `PutMessages`) is a break: it is logged, the capture ends as if the stream broke, and the next sync restarts it. A recorder that reads while it cannot write reads for nobody.
6. **Bounded memory.** Frames queue in memory during the catch-up up to `RecorderBufferBytes` (64 MiB); past it the span ends as a break and the redial's catch-up recovers the messages.
7. **Stop.** The session leaving `running` cancels the capture and reads nothing. `Service.Delete` reads `/message` once before it terminates the sandbox, as the deleting principal and best-effort (bounded by `FinalReadTimeout`, 10 s), through `Service.OnStop`, which is wired to `Recorder.Final`; so an explicit stop closes with the last word recorded. A job's delivery calls the same read once more so the verdict covers the final turn. An idle timeout closes with whatever the stream carried. Shutdown, within the server's shutdown budget, cancels every capture, and the next leader attaches within its first sync.

### The gap marker

The recorder decides whether anything was missed from the sandbox's own durable sequence, against where the store's recording of each conversation stopped. No query against the store alone can answer it, since a session the recorder reached at open time and one already half over look alike from the store.

- At attach the recorder reads `LastSeqs` and writes no marker. `LastSeqs` is one query per attach, an index probe per conversation on `events_opencode_seq`.
- The first durable frame of each conversation in the span decides. A frame at `seq > last + 1` means `seq - last - 1` frames were missed. The recorder writes `spov.recorder.gap` ("recording resumed; what happened before this was not captured") naming the count ("58 earlier events", "1 earlier event"), at most once per span. A frame at `seq <= last + 1` is contiguous and marks nothing.
- A conversation with nothing stored has `last = 0`: a first frame above 1 is a gap. That covers a first attach, a span whose first write failed, and a conversation created while nobody listened. A first attach, a redial and a restart are one rule. A spov row such as a steering marker has no durable sequence and cannot move where a conversation's recording stopped.
- The marker is stamped with `t0` (`markAt`), not the write time (`mark` stamps `now`). On a fresh session the decision waits for the first durable frame, possibly minutes after the attach, and the page orders by time before sequence, so a write-time stamp would sort "recording resumed" below content the span did record. A later tidy-up that replaced `markAt` with `mark` would misplace the marker silently. Catch-up messages carry the sandbox's own time, older than the attach either way, so they sort above the marker regardless. `t0` is spov's clock while neighbouring frames carry the sandbox's, so clock skew can misplace the marker by about a second.
- `gapCheck` marks a conversation as checked before it judges the sequence; otherwise a log that starts at 1 would be checked again on its second frame, and that frame reads as a gap. Only a durable frame reaches the check: an ephemeral frame is forced to sequence 0 and would use up the conversation's one check. The marker belongs to the session and carries no conversation id, so on a multi-conversation session a count measured on one conversation is shown against the whole session.
- Why the sequence and not the store: a conversation row proves a conversation was created, not that anything was missed. On a job the recorder wins the race with the supervisor, so the row is absent and no marker is written. On an interactive session the recorder is the only writer, so a row-based rule can never fire. A marker after every restart on sessions that lost nothing would teach readers to ignore the one note that says a transcript is incomplete.

Guards: `TestASpanThatBeginsMidLogMarksAGap`, `TestASpanThatBeginsAtTheStartOfTheLogMarksNoGap`, `TestTheGapMarkerIsStampedAtTheAttachTime`, `TestASpanThatSkipsPastTheStoredLogMarksAGap`, `TestASpanThatContinuesTheStoredLogMarksNoGap`, `TestANewConversationAfterARestartIsJudgedFromItsStart`.

## Rationale

Event-caused reads are the only honest way to read a sandbox nobody is watching. A poll, however slow, is a timer, and a timer is what keeps a sandbox billing. A read on attach, on a turn end and on a break has a cause the sandbox's owner can point to.

Idempotent rows let every step be naive: catch up again, write the frame again, redial and catch up again. Correctness lives in the unique indexes, not in the recorder's memory. A partial unique index lets spov's markers share the table and the cursor with the events they interrupt without inventing a sequence for them. Keying on OpenCode's ids instead of text makes the browser's text de-duplication a client concern only.

Giving up after five redials is the one place the recorder chooses cost over completeness, and it says so in the store: `spov.recorder.stopped` is a visible fact on the page, not a silent gap. A per-break budget would be kinder to a flaky-but-alive sandbox and would also let one keep a recorder dialling indefinitely; the bound is the point.

Running under the existing leader couples the recorder to the reconciler on purpose: the reconciler is what knows a session is running, and its 30 s tick is the resolution at which spov knows anything about a sandbox. Polling faster was rejected: a `ListLive` query per replica per interval forever, for a race that matters only in the seconds after a session opens. Attaching before anything can produce output would close the opening gap, but it puts recorder lifecycle inside the launch and run loops, which the reconciler owns, so the nudges stand in for it.

The gap rule measures the loss instead of inferring it. The durable sequence is the sandbox's own account of its log position, and the decision needs no comparison between the sandbox's clock and the control plane's, and no correlation of message ids across two inferred shapes.

## Measurements

- Frame shapes, measured 2026-09-01 and held verbatim in `TestProjectionAgainstRealSandboxFrames` and `TestMessagesFromRealSandboxShapes`: a durable event carries `durable: {aggregateID, seq, version}`; a message carries `id`, `type` and `time.created`. The durable-log endpoint re-test: `go test -tags integration ./internal/sandbox/ -run DurableSessionLog` (`TestIntegrationDurableSessionLog`), which found `/api/experimental/session/:id/log` still a watermark oracle.
- Redial schedule: 5, 10, 20, 40 and 80 s, five redials over 155 s. The first three fall inside the first minute after a break, so with the initial dial that is four mints against a budget of ten per session per minute shared with attach. Steering may not spend the last three of the ten (`RecordingMintReserve`), the recorder's worst case in one minute.
- Catch-up buffer: `RecorderBufferBytes` = 64 MiB. What a sandbox does when its event writer blocks, stalling the socket, was never measured.
- The opening gap on a job (measured 2026-09-04, without the nudges): the goal was posted at 18:43:04, the agent finished at 18:43:15 and the recorder attached at 18:43:20, five seconds after the last thing it could have recorded. That session stored two events, both spov markers, against 70 or more where the recorder attached first. The page showed nothing, then "recording resumed" as its first row, then everything at job end; nothing was lost because the catch-up reads `/message`.
- The opening gap on an interactive session (measured 2026-09-05, without the launch nudge): the session lived 44 s, created 13:25:54; the recorder's one event was recorded at 13:26:34 (about 40 s in), and the session stopped at 13:26:38. Everything the person did had happened before anything listened, while the transcript appeared on reload because `/messages` read the sandbox's own message store.
- Why a row-based condition fails (2026-09-04, on a deployment): an interactive session's first recorded frame carried durable sequence 59, contiguous to 140 thereafter. 58 events were lost and no marker was written.
- The gap rule across restarts (a hosted-mode server and real sandboxes, 2026-11-02): a job restarted while one command slept for 150 s logged sequences 1 to 39 with no hole, got no marker and no supervisor warning. A job restarted during one shell command (durable log 1 to 67, no hole) still printed "recording resumed; what happened before this was not captured" in the middle of a whole transcript when every restart marked unconditionally: a false positive once per restart per live session, which the sequence rule removes. A job restarted twice while working got two markers, "42 earlier events" and "32 earlier events", matching its two holes (sequences 19 to 60 and 101 to 132) exactly.

## Consequences

- The transcript outlives the sandbox. The session page reads the store, not the sandbox (DL-018).
- Growth is unbounded for now: sessions are stopped, never deleted, so nothing cascades. The raw column is the one to trim first. `LastMessages` is called every 2 s per open list, so its `(session_id, at desc)` index is required.
- Under the memory store, a `spov serve --local` that exits takes its conversations with it.
- A leader failover costs one gap marker and one catch-up per running session, when frames were missed. Events during the failover window are lost for good because the volatile stream replays nothing; messages are not, because the catch-up reads them.
- A short job can still finish before the capture is fully attached: the opening gap shrinks with the nudges and does not close, and the catch-up is why nothing in the transcript is lost.
- The recorder's mints share attach's budget; five redials over 155 s are well inside it.
- A field the UI wants goes on the API view (`MessageView`, `LogEvent`), not the store type; the projection between them belongs to `internal/server`.

## Known gaps

- Between a turn's `text.ended` and its `execution.succeeded`, the store holds the words as an event and not yet as a message. Writing a provisional message row would need the message id from the frame, which has not been measured to be there. A client that merges by text shows the words once either way.
- A span that receives no further durable frame in a conversation marks nothing for it, so frames missed at the very end of a conversation that never speaks again go unmarked; the catch-up still restores its messages. A span that receives no durable frame at all writes no marker.
- An ephemeral frame missed while a conversation's durable log is quiet, a pending ask in particular, is neither restored by the catch-up (messages only) nor marked until the next durable frame. A job whose permission request fell in a restart's downtime reads `running` with no ask card and no note; closing that needs a signal from the sandbox.
- The rule assumes a durable log starts at 1 per aggregate. A shape where an aggregate legitimately begins above 1 is untested and would read as a false gap.
- Once a recorder abandons a session after its redial budget, the session stays unrecorded until the next leader term.
