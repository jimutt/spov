## Context

A session's model decides the quality and cost of everything it does. For an interactive session a person can change it in the terminal UI. A job runs unattended, so whoever asked for it needs a way in, and the web form needs something to send.

Leaving the choice to whatever the sandbox picks is not safe. A job launched with no model ran on a small extraction model that cannot call tools, and failed its first step with "No endpoints found that support tool use". An unattended job's whole value is tool calls. The model was listed by models.dev, by OpenCode's mirror of it and by OpenRouter, so no catalogue would have kept it out. How OpenCode picked it was not determined: the two entries of that model were the only catalogue additions dated that day and the only ones that could not call tools, which fits a recency rule but does not establish one. The decisions below do not depend on which rule it was. They do mean that spov pins the model it runs unattended work on, instead of leaving it to the sandbox. spov already pins a model deliberately for its own one outbound call (the prep ladder), so leaving the expensive unattended run to the sandbox was the odd one out.

What is chosen has to be checked (DL-013) and has to be the same on the job's row as in the sandbox, or a verdict cannot be compared across runs.

## Decision

### One optional string, carried from the request to the sandbox

A model is one optional string, `provider/model[#variant]`, which is OpenCode's own identifier; spov has no naming scheme of its own, and OpenCode is what resolves the string. Empty means OpenCode's default and stays reachable as the last rung of the resolution below.

- It is `Model` on `store.SessionRequest`, `JobRequest` and `session.Options`, `omitempty` in the API, so an omitted model changes nothing for an existing client. `session.Options` is built at one site, `Service.launch`, which the interactive and the job path both reach. `spov fly --model` and `spov jobs create --model` are ordinary API clients and build no `Options`.
- A session's model is not a column. It rides in the request, which is persisted whole as JSON (`TestSessionJSONEncodesTheWholeRequest` guards a new request field persisting). A job's model is `jobs.model` (migration 16, on the `jobs` table alone, defaulting to empty so every existing row keeps its meaning): a redelivery on another replica reads it, a cost view can group by it, and it must be true of what ran. A `model` column on sessions would be a second copy of a fact the request already holds. A job's model is copied onto its session's request at create, as the goal is.
- In the sandbox, `model` is a top-level key of OpenCode's config, written for both kinds of session (DL-038), which takes the string and parses it itself. A model the list lacks is also declared there.
- A job's conversation also has its model set, with `POST /api/session/{id}/model` right after the conversation is created (`setConversationModel`, from `jobConversation`). The call exists because a repository's own `opencode.json`, found by walking up from the conversation's directory, outranks the global config file, and the job's row must be true of what ran. Every session lands at `/workspace` unless a launch names `--landing <repo>`, so a repository's config is on that walk only with a landing. The call is one write per job, on a path that already writes, and it is the call OpenCode's own non-interactive runner makes for `--model`. The server makes the same call when a session's first message opens its first conversation (`firstConversation`). An interactive session otherwise gets the config alone: a repository or the person may override it, and only a job pins its model.
- That endpoint takes an object, `{id, providerID, variant?}` (the field is `id`, not `modelID`), and answers 400 for a string. `modelRef` builds the object from the string. A failure to set the model only warns, so a wrong shape would 400 on every job while the row claimed a model that never applied.

### The user's default lives on the profile

`store.User.DefaultModel` is set through `PATCH /api/v1/me` as `default_model`, beside `git_name` and `git_email`, and reported on `MeView`. It is per user. It rides on the profile row (migration 17), not in a settings table, because the row already holds the git identity and a quota override and a second mechanism for the same kind of fact is one more thing to read and migrate. A `*string` body field distinguishes "not mentioned" from "set to empty"; empty clears the default and is how a user returns to OpenCode's own.

- `PATCH /me` creates the caller's profile row when there is none. In local mode the principal (`auth.Local()`, user id `local`) never has a row, because only the web login path creates one; without this the Settings page saves nothing there (the git identity needs the same). Two first saves racing both see no row and the loser's create conflicts. The loser re-reads and applies its change again to the row it finds, instead of writing the struct it built, which carries only its own fields and would drop the winner's. `apply` is therefore a function over a `store.User`, and it is applied twice on that path (`TestAFirstSaveThatLosesTheRaceDoesNotClobberTheWinner`). The other guards are `TestADefaultModelIsStoredAndReported`, `TestPatchMeCreatesTheProfileWhenThereIsNone` and `TestClearingTheDefaultRestoresOpenCodesOwn`.
- The created row copies the principal's `Admin` flag, and that grants nothing: both hosted authenticators require an existing user row, so the branch is reachable only by a principal built without one, which is local mode's, and a hosted account is an admin through the allowlist.
- The default is checked when it is stored, with the same `checkModel` a launch uses (so `keyAdvice`, including the local-mode restart sentence, is unchanged on all three paths: session create, job create and settings save; a default naming a provider whose key the daemon has not loaded is unusable for exactly that reason), against the catalogue and the caller's own keys, so storing and launching cannot disagree about what is usable (`TestAnUnusableDefaultIsRefusedWhereItIsChosen`). A setting that cannot work is refused in front of the person choosing it. The launch checks the stored value again, because a key can be removed and a model can leave the list afterwards. A stored default may be a custom name the list lacks, and Settings saves it with the same note a launch gives (DL-013).
- On Postgres the setting is more than a migration: `UpdateUser` is a hand-written query feeding sqlc, so the query, the generated code and the row conversion in `accounts.go` move together. The memory store stores the struct and needs nothing. A column added to the table and to `CreateUser` but missed in `UpdateUser` would revert on the next save, and no unit test sees it. The guard is the store suite's "a user default model is stored and read back", which runs on the memory store and, under the integration tag, on Postgres.

### Resolution happens once, before anything is written

`resolveModel(requested, profile)` picks the model in `Service.Create` and `Service.CreateJob`: the request wins, then the stored default, then OpenCode's own. It is pure (it takes the profile, not a context), trims both rungs because the profile is read straight from a row, and sits beside `checkModel`.

- Resolution runs before the check, and the check validates whatever was resolved. What skips the check is an empty resolved model (no default and none named), not an empty request. The row is written after resolution, so the stored request and the job row name the model that ran. It cannot move to the supervisor.
- Once a default is set, OpenCode's own is reachable only by clearing it. There is no sentinel value: "let the sandbox pick" is what ran the tool-less job, and a magic string in a model field is a parsing trap.
- A caller with no profile row has no default, silently, because a local-mode token legitimately has none (a warning per launch would be noise, and treating the miss as an error would fail every local launch).
- The profile is read once per create. `profileFor` reads the row, and each create passes it to `resolveModel` and to `quotaOf`. `quotaFor`, which reads the same row, has no production caller; its comment names the pair to use instead (`TestTheProfileIsReadOncePerCreate`).
- Resolution is server-side for both kinds of launch, so every client gets it. The tests are `TestALaunchWithNoModelRunsOnTheStoredDefault`, `TestTheRequestBeatsTheStoredDefault`, `TestACallerWithNoProfileLaunchesOnOpenCodesOwn` and `TestAStoredDefaultIsTrimmedBeforeItIsUsed`.
- A running session is unaffected by a later change of the default.

A refusal says which rung supplied the model. `refuseModel(src, model, reason)` wraps the check's reason in one of three sentences chosen by a `modelSource`: the model this launch named, the caller's stored default ("is your default model and cannot be run", which points to Settings and to `--model`), and a default being saved ("cannot be your default model"). The reason itself is unchanged, so a catalogue refusal still never says "key" and "no such model" and "no key" keep separate wording. The fix for a stale default is on a web page (the default is set only in Settings, not from the CLI), so the message has to say both where the value came from and where to change it. A stale default is refused on every launch, including a launch that named no model, and not silently dropped or dropped with a warning (`TestAStaleDefaultIsRefusedAndSaysWhereItCameFrom`).

`checkModel` bounds the model to `MaxModelBytes` (256), not `validateRequest`, which sees only the request and never a profile-supplied value. That also bounds the job create. The over-long refusal is the only one that does not name the reference, because quoting a value to say it is too long is the failure it exists to prevent. `modelNoun` names the rung without the value (`TestAnOverLongModelIsRefusedWithoutBeingEchoed`).

### Three parsers of one reference

`prep.LookupModel`, `modelRef` and `withoutVariant` in `web/src/lib/jobform.ts` all parse `provider/model[#variant]`: the first `/` ends the provider, the first `#` starts the variant, and an empty half is not a reference. The first two are tested against each other (DL-013). The third is invisible to the Go test, so a change to the rule is made in all three.

### Switching a running session's model

`POST /api/v1/sessions/{ref}/model {model, conversation?}` switches the model of a running session. It is a per-act write like a message and answers 202: the same authentication, connection reuse, mint budget and rate limit (DL-019). `SwitchModel` makes the call a job's conversation gets at its start, `setConversationModel`, on the chosen conversation.

- The model passes `checkModel`, asked about the session's owner, whose keys the sandbox holds, not an admin acting on the session. A model the list lacks is accepted only if it is the session's own launch model, which the sandbox's config declared; any other custom name is refused with the reason, because it can be declared only at launch.
- On a job it is allowed whenever a message is (`jobRefusesAMessage`), and the job's stored request keeps its launch model. An interactive session with no conversation yet gets one first.
- It writes an audit marker, `spov.session.model.switched`, naming who switched and to which model. `contract.Used` already holds the route.
- The current model is read from the log: the newest `session.model.selected` frame of the conversation (`storedModel`, carried as `LogEvent.model` and read by `currentModel` in `web/src/lib/modelpick.ts`), else the launch model. A switch made from the terminal UI therefore shows too. The frame is durable, so the recorder already keeps it, and the transcript does not draw it (`Plumbing`).
- The page shows the current model beside Send as a picker (`ModelSwitch.svelte`, DL-059). The picker reads the list only when first used and offers neither the default entry nor the custom one (`allowCustom`, `showDefault`).

## Rationale

One field on a shared type and one write site into the sandbox keeps the interactive half nearly free, so the work is done once. OpenCode's identifier rather than a spov-side name avoids a mapping table that rots against every provider's catalogue, with the error of a wrong mapping surfacing inside a sandbox where nobody sees it.

Config is the primary path because the key is documented and measured in the pinned build, and because spov is not in the call that opens an interactive conversation. The extra per-conversation call for a job is a narrower scope overriding a broader one, which is what config layering is for. Rejected alternatives:

- an `OPENCODE_MODEL` environment variable: not a documented contract, and the environment is where provider keys live, so a variable that looks like a credential but is not invites the wrong handling;
- a `model` key on the session-create body: spov does not send it, and an ignored key means every job runs on the default while its row claims otherwise;
- the config alone for jobs: a repository's config can outrank it;
- `OPENCODE_CONFIG_CONTENT` for the whole config: it overrides every source, including a repository's own, is invisible while debugging and puts the config beside the password in the process environment; it remains the escape hatch;
- jobs only: the request, the row and `Options` are shared anyway.

The profile is where per-user facts already live: `GitName` is the exact precedent, a value changed rarely and read on every launch. The config layering is per deployment and per process, while a default is per user, must survive a restart and be readable by any replica, which is a row and not a file. The default is validated on write for the same reason the launch check exists: a refusal costs one response, a pass costs a sandbox and a run that cannot work, and a default repeats that bet on every launch until it is changed. The alternatives, rejected: a settings table, storing the default unvalidated (it moves a legible error to a later launch about a model the caller may not remember choosing), and storing a provider instead of a model (it is the sandbox's pick within a provider that caused the failure, and "anthropic" does not say which model).

Resolution is server-side because the CLI would otherwise have to read `/me` before every launch, the web app would need the same logic again, and an older CLI would never gain it. Falling back silently when a default is stale was considered seriously, because it always launches, and rejected because a run that always launches on the wrong model is what a broken run looks like from outside. Falling back with a warning is a second way for a job to differ from what was asked, for a case the caller can fix in one click.

A switch is the same kind of act as a message, so it takes the same path and guards, and reading the current model from OpenCode's own frame keeps a switch from the terminal UI visible.

## Measurements

- Spike S11 (conversation model endpoint and config precedence): `GET /api/config` at a checkout inside the workspace lists the global file first and the repository's last (order is precedence, so the repository wins), and at `/root` the repository's config is absent. The model endpoint answers 204 to the object `{"model":{"providerID":"anthropic","id":"claude-opus-4-5"}}` and 400 `Expected Model.Ref at ["model"]` to the string form. The reference persists (read back with variant `default`) and is not validated against a catalogue: it was accepted with no provider key configured, which leaves validation as spov's job. Not measured: that a turn prefers the pinned model over a discovered config, which needs a real turn with a key. Re-run: `go test -tags integration ./internal/sandbox/ -run S11ModelPrecedence -v`.
- A job with no model ran on the tool-less extraction model twice, confirmed by attaching to the running session (see Context).
- Spike S-M1: a listed model resolves in a running sandbox by itself, and an unlisted one cannot be declared after launch, which is why a switch refuses any custom name but the launch's own. Re-run: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SM1 -v`.

## Consequences

- A caller chooses the model once, in Settings, or per launch, and a job's row says what ran it.
- A user with a stale default is blocked on every launch until it is fixed. That is the intended cost; the alternative is a sandbox spent on a run that cannot work.
- `MeView`, `patchMeInput` and the session and job request types are wire types, so a change to them needs `scripts/gen-api-client.sh` and both generated files committed.
- The sidecar's provider keys are fixed when it is created (DL-034), so a key the owner stores after launch passes a switch's check and still fails in the sandbox until the sidecar is recreated.
- `jobs.model` is empty when a job ran on OpenCode's own default. A session needs no column.
- Resolution sits behind one function, which is where an organisation-level default or a restriction on the models users may choose would slot in.

## Known gaps

- The default can be set only in the browser's Settings page, not from the CLI, so a `spov jobs create` refused for a stale default has its remedy on a web page.
- There is no organisation-level default and no way for an organisation to restrict which models its users choose. An admin cannot set another user's default, although `PATCH /api/v1/users/{id}` lets an admin override a user's quota; a default is a preference, not a limit, and changing it silently for someone is a different act from raising their quota.
- A switch mid-run on a job makes its verdict harder to read, since the job's row keeps only its launch model.
- Combined with the refusal of a stale default, the browser-only setter means a `spov jobs create` can fail with a remedy that is on a web page; that is the strongest argument for a CLI setter.
- Changing the model of a running job is possible only through the switch, and a job's verdict is harder to read when it does.
- No test checks that a turn prefers the pinned model over a discovered repository config (see Measurements).
