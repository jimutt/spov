## Context

DL-160 leaves a launch's own `#variant` unchecked because there was no sandbox to ask. With DL-185 and DL-186 the server knows, before any sandbox exists, which modes a model is offered with. Spike S-MV1 (`SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SMV1 -v`, 2.4.2) measured that an unknown variant set through the session's model endpoint fails every turn with `provider.no-route` "Variant unavailable for <model>: <variant>", and that the config file's `model` string ignores a `#variant` either way.

## Decision

- `GET /api/v1/models` gives each provider a `variants` object, `{"provider/model": ["low", "high", ...]}`, holding the modes `Service.ModelModes` offers for each of its listed models that has any, in OpenCode's order. A model with none is absent from it. The models stay `provider/model` references; a mode is still sent as `provider/model#mode` in the one model field (DL-014).
- A session or job request may also carry the mode alone as `reasoning` (DL-190), which the server sets on the model `resolveModel` gives, the caller's default included, in place of any mode that default carries; a request whose own `model` names a mode as well is a 422, and `reasoning` with no model resolved is a 422 too.
- A create (`POST /sessions`, `POST /jobs`, and a schedule's create when there is one) whose request names a mode, in either place, is checked after `resolveModel`, beside `checkModel`: the mode must be one `ModelModes` offers for the model. Otherwise it answers 422 "\"<mode>\" is not a reasoning mode <provider/model> offers" (the mode quoted, after it is checked to be an id; one that is not is refused without being quoted), followed by "; it offers low, high, max" or "; spov knows no reasoning modes for it", in DL-160's words. Only a mode the request itself names is refused: one that comes from the caller's stored default is left to the opening's check (DL-188), so a pin bump that drops a mode never refuses every launch of that user. Storing a default with a mode (`PATCH /me`) is checked the same way, since its owner is choosing it then (DL-189). `reasoning` is a mode id (`modelcat.ValidID`); `default` (`DefaultReasoning`) selects the model's own default, dropping any mode the resolved model carries, is never checked, and is accepted when no model resolves.
- `GET /api/v1/models` is served without `variants` when the seen modes cannot be read, so a store failure never takes the model pickers down; the create check, which refuses, returns the error.
- The config file's model is written without the `#mode` (`SandboxConfigJSON`, `JobConfigJSON`), since OpenCode ignores it there and the opening sets it.

## Rationale

The list a person picks from and the list a launch accepts are one list, as DL-160 has it for the switch. Refusing at create costs nothing and tells a CLI user at once; a default chosen long ago must not turn into a refusal the day the pin moves.

## Consequences

- A hand-written `--model x#foo` that worked silently before is refused unless the model offers `foo`.
- A model listed with no known mode accepts only its default from a create until a sandbox reports its modes (DL-186).
