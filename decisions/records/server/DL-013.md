## Context

A caller who names a model needs to know what to name. Free text is the worst input for a value whose typo costs a whole sandbox launch to discover, and a model name that is wrong for any reason (a typo, a retired model, a provider the caller has no key for) otherwise shows up only inside a sandbox that has already been bought, cloned into and started. A job then provisions, opens its conversation and produces nothing, which reads like a hung job and can be diagnosed only by attaching. Refusing at request time costs one response.

Two facts about providers pull in different directions. Which providers spov forwards a key for, and the one host where the credential proxy may use each key, are a security boundary and must not follow a downloaded file. Which models a provider offers changes every few weeks, and a list kept by hand falls behind: a hand-kept literal misses the newest models of several providers within weeks.

The pinned OpenCode resolves model names against models.dev, which it fetches from OpenCode's mirror at `https://models.opencode.ai/api.json`. The mirror was byte-for-byte identical to models.dev when compared, and a sandbox can reach it under every egress preset (`*.opencode.ai` is in `ModelAPIDomains`).

## Decision

### Providers are a static literal; models are models.dev's

`prep.Catalogue()` lists the providers: OpenCode's own provider id (the half of `provider/model` before the first slash), a display name, the environment variable the key lives in, and the proxy API (host, header, and paths where the key is used) from which the credential proxy decides where a key may go (DL-034). It has no model list. The ids are exact strings read out of the pinned OpenCode build, and they are not always the obvious word: Gemini's provider id is `google` while its key variable is `GEMINI_API_KEY`. OpenCode Go and OpenCode Zen are two providers that share one key variable and one API (DL-015).

The same literal is the forwarded-key list. `prep.ProviderKeyEnvs()` gives the variables, and `providerEnvVars` in `internal/cli/fly.go` is that call, so a provider cannot be offered whose key is never forwarded into the sandbox (which would fail at the first turn, not at the pick). `TestEveryForwardedProviderKeyIsStillForwarded` guards it.

`internal/modelcat` holds the models. `Parse` reads models.dev's document, for the literal's providers only, and keeps each model that takes and produces text, can call tools (an agent that cannot call tools cannot do a job) and is not deprecated. Models are sorted newest first by release date, then by id. Beta models are marked, and each keeps its context and output limits. Deprecated models are kept by id alone, because the check needs them (below).

The download is untrusted. The document is bounded in size. A model id is kept only if `ValidID` accepts it: non-empty, at most `MaxModelIDBytes` (200) bytes, and no whitespace, control or format characters and no `#`. A release date is kept only if it has the YYYY-MM or YYYY-MM-DD shape. Names and numbers are bounded. An entry whose own `id` differs from its key is dropped, because OpenCode resolves a model by its key.

### Fetching, caching and the snapshot

`modelcat.Source` is the deployment's list, read through `Deps.Models` (`ModelCatalogue`). It serves the last fetched list, else the persisted one, else the snapshot, and reading it never waits on the network.

- A list is fresh for an hour (`Fresh`). An older one is served while a background refresh runs, and a failed fetch is not tried again for five minutes (`FailureBackoff`).
- A refresh sends the held ETag. A 304 keeps the list and renews its age. A 304 to a request that named no version is an error, since it would turn the snapshot into a "live" list.
- A document that parses but offers no model of the literal's providers is rejected. A failed fetch never empties the list.
- A server on Postgres keeps the list in memory. Any other server (a local one) keeps it under `models` in the state file beside `server.json` (`statefile`'s `LoadModels`/`SaveModels`, wired in `internal/cli/imagestate.go`). A persisted list older than the binary's snapshot is set aside, since the snapshot may carry a provider or a filter the old list lacks.
- A filtered snapshot of the same shape is embedded in the binary and serves until the first fetch succeeds. `scripts/model-snapshot.sh` regenerates it (through `internal/modelcat/snapshotgen`) and runs before a release; review its diff.
- Tests pin a list with `FixedModels(modelcat.Fixed(...))`, never the snapshot. `modelcat.List.Lookup` is the only place that answers whether a model is listed.

### `GET /api/v1/models`

The endpoint answers, per provider: `provider`, `name`, `key_env`, `have_key`, `sign_in`, `models` and `beta`. Top-level `catalogue` is `{source: "live" | "snapshot", as_of}`: the time the list was last fetched, or the snapshot's date. The age lets a picker say "from spov's built-in list" when the server has never reached models.dev.

- Models are full `provider/model` references, newest first, so a client does not assemble them. OpenRouter's model ids contain slashes of their own (`openrouter/anthropic/claude-sonnet-5` is three segments), so every reader splits on the first slash, as `LookupModel` and `modelRef` do. `beta` is the subset of `models` that models.dev marks beta.
- Every provider is listed, including one the caller holds no key for and one with no model left after filtering, so the answer to "why can't I pick this one" is on the same screen as the choice.
- The endpoint requires a principal. Model names are not secret; key presence is.
- `have_key` asks `heldProviders`, which asks `Service.storedProviderKeys`: the deployment's environment, or the caller's stored keys per variable where a per-user resolver is wired, plus the OpenCode sign-in. A launch resolves keys through the same call (`providerKeysFor` adds the sign-in's token), so the answer cannot disagree with what a launch would do. The credential store alone would report no key on a deployment that exports `ANTHROPIC_API_KEY` for every user, marking a usable model unavailable. `TestHaveKeyFollowsWhatALaunchWouldCarry` guards it.
- The key map holds the secrets themselves, so `heldProviders` reduces it to presence immediately (the value is never kept), and a blank value is not a key. `TestTheModelListCarriesNoKeyValue` guards it.
- `sign_in` is `"opencode"` on a provider that the OpenCode sign-in would unlock, and only where a session would be given it (`consoleCarried`). A sign-in whose token has lapsed still counts as held, because the launch refreshes it. Clients word the missing-key label and its note from this field, never from the variable name (DL-015).

### The check before the quota

`Service.Create` and `Service.CreateJob` call `checkModel` after the request is validated (both normalise through `withDefaults` first, so they cannot be checked differently) and before the quota is taken or anything is provisioned (`TestTheModelIsCheckedBeforeTheQuota`, `TestARetiredModelIsRefusedBeforeAnythingBillable`). The settings save and a running session's model switch call it too (DL-014). An empty resolved model is OpenCode's own default and skips the check. A model longer than `MaxModelBytes` (256) is refused before any refusal quotes it.

The check asks two questions, and each refusal says which half is wrong:

1. Is the reference one spov can run? `prep.LookupModel` tells three answers apart: the string is not `provider/model` at all (`ErrNotAReference`), the provider is not in the literal (`ErrNoSuchProvider`), or the provider is fine and the model half is what is in question. The model half has any `#variant` removed, so a refusal about `anthropic/claude-sonnet-5#high` quotes the model and does not read as if the whole string were rejected. `modelcat.List.Lookup` then finds the model listed, deprecated, or neither.
2. Does the caller hold the provider's key? Presence is asked through `heldProviders`, the same function the picker uses, so a provider the list marks available cannot be one a create refuses. A missing key is refused naming the variable and how to supply it. Presence only: the key value never reaches a client-visible error.

What is refused:

- a reference that is not `provider/model`, a malformed model id, and a provider spov's literal does not have;
- a model the list marks deprecated, since the pinned OpenCode cannot resolve it (it answers `Model unavailable: <provider>/<model>`);
- a model under a provider whose key the caller does not hold.

What passes: a model the list does not have, under a provider the literal has and the caller holds a key for. It launches with the note "`<model>` is not in spov's model list; launching on it anyway". The note is in the launch's progress (which `spov fly` prints) and is written to the session's log as `spov.session.model.custom`, drawn as one of spov's notes, for a session and a job alike (`TestAnUnlistedModelLaunchesWithANote`). A stored default may also be a custom name, and Settings saves it with the same note. Because a custom name is written into the sandbox's config, its shape is checked first; the config declares it (DL-038).

The refusal is 422 (`ErrInvalidRequest`, which `toHumaError` maps), not 400, so one class of refusal has one status. A key resolution that fails is neither a refusal nor a pass: failing open buys the sandbox the check exists to avoid, and refusing as invalid blames the caller for spov's outage. It returns as the error it is, which maps to 502. Refusals are matched by name (`prep.ErrNotAReference`, `ErrNoSuchProvider`, `modelcat.ErrNotAModelID`), never by a trailing `err != nil`, so a future transport error cannot become a 422.

### Key advice follows the deployment

A hosted server resolves stored keys per request, so storing the key is the whole fix. A local server reads the environment and the credential store once at startup, so storing or exporting a key changes nothing until `spov serve` restarts. `keyAdvice` tells the two apart by whether a per-user resolver (`UserProviderKeys`) is wired, and says so. `TestTheKeyAdviceSuitsTheDeploymentItIsGivenOn` guards it.

## Rationale

The interface outlives its source. A client written against `GET /api/v1/models` keeps working however the list is produced, and nothing in the response says where a name came from except the list's age. A list the caller cannot use is worse than no list, hence `have_key` per provider: offering a model that fails on a missing credential is the same class of error as offering one that does not exist.

models.dev is what the pinned OpenCode resolves against, so a name taken from it is one the sandbox recognises, and one file covers every provider without needing a key. The provider list is a credential question, not a catalogue question, so it stays closed: the provider decides where a key may go. The model under it is the caller's business, and refusing a model the list lacks would only make spov the bottleneck for using a new one (a provider can give an account a model before models.dev lists it). A typo under a known provider is not caught by spov in that case; it is caught by OpenCode at the first turn.

The check is at the handler, not in the supervisor. By the time a supervisor has a job, the request was accepted and the caller is gone; a failure there is a failed job with a row, a verdict and an attempt count, describing what is a client error. The alternatives were rejected: validating in the supervisor still costs the job row and the queue round trip, passing anything through is the failure the check exists to prevent, and a warning lands in a log the caller does not read.

"No such model" and "no key for that provider" have different fixes and must keep separate wording. A catalogue refusal never mentions a key: "no provider spov carries a key for" sends a reader to store a key for a provider that does not exist. `TestTheTwoRefusalsAreNotTheSameMessage` makes that mechanical.

The check and the sandbox are two parsers of one string and must agree. `LookupModel` decides what a create admits; `modelRef` (in `internal/server`) decides what the session's model endpoint is told. A reference one accepts and the other refuses passes validation and then runs on OpenCode's default. So both split on the first slash, strip a `#variant`, and refuse an empty half. `TestTheCheckAndTheSandboxAgreeOnWhatAReferenceIs` pins them to each other in both directions. A third parser, `withoutVariant` in `web/src/lib/jobform.ts`, cannot be seen by the Go test; change all three together.

A free-text box with no list was rejected, and so was querying each provider live (no uniform catalogue, an outbound call on a UI path, and a cache and failure semantics of its own). OpenCode's own `GET /api/model` and `GET /api/provider` are the most authoritative source, since they are the thing that resolves the string, but they need a running sandbox to answer a question asked before there is one. A build-time capture of them would be worth revisiting.

The check is a guardrail on an honest request, not a boundary. A caller with a direct API token can send anything, and OpenCode is what resolves the string.

## Measurements

- The mirror `https://models.opencode.ai/api.json`, measured 2026-10-19: 5.8 MB, about 410 KB compressed; 232 providers and 9,056 models; it has an ETag and a conditional request answers 304. All ten of spov's providers are in it, each model with `tool_call`, `modalities`, `status` (`beta`, `deprecated` or none), `release_date` and `limit`. OpenRouter alone lists 390 models, 319 of them able to call tools; xAI lists video models, which the text filter drops. The pinned build fetches this mirror (the string `Failed to fetch models.dev` is in the binary). Re-run: `scripts/model-snapshot.sh`.
- The embedded snapshot, 2026-10-19: 538 models, 82 KB.
- Spike S-M1: the pinned OpenCode resolves an active models.dev model by itself, refuses a deprecated one, and fails on a model neither listed nor declared in its config. Re-run: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SM1 -v` (local, no Modal, no key).
- A listed model can still fail in the sandbox as `Model unavailable: <provider>/<model>`. Seen once on `openrouter/qwen/qwen3.8-27b`, which models.dev, the mirror and OpenRouter all listed; egress was ruled out. OpenCode resolves a reference from its config catalogue, its cache and its bundled snapshot before it tries the network, so a first turn can resolve against a stale snapshot. The same SM1 spike shows the error.
- The check needs no change to a Go type, so the generated API document is unchanged (`scripts/gen-api-client.sh`). A change to the models API's types does need that script run, and CI fails on drift.

## Consequences

- A wrong provider, a retired model or a missing key is a refusal in front of the person who typed it, with the fix named. A CLI can complete model names and the web form can render a select.
- The list is as fresh as models.dev and the hourly refresh. A server that cannot reach the mirror serves the snapshot, which the response says (`catalogue.source`) and which lags until the next release.
- In hosted mode `have_key` opens up to nine stored credentials through the sealer per request and warns once per unreadable key. `CredentialStore.List` would be cheaper but would report present for a key a launch withholds as unreadable, which is the disagreement this endpoint exists to avoid. Clients should read the endpoint once on load, not on a timer.
- Every change to a Go type under `internal/server` needs `scripts/gen-api-client.sh`; the `beta` and `catalogue` fields reach the web form through the generated client, and `modelGroups` in `jobform.ts` reads them.
- Tests that need a list use `FixedModels`; the check, the models API and `prep.LookupModel` read the live list through one seam.
- The ladder models of DL-047 must be in the list: `TestTheSnapshotHoldsEveryRung` checks each rung's fallback and family against the snapshot. A retired ladder model answers 404 and a failed prep pass does not fail the job, so the drift would otherwise be silent.

## Known gaps

- The response carries identifiers, beta marks and the list's age, with no per-model metadata such as pricing or capability flags. The context and output limits are kept in the list and not served.
- A model delisted between the request and the provision is not re-read. The check is at the create and the supervisor provisions later; catching it would cost a failed job.
- A listed model the provider has retired passes both checks and fails in the sandbox (see Measurements).
- A hosted caller whose stored key cannot be decrypted has it withheld by the per-user resolver with a server-side warning, so the caller is told to store a key they already stored. Telling it from an absent key would mean materialising the value, which the check may not do; the server's warning is the answer.
