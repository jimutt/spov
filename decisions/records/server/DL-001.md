## Context

spov must be a small, fast, native binary that drives Modal sandboxes, talks to the OpenCode server API and starts the OpenCode TUI. The deciding constraint is how a program reaches Modal. Modal's gRPC API is not public and can change without warning, the `modal` CLI cannot create sandboxes, and Modal Functions and web endpoints are Python-only. Modal ships official SDKs for Python, JavaScript and Go, each with full Sandbox support. Of the languages that compile to a native binary, only Go has one.

The control plane (`spov serve`) has the same question. Everything it needs from Modal (sandbox creation, connect tokens, egress policy, filesystem snapshots, file I/O) exists in the Go SDK, and a webhook receiver is an ordinary HTTPS server. Modal Functions being Python-only is therefore no reason to write the control plane in Python or to host it on Modal.

## Decision

spov is written in Go and links `github.com/modal-labs/modal-client/go` directly. There is no Python sidecar and no generated gRPC client.

The control plane is Go too. It lives in the same module and the same binary as the CLI (`spov serve`), and Modal is only the sandbox provider, with no language constraint on the server. The control plane runs as an ordinary service on infrastructure the operator already has (a VPS, Kubernetes), not as a Modal app.

`cmd/spov` stays thin. The wiring of `spov serve` lives in `internal/server` and `internal/cli`, and `internal/session` holds the launch logic that is the server's core. The CLI imports it only for the client proxy and the step types (see DL-002). The package layout and the walls between packages are in `AGENTS.md`. Decisions about the shape of a sandbox belong to the `sandbox` namespace, and decisions about the API, identity and storage belong to `server`.

### The library stack

| Concern | Choice | Why |
|---|---|---|
| CLI framework | `spf13/cobra` | completions, doc generation, wide familiarity |
| Config | `knadh/koanf` v2 | an explicit merge order of user file, project file and environment |
| Terminal UI | `charm.land/lipgloss/v2`, `charm.land/bubbletea/v2` | the repository picker is spov's own Bubble Tea model, with `sahilm/fuzzy` for matching (see DL-028) |
| Modal | `github.com/modal-labs/modal-client/go` | pinned to an exact version |
| Forgejo and Gitea | `codeberg.org/mvdkleijn/forgejo-sdk/forgejo/v3` | behind an internal interface |
| GitHub and GitLab | `net/http` in `internal/git` | no vendor SDK |
| HTTP and SSE | standard `net/http` and a hand-written SSE reader | the protocol is small enough to implement directly |
| Local secrets | `zalando/go-keyring` | the OS keyring |
| Release | goreleaser | cross-compiled archives for linux and darwin on amd64 and arm64, with checksums and a changelog, on the free tier |

The server adds huma for the API, pgx for Postgres, River for the job queue, `openai-go` for the prep pass and OpenTelemetry for metrics. `go.mod` is the live list.

Forge clients sit behind spov's own interfaces, so a vendor SDK that bumps its major version often does not leak into the rest of the code.

The Modal SDK is pre-1.0 and ships breaking minor releases. spov pins the exact version and keeps its types behind `internal/sandbox`.

Three import paths mislead tools that rely on stale documentation: the Charm libraries are `charm.land/*` v2, not `github.com/charmbracelet/*` (pkg.go.dev serves old betas); the Modal SDK is `modal-labs/modal-client/go`, not the deprecated `libmodal/modal-go`; and koanf paths end in `/v2`. `AGENTS.md` carries the table.

### The go directive

The `go` directive in `go.mod` follows the highest floor any dependency imposes, not spov's own needs. `go mod tidy` raises it to match and undoes a value lowered by hand. It is `1.26.0` because River v0.47 requires it, and CI builds on 1.26 (`GO_VERSION` in `ci.yml`). Raise it for spov's own code only when a language feature needs it.

## Rationale

- Go is the only native-binary language with a first-party, supported Modal SDK that covers sandboxes, tunnels, exec, secrets, volumes and published images.
- Rust would mean owning a generated client against an API Modal calls unstable, or a Python hop for every action.
- A TypeScript program compiled to one file is about 90 MB at its smallest, and a Python program frozen into one executable takes about 1.8 s to start (see Measurements). Neither suits a CLI that runs on every command.
- One language means `internal/git` (repository-narrowed GitHub App tokens) and `internal/sandbox` (the whole Modal surface) exist once. A Python server would fork both.
- One binary means local mode, where the CLI starts its own server, gets the server code without a second artefact. A second binary would only add a version-skew surface.

## Measurements

A Go binary with a spov-shaped dependency set measured about 9 MB stripped, about 2 ms to start, and 5 to 15 s to build. The alternatives were measured the same way: a TypeScript program compiled to one file came to about 90 MB at its smallest, and a Python program frozen into one executable took about 1.8 s to start.

## Consequences

- A bump of the pinned Modal SDK version is a change to `internal/sandbox` and the integration tests, not to the whole tree.
- The binary carries the server, so `cmd/spov` must stay thin, and the walls between packages (`.golangci.yml`) keep the CLI from reaching the launch core directly.
- A Kubernetes deployment might want the API image separate from a worker image. That is a build-flag question, not a reason to split the module.
- Dependencies set the `go` directive. A new dependency can raise it, and CI's Go version moves with it.
