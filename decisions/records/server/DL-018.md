## Context

A browser watching spov needs two live things: the state of the caller's sessions, and the transcript of one session. Any replica must be able to serve either request. The sandbox is expensive to keep alive, and Modal ends a sandbox that has been idle for its `IdleTimeout` (30 minutes by default); a sandbox that is never idle lives until its overall timeout (4 hours by default, at most 12 in spov). So the design has to answer what counts as traffic on that clock, because a dashboard left open in a forgotten tab must not keep a sandbox billing.

Two spikes settled that (see Measurements). A stream that is held open does not reset the idle clock. A plain HTTP request does, whatever it asks for. So anything that polls a sandbox, a message re-fetch on a timer included, keeps it alive to its overall timeout.

## Decision

**The store is the read model, and the recorder is the only reader of a sandbox.** `internal/server` makes no request to a sandbox on any read path: not the session list, not `/messages`, not `/log`. A browser watching a session mints no connect token, so the per-session mint budget is spent only by attach and by the recorder (see DL-030). Everything that reads a sandbox lives in two files the recorder owns: `sandboxio.go` (`openSandboxEvents`, `sandboxGet`, `readSSEFrames`, `SandboxReadTimeout`, `MaxSandboxReadBytes`) and `frames.go` (`projectFrame`, `isDurable`, `find`, `parseMessages`, `conversations`, and OpenCode's inferred shapes). See DL-017 for what the recorder stores. Two other reads exist and are not read paths: the job-end visit that collects reports, evidence and the outcome file (see DL-045 and DL-051), and a person's own steering acts (see DL-019), which are writes made one at a time. A job's lifecycle writes (its opening turn, the loop command and the model pin, in `supervisor_open.go`) are likewise made once per act (see DL-046).

### The session-state stream

`GET /api/v1/sessions/events` is caller-scoped. Its contents are the output of `Service.StreamList` for the calling principal: a user sees their own sessions and an admin the organisation's, so authorisation is inherited rather than reimplemented. The newest page plus every live session is sent (see DL-012). It is one connection per caller, never organisation-wide, and one stream serves the whole list because a browser allows six HTTP/1.1 connections per origin, so a stream per session card would fail at the seventh.

`pollFeed` feeds it by reading the store every `StateFeedInterval` (2 s) behind a `Subscribe`-shaped seam, and sends a new list only when a fingerprint changes. The fingerprint covers the session rows and, through `decorationStamp`, what the list renders from elsewhere: each session's last message and its job badge. A recorder writing a message touches no session row, so without that stamp an open list would keep showing a stale newest line. An open list therefore costs one `List` and one `LastMessages` read every 2 s, plus one more `LastMessages` when something changed. The `messages_last` index on `(session_id, at desc, id desc)` makes that cheap.

There is no LISTEN/NOTIFY. Session state changes on the reconciler's 30 s tick, so NOTIFY would deliver a 30-second-old fact 2 s sooner, at the cost of a dedicated Postgres connection per replica. The seam is where it would be swapped in.

`SessionView.last_message` is a nested `MessageView`, filled by one `LastMessages` query for the page. It is a read-model object rather than a scalar field on the view.

### The session log

`GET /api/v1/sessions/{ref}/log` streams the stored events of one session.

- It takes `?after=<pos>`. Every `log` frame carries `pos`, a cursor (`LogEvent.Pos`) and not a display field; `LogEvent.Session` stays the OpenCode session id. A client resumes from the last position it saw and misses nothing.
- On open it replays `ListEvents(after, LogPageSize)` (200 rows a page) until exhausted, then tails behind the same seam as the state stream.
- spov's own markers (`spov.recorder.gap`, `spov.recorder.stopped`) are ordinary frames, so the page draws the seam where the recorder was not listening, not where the browser was not.
- When the stream is caught up, quiet, and the session is not live (or has been deleted), it sends `EndEvent{reason: "stopped"}` and closes. A store-fed stream catches up in milliseconds, so without this end the client would reopen forever on a session that will never speak again. The check runs only on a quiet tick, so a busy session costs no extra read.
- The session resolves through `Service.Get`: a non-owner gets 404 and an admin sees the organisation's. Event rows carry `org_id` and every query takes it.

`GET /api/v1/sessions/{ref}/messages` returns the stored conversations and messages projected onto `ConversationView` and `MessageView`, on any replica, with `Cache-Control: no-store` because the rows move while the session runs. `warnings` carries `"nothing has been recorded for this session"` when there are neither conversations nor events, and the text of a `spov.recorder.stopped` marker when that marker is the session's newest event. It is the newest event and not the newest marker because a recorder that gave up and a later one that resumed both leave a marker, and only the one with nothing written after it is still true. A failed-renewal note is not news of the recording and is skipped (see DL-021). `ConversationStore.LastEventExcept` answers this with one indexed lookup. The warning requires `Source == SourceSpov` as well as the name, because it is the one place the server repeats a stored event's text to a user as its own, and a sandbox chooses its own event names. Without the source check a sandbox could emit a durable frame named `spov.recorder.stopped` and put arbitrary text in spov's voice. The same rule runs through every reader of stored events: a row is spov's by its `source`, never by its name. The store refuses a sandbox-sourced row named in the `spov.` namespace (`Event.Validate`), the page draws a seam from `source`, and the supervisor reads its own markers by source and name (see DL-046).

### Stream edge rules

- `Sender.Comment` sends a heartbeat every `HeartbeatInterval` (20 s), because huma sends none.
- A stream lives at most `StreamLifetime` (5 minutes), then sends `EndEvent{reason: "lifetime"}` and the client reopens. The session cookie is validated only when a stream opens, so the lifetime is also the revocation bound: a removed user is out within the lifetime plus the allowlist's 10 s refresh (see DL-007). The lifetime and heartbeat are unexported fields set from these constants, so a test can watch an end without waiting; they are not configuration.
- The scs session is read-only inside a stream, and streaming works only through `Unwrap()`, so no middleware may wrap the `ResponseWriter` without forwarding it.
- Behind Kamal, responses are buffered by default. SSE survives only because kamal-proxy exempts `text/event-stream` and huma sets that header before the first write. The ordering is the fragile half.
- `/api/v1/sessions/events` shadows a session literally named `events`, because Go's mux prefers the literal route. That session is reachable by ID, which is what any URL the server generates uses. Renaming the stream would cost more than the collision.

### The browser

`logStream` in `web/src/lib/api/live.ts` carries the last `pos` into a reopen as `?after=`. Without it a lifetime reopen replays the whole log and the page appends every event again every five minutes. An `end` with reason `stopped` ends the generator, or a finished session would reopen in a tight loop. Both apply only to a stream that declares a cursor: the session list has no finished state, and an `end` it does not understand must reopen rather than stop the page silently. Ending calls `onEnded`, on which the detail page re-reads the conversation once, because `Recorder.Final` writes the last messages just before the session stops. An orderly `end` reopens without reporting a gap; only a dropped connection does. Cost stays a 60 s browser poll of `/me/usage`, since its inputs move on the reconciler's clock and there is nothing to stream.

## Rationale

- One reader of the sandbox is easier to reason about than several. The billing rule is true by construction: no read path contains a request that could reset an idle clock, so there is no per-path guard to maintain.
- A log stream is useful to a client when it can resume from a cursor, and the store can replay from one.
- Polling the store behind a seam matches the data's rate of change and keeps a later move to LISTEN/NOTIFY local to the feed.
- The state stream sends the same output as the list endpoint so that authorisation, paging and decoration have one implementation.

## Measurements

- **S-A, the Modal idle clock.** S-A ran four sandboxes in parallel with an `IdleTimeout` of 2 minutes, observed for 4m30s: a no-traffic control, a held-open `log?follow=true` stream, a `log?follow=false` poll every 30 s, and a plain `/api/info` request every 30 s as the calibration arm. The held-open stream died with the control at 2m1s, so it does not reset the idle timeout. The poll and the calibration arm were both still alive at 4m30s, so a plain request does, whatever it asks for. Every arm, the control included, paid one request at t≈0 (`createSession`), so S-A shows that holding a stream is free and says nothing about opening one; a reconnect that redials is a request. S-A and S-B together used five billable sandboxes, all terminated. A measurement through a tunnel found that a held-open stream keeps a sandbox alive; that does not hold through the connect endpoint. Re-run: `go test -tags integration ./internal/sandbox/ -run TestIntegrationLogReadingAndIdleTimeout -v`.
- **S-B, OpenCode's experimental durable log.** `/api/experimental/session/:id/log` answers 200 `text/event-stream`, ends on `follow=false` and 404s an unknown session. At every cursor, with and without `follow`, it returns only its `log.synced` watermark, while `/api/event` delivers the durable output in full. The `seq` advances, so the watermark is a progress signal but not a transcript source. Measured on OpenCode `0.0.0-beta-18743`; a later run gave the same results. Both spikes' assertions are written to fail if the behaviour improves, which is the signal to revisit this record. Re-run: `go test -tags integration ./internal/sandbox/ -run TestIntegrationDurableSessionLog -v`.
- **The `/api/event` frame shape** (`0.0.0-beta-18743`): `id` (`evt_…`), `created` (ms), `type`, `location{directory}`, `data{sessionID, agent, assistantMessageID, …}`, and a `durable` object `{aggregateID, seq, version}`. The marker is a key holding an object, not a string value. A projection that filtered on a string `durability == "durable"` dropped every frame and the live tail was silent, with nothing logged, because dropping unmatched frames is what the filter is for. `isDurable` tests for a non-empty `durable` object, and accepts a non-empty string there and the older `durability == "durable"` as fallbacks. Re-run: `go test ./internal/server/ -run TestProjectionAgainstRealSandboxFrames`, which holds captured frames verbatim.

## Consequences

- Watching costs nothing in sandbox lifetime, which is what makes the dashboard safe to leave open. Anything added later to a read path that requests a sandbox, on a timer or not, silently brings back the billing problem S-A measured.
- The live tail is as fresh as the recorder plus the feed's 2 s, and it depends on a recorder leader being up. A failover pauses every tail for up to a sync, and the markers say so on the page.
- The activity feed can have gaps across a disconnection while the conversation itself is whole, and the UI must not imply otherwise.
- Frames the projection cannot match are skipped. A projection that returns nothing is a wrong shape before it is a dead sandbox. `TestMessagesFromRealSandboxShapes` holds message envelopes captured from a running sandbox (the speaker is `type`, not `role`), but the rest of the `/api/session/:id/message` shape that `parseMessages` reads is inferred, not measured.
- The sandbox is the untrusted side, so the recorder's reads are bounded: one accumulated frame is capped (the scanner caps only a line), a read is capped at `MaxConversations` (32), both sandbox clients refuse redirects, the dialer gives up if headers do not arrive in 30 s, and sandbox-supplied ids are path-escaped.
- The state stream's payload grows by one message per session, and the feed makes a second query.

### Guards

- `TestNoReadPathTouchesTheSandbox` points the fixture's sandbox at a server that fails the test on contact and drives the list, `/messages` and `/log`. If a read is added to one of these paths, the read is the bug.
- `TestTheRecorderNeverReadsOnATimer` covers the recorder's half.
- `TestProjectionAgainstRealSandboxFrames` guards the frame shape.

## Known gaps

- A session no recorder saw has an empty transcript and a warning that says why. There is no sandbox fallback, by design.
- A stopped session is addressable only by its ID, because `Sessions().Get` resolves a name among live sessions alone.
- `/messages` has no cap on conversations and the store paginates nothing yet. A sandbox with hundreds of conversations has not been seen. The bound to add is on the query, not a sandbox read.
