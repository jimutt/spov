## Context

A GitHub App installation token lasts an hour. spov mints one per session, narrowed to the session's repositories, and a session or a job can run for several hours, so without renewal git and `gh` fail inside the sandbox an hour in, with nothing but an authentication error to say why.

Nothing in a sandbox calls the server, and a local `spov serve` cannot be reached from Modal at all. The server can run a command in a live sandbox through Modal's API (`Handle.Exec`, which `attach` also uses). Whether the sandbox holds the token itself depends on the credential proxy (see DL-034). With the sidecar, the real token lives in the sidecar and the main container holds placeholders. A sandbox without the sidecar keeps its tokens in files in the main container.

## Decision

The server re-mints a session's GitHub App token before it expires, while the session is in use, and writes the new token into the sandbox. The sandbox never asks for a token and holds nothing that could mint one. The App's private key is never in the sandbox.

### When a token is due

`RenewGitTokens` runs once a minute, with a small jitter (`RunRenewals`), on one replica: the one that holds the reconciler's leader lock (see DL-004 and DL-003). It reads the store for running sessions that have a renewable token whose expiry is within `RenewWithin` (15 minutes), and touches a sandbox only to write a due token into it. The server stores each token's mint time and expiry (`GitTokenMintedAt`, `GitTokenExpiresAt`), never the token, and `SessionStore.SetGitToken` is their only writer; `Update` keeps the stored values. With a one-hour token, a session in use is written to about every 45 minutes, and that write is the only sandbox write on a timer. The same pass then writes refreshed OpenCode sign-ins into the sessions behind on them (see DL-015).

A platform is renewable when `git.Renewable` says so, which is true only for a GitHub App. `Kind()` cannot tell an App from a personal access token, and a PAT or a Forgejo token is the stored secret itself, which spov never renews.

A renewal resolves only the credential tier the launch recorded, so it never switches whose credential the sandbox holds; a tier that is gone fails the step (see DL-042). It mints with the git access the launch recorded, including the wide token for `all` (see DL-043).

### Only while the session is in use

An exec resets Modal's idle clock (spike S-R1), so a timer that re-minted every live session would keep abandoned sessions billing to the hard timeout. `inUse` gates every re-mint. A session is in use when:

- its job is unfinished (a job's session is in use for as long as the job is); or
- since both the current token was minted and the last re-mint was tried, there is a stored event other than the recorder's markers (`MarkerGap`, `MarkerStopped`) and the renewal-failed note, or a connect mint by anyone but the recorder. A steering message writes a stored event, so it counts as activity. `LastEventExcept` looks past a marker written after real activity.

A re-mint can therefore extend an idle sandbox's life by less than an hour: the gap between its last activity and the re-mint. The cost is on the other side. A session left idle past its token's expiry has no token when its person comes back, and the first pass after the first act re-mints it, so up to about a minute of git failures follows. Loosening `inUse` keeps abandoned sessions billing (`TestAnIdleSessionIsNeverReminted`). Metrics count renewals as renewed, skipped (due but idle) or failed (see DL-011).

### Writing the token

`writeToken` decides where the token goes by the sandbox's `proxy` tag, never by whether the sidecar answers (see DL-034). With the sidecar, it runs the sidecar's `set-token` command for the platform. Without it, `opencode.RefreshArgs` runs one script per platform in the main container through `Handle.ExecInput`: git's own `git credential-store store` replaces only that host's entry in the credential file under git's lock, so it cannot race git's own rewrite after a push, and gh's files are written to a temporary name and moved into place. The token goes on the exec's standard input and never in argv, which is visible to process listings and may be recorded by the provider.

gh reads `~/.config/gh/hosts.yml`, never `GH_TOKEN`. The environment variable overrides the file, and a running process's environment cannot be changed from outside. The entrypoint writes one fragment per host under `hosts.d`, in gh's multi-account format, and `hosts.yml` is their concatenation, so rewriting one host's token leaves another's alone. `config.yml` is marked `version: "1"`, because the older single-account format makes gh call GitHub on first use to migrate it, which fails offline or with a bad token. The files are mode 0600 and their directories 0700, and `~/.config/gh` is on the plugin's deny patterns beside the git credential file and tea's config.

### Revocation

A re-minted token is revoked only once a later one for its platform is known to be in place (`Service.hold`), because a failed exec may still have written its token. A failed re-mint holds its token. A later success revokes everything held before it for that platform. Everything held is revoked when the session is deleted or not live. Each platform stands alone, so one that fails does not undo another. The launch's own token is left to the launch's revoker, since it has under 15 minutes left by then. A server restart loses the held tokens, so a token minted before a restart cannot be revoked and expires on its own within the hour.

### A failed renewal

A failed re-mint is warned and retried only after newer activity, not on the next pass. The row stays due, but a retry needs activity newer than the failed attempt (`attempted`), so a refresh that keeps failing cannot write into an idle sandbox every minute. If it keeps failing, the token expires and git fails inside the sandbox. The expiry in the row moves only when every platform succeeded. A session found to have no renewable platform left is warned about once and then skipped.

The failure is also written into the session's log as `spov.session.credentials.renewal.failed` (`MarkerRenewalFailed`, `noteRenewalFailed`), because the person who can act reads the session page and not the server's log, and a log marker reaches every client and survives a reload. The text names the platform, the redacted reason, and when the token in the sandbox stops working, for example: `Could not renew the git token (resolving example-org/app: no credential for platform "github": …); git access through it ends at 20:18 UTC.` ("ended at" once that time has passed). The reason goes through `redact`. The page draws it as one of spov's quiet notes, in full on one line up to 400 characters (`noteText`, `NoteMarkers` in `timeline.ts`), because it is spov's own sentence and not a payload. It applies to interactive sessions and jobs.

- It is written once per run of failures: the first failure after a successful mint, or after server start, writes it; later failures do not; a successful renewal starts a new run. The state is process-local, so a restart may write it once more.
- It is not activity. `inUse` skips it as it skips the recorder's markers, so a failure never causes the next attempt. Writing it on every attempt would flood a job's log, and counting it as activity would turn one failure into a retry every minute (`TestAFailedRenewalIsNotedOnceAndIsNotActivity`).

### Adopted job sandboxes

A job sandbox adopted after a server restart has lost the token's expiry, so its credentials are worked out again from the owner's forge and its renewable token is marked due at once (`AdoptJobSandbox`; see DL-045).

## Rationale

- **Push, not pull.** A credential helper in the sandbox that asked the server would need the server reachable from Modal, which a local server is not, and would leave a standing secret in the sandbox that can mint tokens for as long as the session lives. Pushing works the same in both modes, and the sandbox holds only a token that expires within the hour. Putting the App's private key in the sandbox would let it mint tokens for every repository the App is installed on. Proxying git through the server has the same reachability problem and a much larger surface.
- **Gated on activity, because of S-R1.** See above.
- **A file for gh, because of S-R2.** The environment variable is the one thing a running sandbox cannot have changed under it.
- **Standard input for the token.** The token is readable from the credential store anyway, so this is about not leaking it further than the sandbox already holds it.

## Measurements

- **S-R1, an exec resets the idle clock.** With `IdleTimeout` of 2 minutes, a sandbox given nothing died at 2m16s. One given a short exec every 60 s was alive at 4m30s. A write keeps a sandbox alive like a plain HTTP request (see DL-018). Re-run: `go test -tags integration ./internal/sandbox/ -run ExecAndIdleTimeout -v`, which creates two billable sandboxes and terminates them.
- **S-R2, gh's config.** gh 2.98 reads its token from `~/.config/gh/hosts.yml` without `GH_TOKEN` and follows a rewrite of the file. It needs the multi-account format (gh 2.40 and later) with `config.yml` at version `"1"`; the older format triggers a GitHub call to migrate it. When `GH_TOKEN` is set it still wins over the file. Re-run: `go test -tags integration ./internal/sandbox/ -run 'GhReadsItsConfigFile|RefreshThroughExecInput'`, which creates billable sandboxes and terminates them. Re-run it on a gh or image bump.

## Consequences

- GitHub App sessions and jobs keep git and gh working for as long as they are in use.
- The entrypoint and the image depend on gh's config format.
- A renewal is a sandbox touch beside the recorder's reads and a person's steering writes, and the only one on a timer. The `inUse` guard is what keeps it from billing idle sandboxes.
- The launch does not warn about a token outliving its hour for a GitHub App platform. A user's GitHub PAT is unaffected.

## Known gaps

- A token minted before a server restart cannot be revoked and expires on its own.
- A pass renews its sessions one at a time, which matters only with many due at once.
- A session idle past its token's expiry has up to about a minute of failing git after its person returns.
