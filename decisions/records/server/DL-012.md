## Context

The session and job listings grow with every session and job. A client that reads the whole history on every call gets slower and heavier over time. What people look at is the newest few entries, with a way back when they need it. Whatever a listing leaves out, it must never leave out a live session or an unfinished job: a forgotten sandbox that keeps billing must not scroll out of sight, and the limit meters count live sessions and unfinished jobs from the list they hold.

## Decision

### The listings

`GET /api/v1/sessions` and `GET /api/v1/jobs` are both newest first and paged by an ID cursor:

- `limit` is how many entries to return. The default is 50 and the maximum is 200. A larger value is clamped and not refused (`pageSize`).
- `before` is an ID, and only entries older than it are returned. Session and job IDs are ULIDs, so ID order is creation order, and `id < before` ordered by `id desc` is the whole query. There is no offset, so an entry created while a reader pages does not shift the pages under them. The cursor is exact under concurrent inserts and costs one index range scan.
- The response carries `next`, the cursor for the following page (the last ID returned, empty when nothing older matches), and `total`, the number of entries that match the filter, for a position such as "1-5 of 127". `total` is one `count(*)` over an indexed filter, which is cheap at any size spov will reach.
- The handlers read one row more than the page (`pageOf`), so a page that ends exactly at the oldest row says there is nothing after it.

Both listings take a `state` filter as one comma-separated parameter. huma silently keeps only the first value of a repeated parameter, so `?state=queued,running` is the form. An unknown state is refused with 422. With the filter, a client can ask for every live session in a single call (`TestListJobsFiltersByStateAndRefusesAnUnknownOne`). `store.SessionFilter` and `store.JobFilter` carry `Before` and `Limit`, and each store has a count with the same filter. Postgres serves both from the primary key. The session listing's `List` is hand-written pgx (see DL-003).

A client that wants everything follows `next`. `--json` output includes `next` and `total` as decoded (see DL-023).

### The session-state stream

`GET /api/v1/sessions/events` takes `limit` (default 50, maximum 200, as the listing). Each frame is the newest `limit` sessions followed by every live session older than them, newest first (`Service.StreamList`). A live session includes every session of an unfinished job, queued included, since such a session is `starting` or `running`.

Older pages are not streamed. A page reads them once from `GET /api/v1/sessions?before=` and draws them as they were read. An older session that changes while someone looks at it updates on the next read, not live. The feed's fingerprint and `decorationStamp` cover exactly the sessions that the frame carries, so a change outside them sends nothing. The frame shape is a list of sessions, and a client that ignores `limit` gets the default.

The newest page is what people watch, and a fixed page keeps each frame and each poll bounded however long the history grows. Carrying every live session keeps a billing sandbox always on screen and keeps the limit meters exact without a second request. Streaming older pages would mean one feed per page a reader opened, for rows that rarely change once finished. An old session that is still live is drawn above the page's oldest rows. The web app's use of this is in DL-060.

### `spov ls` and `spov jobs`

`spov ls`, `spov jobs` and `spov jobs list` print the newest `-n/--limit` entries (default 5) of every state, finished included, newest first. Below them in the same table come any live session (for `ls`) or unfinished job (for `jobs`) that is older than those. `--page N` shows the Nth page of `--limit` entries, and the live entries are added on page 1 only. Showing finished entries makes the job that just finished visible, and pinning live entries means a forgotten sandbox is never paged out of sight.

A footer says where the reader is and how to go on, such as `1-5 of 127 · next: spov jobs --page 2`. It says how many live entries were added, and it is left out when everything fit. There is no `--all`. `--json` prints the API view of what the table shows: the listing body with `next` and `total`, with the live entries in the list.

The CLI reads a page through the server's cursor, at most 200 entries per request (`pageThrough` in `listpage.go`), and reads the live entries with the listing's `state` filter. `spov stop --all` and shell completion read live sessions the same way and never a page of everything. Completion offers at most the 200 newest live sessions and the newest page of jobs, so a job older than the newest 50 is not completed. A cursor underneath means pages do not shift when a session starts during a read.

## Rationale

- An offset would show a row twice or skip one whenever a session starts while someone pages, which on this product is often.
- A default limit makes the cheap call the default, and the clamp keeps a client that asks for everything from being refused.
- Five rows answer "what is going on" without scrolling, and the footer makes the rest one command away.

## Consequences

- A deep `--page` reads the rows before it, up to 200 per request, only to find the cursor. That costs a few requests for a page far back, which is rare. A script that wants everything pages through `--json` and `next`.
- Guard tests are `TestTheStreamListKeepsEveryLiveSession`, `TestLsShowsTheNewestFiveAndKeepsLiveOnes`, `listpage_test.go` and `internal/server/paging_test.go`. `proseWords` and `TestEveryNamedCommandExists` cover the command named in the footer.
