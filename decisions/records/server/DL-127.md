## Context

DL-006 stores CLI tokens and device codes as hashes. Browser sessions (DL-007) were the exception: scs wrote each row of `web_sessions` under the cookie's own value, so anyone who could read the database or a backup could replay any live session, an administrator's included, and from there approve a device code for a 90-day CLI token. A security review on 2026-11-11 found it.

## Decision

The session manager always sets scs's `HashTokenInStore`: the store's key is the SHA-256 of the token, unsalted, which is sound because the token is 32 random bytes. There is no setting to turn it off.

scs's `Iterate` hands out the store's key as the session's token, and `Destroy` hashes whatever token it is given, so `Destroy` inside `Iterate` would delete nothing under hashing. Revocation therefore deletes by key (`Login.destroyIterated`), and the handle the API shows for a browser login is a prefix of the store key (`tokenID`, `Login.storeKey`), no longer a prefix of the cookie's value.

## Consequences

- Rows written before this change are keyed by the raw token and no longer match: everyone signs in once more, and the old rows expire by themselves.
- The handles in `GET /api/v1/me/sessions` change once.
- The session's contents (user ID, the OAuth state and PKCE verifier during a login) stay readable in the row; none of them is a credential.
