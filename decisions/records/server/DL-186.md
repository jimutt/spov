## Context

DL-185's snapshot is as old as the pin. models.dev adds models every week, and spov's model list follows it hourly (DL-013), so a model can be listed with no known modes until the next bump. Every running sandbox already reports its build's modes for the providers it holds (DL-159).

## Decision

- When the recorder keeps a run's list (`SetModelVariants`), it also lays the list over the organisation's seen modes, when the session's current run is on that sandbox and ran the deployment's pinned OpenCode (`store.Run.OpenCode` equal to `Defaults.OpenCodeVersion`, which the recorder is given); a run on another version, as during a rolling deploy, writes nothing there. Only models of providers in spov's catalogue (`prep.Catalogue`) are kept. A failure to keep them is logged and changes nothing else (`Recorder.keepSeenModes`).
- The seen modes are `store.ModelModeStore` (`Store.ModelModes`): one entry per organisation and OpenCode version, a map of `provider/model` to its modes. Each model a report names replaces its entry, the others stay; a merge whose JSON would pass `MaxSeenModelModesBytes` (1 MiB; each store measures its own encoding, so the edge is approximate) is replaced by the report alone, and a report past it alone keeps the entry as it was, and a write for another version than the one kept drops the old version's. Postgres keeps it in `model_modes_seen` (migration 44, one row per org and version, merged with jsonb `||` in one statement that also deletes the org's other versions); the memory store keeps it in a map that joins transactions but is not journaled, so a restart empties it.
- What a launch is offered for a model (`Service.ModelModes`) is the seen entry for the deployment's pin when it names the model, else the snapshot's entry when the snapshot is that build's, else nothing.

## Rationale

The lists are already read and validated, so keeping the newest per model costs one upsert per run. Per organisation keeps the store's org filter meaningful. A single row per organisation and version makes the merge one statement, and the byte bound and the version prune keep it from growing past one build's catalogue, whatever sandboxes report.

## Consequences

- A sandbox's list is untrusted input and now reaches other users of the organisation as offered modes: a root shell that serves OpenCode's port could add or hide a mode for a model. The ids pass `parseModelVariants`' checks, only carried providers are kept, a report that fills the bound is replaced by the next one that fits, a create still names a model the catalogue lists (DL-013), and DL-188's check at the opening keeps a wrong mode from failing a run.
- A local server forgets what it saw at each restart and falls back to the snapshot.
- A report never says a model has no modes (`parseModelVariants` drops such a model), so a model whose modes OpenCode stops listing keeps its last seen ones until the next pin.
- A store error answers no modes rather than the snapshot's, so a caller never refuses a mode the organisation's sandboxes reported.
