## Context

DL-185's snapshot is as old as the pin. models.dev adds models every week, and spov's model list follows it hourly (DL-013), so a model can be listed with no known modes until the next bump. Every running sandbox already reports its build's modes for the providers it holds (DL-159).

## Decision

- When the recorder keeps a run's list (`SetModelVariants`), it also lays each model's modes over the organisation's seen list for the OpenCode version the session's image was built for (from `store.Session.Booted`; a session whose version cannot be read writes nothing there). The seen list is `store.ModelVariantStore`: Postgres table `model_variants_seen` (org, opencode version, model reference, modes, seen at; one row per model), and in the memory store an unjournaled map, which a restart empties.
- A model's newest report replaces its row. At most `MaxSeenModels` (2,000) models are kept per organisation and version; a report of a new model past that is not kept. Rows of any other version than the one being written are deleted in the same write.
- What a launch is offered for a model (`Service.ModelModes`) is the seen row for the deployment's pin when there is one, else the snapshot's entry, else nothing.

## Rationale

The lists are already read and validated, so keeping the newest per model costs one upsert per run. Per organisation keeps the store's org filter meaningful. The bound and the version prune keep it from growing past one build's catalogue.

## Consequences

- A sandbox's list is untrusted input and now reaches other users of the organisation as offered modes: a root shell that serves OpenCode's port could add or hide a mode for a model. The ids pass `parseModelVariants`' checks, a create still names a model the catalogue lists (DL-013), and DL-188's check at the opening keeps a wrong mode from failing a run.
- A local server forgets what it saw at each restart and falls back to the snapshot.
