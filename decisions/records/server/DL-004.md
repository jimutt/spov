## Context

Listing sandboxes through the Modal SDK costs 1 + 2N RPCs for N sandboxes, so a server cannot do it for each request. Listings read the store (see DL-003), and a reconciler keeps the store in step with what Modal runs. It has to cope with a server restart, with sessions started by another spov, with replicas that die in the middle of a launch, and with sandboxes the store lost track of while they keep billing.

## Decision

### The loop

`Reconciler.Run` reconciles once at start and then every `ReconcileInterval` (30 s) plus up to 20% random jitter. Each pass lists Modal's sandboxes by the tag `spov=1` and compares them with `Sessions().ListLive`. `GET /sessions` reads only the store. A local server also reconciles once before it announces itself, so a CLI that spawned it does not see a 404 for a running sandbox (see DL-002).

Exactly one replica reconciles. In hosted mode `postgres.Leader` takes `pg_try_advisory_lock(hashtext('spov.reconciler'))` on its own `pgx.Conn`, not on a pool connection, because an advisory lock belongs to its database session and a pooled connection would release it. A replica that is not the leader retries every 30 s. The holder checks every 5 s that it still holds the lock, and a lost lock cancels the work within that time. The holder releases it on shutdown. Without the lock every replica would multiply the provider calls, adopt the same sandbox concurrently, and run a stale-`starting` sweep that judges launches it is not running. An advisory lock is the smallest correct election while there is little background work. Local mode is one process against no database and runs the loop directly (`Env.reconcilerRunner`).

### What one pass does

For each live session in the store:

- **Sandbox gone.** A session whose sandbox the provider does not list as running is marked `stopped`. The stop goes through `MarkStopped`, so a session that `Delete` stopped in the meantime is neither overwritten nor counted twice.
- **Launch in flight.** A `starting` session is left alone until it is older than `LaunchTimeout` (5 minutes by default) plus one minute, whether or not it has recorded a sandbox yet. The launch may be running on another replica.
- **Starting with a running sandbox.** A `starting` session with a sandbox ID whose sandbox the provider reports running becomes `running` with its error cleared.
- **Orphaned launch.** A `starting` session past that bound belonged to a replica that died. With a sandbox that is not running it becomes `failed` with `launch orphaned`. With no sandbox it becomes `failed` with `the server stopped while the session was starting`.
- **A queued job's session** (`starting`, no sandbox, waiting on the queue) is skipped and is never swept as an orphan. A job's session whose job has moved on is swept like any other (see DL-045).

For each running sandbox the provider lists:

- **Reaping.** A spov sandbox older than the organisation's maximum session age (its timeout quota; a reconciler built without one does not reap) plus one hour (`reapGrace`) is terminated whatever the store says, and a live session that named it is marked `stopped` with a reason that says it was reaped. The grace is generous on purpose, because reaping a session still in use costs more than an extra hour of a sandbox. The reaper is the last defence against a sandbox billing with nothing tracking it (see DL-009).
- **Listing miss.** A sandbox whose session is marked `stopped` is brought back to `running`. A transient listing miss must never hide a billing sandbox.
- **Adoption.** A sandbox the store does not know is adopted as a running session, with its name, repositories, owner and organisation read from its tags. A tagged owner is used only if it is a ULID or the local principal, and a tagged organisation only if it is one this server serves; otherwise the reconciler's default applies. Organisation IDs such as `default` and `local` are not ULIDs, so the owner check cannot serve for them. A sandbox whose name is held by a live session is adopted under its sandbox ID. So is a sandbox with no name tag. In hosted mode an adopted session belongs to a system owner until an admin reassigns it.
- **A launch that has created its sandbox but not recorded it.** A running sandbox whose name belongs to a live `starting` session with no sandbox ID is left to that launch (`launchInFlight`), so a session is not adopted a second time under its own sandbox's ID.

### A job's sandbox is recognised by its tag

A job's session is named `job-<id>`, so `launchInFlight`, which looks a session up by sandbox name, cannot find it. A reconcile pass that lands in a job's provisioning window, after the sandbox exists and before the job records `started_at`, would adopt that sandbox as a second, interactive session. That session would count one sandbox against both the session limit and the job limit. The recorder would attach twice and write the same transcript into two rows. Deleting the phantom session would also terminate a running job's sandbox. A window of a few seconds is enough, since a pass runs every 30 s.

The reconciler therefore skips a sandbox whose `job` tag (`sandbox.TagJob`, carried in `sandbox.Info.Tags`) names a job that still counts, before it considers adoption. The tag is a fact the supervisor sets at creation and nothing else writes, whereas the name is a convention. Matching the `job-` prefix would couple the reconciler to the supervisor's naming and fail for a renamed session.

"Still counts" is `JobState.Counts()`, the predicate the job quota uses, so the two cannot drift. `liveJobs` builds both answers the pass needs (the sessions of queued jobs, and the IDs of counting jobs) from one `Jobs().ListLive` call, with no query per sandbox.

A job sandbox whose job row is gone, or is terminal while its sandbox was not terminated, is still adopted. That is the backstop against a billing sandbox nobody tracks. Skipping every job-tagged sandbox was rejected for that reason. A job sandbox created without the tag would be adopted like any untagged sandbox, and `sandbox.JobTags` is the only way a job sandbox is created.

### Periodic work that runs where the reconciler runs

The leader's lock also gates other background passes. Each has its own record: the job supervisor's sweep (DL-046), git-token renewal (DL-021), the credential-proxy sidecar check (DL-034), the daily image prune (DL-016), the shared-state metrics snapshot (DL-011) and the conversation recorder (DL-017).

## Rationale

- One bounded background cost per server replaces a per-request cost that grows with the number of sandboxes.
- Reading the tag closes the window for a job's sandbox however long provisioning takes. Having the supervisor record `sandbox_id` sooner would narrow the race without removing it, because a sandbox exists before any code can record it.
- Letting the recorder deduplicate by sandbox ID was rejected because it treats the symptom and leaves the quota double count and the terminate hazard.

## Measurements

The race was seen with two concurrent `pr` jobs. The job was created at 15:12:56.145 with a `starting` session and no sandbox. Its sandbox was then created and tagged `job=<id>`. A reconcile pass at 15:13:01 found a sandbox unknown to the store, did not find a session by that name, and adopted it. The job recorded `started_at` at 15:13:19.974. The first of the two jobs escaped only because its provisioning did not overlap a 30 s pass.

Guard tests are `TestReconcileDoesNotAdoptAProvisioningJobsSandbox`, `TestReconcileAdoptsTheSandboxOfAFinishedJob`, `TestReconcileStillAdoptsAnUntaggedSandbox`, `TestReconcileLeavesAQueuedJobsSessionAlone`, `TestReconcileSweepsTheSessionOfAJobThatHasMovedOn`, `TestReconcileLeavesALaunchInFlightUnadopted`, `TestReconcileOrphansALaunchWhoseReplicaDied` and `TestReconcilerWaitsForTheLockWhenHosted`.

## Consequences

- The reconciler reads a sandbox tag to decide, so a missing tag changes its behaviour. It already reads tags for ownership.
- A listing is at most one pass behind Modal: a sandbox that Modal started or stopped shows up within about 30 s.
- A launch whose replica dies leaves a `starting` session for up to `LaunchTimeout` plus a minute.

## Known gaps

- A duplicate session that already exists in the store is not cleaned up. Deleting it by hand terminates the shared sandbox if the job is still live.
- An interactive launch is guarded by name only, which is correct there because the session is named after its sandbox.
