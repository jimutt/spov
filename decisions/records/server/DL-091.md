## Context

A local `spov serve` runs on the memory store and exits after a minute with nothing to do. DL-003 chose that: local mode persists nothing, and Modal's tags are the only record that survives a restart. DL-017 accepts the consequence that a local server's conversations go with it. Resume (DL-087) therefore needed a Postgres server, and so did exit snapshots (DL-084). Local resume was left as a follow-up, agreed on 2026-11-06.

The two tools spov sits beside keep their history like this (looked at on this machine, 2026-11-06):

- **OpenCode 2** keeps one SQLite database, `$XDG_DATA_HOME/opencode/opencode.db`, in WAL mode. It has an append-only `event` table keyed by `(aggregate_id, seq)` and a `session_message` table with a JSON `data` column.
- **Claude Code** keeps one append-only JSONL file per session, `~/.claude/projects/<escaped-cwd>/<session-id>.jsonl`. Each line is a typed record (`type`, `uuid`, `parentUuid`, `timestamp`, `version`). Large tool output sits in a directory beside the file, files are mode 0600, and transcripts are cleaned up after 30 days by default.

DL-003 rejected a SQLite store for local mode because it would fork the schema under sqlc for a mode that needed only live state. That reason still holds.

## Decision

A local server keeps its sessions in a journal under `$XDG_DATA_HOME/spov/sessions/` (`~/.local/share/spov/sessions/` by default). The format is DL-092's and the retention DL-093's.

**The engine stays the memory store.** The journal is written by the memory store itself. Each committed write emits the stored rows to a sink: a session's row and its runs, a conversation, a message, an event. A write inside a transaction emits only when the transaction commits. At start, `store.OpenJournal` reads every session's files back into the memory store, rows and indexes exactly as they were (IDs, event positions, times), before the server serves anything. The memory store's contract suite still holds, and the journal is tested against it: a store reopened from its journal must answer the same reads.

**What is kept.** Sessions with their runs, conversations, messages and events. Not kept:

- mints and the message limiter, which only bound rates;
- the sealed proxy CA, since every run makes a new one (DL-087);
- the Sync bundle, which is never serialised (`json:"-"`).

There are no users, tokens or jobs in local mode.

**One writer.** The server holds an exclusive `flock` on `sessions/.lock` for its whole life. A second server waits up to 5 s for the lock, which covers a server of another build being stopped and a new one started (DL-023), then refuses to start, naming the directory.

**A write that cannot be journalled** (disk full, say) is already in memory and is not undone. The server warns once per run of failures and keeps serving; what was lost is lost only from the next start.

**What follows.** A local server whose sessions are journalled is persistent (`Deps.Persistent`), so DL-087's resume and DL-084's exit snapshots apply to it on the same terms as a Postgres server. The condition "the server keeps its sessions in Postgres" in DL-084 and DL-087 becomes "in Postgres or in the local journal". A local listing shows stopped sessions across restarts, paged as DL-012 pages them.

## Rationale

The memory store already answers every query a local server needs, with the indexes DL-071 tuned. Making it durable keeps one engine and one contract, where a third store implementation would fork both. An append-only log per session is the convention both neighbouring tools' users already know. It is readable with `jq` and `grep`, removable a session at a time, and survives a crash with at most a torn last line.

The lock is what makes an append-only file safe: two writers would interleave lines and replay them as one history.

## Consequences

- DL-003's "local mode persists nothing" no longer holds for sessions. Its rejection of SQLite does, and is the reason for this shape.
- Start-up reads every kept session, which the 30-day retention bounds (DL-093). A history too large to load quickly is a reason to revisit, measured with the long-conversation fixture (DL-070).
- Tests must never journal into a real home. The journal opens only from `spov serve --local`'s own wiring, and every CLI fixture sets `XDG_DATA_HOME`.
