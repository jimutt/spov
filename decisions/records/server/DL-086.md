## Context

Modal keeps an exit snapshot for 30 days and publishes no storage price for it (DL-084). Every interactive session on a hosted server under the proxy leaves one behind. Kept until Modal's own expiry, a busy deployment would hold a month of images nobody will resume.

## Decision

Three server-only settings (DL-026): the server's user file and `SPOV_*`, never a project file. They are added to DL-026's table of keys a project file cannot set.

| key | env | default | meaning |
|---|---|---|---|
| `snapshots.enabled` | `SPOV_SNAPSHOTS_ENABLED` | `true` | off means no sandbox gets an exit snapshot (DL-084) |
| `snapshots.retention` | `SPOV_SNAPSHOTS_RETENTION` | `168h` | how long after its run ended a snapshot is kept |
| `snapshots.max_per_user` | `SPOV_SNAPSHOTS_MAX_PER_USER` | `20` | how many kept snapshots one user may have; `0` means no cap |

A retention over 720h (Modal's 30 days) or under 1h is refused at startup, as is a negative cap. A server on the memory store takes none (DL-084), whatever these say.

`Service.PruneSnapshots` runs daily where the reconciler runs, beside `RunImagePrune` (DL-016), and after each snapshot is kept. It marks `deleted` on:

- every kept snapshot whose run ended longer than the retention ago;
- each user's kept snapshots beyond the cap, oldest `ended_at` first;
- a superseded snapshot: once a later run of the same session that reached `running` has its own kept snapshot, the earlier one is pruned. A run that never reached `running` prunes no earlier snapshot (DL-085). S-SR1 showed a later generation boots after the earlier one is deleted.

Then it deletes each marked image from Modal. A delete that fails is retried on the next pass; the run stays `deleted` in the store either way, so it is never booted.

Turning snapshots off stops new ones. It does not delete those already kept, which age out under the retention.

Pruning counts go in `spov_snapshot_prunes_total{reason}`, with reason `retention`, `cap`, `superseded` or `unused`, documented in `docs/metrics.md` (DL-011).

## Rationale

Deployment config only, as agreed: an operator pays Modal's bill, and a per-user setting would add a layer with no one asking for it.

Marking before deleting follows DL-016, so a crash between the two never leaves a run pointing at a deleted image. Pruning a superseded snapshot keeps the count to one per session in the common case, so the cap mostly counts sessions.

## Consequences

- `docs/configuration.md` documents the three keys, and the configuration sample test covers them.
- The cap can prune a snapshot before its retention ends, so the date a page shows is "at the latest" (DL-088, DL-090).
