## Context

A hosted spov needs a way for people to sign in from a browser. The sign-in has to name who may use the server, who may administer it, and it has to take effect on every replica. GitHub has no OpenID Connect discovery or ID tokens for this, and the one rule that matters for an allowlist is that only an e-mail address which is both `primary` and `verified` can be trusted. GitHub lets anyone add an unverified address to an account, so that rule separates an allowlist from an open door.

## Decision

### Web login

Login is GitHub OAuth, the authorization-code grant with PKCE S256 and a `state` nonce, through `golang.org/x/oauth2` directly. A back-channel code exchange over TLS already authenticates the provider, so no OIDC library is used. Only GitHub is supported. The scope is `read:user user:email`. After the exchange the server calls `GET /user` and `GET /user/emails` and accepts only an address that is both primary and verified. Anything else fails with a page that says why.

Login is optional and off by default. `SPOV_GITHUB_OAUTH_CLIENT_ID` and `SPOV_GITHUB_OAUTH_CLIENT_SECRET` configure it. Without them the API runs on bearer tokens alone. Half a credential, or an OAuth app without `SPOV_DATABASE_URL` or `SPOV_PUBLIC_URL`, is refused at startup and does not fail at the first login. With login off the login paths are not routed and fall through to the authenticated API, so `/login` answers 401. Local mode wires none of this and uses `LocalAuthenticator` only (see DL-006).

Routes outside `/api/v1/`, unauthenticated by construction:

- `GET /login` starts the flow. `?next=` is restricted to a path on this server, and `safeNext` drops anything else, such as an absolute URL or a `//host` form, rather than correcting it.
- `GET /oauth/github/callback` completes it.
- `POST /logout` destroys the current session.

There is no login page in the server. `/login` redirects straight to GitHub, and a failed login shows an error page. The web app owns the rest.

The `state` and the PKCE verifier live in a short-lived session whose deadline is `FlowLifetime` (15 minutes), not the session lifetime. `/login` is unauthenticated, so anyone who can reach it writes a row per request, and at 7 days those rows would pile up. A completed login resets the deadline to the full lifetime.

Users are created on the first allowed login, in the single `default` organisation. Their e-mail, name, GitHub login, and git name and e-mail are initialised from the GitHub profile, and the git identity can be changed later. The principal is `{UserID, OrgID: default, Email, Admin}`. A user whose GitHub primary e-mail changes becomes a new user, unless an administrator edits the allowlist.

### Sessions

Sessions use `scs` with `pgxstore`: lifetime 7 days, idle timeout 24 h, cookie `spov_session` with `HttpOnly; SameSite=Lax; Path=/`. The cookie value is an opaque scs token and nothing is signed, so a server-side session is revoked with a `DELETE`. The table is named `web_sessions`, and `pgxstore.NewWithConfig` is used for that. pgxstore's default table name is `sessions`, which is spov's own table in the same schema. `Secure` follows the public origin's scheme, and the server warns when it is off. A deployment on plain http would otherwise set a cookie the browser never sends back. The session carries only the user ID. The identity and the allowlist are read again on every request.

`CookieAuthenticator` resolves the cookie through scs, loads the user, re-checks the allowlist and returns the principal. It returns `ErrUnauthenticated` when there is no cookie. The hosted chain is `Chain(Cookie, Token, shared bearer)`, and the browser guard runs before all of them.

`GET /api/v1/me/sessions` lists a user's logins, and `DELETE /api/v1/me/sessions/{id}` revokes one. A session is identified by a 12-character prefix of its token. Someone else's session answers 404 and not 403, because the handle is unguessable and "not yours" would confirm it exists.

The browser guard has one cross-site exemption for this flow. `BrowserGuard.AllowCrossSiteNavigation(path)` exempts one path, for `GET` only, from the `Sec-Fetch-Site` and `Origin` checks. GitHub redirects the browser to the callback as a top-level cross-site navigation, and without the exemption every real browser login is refused with 403. The `Host` check still applies, and the callback's own `state` nonce is the CSRF defence the exemption relies on.

Every hosted server traps SIGHUP, including one with no login configured. Go's default action for SIGHUP ends the process, and an operator sending the reload signal has no reason to expect that. The handler only logs that the allowlist lives in the database. Local mode does not trap it.

### The allowlist

The allowlist lives in the store: `allowlist_entries`, with an organisation-scoped e-mail key, an `admin` flag and `created_at`. E-mail comparison is case-insensitive, and an address is validated and limited to 254 characters (RFC 5321). A partial index on the admin entries serves the admin count. It is the only thing that says who may log in and who is an administrator.

- **Checked twice.** The allowlist is checked at login and on every authenticated request, so removing an entry locks the user out on their next request and not at session expiry. `Principal.Admin` comes from the allowlist and not from the stored user row.
- **Admin API.** `GET /api/v1/allowlist`, `PUT /api/v1/allowlist/{email}` (body `{"admin": bool}`, an upsert) and `DELETE /api/v1/allowlist/{email}`, all behind `requireAdmin`. Deleting an entry also deletes that user's web sessions from whichever replica handles it (`Login.RevokeSessions(orgID, email)`). The endpoints are registered unconditionally, so the OpenAPI document does not depend on configuration, and refuse at request time. Management is by API.
- **Cache.** Each replica holds a cached copy, refreshed every 10 s (`AllowlistRefresh`) and swapped atomically, with no I/O and no lock per request. A removal takes effect on every replica within that interval. For an open SSE stream the bound is the stream lifetime (5 minutes), because the cookie is checked when the stream opens, so the composed guarantee is the lifetime plus the refresh interval. Login reads through the cache (`Allowlist.Live`) and updates it, so a user added seconds ago is not turned away at their first login.
- **Reads.** An empty read is applied. A failed read keeps the previous list, so a database blip does not log everyone out. Keeping the list on an empty answer would make the last entry impossible to remove.
- **Never zero admins.** No operation may leave the organisation without an administrator. Self-demotion and self-deletion are refused, and so is any change whose result is zero admin entries (`guardLastAdmin`).
- **Seed.** `SPOV_ALLOWLIST_FILE` (default `/etc/spov/allowlist`) is a first-boot seed with one entry per line, `email` or `email admin`, `#` comments. At startup, when the organisation has no administrator entry, the file is imported (`SeedAllowlist`) and the server logs that from then on the file is ignored. This is the break-glass path too, because it runs whenever there is no admin entry and not only when the table is empty. The import takes an advisory lock and upserts, so replicas that start together converge. The file is parsed strictly: a line that is neither an address nor `address admin` is an error naming its line number, the address must be a plain address, a repeated address takes the widest privilege it was given so an admin line is not undone by a later plain one, and a directory where the file should be (what a bind mount with a missing source leaves) is named as such. A file that allows nobody, or cannot be read, is fatal at a first boot (empty table) and a loud warning otherwise. A file that allows people but names no administrator is announced, not refused, and its seed runs again on each boot.

### Locking

`CountAdmins` takes `pg_advisory_xact_lock(hashtext(org_id), hashtext('spov:allowlist'))` when it is called inside a transaction and skips the lock outside one, where it would release immediately. It has the same shape as `SessionStore.CountLive` for quotas (see DL-009). The guard and the seed both start by counting admins, and `count(*)` takes no row locks, so both need the lock.

A mutating transaction counts admins before it reads the entry it is about to change. Taking the lock first serialises the read as well as the count. Folding the count into the guard, which is reached only once the entry has turned out to be an admin, leaves the read outside the lock. A promotion that commits between the read and the write could then let an entry be demoted without passing the guard, and three concurrent operations would reach zero admins. The memory store cannot show this, because it serialises everything on one mutex.

### Who may call the API

`requireAllowlist` refuses a caller who is not an administrator, a server with no login, and a caller from another organisation. The shared bearer token resolves to organisation `local` while logins live in `default`. Scoping to the caller's organisation would answer `200 {"entries":[]}` to an operator, `200` to a grant that lets nobody in, and `404` to the removal of an address that is allowed, all silently. The refusal names `spov login`'s per-user token as the credential that works.

`requireLiveAdmin` re-reads the caller's own entry from the store inside the lock-holding transaction. `Principal.Admin` comes from the cached list, so a just-removed admin would otherwise keep admin rights for up to a refresh interval on every replica but the one that served the change. For a read that bound is the point. For a write it is not, because promoting an address has no last-admin guard, and a removed admin could put themselves back for good. This makes `guardLastAdmin`'s zero-admin rule unreachable through the API, since the caller is provably an admin and the target provably someone else. The rule is kept and tested directly.

Admin rights come only from the allowlist. `admin` is not accepted in the body of `PATCH /api/v1/users/{id}`, and Huma refuses the unknown property so an old client is told. The endpoint stays for its quota half. `UserView.Admin` reports the allowlist (the cached copy), not `users.admin`. `store.User.Admin` is still written at login and nothing reads it except local mode, so do not trust it in SQL.

`toHumaError` passes a `huma.StatusError` through ahead of its sentinel mapping. Without that, a refusal raised inside `Store.Tx` was reported as a 502 (see DL-005).

## Rationale

- Server-side sessions make revocation a `DELETE`. Signed cookies would need a denylist that is the same table with extra steps.
- One organisation with `org_id` everywhere means role-based access later is rows and a UI and not a migration.
- A cache refreshed on a timer gives a bounded lockout on every replica without a signal that reaches only one process, and keeps the no-I/O-per-request property.
- Seeding once from a file keeps the bootstrap story simple without leaving two writable sources of truth.

## Measurements

- **Browser headers.** Neither Go's `http.Client` nor curl sends `Sec-Fetch-*` headers, so the test suite and the smoke script passed against a login that could never work in a browser: every real login was refused 403 without the callback exemption. Tests and the smoke script send the headers.
- **SIGHUP.** In a container, a hosted server without login configured exited with status 2 on SIGHUP.
- **Library versions.** `golang.org/x/oauth2` v0.36.0 and `alexedwards/scs/v2` v2.9.0 when the login was built. `scs/pgxstore` is an untagged module, pinned to an exact pseudo-version in `go.mod`.
- **Concurrency guards.** `TestTheOrgCannotBeRacedIntoHavingNoAdmin` and `TestConcurrentSeedersConverge` run against real Postgres and hold the transaction open past the count so that every racer reads before any writes. `TestTheAdminCountIsTakenBeforeTheEntryIsRead` pins the ordering, and the live-admin check and the organisation check were each confirmed by removing them. Re-run: `go test -tags integration ./internal/store/postgres/ -run 'Allowlist|Seeders|NoAdmin'` with `SPOV_TEST_DATABASE_URL` set, and `go test ./internal/server/ -run TestTheAdminCountIsTakenBeforeTheEntryIsRead`.

## Consequences

- `SPOV_ALLOWLIST_FILE` seeds a new deployment and is ignored afterwards. The allowlist survives restarts, is the same on every replica, and does not depend on a process signal.
- `internal/store/postgres/allowlist.go` is in `scripts/coverage-exclude.txt` as a thin pgx adapter whose behaviour is the storetest contract against a real database.
- The two disabled-login behaviours differ on purpose: `/login` answers 401 with login off, and the allowlist API refuses at request time.

## Known gaps

- Listing and revoking a user's web sessions decode every live session, because `scs.Iterate` has no by-user query. That is acceptable while the allowlist is short. The fix is a `user_id` column and a query of spov's own.
- An administrator cannot revoke another user's sessions by e-mail except by removing their allowlist entry.
- A user whose primary e-mail changes at GitHub becomes a new user.
- Adding Google would take another `oauth2.Config`, a callback route and a check of the `email_verified` claim.
