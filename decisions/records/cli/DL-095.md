## Context

DL-027 made local sync opt-in. Without `--sync` or `sandbox.sync: true`, a plain `spov fly` takes its repositories from `--repo`, then the configured `repos` list, then an interactive picker, and clones the remote's default branch. That is what a first-time user meets: run from inside the project they want to work on, `spov fly` asks which repository they mean. Then the sandbox's work is lost on exit unless the agent pushed it. Trying the first release (v0.1.0-rc.1) showed that the expected first run is the opposite: `spov fly` in a checkout works on that checkout, and what the agent did comes back to it.

DL-027's synced launch already does this; it is only off by default.

## Decision

This amends DL-027's switches. Sync gains an automatic mode, the default, and the rest of DL-027 (preconditions, remote resolution, seed, export, landing, sync before terminate) applies unchanged to a launch that syncs, however it was switched on.

### Which repository a plain `spov fly` launches

Without `--sync` or `--no-sync`, `spov fly` picks its repositories in this order. The first that applies wins:

1. **`--repo` flags.** The named repositories, unsynced. A launch that names its repositories is never synced automatically, even when one of them is the checkout's; `--sync` still syncs it, under DL-027's rules.
2. **A `repos` list from a project file** (`.spov.yaml`). A project that lists its repositories is asking for that session, so it wins over the checkout. Unsynced.
3. **The checkout of the working directory**, synced: auto sync. The repository and its platform are resolved as DL-027's synced launch resolves them (`resolveSyncLaunch`), including DL-066's error when several platforms match.
4. **A `repos` list from the user file**, unsynced. A user-level list is a general default, and the checkout is more specific.
5. **The picker**, unsynced.

Step 3 applies only when the working directory is inside a git checkout. Outside one, the order goes from step 2 to step 4 without a note, as `spov fly` behaves today.

### Auto sync's preconditions

Auto sync has DL-027's preconditions: a clean checkout, `HEAD` on a branch, the branch with a commit. When one fails, `spov fly` stops before contacting the server and says what to do: commit or stash the changes (or check out a branch), or pass `--no-sync` to launch without the checkout. It does not fall back to an unsynced launch, because a launch that quietly stops syncing loses the agent's work on exit.

The same holds for every later step of a synced launch that can fail (DL-066's several-platforms error, a history over the bundle limit, unpushed commits that cannot be bundled): the error says that sync was automatic and names `--no-sync`. DL-066's advice to pass `--repo <platform>:owner/name` adds `--sync` in this mode, since `--repo` alone launches unsynced.

Step 3 applies whenever git can see a working tree. A directory is outside a checkout only when git answers "not a git repository", or when git is not installed. A checkout git refuses to read (an unsafe owner, a corrupt `.git`) is inside one, so the launch fails with git's own message instead of silently skipping to step 4.

A checkout whose remote matches no configured platform, or that has no remote, launches in DL-027's local-bundle mode, as `fly --sync` does. The launch prints a note that the sandbox has no `origin` and cannot push, and that the work comes back on exit.

### The switches

- `--sync` is explicit sync, unchanged from DL-027: outside a checkout it fails, and a `--repo` naming another repository is refused.
- `--no-sync` turns sync off; the order above then skips step 3. An explicit `--sync=false` is the same as `--no-sync`.
- `sandbox.sync` becomes three-valued. Unset is automatic (the order above). `true` is always, as `--sync`. `false` is off, as `--no-sync`. A flag beats the config. `SPOV_SANDBOX_SYNC` sets it as before. `spov config show` prints an unset value as `null`, which loads back as unset.
- `spov attach --sync` and `spov stop --sync` are unchanged: they stay explicit.

Jobs are unaffected; they never sync (DL-027).

## Rationale

- The working directory is the strongest signal of what a person running `spov fly` wants, and DL-027 already handles everything a synced launch needs.
- Refusing a dirty checkout keeps auto sync as safe as explicit sync. A fallback to an unsynced launch would look like it worked, then discard the agent's work on exit.
- A project file's `repos` list is the project's own statement about its sessions, so it outranks the checkout. A user file's list is not about this checkout.
- Keeping `--repo` launches unsynced means naming repositories never changes behaviour because of where the command happens to run.

## Consequences

- A first `spov fly` in a project needs no flags and no config beyond a platform. Its work comes back to the checkout when the TUI exits, and the sandbox is terminated only after the work has been copied back.
- `spov fly` in a checkout with uncommitted changes now fails until they are committed or stashed, or `--no-sync` is given. Before, it launched an unsynced session.
- A user who set `repos` in their user file and runs `fly` inside a checkout now gets the checkout. Running outside a checkout, or setting `sandbox.sync: false`, gives the list back.
- The config loader has to say whether `repos` came from the project file, which it does not record today.
- More sessions are synced, so a synced session's resume matters more. A resume from the exit snapshot is not seeded again: the snapshot holds the branch as the session left it, and the seed's `checkout -B` would reset it to the launch's base and drop the sandbox's own commits (found in a live test). A transcript resume still seeds its fresh clone, which fails when the base commit was never pushed, since the seed's bundle is not stored (DL-027).
