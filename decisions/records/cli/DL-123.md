## Context

Getting from an installed binary to a first `spov fly` takes five separate steps today, each from the README: sign in to Modal, write a `platforms` entry by hand, opt into gh's login, store a model key, build the sandbox image. Each is a different command, one is a hand-written YAML file, and a missed step shows up only as a failed launch.

Agreed with the user on 2026-11-11: one friendly command that makes sure you are ready to go. The first iteration is GitHub only and assumes the `gh` CLI; other forges are left to the commands they have.

## Decision

### The command

`spov init` is a new top-level command. It walks a fixed list of steps for a **local** setup. Each step first checks; a step that is already satisfied is one ticked line and asks nothing. A step that is not satisfied explains in one or two sentences what is missing and why spov needs it, then offers to fix it (DL-124). Running `spov init` again is always safe: it never redoes or overwrites a satisfied step.

The steps, in this order, because each later one needs the earlier:

1. **Modal.** Satisfied when `credentials.ResolveModal` finds `MODAL_TOKEN_ID`/`MODAL_TOKEN_SECRET` or `~/.modal.toml`.
2. **GitHub.** Satisfied when the user config has a platform of kind `github` whose stored credential exists (gh's login marker, a GitHub App or anything else `spov credentials` holds for it). A setup that already has a GitHub App is left alone.
3. **A model.** Satisfied when a provider key is exported or stored for any provider in the catalogue (`prep.ProviderKeyEnvs`), or the OpenCode sign-in is held locally.
4. **The OpenCode client.** Satisfied when `Env.locateBinary` finds a client the pin accepts (DL-035's grading: a note or a warning still passes, a refusal does not). This step is advisory: it never blocks the ones after it, since `spov fly --web` and jobs need no local client.
5. **The sandbox image.** Satisfied when the provider says the base image for the pinned OpenCode version is published (`HasImage`). It needs step 1.

A step that depends on an unsatisfied earlier step is shown as waiting, with the step it waits for, and is not attempted.

### The end

When every required step (1, 2, 3 and 5) is satisfied, init ends with what to run next: `cd` into a checkout and `spov fly`, and `spov fly --repo owner/name` from anywhere else. It names the repository when it runs inside a checkout whose remote is on GitHub. Otherwise it ends with the list of what is still missing and exits 1.

### Reading only

`spov init --check` runs every check and changes nothing: no prompt, no file written, no program started. It prints the same list and exits 0 when the setup is ready and 1 when a required step is not. A run whose stdin or stdout is not a terminal behaves as `--check`, and says so on stderr, so init never blocks a script.

`--json` goes with `--check` (or a non-terminal run) and prints one document and nothing else on stdout: `{ready, steps: [{name, ok, required, detail, fix}]}`, where `fix` is the command that would satisfy the step.

### Not for a hosted server

With a hosted server configured (`Env.hostedServer`), `spov init` does not run the local steps: Modal, the image and the keys are the server's. It says which server is configured, whether the CLI is signed in to it, and names `spov login` and `spov credentials add`, then exits 0 when signed in and 1 when not. A guided hosted setup is out of scope.

### Presentation

Plain lines, not a full-screen view: a numbered heading per step, a tick, a cross or a dash for its state (with words, never colour alone), and the prompts of DL-124. Colour follows the terminal as the launch view's does. Nothing is cleared or redrawn, so the output can be scrolled back and pasted into an issue.

### Scope

GitHub through `gh` only. Forgejo, Gitea and GitLab keep `spov credentials add`; init's GitHub step says so in one line when the config already has a platform of another kind, and counts only GitHub. A GitHub App is not set up by init. Sandbox templates, add-ons and egress are not part of it.

## Rationale

A checklist that checks before it acts can be run at any time: after a fresh install, after a new machine, or when a launch failed and the user wants to know what is wrong. That makes one command both the wizard and the doctor, and `--check` is the same code with the fixes switched off.

Plain lines were chosen over a bubbletea view because two of the fixes hand the terminal to another program (`modal setup`, `gh auth login`), a pasted secret needs a no-echo prompt, and the image build prints for minutes. A scrolling transcript survives all three.

The order follows what depends on what, and puts the two sign-ins a newcomer most likely lacks first, so the long image build comes last, when nothing else can fail.

## Consequences

- A sixth way to reach each fix exists beside the commands themselves; init calls their functions and must not grow its own copies of their rules.
- "Ready" is defined in one place (`initSteps`), which the README and the first-run hints (DL-125) can point at.
- Other forges get no wizard yet; a user of one runs init for Modal, the model and the image, and `spov credentials add` for the forge.

## Implementation notes

- `internal/cli/init.go`: the steps as a slice of `{name, required, check, fix}`; `check` returns a state and a detail line and takes no input. Tests drive it through `Env`'s seams (`Environ`, `Credentials`, `GhToken`, `LocateBinary`, `Provider`, `Confirm`, `PromptSecret`), with no real Modal, gh or network.
- Add `init` to `TestRootHasNoUnexpectedCommands` and `--json` to `TestTheReadAndCreateCommandsTakeJSON`.
- Tests: a ready setup prints five ticks and asks nothing; `--check` writes nothing and exits 1 when a required step is missing; a non-terminal run is a check; the image step waits for Modal; a missing client does not fail the run; a hosted server skips the local steps.
