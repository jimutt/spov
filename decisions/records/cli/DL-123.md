## Context

Getting from an installed binary to a first `spov fly` takes five separate steps today, each from the README: sign in to Modal, write a `platforms` entry by hand, opt into gh's login, store a model key, build the sandbox image. Each is a different command, one is a hand-written YAML file, and a missed step shows up late, as a server that will not start or a launch that fails.

Agreed with the user on 2026-11-11: one friendly command that makes sure you are ready to go. The first iteration is GitHub only and assumes the `gh` CLI; other forges are left to the commands they have.

## Decision

### The command

`spov init` is a new top-level command. It walks a fixed list of steps for a **local** setup. Each step first checks; a step that is already satisfied is one ticked line and asks nothing. A step that is not satisfied explains in one or two sentences what is missing and what does not work without it, then offers to fix it (DL-124). Running `spov init` again is always safe: it never redoes or overwrites a satisfied step.

### It reads configuration as the local server does

Every step reads the user file and the environment only, never a project file (`Env.ServerConfig`, which is what `spov serve` sets). The local server ignores a project file's `opencode` and `modal` keys, so an init run inside a checkout that reads them would check, and build, an image the server will never ask for.

### The steps

In this order, because each later one needs the earlier:

1. **Modal.** Satisfied when Modal accepts this machine's credentials, which is checked by building the provider (`Env.provider`), an authenticated call. What spov itself finds (`credentials.ResolveModal`: both `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET`, or the file at `MODAL_CONFIG_PATH` or `~/.modal.toml`) only words the result: with nothing found at all the step is missing without asking Modal, and otherwise Modal's own client decides, since it reads more than spov looks at. Credentials that are found and refused are reported as that. With either variable set no sign-in is offered, since the environment would still win.
2. **A git platform.** Satisfied when the user config has at least one platform whose credential resolves now: a stored token, a GitHub App, or gh's login marker for which `gh` answers (`Env.ghToken`). A marker for a `gh` that is missing or signed out does not satisfy it. Any kind counts, so a working Forgejo or GitLab setup is ready; only GitHub through gh is *set up* by init. The explanation says what is lost without one: a session is seeded from the checkout and cannot push or open a pull request.
3. **A model.** Satisfied when a provider key is exported or stored for any provider in the catalogue (`prep.ProviderKeyEnvs`), or the OpenCode sign-in is held and usable. The sign-in is read from this machine's credential store through one helper beside `LocalConsoleStore` that answers only yes or no (a grant that needs reconnecting is a no); the grant's contents never reach init.
4. **The OpenCode client.** Satisfied when `Env.locateBinary` finds a client the pin accepts (DL-035's grading: a note or a warning still passes, a refusal does not). It is not required for "ready": without it the web UI still works.
5. **The sandbox image.** Satisfied when the provider says the image the local server will ask for is published (`HasImage` of `imageName(cfg)`). With `sandbox.image` set, that image is the one checked, and init never offers to build it. It needs step 1.

A step that depends on an unsatisfied earlier step is shown as waiting, naming the step it waits for, and is not attempted.

### The end

When steps 1, 2, 3 and 5 are satisfied the setup is ready. Init ends with what to run next: `spov fly` inside a checkout, and `spov fly --repo owner/name` from anywhere else. With step 4 missing it names `spov fly --web` instead, and the command that installs the client, so nobody pays for a sandbox the TUI cannot join. Otherwise it ends with the list of what is still missing and exits 1.

### Reading only

`spov init --check` runs every check and writes no file, stores nothing, asks nothing and runs no sign-in or build. It prints the same list and exits 0 when the setup is ready and 1 when it is not. The checks themselves run `gh auth token`, read the local client's version and talk to Modal, as any spov command does; building the provider creates spov's Modal app when the account has none, which is the one thing a check can leave behind.

A run whose stdin or stdout is not a terminal behaves as `--check`, and says so on stderr, so init never blocks a script.

`--json` implies `--check` and prints one document and nothing else on stdout: `{ready, steps: [{name, state, required, detail, fix}]}`, where `state` is `ok`, `missing` or `waiting` and `fix` is one line of what to run. This is init's own format, not an API view, which makes it DL-023's one exception; fields may be added, and the five step names (`modal`, `git`, `model`, `client`, `image`) are stable.

### With a hosted server

With a hosted server configured (`Env.hostedServer`), Modal, the image, the keys and the forge credentials are the server's. Init then checks two things: that the CLI is signed in to that server, and the local OpenCode client against the deployment's pin (DL-035's handshake, with its fallback). It names `spov login` and `spov credentials add`, exits 0 when signed in and 1 when not, and offers no fixes. A guided hosted setup is out of scope.

### Presentation and interruption

Plain lines, not a full-screen view: a numbered heading per step and a tick, a cross or a dash for its state, always with the word beside it, and no colour. Nothing is cleared or redrawn, so the output can be scrolled back and pasted into an issue.

A no at a question skips that step. Ctrl-C ends init with exit 130, at a question too (the prompts stop waiting when the run is interrupted), also while another program holds the terminal (DL-124); every fix is written so that an interrupt leaves nothing half-done.

### Scope

GitHub on github.com through `gh` only. Forgejo, Gitea, GitLab, GitHub Enterprise and a GitHub App keep `spov credentials add`. Sandbox templates, add-ons and egress are not part of it.

## Rationale

A checklist that checks before it acts can be run at any time: after a fresh install, on a new machine, or when a launch failed and the user wants to know what is wrong. One command is then both the wizard and the doctor, and `--check` is the same code with the fixes switched off.

Plain lines were chosen over a bubbletea view because two of the fixes hand the terminal to another program, a pasted secret needs a no-echo prompt, and the image build prints for minutes. A scrolling transcript survives all three.

Checking Modal by using it, and a gh marker by asking gh, is what makes a tick mean the next launch will get past that point. A check that only looked for a file would tick a revoked token.

## Consequences

- "Ready" is defined in one place (`initSteps`), which the README and the first-run hints (DL-125) point at.
- A check can create the Modal app. That is accepted: every launch would.
- Other forges get no wizard yet; a user of one runs init for Modal, the model and the image, and `spov credentials add` for the forge, and init then reports them ready.

## Implementation notes

- `internal/cli/init.go`: the steps as a slice of `{name, required, needs, check, fix}`; `check` returns a state and a detail line and takes no input. New seams on `Env`: `Choose(prompt, options)` beside `Confirm`, and `RunInteractive(ctx, name, args...)` (DL-124). `Env.ghToken` gains sentinel errors for "gh is not installed" and "gh is not signed in", which init words differently.
- Tests drive it through `Env`'s seams (`Environ`, `Credentials`, `GhToken`, `LocateBinary`, `Provider`, `Confirm`, `Choose`, `PromptSecret`, `RunInteractive`), with no real Modal, gh or network.
- Add `init` to `TestRootHasNoUnexpectedCommands` and to `TestTheReadAndCreateCommandsTakeJSON`.
- Tests: a ready setup prints five ticks and asks nothing; `--check` writes nothing and exits 1 when a required step is missing; a non-terminal run is a check; the image step waits for Modal; refused Modal credentials are step 1's failure; a gh marker with gh signed out is missing; a Forgejo-only setup is ready; a missing client is not a failure and changes the closing command; a project file's `opencode.version` does not change step 5; a hosted server skips the local steps.
