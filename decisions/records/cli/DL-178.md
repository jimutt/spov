## Context

The CLI receives a sync-back as a JSON object, decodes the base64 into memory, and `git.ApplySync` reads the bundle and the worktree archive as byte slices, several times over (the archive is listed, checked against the veto, unpacked and listed again for the result). At DL-177's 1 GiB that is too much to hold, and DL-176's archive arrives as a stream that may be cut off partway.

## Decision

**Reading the archive.** `client.ExportSessionSyncArchive` and `client.ExportJobSyncArchive` return the response body as a reader for a 200, and the usual `client.Error` otherwise. The request has no timeout of the client's own (streams are unbounded, as for the log); it runs under the caller's context.

**Spooling.** `git.SpoolSyncArchive(ctx, dir, r)` reads the tar into a new directory `spov-sync-<random>` (mode 0700) under the checkout's git common directory (`git rev-parse --git-common-dir`), on the checkout's own filesystem rather than a temporary directory that may be memory-backed, and returns a `git.SpooledSync` naming files. It accepts exactly DL-176's layout: `spov-sync.json` first (at most `MaxSyncMetaBytes`, `format` 1), zero-length `spov-sync-keepalive` entries, `state.bundle` and `worktree.tar.gz` only as the metadata declares them, regular files only, no other name, no repeat, a running total within `MaxSyncExportBytes`, and `spov-sync-end.json` last, whose packed sizes must equal what arrived. The end entry is the completeness check: Go's `archive/tar` reads a stream cut at a header boundary as a clean end, so nothing short of that entry counts. Anything else is a failed export and nothing is landed. A stream that ends early or breaks for any reason before the end entry (an aborted HTTP/1.1 body, a reset HTTP/2 stream, the deadline) is `ErrSyncCutShort`, with its cause, whose message says the transfer was cut short and that running the sync again is safe.

**Landing from files.** `git.ApplySync` takes a `git.SpooledSync` (`BundlePath`, `WorktreeTarPath`, with the metadata's fields) in place of `git.ExportedState`. Every reader in it (the unbundle, `archivePaths`, the in-place and fallback unpacks, `inPlaceChanges`) opens the file and streams it; none reads it whole. The fallback's temporary work tree moves under the same git common directory. `git.ExportedState`, with byte slices, stays the server's type for the JSON route; the CLI writes that route's answer into a spool directory too, so `ApplySync` has one input shape. DL-126's checks run unchanged, in the same order, before anything is written to the checkout, with DL-177's working-tree bounds read in `archivePaths`. The spool directory is removed when the landing returns, whatever its outcome; a `spov-sync-*` directory over a day old is removed at the start of the next sync-back in that checkout.

**Time.** The transfer and the spool run under `ArchiveTimeout` plus one minute (DL-176). The landing runs without a deadline once it starts: its work is bounded by DL-126's sizes, and a timer that fired mid-landing could leave git's lock files in the checkout. `verifySyncCheckout` keeps today's two-minute budget.

**Interrupting.** The sync-back runs detached from the TUI's context (DL-027), so the first Ctrl-C (or SIGTERM) after the TUI exits reaches it only through the CLI's own handler, which this decision sets; `spov jobs apply` also starts no transfer once it was interrupted during the checkout check:

- during the transfer and the spool, Ctrl-C ends them, removes the spool, lands nothing, leaves the session running and prints the same hints as a failed sync-back (sync again with `spov fly` attach and exit, or take the work with the sandbox's own `git push`);
- once the landing has begun, Ctrl-C is held until it finishes, with one line saying the sync-back is being written into the checkout; nothing ends the landing early.

**Progress.** When the metadata's measures total over 16 MiB, the CLI says so before the packed parts arrive ("Receiving 3 commits and 120 files (412 MiB)...", leaving out a count of none), and on a terminal redraws one line on stderr with the bytes received at most twice a second; off a terminal it prints only the first line. A smaller sync-back prints what it prints today.

**Older servers.** A CLI asks the archive route first. A server from before DL-176 answers an unknown path under `/api/` with the mux's plain-text 404, while a missing session or job is huma's `application/problem+json` 404, so one answer tells them apart: on a 404 that is not problem JSON, the CLI asks the JSON route, with its 32 MiB, as it did before. For a session this comes before fly's retry by name (a session a restart renamed), which then applies to whichever route answers; for a job it comes before `applyJob`'s rule that a 404 means nothing to take.

## Rationale

A spool on disk is what git needs anyway: it fetches a bundle from a file, and the landing reads the worktree archive more than once. Bounding the spool by the declared parts and the total, and requiring the end entry, turns every way a stream can go wrong into one refusal before the checkout is touched, which is DL-126's rule that the export is hostile input. The git directory is the one place known to be on the checkout's filesystem and to have room for what is about to land there.

Holding Ctrl-C only while git writes gives the user a way out of a long transfer without ever leaving a half-written checkout.

## Consequences

- At its peak a sync-back of the maximum size needs room on the checkout's filesystem for the spool (up to 1 GiB packed), the fetched objects and the unpacked files (each up to 1 GiB), so a few GiB; a full disk fails with the OS's error before the checkout is changed, or, during the unpack, with DL-126's existing handling.
- `ApplySync`'s callers and tests build spools instead of byte slices.
- A user of an old server pays one extra request per sync-back until the JSON routes are removed.
