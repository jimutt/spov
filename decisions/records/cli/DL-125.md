## Context

DL-099 made the README a first-time user's page, and its Get started section is five numbered steps with a hand-written YAML block. With `spov init` (DL-123, DL-124) most of that is one command. The errors a newcomer meets first do not name it, and two of them are misleading today: with no Modal credentials the CLI says only that the local server did not start, and the "no git platforms configured" errors tell the user to add `platforms:` to `.spov.yaml`, which a project file may not set (DL-026).

## Decision

- **The README's Get started** becomes three steps: install, `spov init`, `spov fly`. The "You need" list stays, since init cannot make accounts. What init does is described in a short list (Modal, GitHub through gh, a model, the image), and the manual commands move to a "By hand" subsection that keeps today's content for people who script their setup or use another forge.
- **The install script** (DL-080) names `spov init` as the next command in both of its endings, with and without `--with-opencode`, using the installed binary's full path when its directory is not on `PATH`.
- **`docs/sessions.md`** gains a short "First-time setup" section on init, `--check` and `--json`, and `docs/credentials.md` says init sets up GitHub through gh.
- **First-run errors.** Three situations name `spov init`, each keeping its own fix first:
  - **No Modal credentials.** Before it spawns a local server, the CLI checks `credentials.ResolveModal` (only where the provider is the real one, so a test's fake needs none); when it finds none at all (`credentials.ErrNoModalCredentials`) it refuses with that reason, `modal setup`, and `spov init`, instead of waiting for a server that cannot start.
  - **No git platform configured.** The three messages (`resolveRepoRefs`, the picker and the server's listing) name the user file, never `.spov.yaml`, and then `spov init`, except where a server is answering for its own configuration (`Env.ServerConfig`).
  - **The base image is not published.** The launch's failure names `spov serve image build` and then says `spov init` does it for a local setup; the words are the server's (`internal/server/variant.go`), the same on a local and a hosted one.
- **`spov init`'s short text** is "Check this machine is ready, and set up what is missing".
- **The troubleshooting list** in the README ("When something goes wrong") starts with `spov init --check`.

## Rationale

The quickest path should be the one the page leads with, and the manual path must stay findable because init covers only GitHub through gh. Hints are added to the errors a first run actually hits, and kept to three, so init does not become noise in every message. Checking Modal before the spawn turns a timeout that names a log file into a sentence that names the fix.

## Consequences

- `TestEveryNamedCommandExists` checks the new hints name a real command.
- A CLI command that needs the local server now fails at once without Modal credentials, where it used to wait for the spawn timeout. A command that needs no server is unaffected.
- The README's manual steps and init can drift apart; the "By hand" subsection is short and names the same commands init calls.

## Implementation notes

- README.md, docs/sessions.md, docs/credentials.md, scripts/install.sh (both endings), the spawn path in `internal/cli/localserver.go`, the platform messages in `internal/cli/select.go`, and the image failure's wording in `internal/server`.
- AGENTS.md gets a short "First-time setup" map entry naming `initSteps`, the config writer and the guard tests.
- Tests: with no Modal credentials a command that needs the local server fails without spawning, naming init; the platform messages name the user file; a server's own platform answer does not name init.
