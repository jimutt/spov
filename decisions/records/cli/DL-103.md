## Context

`spov jobs create --json` already returns the job view at once, with its `id` and `session_id` (DL-045, DL-023), so an orchestrator can record both before the job runs. What it cannot do is wait: no command blocks until a job finishes, and a script has to poll `spov jobs show --json`. spov exits 1 on any error today, so an exit code that means an outcome must not be 1.

## Decision

This amends DL-023 (the `jobs` group, and what `jobs create --json` prints).

- **`spov jobs wait <id> [--timeout d] [--json]`** blocks until the job is terminal: `succeeded`, `failed` or `cancelled` (`JobState.Terminal()`). `blocked` and `steered` are not terminal, so the wait goes on through them, as the job does.
  - It polls `GET /api/v1/jobs/{id}`, a store read that never touches a sandbox, every 5 s. `--timeout` bounds the wait; unset, it waits as long as the job runs.
  - When stderr is a terminal, it writes a line to stderr each time the job's state changes, the first read included.
  - With `--json` it prints only the final job view on stdout, as `jobs show --json` does. Without it, it prints the job's summary as `jobs show` does.
- **Exit codes**, for `jobs wait` and `jobs create --wait`:

  | Code | Meaning |
  |---|---|
  | 0 | succeeded |
  | 3 | succeeded, partly (`JobView.partial`) |
  | 4 | failed |
  | 5 | cancelled |
  | 6 | the wait timed out; the job goes on |
  | 1 | spov itself failed: a bad flag, sign-in, an unknown ID, the server unreachable |
  | 130 | interrupted (Ctrl-C); the job goes on |

  The final view is printed before a non-zero outcome code; a wait that timed out prints the last view it read. 2 is left alone, since cobra and shells use it for usage errors.
- **`spov jobs create --wait`** creates the job, prints it (with `--json`, the created job view on its own line, so the IDs come first), then waits as `jobs wait` does, with the same `--timeout` and exit codes. With `--json` the output is two JSON documents, one per line (each compact, on a single line): the created view, then the final one. A create that fails exits 1 before any wait. `--timeout` without `--wait` is refused (exit 1).
- For every job kind, not only `sync` (DL-100). For a sync job, `succeeded` is reached at delivery, so the wait returns while the sandbox is held (DL-101), and `spov jobs apply` follows (DL-102).
- Ctrl-C ends the wait and never the job, as for `attach` (DL-025).

## Rationale

- Outcome codes of their own let an orchestrator branch on what happened without parsing JSON, and never confuse a failed job with spov failing to ask. Partial success gets its own code, since a script usually treats it differently from both.
- Polling the store-backed job view reuses the read every client already makes, so a waiting script never keeps a sandbox alive (DL-018).

## Consequences

- `wait` joins the `jobs` group (DL-023), and `jobs create` gains `--wait` and `--timeout`. DL-023's statement that `jobs create --json` prints one view holds without `--wait`.
- A script that runs `create --wait --json` reads two lines. `jobs create --json` followed by `jobs wait --json` gives one each.

## Implementation notes

- `internal/cli/jobswait.go`: `newJobsWaitCmd` and `waitForJob(ctx, env, c, id, timeout, onChange func(server.JobView)) (server.JobView, error)`, which polls a job as `awaitJoinable` (`internal/cli/attachwait.go`) polls a session. `waitAndReport` prints the view and maps the result to an exit code; `createJob` calls it for `--wait`.
  - Add an `Env.JobPoll` interval (default 5 s), so tests can set milliseconds, as `Deps.StorePoll` does for the server. `Env.StderrIsTerminal` overrides the terminal check for the progress lines.
  - Terminal is `JobState.Terminal()`, which already exists (`Counts()` is its complement); no new predicate.
- Exit codes: return a typed error, exported as `cli.ExitError{Code int, Err error}` since `cmd/spov` is another package, which `exitStatus` in `cmd/spov` maps to the process's exit code. Today it exits 1 on any error; keep that for every other error. An `ExitError` with a nil `Err` prints nothing extra.
  - Map the context's cancellation from Ctrl-C to 130, and the deadline from `--timeout` to 6. A read that fails in transit or with a 5xx (other than 501) is retried up to 5 times in a row, waiting the poll interval doubled each time and capped at a minute (5 s, 10 s, 20 s, 40 s, 1 min), with a line on stderr for each; a successful read resets the count. A sixth failure in a row, or any 4xx, ends the wait with exit 1.
- `createJob`: after printing, call `waitForJob` when `--wait`, sharing `--timeout`.
- Completion for `wait` offers unfinished jobs, as the other acts do. The job ID argument completes through `completeJobs(env, true)`.
- Docs: `docs/jobs.md`'s command table, and a "From a script" section (written without the sync steps until the `sync` kind exists):
  1. `id=$(spov jobs create --json --kind sync ... | jq -r .id)`
  2. `spov jobs wait "$id" --json`
  3. branch on `$?`
  4. `spov jobs apply "$id"`
- Tests to add:
  - `TestJobsWaitExitsByOutcome` (each terminal state, partial, timeout, an unknown ID exits 1);
  - `TestJobsCreateWaitPrintsTheJobFirst` (two lines with `--json`);
  - `TestInterruptingAJobsWaitLeavesTheJobAlone`;
  - `TestTheReadAndCreateCommandsTakeJSON` gains `wait`.
