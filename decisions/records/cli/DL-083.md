## Context

The quick start asks a new user to make a GitHub token and store it with `spov credentials add github`. Most of them already have `gh` signed in on the same machine (raised 2026-11-04).

## Decision

- `spov credentials add github --from-gh` stores, in this machine's credential store, not a token but a marker that the GitHub platform's credential comes from `gh` (`platform:<name>` holds `gh:` followed by the gh host). It is refused on a hosted server, which never reads this machine's store (DL-008).
- At each launch the local server runs `gh auth token --hostname <host>` with a 5-second timeout, so a `gh auth logout` or a re-login takes effect at once, and the token is never copied into spov's store. A `gh` that is missing, logged out or slow fails the launch with that reason, never falls back to something else.
- The listing names it as `github  (gh's login for alice)`, a personal token whose origin is gh. Its reach is gh's grant (usually `repo`, often `workflow`), so it is treated exactly like a stored PAT: the proxy narrows it to the session's repositories and endpoints (DL-034), and the repository listing and git access `all` see what it reaches, which the listing says.
- Nothing picks it up silently: there is no automatic use of gh's login, and no first-run prompt in this decision.

## Rationale

Reading the token at each launch keeps gh the one owner of the credential, so revoking it in one place revokes it everywhere. Making it an explicit opt-in keeps a user from being surprised that spov reaches what gh reaches.

## Consequences

- A local quick start becomes `gh auth login` (if needed) and `spov credentials add github --from-gh`.
- Tests: `TestAGhLoginIsReadAtEachLaunch`, `TestAGhLoginIsRefusedOnAHostedServer`, `TestAMissingGhFailsTheLaunch`.
