## Context

DL-123 defines `spov init`'s steps and its read-only mode. This record says what init may do on the user's behalf to satisfy a step. Several of these touch things earlier decisions kept manual on purpose: DL-083 said nothing opts into gh's login silently and left a first-run prompt out, and the user config file has only ever been written by hand (DL-026).

## Decision

### The rule

Init changes something only in an interactive run, only for a step that is not satisfied, and only after a yes to a question that says what it will do. A no, or Ctrl-C at a question, leaves the step missing and moves on; nothing is half-done. Every fix calls the function the matching command calls, so init has no rules of its own, and after a fix the step is checked again and shown with its new state.

### Modal

Init asks to run Modal's own sign-in and hands it the terminal: the first of `modal setup`, `uvx modal setup`, `pipx run modal setup` and `python3 -m modal setup` whose program is on `PATH` (the last only when the `modal` module imports). With none available it prints the `uvx` command and the two environment variables and leaves the step missing. Init never reads, writes or asks for a Modal token itself.

### GitHub

1. gh must be installed and signed in on `github.com` (`Env.ghToken`). When gh is missing, init names its install page and leaves the step missing. When gh is not signed in, init asks to run `gh auth login --hostname github.com --git-protocol https` in the terminal, then reads the token again.
2. The account is the login gh's token belongs to, read from GitHub with that token (the check `spov credentials add` already makes). Init shows it and asks before going on.
3. **The config file.** Init adds a platform `{name: github, kind: github, account: <login>}` to the user file (`config.UserConfigPath`):
   - no file: it is created, mode `0600`, holding that entry and a comment naming `docs/configuration.md`;
   - a file with no top-level `platforms` key: the entry is appended as a new `platforms:` block, the rest of the file byte for byte as it was;
   - a file that has a `platforms` key but no GitHub platform: init does not edit it. It prints the three lines to add and leaves the step missing, since rewriting a hand-written list would lose its comments and layout.
   - a file that already has a GitHub platform: that platform is used and nothing is written.
   After a write the config is loaded again, and a file that no longer loads is restored to what it was.
4. **gh's login.** Init stores DL-083's marker for that platform (`addLocalPlatform` with `FromGh`), which verifies the token as the command does. This is the first-run prompt DL-083 left out: still opted into by the user's yes, never silently, and still local only.

Init says in one line that the sandbox gets a token narrowed to each session's repositories by the proxy (DL-034), and that a GitHub App narrows further (`docs/credentials.md`).

### A model

When no key is exported or stored and OpenCode is not signed in, init offers three choices:

- **An API key.** It lists the catalogue's providers by name with their variable, takes a choice, reads the key without echo (`Env.promptSecret`) and stores it as `spov credentials add <VAR>` does (`addLocalProvider`). The key is never a flag or an argument.
- **OpenCode Go or Zen.** It runs `runOpenCodeLogin`, the flow behind `spov login opencode`.
- **Skip.** The step stays missing, and init says the agent cannot reach a model until one is added.

A key that is exported but not stored satisfies the step as it is; init says the variable must be set wherever spov runs, and does not copy it into the store.

A local server reads keys once at its start (DL-013). When init stored a key and a local server is already running, init says that server will not see the key until it has exited, which it does by itself when idle. Init does not stop it.

### The OpenCode client

Init does not install anything. When no client the pin accepts is found it prints the install script's command with `--with-opencode` (DL-080) and what works without a client (`spov fly --web`, jobs).

### The sandbox image

Init asks to build the base image, saying it takes a few minutes and is needed once per OpenCode version, then runs the build `spov serve image build` runs (one shared function) with its progress lines. A failed or interrupted build leaves the step missing with the command to run later.

### What init never does

It never stores a Modal token, never copies gh's token into spov's store, never writes a project file, never edits a list in the user file, never installs a program, never launches a sandbox other than Modal's own image build, and never sends anything to a server other than the checks above.

## Rationale

Asking before each change keeps DL-083's promise that nothing takes gh's login silently, while removing the two steps a newcomer gets wrong most: the hand-written `platforms` entry and the `--from-gh` flag nobody knows to look for.

Appending to a file without a `platforms` key is safe to do textually; inserting into an existing list is not, and a wrong edit to the file that decides where credentials go is worse than three printed lines.

Running the vendors' own sign-ins keeps spov out of their credentials. `modal setup` and `gh auth login` are interactive and open a browser, so they need the terminal, which is another reason init prints plain lines (DL-123).

## Consequences

- The user config file gains a writer. It must stay the only one, and it only ever adds one platform.
- `spov serve image build`'s body moves into a function both commands call.
- Init's GitHub step depends on gh. A user without gh is sent to install it or to `spov credentials add github` with an App.

## Implementation notes

- `internal/cli/initfix.go` for the fixes; `internal/config` gets `AddPlatform(path, Platform)` implementing the three file cases, tested on files with comments, with and without a trailing newline, and with a `platforms` key present.
- Running an external program goes through one seam on `Env` (`RunInteractive(ctx, name, args...)`), so tests never start `modal` or `gh`.
- Tests: a no at each question changes nothing; the appended block leaves the rest of the file identical and the result loads; an existing list is not edited; the gh marker is stored and verified; a pasted key is stored and never echoed or printed; an exported key is not copied; the image build is the shared function; an interrupted fix leaves the step missing.
