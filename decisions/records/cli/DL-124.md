## Context

DL-123 defines `spov init`'s steps and its read-only mode. This record says what init may do on the user's behalf to satisfy a step. Several of these touch things earlier decisions kept manual on purpose: DL-083 said nothing opts into gh's login silently and left a first-run prompt out, and the user config file has only ever been written by hand (DL-026).

## Decision

### The rule

Init changes something only in an interactive run, only for a step that is not satisfied, and only after a yes to a question that says what it will do. A no leaves the step missing and moves on. Every fix calls the function the matching command calls, so init has no rules of its own, and after a fix the step is checked again and shown with its new state.

### Modal

Init asks to run Modal's own sign-in and hands it the terminal (`Env.RunInteractive`): the first of `modal setup`, `uvx modal setup` and `pipx run modal setup` whose program is on `PATH`. With none available it prints the `uvx` command and the two environment variables and leaves the step missing. It says the sign-in opens a browser, and that the address it prints can be opened by hand where there is none (WSL, ssh). Init never reads, writes or asks for a Modal token itself. `uvx` and `pipx run` fetch Modal's CLI into their own cache; init installs nothing itself.

### GitHub

Offered when step 2 is missing and the user config has no platform on github.com with a credential. A GitHub platform with another `base_url` (GitHub Enterprise) is out of scope and is neither used nor changed.

1. gh must be installed and signed in on `github.com` (`Env.ghToken`). When gh is not installed, init names its install page and leaves the step missing. When gh is not signed in, init asks to run `gh auth login --hostname github.com --git-protocol https` in the terminal, then reads the token again.
2. The account is the login gh's token belongs to, read from GitHub with that token. This is also the check that the token works: when the account cannot be read, the fix stops and nothing is written or stored. Init shows it and asks before going on. When gh holds several accounts, the active one is used and init says `gh auth switch` changes which.
3. **The config file.** Init adds a platform `{name: github, kind: github, account: <login>}` to the user file (`config.UserConfigPath`). It first loads the user file as `spov serve` does; a file that does not load is reported and not touched. Then:
   - no file: it is created with its directory (`0700`, file `0600`), holding that entry and a comment naming `docs/configuration.md`;
   - a file whose YAML has no top-level `platforms` key (found by parsing, so a commented-out one does not count): the entry is appended as a new `platforms:` block, the rest of the file byte for byte as it was, in the file's own line endings;
   - a file that has a `platforms` key but no platform on github.com, or that is not a plain single block-style document at column zero (a `---` marker, a flow-style root, an indented root mapping): init does not edit it. It prints the lines to add and leaves the step missing, since rewriting a hand-written list would lose its comments and layout;
   - a file that already has a platform on github.com: that platform is used and nothing is written.
   The account is written quoted, so a login that reads as a number or a boolean stays a string. The write goes through a symbolic link to the file it names, so a dotfiles setup keeps its link. After a write the cached configuration is dropped and the user file loaded again; a file that no longer loads, or loads without the platform, is restored to its bytes from before, and a file that cannot be written at all gets the lines printed instead. With no home directory and no `XDG_CONFIG_HOME` the step stops with that reason.
4. **gh's login.** Init stores DL-083's marker for that platform (`addLocalPlatform` with `FromGh`). The token was checked in step 2 by reading its account, so the command's repository-listing check is skipped: an account that reaches no repository yet is exactly who runs init. This is the first-run prompt DL-083 left out: still opted into by the user's yes, never silently, and still local only.

**What the question says.** Where the binary embeds the credential proxy, init says the token stays outside the sandbox and is used only for each session's own repositories (DL-034), and that a GitHub App narrows further (`docs/credentials.md`). Where it does not, the token would be put inside every sandbox, so init says exactly that and asks for it in a question of its own, whose default is no.

### A model

When no key is exported or stored and OpenCode is not signed in, init offers a choice (`Env.Choose`):

- **An API key.** It lists the catalogue's providers, one row per key variable, takes a choice, names where the key will be kept (`Credentials.Name()`, so a plain-file fallback is said before anything is pasted), reads the key without echo (`Env.promptSecret`) and stores it as `spov credentials add <VAR>` does (`addLocalProvider`). The key is never a flag or an argument, and init says it is stored unchecked.
- **OpenCode Go or Zen.** It runs `runOpenCodeLogin`, the flow behind `spov login opencode`; the sign-in is read at each launch, so it needs no server restart. That flow goes through the local server, which needs Modal, so the choice is offered only when step 1 is satisfied; otherwise it is listed as available once Modal is connected.
- **Skip.** The step stays missing, and init says the agent cannot reach a model until one is added.

A key that is exported but not stored satisfies the step as it is; init says the variable must be set in every shell that runs spov, and does not copy it into the store.

### A local server that is already running

A local server reads the platforms and the keys once, at its start, and exits by itself after a minute idle. When init wrote the platform or stored a key and finds a local server running (`Env.existingClient`), it stops that server when it is this build's and has no live session, saying so, so that the next command starts one that sees the change. With a live session it leaves the server alone and says the change applies once that server has exited.

### The OpenCode client

Init does not install it. When no client the pin accepts is found it prints OpenCode's own installer at the pinned version, and that `spov fly --web` works without a client.

### The sandbox image

Init asks to build the base image, saying it takes a few minutes and is needed once per OpenCode version, then runs the build `spov serve image build` runs (one shared function) with its progress lines. A failed build leaves the step missing with the command to run later.

### What init never does

It never stores a Modal token, never copies gh's token into spov's store, never writes a project file, never edits a list in the user file, never installs a program itself, never launches a sandbox other than Modal's own image build, and never changes a hosted server.

## Rationale

Asking before each change keeps DL-083's promise that nothing takes gh's login silently, while removing the two steps a newcomer gets wrong most: the hand-written `platforms` entry and the `--from-gh` flag nobody knows to look for.

Appending to a file without a `platforms` key is safe to do textually; inserting into an existing list is not, and a wrong edit to the file that decides where credentials go is worse than three printed lines.

A binary without the proxy puts the forge token in the sandbox (DL-034). One yes to "use gh's login" must not also be the yes to that, because gh's grant is usually wide.

Stopping an idle local server is safe (it would have exited within the minute) and is what makes "ready" true for the very next command.

## Consequences

- The user config file gains a writer. It must stay the only one, and it only ever adds one platform.
- `spov serve image build`'s body moves into a function both commands call.
- Init's GitHub step depends on gh. A user without gh is sent to install it, or to `spov credentials add github` with an App.

## Implementation notes

- `internal/cli/initfix.go` for the fixes; `internal/config` gets `AddPlatform(path, Platform)` implementing the file cases, tested on files with comments, with and without a trailing newline, with CRLF endings, behind a symbolic link, with a commented-out `platforms`, with a `platforms` key present, and with a document marker.
- Tests: a no at each question changes nothing; the appended block leaves the rest of the file identical and the result loads; an existing list is not edited; the gh marker is stored for the platform init wrote (the config cache is dropped); a pasted key is stored and never echoed or printed; an exported key is not copied; the sign-in choice is absent without Modal; without the proxy the gh question is asked twice and a no stores nothing; an idle local server is stopped after a change and one with a live session is not; the image build is the shared function.
