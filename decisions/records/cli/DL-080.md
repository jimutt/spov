## Context

The agreed headline install method is a script, as Claude Code's, OpenCode's and Coder's are. Two questions were left open: where the script is served from, and whether spov gets an update command.

## Decision

- **Served from the release itself.** `install.sh` is attached to every release, so `https://github.com/jimutt/spov/releases/latest/download/install.sh` is the stable URL and a pinned version has its own (`releases/download/v0.1.0/install.sh`). No website or other host is needed, and the script that installs a release is the one released with it. The docs show download-then-run first (`curl -fsSLO …; less install.sh; sh install.sh`) and the piped form beside it.
- **What it does:**
  1. Detects the platform from `uname` (Linux or macOS; amd64 or arm64). Anything else is refused. On Windows outside WSL it says spov runs in WSL.
  2. Resolves the version: `SPOV_VERSION`, else the latest release, from the `releases/latest` redirect so no API token or JSON parser is needed.
  3. Downloads the archive and `checksums.txt` to a temporary directory, and checks the archive's SHA-256 against it **before** unpacking. A mismatch, or an archive missing from the checksums, stops it.
  4. When `cosign` is on `PATH`, also verifies `checksums.txt` against its Sigstore bundle, requiring the identity of this repository's release workflow. `SPOV_REQUIRE_SIGNATURE=1` makes a missing cosign an error instead of a note.
  5. Installs `spov` to `SPOV_INSTALL_DIR`, default `~/.local/bin`, without sudo, and says how to add it to `PATH` if it is not there.
  6. With `--with-opencode`, also installs OpenCode at the pin: the deployment's (`$SPOV_SERVER/opencode-pin.json`, DL-035) when a server is configured, else the new binary's own default. It downloads the platform's npm package (`@opencode/cli-<target>`), checks it against the integrity npm publishes, and puts the binary where spov's locator looks first (`~/.local/share/spov/bin/<version>/opencode`, `Locator.ManagedPath`).
- **No update command.** Running `install.sh` again updates: it installs the version it resolves over the one there. An update command would duplicate the script's verification inside the binary, and a version notice can come later if it is wanted.
- The script is POSIX `sh`, needs only `curl` or `wget`, `tar`, and `sha256sum` or `shasum`, and is tested by running it against a fake release server (`TestInstallScript…`).

## Rationale

A release asset keeps the script and the binaries it installs from one tag, which removes a second thing to host and keep in step. Verifying before unpacking means a tampered archive never touches the disk outside a temporary directory. Fetching OpenCode at the deployment's pin removes the commonest first-run failure, a local OpenCode of another version (DL-035).

## Consequences

- The README's install section starts with the script; building from source stays below it.
- Tests: `TestInstallScriptVerifiesBeforeItUnpacks`, `TestInstallScriptPinsAVersion`, `TestInstallScriptRefusesAnUnknownPlatform`, `TestInstallScriptFetchesThePinnedOpenCode`.
