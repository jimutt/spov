## Context

A security review on 2026-11-11 (findings C-01, C-02, C-06, D-07 and D-15) found five small gaps on the user's own machine, around the CLI, sync-back (DL-027, DL-126) and the installer (DL-080).

- spov ran git in the user's checkout with whatever that checkout configures. A `core.hooksPath` or `core.fsmonitor` in the checkout's config, or a hook in its hooks directory, runs a program of the checkout's choosing on a command as ordinary as `git status`. DL-126 stops a sandbox from planting such a program; it does not stop one that is already there from running during a sync.
- A sync-back printed a count of files and said nothing about which ones, so a person could not see from spov's output what had landed in their checkout.
- The CLI printed text an agent or a sandbox wrote (a job's verdict, its error, what it left unfinished, a report's path and title, a launch note, a sync export's paths, the stderr of a sandbox command quoted in an error) with its control characters. An escape sequence in it can recolour or erase lines, forge a verdict block, set the window title or write the clipboard.
- `scripts/install.sh --with-opencode` put the pin it read from `$SPOV_SERVER/opencode-pin.json` into a download URL and a directory name unchecked, so a server that answered `2.2.5/../../other/1.0.0?x=/../../bin/2.2.5` could name another npm package for the URL and the real pin's directory for the result. `SPOV_VERSION` and the version read from the releases redirect had the same gap.
- Without cosign the script said only "cosign is not installed, so only the checksums are checked", before the checksum was checked, and `SPOV_REQUIRE_SIGNATURE=1` was not shown to be the way to a verified install.

## Decision

1. **One place git is started.** Every git process spov starts goes through `git.Command` (`internal/git/command.go`), which puts `--no-pager`, `-c core.hooksPath=/dev/null` and `-c core.fsmonitor=false` before the subcommand, sets `GIT_PAGER=cat` and `GIT_TERMINAL_PROMPT=0`, and drops `GIT_EXTERNAL_DIFF` from the environment. `/dev/null` is the form git accepts on Linux, macOS, WSL (a checkout under `/mnt/c` included) and Git for Windows. The sync seed and bundle, `ApplySync` and its fallback, `BundleCommit`, the status and checkout checks, the identity read and the checks `internal/cli` makes all go through it. An alias cannot redirect a command, because every subcommand spov runs is a built-in and git does not let an alias shadow one. The one exception is DL-126's question about the real hooks directory (`rev-parse --git-path hooks`), which would otherwise be answered with the null device; it uses the same guard without the hooks path. This extends DL-126, which keeps a sandbox from planting a program in the checkout, to the programs the checkout already names. The guard does not turn off filter drivers: the user's own (git-lfs's smudge, say) still run when the sync-back's fast-forward checks out the session's files, under the attributes the checkout already has. A session that adds or changes a `.gitattributes`, `.lfsconfig` or `.gitmodules` anywhere never lands in place (DL-126), so its attributes cannot bring a driver into play during the sync; once the user checks out `spov/<session>`, they apply as any branch's do.
2. **Sync-back says what changed.** After every sync-back (`spov fly` at exit, `spov attach --sync`, `spov stop --sync`, `spov resume`, `spov jobs apply`) the CLI prints, to stderr, the branch it landed on, the number of commits added with the short range (`from..to`, twelve characters each), and each changed (`M`), added (`A`) or deleted (`D`) path, at most 30, then `and N more`. In place, the paths are the committed difference from the checkout's old head, then the session's uncommitted files and deletions on top; on `spov/<session>` they are the difference from the session's base commit to the branch tip. Since the list is capped, a fallback's reason and a refusal's error each name the offending paths themselves, up to three and then how many more (DL-126). Hints and this listing stay on stderr, so `--json` keeps stdout clean (DL-023).
3. **Agent-written text is printed safely.** `cli.Printable` shows every C0 and C1 control character, DEL, the bidirectional embeddings, overrides and isolates, line and paragraph separators and any byte that is not UTF-8 as a visible escape (`\x1b`, `\u009b`), keeping newline and tab; CRLF reads as a newline. `printableLine` also escapes newline and tab, for one-line fields such as a path. The helper is applied to a job's note, verdict, unfinished text and goal, each deliverable line (path, title, detail, branch), the report list, a launch's notes and failure reason, the paths and branch names of a sync result, the error text `cmd/spov` prints (which quotes a sandbox's stderr), and the CLI's own warnings that quote an error. `--json` output is JSON-encoded, which escapes what is below U+0020; `encodeJSON` also writes the C1 controls, DEL and the bidirectional characters, which `encoding/json` leaves raw, as `\u` escapes. `spov jobs report` prints the report raw when stdout is not a terminal, since a script wants the bytes, and through `Printable` when it is (`Env.StdoutIsTerminal`, nil asking the terminal, as `StderrIsTerminal` does for progress lines); `--save` writes the bytes as they are.
4. **The installer checks versions.** A version is `N.N.N` with an optional `-prerelease` of letters, digits, dots and hyphens. `install.sh` refuses anything else, before it downloads anything, for `SPOV_VERSION`, the version read from the releases redirect, and the OpenCode pin however it was found (`SPOV_OPENCODE_VERSION`, the server's `opencode-pin.json`, or the new binary's own default). Build metadata (`+`) is not accepted.
5. **The installer says what it did not verify.** Without cosign the script still installs after the checksum matches, as before, and then prints one line: the checksum was verified but the signature was not, because cosign is not installed, with how to verify it (install cosign and run the script again) and that `SPOV_REQUIRE_SIGNATURE=1` refuses an unverified install. `SPOV_REQUIRE_SIGNATURE=1` without cosign fails before anything is installed and names cosign. A tampered archive never reaches the line, since its checksum fails first. The release workflow and the goreleaser configuration are unchanged.

## Rationale

A single constructor is the only guard that holds as the code grows: a new `exec.Command("git", ...)` somewhere else fails `TestEveryGitCommandIsBuiltByCommand`, and a rigged checkout whose hooks, filesystem monitor and aliases write a marker file shows that a full sync-back runs none of them. The guard is a prefix of options and not a sanitised copy of the user's config, because the user's own config (an identity, a remote) must still be read.

Printing the paths is the other half of DL-126: refusing what `git status` would not show is only useful if the person can see, at the moment it lands, what did land. The cap keeps a large sync readable and the full list stays one `git status` away.

A sanitiser at the print sites, not a wrapper on stdout and stderr, because the drawn launch view and the OpenCode TUI legitimately write escape sequences to the same streams. The terminal check on a report follows the existing notion of one for stderr, and a script that pipes a report keeps its bytes.

The installer's version shape is strict because it is the only thing between a server's answer and a path, and a hostile string has no legitimate form of that shape. Saying the signature was not verified after the checksum matched keeps the statement true: before the check it described a state that could still fail.

## Consequences

- A command that needs a hook or a filesystem monitor to run during a spov git call no longer does. spov never needs one; a user whose tooling relied on a post-checkout hook firing during a sync-back will not see it fire.
- A printed path or message may now show `\x1b` where the text held an escape. A report on a terminal that holds ANSI colour will show its escapes as text; piping it keeps the colour bytes.
- `SyncResult` gains `Changes`, `RangeFrom` and `RangeTo`, and the listing costs one `ls-tree` and one `diff --name-status` per apply.
- A version with build metadata, or any other shape, cannot be installed with `install.sh`; spov's releases do not use either.
- The installer still trusts the releases URL for the "latest" tag and does not compare against an installed version (D-15's remaining points); `SPOV_REQUIRE_SIGNATURE=1` with cosign is the checked path, and the README says so.
- Not covered: a git alias cannot be set to shadow a built-in, but a future spov command that ran a non-built-in git subcommand (`git foo` resolving to an alias or an external `git-foo`) would need its own guard.
