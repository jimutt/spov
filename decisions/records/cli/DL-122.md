## Context

Templates (DL-119, DL-120) are made in the browser. The CLI should be able to launch from one, so one definition serves both clients. A template can attach `asked` routed credentials, and DL-075 holds that a project file, which is shared, can only take credentials away.

## Decision

### Naming one

- `spov fly --template <name>` and `spov jobs create --template <name>` send `template`.
- `sandbox.template` in the user file is the default for `spov fly`, and `sandbox.job_template` for `spov jobs create`; a job never takes `sandbox.template`, as with `job_git_access` and `job_credentials`. `--no-template` launches without the configured one. `--template` and `--no-template` are mutually exclusive.
- A project file may not set either key. They join DL-026's user-only keys, and a project file that sets one is refused at load with the reason: a template can attach credentials, and a file that comes with a repository must not choose it.
- `SPOV_SANDBOX_TEMPLATE` and `SPOV_SANDBOX_JOB_TEMPLATE` work as other `SPOV_*` layers do.

### What is sent with it

The server lets a request's own field win over the template's (DL-120). So when a template is named, the CLI sends a template-covered field (`egress`, `egress_extra_domains`, `addons`, `apt`, `env`, `git_access`, `credentials`) only when a flag or a config layer set it, never a built-in default. A value from a config file is sent as it is today and wins over the template for that setting; the launch's progress, which names what the template set (DL-120), shows the result. The configuration's credential narrowing is still sent as `credentials_preferred`.

`spov resume` takes no `--template`: a resumed session uses its recorded settings.

### The group

`spov templates` is a new group (DL-023's naming: a plural noun group, as `credentials` and `jobs`):

- `spov templates list` (and bare `spov templates`): a table of name, description and summary; `--json` prints the API's listing and nothing else on stdout.
- `spov templates show <name>`: the template's settings; `--json` likewise.
- `spov templates remove <name>`.

Creating and editing stay in Settings (or the API) in this round. Completion offers template names for `--template`, `show` and `remove`, through `Env.existingClient` only.

## Rationale

The flag and the user file are the person's own; the project file is someone else's. Letting a project file name a template would let a cloned repository widen what a launch attaches, which DL-075 rules out for credentials directly.

No `templates add` yet: a command with a flag per setting duplicates the form, and the person who launches only from the CLI already has config files. The listing and `show` are enough to see what `--template` will do.

## Consequences

- `sandbox.template` is the first `sandbox` key a project file may not set, so the user-only check must work on a key inside a section a project file otherwise may set.
- `TestEveryNamedCommandExists` covers the new commands wherever a hint names them; `TestTheReadAndCreateCommandsTakeJSON` gains `templates list` and `show`.

## Implementation notes

- `internal/cli/templates.go`; the flags in `fly.go` and `jobs.go`; the keys in `internal/config` with `Sources` saying which layer set a covered field, so the CLI can leave a default unsent.
- Tests: a project file that sets `sandbox.template` is refused; `--template` is sent and `--no-template` clears the user file's; a job ignores `sandbox.template`; with a template named, a built-in default egress is not sent and a config file's is; completion never starts a server.
- Docs: `docs/configuration.md`, `docs/credentials.md`, `docs/sandbox.md`, and a README line.
