## Context

Templates (DL-119, DL-120) are made in the browser. The CLI should be able to launch from one, so one definition serves both clients. A template can attach `asked` routed credentials, and DL-075 holds that a project file, which is shared, can only take credentials away.

## Decision

### Naming one

- `spov fly --template <name>` and `spov jobs create --template <name>` send `template`.
- `sandbox.template` in the user file is the default for `spov fly`, and `sandbox.job_template` for `spov jobs create`; a job never takes `sandbox.template`, as with `job_git_access` and `job_credentials`. `--no-template` launches without the configured one. `--template` and `--no-template` are mutually exclusive. The user chose this on 2026-11-10 (flag and user file, never a project file): a name the person wrote into their own file is their explicit configuration, unlike a choice a browser would remember by itself (DL-121). A configured template that no longer exists refuses the launch with the key's name and `--no-template` as the way on.
- A project file may not set either key. They join DL-026's user-only keys, and a project file that sets one is refused at load with the reason: a template can attach credentials, and a file that comes with a repository must not choose it.
- `SPOV_SANDBOX_TEMPLATE` and `SPOV_SANDBOX_JOB_TEMPLATE` work as other `SPOV_*` layers do.

### What is sent with it

The server lets a request's own field win over the template's (DL-120). Naming a template is an explicit act, so only another explicit act may override it: when a template is named, the CLI sends a template-covered field (`egress`, `egress_extra_domains`, `addons`, `apt`, `env`, `git_access`, `credentials`) only when a flag set it (`--egress`, `--env`, `--addons`, `--git-access`, `--credentials`, `--no-credentials` and the like, by the flag's `Changed`). A value from a config file, the user's or a project's, and any built-in default, is not sent for those fields; a cloned repository's `.spov.yaml` therefore cannot widen a template's egress or replace its add-ons. When a config layer did set one of them, the CLI says once which settings the template took the place of.

Two things from the configuration still go: the credential narrowing, as `credentials_preferred`, because it can only take access away (DL-120 applies it to the template's list), and everything a template does not cover (the image, the model, timeouts, repositories). A configured `sandbox.image` with a template that names add-ons is refused by the server, naming the template (DL-120).

`spov resume` takes no `--template`: a resumed session uses its recorded settings.

### The group

`spov templates` is a new group (DL-023's naming: a plural noun group, as `credentials` and `jobs`):

- `spov templates list` (and bare `spov templates`): a table of name, description and summary; `--json` prints the API's listing and nothing else on stdout.
- `spov templates show <name>`: the template's settings, from `GET /api/v1/me/templates/{name}`; `--json` likewise.
- `spov templates remove <name>`.

Creating and editing stay in Settings (or the API) in this round. Completion offers template names for `--template`, `show` and `remove`, through `Env.existingClient` only.

## Rationale

The flag and the user file are the person's own; the project file is someone else's. Letting a project file name a template would let a cloned repository widen what a launch attaches, which DL-075 rules out for credentials directly.

No `templates add` yet: a command with a flag per setting duplicates the form, and the person who launches only from the CLI already has config files. The listing and `show` are enough to see what `--template` will do.

## Consequences

- `sandbox.template` is the first `sandbox` key a project file may not set, so the user-only check must work on a key inside a section a project file otherwise may set.
- With a template named, a user file's `sandbox.egress` or `sandbox.addons` stops applying to that launch. On a local server the same file is also the server's own defaults, which sit under the template (DL-120), so a browser launch and a CLI launch from one template resolve the same.
- `TestEveryNamedCommandExists` covers the new commands wherever a hint names them; `TestTheReadAndCreateCommandsTakeJSON` gains `templates list` and `show`.

## Implementation notes

- `internal/cli/templates.go`; the flags in `fly.go` and `jobs.go`; the two keys in `internal/config`, refused in a project file.
- Tests: a project file that sets `sandbox.template` is refused; `--template` is sent and `--no-template` clears the user file's; a job ignores `sandbox.template`; with a template named, neither a built-in default egress nor a config file's is sent and a flag's is, and the narrowing still goes; a configured template that is gone names its key; completion never starts a server.
