## Context

Git platforms, default repositories, sandbox sizing, the OpenCode version and the Modal environment must be configurable at two levels: the user's (which platforms and accounts they have) and a project's (which repositories this project bootstraps with). A project file, `.spov.yaml`, is found by walking up from the working directory, so it usually arrives with a repository somebody else wrote. Anything such a file can set is therefore set by a third party, and two kinds of key decide where a credential is sent:

- `server.url`. Every command in that clone talks to the named server and sends `SPOV_SERVER_TOKEN` to it, along with goals, repository lists and the git identity. `spov credentials add` there would send the token the user types. Shell completion (DL-023) would make a Tab press enough to trigger it.
- `platforms`. Stored tokens are keyed by platform name alone, and a later layer replaces the whole list. A project that redefines `github`, or any other stored name, with its own `base_url` would receive the user's stored token for that name on the next launch or repository listing.

A third route is `prep.base_url` and `prep.key_env`: the prep pass sends the model key they name to the base URL they name (DL-047). A server that read a project file would send the user's key wherever the project chose. The keyring token for a hosted server is not exposed through the first two, because it is stored per server URL.

## Decision

### Three layers

Configuration is merged with koanf from defaults and three layers, later overriding earlier:

1. **User:** `$XDG_CONFIG_HOME/spov/config.yaml` (`~/.config/spov/config.yaml`). It holds git platforms (name, kind, base URL, account), default sandbox resources and timeouts, the server URL and the Modal environment.
2. **Project:** `.spov.yaml` in the current directory or the nearest ancestor. It holds the repository bootstrap list (platform, owner/name and target directory), the landing repository, and sandbox and image overrides.
3. **Environment:** `SPOV_*` variables. Only scalar keys are addressable (`SPOV_SANDBOX_TIMEOUT`, `SPOV_MODAL_APP`), derived from the `Config` struct tags by `buildEnvKeys`, so the two cannot drift apart. A variable naming no field is ignored and reported, not silently merged. An empty value means unset, not set to empty. Modal credentials are not configuration: they come from the credential store or `MODAL_TOKEN_*`.

Rules that hold across layers:

- List-valued keys (`platforms`, `repos`, `addons` and the other lists) are replaced by a later layer, not merged into it, so a project's `repos` replace the user file's whole. `platforms` can only come from the user file (below), and a repository must name one of them: `Validate` reports a repository that names no platform or an unknown one.
- A platform name may contain only letters, digits, `-` and `_`, because it is the key its token is stored under.
- Unknown keys in either file are rejected, so typos surface at load time. The schema is versioned (`version: 1`) and `Validate` rejects a version it does not understand.
- Platform kinds are `github`, `forgejo`, `gitea` and `gitlab` (DL-041).
- Secrets never live in config. A platform is referenced by name and its token is resolved from credential storage (DL-008), which is what makes `.spov.yaml` safe to commit.
- `Repo.Dir` is validated as a clean workspace-relative path (no absolute path, no `..`) at the config boundary, before anything clones into it (`validWorkspaceDir`).
- `spov config show` reports the merged values with their provenance: the user file, the project file, the variables applied and the variables ignored. `config show --format yaml|json` prints it.

### What a project file cannot set

`config.Load` refuses a project file that names `server` or `platforms` at all, whatever the value. An empty or `null` section would replace the user file's in the merge just as a value would, so presence is what is refused. The error names the file and the key and says where it belongs: the user file, or `SPOV_SERVER` and `--server` for the server. Every command that loads config in that directory fails until the key is moved, including `config show`, and completion then offers nothing. A project's `repos` still name platforms, which always come from the user file, or from the environment for a scalar.

The refusal is by key and not a warning, so a hostile or mistaken file is visible at once and not run quietly with other values. Only these two keys are barred, which keeps what project files are for: repositories, the landing repository and sandbox settings.

### The server reads no project file

`spov serve`, local and hosted, reads no project file. Its configuration is the user file and the environment, through `config.LoadUser`. Session choices (sandbox size, egress preset, image, add-ons, git identity) already travel in each request. The CLI spawns the local server with the state directory as its working directory, not the clone it was run from, so a local server does not take the configuration of whichever directory first started it and keep it for every directory it later serves. A server whose configuration depends on its starting directory would be wrong even without an attacker.

Consequences for where keys go:

| Section | Read by |
|---|---|
| `repos`, `landing`, `server` | the CLI |
| `platforms` | the CLI, and `spov serve`, which resolves its deployment credentials by platform name |
| `sandbox`, `git.name`, `git.email` | the CLI, which sends them with each request; the server uses its own as defaults |
| `opencode` | the CLI, and `spov serve`, whose pin it publishes |
| `modal`, `quotas`, `prep`, `metrics`, `git.allow_all` | `spov serve` |

Server-only keys in a project file are ignored by a local server, and belong in the user file or the environment. A hosted deployment configures through the user file or `SPOV_*`, never a `.spov.yaml` in its working directory. `docs/configuration.md` is the reader's account.

### Git access stays a project choice

`sandbox.git_access` and `sandbox.job_git_access` are allowed in a project file, although `all` widens what the user's own tokens reach. With `all`, the sandbox's proxy adds the user's token to requests for every repository on each forge the user holds a token for, not only the session's (DL-043).

What this exposes: a repository the user clones from someone else can ask for `all`, and its `AGENTS.md`, which the agent is told to read, can then instruct the agent to fetch the user's other private repositories and send them out over open egress (DL-031).

What bounds it: the project file can only request `all`. `--git-access repos` on the launch overrides the file, a hosted deployment's own credential still needs the deployment's consent (`git.allow_all`), and the session page lists each credential's git access. The attack also needs the agent to follow the injected instruction.

Why it is accepted: per-project git access is a legitimate choice, and barring the setting would remove it. The remaining risk is that of running an agent on code someone else wrote, with the user's reach widened by their own request, and the user is told where the keys are and what they allow. Before launching in a repository the user did not write, they should check its `.spov.yaml` for `git_access: all`.

Guards: `TestAProjectFileCannotRedirectCredentials` and `TestAProjectFileCannotSayWhereCredentialsGo`.

## Rationale

- Where a credential goes is the user's choice, not a repository's. Refusing makes the attempt visible, and barring only two keys leaves the rest of the project file useful.
- Mirroring git and OpenCode's own global-versus-project split makes the layers familiar. YAML over JSON allows comments, and koanf makes the precedence explicit.
- Keeping secrets out of the files makes `.spov.yaml` safe to commit.

## Consequences

- Per-project platform lists are not possible. A project that needs a platform tells its users to add it to their user file.
- List replacement means a project file's `repos` replace the user file's `repos` whole. Platforms come only from the user file, so a project cannot hide or redefine one.
- A project file that names `server` or `platforms` breaks every command in its directory until fixed. That is deliberate.
- A new top-level key that decides where a credential goes belongs in `userOnly` in `load.go`.
