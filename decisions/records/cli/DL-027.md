## Context

An interactive `spov fly` session clones the remote repository's default branch into the sandbox and, on exit, terminates the sandbox. Commits and working-tree edits made in the sandbox and not pushed to the forge are lost when the session closes. A developer who works from a local checkout wants the opposite round trip: the sandbox starts from the checked-out local branch, including commits not yet pushed, and the result comes back to the local checkout.

Three constraints shape the design. The CLI is an HTTP client of the server and never calls the sandbox provider (DL-002). The sandbox entrypoint clones with `--depth 1` on the default branch (DL-041), which has not the history to check out another branch or to unbundle commits based off something other than the default tip. And a terminated sandbox's filesystem is gone, so losing unpushed agent work is unrecoverable.

## Decision

### Switches

Local sync is opt-in, for one repository, and only for interactive sessions.

- `spov fly` accepts `--sync` and `--no-sync`, which are mutually exclusive. With neither, `sandbox.sync` (`SPOV_SANDBOX_SYNC`, default `false`) decides, so a developer can make every `fly` in a checkout round-trip.
- `spov attach <ref> --sync` syncs the sandbox repository back to the current checkout when the TUI or `--web` wait exits, or immediately with `--no-tui`. It leaves the session running, as attach always does.
- `spov stop <ref> --sync` syncs back and then terminates the sandbox. It is refused with `--all`, on a job's session, on a session with more than one repository, and on a session that is not running.
- No new command is added to the tree (DL-023); `--sync` on `attach` and `stop` covers `fly --keep` and `fly --no-attach`.

Opt-in keeps the remote-only behaviour of `fly`, which works outside any checkout and across several repositories.

Sync mode takes the repository from the checkout of the working directory. A `--repo` naming another repository, or more than one `--repo`, is refused. A single `--repo` or `repos` entry that matches the checkout is allowed, and a multi-repository `repos` list in config is ignored in favour of the checkout while `--sync` is active. A synced launch always lands in the repository's workspace directory, replacing any `landing` from flags or config, so OpenCode starts in the synced checkout and not at `/workspace`; the export reads the repository from the same directory. `fly --sync` outside a git repository fails before contacting the server and names `--no-sync`.

### Preconditions and remote resolution

A synced launch is refused, before contacting the server, unless the checkout is clean (`git status --porcelain --untracked-files=normal` is empty), `HEAD` is attached to a branch (`symbolic-ref -q --short HEAD`) and the branch has a commit. Staged or unstaged changes, untracked files, an in-progress merge, rebase, cherry-pick or revert, and a detached `HEAD` all refuse it; the developer commits or stashes first. `git.InspectLocalCheckout` implements this.

The remote is `branch.<name>.remote` when set, else `origin`. Its URL (HTTPS, `ssh://`, or SCP-style `git@host:path.git`, with `.git` stripped) is parsed into host, optional base path and `owner/name` (split at the last slash, DL-041). SSH remotes therefore work locally even though the sandbox clones over HTTPS through the credential proxy (DL-034).

The host and base path are matched against the configured platforms (a platform with no `base_url` is `github.com` or `gitlab.com` by its kind). Several platforms on one host are told apart by a `repos` entry for the same repository, then by the platform whose `account` is the repository's owner. `--repo <platform>:owner/name` names the platform outright and must match the remote. If the repository has no remote, its host matches no configured platform, or no credential is available for the matching platform, the launch runs in local-bundle mode: the platform is empty, the owner is `local` (or the parsed remote owner) and the CLI packs a full bundle of `HEAD` (`git.BundleHEAD`). A `--repo` that names a platform on a checkout with no remote is refused.

### The seed

The CLI records the branch name and the `HEAD` commit as the base. It sends a `sync` seed on `POST /api/v1/sessions`:

- `branch`, validated with `git check-ref-format --branch` rules.
- `base_commit`, a 40-hex SHA.
- `bundle`, optional, a base64 git bundle. The CLI refuses a bundle over 16 MiB raw (see Known gaps for how the server counts it). `POST /api/v1/sessions` accepts a body of up to 24 MiB when a bundle is attached (`MaxSessionBodyBytes`), against 1 MiB for every other request.

When the sandbox clones from a configured platform that has a credential, the bundle holds only the unpushed commits. If a remote-tracking ref on the remote is an ancestor of `HEAD`, the CLI bundles the range from it to `HEAD`, preferring `refs/remotes/<remote>/HEAD`, then the branch's own tracking ref, then any other ancestor. It omits the bundle when `HEAD` is already the tip of the remote's tracking ref for the branch or its default branch. If no remote-tracking ancestor exists, or there is no forge credential, the bundle packs `HEAD` whole. A bundle over 16 MiB is refused, with advice to push the branch first. Cloning the base from the forge inside the sandbox and overlaying a compact bundle avoids uploading the whole object database from the developer's machine, and still supports local-only branches.

The launcher applies the seed (`applySyncSeed`) once the server reports healthy and before the launch is reported ready, by exec in the sandbox, so after the entrypoint's clone and before any conversation exists. If the base commit is not present it fetches the branch or commit from `origin`, deepening as needed. It unbundles a supplied bundle through `Handle.ExecInput`, so bundle bytes stay out of command lines, the entrypoint script and database rows. Then it runs `git checkout -B <branch> <base_commit>`. With no platform (`RepoRef.Platform == ""`) there is no remote clone, and the repository is initialised in `/workspace/<dir>` from the full bundle, with no `origin`. The same happens when the server finds no credential for the platform at launch and a bundle was sent: it notes that it is seeding from the local bundle and goes on without a clone. A seed with neither a clone nor a bundle fails the launch.

`SessionView.Sync` exposes the branch and base commit and never the bundle, so `attach --sync` and `stop --sync` know the starting point. The store keeps only the branch and base commit; the bundle goes to the launch in memory.

### Export

`POST /api/v1/sessions/{ref}/sync-export` packages the sandbox repository's state. It is authenticated as the session's owner or an admin. It is refused on a session that is not running, that has more than one repository, or that belongs to a job. It runs one script in the repository (`session.ExportSync`) and returns:

- `head_commit` and `branch`.
- `bundle`: a base64 git bundle of `<base_commit>..HEAD` when `HEAD` differs from the base, or of `HEAD` if history was rewritten past the base. A session with no recorded base uses `refs/remotes/origin/HEAD` when that is an ancestor of `HEAD`.
- `worktree_tar`: a base64 gzipped tar of modified, staged and untracked non-ignored files (`git status --porcelain=v1 -z --untracked-files=all`, so files inside new directories are listed one by one), preserving executable bits and symlinks.
- `deleted`: tracked paths deleted in the tree or index, and the old path of a rename.

The whole export is bounded to 32 MiB. It is an explicit user-initiated act, like steering (DL-019), and not a background read, so the rule that no page load reads a sandbox holds (DL-018). The route and schema fields are part of the generated API (DL-005).

### Landing locally without clobbering

`git.ApplySync` decides where the result goes.

- If the sandbox changed nothing (`head_commit` equals the base, with an empty tar and no deletions), it prints that and leaves the local repository untouched.
- **In place** when the checkout is on the starting branch, its `HEAD` is the base commit, `head_commit` itself or an ancestor of `head_commit`, and `git status` is empty. It unbundles the bundle, runs `git reset --hard <head_commit>`, unpacks `worktree_tar` onto the repository root, removes the paths in `deleted`, and prints a summary.
- **On a fallback branch** when the local state diverged: the developer switched branches, committed locally, or has uncommitted or untracked files. It never overwrites the working tree. It unbundles to a temporary ref and, if the tar or deletions are non-empty, builds one synthetic commit on top of `head_commit` using a temporary `GIT_INDEX_FILE`, with the message `spov: uncommitted changes from <session-name>`, so the real index and tree are untouched. It then updates `refs/heads/spov/<session-name>` (`spov/sync` if the session name is not a valid branch name), says why the sync did not land in place, and prints `git checkout` and `git merge` commands for it. The synthetic commit is authored by `spov`.

Tar extraction validates every entry path and rejects absolute paths, `..`, paths that escape the root and paths into `.git`. It refuses a symlink that points outside the repository or into `.git`, a path whose parent directory is a symlink, and any entry type other than regular files and symlinks, which excludes hardlinks. Re-running `attach <ref> --sync` is idempotent when the checkout already has the previous sync's commits and is clean.

### Sync before terminate

When a command both syncs and terminates (`fly --sync` without `--keep`, and `stop --sync`), sync-back runs first, and a sync failure leaves the sandbox running.

- `fly --sync` on its default exit exports the state after the TUI or `--web` wait ends and applies it locally, under `context.WithoutCancel` with a two-minute timeout, so the Ctrl-C that closed the TUI does not abort the sync. Only after the local apply succeeds does the session terminate.
- `fly --sync --keep` and `--no-attach` seed from the local branch, leave the sandbox running without syncing on exit, and print hints with `spov attach <name> --sync` and `spov stop <name> --sync`.
- `stop --sync` first checks that the checkout matches the session's repository (`verifySyncCheckout`: same remote repository, same platform host), then exports, applies and deletes the session.
- If export or the local apply fails, the sandbox is not terminated. spov prints the error, says the sandbox is still running and billing, and prints `spov stop <name> --sync` to retry, `spov attach <name> --sync`, and `spov stop <name>` to discard. When `--sync` is active, termination on TUI exit therefore depends on sync-back succeeding.

`TestEveryNamedCommandExists` covers the `--sync` hints (DL-023).

## Rationale

- Unpushed commits and working-tree edits are the work most likely to be lost, and a round trip through the developer's own branch is where they are wanted.
- Sync on the server keeps the HTTP client boundary and works the same against a local server and a hosted one. `ExecInput` carries binary payloads without putting them in argv.
- Landing in place matches what a developer waiting in the TUI expects when quitting. Landing on `spov/<session-name>` after parallel local work guarantees nothing is lost on either side.
- A failed sync must not be followed by a termination, because the sandbox is the only copy of the work.

## Consequences

- Uncommitted local work must be committed or stashed before `fly --sync`.
- The sandbox keeps billing while it runs, including after a failed sync, until the developer retries or stops it.
- Two payload bounds apply: 16 MiB for the seed bundle and 32 MiB for the export. A larger history or a larger set of edits is refused, not truncated.
- Sync does not apply to jobs, which deliver through pull requests and reports (DL-051).

## Known gaps

- The CLI bounds the seed bundle at 16 MiB raw, but the server checks the length of the base64 text against the same 16 MiB, which is about 12 MiB raw. A bundle between the two passes the CLI and is refused by the server with a validation error.
- When several configured platforms match the checkout's host and neither a `repos` entry nor the account settles it, `fly --sync` without a platform in `--repo` does not report the ambiguity: it falls back to local-bundle mode, so the sandbox has no `origin`.
