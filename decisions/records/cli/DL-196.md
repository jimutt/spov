## Context

CI and people who live in the terminal create jobs with `spov jobs create`; they will want schedules the same way. DL-023 keeps job things under `jobs`.

## Decision

- `spov jobs schedule` is a group: `create <name> [goal]`, `list` (also the bare group), `show <name>`, `edit <name> [goal]`, `pause <name>`, `resume <name>`, `delete <name>`, `run <name>`. `create` takes every job-describing flag `spov jobs create` takes (kind, repos, landing, check, model, reasoning, max duration, git access, credentials, template, env, pr policy, no prep), except `--wait`, `--timeout`, `--hold` and the sync kind, with `--json` printing the created view, plus `--cron <expr>` (or `--hourly`, `--daily HH:MM`, `--weekly DAY HH:MM`, `--monthly DAY HH:MM`, its day 1 to 28 as the web form's, since a later day skips the months without it) and `--tz <zone>` (default: TZ's IANA name, else the zone `/etc/localtime` links to, else `/etc/timezone`'s, else UTC). `edit` takes the same flags and sends only those given: a cadence flag or `--tz` alone sends only that field, and a job flag reads the stored job and sends it back whole with the given flags over it, never re-reading the configuration files (`--env` sets variables by name over the stored ones). The job flags are registered by one function and marked, so a new one reaches schedules, and `edit` refuses a marked flag it does not apply. `list` shows the server's first page, with a footer when there are more; there is no `ls` alias (DL-023 names the aliases).
- `list` and `show` print tables, and `--json` the views (DL-023's rule); `show` includes the next runs and the history. `run` prints the started job's id and the same hints `jobs create` prints, or the skip's reason with exit status 1.
- Names complete from `GET /api/v1/schedules` through `Env.existingClient` (DL-023), as job ids do.
- `delete` asks for confirmation on a terminal unless `--yes`, and without a terminal refuses and names `--yes`; nothing else asks.
- Against a local server every subcommand prints that schedules need a hosted server, from the 501.

## Rationale

Sharing `jobs create`'s flags means a command line that starts a job becomes a schedule by changing `create` to `schedule create <name>` and adding a cadence.

## Consequences

- The job flags are registered by one shared function for both commands, so a new job flag reaches schedules too.
