## Context

`spov fly` and `spov attach` end the same way: the terminal goes to the OpenCode TUI, which is a full-screen program that must be a foreground child of spov. `attach` is the way back into a session that outlives its first terminal (`fly --keep`, `fly --no-attach`, or a job from `spov jobs create`), and each of those commands prints `spov attach <name>` as the next step. The session a job names exists from the moment the job is queued, so that command has to work when typed at once.

Two facts about OpenCode shape the handover. The client handshakes with `GET /api/health` under a 5 s deadline, and it only warns on a version mismatch. And with no session argument it opens on its home screen, where a typed message starts a second conversation beside the running one. That was measured on a running job (see Measurements): the job kept working in its own conversation while a message typed after attaching opened another one on the same sandbox. Attach looked as if it worked and never reached the agent.

## Decision

### The handover to the TUI

`opencode.TUI` runs the client as `opencode --server <url> [--session <id>]` with the terminal's stdin, stdout and stderr inherited. A full-screen TUI cannot be piped, and no directory argument is passed because the client would `chdir` locally, which says nothing about the remote working directory.

The order is fixed:

1. Wait for the session to be joinable (below).
2. Connect through the server and start the loopback proxy. `Env.connectSession` asks the server's connect endpoint for the edge URL, token and password (DL-030) and health-checks through the proxy, so a proxy that cannot reach the sandbox fails here and not as a broken TUI. The health check is what meets the client's 5 s handshake deadline: the client is started only once the proxy answers.
3. Check both version gates and locate the client (`prepareTUI`, shared with `fly`; the grading is in DL-035).
4. Close any launch view, then spawn the client. See DL-024 for the `fly` side.

The proxy holds the connect token and the session password, so the child gets no password: `scrubEnv` removes any inherited `OPENCODE_PASSWORD` and `OPENCODE_SERVER_PASSWORD`, so a stale one cannot override the session's and a password in a child's environment is not readable by every process running as the user. `Locator` finds the client in spov's own pinned copy under its data directory, then the official install directory, then `PATH`, so a user's global install is used when its version agrees and is not fought with when it does not. The binary is named `opencode`.

`exec.Cmd.Cancel` is a no-op: the TUI is interrupted by the user's own Ctrl-C through the terminal's process group, and spov's cancelled context does not kill it. Ctrl-C signals the whole foreground group, so the client and spov are interrupted together. `TUI.Run` therefore separates `Start` from `Wait`, and past `Start` a cancelled context means the session was interrupted (exit code 130), not that spov failed to run the client. Treating Ctrl-C as a failure would keep the sandbox, which is the leak that ending the session on exit exists to prevent.

When the TUI exits, `fly` terminates the sandbox unless `--keep` is given, and `attach` detaches and leaves the session running. A TUI failure does not terminate a sandbox: the server is healthy and reachable from a browser, so spov prints how to attach again and how to stop it.

### Attach reconnects and never creates or ends

`attach` resolves the session through the server, waits, connects, applies the same version gate as `fly` (including `--allow-version-mismatch`), and hands over the terminal. It never creates or terminates a session; `stop` is the way out. The server recovers the session's password on demand, when the replica answering did not launch the session: `session.PasswordFromSandbox` reads `OPENCODE_PASSWORD` back out of the running sandbox with `printenv`, because a process started by an exec inherits the sandbox secret's environment. The password is held in memory only, in a bounded cache, so an evicted entry costs one exec. It reaches the server as exec stdout, and is never logged, printed or put in an error.

A recovered password adds availability and no exposure: anyone able to exec into the sandbox can already read it, and the boundary is the credential for the sandbox provider's account. A sandbox that does not run a spov entrypoint, or that never had the variable, fails with an explicit message (`ErrNoPassword`), not a blank password that produces a 401 loop. A session that is stopped is refused before any connection, with a clear message and not a health timeout.

Every failure after the session is known to be running appends how to stop it (`spov stop <ref>`), because the sandbox is up and billing and the user is looking at the connection failure. The failures that leave nothing running (the session does not exist, or has already stopped) are excluded. `--no-tui` prints how to reach the web UI and leaves out the attach line, since the user has just run that command, and does not say the sandbox is "still" running. `--sync` lands the sandbox repository's changes locally on exit (DL-027).

### Waiting until the session can be joined

`awaitJoinable` polls the server every second (`Env.AttachPoll` in tests) with `GET /api/v1/sessions/{ref}` and, for a job whose state and session are both ready, `GET /api/v1/sessions/{ref}/messages` to see whether a conversation is recorded. Both answer from the store, so the wait contacts no sandbox and resets no idle clock (DL-018).

A session is ready when:

- An interactive session is `running`.
- A job's session is `running`, its job is `running`, `blocked` or `steered`, and at least one conversation is recorded for it.

A job that is `queued`, `provisioning` or `delivering` is waited on. `delivering` waits because the job is concluding and its sandbox is about to be terminated, so attaching then would hand over a terminal that dies. A job's session that is `running` is not enough on its own: until the supervisor opens the job's conversation and posts the goal, attaching joins nothing and a typed message starts a second conversation. A job moves to `running` only after that, so in practice the job's state is the signal, and the conversation check covers a failed record of it.

The wait polls the store and not the launch event stream. That stream does not exist for a queued job, a replica that did not run the launch answers it with a generic step, and it closes after the launch timeout while a queued job can wait longer. The costs are a store read a second while waiting and the loss of step-level launch progress for jobs. Progress is one line on stderr for each change of what is waited on (the job is queued, starting the sandbox, waiting for the job's conversation, the job is finishing), and nothing prints when the session is ready on the first read. An unknown reference fails at once from that first read. A failed read ends the wait with the "nothing was stopped" hints and is not retried.

`GET /sessions/{ref}` carries `SessionView.job` (id, kind, state and whether it is partial), as the listing does, from one `BySessions` read. If that read fails the server warns and leaves the field out; attach then treats a job's session as interactive and joins a running session without waiting for its conversation. That is accepted, so a store failure on a decoration cannot break `attach` and `stop`. The same field is how `spov stop` names the job it cancelled (`TestStoppingAJobsSessionNamesTheJob`).

### Leaving the wait

- Ctrl-C ends only the wait. It sends no delete, cancel or interrupt, unlike Ctrl-C during `fly`'s launch, which deletes the session `fly` started. Attach did not start the session, and a job belongs to the supervisor and to an earlier command, so losing patience must not be destructive. It prints what is still going on and how to come back or stop it (`spov attach <ref>`, `spov jobs cancel <id>` for a job, `spov stop <ref>` for a session) and exits non-zero.
- A job that reaches a terminal state (`succeeded`, `failed`, `cancelled`) ends the wait with a message naming it and pointing to `spov jobs show <id>`. A job's session that fails or stops before the job is joined reports the session's error and points to `jobs show`. An interactive session that fails or stops suggests `spov fly`.
- `--timeout <duration>` bounds the wait. The default is 0, no limit, and a negative value is refused. On expiry attach reports what it was waiting for, says the session and job continue, and exits non-zero.
- `--no-wait` fails at once, with the same messages, when the session cannot be joined on the first read. A script that relied on failing fast on a `starting` session needs it. `--timeout` and `--no-wait` are mutually exclusive.

There is no default timeout because every phase attach waits on already ends on the server's terms: the reconciler fails a launch that overruns its timeout, and a job's wall clock bounds its run (DL-049). After readiness attach runs as above.

Guards: `TestAttachWaitsForAQueuedJob`, `TestInterruptingTheWaitLeavesTheJobAlone`, and the rest of `attachwait_test.go`.

### Which conversation

Attach passes `--session <id>` of the session's oldest conversation (`Client.Conversations`, `GET /api/v1/sessions/{ref}/messages`; `TUI.Command` appends `--session` only when it is set). For a job, `awaitJoinable` returns the conversation it found, so attach does not read it twice; for an interactive session `openingConversation` reads it once after the wait. Both use `firstConversation`, which takes the first conversation with an ID from the listing, and the server lists conversations oldest first. `fly` passes none: a fresh sandbox has no conversation and the client creates one. `--web` is out of scope.

The client resolves `--session` against the remote server named by `--server`, not against local state, so the session ID travels with the endpoint. With none recorded, an interactive session falls back to the home screen. The recorder attaches on the reconcile cycle, so a young session may have none, and refusing would break the command for a state that resolves itself. A job's session waits instead.

Oldest wins for these reasons:

- A job's session opens exactly one conversation and the supervisor posts the goal into it. Anything later is the agent's own, such as a subagent, or the stray one an attach itself created. Only the oldest is the job, and `jobConversation` reasons the same way.
- Most-recently-active reads better for a long interactive session, but on a job it lands the user in a subagent's conversation, which looks like the job's transcript and is not. A rule that is oldest for jobs and newest for interactive sessions would be two behaviours where the evidence supports one.
- Ordering is by `created_at`, then `id`, in both stores. A ULID is monotonic only across milliseconds, so two conversations created in one millisecond have no creation order in their IDs. A shared store test seeds descending IDs with ascending times.
- `created_at` is when spov first saw the conversation, not when OpenCode made it: the recorder upserts with no `CreatedAt`, and the upsert keeps the original on conflict. It is exact for a job, because `jobConversation` writes the job's row before the agent can spawn anything, and exact on an interactive session whenever the recorder saw the conversations in separate passes. It is not guaranteed for two conversations first seen in the same catch-up batch. Taking the creation time from the listing would close that, but the listing's shape is not pinned against a running sandbox (DL-018).

At OpenCode's GA, `--session` means continue-or-create, which is why a job's attach waits for a recorded conversation (DL-035).

### `--web`

`spov fly --web` and `spov attach --web` open OpenCode's web UI through the loopback proxy, which holds the connect token and the password, so the browser needs no credential. The browser needs no local client either, so only the sandbox's version is checked (DL-035). spov prints the loopback URL, in case the opener picks the wrong browser or profile, and stays in the foreground as the proxy until interrupted. `--web` is mutually exclusive with `--no-attach` (`fly`) and `--no-tui` (`attach`); `--no-attach` still means create and exit, and the session is then reachable only through `spov attach`.

Interrupting spov is the exit signal exactly as the TUI exiting is: `fly --web` terminates the sandbox unless `--keep`, and `attach --web` detaches. Closing the browser tab does nothing. This gives web sessions terminate-on-exit and does not rely on the idle timeout, at the price of a terminal occupied for the session's life; a background mode is not offered.

The opener is chosen by platform (`browserCommand`): `open` on macOS, `cmd.exe /c start ""` on Windows, `xdg-open` on Linux. Under the Windows Subsystem for Linux (detected from `WSL_DISTRO_NAME`, `WSL_INTEROP`, or a kernel version naming Microsoft) it prefers `wslview`, then `cmd.exe /c start` with an empty title argument, then `xdg-open`. If none is found the URL is printed and spov continues, since failing to open a browser never fails a session that is up.

The opener is fully detached: its own session (`setsid`), no stdin, stdout or stderr, and started outside spov's context so that ending the session does not kill the browser. Under that subsystem without `wslview` or `cmd.exe`, `xdg-open` starts a Linux browser as a foreground child that inherits stdin and competes with spov for the terminal, and the browser hangs.

## Rationale

- Ctrl-C belongs to the process that owns the session. Cancelling a job because a user lost patience would make waiting dangerous, and the printed hints keep cancelling one command away.
- Polling the store gives one loop that covers every phase, works whichever replica ran the launch or runs the supervisor, and has no server-side time limit. A store read a second is much less than the web's session page already makes.
- Terminate-on-exit for `--web` gives it the same cost control as the TUI, where depending on the idle timeout would leave a forgotten tab billing.

## Measurements

- Attach to a running job without `--session`, then type a message: the job's conversation had 14 messages and the typed message opened a second conversation of 3 messages on the same sandbox. This is the failure the `--session` rule fixes.
- Create to healthy: 3 to 4.5 s from sandbox create to a healthy server. The launcher waits up to 3 minutes for health (`defaultHealthTimeout`), which absorbs a cold image pull; the CLI's own check through its loopback proxy waits up to 30 s (`ProxyHealthTimeout`).
- A session's password can be read back from a running sandbox by a process that never launched it: `TestIntegrationAttachRecoversPassword` launches a real session, discards the password and reattaches with the sandbox name alone. `go test -tags integration ./internal/session/ -run AttachRecoversPassword` (a billable sandbox).
- Conversation `created_at` spacing on a real session: four rows 28 s, 6 s and 87 s apart, with the job's own conversation correctly first.
- The 5 s client handshake deadline on `GET /api/health` is why health is awaited before the client starts.

## Consequences

- The command `jobs create` prints works straight away. A job queued behind the quota shows that it is queued and does not fail.
- Attach waits for a `starting` interactive session, such as one started from another terminal with `fly --no-attach`, and does not refuse it.
- A job's session is never attached without a conversation. The home-screen fallback is for interactive sessions only.
- `--session` is a client flag on a pre-1.0 binary. If a build renames or drops it, the client errors at spawn, which is visible, unlike the wrong-conversation failure it replaces.
- A failed read of the transcript never fails an attach; `openingConversation` warns and falls back to the home screen.

## Known gaps

- A session with several conversations can only be attached at its oldest. Choosing among them needs a selection UI.
- Whether the TUI draws the earlier transcript on entry is OpenCode's behaviour. Attach guarantees that the session is joined, not what is drawn.
- Two conversations first seen in the same recorder catch-up batch may not be ordered by creation (above).
- The unit tests run against fakes. The live path (a real terminal, a provider key and a billable sandbox) is exercised by hand.
