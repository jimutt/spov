## Context

Sync-back (DL-027) lands a sandbox's commits and its uncommitted files in the user's checkout when a synced session closes, and `spov jobs apply` does the same for a sync job. Everything in the export is written by programs inside the sandbox, where a prompt-injected agent has root, so the export is hostile input to the user's own machine.

A security review on 2026-11-11 found that the unpacker refused only `..`, absolute paths and a `.git` segment. An export could therefore:

- overwrite or delete a file the checkout ignores (`node_modules/.bin/tsc`, `.venv/bin/python`, `.env`), which `git status` and `git diff` never show;
- write a hook where `core.hooksPath` points into the working tree (husky's `.husky/_`, a tracked `.githooks`), which git runs at the user's next `git status`;
- reach `.git` through a name the filesystem resolves to it: NTFS's short name `GIT~1`, trailing dots and spaces, an alternate stream suffix, or code points HFS+ ignores.

## Decision

An in-place sync never writes, replaces or deletes a file that `git status --ignored` would have shown as untracked or ignored before it, whether the change comes by commit or by archive, and never changes what git runs or reads as configuration. `inPlaceVeto` (`internal/git/syncguard.go`) decides this before anything is written, on the checkout as the user left it. When it finds a problem the apply writes `spov/<session>` as for a moved checkout, with a reason naming up to three of the paths (then "and N more"), which the CLI prints. The touched paths are the commits' (`git diff --raw --no-renames` from the checkout's head), the archive's entries and the deletions.

1. **Untracked and ignored files in the way.** A path the commits add, modify or change the type of, or that the archive writes or the deletions remove, falls back when the checkout holds there, above it or below it something it does not track: an entry `git status --porcelain --ignored --untracked-files=normal` lists, or anything on disk (an empty directory) that no tracked path of the checkout's commit, or for an uncommitted path of the sandbox's, accounts for. An archive entry the sandbox's commit does not track and that the checkout's ignore rules match (`git check-ignore --no-index`) falls back as well: an honest export can hold one when the user ignores more than the sandbox (a global `*.log`, `.git/info/exclude`), and the file reaches the fallback branch in its commit.
2. **The commits land through git's own guard.** The branch and the work tree move with `git merge --ff-only --no-overwrite-ignore --no-stat -q <head>` (`fastForward`), not `reset --hard`. Measured on git 2.43: `reset --hard` and `git read-tree -m -u <cur> <head>` both overwrite an ignored file, replace an ignored directory with a file and remove a tracked directory together with an ignored file inside it; the fast-forward with `--no-overwrite-ignore` refused all four and wrote nothing. When git refuses and the checkout is still at its old head and clean, the apply falls back with git's message as the reason; any other failure is an error that says the checkout may be partly updated.
3. **What git runs or reads as configuration.** A touched path that is, lies under, or lies above one of these falls back: the hooks directory (`rev-parse --git-path hooks`); every config file git reads for the checkout (`git config --list --show-origin`) and every file an `include.path` or `includeIf.*.path` names, whether it exists yet or not; and any path a config value names (a `core.fsmonitor` script, a filter driver, `core.attributesFile`), a token with a slash or naming an entry at the root. Each is taken as configured and as resolved through symlinks on disk, so a symlink added or retargeted anywhere along the hooks path counts. Paths under the git directory are left out, since no export can reach them. A touched `.gitattributes`, `.lfsconfig` or `.gitmodules` at any depth (with `namesGitDir`'s rules for case, trailing dots and spaces, streams and HFS+ ignorable code points) falls back too, so the user's filter drivers (git-lfs's smudge among them) do not run on attributes the session wrote.
4. **Names a filesystem aliases.** For every touched path, each component that exists on disk must appear under its exact byte-for-byte name in its parent directory's listing (`os.ReadDir`); one that `Lstat` finds but the listing does not name is an alias (an NTFS 8.3 short name such as `GITHOO~1`, a case alias, an HFS+ variant) and the apply falls back. A component that does not exist yet falls back when it holds `~` followed by a digit, ends in a dot or a space, or holds a `:`. A committed path that names the git directory (`namesGitDir`) falls back as well.
5. **Submodules.** A touched path under a gitlink of the checkout's commit falls back. An uncommitted path under a gitlink of the sandbox's commit is refused with an error, since git status could not have listed it and neither landing can hold it.
6. **Refusals.** The whole export is refused, with an error naming the path and nothing written, when a deleted path is not a file or symlink of the sandbox's commit, an archive entry is not a regular file or a symlink inside the repository, or an archive or deleted path lies under a file, a symlink or another archive entry. These are checked before the commits land. A path segment is refused when it is `.git` under git's own NTFS and HFS+ rules (`namesGitDir`), and any path holding a backslash is refused.

An honest export is built from `git status` without `--ignored`, so the refusals in rule 6 meet nothing a session legitimately produces; an export that names such a path was not built by spov's script, and the rest of it deserves no trust either. The session is left as it was, so the work is not lost. The fallback branch is built in a temporary index and directory and writes nothing to the checkout, so rules 1 to 5 only decide where the work lands.

## Consequences

- A session that legitimately edits a repository's tracked hooks (`.githooks/pre-push`, say), a `.gitattributes`, a config file the checkout includes, or that commits over a file the user ignores, now lands on `spov/<session>`, not in place. So does a new file whose name holds `~` and a digit or ends in a dot or a space, and, on a case-insensitive filesystem, a case-only rename. These fall back rather than fail, so nothing is lost.
- Each in-place apply costs two `ls-tree -r -t`, one `diff --raw`, one `status --ignored`, one `config --list` and a directory listing per directory a touched path crosses.
- `TestSyncBackOnAWindowsDriveNeverWritesThroughAShortName` runs a real sync onto NTFS under `/mnt/c/Users/Public/spov-fix-probe` where that drive is mounted and short names resolve, and skips elsewhere; `TestEveryExistingComponentMustBeListedUnderItsExactName` checks the listing rule with a fake filesystem.
- The unpacker stays, with git's path rules ported into it. Landing the uncommitted state through git itself (a temporary commit and `git restore`) would make git enforce them, and is the sturdier design if this code is revisited.
- Other files that tools run on their own (`.envrc`, editor task files) are not covered when they are tracked: a change to one is visible in `git status`, which is the line this decision draws.
- Not covered: filter drivers the user has already configured still run during the fast-forward on the files the commits change, under the attributes the checkout already has (git-lfs fetching an object a committed pointer names, from the endpoint the user's own config and the unchanged `.lfsconfig` give). A config value naming a program by a bare name on `PATH` is not a work-tree path and is not checked.
