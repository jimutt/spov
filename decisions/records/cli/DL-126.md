## Context

Sync-back (DL-027) lands a sandbox's commits and its uncommitted files in the user's checkout when a synced session closes, and `spov jobs apply` does the same for a sync job. Everything in the export is written by programs inside the sandbox, where a prompt-injected agent has root, so the export is hostile input to the user's own machine.

A security review on 2026-11-11 found that the unpacker refused only `..`, absolute paths and a `.git` segment. An export could therefore:

- overwrite or delete a file the checkout ignores (`node_modules/.bin/tsc`, `.venv/bin/python`, `.env`), which `git status` and `git diff` never show;
- write a hook where `core.hooksPath` points into the working tree (husky's `.husky/_`, a tracked `.githooks`), which git runs at the user's next `git status`;
- reach `.git` through a name the filesystem resolves to it: NTFS's short name `GIT~1`, trailing dots and spaces, an alternate stream suffix, or code points HFS+ ignores.

## Decision

An in-place apply changes only paths the user can see with `git status` afterwards, and never a file git would execute.

1. **Ignored and untracked paths.** Before anything is written, an in-place apply refuses the whole export, with an error naming the paths, when an archive entry that the sandbox's head commit does not track matches the checkout's ignore rules (`git check-ignore --no-index`), or when a deleted path is not tracked by that commit. The rules are read before the reset, so they are the user's and not ones the session committed. A tracked file that matches an ignore rule is shown by `git status` and lands as before.
2. **Hooks.** When the directory git runs hooks from (`git rev-parse --git-path hooks`) lies in the working tree, and the session's commits or uncommitted state change any path under it, the apply does not land in place: it writes `spov/<session>` as for a moved checkout, with a reason that names the directory. Nothing is refused, and the user reads the change before checking it out.
3. **Names of `.git`.** A path segment is refused when it is `.git` under git's own NTFS and HFS+ rules (`namesGitDir`), and any path holding a backslash is refused.

An honest export is built from `git status` without `--ignored`, so rule 1 refuses nothing a session legitimately produces. Refusing, not dropping the entries, is deliberate: an export that names such a path was not built by spov's script, and the rest of it deserves no trust either. The session is left as it was, so the work is not lost.

The fallback branch needs none of rule 1: it is built in a temporary index and directory, and writes nothing to the checkout.

## Consequences

- A session that legitimately edits a repository's tracked hooks (`.githooks/pre-push`, say) now lands on `spov/<session>`, not in place.
- The unpacker stays, with git's path rules ported into it. Landing the uncommitted state through git itself (a temporary commit and `git restore`) would make git enforce them, and is the sturdier design if this code is revisited.
- Other files that tools run on their own (`.envrc`, editor task files) are not covered when they are tracked: a change to one is visible in `git status`, which is the line this decision draws.
