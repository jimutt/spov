## Context

A sandbox bills for its whole wall-clock lifetime, so the CLI must never leave a sandbox that its user cannot see or end. The commands that list and end sessions therefore exist alongside the one that launches them. The CLI is an HTTP client of `spov serve` (DL-002), so every command below talks to the server, and a local server is started on demand where there is none.

The tree has to give each verb one meaning. Sessions are what a user handles most, and autonomous jobs are a second resource with their own lifecycle. The web app's buttons and the hints that the CLI and the server print name these commands too, and a hint that names a command that does not exist is worst at the moment something has gone wrong.

## Decision

### The tree

| Command | Does |
|---|---|
| `spov fly` | Launch an interactive session and attach to it. |
| `spov attach <session>` | Attach to a running session. |
| `spov ls` | List sessions, newest first (alias `list`). |
| `spov stop <session> [--all]` | End a session and terminate its sandbox. `--sync` first brings the sandbox's work back to the local checkout, for one session (DL-027). |
| `spov jobs` | List jobs. `spov jobs list` (alias `ls`) is the same command. |
| `spov jobs create [goal]` | Create a job. |
| `spov jobs show <job>` | Show one job. |
| `spov jobs report <job> [<path>]` | Print a report a job delivered, or save it. |
| `spov jobs cancel <job>` | Cancel a job and terminate its sandbox. |
| `spov jobs resume <job>` | Hand a taken-over job back to its loop. |
| `spov jobs interrupt <job>` | Stop the job's current turn and take the job over. |

`ls` and `jobs` show the newest page of every state plus any live session or unfinished job older than it (`--page`, `-n`); the paging rules are in DL-012. `login`, `logout`, `whoami` and `credentials` are the account commands (DL-008). `spov serve` and its subtree (`image build|prune`, `migrate up|down|status`, `openapi`) are operator commands. `migrate down` is the usual word for a migration and is not a session verb.

Sessions keep top-level verbs because they are what a user handles most, and a `sessions` group would make the common commands longer for symmetry alone. Jobs get a group. `stop` follows Docker's meaning, end the running thing; `down` suggests tearing down a stack. There are no compatibility aliases, stubs or suggestions: `down`, `run`, `new` and `ps` are unknown commands. `TestTheRenamedCommandsAreGone` keeps them from returning and pins the aliases that remain (`list` on `ls`, `ls` on `jobs list` and `credentials list`). The CLI and the server are upgraded together, and the server does not keep old command names for older CLIs.

### Naming rules

1. A resource group, such as `jobs` or `credentials`, lists when called bare and also has a `list` subcommand with the alias `ls`.
2. Viewing one item is `show`, as in `jobs show` and `config show`, never `view`.
3. Creating is `create` inside a group. `fly` is the one branded exception.
4. `stop` ends a session and its sandbox, `interrupt` stops a turn, and `cancel` ends a job. No command uses one of these words for anything else.
5. An alias is allowed only where it matches a spelling used elsewhere in the tree (`ls`/`list`).

The web app follows the same words. Its turn button is **Interrupt** (**Interrupting…** while in progress), and the server's interrupt refusals and its OpenAPI summary say "interrupt" because both the button and `spov jobs interrupt` show them. **End session** and **Cancel job** keep their names: the CLI says `stop` for a session and the web says End session, and both end the sandbox. End session reads clearly next to Interrupt on a page. The code identifiers `canStop` and `jobRefusesAnInterrupt` keep their names.

### Launching: `fly`

`spov fly` creates the sandbox, bootstraps the repositories, starts OpenCode and attaches the TUI. The TUI is a foreground child, so when it exits the sandbox is terminated unless `--keep` is given; with `--keep` spov detaches and the sandbox outlives the CLI process. Every sandbox is tagged and bounded by a timeout and an idle timeout (DL-029), so none is left unseen or unbounded.

The repositories come from three sources, in this order:

1. `--repo owner/name` (repeatable), or `--repo <platform>:owner/name` when several platforms are configured. This is explicit and scriptable and overrides the configured list.
2. The project file's `repos` list.
3. An interactive picker over the repositories the server can list, shown only when neither of the above names anything and a terminal exists (DL-028).

The picker is offered only when `/dev/tty` can be opened, not merely when stdin is a character device (`interactiveSelector`). The picker reads the terminal directly, so a piped or scripted run would otherwise fail with an opaque TTY error instead of spov's message pointing at `--repo`. With a user-level `platforms` entry, `spov fly --repo owner/name` works in any directory with no project file. A configured `landing` names a repository of the configured list, so it is ignored when `--repo` replaces that list.

`spov attach` waits until a session can be joined and then re-resolves the URL and credentials and starts the client; it is covered by DL-025.

### `jobs interrupt`

`spov jobs interrupt <job>` reads the job (`GET /jobs/{id}`) to find its session and calls `POST /sessions/{session}/interrupt`, the endpoint behind the web's Interrupt button. The server's refusals in `jobRefusesAnInterrupt` apply and the CLI prints the server's reason. The server checks the job's state before the session's, so a queued or provisioning job is refused in the job's words ("it has no sandbox yet") and not as a session that is not running. On success the CLI says the job has been taken over, and prints `spov jobs resume <job>` to hand it back and `spov attach <session>` to steer it (the two hints go to stderr). When the server reports that no turn was interrupted, the job is still taken over and the line says so: either no turn was running, or a message that was waiting has just started one.

There is no top-level `spov interrupt`; an interactive session's turn is interrupted from its TUI or from the web. `interrupt` and `resume` are the two halves of taking a job over, so they sit under `jobs` beside `cancel`. Reusing the session endpoint keeps one implementation of the interrupt and its marker, where a job-scoped endpoint would be a second route to the same code. `jobs resume`'s help mentions `interrupt`.

`spov stop` on a job's session keeps the server's behaviour, which cancels the job. The CLI adds no refusal, its output names the job it cancelled, and its help says what it does to one. `jobs cancel` is the clearer way to end a job.

### `--json`

These commands take `--json`: `ls`, `jobs` and `jobs list`, `jobs show`, `jobs create`, `credentials` and `credentials list`, and `whoami`.

- It prints the API's own response body for the call and nothing else on stdout: `{"sessions": [SessionView…]}` for `ls`, `{"jobs": [JobView…]}` for `jobs list`, one `JobView` for `jobs show` and `jobs create`, `{"credentials": [CredentialView…], "enabled": …}` for `credentials`, and `MeView` for `whoami`. The OpenAPI document (`docs/api/openapi.yaml`) describes the format and there is no second schema. The listing bodies carry `next` and `total`, and `ls` and `jobs` print the page they show (DL-012).
- The CLI writes back the view it decoded, so a field this CLI version does not know and huma's optional `$schema` link are left out. An empty list is `[]`, never `null`.
- With a local server, `credentials --json` has the same shape, built from the local probe: a platform under its configured name (what `credentials remove` takes there), a provider key as `provider:<VAR>` as a server keys it, and `enabled` true. The OpenCode sign-in line is left out; it is its own view (`GET /api/v1/me/opencode`).
- Notes, hints and progress go to stderr or are dropped, including the repository picker's own output.
- Tables and prose are for people. Their columns and wording may change in any release, and the docs say so.
- `config show --format yaml|json` stays as it is; it prints local configuration, not an API view.

API views are already versioned, generated and drift-gated (DL-005), so reuse gives scripts a documented format at no extra cost, and a boolean `--json` is shorter than a `--format` flag whose only alternative is the table. A field added to a view appears in `--json` output, and a renamed field breaks scripts in the same release as the API change. That is acceptable before v1 and goes in the release notes. `TestTheReadAndCreateCommandsTakeJSON` is the guard.

### Completion

Cobra's generated completion (`spov completion bash|zsh|fish|powershell`) completes commands and flags. Arguments that name a session, a job or a credential complete from the server:

- Session names and IDs for `attach` and `stop`, from `GET /sessions`, live sessions only. A session is offered by name, and by ID once what is typed is a prefix of one (a session with no name is always offered by ID), so the list is not doubled. `stop --all` completes nothing.
- Job IDs for `jobs show`, `report`, `cancel`, `resume` and `interrupt`, from `GET /jobs`, unfinished jobs first and newest first within each. `show` and `report` also offer finished jobs; the three acts offer unfinished ones only, since a finished job refuses them.
- Credential names for `credentials remove`, from the same listing as `spov credentials`, spelled as `remove` takes them: a provider key by its bare variable. With a local server this is the local probe's listing and needs no server.

Each candidate carries a short description (state and age, or state and the goal's first line), and the shell keeps the order given. The sessions are the live ones, up to the largest page the server gives; the jobs are the newest page, so an older job is not offered.

A completion asks only a server that is already reachable: the configured hosted server, or a local server the state file names that answers and is this build. `Env.existingClient` does this; completion never uses `Env.client`, which can spawn a local server or stop one of another build. It never runs the device flow and never calls a sandbox. A one-second timeout covers the whole lookup, including a keyring read that ignores the context, and the lookup runs aside so that such a read cannot hold the shell. On any failure or timeout it offers nothing and the shell falls back to plain input. `TestCompletionNeverStartsOrStopsAServer` is the guard.

### Every named command exists

`TestEveryNamedCommandExists` collects every `spov <words>` command named in a Go string literal under `internal/` and `cmd/`, and in the web source, and fails when the words do not resolve to a command in the cobra tree it reads from `NewRoot`. Flags are checked against that command's flags, and a bare word after a group must be one of its subcommands. A sentence that starts "spov cannot…" would fail it, so such words are on the test's `proseWords` list in `hints_test.go` and are skipped unless inside backticks or `<code>`. Test files are out of its scope, so a test may name a command only as an example.

## Rationale

- Top-level session verbs keep the interactive lifecycle short, and `spov --help` reads as that lifecycle plus a `jobs` group. A bare group that lists matches the gh and docker habit.
- `ls` and `stop` sit beside `fly` because they are the safety net for cost. Tags are the cheap way to find spov's sandboxes; a name alone is not filterable in Modal.
- Hints are what a user follows when something goes wrong, so a stale one sends them to an unknown command at the worst moment. A test that resolves each one is cheap and holds across later renames.
- Completion removes the most common friction in the CLI, copying an ID from `spov ls` into the next command. Starting a local server on a Tab key press would be slow and surprising, and the server could then sit idle until its exit timer, so a completion that sometimes offers nothing is the better failure. The server answers every read from its store, so completion costs no sandbox time (DL-018).

## Consequences

- The CLI keeps a client call for every endpoint it reaches, including the session interrupt, and the server needs no job-scoped interrupt route.
- The list and show commands need a path that writes the decoded view and keeps stdout clean.
- The release notes list the replacements for `down`, `run`, `new` and `ps`. There are no deprecation warnings.
- A new command that prints a hint, or a new place that names one, is checked by `TestEveryNamedCommandExists` without further work.

## Known gaps

- A signed-out user gets no completion suggestions, not an error.
- Completion reads the keyring: for a hosted server's token when `SPOV_SERVER_TOKEN` is unset, and for the local probe behind `credentials remove`. A locked Secret Service collection can show its unlock prompt on a Tab press. This is accepted, because any command would raise the same prompt.
