## Context

Every session worked from `/workspace` unless `landing` named a repository (DL-037), so that the order of `--repo` flags never decided which repository's instructions the agent read. OpenCode reads a project's `opencode.json` and `.opencode/` (its plugins, plugin files, commands, agents and rules) from the directory it runs in, walking up, never down. A plain `spov fly --repo owner/app` therefore ran OpenCode in `/workspace` and silently left out everything the repository configured, while a synced launch of the same repository, which lands in it, loaded it all. Tested against OpenCode 2.3.0 in Modal sandboxes with `envsitter-guard` and `opencode-rules`: loaded in a synced session, absent in an unsynced one.

## Decision

- An interactive session whose request names exactly one repository and no `landing` starts in that repository's directory (`git.SingleRepoDir`, the name bootstrap gives a lone clone), set on the request before it is stored (`defaultLanding` in `Service.Create`). OpenCode then honours the repository's `opencode.json`, `.opencode/` and `AGENTS.md` as a local OpenCode in the checkout would.
- Only on a server that runs the credential proxy (DL-034). Without it the forge token and the provider keys sit in the sandbox's main container, where a repository's own plugin, local MCP command or provider `baseURL` would reach them as OpenCode starts, so such a session stays in `/workspace`, as before.
- `landing: .` (`opencode.WorkspaceLanding`) names the workspace root: a one-repository session that should not run its repository's configuration keeps `/workspace`. The CLI sends it with a `--repo` list too, since it names no repository, and the server stores the request with an empty landing.
- A session with several repositories still works from `/workspace`, and `landing` still chooses one of them, as DL-037 says. A job's session is unchanged: it works from `/workspace` (a sync job from its repository, DL-100), since its check command is written relative to the workspace (DL-050).
- spov's generated `/workspace/AGENTS.md` still reaches the agent: OpenCode's own search stops at the repository's root, so the config lists it under `instructions` (DL-174).

## Rationale

With one repository there is no choice for flag order to make, and the repository is where the person would run OpenCode themselves. It is also what a synced launch has always done. A remote repository named with `--repo` or picked in the browser is not the person's own checkout, though: its configuration runs code in the sandbox. With the proxy that code holds placeholders only, and `.` is the way out for a repository the person does not trust to configure the agent.

## Consequences

- The repository's whole `opencode.json` applies, not only its plugins: its `permission` rules, `model`, MCP servers and agents too, as in a local OpenCode run in the checkout and as in a synced session before. A repository that allows every action removes the prompts DL-038 keeps for the git credentials and the auth store, and a repository's `model` replaces the launched one. `docs/plugins.md` and `docs/sessions.md` say so.
- A resumed session keeps the landing its request stored.
- `TestASingleRepositorySessionStartsInsideIt`, `TestASessionWithSeveralRepositoriesStartsInTheWorkspace`, `TestARepositorysConfigIsNotLoadedWithoutTheProxyOrWhenAskedNotTo` and the CLI's `TestLandingDotKeepsTheSessionAtTheWorkspaceRoot` guard it.
