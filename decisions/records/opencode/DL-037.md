## Context

A sandbox holds the session's cloned repositories side by side under `/workspace`. spov's model is multi-repository: `--repo` repeats, the picker is a multi-select, the permission grant covers the whole tree, and the generated `/workspace/AGENTS.md` sits at the workspace root. A session's working directory is the one place that could disagree with that. Defaulting it to the first clone would let the order of the `--repo` flags decide which repository's instructions the agent reads and which directories are external to it.

How OpenCode finds instructions matters here. Instruction discovery (`AGENTS.md`) and project config discovery both walk up from the session's directory to the filesystem root. Nothing walks down. A directory with no git root above it is a project rooted at itself, so `/workspace` not being a repository is fine.

Agents also need a place for things that are not the work: one-off scripts, downloads, notes and intermediate results. OpenCode has no scratch concept, so without a named place an agent writes them into a repository, where they risk being committed, or into `/tmp`. A report job cannot write except through the shell, and one job retried a denied write 91 times before a writable place existed.

## Decision

### The session's directory is /workspace

- **Every session works from `/workspace`**, interactive and job alike, not from a repository inside it. `--landing` (and the config `landing`, naming a repository by directory) stays as an explicit override; nothing picks a repository on the person's behalf. `Options.Landing` is passed through as given, and `Entrypoint.WorkingDir` returns the workspace root for an empty landing.
- **An interactive session inherits it** from the server's working directory: the person's TUI sends its own local directory, which does not exist remotely, and OpenCode falls back to the server's.
- **A job's conversation** is created with an explicit `location.directory` (`createConversation`), which defaults to `WorkspaceRoot`, never the home directory.
- **`sessionDir` reads `store.Session.Landing`**, which is `Entrypoint.WorkingDir()` as recorded at launch and is the server's real working directory. It never reads `Sandbox.Workdir`, which the entrypoint's first act leaves and which therefore moves nothing. Reading it would put a job's conversation at the workspace root while its server ran in a repository.
- **A local-sync session** (see DL-027) starts the entrypoint at `/workspace` and records the synced repository's directory as the session's landing, since the directory is created after the entrypoint starts.
- **A check command runs in `/workspace`**, with the directory sent explicitly by the plugin. A check is therefore workspace-relative (`./<repo>/scripts/check.sh`), or the job names `--landing <repo>`. There is no separate `check_dir`.
- **Reports live in `/workspace/out`** whatever the landing (`opencode.OutDir`), because a deliverable belongs to the spov session and not to a repository. Following the landing would drop a report into a checkout the agent may be committing (on a `pr` job, into the branch it opens) and has no answer for a multi-repository job. The agent is told the directory in its goal and collection reads the same constant, so the two cannot drift. See DL-051.
- **The job allowlist keeps `external_directory`.** A session landed in a repository asserts it for `/workspace/out/*` before writing a report, and a job that is denied it still finishes by falling back to `cat` through the shell, so the failure looks like a working run. It is not redundant (`TestEveryJobKindCanReadItsOwnWorkspace`; see DL-040).

### What discovery means from /workspace

Landing at `/workspace` means no repository's own `AGENTS.md` or `opencode.json` is auto-injected. The generated `/workspace/AGENTS.md` is discovered, because the walk starts at the session's own directory, and it carries one instruction: before changing anything in a listed directory, read that repository's own `AGENTS.md` and `CLAUDE.md` if they exist. This is a guardrail, not a mechanism. An agent that ignores it reads no repository instructions. A deterministic lift of those files into the generated file is not built; the trigger for building it is an agent that had instructions available and did not read them. The job orientation (see DL-039) is the only source of per-repository context besides that file.

### The generated AGENTS.md

`AgentsMarkdown` renders `/workspace/AGENTS.md` from the repositories actually cloned, so it cannot describe one that is absent. It lists each repository's directory, slug, host and the CLI to use (`tea` for Forgejo and Gitea, `gh` for GitHub, `glab` for GitLab, or none), then the instruction to read each repository's own instruction files, then how to open a pull request with each CLI in use, then the scratchpad section. It also carries the toolchain section described in DL-033. It is written by the entrypoint through a quoted heredoc, so the shell expands nothing in it, and it is short and factual: it competes for attention with the repositories' own files.

### The scratchpad

Every sandbox, interactive or job, gets `/workspace/.scratch` (`opencode.ScratchDir`), created by the entrypoint before the server starts, beside the repositories and `out`.

- The generated AGENTS.md names it in a section of its own: temporary files, one-off scripts, downloads, notes and intermediate results go there, not in a repository and not in `/tmp`. Nothing in it is collected, delivered or committed, and it goes when the sandbox does. For a report job the section also says the reports go in `/workspace/out`, one Markdown file each.
- Interactive sessions reach it through the grant over `/workspace`. A job writes to it under the write-roots rule (see DL-040).
- It is not evidence and is not preserved; reading it after a run needs the sandbox.

### Reserved names

No clone takes `out` or `.scratch`. `git.Bootstrap` treats both as already taken, so a repository with either name moves to its next candidate directory (`owner-name`, as for a name clash), and the entrypoint's validation refuses a clone into either. `git.ReservedDirs` and the entrypoint's `reservedDirs` must agree (`TestTheReservedDirectoriesAgree`).

## Rationale

- One setup rather than two. A job and an interactive session differ in what they are told to do, not in where they believe they are.
- No repository is privileged. The order of `--repo` flags means nothing.
- It is the directory the rest of the design assumes: the grant, the generated file and the job orientation are all about `/workspace`, so landing there makes the grant cover the working directory and the generated file sit at the start of the walk.
- Provided scratch space keeps temporary files out of repositories. Placing it under `/workspace` needs no new grant, and the dot keeps it out of casual listings.
- Alternatives rejected: landing at `/workspace` only for several repositories (a differing setup, and it makes the multi-repository case the unusual one); defaulting a job to the landing repository (it fixes the symptom with an arbitrary rule); relying on the orientation to compensate for a wrong directory; keeping the first-clone default (arbitrary).

## Measurements

- **Project resolution (spike S11):** a seeded `/workspace/repo` holding only an `opencode.json` and no `.git` resolves to a project rooted at itself (directory `/workspace/repo`), and `/root` likewise resolves to a project of its own. `GET /api/config` at `/workspace/repo` lists the repository's own `opencode.json`, and at `/root` does not, so discovery is the upward walk described above. `go test -tags integration ./internal/sandbox/ -run S11Model -v` (one sandbox, no agent turn, no model key). Re-check on an OpenCode bump.
- **A job with no orientation:** an agent searched `/tmp/opencode` for a `.git` directory and never referenced `/workspace` across 279 events.
- **Denied writes:** a report job retried a denied write 91 times before a scratchpad existed.

## Consequences

- A single-repository session's working directory is the workspace, not the repository. That repository's own `AGENTS.md` is not auto-injected, and a check written as `./scripts/check.sh` does not resolve. `--landing <repo>` restores both. This cost falls on the simplest case.
- A check that cannot be found exits 126 or 127. See DL-050 for how a caller's check and a proposed one are judged when that happens.
- The job's agent is where its work is, and the generated AGENTS.md is discovered rather than merely pointed at.
- A repository named `out` or `.scratch` is cloned into its `owner-name` directory, and the workspace guide's table shows where.
- Guard tests: `TestALaunchLandsInTheWorkspaceAndNotInARepository`, `TestAJobsConversationDefaultsToTheWorkspaceAndNotToHome`, `TestTheReportsAreCollectedFromTheWorkspaceNotTheLanding`, `TestTheWorkspaceGuidanceAsksForEachRepositorysOwnInstructions`, `TestEverySandboxGetsAScratchpadNoCloneCanTake`, `TestTheReservedDirectoriesAgree`, `TestTheCheckRunsInTheSessionsDirectory`.

## Known gaps

- Whether the `external_directory` denial on a job's own checkout stopped once the checkout was below the working directory has not been re-measured; the allowlist keeps the grant until a job run shows the read tool works on a checkout without it.
