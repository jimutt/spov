## Context

From OpenCode 2.3.0 a promise-based plugin tool receives `ToolContext.signal`, an abort signal raised when its call is stopped, for example by an interrupt. Measured at 2.3.0 (spike S-SA3, local, with a plugin that only observes): a plugin tool's call context has the keys `agent`, `id`, `messageID`, `progress`, `sessionID` and `signal`; `signal` is an `AbortSignal`, not yet aborted, and an interrupt of the session aborts it (`AbortError`). The completion tool awaits the job's check inside its call (DL-048), which can run for minutes; the pull request tool writes one evidence line.

## Decision

- Both tools read the signal from their call's context and treat a context without one as never aborted, so the plugin behaves as before on a build that passes none.
- The pull request tool checks the signal before it records. An aborted call records nothing and answers that it was stopped.
- The completion tool, when the signal fires while its check is running, kills the check's process group as a timeout does, records `completion.interrupted` (never `completion.declared`), clears `loop.stopped` and its reason when this call set them, sends no stop marker and answers that the declaration was withdrawn. A signal that fires after the marker was sent changes nothing: delivery has begun.
- So that a withdrawn call leaves no declaration behind, `completion.declared` is recorded once the check is done, just before the stop marker, and a killed check records `check.interrupted` in place of its result (`check.finished` is never written for it).
- A stop that arrived while the check ran, such as the wall clock's (DL-049), is not this call's to clear: it stands, and is announced under its own reason.
- A withdrawn completion counts for no gate, as a deferred one does not. The check runs again when a later call is accepted.

## Rationale

A person who interrupts while the check runs is taking the turn back, and a job that then delivers on a declaration made before the interrupt would ignore them. Withdrawing is the same rule as a completion deferred for a queued message: nothing from the refused call counts. Killing the check's group keeps an abandoned check from holding the sandbox open.

## Consequences

- An interrupt during a long check stops it at once and leaves the job running under the person's control (DL-053).
- The plugin's run tests drive an abort through the real `setup()` (`pluginabort_test.go`). The signal's presence on the call context, and the withdrawal with the real plugin at the pin, are re-measured on an OpenCode bump with `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SSA3 -v` (local, fake model, no key).
- The evidence file's order changes: the check's line now precedes the declaration's.
