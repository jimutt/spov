## Context

spov targets OpenCode 2 and its V2 HTTP API. Version 1 is out of scope. OpenCode's API is experimental and releases come quickly, so spov does not follow whatever is newest: it pins one exact version, `config.DefaultOpenCodeVersion`, which the user config can override. The pin is baked into the sandbox image and is what a local client is compared against. This record names the pin only by that constant; the number changes with every bump.

The pin is the cost of trailing OpenCode: each bump is a deliberate release step with a recurring chore. In return the sandbox's build, which decides what the agent can do and what spov's plugin and readers see, is the one spov has checked.

Three things make the pin more than a constant:

- A hosted deployment's server resolves the image, and the CLI runs on another machine with its own configuration. A client that compares a sandbox against its own default says something wrong about a deployment it does not share configuration with.
- The user's own `opencode` install updates on its own schedule. OpenCode 2 shipped 22 patch releases in its first 19 days (2.0.0 on 11 September 2026 to 2.0.21 on 30 September 2026), so demanding an exact match locally would make `--allow-version-mismatch` a habit.
- OpenCode ignores an unknown query parameter, so a renamed parameter can turn a call into a no-op with no error. Only a comparison against the build's own API description catches that.

## Decision

### One binary, one pin, one cut

The binary is `opencode` everywhere: the image path `/root/.opencode/bin/opencode` (`imageBinaryPath`), the entrypoint's exec (`imageBinary`), `opencode.BinaryName` and the locator's candidates. The installer also leaves an `opencode2` file, a 47-byte shim that execs a sibling binary. spov never runs it, because a copy placed elsewhere execs a file that is not there, while the image's in-place `--version` check still passes.

OpenCode 2 GA and the earlier beta cannot talk to each other. A GA client probes `GET /api/info`, a beta client `GET /api/health`, and each refuses the other's server. spov therefore supports one line only, with no fallback and no dual support.

Everything that names the pinned build moves with the pin: `ActionVocabularyVersion`, the committed contract document, the image's release record, the example config, the README and AGENTS.md. A bump records the build in `openCodeReleases` (`internal/sandbox/image.go`): its npm scope, the binary's name inside the package, and `dist.integrity` for each target (see DL-032). A version with no entry is taken to be published like the current line (`@opencode/cli-*`, binary `opencode`). The order of a bump is in AGENTS.md ("Bumping the pin"); this record holds the reasons.

A new pin reaches users prepare-then-switch: build the image, switch the server's pin, then update the CLI.

The TUI's environment scrub removes `OPENCODE_SERVER_PASSWORD` as well as `OPENCODE_PASSWORD`, because the client falls back to it when the first is unset.

### The server publishes its pin

`GET /opencode-pin.json` answers `{scheme, opencode}` (`server.OpenCodePin`, `PinScheme`), unauthenticated, with `Cache-Control: no-store`. It reports the version the deployment is configured to pin (`Defaults.OpenCodeVersion`), not an inspected image.

- **Raw mux, not huma.** `requireSecurity` stamps bearer security on every huma operation and panics on a path outside `APIPrefix`, so a public huma operation cannot be documented at all. The endpoint sits beside `/livez` and is absent from the OpenAPI document, as the device flow is.
- **Not `opencode.json`.** That is OpenCode's own config file, which the entrypoint writes into every sandbox, and the two would be confused when searching.
- **A scheme beside the version.** A client that does not know the scheme reads no version at all. The field set can grow without a second endpoint, and a newer server's answer is never half-read by an older client.
- **One field of substance.** The body carries no image name, no Modal app and no build identity (`TestThePinCarriesNothingButTheVersion`).
- **Unauthenticated on purpose.** The pin is a published upstream release number, it appears in every sandbox's `/api/info` answer and in the image name, and a client needs it before it has credentials in order to explain a mismatch. The cost is that anyone who can reach the port can learn which OpenCode version a deployment runs, and so which known issues of that version apply. That is accepted because withholding it would hide nothing that is not already public upstream, and would break the case the endpoint exists for. It exposes nothing else.
- **A handshake, never a gate.** An unreachable or older server, or a body with an unknown scheme, means the client falls back to its own configuration. The read is bounded by `client.PinTimeout` (5 s) and its failure is silent. Nothing about a launch depends on it succeeding.

`spov fly` and `spov attach` resolve the expectation once (`expectedOpenCodeVersion`) and, for the terminal client, use it for both gates. A browser session needs no local binary, so it applies the sandbox gate alone. The server's pin, when the already-resolved client reaches it, wins and is described as "this deployment pins". Otherwise the config's version is used, described as "spov's built-in default is" or "your configuration says". The resolution never builds a new client, because that can start a local server as a side effect of a version check.

`sess.Health.Version` (what one sandbox is) and the pin (what the deployment pins) answer different questions. The gap between them is what a mismatch is, so they are never collapsed.

### Two gates with different rules

**The sandbox gate is exact.** The sandbox must report the pin. The server builds the image, so a mismatch is a deployment fault. `CheckVersion` returns a `VersionMismatchError` carrying `Source`: the server's pin, the built-in default or the config file. The message names the expected version, where it came from, and what the sandbox reported, so a reader can tell the three apart. A deployment that sets `sandbox.image` to a build other than its `opencode.version` reports a pin its sandboxes do not match, so every launch warns or refuses until it states the version its image carries.

**The local client gate grades by version part** (`opencode.CompareVersions`, `Locator.Locate`):

| Local client against the pin | Result |
|---|---|
| Same version | Nothing printed |
| Same major and minor, another patch | Used, with a note naming both versions and the pin's source, for example `Using your local opencode 2.0.23; this deployment pins 2.0.21.` |
| Same major, another minor | Used, with a warning that the client may not match the server |
| Another major | Refused as `ClientVersionMismatchError` |
| A prerelease (`0.0.0-beta-*`, `0.0.0-dev-*`) or an unparseable version on either side | Exact match or refused |
| A `0.0.0-*` prerelease paired with a release | Refused with `Unbridgeable` set, and the flag does not override it |

A release is exactly `major.minor.patch` in decimal, so `2.0.21-rc.1` and `2.0` compare exactly. `--allow-version-mismatch` overrides every refusal except an `Unbridgeable` one, whose message says to install the pinned build; a pre-2.0 build and a release cannot attach to each other.

The locator looks in spov's own pinned copy (`<data dir>/bin/<version>/opencode`, which it uses without checking), then the official install directory, then `PATH`. spov does not download a client; the user installs one with OpenCode's own installer. Among candidates it prefers an exact match, then another patch, then another minor, and never picks a refused one. It returns `opencode.Located` (path, version, drift), from which `driftNote` words the note or warning. A refused client is still returned beside the error so the flag can use it. Among refused clients, an overridable one is reported over an `Unbridgeable` one, which is reported over a binary whose version could not be read. Without the flag, an overridable refusal says how to re-run with it.

`--allow-version-mismatch` is applied by each gate on its own path. `prepareTUI` waves through only a `ClientVersionMismatchError` from locating the local binary (`asVersionMismatch` matches only that type, so a sandbox mismatch is never taken for a local one), and `checkServerVersion` handles the sandbox's `VersionMismatchError` separately, continuing with a warning when the flag is given. The server publishes only its pin; the compatibility rule lives in the client.

### The server contract spov relies on

These are the shapes spov sends and reads; they are the reason a bump is checked.

- **Readiness and the version check** use `GET /api/info` (`opencode.InfoPath`): a 200 with a non-empty `version` is healthy. OpenCode 2 GA dropped `/api/health` relative to the beta, which is why another minor release warns rather than only noting.
- **The proxy heartbeat** targets the same path. Any answer short of a 5xx counts as a beat, since it reached the sandbox. A 404 or 405 is said once, naming the route and the status, so a moved endpoint cannot go unnoticed. A failure or a 5xx counts towards the "has not answered" warning.
- **Interrupt** takes `resume`, not `continue`. Every caller states the value (`interruptURL`): Stop sends `resume=true` (`ResumeOnInterrupt`) and the run-end interrupt sends `resume=false`. An absent value means false, and a stale parameter name is ignored without error, so a person's queued message would be left parked. See DL-053.
- **`/command`** takes `name` (not `command`) for pause, resume and the wall-clock bound. Otherwise OpenCode answers 400 `Missing key ["name"]`, and a job at its wall clock would not be stopped on that path.
- **`--session` on the TUI** means continue-or-create. This is why a job's attach waits for a recorded conversation (see DL-025).
- **The stored transcript** carries `{type: "idle", outcome}` once per turn end. `parseMessages`, `loopStoppedInMessages` and the timeline tolerate it: the row is kept with role `idle` and no text, the timeline drops it, and it is never a stop marker (`TestTheIdleMessageGAAddsIsKeptAndSaysNothing`, from a captured page).
- **Web search** is pinned by `websearch: {provider: "exa"}` in both session and job config (`opencode.WebSearchProvider`). Left unset, OpenCode chooses among Exa, Firecrawl, Parallel, Tavily and TinyFish, and only Exa's host is on the egress presets. No environment variable selects it.
- **Relied on, unchanged:** Basic auth, the `/api/event` envelope and `durable.seq`, the `session.execution.*` events and their `reason`, `session.inbox.enqueued`, the `/message` shapes including the synthetic stop marker, the tool part shape (`state.status`, `error.type`), the `/prompt` and `/synthetic` bodies, the `/model` object, `fs.read` and session creation. An inbox item's creation time is `time.created`. A missing `fs.read` file is a 404 (`readEvidence` accepts a 404 or a 500). The permission reply body field is `decision`, and `/session/{id}/wait` lives under `/api/experimental/` (spikes only).
- **Not used:** an inbox item moves between steer and queue with `PATCH /session/{id}/inbox/{id}` and a `{delivery}` body; spov uses neither it nor the older route pair. Possible later uses are `idle.outcome` as a durable turn end, `/message?type=` server-side filtering, and `GET /session/{id}/diff` as evidence for the deliverable gate.

OpenCode adds three endpoints behind the sandbox password: `GET /api/credential`, which returns stored secret values; `POST /api/pair` with a public `/auth/connect/{code}`, which mints a token that works as the password; and `POST /api/experimental/fs/write`, which writes anywhere. spov treats the password as full control of the sandbox. Provider keys and forge tokens live in the credential proxy sidecar and not in the sandbox's main container, so `/api/credential` there holds no real provider key (see DL-034).

### A bump is checked against the pinned build's own API

1. **The OpenAPI document is committed** at `internal/opencode/contract/openapi.json`, sorted and indented so a bump's diff reads line by line. `scripts/opencode-contract.sh <binary>` fetches it by running the binary isolated: a temporary HOME and XDG directories, bound to loopback, a throwaway password and no provider keys. The document's `info.version` is a fixed `0.0.1`, not the build, so the script also writes the binary's own version to `contract/version`.
2. **`contract.Used`** lists every OpenCode operation spov sends, as a method and the document's path template. A unit test checks each is in the document.
3. **Every fake OpenCode server in the unit tests is wrapped in `contract.Checked`**, and the recorder's non-HTTP fake calls `contract.CheckRequest`. Each request spov sends in a test is matched to an operation in `Used` and checked against the document: unknown query parameters, unknown or missing body fields, enum values and patterns. This checks what the call sites send, with no hand-written copy of the request to keep in step. A fake that tests plumbing with made-up paths stays unwrapped.
4. **`TestTheDocumentIsThePinnedBuilds`** fails until `contract/version` equals `DefaultOpenCodeVersion`, so a bump that does not refresh the document fails. The validator knows a fixed set of schema keywords and fails on a document that uses another until it learns it.
5. **Event payloads, stored messages and the plugin API are outside the spec** (the document types events as an opaque string). `TestIntegrationLocalOpenCodeProbe` runs the pinned binary on the developer's machine, isolated, with the real plugin and a fake OpenAI-compatible model. It drives the job opening, the completion tool, the loop command, a human message and the interrupt through spov's own request code (`promptURL` and `interruptURL` are shared with the steer and Stop paths), and reads the results through the recorder's projection and the supervisor's readers. It needs no Modal and no provider key. Its `probeProviderPackage` names a build-specific package and moves with a bump. A bump then runs the Modal spikes AGENTS.md names.
6. **Spikes default to the pin**, read as `contract.Version()` because `internal/config` imports `internal/sandbox`. They download the pinned package from npm, using the same release table as the image, and fail rather than skip when they cannot get the binary. A skipped spike reads as a passed one in a hurried bump.
7. **The contract package is imported only by tests.** The depguard rule `opencode-contract-only-in-tests` keeps the embedded document out of the binaries.
8. **A bump's pull request carries** the diff of `openapi.json` against the previous document and the new integrity values.

## Rationale

- The server is the only component that knows what its sandboxes will run, because it resolves the image. A client-side default is a reasonable fallback and a poor authority: it exists so a bare `spov fly --local` works, and should never be the number a hosted launch is judged against. A mismatch message that names the source of each version lets a reader see which of the three numbers (config file, built-in default, server pin) is the odd one.
- A handshake rather than a gate keeps version skew from becoming an outage. A mismatched client is usually usable, and refusing to launch would be a worse failure than the one reported.
- The two gates protect different things. The sandbox's build decides what the agent can do, so it is exact. The local client only renders the server's API, and OpenCode itself treats a client and server on different versions as a warning, with patch releases as its bug-fix channel. Naming both versions in every note keeps a patch-level incompatibility traceable when one happens.
- The wire between the GA and beta builds is incompatible in both directions, so a transitional release that supported both would add code deleted in the next one.
- Comparison against the build's own document turns "did a route change" into a unit test. Checking the requests the fakes receive covers every call site the tests already exercise. Failing loudly on a missing binary is the only safe default for spikes.

## Measurements

All taken at 2.0.22. Re-run them on a bump.

- **Image and boot (Modal):** the image builds and boots, a sandbox is healthy about 4 s after create and reports the pin, attach recovers the password, and a launch through the credential proxy works. `go test -tags integration ./internal/sandbox/ -run ToolchainImage -v`.
- **Spikes brought up to the pin:** `TestIntegrationSpovGoalPluginDrivesTheLoop` opens its run with a synthetic as a job does, since a prompt triggers the human-message hold; `TestIntegrationAttachRecoversPassword` launches with an egress policy. `go test -tags integration ./internal/sandbox/ -run 'SpovGoalPluginDrivesTheLoop|AttachRecoversPassword'`.
- **OpenAPI document size:** 140 operations in the committed document, the same count as the beta build's. `scripts/opencode-contract.sh <binary>`.
- **Idle clock:** a request to `/api/info` every 30 s resets Modal's idle clock, and a held stream does not. `go test -tags integration ./internal/sandbox/ -run 'TestIntegrationLogReadingAndIdleTimeout|TestIntegrationIdleTimeoutCountsConnectTraffic'`.
- **Interrupt resume (S-LS1):** `resume=true` on an idle session delivers a waiting steer; an absent `resume` and `resume=false` deliver nothing; a repeated prompt id returns the original record. `go test -tags integration ./internal/sandbox/ -run SLS1`.
- **Spikes passing:** S-LS2 and S-LS3 (interrupt and reject), S5 and S6 (permission replies with `decision`), the durable log, S7 (`fs.read`), S11 (model precedence), and S-K1 and S-K2 (provider-key routes). `go test -tags integration ./internal/sandbox/ -run 'SLS2|SLS3|S7FsReadShape|SKModelCallsThroughTheProxy|SKARunningOpenCode'`.
- **`/api/credential`:** in a sandbox holding every provider's key it answered `{"data":[]}`.
- **Silent renames, against the beta document:** sending `resume` on the interrupt and `name` on `/command` fails 14 and 8 contract checks respectively. `go test ./internal/opencode/contract/ ./internal/server/`.
- **Local probe:** checks event payloads, stored messages and the plugin API against the pinned binary with no Modal and no key. `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run LocalOpenCodeProbe -v`.
- **No-sandbox spikes:** the action vocabulary, S8, S10 and TUI-delivery spikes pass on the pinned build. `go test -tags integration ./internal/sandbox/ -run ActionVocabulary`.

## Consequences

- The local client may drift within the pin's major version; "the same build on both ends" holds for the sandbox only.
- A bump is more work: refresh the document, fix what the wrapped fakes report, run the probe and the spikes. In exchange, a silent wire change becomes a failing unit test.
- A new public endpoint is a surface, however small. The pin endpoint answers before authentication and can be scraped for the version.
- The client gains a call on the launch path and so a way to be slow; the bound and the silent failure keep that to the old behaviour.
- A client and a server on different versions still produce a warning. What changes is that the warning is about the right two numbers and says where they came from. Keeping a deployment and its users in step is the prepare-then-switch order.
- A new call to OpenCode needs an entry in `contract.Used` and a wrapped fake in the same change; nothing enforces that across packages. `TestOnlyAHumansOwnWordsReachThePromptEndpoint` skips the contract package, which names the prompt route and sends nothing.
- Guard tests: `TestThePinCarriesNothingButTheVersion`, `TestTheLocalBinaryIsLocatedAgainstTheDeploymentsPin`, `TestTheLocalClientIsGradedAgainstThePin`, `TestAsVersionMismatch`, `TestCompareVersions` (a table covering each row, prereleases and the beta/GA pairing), `TestTheDocumentIsThePinnedBuilds`.

## Known gaps

- Patch-level wire stability is OpenCode's convention, not something spov has measured.
- The recorder reads `GET /api/session/{id}/message` once, without a cursor, although the route takes `limit`, `order` and `cursor`. Older messages of a very long conversation may never be stored. This is a candidate for its own decision and needs checking against the page size OpenCode applies.
- The pin endpoint reports the configured version, so a deployment that overrides `sandbox.image` can run something else without the server knowing.
