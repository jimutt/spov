## Context

An interactive session is permissive because a person is present to see what happens. A job has nobody present, and the task text it runs on may be untrusted: a pull request title or an issue label can carry instructions the agent follows. spov needs a policy on what a job's agent may do, decided where the agent's tool calls are made.

OpenCode's server-side `ctx.permission.hook("evaluate")` makes that possible. A plugin hook is consulted for every permissioned action with `{sessionID, agent, action, resources, source, metadata, effect}`, where `resources` carries the shell command itself and `source` names the tool call. Setting `effect` to `deny` produces a tool part with `executed: false` and `state.error.type: "permission.rejected"`, so the hook is authoritative. The incoming effect is `allow`, because the sandbox is permissive by default, so a policy that only narrows what it is asked about inherits an allow-all baseline.

Two measured limits bound what this is worth. The session's own `/shell` endpoint answers 204 and runs the command with no evaluation. And the whole OpenCode API is reachable by anything holding a connect token, because spov's proxy fronts it for attach.

## Decision

### The hook decides, as an allowlist per kind

A job's permissions are decided in the sandbox by the `evaluate` hook of the `spov-goal` plugin (see DL-039). The policy is an allowlist, never a denylist over the allow-all baseline: the job's kind decides what is permitted and anything unmatched is denied. `PermissionsForKind` returns it. An unknown kind returns the empty policy, which denies everything, the only safe default over an allow-all baseline and the one a new kind fails into before its policy is written (`TestPermissionsForAnUnknownKindDenyEverything`).

- Every job may `read`, `glob`, `grep`, `webfetch`, `websearch`, `skill`, `subagent` and `shell`, and `external_directory` (the workspace is outside the agent's directory, so reading a file in a cloned repository asserts it as well as `read`).
- A `pr` job also gets `edit`, unscoped.
- A `report` job gets no unscoped `edit`; it may edit only under its write roots (below).
- No kind may `question`: nobody is present to answer, and an ask parks the session. At the pinned build a job's plugin decides every permission, so a job reaches `blocked` for an ask only if its permission hook failed to install.
- A denial is not a failure. The agent narrates it and carries on, and the denial is a fact for the verdict's conduct gate to read (see DL-050).
- `external_directory` stays in the job allowlist, because a session landed in a repository asserts it for `/workspace/out/*` before writing a report. The job's config file carries no permission key (see DL-038), so this grant comes only from the allowlist (`TestEveryJobKindCanReadItsOwnWorkspace`).

### The action vocabulary is read from the binary

The permissioned actions are `shell`, `edit`, `read`, `glob`, `grep`, `webfetch`, `websearch`, `skill`, `subagent`, `question` and `external_directory`. Three facts shape the policy:

- The shell action is `shell`, not `bash`. An allowlist naming `bash` denies all shell while the job still finishes, a silent total denial.
- `edit` is the single write gate. The file tools `write`, `edit` and `patch` all assert `edit`; there is no separate `write` or `patch` action. Withholding `edit` is what makes a job read-only.
- Tools that never assert a permission (todo, list, patch and the task driver itself) are not permissioned, so naming one in an allowlist protects nothing and grants nothing. The actions of two MCP resource tools (`opencode_list_mcp_resources`, `opencode_read_mcp_resource`) stay outside every allowlist.

An MCP tool's action is computed as `<server>_<tool>`, so the vocabulary is not a closed set. That is the standing reason for an allowlist: an action nobody listed is denied and not admitted by a pattern. The names are read out of a minified bundle and are not stable API. `ActionVocabularyVersion` records the build they were read from, and `TestIntegrationActionVocabulary` re-reads them from the build under test and fails when an allowlist names an action that build does not assert. It downloads the published binary and creates no sandbox, and keeps `bash` and `write` as named negative cases. Matching is confined to `assert({action: ...})` call sites and the variables they resolve to, because the bundle carries unrelated `action:"..."` fields (an audio-stream error object has `action:"write"`).

### A deny list for the sandbox's own credentials

A narrow deny list sits inside the allowlist: the git credential store, the tea, gh and glab config directories, OpenCode's auth store and the plugin file itself (`denyPatterns`). It is matched against the resources of every action, not only `read`, so the allowlist can grant `external_directory` without reaching those paths. It is checked first. Patterns are runtime paths (`/root/...`), as the agent sees them, and not the entrypoint's `$HOME` form: a pattern carrying a literal `$HOME` matches nothing, and a test that only asserted a pattern was present would pass on protection that does not exist. The test asserts what each pattern matches, and that granting `external_directory` left the credential paths refused (`TestEveryJobKindCanReadItsOwnWorkspace`).

The decision scans the untruncated resources. Truncating before matching let a command longer than the cut-off carry a denied path in its tail; truncation belongs only in the evidence log.

### An incoming deny is never relaxed

OpenCode has a built-in `evaluate` hook that applies configured and organisation policies and runs before spov's. spov's hook always writes its own effect, so it would turn a policy deny into an allow. The plugin's effect therefore replaces only `allow` and `ask`; a deny that reaches the hook is kept (`TestAnIncomingDenyIsNeverRelaxed`). spov writes no such policies, but a deployment that adds them keeps them. A kept incoming deny counts as a denial for the repeated-denial guard and its evidence line carries `incoming: true`. A session-level `permissions` ruleset with a deny skips the hook as a config deny does, so spov never sets `session.permissions` on a job's session.

### A report job may edit under its write roots

A report job's only deliverable is files under `/workspace/out`, and `edit` is the only action the file tools assert. Withholding it entirely meant the one file the job must write could be written only through the shell, with nothing telling the agent so: a report job called `write` 91 times, each denied, and never tried the shell.

So an `edit` is allowed for a report job when every entry in `resources` resolves inside `/workspace/out` or the scratchpad `/workspace/.scratch` (`reportWriteRoots`; see DL-037). Empty, non-string or unreadable resources are denied. The plugin receives the session's directory in its config and resolves each resource against it, removing `.` and `..` segments, before comparing: `..` cannot escape and `/workspace/output` does not count as `/workspace/out`. The raw string is never compared (`TestAReportJobMayEditOnlyUnderItsWriteRoots`). The report goal tells the agent that the repositories are read-only and where it may write. Changing either location is a change in Go and in the plugin, guarded like the other paired names.

### The repeated-denial guard

The plugin counts denials of the same call: the same action and the same resources, with no allowed evaluation between. Any allowed evaluation resets the count, except `external_directory`, which OpenCode asserts and the allowlist grants before every edit of a path outside the session's directory; counting it as a break would let a loop writing `/tmp/report.md` run forever.

- **At five denials (`DenialNoteAt`)** the plugin sends one synthetic note (`resume: false`), at most once per distinct call, to the session the call came from. It names the denied action and resource and says the denial is policy and repeating the call will not change it; for a report job it also names the write roots and says the shell can write there too.
- **At ten (`DenialStopAt`)** the plugin stops the loop through the same announcement as any stop, with reason `denied`, and the call as the marker's payload up to 4000 characters. The stop goes to the job's own session, never a subagent's.
- **While a person holds the loop** (paused for a takeover; see DL-052) denials are counted but nothing is noted or stopped, since ending the run under a person who is steering would deliver it mid-conversation.
- **The verdict** opens with the call, taken from the first stop marker only, redacted and then cut at 300 characters (`deniedNote`). A denied shell command can carry a credential, and cutting before redaction could leave a token below the length its pattern needs. The web timeline words the reason as "the same call kept being denied" (`stopNote`).

The note works because a `resume: false` synthetic sent from inside the permission hook is enqueued with `delivery: "steer"` and reaches the model at its next step. The evaluation carries `sessionID`, so the plugin addresses the note without waiting for an execution event. Neither the note nor the stop is awaited inside the hook, which decides synchronously.

### What this is, and what bypasses it

The hook is a guardrail on what the model decides, never a boundary. The session's `/shell` endpoint and the proxied API bypass it, and the shell can write anywhere. Containment is the sandbox boundary, the egress policy Modal enforces outside the sandbox (see DL-031) and the scope of the tokens the sandbox holds (see DL-034). Job egress defaults to `open`, so the policy is not what stops a hostile instruction from reaching a host. `permission.evaluate` must never be cited as the control that makes a job safe, and nothing may relax egress or token scope because of it.

The plugin is never a precondition. A job whose plugin did not load runs on OpenCode's own defaults, and nothing is to be fixed by requiring the plugin to load: confirming registration needs a sandbox read the supervisor does not make. A missing hook is a fact for the verdict, not a reason to refuse to start.

One path is fail-open, and nothing here can close it. The hook's only channel is the assignment to `evaluation.effect`; if that throws or does not take, the incoming `allow` stands. The plugin records `permission.not.applied` as a fact for the verdict. It is the one path that defaults permissive in a deny-by-default design.

## Rationale

- Moving the decision into spov-owned code inside the sandbox is per action, expressible per job kind, and exists even when the server is driven over HTTP and no CLI flag is involved.
- An allowlist follows from the measured allow-all baseline and from the vocabulary being open. A denylist over a permissive baseline looks right and is wrong.
- Stating what the hook is not is as much of the record as what it is. A control that stops the agent's own tool calls reads at a glance like a sandbox policy, and treating it as one would leave `/shell` and the proxied API as holes nobody remembered.
- The repeated-denial guard belongs in the plugin because only it sees every permission evaluation as it happens. The note comes before the stop because the denial message is OpenCode's own and cannot be reworded, and the loop came from not knowing the alternative: one note lets a capable model recover and the stop covers one that cannot. Five identical denials in a row are not exploration, and ten leaves room for the note to be read. Both thresholds are constants in one place.
- A path grant narrower than `edit` keeps what withholding it was for, that a report job does not change the repositories, and removes the trap.

## Measurements

- **Hook authority (S3, beta build 0.0.0-beta-18866):** `ctx.permission.hook("evaluate")` is authoritative, a deny yields `executed: false` and `permission.rejected`, and the session's `/shell` endpoint bypasses the hook entirely (204, no evaluation). `go test -tags integration ./internal/sandbox/ -run PluginDecidesPermissions`.
- **Action vocabulary (read from the published binary, beta build 0.0.0-beta-18684):** eleven real actions; eight of thirteen guessed names do not exist (`bash`, `write`, `patch`, `list`, `todo`, `todowrite`, `todoread`, `task`). Unchanged at the 2.0.22 pin. `go test -tags integration ./internal/sandbox/ -run ActionVocabulary`.
- **Edit resource shapes (S-W1, beta build 0.0.0-beta-19151, unchanged at 2.0.22):** a path inside the session's directory arrives relative to it however written (`/workspace/out/abs.md` from a session at `/workspace` is `["out/abs.md"]`). A path outside arrives absolute (from `/workspace/repo`, `../out/r.md` is `["/workspace/out/r.md"]`), preceded by an `external_directory` evaluation for `/workspace/out/*`. Creating directories is one `edit` of the file's path. A `patch` over two files asserts one `edit` per file with one resource. `go test -tags integration ./internal/sandbox/ -run SWEditResourceShapes`.
- **Mid-turn synthetic (S-W2, same builds):** a `resume: false` synthetic sent from inside the permission hook is enqueued as `steer` and reaches the model at its next step; in the spike the model ran the command the note named within the same turn. `go test -tags integration ./internal/sandbox/ -run SWSyntheticMidTurn`.
- **Denial thresholds:** note at 5 identical denials, stop at 10, payload 4000 characters, verdict quote cut at 300 after redaction. `go test ./internal/opencode/ -run TestARepeatedDenialIsNotedOnceThenEndsTheRun`.
- **The motivating run:** a report job repeated a denied `write` 91 times in one turn and would have run to its wall clock.

## Consequences

- A job stuck on a denial ends in minutes instead of at its wall clock, and its verdict says why. `denied` is a stop reason the verdict and the web timeline word.
- A report job can create and revise its report with the file tools and keep working files in the scratchpad.
- The entrypoint writes the interactive config's workspace grant for interactive sessions only; the two mechanisms never both answer for a job.
- Guard tests: `TestPermissionsForAnUnknownKindDenyEverything`, `TestEveryJobKindCanReadItsOwnWorkspace`, `TestAReportJobMayEditOnlyUnderItsWriteRoots`, `TestAnIncomingDenyIsNeverRelaxed`, `TestARepeatedDenialIsNotedOnceThenEndsTheRun`, `TestTheVerdictNamesTheRepeatedlyDeniedCall`.

## Known gaps

- A `patch` that writes one allowed and one denied file asserts one `edit` per file, so repeating it resets the denial count every time, and that loop is not caught.
- The hook fails open when the effect write fails, as above.
- The shell can write anywhere, and a pull request job's unscoped `edit` and shell are bounded only by the tokens and egress it runs with.
