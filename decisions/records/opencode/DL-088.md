## Context

A kept exit snapshot (DL-085) holds the main container's whole filesystem: `/workspace` with every clone and its uncommitted changes, installed packages and caches, `/tmp`, and OpenCode's own store under `~/.local/share/opencode`. S-SR1 showed a restored OpenCode lists its conversations with the same messages, so nothing has to be imported, and its durable log continues where it was. The snapshot holds no process, and no secret when the proxy was on (DL-084). It does hold the OpenCode binary the run had, the previous run's CA in the trust stores, and the files the entrypoint wrote then.

The entrypoint (`internal/opencode/entrypoint.go`) assumes a fresh image. It waits for the proxy, installs the CA, clones every repository, writes the generated `AGENTS.md`, the plugin and the config files, starts add-on services and then OpenCode.

## Decision

**The choice.** A resume boots from the snapshot of the session's newest run that reached `running` (DL-085) when all of these hold:

- that run's snapshot is `kept` or `pending`, not `none`, `failed` or `deleted`;
- the run ended within the retention (DL-086);
- the run's OpenCode version is the deployment's current pin. The snapshot carries the binary it ran, and the sandbox must report the pin exactly (DL-035).

Otherwise it takes the transcript path (DL-089). An older run's snapshot is never used, since it would bring back neither the later run's work nor its conversation.

**A pending snapshot.** When the chosen run's snapshot is still `pending` (a resume within a minute or two of the stop), the resume collects it itself, through `Provider.ExitSnapshot` with a 60 s wait, before anything else starts. If it is kept, the resume goes on from it. If it fails or the wait runs out, the resume is refused with 409, and the view then offers the transcript. A person confirms that knowingly; a resume never falls back by itself.

**What the client sees.** `SessionView.resume` is `{mode: "snapshot" | "transcript", pending?, until?}`. `pending` is set while the snapshot is being collected, and `until` is the latest the snapshot is kept: its retention end, which the cap may bring forward (DL-086). It is present only for the session's owner, and only when the session is resumable (DL-087). It is computed from the batched runs read of the listing (DL-085) and is part of `decorationStamp` (DL-012), so a kept, pending or pruned snapshot refreshes the list.

**The boot.** The new sandbox is created from the snapshot's image ID (`Spec.ImageID`, DL-084), with the recorded spec otherwise and `Image` naming the launch's image. It is created with `ExitSnapshot` again under DL-084's rule, so a resumed session can be resumed again. The entrypoint is given `SPOV_RESUME=snapshot`, and with it:

- it waits for the proxy, then installs the run's new CA (DL-087) in place of the old one. `MainCAFile` is replaced and the system bundle and the Java trust store are rebuilt from it (`update-ca-certificates --fresh`, then the trust store), rather than appended to as `InstallCACommand` does;
- it skips every clone and checks that each recorded clone directory exists. A missing one fails the run with exit 96 (`SnapshotMismatchExitCode`), naming the directory;
- it writes the placeholders, the git and forge CLI config, the routed credentials' files, the plugin and `AGENTS.md` again, since a run's credentials and routes may differ from the last. `AGENTS.md` loses any transcript-resume section an earlier run had (DL-089);
- it starts the add-on services and then OpenCode, which opens its own store.

**A missing conversation.** If a conversation the store holds is not in the restored OpenCode's listing, it is imported as in DL-089 before the session is `running`, and the import is noted in the log.

## Rationale

The snapshot is the better resume whenever it exists: the work in progress comes back, not only the conversation. Choosing it on the server, and showing the choice in the view before a resume, lets the page word the confirmation honestly (DL-090). Waiting for a pending snapshot keeps a quick stop-and-resume from losing the very work snapshots exist to keep.

Rebuilding the trust stores, rather than adding to them, keeps the previous run's CA from being trusted again. Its key is deleted with the stop, but a bundle that only ever grows is wrong to leave. Rewriting the configuration files on every boot keeps a resumed sandbox in step with the credentials resolved at resume. Skipping the clones is what keeps uncommitted work, and checking the directories catches a snapshot that is not what the run recorded.

## Consequences

- The entrypoint gains a resume mode and exit 96. `TestTheReservedDirectoriesAgree` still holds, since no clone runs.
- A change to the plugin or the config shape takes effect on resume, because those files are rewritten at boot.
- A pin bump makes every older snapshot unusable for resume, and those sessions resume from the transcript until their snapshots age out. Upgrading the binary inside a restored sandbox was rejected: it would open an older OpenCode store with a newer build, which nothing has measured.
