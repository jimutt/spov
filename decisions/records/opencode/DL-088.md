## Context

A kept exit snapshot (DL-085) holds the main container's whole filesystem: `/workspace` with every clone and its uncommitted changes, installed packages and caches, `/tmp`, and OpenCode's own store under `~/.local/share/opencode`. S-SR1 showed a restored OpenCode lists its conversations with the same messages, so nothing has to be imported. It holds no process, and no secret when the proxy was on (DL-084).

The entrypoint (`internal/opencode/entrypoint.go`) assumes a fresh image. It waits for the proxy, installs the CA, clones every repository, writes the generated `AGENTS.md`, the plugin and the config files, starts add-on services and then OpenCode.

## Decision

**The choice.** A resume boots from the snapshot of the session's newest run when all of these hold:

- its snapshot is `kept`, not `deleted` or `failed`;
- the run ended within the retention (DL-086);
- the run's OpenCode version is the deployment's current pin. The snapshot carries the binary it ran, and the sandbox must report the pin exactly (DL-035). Each run records its version, `session_runs.opencode` (DL-085).

Only when there is none does it take the transcript path (DL-089). `SessionView.resume` tells a client which one is available before it asks: `{mode: "snapshot" | "transcript", until?}`, where `until` is when the snapshot would be pruned. It is absent when the session cannot be resumed.

**The boot.** The new sandbox is created from the snapshot's image ID, with the recorded spec otherwise. It is created with `ExitSnapshot` again under DL-084's rule, so a resumed session can be resumed again. The entrypoint is given `SPOV_RESUME=snapshot`. With it, the entrypoint:

- waits for the proxy and installs the CA if DL-087 made a new one (with the kept CA, the trust stores already hold it);
- skips every clone and checks that each recorded clone directory exists. A missing one fails the resume with exit 96 and the directory's name;
- writes the placeholders, the git and forge CLI config, the routed credentials' files and `AGENTS.md` again, since a run's credentials and routes may differ from the last;
- starts the add-on services and then OpenCode, which opens its own store.

**A missing conversation.** If a conversation the store holds is not in the restored OpenCode's listing, it is imported as in DL-089, and the import is noted in the log.

## Rationale

The snapshot is the better resume whenever it exists: the work in progress comes back, not only the conversation. Choosing it on the server, and showing the choice in the view before a resume, lets the page word the confirmation honestly (DL-090).

Rewriting the configuration files on every boot keeps a resumed sandbox in step with the credentials resolved at resume. Skipping the clones is what keeps uncommitted work, and checking the directories catches a snapshot that is not what the run recorded.

## Consequences

- The entrypoint gains a resume mode and exit 96. `TestTheReservedDirectoriesAgree` still holds, since no clone runs.
- A snapshot is bound to the spov build that wrote its entrypoint files only through the files rewritten at boot. A change to the plugin or the config shape takes effect on resume.
- A pin bump makes every older snapshot unusable for resume, and those sessions resume from the transcript until their snapshots age out. Upgrading the binary inside a restored sandbox was rejected: it would open an older OpenCode store with a newer build, which nothing has measured.
