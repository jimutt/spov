## Context

A sandbox runs one OpenCode server, started by an entrypoint script that spov renders (`opencode.Entrypoint`). The script has several jobs: install the proxy's CA and wait for the sidecar, write git credentials and identity, clone the session's repositories, write the workspace guide, config and plugin, and start the server.

OpenCode's defaults do not fit a remote sandbox. `serve` listens on loopback and an ephemeral port. The TUI sends its own local directory as the initial directory, which does not exist on the server, so OpenCode falls back silently to the server's working directory. A provider key POSTed to OpenCode's credential API is stored in its database and from then on outranks the environment variable. `{env:...}` interpolation in config is not JSON-escaped.

Clone URLs and directory names come from remote forge APIs, and a launch pays the clone time on the path the user is watching.

## Decision

### Starting the server

- **Shell.** The command is `bash -c <script>`, never `bash -lc`: a login shell sources `/etc/profile` and resets `PATH`. `PATH` and `HOME=/root` come through the sandbox's `Env`, and every binary is invoked by absolute path. The script begins with `set -e`.
- **Binary.** The server runs in place from `/root/.opencode/bin/opencode` (see DL-032 and DL-035), as `exec /root/.opencode/bin/opencode serve --hostname 0.0.0.0 --port 4096`. `exec` ties the server's lifetime to the sandbox's.
- **Port.** Fixed at 4096 (`DefaultPort`), with the sandbox's `EncryptedPorts` set to match. The server is plain foreground `serve`, not `--service`, which keeps readiness probing simple.
- **Working directory.** The server starts in the landing directory, which is `/workspace` unless a session names a cloned repository (see DL-037). `Validate` rejects a landing that nothing clones, because the `cd` would otherwise fail under `set -e` and surface only as a bare readiness failure.
- **Order.** Add-on services start first, in the background (see DL-033). When the proxy sidecar is present, the entrypoint installs its CA and waits for `proxy:3128` before anything else goes out, exiting with code 97 if it never answers (see DL-034). Then come git credentials and identity, the clones, `mkdir` of the scratchpad and the report directory, the workspace guide, the OpenCode config, the plugin for a job, and the forge CLI logins.

### Credentials

- `OPENCODE_PASSWORD` and provider keys reach the entrypoint only as environment variables, delivered through an ephemeral Modal Secret (`EnvConfig.Secrets`); `PATH` and `HOME` go through the plain `Env`. The split protects metadata and logs: `Env` values are ordinary sandbox metadata in Modal's control plane, while Secret contents are redacted there. Inside the sandbox both arrive identically, so it does not protect against a hostile process in the sandbox.
- Keys are never POSTed to OpenCode's credential API (a stored credential permanently outranks the environment variable) and never interpolated into config. Rotating a key means recreating the sandbox. `EnvConfig.Secrets` refuses a provider key that would overwrite `HOME`, `PATH`, `OPENCODE_PASSWORD` or a proxy variable, and an empty password, since an empty password disables OpenCode's authentication.
- Only the catalogue's provider variables are injected (`prep.ProviderKeyEnvs`; see DL-013). Without a model key the server starts and reports healthy, but the agent cannot reach a model, so `spov fly` warns.
- Nothing credential-shaped appears on a command line. `/proc/1/cmdline` holds variable names only, because the script references `"$VAR"` and the shell expands it. Credential files are mode 0600, and clone URLs carry no credential, so `git remote -v` is clean. Forge CLI logins read their token from an environment variable and never have it interpolated into the script (`TestEntrypointNeverWritesATokenIntoTheScript`).
- The sandbox is single-tenant: only `root` and `nobody` exist.

What this protects and what it does not. With the proxy sidecar, the forge tokens and provider keys are held by the sidecar and the agent's environment holds only `OPENCODE_PASSWORD` (see DL-034). The agent has a shell and the server runs with that password in its environment, so the agent can read it. That is acceptable because the password opens only the sandbox's own OpenCode server, which the agent already controls, and the sandbox exposes no ports (see DL-030). Without the sidecar (a local server built without the embedded proxy, or a hosted one run with `SPOV_TOKENS_IN_SANDBOX=1`), the forge tokens and provider keys are in the main container's environment and credential files as well. A prompt-injected agent, from a hostile README in a cloned repository say, could then exfiltrate them, and what bounds the damage is each token's scope: a repository-scoped token by default.

### Cloning

1. **Hardened command.** Each clone is `git clone --depth 1 -- <url> <dir>`, with the URL and directory single-quoted (`shellQuote`). Quoting alone is not enough: a quoted `--upload-pack=<cmd>` is one shell word but still an option to git, which runs the command (confirmed exploitable). The `--` separator makes git read the URL as an operand. `Validate` also rejects a URL or directory beginning with `-`, the `ext::`, `file://` and `file::` transports, which name a command or reach the local filesystem, and a URL containing a newline, carriage return or NUL. It rejects directories that are absolute, unclean, empty or traverse out of `/workspace`, duplicate directories, and the names spov reserves (`out`, `.scratch`).
2. **Parallel, capped at 5.** `CloneConcurrency` is 5 and is not configurable. A sandbox defaults to 0.5 CPU and 2 GiB, so an unbounded fan-out would put a `git` process and its `git-remote-https` child for every repository on half a core. The script starts clones in the background in batches of five and drains each batch before starting the next. A single clone is run plainly.
3. **Waited on by PID.** A bare `wait` after `&` returns success even when a job failed, including under `set -e`. The script collects each `$!` and runs `for p in $pids; do wait "$p"; done`, so one failing clone exits the script with that clone's status (128 in the measured case) before the server starts. A sandbox never boots with a missing or half-cloned repository. `TestScriptFailsWhenACloneFails` and `TestScriptFailsInASecondBatch` check this.
4. **Independent.** Each clone gets a distinct directory, and the git credential store is written once before any clone and only read afterwards. The list's order still decides the default landing, computed before any clone starts; completion order is unspecified.

### Readiness

Modal probes the port with a TCP probe, then spov polls `GET /api/info` until it answers 200 with a non-empty version (`Client.WaitHealthy`; see DL-035). A 401 ends the wait, since retrying cannot fix a wrong password.

## Rationale

- An explicit working directory is the only reliable control over the TUI's landing directory.
- Env-only keys leave no secret on disk and avoid the stored-credential precedence trap.
- Clones are network-bound and independent, so parallel cloning has no downside except the wait semantics, and the per-PID wait keeps the property that a failed clone fails the launch immediately and legibly, where a bare `wait` would turn it into an empty directory found much later.
- The cap keeps the win for every realistic session, since the speed-up is bounded by the slowest clone well before it is bounded by the cap, while a pathological repository list cannot exhaust the sandbox. A knob would be configuration nobody has asked for.

## Measurements

- **Start-up on Modal:** create to TCP-ready 3.2-3.4 s including a shallow clone, and to healthy 3.9-4.1 s. A separate spike read TCP ready 2.5-3.7 s and healthy 3.2-4.4 s after create. The server process's working directory is the landing directory and it reports the pinned version. `go test -tags integration ./internal/sandbox/ -run EndToEnd` (creates billable sandboxes).
- **Parallel clones:** four clones of about 2 s each took 8.0 s sequentially and 2.0 s in parallel.
- **Concurrent credential store:** five concurrent clones left `/root/.git-credentials` byte-identical.
- **Wait semantics:** three background jobs, one failing, with a bare `wait` under `set -e`: the script exits 0 and carries on. With the per-PID wait, one failing clone exits 128 and never reaches the server start, measured in the exact `bash -c` form the sandbox uses. `go test ./internal/opencode/ -run 'TestScript'`.
- **Hostile URL:** git clone with a `--upload-pack` URL ran the command when it was only shell-quoted, and ran nothing with the `--` separator and the URL validation. `go test ./internal/opencode/ -run TestCloneURLsCannotBecomeGitOptions` drives real git and asserts nothing executes; `TestScriptQuotingAgainstRealShell` runs substitution, backtick and embedded-quote URLs through a real shell.

## Consequences

- Clone stderr interleaves. This is invisible today because the sandbox exposes no stdio, but a reader of the output would see it mixed. Per-repository log files would fix it, at the cost of losing the output unless something reads them back.
- The error that fails the entrypoint may come from any clone in a batch, not the first in list order.
- With more repositories than the cap, the tail waits for a slot.
- A key change needs a new sandbox.
- Guard tests: `TestEntrypointOrdering`, `TestEntrypointRunsTheBinaryInPlace`, `TestEntrypointCommandIsNotALoginShell`, `TestEntrypointValidate`, `TestEntrypointQuotesCloneURLs`, `TestCloneURLsCannotBecomeGitOptions`.
