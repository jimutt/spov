## Context

A job needs an agent that keeps working toward a goal across turns, remembers the goal after OpenCode compacts the conversation, and ends on a signal the supervisor can read. OpenCode runs one turn at a time and has no notion of a standing goal, so the sandbox needs something running beside the agent to supply those. That something is the `spov-goal` plugin, a server-side OpenCode plugin.

Three properties of the environment shape it:

- The published V2 plugin package's context is much narrower than the in-repo one and cannot drive a loop, so the plugin must not depend on it.
- A plugin's own `prompt` call arrives as a `session.inbox.enqueued` item of type `user` with no item id, exactly like a human's message, so nothing can tell it from a person's. A `synthetic` item arrives typed `synthetic`.
- Whether compaction drops a standing goal is not stable. Two runs minutes apart on the same build disagreed, because what survives is whatever the summariser kept.

The plugin runs inside a sandbox that also runs an untrusted agent. It is spov-owned code and holds no credential of its own.

## Decision

### One self-contained file, written once at start

`internal/opencode/plugin/spov-goal.js` is one plain-object default export with no import of any OpenCode package (`node:` built-ins are allowed; `@opencode-ai/plugin` is what it must not import). The entrypoint writes it to `$HOME/.config/opencode/plugins/spov-goal.js`, where it loads with no config entry and no npm cache (`TestPluginImportsNoOpenCodePackage`). Its source is embedded in the server binary and written at sandbox start, not baked into the image. Images are built by an operator step and the server deploys often, so the plugin in a sandbox always matches the server that launched it. OpenCode watches local plugin files and re-imports them when they change, which would reset the loop and denial state, so nothing rewrites the file during a session.

The job's config is rendered into the source, in place of one `SPOV_GOAL_CONFIG` token that appears exactly once (`Plugin.Source`, `pluginConfig`). One file is one thing for the entrypoint to place, and the plugin cannot load against a config that failed to arrive. The config holds the kind, the goal text, the allowlist, the check, the evidence paths and the tool and event names; its Go and plugin spellings are kept equal by guard tests (the stop marker, completion tool, check event, completion event and pull request tool names; see DL-048 and DL-051).

The goal is user text inside a JavaScript literal. `json.Marshal` makes the literal safe because it escapes U+2028 and U+2029, which JavaScript reads as line terminators where JSON does not, and `<`, `>` and `&`. Any replacement encoder must escape the same five. `TestPluginSourceEscapesTheGoal` counts the JavaScript lines the rendered source spans, since a helper that splits on terminators stops at the very character under test. The source reaches the sandbox through a quoted heredoc, and the entrypoint refuses a source containing the terminator `SPOV_PLUGIN_EOF`, because a goal carrying it would end the heredoc early and the shell would run the rest as commands (`TestEntrypointRefusesAPluginContainingTheHeredocTerminator`).

If the plugin never loads, nothing re-prompts and the job is a single pass the server still judges. The plugin is never a precondition for a verdict.

### Continuation is a synthetic item, never a prompt

The plugin continues a run with `ctx.session.synthetic({sessionID, text, resume: true, delivery: "queue"})` on `session.execution.succeeded`, filtered to events carrying `data.sessionID`. It never calls `ctx.session.prompt`, which would arrive as a `user` item and look like a human takeover, moving the job to `steered` on its own first turn (`TestPluginContinuesWithSyntheticAndNeverPrompt`). Every continuation arrives typed `synthetic`, so a long job never drifts into `steered`. The `queue` delivery means a continuation never goes ahead of a message a person queued first, an interrupt included (see DL-052). No count of continuations ends a run (see DL-049).

Continuation is in-session: context accumulates and OpenCode's own compaction handles it, while re-assertion keeps the goal alive. Rotating to a fresh session is a trade left open. The cost is that context and cost per turn grow through a job's life.

### The goal is re-asserted on every request

The plugin registers one handler for both the `context` hook and the `compaction` hook and pushes the goal onto `system[]` each time. OpenCode fires `context` for primary requests only, and compaction, generate and title have separate hooks, so a compaction summary is written knowing the goal only because the handler is on `compaction` too (`TestTheGoalReachesCompactionAsWellAsEveryRequest`). The handler never sets `result`. It is unconditional because, with compaction unstable, there is no trigger worth reacting to.

`system[]` entries are `{type: "text", text}` objects. The handler pushes a string when the existing entries are strings or the array is empty, and an object shaped from a neighbour (carrying `text` or `content`) otherwise, so it survives either direction of change. An entry of an unrecognised shape is skipped, with a `goal.push.skipped` evidence line and a console line, since the evidence file is not collected for a cancelled job. `TestTheGoalIsInjectedWhateverShapeSystemIs` drives the real hook under a JavaScript runtime against every candidate shape. The reason: if an inferred shape is wrong, the goal is never injected and a job spends all its turns reporting no standing goal. A source-text assertion cannot catch that class of bug.

The goal text the plugin re-asserts is the preamble, the job's goal verbatim, the workspace orientation, the kind's deliverable note, and the instruction to end by calling the completion tool. It rides on the re-asserted goal and not on the opening turn, so compaction cannot lose the path a report job must write to.

### The workspace orientation, and the branch note

Every job, whatever its kind, gets the same orientation text (`Plugin.workspaceNote`): the sandbox is prepared by spov, each cloned repository with its directory, host and forge CLI, and a pointer to `/workspace/AGENTS.md` for the rest. It states facts and no policy, and does not duplicate the generated file. It assumes the session works from `/workspace` (see DL-037). A plugin built without a repository list renders no orientation, which is what a test's plugin has.

The agent reliably reads what it is sent but may never read the filesystem. In the measured failing runs the agent never referenced `/workspace` or the generated `AGENTS.md` in 279 events. It used 29 tool calls on a one-line README change, mostly orientation, and cloned a repository it was not given.

A `pr` job also gets `branchEpilogue`: work on a new branch, never commit or push to the default branch, one branch per pull request, and record each pull request with the `spov_pull_request` tool as it opens (see DL-051). On GitLab a note says a pull request is a merge request.

Both are guidance, not containment. The orientation and the branch note must carry no credential: `WorkspaceRepo.Slug` is `owner/name` and never carries one, because a clone URL with userinfo would put a token in every request. An agent that ignores them can clone whatever its token reaches and push to the default branch. The boundary is the token's scope, the egress policy and branch protection on the forge, which is outside spov. Denying `git push` in the permission policy was rejected, because the deny list is a substring match on the command and would catch `git push origin main` while missing a bare `git push` with an upstream set, which is enforcement in appearance only.

### The /spov-goal command and the pause notice

`/spov-goal status|pause|resume|stop|bound` is registered through `ctx.command.transform` and invoked as `POST /api/session/:id/command {name: "spov-goal", text: "<args>"}` (see DL-035 for the `name` field). The handler receives `{sessionID, prompt: {text}, delivery}`. The endpoint answers 204 and runs the handler asynchronously, so it returns nothing, and the plugin's replies travel as session content: a synthetic item with `resume: false`, which starts no turn. An attached human sees a reply at once. The server sees it only when the recorder next reads `/message` (a turn end, or the recorder's final read), so a reply is never a channel for anything the supervisor needs promptly.

`pause` sets `loop.paused`, which stops further continuations and does not move the job row. "Paused" in the plugin and a job's lifecycle state are different facts (see DL-045). A turn already in flight keeps running, because a `resume: false` synthetic starts no turn and cannot retract one. `PAUSE_NOTICE` says so, and is addressed to the agent:

- the loop will not send another continuation, and this does not stop work already running;
- the agent is being paused by the person watching, should finish the tool call it is in, take no new action and not declare the goal complete;
- someone will resume it or say what to do next;
- it names no tool, since an agent that reached for the completion tool would end the job instead of suspending it.

The last two matter because an agent told to stop with no way to comply talks itself out of it; the measured reasoning included "there's no way to wait". A `resume: true` synthetic was rejected as the pause reply: it would start a turn, the opposite of a pause. The notice is a guardrail on an honest run, not a mechanism. A synthetic item is delivered into context and not interrupted into inference, so an agent in a long tool call may not see it until that call returns, and a person can still press ESC or use Interrupt (see DL-053). The supervisor's own pause uses the same handler and so the same wording. `PAUSE_NOTICE` is a constant so a test can read it; four properties are pinned (it does not claim to stop what is running, it is addressed to the agent, it says someone will resume, and it neither names the completion tool nor invites declaring completion), and `TestPausingSendsTheNoticeWithoutStartingATurn` drives the real `setup()` to catch a notice declared and never emitted or sent with `resume: true`.

### What else the plugin carries

The permission hook and incoming-deny rule, the denial note, and the write roots are in DL-040. The completion tool, the check, the evidence and outcome files, takeover holds and turn retries are in DL-048, DL-050, DL-052 and DL-054. Each hook is attached inside its own `try`, so a build that lacks one domain of `ctx` still loads the plugin and attaches the rest, and the `setup` evidence line lists the domains the build gave it (`TestAMissingToolDomainDoesNotStopThePluginLoading`). The plugin's behaviour is tested by running its real `setup()` under bun or node with a fake `ctx`, not by matching source text.

## Rationale

- The file form avoids the packaging hazard: no package spec to pin, no cache directory to seed, no `HOME` or XDG mismatch between image build and runtime.
- Routing the plugin's own sends through `synthetic` costs nothing, since it drives a turn just as well, and gives a takeover signal that needs no bookkeeping: anything typed `user` is a person.
- Re-asserting unconditionally is cheaper to reason about than reacting to compaction.
- The orientation belongs in what the agent is sent for the same reason the goal does.

## Measurements

- **Plugin loading (S1, beta build 0.0.0-beta-18866):** a plain object default export in a `.js` file under the plugins directory loads with no config entry, no npm cache and no import of the plugin package. The published V2 context cannot drive a loop. `go test -tags integration ./internal/sandbox/ -run SpovGoalPluginDrivesTheLoop`.
- **Compaction (S2):** whether compaction drops the goal is not stable; two runs minutes apart on the same build disagreed, and a manual compaction is admitted as a control item into the run in flight. `go test -tags integration ./internal/sandbox/ -run PluginSurvivesCompaction`. At 2.0.22 on Modal the compaction hook fires with a `system[]` of `{type:"text",text}` entries that takes the goal.
- **Prompt against synthetic (S4):** the plugin's own prompt arrives as `session.inbox.enqueued` with item type `user` and no item id. A synthetic arrives typed `synthetic`, and with `resume: true` schedules a turn on an idle session. `go test -tags integration ./internal/sandbox/ -run PluginSeesTheHumanInbox`.
- **Three continuations (S5, beta build 0.0.0-beta-18684):** three `ctx.session.synthetic({resume: true})` continuations produced four turns (the opening one plus one per continuation), and every item arrived typed `synthetic`. `go test -tags integration ./internal/sandbox/ -run S5SyntheticLoopAndPermissionAnswer`.
- **Shape of `system[]` (S8):** read out of the downloaded binary, with no sandbox and no key: at 2.0.22 an entry is an object with a `text` field. `go test -tags integration ./internal/sandbox/ -run S8ContextSystemShape`.
- **Command endpoint:** `POST /api/session/:id/command` answers 204 and runs the handler asynchronously, returning nothing.
- **At 2.0.22 on Modal:** the real plugin attaches both hooks, decides permissions, sustains two continuations, sees a human inbox item and a takeover; the action vocabulary and edit resource shapes are unchanged. `go test -tags integration ./internal/sandbox/ -run 'PluginSurvivesCompaction|ActionVocabulary|SWEditResourceShapes|SWSyntheticMidTurn'`.
- **A `pr` agent without the branch note:** observed once, it committed, ran `git push origin main`, then created a branch and a redundant pull request. Nothing detected it, because the conduct gate reads refusals and the push was not refused.
- **A pause on a running job:** the agent carried on for another four tool calls, because the turn in flight cannot be retracted.
- **Aborted tool-part state (S6):** an aborted state comes from the session's reply endpoint, so an abort may be reachable from the plugin. It is not used.

## Consequences

- The entrypoint command grows by the plugin's source; it is already the place that writes `AGENTS.md`, git credentials and the config.
- `/spov-goal status` answers into the session rather than to the caller. A server that wants status reads it back from the store, late.
- A synthetic item shows in the transcript, so the web transcript derives a speaker role for it (see DL-058).
- The goal text grows by a few lines per request.
- Guard tests: `TestPluginImportsNoOpenCodePackage`, `TestPluginContinuesWithSyntheticAndNeverPrompt`, `TestPluginSourceEscapesTheGoal`, `TestEntrypointRefusesAPluginContainingTheHeredocTerminator`, `TestTheGoalIsInjectedWhateverShapeSystemIs`, `TestTheGoalReachesCompactionAsWellAsEveryRequest`, `TestPausingSendsTheNoticeWithoutStartingATurn`.

## Known gaps

- Whether appending to `system[]` on every request costs prompt-cache warmth is unmeasured. If it is expensive, the fallback is a message part rather than a system part.
- A pause cannot guarantee the turn in flight stops. Aborting that turn from the plugin is not built.
- spov ships no plugin into a person's own OpenCode, so an attached TUI shows no job state; the web session page does.
