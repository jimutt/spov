## Context

spov clones every selected repository into `/workspace`, and OpenCode treats any path outside the session's directory as external. `permission.external_directory` defaults to `ask`, so asking an interactive agent to work in a sibling repository interrupts it with a prompt such as `Access external directory /workspace/other-repo`. The person has already said which repositories the session is for, so being asked again per repository contradicts the setup they just performed.

OpenCode matches these patterns by substituting each `*` with `.*` in a regex, with no path normalisation and no globbing. So `/workspace/**` cannot match the bare `/workspace` (the slash is literal), and `/workspace/../root/...` matches it.

A job session is different. A job's permissions come from the plugin's `permission.evaluate` hook (see DL-040). OpenCode's config normaliser concatenates three permission-shaped keys (`tools`, `permission` and `permissions`) into one rule list, renaming actions as it goes (`bash` to `shell`, `write` and `patch` to `edit`, `task` to `subagent`), and accepts both the older and the V2 shapes. The evaluator resolves the config-derived rules first. A config `deny` returns before the hook is triggered at all, and a config `allow` or `ask` becomes the hook's incoming effect, whose answer is then used. So a deny in a job's config outranks the plugin's allowlist silently, and the supervisor's conduct gate would read the refusal as the agent's conduct.

Finally, a launch can name a model that spov's model list lacks (see DL-014). OpenCode resolves such a name only if the config declares it.

## Decision

The entrypoint writes one global OpenCode config, `$HOME/.config/opencode/opencode.json`, before starting the server (`writeOpenCodeConfig`, `ConfigFile`). It is written unconditionally, also for a single repository, as the global config so a repository's own `opencode.json` still layers over it. The path uses `$HOME` and not a literal `/root` because the entrypoint's tests run it under bash locally, where a hard-coded path would fail `mkdir` and abort under `set -e`. It is a file, not `OPENCODE_CONFIG_CONTENT`: a file is inspectable, and the variable would override every other config source and put the config in the process environment beside the password.

There are two documents, produced by one function that branches on content (`marshalConfig`):

### Interactive sessions (`SandboxConfigJSON`)

- `$schema`, the session's `model` string, and `websearch: {provider: "exa"}` (see DL-035).
- V2 `permissions` rules allowing `external_directory` on `/workspace` and `/workspace/**`. The two are listed separately for the reason in the context. The grant is scoped, not a bare `"allow"`, so a prompt remains for `/root/.git-credentials` and the OpenCode auth store.
- The grant lets the agent read and edit across every bootstrapped repository and anything else under `/workspace`, including a path someone created there by hand. Content in one repository can steer the agent into the sibling repositories without a prompt.

What the grant is for: it stops the accidental case, an agent wandering from one cloned repository to another or to a credentials file and being interrupted for it. It does not contain a hostile agent. Because `*` becomes `.*` without normalisation, `/workspace/../root/.git-credentials` matches the pattern, and the agent runs as root in a single-tenant sandbox. What protects the host is the sandbox boundary, not this permission (see DL-029 and DL-034).

### Job sessions (`JobConfigJSON`)

- `$schema`, `model`, `websearch`, and nothing permission-shaped: no `permission`, no `permissions` and no `tools` key. All three normalise into the same rule list, so all three are the exclusion. A job's `external_directory` grant comes from the plugin allowlist, not from the config (see DL-040).
- Restoring the workspace grant for jobs would be harmless today, because a config allow is only the hook's input, but redundant, and a future deny added to a shared file would take effect silently.
- What else may go into a job's config is not decided in general. Each new key is its own question; a permission-shaped one is answered by this rule.

### The model

`model` is a first-class top-level field of the normaliser, so the config carries the session's model string for both kinds (see DL-014). A repository's own discovered `opencode.json` outranks the global file, so a repository can override a model spov validated. The per-conversation model call therefore remains. The model string is encoded as JSON, which escapes the newlines that would otherwise close the entrypoint's heredoc; this holds only while that heredoc stays quoted.

### An unlisted model

When a launch's model is not in spov's list, both documents declare it at `providers.<provider>.models.<model>: {name: <model>}` (`declare`). The key is `providers`, plural, at the pinned build. A listed model is not declared, so OpenCode keeps models.dev's limits for it. Nothing else under the provider is written (no settings, base URL or key), because those belong to the proxy. A `#variant` is not part of the declared id. Whether to declare is decided at launch (`Service.modelUnlisted`) against the list as it then is, and the id goes through the same encoder as the model string. A custom model can therefore be chosen only at launch; a mid-session switch reaches listed models and the session's own declared model.

### Confirming the shape

The shape of the config is confirmed by reading the pinned binary's normaliser, not by fetching the published `$schema` URL: the binary's own guidance says not to use that URL to determine the V2 configuration shape. A key spov writes that OpenCode does not recognise is ignored silently, so `TestTheConfigDocumentsMatchThePinnedSchema` validates every document against the schema in the committed contract (see DL-035), and a bump re-reads the normaliser.

## Rationale

- A rule should be as wide as its reason. The reason a job has no permission keys is the measured deny short-circuit, so the exclusion is those keys and not the file. A pinned invariant that a test enforces beats a blanket ban kept by memory, and it states the hazard for the next reader.
- With model as a config field, one function writes both documents and the model reaches both kinds of session by one mechanism.
- Scoping the grant to the workspace costs nothing over a blanket allow and keeps one real signal: a prompt to read credentials is worth seeing, because nothing in a normal session needs them.
- Declaring is the only way OpenCode resolves an unlisted name, and declaring only what needs it leaves a listed model as OpenCode knows it.

## Measurements

- **Permission precedence, read from the pinned binary:** the normaliser accepts both permission shapes and concatenates them, so the interactive `external_directory` grant is live; a config deny returns before the hook is triggered; an allow or ask is the hook's incoming effect. There is no test for it: re-read the normaliser on an OpenCode bump. `go test -tags integration ./internal/sandbox/ -run ActionVocabulary` reads the action vocabulary from the binary the same way.
- **Config precedence (spike S11):** with a global config naming one model and a repository's `opencode.json` another, the repository's discovered config ranks above the global file. `go test -tags integration ./internal/sandbox/ -run S11Model -v` (one billable sandbox, no agent turn, no model key).
- **Spike S-M1 (custom model; OpenCode 2.0.22 locally, a fake OpenAI-compatible model behind a provider, the key in the environment as a sandbox holds it):**
  1. A model models.dev lists as active resolves with no declaration and is called with all 12 tools.
  2. A deprecated model fails `provider.no-route`, "Model unavailable", declared or not.
  3. An unlisted model fails the same way unless declared at `providers.<provider>.models.<model>`. Declared with only a `name`, it resolves and is called with all 12 tools; capabilities are not needed.
  4. Declaring models under a provider does not remove the provider's catalogue models.
  5. A `#variant` on a declared model with no variants resolves to the model itself.
  6. The only config-update route, `PATCH /api/experimental/config`, takes `shell` alone, so a model cannot be declared in a running sandbox.

  `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SM1 -v` re-measures all six (local, no Modal, no key).

## Consequences

- The interactive agent works across all cloned repositories without interruption.
- spov owns a generated file inside the sandbox, so a renamed key or changed default in OpenCode can break it silently. The exact pin bounds that to a bump, and the schema test catches an unrecognised key.
- A job's config holds the model and web search, so it can be got wrong. The test replaces the guarantee an absent file gave.
- Guard tests: `TestJobSessionLosesTheExternalDirectoryGrant` (parses the rendered config of both kinds, checks the three keys are absent from the job's and the grants present in the interactive one, not a substring), `TestAModelCannotEscapeTheConfigHeredoc`, `TestSandboxConfigIsScopedToTheWorkspace`, `TestAnUnlistedModelIsDeclared`, `TestTheConfigDocumentsMatchThePinnedSchema`.
