## Context

OpenCode 2.4 adds automations: the agent can schedule a prompt, a Code Mode script or a shell command to run once, on an interval, on a cron or on an MCP event, and a prompt can be sent to its own session. They are on by default. At 2.4.2 they reach the agent through Code Mode (`tools.automation.create` and its siblings in the `execute` tool's catalog), which asks no permission for a prompt into the session, so a job's allowlist (DL-040) does not cover them. The catalog tells the model to use them "instead of waiting, sleeping or polling".

A job's loop is the plugin's: it continues the run, holds for subagents and background commands (DL-143, DL-182) and ends on the completion tool. A prompt an automation sends later would start a turn the loop did not ask for, possibly after delivery has begun, and nothing in spov has measured how that reads to the plugin or the supervisor.

## Decision

A job's OpenCode config (`opencode.JobConfigJSON`) sets `"automations": false`. An interactive session's config (`SandboxConfigJSON`) leaves the key unset, so a person keeps OpenCode's default there.

Spike S-AU1 (`SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SAU1 -v`) runs the pinned build under each config and checks that a job's Code Mode catalog offers no automation tool while an interactive session's does. It is re-run on an OpenCode bump.

## Rationale

The setting removes the tools from what the model is offered, which is the narrowest change that keeps a job's work inside its loop. OpenCode's automation routes on the server stay, as every route does; only spov and a person call them, and a job's shell reaching them is the same guardrail-not-boundary case DL-040 describes.

## Consequences

An agent in a job cannot schedule its own follow-ups; one that wants to check back later waits inside its turn, or ends it, as before 2.4. Scheduled work is spov's to run (its own schedules, if added), never an automation inside one job's sandbox.
