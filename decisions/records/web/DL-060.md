## Context

The sessions page is where a person looks first, and the jobs page is where they ask what came of the work. The two pages need to answer different questions:

- The sessions page answers "what is running, and what does it cost". On a list that mixes interactive sessions with autonomous jobs, the thing to scan for in a job's row is that it is waiting for you, which a plain "Running" hides.
- The jobs page answers "which jobs are waiting on me, which failed overnight, and where are the pull requests". The sessions list answers none of these well, because it mixes interactive sessions in and shows a job's state only as a badge.

There are two concurrency limits, sessions (3 by default) and jobs (2 by default), and a job's session counts as its job, not as a session. A page that counts every live session against one limit cannot explain a refusal such as "you have 2 of 2 jobs running" while it says "3 of 3 live".

A job's session relates to the job through `jobs.session_id`, which is non-nullable and unique with the organisation, so every job points at exactly one session and a session has at most one job.

## Decision

### The sessions page is a table under one summary line

The columns are State, Session, Started, Running for and "Cost, at least". The header says "at least" so the cells show the figure alone. The header is a real `role="table"` header. Below 768 px it is visually hidden but still read by a screen reader, and each row folds to three lines with "at least" written into the cost cell.

- The Session cell holds the name, then a meta line with the kind in words ("Pull request job", "Report job", "Interactive") and the repositories in monospace. The last message follows, clamped to two lines, starting with "Agent:" or "You:" in semibold.
- Running for holds the duration, the lifetime track and its caption ("of 24h", "Stops in 12m", "Ended early").
- `listState` in `format.ts` is the one place the State column's rule lives. For a job's session it shows the job's state (Steered, Delivering, Succeeded), with a short reason beneath when it matters: "Waiting for you" for a steered or blocked job, and "Sandbox stopped" (or "Sandbox failed") whenever the session's sandbox is not live, which takes precedence. For an interactive session it shows the session's own state. `format.test.ts` covers an interactive session, a live job, a waiting job and a finished job.

The summary line above the table is at body size. It holds the two limit meters, "Since 1 October: 14 sessions, 31.4 sandbox hours", "Spend at least $4.82", and a "How spend is estimated" link to the usage page, which carries the footnote explaining the figures. Spend always says "at least" in words.

### A session row carries its job, filled by one batch lookup

`SessionView.job` is a nested `SessionJobView` with the job's id, kind, state and `partial`. It carries no goal, verdict or deliverable. A report is a whole artifact, so putting one on a listing would send every report body in the organisation down the wire to draw a badge. A list says what a row is, and the session page says what happened. A verdict is not on the row because a list would have to explain three gates in a row's width.

- `JobStore.BySessions` takes the page's session ids and returns the jobs among them. `viewsOf` calls it once per page, beside `LastMessages`. The Postgres implementation is a single `select distinct on (session_id)` over the organisation's jobs with `session_id = any(...)`, ordered by newest job id so that a corrupt store answers the same way on every request. The memory store does the same, and both take the organisation from the caller, so session ids of another organisation match nothing (`storetest`). An empty page is answered without a query; a page whose sessions have no jobs still makes it, since one indexed lookup is cheaper than the branch to skip it and cannot go stale.
- A failed decoration is warned about and omitted, never fatal, as with `LastMessages`: the list is the session's state and must not be withheld by a decoration. `GET /sessions/{ref}` carries the same job, read with `BySessions` for one session (`sessionJob`). `TestTheListSaysWhichSessionsAreJobs`, `TestTheSessionViewNamesItsJob` and `TestTheListStampMovesWithAJobsState` guard the decoration and its stamp.
- `decorationStamp` is the change fingerprint of the list's feed. It hashes exactly the job fields the row carries (id, kind, state and `partial`, through `sessionJobView`), so a job moving from running to succeeded, or being judged partial, reaches open lists, while a cursor advance does not wake every open session list. Hashing the whole job would. A read that fails gives the constant `?` rather than an empty stamp, so a failing store does not read as a list whose messages all vanished.
- Changing `SessionView` requires `scripts/gen-api-client.sh`, which rewrites the two generated API files.

### The jobs page groups states into four filters

`/jobs/` lists the caller's jobs, newest first. Its header item sits between Sessions and Usage and is active on `/jobs/new` too. A row links to the job's session page: a job is shown on its session's page, and there is no job detail route. The page links to `/jobs/new` as the sessions page does.

- **Four filters over groups of states.** All (the default, because opening the page to see what happened is the common case), Active (`queued`, `provisioning`, `running`, `delivering`), Needs you (`blocked`, `steered`, the two states that wait on a person, with its count shown when not zero) and Finished (`succeeded`, `failed`, `cancelled`). `GROUP` in `web/src/lib/joblist.ts` is a `Record` over every job state, so a new state fails `astro check` until it is placed in a group. The filter lives in the URL (`?show=needs-you`) so a view can be linked, and an unknown value reads as All.
- The filter is sent as one comma-separated `?state=` parameter, because huma keeps only the first value of a repeated parameter.
- **The table.** It uses the sessions table's row treatment with columns State, Job and Running for. The state mark has its own column. The goal's first non-blank line is the row's link, the kind is in words ("Pull request job"), the outcome line is beneath, and the age is at the right. The age runs to now for an unfinished job and to when it stopped for a finished one.
- **One outcome line per row** (`outcomeOf`), chosen by kind and status and never by sniffing text. One verified pull request with an http(s) URL, on a job that is not partial, shows as the link. A succeeded job otherwise shows what it delivered, counting only verified members ("2 pull requests", "1 report", "1 pull request, partly done" when partial); a report is counted and never linked. A blocked, steered, failed or cancelled job shows its `error`: what it waits on, why it failed or who cancelled it.
- **Polling.** The page polls the listing every 10 seconds while open, the same interval as the session page's job resource. It is a store read and never touches a sandbox. The session state stream does not serve, because a job moves from `running` to `blocked` while its session stays `running`.
- **No report bodies.** A job view carries the deliverable inventory and never a body, so a listing costs the same however long reports are, and no `?fields=` or `?brief=` parameter exists. `TestJobViewsCarryTheInventoryAndNoBody` guards this (see DL-051).

### Both limits are shown as the server counts them

The sessions page's summary line shows "1 of 3 sessions" and "2 of 2 jobs", each with one tick per unit, up to 24 so the row stays bounded however large a limit the server reports (`LimitMeter.svelte`). `/me`'s `quota` reports both limits (see DL-009). The jobs page shows "2 of 2 jobs in progress" under its heading and reads the job limit once from `/me`.

- `limitUse` counts as the server's quota does. A job counts while its state is not finished, queued included (`UNFINISHED`). A live session counts only when it does not belong to such a job. The sessions page computes this in the browser from the sessions stream it already holds, so it adds no request and no polling, and `joblist.test.ts` pins the rule to the server's.
- `UNFINISHED` is derived from `GROUP` as the complement of the finished group, as `store.JobState.Counts` is the complement of `Terminal` on the server. A new job state is therefore placed for both the filters and the limit at once.
- The jobs page reads the unfinished jobs with one listing (`limit=200`, counted by `total`) whatever filter is on screen. That listing gives both the meter and the Needs you count, so the page makes no separate query for it.
- At the limit, the count and ticks turn gold with a title saying another launch is refused until one ends. Without a limit the meter shows the count alone.
- The sessions page shows no count of every live session; job sessions are in the list and are counted as jobs. The streamed list always carries every live session, so the counts stay exact.

### A partial success is drawn as done in part

A job that succeeded with part of what was asked is `succeeded` with `JobView.partial`. On every list that draws a job's state (the sessions State column, the jobs list, the session page's job heading) `jobMark` gives it the mark `part`, a gold tick, and `jobWord` words it "Succeeded, partly". The folded verdict's "Partial" uses the same mark. It stays the `succeeded` state: it is wording and a mark, and nothing in the lifecycle, filters or counts changes. A distinct mark rather than only a colour keeps the rule that a state never rests on colour alone. `Mark` has six values, and `StateMark`'s `Record<Mark, …>` colour table must place each one (checked by `astro check`).

`SessionJobView.Partial` is derived by `partialOf`, the same function `JobView.Partial` uses (state `succeeded` and a deliverable gate that is partial). A boolean says nothing a report body would, so the rule against carrying `result` holds. The session listing parses each decorated job's verdict once per list. `TestTheSessionBadgeSaysASuccessWasPartial` guards the badge.

### Both pages show fifty rows and append older ones on request

Both pages show 50 rows (`PageSize`) and a "Show older" button that appends the next 50. The server half is described in DL-012.

- **Sessions page.** The stream asks for `limit=50` and stays live: the newest 50 plus every live session. "Show older" reads `GET /api/v1/sessions?before=<cursor>&limit=50` once and appends the result. The cursor is the oldest id of the newest page, not of the live sessions pinned below it (`sessionsCursor`). Appended rows are drawn as read, not live. A session present in both is drawn once, with the stream's copy.
- **Jobs page.** The listing for the chosen filter asks for `limit=50` and is polled. "Show older" follows `next`. Appended pages are tagged with their filter like the first page, and switching the filter drops them, so one filter's rows are never drawn under another's name. A read that started before a switch is dropped even if the reader has switched back.
- The button says how many remain, from `total` ("Show older (77 more)"). The jobs page knows `total` from its first page. The sessions page learns it from the first older page, so its button says "Show older" until then. The button is drawn only while `next` is set and is disabled while a read is in flight, so a double click does not append a page twice.
- The limit meter and the Needs you count read their own data and do not change with paging.
- The logic is in `web/src/lib/paging.ts` (`appendPage`, `merged`, `olderLabel`), where vitest reaches it.

## Rationale

- Columns let the eye run down one fact, such as which rows are waiting on you or what each costs. On a list where most rows are jobs, putting the job's state in the State column shows "steered" where "running" would hide it. The session's own state is on its page, and the reason line names it when it differs.
- One summary line gives the page's facts in a small part of the height and leaves the list as the first thing on the page.
- One query per page rather than one per row is the performance answer, and `viewsOf` already uses that shape for the last message. Listing every job and joining in the browser was rejected because it grows with the account's history, not with the page.
- A separate jobs page, rather than a filter on the sessions list, keeps each page to its question; a job filter on the sessions list would leave interactive sessions with no meaningful value. Groups replace the nine raw states because nobody filters for `provisioning`; the raw state is still on every row.
- A refusal should be predictable from the page. Counting in the browser from the stream the page holds keeps the sessions page free of polling, and the rule is one line.
- Appending keeps the newest rows where they are and suits a list read from the top. Numbered pages would make page 1 the only live one and lose the reader's place. Fifty rows cover most of a working week of jobs. Older pages are read once because almost every row there has finished.

## Measurements

- A real job's run contained 36 `session.retry.scheduled` events. They were the bulk of what a folded run's summary counted as "other events", which is why the summary names model retries separately (see DL-058).

## Consequences

- A reader may see "Delivering" or "Succeeded" where they expected "Running". The reason line says "Sandbox stopped" when the session has ended, so the two facts are not confused.
- `Counts` on the server and `UNFINISHED` in the browser must agree; a new job state is decided once in `GROUP`.
- Copy on these pages follows the app's plain-word rules (see DL-056).
- A list that keeps appended pages loses them on reload, which also happens with a folded run.

## Known gaps

- An administrator's jobs listing is the organisation's whole history, with no owner column and no search of the goal text.
- The sessions stream carries no cursor, so with exactly 50 sessions "Show older" is offered once, the read finds nothing and the button is removed.
- A row created while older pages are shown pushes the newest page's oldest row onto neither page. It is missing until a reload. This is accepted rather than patched.
