## Context

`/sessions/new` and `/jobs/new` went to the new session's page with `location.assign`, which kept the form in the history. Back from a running session, the phone's button or the browser's, returned to the empty form. A person leaving a session is far more likely to want the list, to check on another session or a job, than a second blank form; on a phone the system Back button is the main way out.

## Decision

On success both forms leave with `nav.replace` (`location.replace`) instead of `nav.go`, so the session's page takes the form's place in the history. Back from it returns to wherever the form was opened from: the sessions list, or the jobs list for a job started from there. The same on every screen size. The session page's own "‹" link still goes to the sessions list. Everything else DL-061 says about the redirect (its address, that it happens only on success, the `Committed` guard) is unchanged.

## Rationale

Replacing the entry is what a create flow in an app does: the form has done its work and is not a place to return to. Rewriting the history to put the list behind the session, whatever came before the form, was rejected: a page restored from the back/forward cache would show the form under the list's address, and a person who opened the form from a link elsewhere expects Back to take them there.

## Consequences

- A form opened directly (a bookmark, a new tab) has nothing behind it, so Back leaves the app; the "‹" link still reaches the list.
- To start a second session, the reader goes back to the list and presses Start again, one tap more than Back to the form was.
