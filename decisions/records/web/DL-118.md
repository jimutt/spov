## Context

A routed credential can be listed and removed in Settings, but only `spov credentials add` stores one (DL-077 left the browser's add for later, and DL-074 gave an admin only Delete there). Someone who works in the web app cannot give a session a private registry. Sandbox templates (DL-119) name routed credentials, so the browser needs a way to hold them first.

## Decision

- The routed credentials section of Settings (`RoutedCredentials.svelte`) gains **Add credential**, and each of the user's own rows gains **Replace**. Both open one form; its logic is plain functions in `web/src/lib/routedform.ts`.
- The form's fields are the CLI's (DL-073): a name; either a preset (`npm`, `maven`, `nuget`, `pypi`, with the preset's own options, DL-076) or hosts, an optional list of path prefixes and one scheme (`bearer`, `basic` with a username, `header` with a header name); the attach mode (`always`, the default, or `asked`); and the secret.
- It writes through the existing endpoints and adds none: `PUT /api/v1/me/routed-credentials/{name}` with `{secret, route}`. The server's 422 text is shown as it is; the form repeats only the checks that need no server (the name's shape, a host present, a scheme chosen, a secret present).
- **The server expands a preset.** For a preset the form sends only the preset's name and its options (`url`, and `scope`, `repo_id`, `user` or `paths` where the preset takes them) with the attach mode. Both `PUT` routes run `routedcred.FromPreset` on a route that names a preset and store what it returns, so the hosts, the scheme, the default user and the path prefix taken from the URL are the server's, never the browser's. A preset route that also carries hosts or a scheme that differ from the expansion is refused. `Route.Validate` also checks a preset route's paths, user and repository id against the expansion: its paths are the URL's own prefix, or the wider prefixes of it that DL-076's `--path` allows. The form sends paths for a preset only when a replace prefilled a widened set, so replacing a credential the CLI widened does not narrow it unnoticed; it has no control of its own for them. The CLI keeps expanding before it sends; the server's expansion of an expanded route is the same route. Without this a browser could store an `npm` credential for a shared Artifactory host with no path, which DL-076 rules out.
- **The server checks the name against platforms.** `checkRoutedCredential` refuses `github`, the one platform key a routed credential's name could take (every other is `<kind>:<host>`, which the name rule already excludes), as the CLI's `shadowsAPlatform` does, so a browser-added credential cannot make `spov credentials remove github` ambiguous.
- **Add never replaces.** Add refuses, in the form, a name the listing already holds for the chosen owner, and points to Replace.
- A replace prefills the route from the listing and always asks for the secret again, because a `PUT` replaces the route and the secret together (DL-073). The name cannot be changed in a replace. An admin also gets Replace on the organisation's rows; saving a replace of an organisation credential is behind `ConfirmAct.svelte`'s second press, as its Delete is, because every member's sessions get it.
- The secret is typed into a `type="password"` field with `autocomplete="off"`. It is held only in the form's state, cleared when the write settles either way, and never written to browser storage, a URL or a log line. No response carries it back.
- An admin's form has an owner choice, **Mine** (the default) or **Organisation**, which writes `PUT /api/v1/org/routed-credentials/{name}` instead (DL-074). The choice is drawn only for an admin, and never where the organisation endpoints answer 501 (a local server).
- Where the personal endpoints answer 501 (a hosted server with no credential key) the section says so and offers no form, as today.
- There is still no verification. After a save the section says the credential is stored unchecked, as the command does.
- Enter never submits the form, and a failed write keeps the typed route but not the secret.
- The writes are guarded by `BrowserGuard` alone, as every browser write is (DL-061). No token scheme is added.

## Rationale

The API was built for this in DL-073 and DL-074, so the browser needs only a form. Asking for the secret again on a replace follows from the seal binding the route: the server cannot move a stored secret to a new route, and should not. Clearing the secret on failure costs a retype and keeps a secret from sitting in a page the user has walked away from.

## Consequences

- A hosted user can set up a private registry without the CLI.
- Settings holds a secret field for the first time besides the provider keys; the same care applies (never echoed, never stored client-side).
- The section's line that names `spov credentials add` as the only way goes away.

- `web/src/components/RoutedCredentials.svelte`, new `web/src/lib/routedform.ts` with vitest cases for the request it builds per scheme and preset, and the local checks.
- A mounted test only for the wiring: the secret field is empty after a settled write, and the owner choice is absent for a non-admin.
