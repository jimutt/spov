## Context

The browser is the main way a person talks to a running session. The server relays a message into the sandbox's inbox, defines what it means on a job, and makes Interrupt safe (DL-019, DL-052, DL-053). This record is the page that uses them: a text box, what it may say, which controls sit beside it, and how a sent message appears before the transcript holds it. Autocomplete for slash commands and file references is out of scope.

## Decision

### The composer is a component of its own

The composer sits at the bottom of the session page, below the transcript, in `Composer.svelte`, with its logic in `web/src/lib/steer.ts`. Which control is drawn for which job state exists only in rendered markup, and mounting the whole session page to check a text box means stubbing two streams and three resources. So behaviour is tested in `steer.test.ts` and `composer.svelte.test.ts`. `sessiondetail.svelte.test.ts` mounts the page only for wiring: that the composer is rendered, that the echo reaches `buildTimeline`, and that the job's state is passed through. Each of those is one line that can be dropped in a way that compiles, type-checks and passes every other test.

The three write actions go to different places: a message and Interrupt are addressed by session (`/sessions/{ref}/messages` and `/sessions/{ref}/interrupt`), and Resume by job (`/jobs/{id}/resume`). The page holds both ids, and a control wired to the wrong one gets a 404 on every press, which looks like the feature went away. The mounted page test checks where each goes. All three are same-origin POSTs that rely on the browser guard for CSRF protection, and no token scheme is added (DL-055).

The fixed "Jump to latest" control must not overlap the composer. The composer does not disturb the tail latch, which changes only in a scroll handler on the window (DL-057). Mounted tests that scroll must stub `Element.prototype.scrollTo`: jsdom does not implement it, and the call happens inside a `requestAnimationFrame` callback, so every test passes while vitest prints an unhandled error and exits 1.

### Sending

- **Enter sends and Shift-Enter inserts a newline** (`sendsOnEnter`). This is the opposite of the job form's rule (DL-061), because the costs differ: the job form provisions a sandbox and runs an agent unattended, while a message goes to a sandbox already running and paid for. The Enter that commits an input-method candidate is not a send; it is recognised by `isComposing` and the legacy `keyCode === 229`, since otherwise each accepted candidate posts a half-typed word.
- **Send steers.** The message is read at the agent's next step, once the running step or tool call has finished, without stopping it. The composer does not offer `queue` (read when the whole turn ends); the API keeps it. A slash command is sent as literal text, since OpenCode's command endpoint is not used.
- **On a running job** (`offersAfter`; not a steered job, which is already the reader's, and not an interactive session, which has no loop) a control beside Send chooses what follows the message: "continue autonomously" (the default) or "hand over to me". It is a property of the message and not a mode of the page, so it sits beside Send and resets to continue after every send, which means a handover is never left set by accident. A retry with a different choice is a new message.
- **The model beside Send.** The session's current model is shown beside Send as a picker that switches it (`ModelSwitch.svelte`, DL-014). The page shows the model the log says is selected, not the picker's choice.
- **The send names no conversation.** The server resolves an omitted conversation against its own rows and refuses a session that has several, because the transcript shows every conversation on one timeline with nothing a reader could point at to choose one, and a guess would put the reader's words in front of an agent they were not talking to.
- **No confirmation on Interrupt, and no composer on the session list.** A stray Enter sends and does not interrupt, and a turn can be restarted. A list row has no room to explain what a message does to a job.

### When the composer can send

A state that cannot take a message shows the reason, not an empty space. `sendability` mirrors the server's `jobRefusesAMessage` and is advisory; the server decides, in its own words, when a job changed between the poll and the send. An unknown job state is allowed to send, because a newer server's unfamiliar state is more likely a new in-flight state than a new refusing one. A composer wrongly disabled gives the reader no way to find out why, and a send wrongly allowed returns the real reason. That default is safe because `everyJobStateIsKnown` is a compile-time proof that every state in the generated API document has been considered, so an unconsidered state fails `astro check`.

The composer is shown only when both signals agree (`composerShown`). The session row can be stale towards `running` and never away from it, since states only move forward and the resource stops polling once the session settles. The stream ends only on a quiet tick, so a page opened on an old stopped session would show a composer until that tick arrives.

"No job" and "the jobs request has not answered yet" are both `undefined`, and `Resource.loaded` tells them apart. In that window the copy makes no claim about a job, because the jobs listing answers after the session row and answers 501 on a server with no supervisor.

### Message ids and the echo

Each send carries a browser-generated id (`newMessageID`): the prefix `msg_`, the milliseconds in hex, then fourteen random characters. The server bounds the whole id at 128 bytes. The ids sort in time order, so anything sorting by id agrees with the clock. The random part prevents collisions and not guessing. The id is the idempotency key and the echo key at once, and it is OpenCode's message id: there is no second "inbox id". The sandbox does not require the exact format.

The server's behaviour that the client relies on:

- The prompt endpoint accepts an optional `id`. A duplicate id in the same session silently dedupes and returns the original with 200. If two ids collided, the second message would go nowhere while the request still returned 200.
- An id reused from another session returns 409. The client never reuses an id across sessions.
- Idempotency covers only the sandbox. The connection mint, the recorder nudge and a refusal computed against a job state that may have changed are not idempotent, so a retry is safe for the message and is not a no-op.
- **Retry rule.** Every 4xx is decided before the message reaches the sandbox (the body, the job's state, the conversation, the mint floor and the rate limit are checked first), so nothing was delivered and the next send is a new message with a new id. A 5xx or a dropped connection is indeterminate, because the relay can fail after the sandbox took the message, so the id is kept and sent again and the sandbox decides whether it is a duplicate. This is why the composer retries freely where job creation, which has no idempotency key, must not (DL-061).

`MessageIDPrefix` is written in Go and in TypeScript. `TestTheMessageIDPrefixMatchesTheBrowser` reads the TypeScript source and pins them together. Drift makes every send a 422 with nothing in either codebase saying why.

**The echo.** A sent message is drawn at once and replaced when the live stream or the stored conversation delivers the same id.

- It is reconciled by filtering on every render, on the id alone (`unseen`). Either source clears it, and a re-read after a gap can bring back a message the stream already delivered, so removing an echo on arrival would need to be remembered. Filtering gives the same result with nothing to remember. The list grows for the life of the tab, bounded by how much one person types into one page. It is never pruned from an `$effect`: an effect that reads the list, filters it and writes it back marks its own dependency dirty and loops until `effect_update_depth_exceeded`. It is never matched on text, because a reader who sent the same word twice would see one.
- An echo the server accepted but the recorder has not stored stays on screen. A recorder that attached late stores nothing, and a row that vanished would show a reader their own words gone while the agent replies to them. A refused send is the opposite: its row is withdrawn and the text goes back in the box, because at that moment those words exist nowhere else.
- An echo's timestamp is never earlier than the last entry on screen, because the echo carries the browser's clock and everything else the sandbox's. They were typed at the end, so they go at the end.
- `buildTimeline` decides that a user frame repeats something already on screen by message id where ids exist. Two identical messages from a person ("ok", "ok") are two messages. spov's own continuation keeps the text rule, because the same sentence repeated is machinery, and forty identical continuation blocks would bury the turns between them. A transcript stored before ids existed keeps the text rule for its user messages.
- **A pending echo is its bubble faded.** It is the same bubble at reduced opacity (about 55%) that eases to full over about half a second (none under reduced motion) once the transcript holds it. The echo and the transcript's copy share the key `messageKey(id)` (`msg:<id>`), so one element stays and only opacity changes; a key that differs between them makes the bubble jump. A message without an id keeps its positional key. No note is drawn under it, because two lines of text under every sent bubble were visually busy; `echoNote` ("Sending…", "Sent, not yet in the transcript") remains for screen readers and as the bubble's title. An echo that never reaches the transcript stays faded.

**A message's status** comes from the stored log, not from the sandbox. `messageStatuses` reads a person's message as queued from its enqueue, processed from its delivery, cancelled from its cancellation, and not processed when the session or its job's run ended while it was still queued. A queued message is drawn below the log until the agent reads it, with a Cancel control (`DELETE /api/v1/sessions/{ref}/messages/{id}`); a processed one needs no word, a cancelled one says "Cancelled before the agent read it", and an unprocessed one says "Not processed: the run ended before the agent read it". The note under a queued message is worded by how it was sent and what follows it (`queuedNote`).

### One status bar, and the controls outside the form

One status bar sits above the box (`composerStatus`). It holds one line for the state ("Working on a step", "Working on a step · paused for you", "Paused for you", "Waiting on a question", or "Waiting on your answer" while a permission or question card in the transcript waits for the reader), and the controls are right-aligned after it. It is not drawn when there is nothing to say, because separate rows read as two statuses. Explanations are behind an (i) (`controlsNote`, naming only the controls drawn). Under Send is one short line (`SendShort`) with the full note behind its own (i) (`deliveryNote`).

- **Interrupt** is drawn while a turn is in flight and the job's state allows it. `turnInFlight` decides from the last execution frame by store position, and all three ending events (`succeeded`, `failed`, `interrupted`) clear it; keying only on `succeeded` would leave Interrupt on screen after it was pressed, and deciding by arrival order would make the control depend on the transport. Nothing is polled and nothing is asked of the sandbox: the frames are already on the page. It cannot say which conversation a turn belongs to, which follows from the send naming none, so it asks only whether some turn is running here. It reads what the person sent at once (DL-053). There is no "Interrupt and send" button, since Send then Interrupt does the same.
- **Interrupt fails quietly by design.** If the page never saw a `started` frame (the recorder attached mid-log, which the gap marker records), Interrupt stays hidden for that turn and the gap marker is the thing to read. Nothing is guessed from the job's row, because Interrupt offered when no turn is running delivers a parked message instead of doing nothing. `interrupted: false` is shown as success and the message never says "the session was idle". It says the interrupt was accepted and gives both readings: either no turn was running, or a message that was waiting has just started one. The outcome describes the turn that was interrupted, so it clears when the next turn begins. The interrupted turn's end and the next turn's start can arrive in one batch, and then the in-flight state never falls, so the outcome is also withheld once a second turn has ended after the press (`turnsEnded`; the interrupted turn's own end is the first).
- **Resume** is offered on a `steered` or `blocked` job (`resumable`). A steered job's loop really is held, and Resume releases it. A blocked job was never paused: Resume only hands the job back to its loop and does not answer the request its agent is parked on, which is answered in the transcript card, and answering resumes the job by itself (DL-020). Resume stays disabled until the page has read that the job moved, because the 204 alone leaves `resumable` true from a stale `steered` row and a second press would get a 409 for an action that worked. `onJobChanged` is `Resource.refresh`, which reports its own failure and never rejects. Interrupt re-reads nothing, because its row does not change.
- **Both controls sit outside the composer form.** Sending is refused in `blocked`, so a Resume inside the form would be missing in the state that most needs it. Interrupt is outside for a narrower reason: `canStop` mirrors `jobRefusesAnInterrupt` and the form mirrors `jobRefusesAMessage`. They refuse the same states today, which is an observation and not a law, pinned by `TestTheTwoRefusalsCoverTheSameStates` and its browser twin; putting one control inside the other would decide that the server's two rules are one. They share one area above the box, because to a reader they are the same kind of thing: something to do about the run rather than something to say to it. Resume's visibility is tied to `composerShown`, which is stricter than Resume needs; that is not a gap in practice, since a steered or blocked job's session is running.

### What the copy may say

On a job, a message does not stop the agent or the job. The running turn is untouched, and the loop is held at the supervisor's next pass. The page may say a message is read once the agent's current step finishes, that a job carries on after a `continue` message, that it pauses for the reader after a handover, and that Interrupt stops the step and the agent then reads the message at once. It never says a turn stops, that the job is suspended, that the agent will stop, or that the state changed. A reader told "taken over" who then watches the agent keep building has been told something false by spov. The note names Interrupt only while Interrupt is drawn: naming a control that is not on the page is the same false statement one step removed. Until the jobs read answers, the note must be true of a job and of an interactive session alike.

### Audit markers are not drawn

The markers spov writes for the audit trail (`spov.session.steered`, `spov.session.message.cancelled`, `spov.job.interrupted`, `spov.job.resumed` and the like) are not drawn in the transcript. Each carries machine identifiers above a message already on screen in the reader's own words. This is a second, narrower question asked only of rows already known to be spov's (`AuditMarkers` in `timeline.ts`). `isSeam` stays keyed on `source`, which is the trust rule: keying on a `spov.` prefix would let a sandbox draw markers in spov's voice or hide one by borrowing a name. Markers that describe the recording (a gap, a recorder that gave up, a failed collection) are still drawn, and the default is to show a marker, so one this build has never seen is still drawn (DL-058).

## Rationale

- The composer is a component of its own because the untestable half of a page is whatever exists only in markup.
- Enter sends because the action is cheap on a running sandbox, and because blocking it would make the input look broken.
- A browser-minted id gives the echo an exact key and the retry an idempotency key without a round trip before the echo can render. The coupling to OpenCode's id space is deliberate and small.
- Filtering on every render gives the same result as removing on arrival, with nothing to remember.
- A message could not stop a continuation: the event that ends the turn it was answered in is the event that triggers the next turn, and the plugin sends its continuation within milliseconds. Interrupt prevents it at the source, because the plugin continues only on `session.execution.succeeded` and an interrupt sends nothing. That is why the copy separates what a message does from what Interrupt does.
- No confirmation on Interrupt, because a turn can be restarted, unlike a deleted credential.

## Measurements

- **S-LS1, the turn-started frame.** `session.execution.started` at the pinned OpenCode build carries a `durable` object (`{aggregateID, seq, version}`), so it survives `projectFrame` and reaches the store, and Interrupt can be derived from the log with no fallback and no polling. Re-run: `go test -tags integration ./internal/sandbox/ -run SLS1 -v` (it creates a billable sandbox), plus `TestTheTurnStartedFrameReachesTheStore` in the unit tests.
- **S-LS1, the prompt response and the id dedupe.** `POST /prompt` returns `{"data":{id, sessionID, timeCreated, type, payload:{text}, delivery}}` with the caller's own id. Repeating the id returns the original with 200, not 409. A plain `msg_<nanoseconds>` id is accepted.
- **S-LS1, `continue=true` on an idle session.** With a waiting steered item, it returns `false` while delivering that item and starting a turn.
- **S-LS1, `steerMessageIDFor`.** The inbox id and the message-store id are equal for a human message on a real sandbox, which the page's identification of a user's message depends on (`storedMessage` reads `inboxID` from the event frame and `parseMessages` reads `id` from `/message`). If human messages ever render twice, check that equality first.
- **Steer timing in a real run.** A message landed at 16:55:12.095. The plugin's continuation went out at 16:55:15.294, 3 ms after the turn ended. The pause reached the session at 16:55:21.235, 9.1 s after the message and 146 ms after a pull request had already been created.
- **S6, a blocked job.** The flow is to answer the question first and then resume. Re-run: `go test -tags integration ./internal/sandbox/ -run S6 -v`.

## Consequences

- The session page has three write actions, the message, Interrupt and Resume, and the first ones that change something other than the caller's own account.
- Three behaviours are not function-shaped and belong in a mounted test: which control is shown for which job state, that sending is disabled while a send is in flight, and that Enter in the box is wired to the send at all.
- `TestTheTurnStartedFrameReachesTheStore` is the guard that keeps Interrupt drawable, because no constant for `session.execution.started` exists in `internal/server`, so there are no two copies to compare. `TestTheTurnEventNamesAgreeWithTheBrowser` pins the three ending events in both directions and that a start must not read as an ending (`turnEnded` matches by suffix).
- A new job state must be decided in `jobRefusesAMessage` on the server and in `sendability`, `canStop` and the other `Record`s in the browser, or it fails `astro check`.

## Known gaps

- Whether a subagent's child session emits its own `session.execution.*` frames onto the same stream is unmeasured. If it does, a child's `succeeded` arriving mid-turn would clear the in-flight state and hide Interrupt while the parent's turn runs. Settle it against a captured job log; reading `ev.session` here would also need a rule for which conversation is the reader's, and the send deliberately has none.
- With the audit markers hidden, a message another person sent looks like the reader's own, and nothing on the page says a person ended a turn. The fix is a label carried on the wire, not parsing the marker's text.
- An accepted echo whose live frame has no readable id would show the message twice, once as the transcript's copy and once as the echo. Matching on text would close that and open a worse hole, hiding a second identical message.
