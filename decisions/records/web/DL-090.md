## Context

A stopped interactive session can be resumed (DL-087), from its snapshot or from its transcript (DL-088, DL-089), and the two give back very different things. The reader has to know which one they are about to get, and a resume costs a sandbox, so it must not happen by accident (DL-061's guards).

DL-023 names the command tree with one meaning per verb. "Resume" already means releasing a job's held loop (`spov jobs resume`, the composer's Resume button, DL-054, DL-059).

## Decision

**The session page.** An interactive session whose view carries `resume` (DL-088) shows a Resume control behind `ConfirmAct.svelte`'s second press. The confirmation is worded by `resume.mode`:

- `snapshot`: the workspace comes back as it was when the session stopped, including uncommitted changes. It names `until`.
- `transcript`: the repositories are cloned fresh, the conversation is restored, and uncommitted changes and installed packages are gone.

The resume uses the launch's duration; the page offers no duration field. The control's logic lives in `web/src/lib/resume.ts` (which mode, its words, and whether to offer it), and its failure is held by `SessionDetail` as End session's is (DL-057).

**The composer.** On a resumable stopped session the composer stays drawn, and Send reads "Resume and send". The first press arms it with the same mode wording, and the second press POSTs the resume with the message (DL-087). Enter never submits it, and a `Committed` error never re-enables it, as for the job form (DL-061). This amends DL-059, which draws no composer on an ended session.

**The listing.** A stopped session with a snapshot shows a quiet "resumable until <date>" in the sessions list and in `spov ls`. A transcript-only session shows nothing extra.

**`spov resume <session>`.** It takes `--max-duration` and `--json`, and by default attaches when the session runs, as `spov fly` does. `--no-attach` prints how to attach instead. Before it resumes, it prints which mode it will use, and for `transcript` it asks for confirmation on a terminal; `--yes` skips the question. Completion offers the stopped sessions a running server says are resumable (`Env.existingClient`, DL-023).

**`spov attach` on a stopped session.** On a terminal it says the session has stopped, names the mode and asks whether to resume it, defaulting to no. Off a terminal it exits non-zero naming `spov resume`. This amends DL-025, whose wait otherwise ends on a stopped session.

**The verb.** `spov resume` at the top level reopens a stopped session. `spov jobs resume` keeps releasing a held job loop. This amends DL-023's one-meaning rule with that one pair, which never meet: a job's session is never resumable as a session (DL-087), and an interactive session has no loop to release.

## Rationale

Wording the confirmation from the server's `resume.mode` keeps the page honest about what comes back. Asking about a transcript resume on a terminal, but not a snapshot one, puts the friction where work can be lost.

"Resume and send" serves the common case of coming back to a session to carry on. Sending the message with the resume (DL-087) keeps it from being lost if the tab closes while the sandbox boots.

Reusing "resume" reads naturally for both, and the two contexts never share a screen.

## Consequences

- `TestEveryNamedCommandExists` covers `spov resume` and its flags in any copy that names it.
- `--json` on `spov resume` prints the session view (DL-023).
- The session-state stream and `live.ts` must take a `stopped` session going back to `starting` (DL-087).
