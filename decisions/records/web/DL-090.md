## Context

A stopped interactive session can be resumed (DL-087), from its snapshot or from its transcript (DL-088, DL-089), and the two give back very different things. The reader has to know which one they are about to get, and a resume costs a sandbox, so it must not happen by accident (DL-061's guards).

Today a stopped session is final everywhere a client reads it. The page's resources stop polling on a terminal state (DL-057), and the composer is drawn only while states move forward (DL-059). The log stream ends with `EndEvent{stopped}`, which ends `live.ts`'s generator (DL-018). `spov attach`'s wait ends on a stopped session (DL-025).

DL-023 names the command tree with one meaning per verb. "Resume" already means releasing a job's held loop (`spov jobs resume`, the composer's Resume button, DL-054, DL-059).

## Decision

**The session page.** An interactive session whose view carries `resume` (DL-088, present only for its owner) shows a Resume control behind `ConfirmAct.svelte`'s second press. The confirmation is worded by `resume.mode`:

- `snapshot`: the workspace comes back as it was when the session stopped, including uncommitted changes, kept until `until` at the latest. While `pending` is set, it says the snapshot is still being taken and that the resume waits for it.
- `transcript`: the repositories are cloned fresh, the conversation is restored, and uncommitted changes and installed packages are gone.

The page offers no timeout field, so the resume takes the launch's timeout. A 409 for a snapshot that could not be collected re-reads the session, which then offers the transcript wording for a fresh confirmation. The control's logic lives in `web/src/lib/resume.ts` (which mode, its words, and whether to offer it), and its failure is held by `SessionDetail` as End session's is (DL-057).

**Following a resume.** While a stopped session's view carries `resume`, the page keeps reading the session from the store every 30 s, a store read only (DL-018). When the session is back in `starting` or `running`, whether this page resumed it or another client did, the page:

- restarts its job-less session resources as for a live session;
- reopens the log stream with `?after=<pos>` from its last position, so the resume's seam and the new run's events follow the old ones without a reload.

This amends DL-057's stop-on-terminal rule and DL-018's final `EndEvent{stopped}`, which now ends a stream but not the session's story.

**The composer.** On a resumable stopped session the composer stays drawn, and Send reads "Resume and send". The first press arms it with the same mode wording, and the second POSTs the resume with the message, its id and the conversation the reader is viewing (DL-087). Enter never submits it, and a `Committed` error never re-enables it, as for the job form (DL-061). This amends DL-059, which draws no composer on an ended session.

**The listing.** A stopped session with a snapshot shows a quiet "resumable until <date>" in the sessions list and in `spov ls`, worded as "at the latest". A transcript-only session shows nothing extra.

**`spov resume <session>`.** Its flags are `--timeout`, `--keep`, `--no-attach`, `--yes` and `--json`.

- Before it resumes, it prints which mode it will use, and for `transcript` it asks for confirmation on a terminal. `--yes` skips the question, and off a terminal `transcript` needs `--yes`.
- It then follows the resume and attaches, as `spov fly` does. Exiting the TUI stops the session again unless `--keep` is given, and Ctrl-C during the boot stops the new run. Either way the session stays resumable.
- `--no-attach` prints how to attach instead, and `--json` prints the session view and implies `--no-attach` (DL-023).
- Completion offers the newest 200 of the caller's resumable sessions from a running server (`Env.existingClient`, DL-023).

**`spov attach` on a stopped session.** On a terminal it says the session has stopped, names the mode and asks whether to resume it, defaulting to no. On yes it resumes and then behaves as attach does: Ctrl-C during the wait ends only the wait while the resume carries on, and exiting the TUI leaves the session running (DL-025). Off a terminal it exits non-zero, naming `spov resume`. This amends DL-025, whose wait otherwise ends on a stopped session.

**The verb.** `spov resume` at the top level reopens a stopped session. `spov jobs resume` keeps releasing a held job loop. This amends DL-023's one-meaning rule with that one pair, which never meet: a job's session is never resumable as a session (DL-087), and an interactive session has no loop to release.

## Rationale

Wording the confirmation from the server's `resume.mode` keeps the page honest about what comes back. Asking about a transcript resume on a terminal, but not a snapshot one, puts the friction where work can be lost.

`spov resume` follows `spov fly` because both start a sandbox the person is about to use, so leaving the TUI should not leave one billing. `spov attach` keeps its own rule because the person came to join a session, not to own its lifetime.

A page that follows a resume from elsewhere is what "the same session" promises. A page left open would otherwise show a stopped session that is running.

Reusing "resume" reads naturally for both, and the two contexts never share a screen.

## Consequences

- `TestEveryNamedCommandExists` covers `spov resume` and its flags in any copy that names it.
- The 30 s read of a resumable stopped session is a store read and never reaches a sandbox (DL-018).
