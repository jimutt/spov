## Context

A session page has two sources for what happened. The conversation is the messages OpenCode stored, read from `/messages`. The log is the stream of events the recorder stored, read from `/log`. Both describe the same activity by different routes: an event shows up in the log as it happens, and the same words show up in the conversation on the next read. Two separate lists would make a reload look like it rewrote the past, because messages that had been on screen for minutes as events would appear in the other list in another form.

Both sources come from the store (DL-018, DL-017). A stopped session is readable, and nothing on the read path touches a sandbox. The conversation survives a reconnect; the activity feed can have a gap where the recorder was not listening, and the page says which it is showing and does not imply the log is complete.

A run also produces a great deal of machinery: step and delivery boundaries, four events per tool call, records spov keeps for its verdict. A reader wants to see what the agent said and did, and to know who said it.

## Decision

### One timeline

`web/src/lib/timeline.ts` merges the conversation and the activity into one chronological list. It is a plain module that takes both as data, so it is unit-tested, and the component only renders. Entries are ordered by `at` and then by a stable sequence number; an entry with no timestamp keeps arrival order and is not scattered by a NaN comparison.

An entry's identity is a `key`, never its position. A message's key is its conversation and index, or `msg:<id>` for a person's own message; an event's key is `e<pos>`, the position the store assigned, which is stable across reconnects. Position-based numbering would renumber every event when a re-read returned one more message, and fold an expanded run back up after a reconnect.

Two event names carry what was said and are promoted to messages: `*.text.ended` (the agent's reply) and `*.inbox.enqueued` (the prompt just sent). The split is by name and not by whether text is present: `session.retry.scheduled` also carries text, the provider's error, and that is machinery talking about the session. A promoted event is dropped when the conversation already carries the same words. For a person's message the match is by message id where ids exist, and otherwise by exact trimmed text, with the same rule among promoted events. A known limit of the text rule is that an agent saying the same thing twice shows it once until the next read. Echoes of a message the browser just sent, queued-message status and permission asks are drawn from the same timeline and belong to DL-059.

On the server, `MessageView` carries `at` (the message's `time.created`) so the two sources share a clock. `collectText` returns nothing for a part of type `reasoning` or `tool`. Reasoning is the model's working and not what it said, which makes it a disclosure boundary: no surface shows reasoning today, and a surface that did would be an explicit one and not a side effect of collecting every string called `text`. A tool part is volume that the event row already reports (a `read` of a large file otherwise puts the whole file into the message). A message whose only content was a tool call then has no text, and the page drops it instead of drawing a speaker label with nothing beside it. A reader who wants a tool's output has the event row. A whitespace-only message is not a message on either path, since `"\n"` is truthy and would otherwise draw an empty speaker block.

`maxProjectDepth` is 5, because a person's prompt sits at `data.item.payload.text`, four levels down; the search is breadth-first so a shallower match wins. The shape `collectText` reads is partly inferred; `TestProjectionAgainstRealSandboxFrames` and the captured frames are the guard.

Consecutive events collapse into a run by position in the timeline and never by a name allowlist, which goes stale with the next OpenCode build and fails by hiding a new event that mattered. A message always breaks a run, so a collapse can never hide speech, and a seam is never folded into one, so a gap stays visible. A run is identified by its first entry's key. Expansion reads only from what the page holds, is per run and is not remembered across a reload. `CollapseFrom` is 2, because the control shares the first row, so two events already save a row; a test pins the value.

### Read once, resume by cursor

The page reads the conversation when it opens, after a dropped connection once the stream is back, and once when the stream ends because the session is over. It never reads it on a timer. `live.ts` tells the three endings apart:

- `end` with `reason: lifetime` (every stream is closed by the server after five minutes) reopens at once and silently, without telling the page anything was missed;
- a dropped connection, or a body that ends without an `end` event, sets a pending gap and calls `onGap` once the stream is back up, and the page re-reads the conversation in case a turn ended while it was disconnected;
- an `error` event is terminal: the server has said why, and reopening would only collect the same refusal. A 401 goes through the app's login funnel (DL-055).

`logStream` remembers the last `pos` it yielded and reopens at `?after=<pos>`, on a lifetime close and after a break alike. Without the cursor, a stream that replays and ends is reopened in a tight loop, and a cursorless reopen redelivers the whole log every five minutes. A stopped session's stream ends with `end{reason: "stopped"}`, which is final: the status reads "Recording ended" and not "Not live, reconnecting". The page holds the whole replayed history, absorbs a burst of frames into one update because the timeline is sorted and grouped on every assignment, and keys events by their stored position.

Reconnect backoff keys on how long a connection lasted and not on whether it opened. The delay starts at 1 s, doubles to 30 s, and is forgiven only after a connection has lasted `StableAfter` (30 s, well inside the server's five-minute lifetime). A server that accepts a connection and closes it without sending anything (a draining replica, a rolling deploy, a proxy cutting the body) would otherwise never back off. A gap is reported once when the stream is back up, not once per failed attempt, so a server that is refusing connections costs one re-read and not one per retry. The guards are `live.test.ts`: "an orderly close reopens without reporting a gap" and "backs off instead of re-reading once a second".

The conversation read is a store read and costs no sandbox time, but the rule stands because a re-read on every reopen would be a poll, and it would redo what the cursor makes unnecessary. The tail latch (DL-057) must not re-anchor on the five-minute reopen either.

The empty state follows the server: the response's `warnings` ("nothing has been recorded for this session") render as that sentence, and the page's own "nothing yet" line shows only when there are none. A warning is dropped once anything is on screen (`shownWarnings`). A session with markers but no conversation counts as recorded.

### Who spoke

`LogEvent` carries a `role`, which says whether a person, spov or the agent spoke. `storedRole` re-derives it from the stored row's raw frame by calling `jobs.InboxItemType`; a breadth-first `roleKeys` search would return the event name. `projectFrame` sets no role, because its output is stored and never sent. `TestTheLogSaysWhoSpoke` is the guard, and a test pins the live and stored paths to each other for a synthetic message. The reason is not cosmetic: nothing of spov's is ever a `user` inbox item (a job continued with a prompt enters `steered` on its own first turn, DL-052). Guessing the speaker from the event name told a reader that a person had typed spov's goal and stop marker, which hides the distinction steering rests on. `spokenBy` keeps its name-based guess only as a fallback for an event with no role, such as one from an older server. `speaker()` in `format.ts` is shared by the list and the page so they cannot disagree. The sessions list draws each entry's last message with it; a message with a role but no text (an assistant turn that was only reasoning) is drawn as the speaker with an ellipsis, and the placeholder "Nothing recorded yet" is for an entry with no message at all.

### Seams, notes and records

A seam is one of spov's own markers, decided by `source` and never by a name. `LogEvent.source` is `opencode`, `ephemeral` or `spov`, and `isSeam` reads only that. `store.SpovNamespace` (`spov.`) is reserved: `Event.Validate` refuses an OpenCode-sourced row that claims it, and the recorder drops such a frame with a warning, not a write failure, so a sandbox can neither draw a full-width seam of its own wording nor break its own recording. The recording gap and stop are server frames, `spov.recorder.gap` and `spov.recorder.stopped`, drawn where the recorder was not listening: a browser break loses nothing, so a client-drawn seam would report a gap that did not happen. A gap is one sentence between two dashed rust rules with its time inline. A rust dashed rule means the recording is incomplete, and nothing else uses it.

All of the following are asked only of rows whose source is spov, so a sandbox cannot draw or hide one by borrowing a name.

- `spov.job.evidence` and `spov.job.outcome` are records the verdict is read from. They are not drawn (`isRecord`).
- `spov.job.collected`, `spov.job.bounded` and the other quiet notes (`NoteMarkers`) are one quiet line tagged "spov", like the stop marker, shortened past `NoteTextLimit` (400).
- The audit markers of steering and answering are hidden (`AuditMarkers`, DL-059).
- Every other spov row stays a seam, including one this build has not heard of.
- A seam's drawn text is bounded. `seamText` shows the marker's text when it is at most `SeamTextLimit` (120) characters and has no newline, and otherwise the marker's name, not a truncated head, since the head of a JSONL blob reads as the whole message. The event is never dropped. The limit is a rendering constant with no server counterpart, and gate 1 reads the evidence marker's stored text either way.
- The stop marker is rendered and never printed. `SPOV_LOOP_STOPPED` with its JSON payload is a contract the supervisor matches by prefix, and `TestTheStopMarkerMatchesThePlugin` pins the literal across Go and the plugin, so its text never changes to read better. `stopNote` renders the reason and the continuation count when they say something. An unparseable payload falls back to the raw line, so drift degrades presentation and does not hide a stop. It is a fourth place that knows the literal.

### Work, not plumbing

`condense` prepares the timeline for drawing, for OpenCode rows only.

- `Plumbing` is a list of OpenCode event names to drop and never to keep: step, text and reasoning boundaries, delivery and inbox bookkeeping, execution boundaries, compaction start, the model and agent selection. A new event still shows until it is listed, which fails safe where an allowlist would hide it. Re-check the list on an OpenCode bump. Speech events with no text are dropped.
- Every event of one tool call is joined into one line at the call's first event, wherever its others landed: the tool's name and one line of its input (`toolInput`: the command, path, pattern or URL, found in the raw text when the input arrives cut short), and the error beneath for a failed call. The join is by call id (`data.id`), not by order, because parallel calls are common. The tool's name is only on `tool.input.started`, its input on `tool.input.ended` and its ending on `tool.success` or `tool.failed`. `LogEvent` carries `call` and `tool`, re-derived from the stored frame by `storedToolCall`, which reads tokens and stops at what it needs, so a `tool.success` with a large output is not decoded past its id. For an OpenCode row only. A server that sends no `call` leaves tool events unjoined, minus plumbing. A call whose ending never arrived is drawn with no mark and not as running. A tool's output is not shown.
- A thought (`reasoning.ended`) is two italic lines.
- A folded run is drawn as its summary alone ("10 tool calls, 1 failed, 3 thoughts"); opened, it is the lines; a run of one line is drawn as that line. A model retry (`session.retry.scheduled`) is named in the summary ("2 model retries") and is not counted among other events.
- Plain message text loses blank lines at either end (`trimBlankLines`), because plain text is drawn as written and a trailing `\n\n` drew an empty band.

### One column

The transcript is one column capped at `--read-w`, with no gutter; `--log-w` equals it, and anything capping the transcript uses `--log-w`. The layout says who spoke without labels:

- your messages are right-aligned bubbles on `--raised`, at most about 85% of the column, with their status lines (waiting, cancelled, not processed, the echo's note) inside the bubble;
- the agent's text runs full width and carries no label;
- spov's own lines (synthetics, the stop marker, job notes) keep a small inline "spov" tag in a quiet style, so a reader never takes spov's words for the agent's;
- tool runs sit flush in the column;
- the composer, the warnings and "Jump to latest" are capped at the same width.

A message's details ("Agent · 21:06") sit under it and are shown on hover, when something inside it holds focus, or on a tap (`toggleDetails`, which does nothing while text is selected, so a phone reaches what a mouse reaches on hover). They stay in the document for screen readers. Messages are not made tab stops, because a stop per message costs a keyboard user far more than a hidden time saves.

`timeDividers` draws a quiet time ("21:20", or the date and time on a new day) before the first dated entry and before any entry that follows the previous one by more than `TimeGap` (10 minutes). There is none where the previous entry is undated. Time matters more on a long job than in a chat, but not on every line. Tests key on `data-testid` and never on a speaker's text.

## Rationale

- Chronology is what a reader is looking for: whether the agent is working, stuck or finished. Provenance is an implementation detail of how spov learned about an event. The durability distinction is carried by form (a turn against a quiet line, a seam where the recording broke) and not by putting the sources in different boxes.
- Merging in the client keeps the two server surfaces as they are. Nothing merges on the server, and the two streams stay independently correct.
- Resuming by cursor is what a client should do with a log, and a server-drawn seam is the only truthful one.
- The role belongs on the wire because the server is the side that knows. A client inferring a fact the server has already measured is how two views come to disagree.
- Consistency between the live path and the stored path is the requirement, since a reader moves between them by reloading and whichever one is unbounded looks broken. The bound is set where the two disagree.
- A denylist of plumbing fails the safe way: a new event shows until it is listed.
- The layout itself says who spoke, the time is one hover or tap away, and the divider gives a long job its rhythm without a timestamp on every line.

## Measurements

- **Message shape.** On a beta build of OpenCode 2 (`0.0.0-beta-18743`), stored messages carry `time.created`, the speaker is the `type` field and not `role`, and a person's prompt sits at `data.item.payload.text` (depth 5). Re-run: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run LocalOpenCodeProbe -v`.
- **Tool text in message text.** A `read` of a 16 KiB file put 18,566 characters of the file into one stored message, at `content[1].state.content[0].text`. Re-run: `go test ./internal/server/ -run TestProjectionAgainstRealSandboxFrames`.
- **Unbounded seam.** `spov.job.evidence` carried the plugin's whole evidence file, 4,478 characters of JSONL, which printed as a sentence in spov's voice.
- **Plumbing.** In one report job, 141 of 160 OpenCode events were step, reasoning, text, delivery and execution boundaries. An opened run listed four events per tool call (`tool.input.started`, `tool.input.ended`, `tool.called`, `tool.success`). Re-check `Plumbing` in `web/src/lib/timeline.ts` on an OpenCode bump.
- **Reconnect without backoff on duration.** A server that accepted and closed immediately produced 60 transcript re-reads a minute from one open tab. Re-run: `cd web && bun run test -- live.test`.

## Consequences

- `LogEvent` carries `source`, `role`, `call` and `tool` and `MessageView` carries `at`, so the generated client follows them (DL-005).
- `MessageView.at` and `SessionView.estimated_cost` are two fields that exist for the UI on otherwise stored read views. A third should first ask whether the read model wants a shape of its own.
- There are three writers of a speaker (`storedRole`, `parseMessages` and `spokenBy`'s fallback), and the test that pins the live and stored paths to each other is what finds drift.
- A session with a long event stream and few messages reads as mostly folded runs, which is what such a session is.
- A page opened on a very long session receives its whole history on connect, in bursts. The cursor already supports the remedy, an `after` that starts near the end plus a "load earlier" control.
- A new OpenCode event name is drawn until `Plumbing` lists it, and a new spov marker is drawn as a seam until it is placed in a set.

## Known gaps

- No surface shows a model's reasoning or a tool's output.
- Text-based de-duplication hides a repeated sentence from the agent until the next read.
- `inbox.delivered` is dropped as plumbing; the promotion rule in `spokenBy` is the one place to change if it ever needs to be drawn.
