## Context

DL-111 takes a child conversation out of the main list. A reader still needs to see that the agent delegated work, what it was asked to do, whether it is running or done, and what it found, in the place in the parent's story where it happened.

OpenCode's own surfaces agree on the pattern, which is the one to copy:

- the parent's transcript carries **one task row per subagent call**: its description and agent, a running indicator while it works ("Delegating…" before the child exists) and a count and the latest action as it goes;
- the row **links to the child session** (TUI: click, or `session.child.first`; web app: an expandable card with an open link), and the child is a full session view with a way back (`session.parent`), siblings (`session.child.next`/`previous`) and its own transcript;
- **permission and question prompts raised inside a child are surfaced in the parent**, so a subagent can never be stuck behind a prompt nobody can see;
- child sessions stay out of the root session list, and the sidebar lists them under their parent.

The link from a row to its child is not always available in OpenCode: the child id travels in the tool part's `metadata.sessionId`, which a known race can leave empty for the whole running phase (opencode issues 20184, 41055), while `session.parentID` is always right. A plugin-created child has no task part at all (issue 29175). The plan therefore uses parentage as the authority and the call as a hint.

## Decision

### The card

A child conversation is drawn as one `subagent` block in its parent's timeline (`Block` gains the kind), at the position of the call that started it. It shows:

- the label: the child's title or the call's `description`, and the agent type where the call carries it (`toolInput` already reads `description`);
- a state: running, done, failed or stopped, from the child's own frames (its last execution frame, its failed tool calls), with the call's `tool.success`/`tool.failed` as the fallback when the child has none;
- a summary in the existing words (`runSummary` over the child's condensed events: "12 tool calls, 1 failed") and, while running, the latest action as one line;
- a pending-ask badge when the child has an unanswered ask (below);
- a disclosure, closed by default, as a folded run is. Opened, it draws the child's own condensed timeline from DL-111 inside the card: the prompt as a quiet row, tool lines, thoughts and the child's text, indented under a rule. The child's final text is also shown closed, as one clamped paragraph, since it is what the parent acted on.

Nothing in the card is a bubble, an "agent" label or a "spov" tag. It is its own thing, so a reader never takes it for either.

### Which child belongs to which call

Parentage decides *whether* a conversation is a child; the call decides *where* it is drawn:

1. If a frame of the call, or the call's input or result, names the child's session id (to be measured, S-SA1 in DL-110), that is the link.
2. Otherwise a call is paired with the children of its parent created during its span (from its `tool.input.started` to its ending), oldest to oldest, one each, using the child's `Info.time.created` where the page has it and its first frame's time where not.
3. A child no call claims (a background subagent that outlives its call, a plugin-created child) is drawn standalone at its creation point, as the same card with the label from its title.

No child is ever dropped for want of a link. The pairing is a pure function in `timeline.ts` and is tested with parallel calls, a background child and a missing id.

### Asks

An ask raised in a child is drawn in the **main** timeline at its own position as today (DL-020: never folded into a run, answered through the conversation its row belongs to, which `asks.go` already resolves from the stored row), with a "from subagent <label>" line. The card's badge counts its pending asks and scrolls to the first. A pending child ask counts for "needs you" wherever the root's does.

## Rationale

- One card per subagent keeps the main transcript's length proportional to what the person talked about and the agent decided, while a reader who wants the detail has it one click away, which is what OpenCode's own task row gives.
- Parentage as authority, the call as placement, is the only combination that survives each of the three cases above, and the fallbacks degrade to "drawn at its creation time", never to "missing".
- Keeping asks outside the fold repeats DL-020's rule for the same reason: an agent held up by a prompt must be visible.

## Consequences

- `Block` gains `subagent`, and `SessionDetail.svelte` gains a block branch; DL-070's window counts a card as one block however much it holds.
- The card reads the child's events from the same log the page already holds, so it adds no request and no sandbox read (DL-018).
- A very large child (hundreds of tool calls) is bounded by the existing fold: the inline timeline is a folded run until opened, and a card opened on a huge child draws its newest 200 blocks with "Show earlier", through the same window code.
- Redaction and sanitising are unchanged: the child's text goes through `markdown.ts`, DL-063's two `{@html}` sites are not added to.
