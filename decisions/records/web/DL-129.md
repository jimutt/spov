## Context

The allowlist is managed only through the API (DL-007), which in practice means `curl` with a per-user token. Adding a colleague is the first thing an operator of a shared server does after signing in, and the most frequent administrative act after that. DL-128 lets an entry name a GitHub account.

## Decision

The Settings page gains a **People** section, drawn for an administrator on a hosted server and for nobody else. It sits with the other organisation settings (`OrgSettings.svelte`) as its own component, `Allowlist.svelte`, with its logic in `web/src/lib/allowlist.ts`. It uses only DL-007's three routes as DL-128 leaves them; no route is added for the page.

- **The list.** One row per entry: the GitHub login and name for an account entry or the address for an address entry, an "admin" mark, and "never signed in" until `last_login_at` is set. The caller's own entries are marked "you". Sorted with administrators first, then by name.
- **Adding.** One field that takes an address or a GitHub username, with or without the leading `@`: text containing `@` after its first character is an address, anything else a username (`entryRef`). An "administrator" checkbox, off by default. The new row shows the name GitHub resolved, which is the confirmation of whom was admitted. A refusal (unknown login, an organisation's account, GitHub unreachable) is shown beside the field in the server's words.
- **Removing** is behind `ConfirmAct.svelte`'s second press. The confirmation says what removal does, in the wording the off-boarding behaviour has when this is built (ending browser sessions today).
- **Changing admin rights** is a toggle on the row, a `PUT` of the same entry.
- **The guards are the server's.** The page disables removing or demoting an entry when the server would refuse it (the caller's only covering admin entry, the last admin entry), computed by `canRemove` and `canDemote` from the list, and still shows the server's refusal if it comes, since the list can be stale. A refusal re-reads the list.
- **Enter** in the field adds the entry; the page spends nothing, so the job form's implicit-submit guard does not apply. One `pending` flag covers the add and every row action, as on the profile forms (DL-062).

A non-admin, and a local server, see no section at all: the page reads `/me`'s `admin` and does not call the allowlist routes otherwise.

No CLI command is added. `deploy/README.md` keeps the `curl` examples for scripts and points to the page first.

## Rationale

- Everything the page needs is already in the API, so it is markup and a small amount of logic, and the API stays the one place the rules live.
- Showing the resolved name on the new row is what makes a mistyped username visible at once (DL-128).
- Mirroring the guards avoids offering an act that will be refused, while the server's check remains the authority.

## Consequences

- The section's behaviour is tested in `allowlist.test.ts`, with a mounted test only for the wiring (the section absent for a non-admin, a refusal shown, the list re-read after a change).
- An administrator can lock a person out from the browser, so the confirmation's wording must stay true to what removal actually ends.
