## Context

The allowlist is managed only through the API (DL-007), which in practice means `curl` with a per-user token. Adding a colleague is the first thing an operator of a shared server does after signing in, and the most frequent administrative act after that. DL-128 lets an entry name a GitHub account.

## Decision

The Settings page gains a **People** section, drawn for an administrator on a hosted server and for nobody else. It sits with the other organisation settings (`OrgSettings.svelte`) as its own component, `Allowlist.svelte`, with its logic in `web/src/lib/allowlist.ts`. It uses only DL-007's three routes as DL-128 leaves them; no route is added for the page.

- **The list.** One row per entry: the GitHub login and name for an account entry or the address for an address entry (with the name of the user it covers, once one has signed in), an "admin" mark, and "never signed in" until `last_login_at` is set, else when they last did. An address entry the server marks `unbound` (DL-128: its person has not signed in since accounts were recorded) says "has not signed in since accounts were added". The caller's own entries, which the server marks with `you`, are marked "you". Sorted with administrators first, then by name (the display name, else the login or address). Every value is drawn as text; nothing GitHub returns is rendered as markup.
- **Naming an entry.** An existing account row is always addressed by `id:<github_id>` (`entryPath`), for the admin toggle, Remove and Retry, since two entries can carry one stale login; an address row by its address. `@login` is sent only to add an entry. Rows show `@login` (`entryLabel`).
- **Adding.** One field that takes an address or a GitHub username, with or without the leading `@`: text containing `@` after its first character is an address, anything else a username (`entryRef`). A username that does not have GitHub's shape, or an address with a space or a slash, is named under the field and never sent (`refProblem`), so the field's text cannot make a path that reaches another route. An "administrator" checkbox, off by default. A successful add says "Added @login, name" with the name GitHub resolved, which is the confirmation of whom was admitted, and the list is read again. A refusal (unknown login, an organisation's account, GitHub unreachable) is shown beside the field in the server's words, with the text left in the field.
- **Removing** is behind `ConfirmAct.svelte`'s second press. The confirmation says what removal does, as DL-132 does it: it ends the person's browser sessions, cancels their jobs, stops their sessions, revokes their CLI tokens and deletes their stored credentials, and keeps their history and templates. When another entry still covers the person (the view's `also_covered_by`, DL-128), it says they keep their access through that entry and nothing of theirs is ended. For an `unbound` address entry, it says that removing it ends everything of theirs even if their GitHub account has an entry, and that they should sign in once first. For an entry nobody has signed in through, it says nothing else is ended (`removalQuestion`).
- **A removal that half finished.** When the delete answers 500, the entry is gone but an off-boarding step failed (DL-132). The section shows the server's message, reads the list again (the row is then gone), and offers a **Retry** that sends the same delete for that entry (by `id:` for an account, which the server's retry matches against the user's account whatever its login now), which is the retry DL-132 and DL-128 define.
- **Changing admin rights** is a button on the row ("Make admin" or "Remove admin rights"), a `PUT` of the same entry.
- **The guards are the server's.** The page disables removing or demoting an entry when the server would refuse it (the caller's only covering admin entry, the last admin entry), computed by `canRemove` and `canDemote` from the list, says why on the row, and still shows the server's refusal if it comes, since the list can be stale. Every row act, refused or not, re-reads the list.
- **Enter** in the field adds the entry; the page spends nothing, so the job form's implicit-submit guard does not apply. One `pending` flag covers the add and every row action, as on the profile forms (DL-062), and each handler checks it. The section has no `$effect`, so DL-062's seeding loop cannot arise.
- **On a phone** the section is one column: the field, the checkbox and Add, then the rows, each wrapping its name, marks and buttons; every control is drawn once.

A non-admin sees no section and the page never reads the allowlist for them: Settings mounts the component only when `/me` says `admin`. A local server's principal is an admin, so its page asks once and is answered 501, and the section is not drawn, as `OrgSettings.svelte` does for its own route.

No CLI command is added. `deploy/README.md` keeps the `curl` examples for scripts and points to the page first.

## Rationale

- Everything the page needs is already in the API, so it is markup and a small amount of logic, and the API stays the one place the rules live.
- Showing the resolved name on the new row is what makes a mistyped username visible at once (DL-128).
- Mirroring the guards avoids offering an act that will be refused, while the server's check remains the authority.
- A removal that half finished leaves no row to press again, so the retry has to be offered where the message is.

## Consequences

- The section's behaviour is tested in `allowlist.test.ts`, with a mounted test only for the wiring (`allowlist.svelte.test.ts`: the list as text, an add and its resolved name, a refusal beside the field, the list re-read after a change, Retry after a 500) and one in `settings.svelte.test.ts` (the section absent for a non-admin, who never reads the allowlist).
- An administrator can lock a person out from the browser, so the confirmation's wording must stay true to what removal actually ends (DL-132).
- jsdom draws no CSS, so the tests check markup; the layout at phone and desktop widths is checked only in a browser.
