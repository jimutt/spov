## Context

The session page drew every block of a transcript and re-derived all of them on each live frame. Step 1 measured what that costs on long sessions, on 2026-11-05.

The sessions were copies of one real 77-message session from the manual-testing database (1,133 events: about 10 per message, four per tool call, three per step), with ids renamed per copy. They were seeded into Postgres at 1,001, 5,005 and 10,010 messages (14.7k, 73.6k and 147.3k events), served by the real server on loopback (`TestIntegrationMeasureLongConversations`) and opened in headless Chromium on the maintainer's machine. Before this decision:

| | 1k | 5k | 10k |
|---|---|---|---|
| Page settled (end of the last long task) | 1.1 s | 5.1 s | 10.2 s |
| DOM nodes | 32k | 160k | 320k |
| JS heap | 52 MB | 263 MB | 482 MB |
| Longest task | 0.54 s | 2.2 s | 4.4 s |
| Main thread per live line | 100 ms | 490 ms | 1,150 ms |
| Keystroke in the composer to next frame | 14 ms | 60 ms | 115 ms |

At 10k, ten seconds of live lines cost 5.4 s of script against 6 ms of style and 17 ms of layout, so the cost was JavaScript, not rendering. Run alone under bun on the same payload, the derivations took about 90 ms per update (`buildTimeline` 64 ms, `condense` 11 ms, the rest 5 ms or less). The rest was Svelte: `activity` and `conversations` were deep-proxied `$state`, so every read of 147k events went through a proxy trap, and every block's template re-ran because `blocks` is rebuilt on each update. A CPU profile of a live window showed 3.7 s of 6 s in Svelte's flush and 1 s in garbage collection; DOMPurify did not appear.

## Decision

1. **A window.** The page draws only a window of its blocks (`web/src/lib/transcriptwindow.ts`). While the page follows the tail, the window is the newest 200 (`WindowSize`) and slides. When the reader leaves the end, it is held at its first block (`held`), however few blocks it has yet, so new blocks are added below and nothing is removed above them. "Show earlier (N more)" releases the latch, moves the start back 200 (`earlier`) and scrolls by what that added, measured on the first block's own row rather than its time divider, with anchoring off for that moment, so the block the reader was looking at stays in place. Returning to the end releases the hold. Time dividers are computed over the drawn window, so its first block has its quiet time (DL-058). A held start is a block key, with its index as the fallback when the key is gone.
2. **Raw state.** `activity` and `conversations` are `$state.raw`. Both are only ever replaced whole.
3. **The latch releases on the reader, not on layout.** `Tail.onScroll` releases only on a scroll that moved up while the content did not shrink since the previous scroll event. With anchoring off while following (item 4), layout moves the position up only by clamping when the content shrinks, or when anchoring compensates for blocks dropped above, which also shrinks it. Growth is not compared, because it often fires no scroll event: requiring an unchanged height would ignore a single-step scroll such as PageUp or a find-in-page jump after any silent growth. The first event only records where the scroller is, since on a real page it is the page's own scroll to the end. This is what DL-057 already says ("releases the moment they scroll up"); the earlier code released on any scroll event short of the end, and a fast replay did that without a reader.
4. **No scroll anchoring while following.** The page sets `overflow-anchor: none` on the document while it follows. A sliding window drops blocks above the reader, and anchoring moved the reader up by their height in the same frame the page had moved them to the end, so the page never reached the end during a replay. A held window never slides, and "Show earlier" corrects its own position.

`content-visibility` was considered and not used: style and layout were about 25 ms in ten seconds, so there was nothing for it to save.

## Rationale

The window bounds the drawn blocks and the per-update template work to about 200 blocks however long the session runs. Holding it while the reader is away keeps the rule DL-057 sets, that a page must not pull itself out from under someone reading. Virtualising the list was rejected: blocks vary widely in height (Markdown, folded runs, asks), it fights the tail latch and scroll anchoring, and it breaks find-in-page and screen readers.

After this decision, measured the same way:

| | 1k | 5k | 10k |
|---|---|---|---|
| Page settled | 0.5 s | 1.3 s | 2.2 s |
| DOM nodes | 8k | 9k | 9k |
| JS heap | 19 MB | 110 MB | 144 MB |
| Longest task | 75 ms | 89 ms | 129 ms |
| Main thread per live line | under 50 ms (no long task) | 64 ms | 75 ms |
| Keystroke to next frame | 5–18 ms | 5–17 ms | 5–18 ms |

A reader who left the end with one PageUp kept their position and the line under the cursor while live lines arrived, "Show earlier" left the first block where it was, and "Jump to latest" returned to following with the window sliding again.

## Consequences

- Find-in-page finds only drawn blocks; older ones need "Show earlier" first.
- The page still downloads and holds the whole conversation, and still derives the whole timeline on each update. At 10k messages that is 17 MB of messages and 69 MB of log on open (uncompressed: gzip cuts the messages to about 38%), and about 75 ms per live line. Loading the tail first from the server would remove both; that is a separate decision.
- The memory store (every local server) checks each new event against every stored one (`eventStored`) and scans every event on each `ListEvents`, so recording and following a long session slows down as the store grows. Seeding 74k events into it took over ten minutes, where Postgres took 34 s. Not addressed here.
- `TestIntegrationMeasureLongConversations` re-runs the measurement from an export of any session (`SPOV_MEASURE_DIR`), against the memory store or Postgres (`SPOV_MEASURE_DATABASE_URL`).
