## Context

spov's only cost figure is an estimate of sandbox compute: the requested CPU and memory times the sandbox's wall-clock life (DL-009). It does not include model tokens. Model spend is paid through the provider keys a session runs with, spov does not meter it (DL-049), and token metering is deliberately outside the metric catalogue (DL-011). In practice the provider invoice is often much larger than the sandbox figure.

The page called the figure "Cost so far", "Spend" and "Cost, at least", and put it in the sidebar, the sessions summary line and every session row. Each of those reads as the whole cost of the work, which it is not. A person deciding whether a job is expensive can be misled by an order of magnitude.

## Decision

Every cost figure the interface draws is named sandbox cost, and it is drawn only where the sandbox is being described.

- **The session page.** There is no top-level cost section in the sidebar. The figure is a row in the Sandbox `details`, which is collapsed by default: "Sandbox cost" with the same "at least" floor. A sentence beneath it says it covers requested compute and elapsed time, that Modal bills the higher of requested and actual use so it can only be more, and that it excludes model tokens, which spov never meters. How the figure is calculated no longer needs its own (i) control.
- **The sessions list.** The summary line keeps the two limit meters and the month's session count and sandbox hours, and loses "Spend at least …" and the "How spend is estimated" link. The table drops the per-row cost column, so its columns are State, Session, Started and Running for. The mobile row loses the cost from its last line.
- **The usage page.** "Spend" becomes "Sandbox cost", and "How spend is estimated" becomes "How sandbox cost is estimated"; the explanation says plainly that model token spend is separate and not included. Beside the figures sits a greyed-out, non-interactive "Model token cost" panel with a "Coming soon" mark and "Not tracked yet" in place of a figure, saying the provider invoice can be much higher.

The floor wording stays wherever a figure is drawn: "at least", and the explanation that Modal bills the higher of requested and actual use. The session page and the usage page each carry that explanation.

## Rationale

- The figure is true and useful, but only about the sandbox. Naming it in the place it belongs is cheaper and more honest than presenting a total spov cannot compute.
- The session page is where a sandbox's size, age and limit already live, so the cost belongs in that disclosure and not at the top of a transcript someone is reading.
- A session row is for finding and opening a session, not for comparing total spend. A per-row sandbox cost beside a list of model-driven work invites exactly the wrong comparison.
- The usage page is the one place a person asks what they have spent, so it is where the gap must be visible. A disabled tracker says the gap is known without inventing a figure.
- Recording the absence now keeps a later token tracker from having to reintroduce a misleading "total cost" label first.

## Consequences

- This amends DL-057 (the sidebar's "Cost so far"), DL-060 (the sessions summary line, the cost column and the row) and DL-106 (the phone row's "running time and cost").
- No API change: `estimated_cost` keeps its meaning and its server-side calculation.
- The usage page is the only place that carries a month-to-date figure; the session's own sandbox cost is visible only after opening its Sandbox details.
- A future token cost tracker replaces the placeholder panel and may then offer a combined figure. Until it exists, no screen presents a total.
