## Context

DL-161 offers a reasoning choice only in a running session's composer, because the forms had no sandbox to ask. DL-187 serves each model's modes in `GET /api/v1/models`, which `/jobs/new`, `/sessions/new` and Settings already read for their model pickers.

## Decision

- `/jobs/new`, `/sessions/new` and the Settings default model draw a Reasoning choice beside the model picker: Default, then the chosen model's modes from the models response's `variants`, in OpenCode's order and words. It is drawn only when a model is chosen in the form and that model has modes; with the form's first option (the inherited default, `defaultOptionLabel`) nothing is drawn, since that default carries its own mode from Settings.
- The form sends the model as `provider/model#mode`, or the bare reference for Default. Choosing another model keeps the mode when the new model offers a mode of the same id, else returns to Default (`switchedTo` in `web/src/lib/reasoning.ts`, shared with the composer).
- Settings seeds the choice from the stored default's `#mode` (`seedField`'s rule of returning its argument unchanged holds), and an empty model clears the mode with it. A stored mode the list no longer offers is drawn as a disabled "<mode> (not offered)", selected, as DL-161 draws it, and the form says the session would run on the default.
- `toJobRequest`, `toSessionRequest` and `withoutVariant` keep one parser of a reference: first `#`, an empty half is no mode.
- On a phone the choice is one more cell of the form's grid, never a second copy (DL-106).

## Rationale

The choice sits where the model is chosen and reads the same list the server checks, so what is offered is what a create accepts. Leaving the inherited default without a choice keeps one place, Settings, where that default's mode is set.

## Consequences

- The Settings page's model field can now hold a mode, and every launch that inherits the default uses it, subject to DL-188 at the opening.
