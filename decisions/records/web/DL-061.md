## Context

Starting work from the browser lets a person sign in from anywhere, start a job, and check it later. It is also the first thing in the web app that makes a browser cause spending. The app already writes: the settings page stores and deletes credentials and the tokens page deletes tokens. Those writes change the caller's own stored state. A launch provisions a sandbox that bills for its whole life and runs an agent unattended.

The cross-site question has an answer already. `BrowserGuard` in `internal/auth/guard.go` runs before authentication on every request the server owns. Health probes, `/opencode-pin.json` and the web app's own files are served outside it. It requires the `Host` header to name this server, which protects against DNS rebinding and is spov's own code. It delegates the cross-origin half to the standard library's `http.CrossOriginProtection`, which refuses a request whose `Sec-Fetch-Site` or `Origin` points elsewhere. An absent header is allowed, because Go clients such as the CLI send neither. So a cross-site form POST from another page is refused before it reaches a handler.

## Decision

### `/jobs/new` posts the CLI's own endpoint

The job form POSTs `/api/v1/jobs`, the same endpoint `spov jobs create` uses. There is no web-only endpoint and no privileged path, so there is one creation path with one set of defaults and one validation order. Authentication is the session cookie, as on every other page.

- **CSRF protection is `BrowserGuard` alone, and no token is added.** The guard's Host check and `CrossOriginProtection` already cover the form's cross-site risk on every request. A token scheme would add its own failure modes and would read as if the guard were not enough. The guard protects against a page on another site making the browser launch a job. It does not protect against a script running inside the app's own origin, which is why the app renders agent text through one sanitiser (see DL-063). Relaxing the guard relaxes this form, and every future browser write inherits this answer.
- **A route, not a modal.** `/jobs/new` can be linked and bookmarked, and it has room for the repository picker, goal, kind, model, time limit, git access and check. The sessions page's heading carries a "Start a job" button and its empty state links to the form. The top nav has no tab for it: the nav lists places a reader goes to look at things, and this form is an action that redirects away from itself on success.
- **The form is filled from the server, not free text.** Repositories come from the repository listing, models from `GET /api/v1/models` and kinds from the API's enum. A kind is a TypeScript union and cannot be fetched at runtime, so exhaustiveness is checked at compile time: `KINDS` is declared `satisfies readonly JobKind[]`, which catches a kind the form invents, and the exported `everyKindIsOffered` makes `astro check` fail when the API gains a kind the form does not offer.
- **The selected repositories are drawn above the filter** as removable entries, so the reader sees how many will be cloned whatever the filter says. A repository the browser's credential cannot reach is shown disabled with the reason (`repoUnreachable`; see DL-042).
- **The optional check field.** Without a check a browser-started job can never have a verified first gate. The hint says the check runs at `/workspace`, so it must name the repository, and that a command which cannot be run stops the job succeeding (see DL-050).
- **A rejected create shows the server's message** through `Problem`: a model refusal, a quota refusal, and the 501 of a local deployment that has no supervisor.
- **The form states no bound the server owns.** `draftProblems` checks only that there is a goal and at least one repository. Size limits, model validity and quota belong to the server, because a second copy of a bound would drift and the reader could not tell which side refused.
- **An unusable model is shown and cannot be chosen.** A provider the caller holds no key for stays in the list, disabled, labelled with the variable to set. The reason is also written as prose beside the picker (`keyNote`), because screen readers commonly skip a disabled option. `keyNote` leads with the providers that have a key and names those that do not, without repeating each one's variable (that stays on the group label), so it stays one sentence when most of the list is unavailable. It says so when no provider has a key, adds a sentence naming the providers a connected OpenCode account would unlock (see DL-015), and renders nothing when every key is held. The server still refuses a stale list.
- **An empty model, check, time limit or git access is left out of the request body**, not sent as `""`. The time limit and git access selects open on an entry that sends nothing, labelled with the default it resolves to (`defaultClockLabel`, `defaultAccessLabel`; see DL-049 and DL-043). Empty means "whatever the server resolves", and sending the field would say something the caller did not. The settings page does the opposite on purpose, because there an empty value is how a setting is cleared (see DL-062).

### Guards against spending twice or by accident

- **Enter never submits.** HTML implicit submission fires a form's default button when Enter is pressed in a single-line input, so the repository filter, which a reader types into expecting the list to narrow, would be one keystroke from provisioning a sandbox. A valid draft is exactly when the button is enabled, so validation does not help. `suppressImplicitSubmit` is on every single-line input (the repository filter, the check field and the model picker's search) and the form is submitted by its button alone. The goal textarea is unaffected, since Enter inserts a newline there.
- **A `Committed` error never re-enables submit.** `POST /api/v1/jobs` has no idempotency key, so pressing the button again after an error would buy a second sandbox for a job that already exists. `createAndGo` throws `Committed` for a 2xx whose answer carries no session id and for a redirect that threw. The form re-enables its submit button for an `ApiError`, which is a refusal, and never for a `Committed`. The message says the job exists and to find it in the sessions list. Nothing reconciles it automatically.
- **The default kind is `report`.** Both kinds spend a sandbox, but only `pr` pushes a branch and opens a pull request on a real forge, so the kind with the larger effect is chosen, not defaulted into.
- **There is no confirmation dialog.** The explicit "Start job" button is the deliberate act, and the accidental path a dialog would guard, Enter, is closed.
- The submit bar states the cost beside the button that spends it: "Works unattended for up to 1 hour on acme/app. Its sandbox is billed for as long as it runs, which can be longer." The second sentence keeps the time limit from reading as a ceiling on billing (see DL-049).

### A created job lands on its session's page

After `POST /api/v1/jobs` the browser goes to `sessionPath(session_id)`, `/session/?id=<session_id>`, through the `nav` seam in `client.ts`. jsdom has no navigation, and a seam called from a Svelte component is watched by nothing, because vitest does not load components. So the create and the redirect are one function, `createAndGo`, which takes the navigator as an argument.

- There is no job detail route. A job is a session plus a goal and a verdict (`store.Job.SessionID` is non-nullable, a composite foreign key, one to one), and a second page would duplicate the transcript tail, folding, sidebar and gate rendering. `/jobs/new` is a creation route and `/jobs/` a listing; neither is a detail route. A job id alone cannot be resolved to a page by the browser. If that is ever needed it is a redirect from a job id to its session, not a second page (see DL-057).
- The page lands on the live view on purpose. The first seconds are provisioning, with an empty transcript and a sidebar reading `queued`, then `provisioning`, which matches what the CLI shows.
- The session exists as soon as the job does (the same transaction) but has no sandbox, and the recorder attaches on its own cycle. If the live view stays empty until a reload after this redirect, check the recorder's `Recorder.Wake` nudge before suspecting the redirect (see DL-017). A person arriving from this redirect is the likeliest to notice, because they watch from second zero.

### The model option says where the default came from

The model picker's first entry sends the empty string, which the server resolves to the account default and then to OpenCode's own (see DL-014). Its label tells the truth about that.

- `defaultOptionLabel` names the account default when there is one ("Your default (anthropic/claude-sonnet-4-5)"), reads "OpenCode's default" only when there is none, and has a third label, "Whatever your account resolves to", used before `/me` answers. Both settled labels are claims about the account, so showing either while the request is in flight could flash a false statement. The third label is true in both outcomes, and submitting meanwhile cannot misreport, since the entry sends nothing in every case. A label saying "OpenCode's default" while the launch uses the account default is the mismatch this prevents.
- The opening value stays the empty string. Seeding the draft with the model string would select a duplicate of an option already in the list and send the same model by a second route.
- The default is read from `GET /api/v1/me`, a third request on load beside `/repos` and `/models`. If `/me` fails, the form reports the failure instead of swallowing it. Once a default is set, there is no per-job way to ask for an unspecified model.
- A note beside the picker (`defaultModelNote`) says the value came from the account, and the picker points at it with `aria-describedby`. The note is checked against the catalogue by `canLaunchOn`, so it never contradicts `keyNote`. A `#variant` default is matched on its plain reference, and an empty group list means "not known yet", not "nothing is launchable". A name the list lacks counts as launchable under a provider the caller holds a key for.
- Choosing another model applies to this job only. The form never writes the account setting back, because a standing preference changed silently by a one-off try is a surprise in the expensive direction. A "save as my default" checkbox was rejected, as a second way to write a setting on the page least suited to it.
- `withoutVariant` in `jobform.ts` is a third parser of model references (split at the first `#`; a half that would be empty is no variant). It must agree with `prep.LookupModel` and `modelRef`, and the Go test cannot see it, so change the three together (see DL-014).

### One searchable model picker

`ModelPicker.svelte` is the one model control, used by the job form, the session form, the settings page and the running session's model switch (which turns the custom entry off).

- A text field filters by provider and model as the reader types (`filterGroups`). Results group by provider, newest first, beta models marked. A provider without a key is shown but not choosable, in `keyNote`'s wording. The first entry is the default, labelled as above. A provider can hold hundreds of models, hence the search.
- **A custom model is never chosen by typing into the filter.** Each keyed provider ends with "Use a model not listed…", which opens a separate field under that provider for the model id and says it is not in spov's list. A typo cannot become a launch by accident. The id is checked as the server checks it (at most 200 bytes, no spaces, controls, format characters or `#`), and a provider's name typed in front of the id is caught, except for OpenRouter, whose own ids hold a slash. `pickNote` says that a custom name launches with a note when its provider has a key, and that every launch refuses it otherwise.
- Logic is in `web/src/lib/modelpick.ts` (`filterGroups`, the custom id check, `isListed`). `modelGroups` and `canLaunchOn` stay in `jobform.ts`. A keyed provider with no listed model is kept for its custom entry.

### `/sessions/new` is a lean form

`/sessions/new` is a repository picker and Start. The request is `{repos}` alone, plus a model only when one was chosen through the shared picker. The server's defaults and the account's profile fill the rest (model, git access, egress, image, duration), exactly as an equivalent `spov fly` resolves them. The picker lists what the caller's credentials reach, allows several repositories and needs at least one. After the POST the browser goes to the session page, which already shows provisioning.

- A session started here is the same row a CLI launch makes, so attach, End session and the quotas work unchanged. No new API was needed.
- It has the job form's guards. Enter never submits and a `Committed` error never re-enables Start, because the create has no idempotency key and a second press buys a second sandbox. After an ambiguous create answer, one lacking the session id, the page says the session was started and to find it in the sessions list. Start stays disabled and nothing reconciles automatically. Scenario 3 exercises this by rewriting the browser's create response with Playwright request routing (`scripts/scenarios/ambiguous-create.js`).
- Logic is in `web/src/lib/sessionform.ts` (`startAndGo`, `toSessionRequest`), sharing the picker code with `jobform.ts`. `RepoPicker.svelte` is the markup both forms use and `NewSession.svelte` holds only markup. The sessions page's primary button is "Start a session", with "Start a job" beside it as the secondary one.

## Rationale

- One endpoint for the CLI and the browser means one set of defaults and one validation order. A web-only endpoint would be a second path to the same row.
- `BrowserGuard` is already applied to every request, so a token would duplicate it.
- Form logic lives beside the component because vitest does not load a Svelte component without the mount setup, and logic left in the component is logic nothing can assert. `createAndGo` takes the navigator for the same reason.
- Alternatives to the redirect were rejected. Staying on the form with an inline status would invent a second place to watch a job. Redirecting to the session list would show a list with the new job somewhere in it, when the person wants that job. A real `/jobs/<id>` route would duplicate the session page.
- A default you cannot see is a default you cannot deliberately override, so the form shows the value already chosen for the reader.

## Measurements

- A provider's model list can be long: the largest in the catalogue holds 319 models (OpenRouter), which is why the picker searches.
- Guards for the account-default label were measured. Hardcoding `defaultOptionLabel` fails two tests, and changing `INHERIT` fails the pairing test. Editing `NewJob.svelte` back to a literal `<option value="">OpenCode's default</option>` is caught by nothing and passes every step of `scripts/check.sh`, and `astro check --minimumFailingSeverity hint` does not fire on it either, because it reports no unused-variable hint for a `<script>` const.

## Consequences

- A job can be started from a phone or a borrowed machine with no CLI, no Go toolchain and no Modal credentials locally.
- The browser can now spend money. Every future write of this kind inherits the CSRF answer above, and a change to `BrowserGuard` is a change to these forms.
- Both resources of the job form (repositories and models) refetch when the tab is refocused (`visibilitychange`). `GET /api/v1/models` decrypts a credential per provider in hosted mode, so consider that before adding a poll.
- `jobform.test.ts` covers the form's logic, including the pairing of the empty option with its label (the option sends nothing and its label names the account default). `TestOwnsPath` in `internal/server` keeps `/jobs/new` and the other web paths owned by the web app.
- `modelpicker.svelte.test.ts` mounts the picker to cover typing, choosing and the custom step.

## Known gaps

- No test checks that `NewJob.svelte` uses `defaultOptionLabel`. Code review is the only guard for that label.
- The CLI does not print which model it resolved.
- The `models` and `providers` fields arrive as `T[] | null` in the generated client because huma marks a Go slice nullable, so the form null-checks them.
