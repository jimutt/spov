## Context

DL-173 drew every synthetic message in a job's session as spov's, because spov was the only one sending synthetics into a job's session. From OpenCode 2.3.0 that is no longer true. Spike S-OI1 (`TestIntegrationSOI1InjectedMessages`, run against the pinned build with a fake model) measured what OpenCode adds to a conversation by itself, in any session:

- a background shell command's result, when the command ends: an inbox synthetic whose text is `<shell id="…" state="completed" command="…">\n<output>\n</shell>`, with `description` set to the command and `metadata` `{source: "shell", shellID, jobID, state, exit, truncated}`;
- a person's own shell command (the session's `/shell` route, the TUI's `!`): the same, with "The following shell command was executed by the user:" before it and no `description`; one that fails to start has `metadata` `{source: "shell", state: "error"}` and no wrapper;
- a directory's own `AGENTS.md`, the first time the agent works under it: a `session.synthetic` frame (published directly, not through the inbox) and a stored synthetic message whose text is "Instructions from: <path>" and the whole file, with `description` "Loaded <relative path>" and `metadata` `{instruction: {paths}}`;
- a subagent's report (DL-144), and, from the build's source, a restart notice (`metadata.notice`) and an image job's result (`metadata.source`).

On a job's page these were tagged "spov" and drawn whole: the raw `<shell …>` markup, and a repository's whole `AGENTS.md` in the middle of the transcript.

spov's own synthetics (the opening goal, `openJob`; the job plugin's continuations, replies and stop marker) carry only `text`, `resume` and `delivery`: no `metadata` and no `description`. S-OI1 checks that one sent so comes back with neither.

## Decision

**The server names an injected message.** A synthetic message or frame that carries a non-empty `metadata` or a `description`, and is not a subagent's report, is served with `injected: {kind, summary, shell}` on `MessageView` (from the stored message) and on `LogEvent` (from an inbox item's payload, or a `session.synthetic` frame's data):

- `kind` is `shell` for `metadata.source` "shell", `instructions` for a `metadata.instruction`, and `other` for anything else;
- `summary` is OpenCode's `description`, as one line of at most 200 characters, absent when there is none;
- `shell` (only for `shell`) is `{command, state, exit, by_person}`: the command is the `description` when there is one, else read from the wrapper; `state` and `exit` are the metadata's; `by_person` is set when the text says a user executed it. The message's `text` is then the command's output without OpenCode's wrapper and preamble. Text that does not have the wrapper's shape is left whole.

A `session.synthetic` frame is OpenCode's own publish, so the log gives it the role `synthetic`. The page then joins it with the stored message, as it does an inbox item.

**The page tags a message "spov" only when spov sent it.** A synthetic is drawn as spov's (DL-058's "spov" tag, the stop marker's sentence) only in a job's session and only when it is not `injected`. Every injected message, in any session, is folded:

- a shell result is one quiet line: who ran it ("Background command", or "Run by a person" for `by_person`), the command's first line, and how it ended (finished, exit N, cancelled, failed to start). A press opens the whole command and its output;
- anything else is DL-173's fold, labelled with its `summary` when there is one, else "Added by OpenCode or a plugin".

A synthetic in a session without a job stays DL-173's fold whether or not it is injected.

**spov keeps sending bare synthetics.** Nothing spov sends as a synthetic sets `metadata` or `description`; a test of the opening goal's body and of the plugin's calls guards it.

## Rationale

OpenCode marks everything it adds, and spov marks nothing it sends, so the mark tells them apart without a list of OpenCode's sources. A source OpenCode adds later is folded by default rather than drawn as spov's. Reading the shell result's parts from the metadata and the description, rather than the wrapper, keeps a command that contains quotes or `">` from cutting its output short. The page gets the output alone and never parses OpenCode's markup.

## Consequences

- DL-173's consequence (a plugin's synthetic in a job's session drawn as spov's) now holds only for a plugin that sets neither `metadata` nor `description`.
- On an OpenCode bump, S-OI1 re-measures the shapes (`SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SOI1 -v`).
- The served `text` of a shell result differs from the stored message's raw text; the CLI prints neither.
