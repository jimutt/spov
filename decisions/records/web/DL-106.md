## Context

The web app was laid out for a desktop and only reflowed below it. On a phone this cost most of the screen:

- The header wrapped to three rows (wordmark, five links, the address and the theme buttons), about a sixth of the height, and stayed there as the page followed a long transcript.
- A session's row in the list was seven or eight lines, led with the session's name, and showed the repositories last, small and clipped. Sessions have no generated friendly name, so the name is often `job-9f2c1` or an ID, and the repository is what tells one session from another.
- The session page opened on the sidebar (name, job, workspace, cost), then a head (title, facts line, clock bar), and only then the transcript. The composer was a full-height form at the foot of the document with a wide model picker, and a sent message could land out of sight above it, so the reader scrolled up to find it.

## Decision

Below `md` (768 px) the header is one bar, and below `lg` (1024 px, where the page is one column) the session page has its own bar and a docked composer. From `lg` up nothing changes.

- **One-bar header.** The wordmark and a button naming the current section; the links, the account and the theme are the panel it opens. The panel is the desktop row's own elements (`md:contents`), so each is rendered once. Escape and a press outside close it. `interactive-widget=resizes-content` in the viewport meta makes an on-screen keyboard shrink the page, so a bar docked to the bottom rides above the keys. The session page's header scrolls away below `lg` (`stickyFromLg`), because the page brings its own bar. `--main-pad-y` and `--page-pad-x` are smaller below `lg`; the sticky sidebar that reads them exists only from `lg`.
- **A session is its repository.** `repoHeadline` gives the first repository (owner muted, name bold, "+N" for the rest) and leads the list row and the session bar. The session's name moves to the meta line beside the kind ("Pull request job · job-9f2c1"). A session with no repository leads with its name. The row is five lines: headline and start time; state; kind and name; the last words; running time and cost, with "at least" kept on the cost (DL-009). The lifetime bar and its caption are dropped below `md`, except the "Stops in" warning. From `md` the table of DL-060 is as it was.
- **A slim session bar.** Below `lg` one sticky bar holds the way back to the list, the headline, the state (the job's, as in the list: `listState`), how long it has run, the name, and a button that opens the rest. The title, facts line and clock bar are for `lg` and up.
- **The sidebar is a sheet.** Below `lg` the same `aside` is a full-screen sheet over the page, opened from the bar's button, closed by its own button or Escape, with the page behind it locked and focus moved in and back. It carries everything the sidebar does, including End session and Resume, and the clock bar. It is one element and not a second copy, so the page holds one of each control.
- **A docked composer.** Below `lg` the composer is docked to the foot of the screen (`sticky bottom-0`) instead of sitting at the foot of the transcript. Below `md` it is a field that starts at one line and grows with its text to about five, a round Send, and one chip that names the model and opens the model switch, the choice of what follows a message and Send's note. The Enter hint, which a phone has no use for, is hidden. The desktop form is the same elements in a flex row. The dock's height is published as `--dock-h` so "Jump to latest" floats above it.
- **Enter on a touch screen writes a new line.** When the main pointer is a finger (`pointer: coarse`, `touchFirst`), Enter inserts a newline and only the Send button sends; Ctrl or Cmd-Enter still sends, for a tablet with a keyboard, and the field's on-screen key is labelled "enter" instead of "send". With a keyboard as the main input Enter sends and Shift-Enter writes a line, as before, whatever the window's width. The "Enter to send" hint is drawn only where Enter sends. This reverses DL-059's rule on a touch screen alone, because a phone's keyboard has no Shift and a message there is more often several lines than one.
- **The jobs page below `md`.** The limit and Start a job share one line (the header already names the page), the filters are one row that scrolls sideways, and a row is four lines at most: the goal's first line, the state with the kind and the time, and how it came out. A linked pull request reads `owner/repo #7` (`linkLabel`, with the forge's own `!` or `#` from `changeRef`) and not a clipped address, which cut off the number; the whole address stays from `md`. A job's view carries no repositories, so the goal and the outcome are what tell jobs apart.
- **Sending returns to the end.** A sent message puts the page back at the end and follows again, wherever the reader had scrolled to, as in any chat. This is the one case where an action of the reader's own re-arms the latch (DL-057); scrolling still releases it.
- **The page follows growth no event announces.** While the latch is armed, a change in the page's size (a web font arriving, an image, the dock changing height) scrolls to the end, as a new block does. Without it the page could settle a few tens of pixels short of the end, which the 64 px tolerance counts as the end, and the last line sat behind the dock.

## Rationale

- One bar spends about 50 px where three rows spent about 125, and the reader keeps one control for every page.
- The composer docked to the screen is what every chat on a phone does, keeps the box where the thumb is, and makes "I sent it, where is it" a non-question. It is sticky rather than fixed, so the document's own scrolling, the tail latch and the measurements built on them are untouched.
- The repository leads because it is the only fact on a row that is always present and always distinguishes sessions.
- The sidebar is a sheet because a phone reads the transcript and asks for the facts on occasion; a page that opens on them puts the thing it is for a screen away.
- Structure changes at `lg` and density at `md`, because the grid is one column up to `lg` and a tablet has room for the table and the full header.

## Consequences

- Amends DL-059 on where the composer sits (below `lg` it is docked, from `lg` it is at the foot of the transcript's column as before) and on Enter (a newline on a touch screen). The rules for what it sends, Interrupt, Resume and the echo are unchanged. Amends DL-057 on the head, the sidebar and the header below `lg`, and on the latch being re-armed by a send and by growth. Amends DL-060 on the row below `md`.
- CSS decides what is drawn and jsdom has none, so the tests assert the markup's state: the sheet's `aria-expanded` and class, the chip's words, and where a send scrolls (`sessiondetail.svelte.test.ts`, `composer.svelte.test.ts`, `format.test.ts`). Nothing but a browser shows the layout; the pull request that introduced this carries screenshots at 390 px, 768 px and 1280 px.
- The header's measured height still feeds `--header-h`; below `lg` nothing sticks to it.
- A control added to the sidebar is on the phone's sheet with no further work. A control added to the composer's row below the field belongs in the options wrapper or it takes a row of the dock.

## Known gaps

- A job's row cannot lead with its repository as a session's does: `JobView` has none, and adding them is an API change. Until then a job is known by its goal.
- A tablet with a keyboard is treated as touch, so Enter writes a line there and Ctrl or Cmd-Enter sends. A pointer-and-keyboard detection finer than `pointer: coarse` would need `any-pointer` and a guess about which the reader is using.
- The bar shows the state of the job when there is one and of the session otherwise, and the elapsed time only when there is no reason to give; the reason ("Waiting for you") wins the space.
