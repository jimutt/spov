## Context

A run of tool calls and thoughts opens inline in the transcript, below its summary line, and folds again only from that line (DL-058, DL-158). A model that works for a long time without writing to the reader leaves runs of hundreds of lines, so once one was open a reader had to scroll all the way back to its top to fold it, on a phone for a long time. Claude's own apps were the reference the user gave: the web app opens such steps in place, its phone app in a drawer over the conversation.

## Decision

- Below `lg` (where `(min-width: 64rem)` does not match when the reader opens it), opening a run leaves its summary line where it is and shows the run in a sheet over the whole page, as the session's details sheet is (DL-106): a bar at its top with the summary and Close, and the run below it, scrolling inside the sheet. Close, Escape and Back close it. Back works because opening pushes a history entry for the same address, which Close takes back; the session page's own `popstate` reads the same view and does nothing. The page behind does not scroll while it is open (`lockScroll`, a count shared with the details sheet and the report preview, so overlays closing in either order never leave the page locked), focus moves to Close, and returns to the summary on close without scrolling the page (`preventScroll`). Opening and closing never move the reader's place in the transcript. A second Close or Escape before the first one's `popstate` does nothing, so it never goes back past the sheet's entry.
- From `lg` a run opens inline as before, and its summary line is sticky under the page's header (`top: var(--header-h)`) while any of the run is on screen, so it can be folded from anywhere in it. Folding a run whose top has scrolled above that line scrolls the page so that the folded summary stays where the reader saw it.
- That scroll is instant with a fine pointer and smooth with a coarse one. This narrows DL-163's "every scroll the page makes is smooth" to what it measured: Firefox for Android stops drawing a sticky bar after an instant scroll, and a wide touch screen can run it, while a desktop browser with a mouse jumps without a flicker and without a long animation back over the folded run.
- Whether a run is a sheet is decided when the reader opens it: a viewport that crosses `lg` while a run is open (a turned tablet, a zoom) keeps a sheet a sheet and an inline run inline. Where the browser offers no `matchMedia` (jsdom), the run opens inline. A run inside a subagent's card behaves the same way, and which calls are open inside a run is still its own state (DL-158).

## Rationale

A sheet keeps a phone's transcript as long as it was, so neither opening nor closing a run moves the reader, and it matches the details sheet the page already has. On a wide screen the run beside the conversation is worth keeping in place, and a sticky summary costs one line while removing the long scroll back.

## Consequences

- `eventrun.svelte.test.ts` checks the sheet's Close, Escape and Back, a double close, a width change while open, and that a wide screen draws the run inline with its summary sticky; `scrolllock.test.ts` checks the shared lock. jsdom cannot show the stickiness itself.
- Like the details sheet, the sheet does not trap keyboard focus or make the page behind it inert; the summary behind it, reached by Tab, closes it through the same history step.
- The history entry a sheet pushes is left behind if the run disappears while open (a switch of view): one Back then changes nothing visible.
