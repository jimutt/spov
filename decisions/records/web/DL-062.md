## Context

The web app needs a place for account preferences: a default model, a git identity, default limits. A page named after credentials alone would not fit a default model, which is not a credential. Two settings pages would need a rule for which setting goes where, and no such rule exists, since all of them are things about the account that are not a session.

Every preference is stored in the caller's profile row and edited through `PATCH /api/v1/me`, which creates a missing profile row (a local server has none until the first write). The page reads the current values from `GET /api/v1/me`, and no other endpoint is involved.

## Decision

### One page of independent sections

`/settings` is a page of sections, not tabs, since each form is short. In order they are:

1. The default model.
2. The OpenCode sign-in.
3. Credentials.
4. For an admin only, the Organisation section, which stores, replaces and removes the organisation's shared GitHub App (`OrgSettings.svelte`, `orgsettings.ts`; the routes are in DL-042).
5. Git access defaults, one for sessions and one for jobs (see DL-043).
6. The default job time limit (see DL-049).
7. The git identity.

There is no `/credentials` page: the path 404s. The app is a static build, and `internal/webui` serves its 404 page for any path it has no file for. There is no redirect stub, because a file kept only to forward a bookmark tends never to be deleted. `TestOwnsPath` in `internal/server/webui_test.go` lists both `/settings` and `/credentials` among the paths the web app owns, on purpose: it catches a route the server might later claim.

Each profile section has its own Save button, so independent settings fail independently. With one shared button, a refused model would take the identity change down with it, and several fields would share one outcome message on a page whose purpose is to report what the server holds.

### Saving a credential refreshes the model list

A provider's models are disabled because `GET /api/v1/models` reported `have_key: false` for it, and storing that provider's key in the credentials section does not change the answer already on screen. `Credentials.svelte` calls `onChanged` after both a store and a delete, and the page refetches the model list, so the greyed-out providers follow the keys. The callback is named for both acts so the delete half does not look like an oversight. The OpenCode sign-in section refreshes the list the same way.

In local mode the refetch returns the same answer, because `spov serve` reads the environment and the credential store once at startup. `have_key` cannot change until the server restarts, and the refusal message says so (see DL-013).

### The default model

The control is the shared `ModelPicker` (see DL-061), populated from the server's model list and never typed. A provider without a key is listed disabled with its variable named, and the reason is also written as prose beside the picker because screen readers skip disabled options. The empty "no default" entry clears the setting.

- `keyNote` in `settings.ts` is the job form's `keyNote`, computed from the catalogue and not from the rendered options. It points to the OpenCode sign-in as being "below", since on this page that section follows the picker.
- No note is built from a model list that failed to load. With no providers `keyNote` would say "no provider has a key", which is a claim about the account caused by a transport error, shown beside a `Problem` saying the list could not be read.
- A stored default the catalogue does not carry is shown by the picker as its value, with the custom-model note, so it does not render as "no default" on the page meant to fix it. A `#variant` reference is launchable although the listing holds plain references, because the server strips the suffix. `withoutVariant` in `jobform.ts` is the third parser of model references and must agree with `prep.LookupModel` and `modelRef` (`TestTheCheckAndTheSandboxAgreeOnWhatAReferenceIs`). `settings.ts` re-exports it instead of carrying a fourth copy.

### An empty value is sent, never omitted

Every settings request sends all of a section's fields, empty ones included (`defaultModelBody`, `identityBody`, `gitAccessBody`, the job-duration save). On this page the field is the setting, so omitting it would mean "leave my value alone" and there would be no way to clear one. The job form follows the opposite rule: there, omitting the model means "resolve it for me" (see DL-061). The two are not to be made consistent.

### What the page says after a save

- The note reports the server's answer, not what was typed. `PATCH /api/v1/me` trims its input and may refuse it, so a page echoing its own input could claim a save that did not happen. A clear produces an explicit note, since a note that went blank would look like a failed save. The note carries `role="status"` so the outcome is announced.
- Save stays disabled until the profile arrives, and the page says why when it cannot be enabled. Nothing can differ from a value the page has not read, and without an explanation a failed `GET /api/v1/me` would leave the button disabled beside a populated control, which looks broken rather than blocked.

### How a control is seeded from the profile

`seedField(loaded, current, prev)` in `settings.ts` folds an arriving profile into one `Field` (`stored`, the server's last value, and `value`, what the control holds). It is a function, not the body of an effect, so a test can reach it. Each control has one `$effect` that calls it. It has three guards, and each looks like a one-line convenience:

1. **Nothing happens before the profile has loaded.** The effect runs once while the request is in flight. Without the guard the stored value is recorded as `""`, the arriving profile is not the first one seen, and the reader's real default never reaches the control.
2. **The draft follows the profile only while the reader has not changed it.** Checking only "has a profile been seen" would make seeding one-shot. The resource reloads whenever the tab becomes visible, so a value changed elsewhere would leave a control stale, with Save ready to revert it. The same test keeps one section's unsaved edit when another section's save refreshes the profile.
3. **It returns `prev` unchanged when nothing changed.** The effect reads the field and writes it back, and in runes mode Svelte does not exempt the running reaction from its own write. A fold that allocates a fresh object on every pass marks its own dependency dirty and reschedules forever, and the page throws `effect_update_depth_exceeded` as soon as the profile arrives.

After a successful save the page calls `me.refresh()`, which abandons any request in flight. Otherwise a request carrying the old profile could land and, since the draft then matches the profile, seed the old value back over the save. `changed(...fields)` is the Save button's enable check, generalised over several fields. It compares trimmed values, because a save sends the trimmed value, and counts a field the profile has not reached as unchanged.

### One pending flag for every profile Save

The profile sections write the same row. The `PATCH /api/v1/me` handler reads the profile, applies the fields the request named and writes the whole row back, so two overlapping saves each lose the other's field while both return 200. A single `pending` value, derived from every profile save in flight, disables all profile Save buttons and is checked at the top of every handler. The `disabled` attribute is what the reader sees. The handler check covers a submit the markup did not start: a stray Enter, a browser extension, `requestSubmit`. The credentials form is excluded, because it writes a different endpoint and row and refuses its own double submit.

### The git identity section

Name and email are read from `GET /api/v1/me` and saved with the same `PATCH` (`identityBody`, `saveIdentity`, `savedIdentityNote`). The identity is set from the sign-in profile when the account is created and can be changed here. The section says the values decide the commit author for a session, that they are unrelated to the account they sign in with, and that they apply to launches naming no author of their own, which is what the browser starts. The CLI sends the local git config instead.

- An empty field falls back to the server's own identity, but `git.ResolveIdentity` fills one field at a time (the request, then this profile, then the server's configuration). A profile with a name and no email produces commits with that name and the server's email. `savedIdentityNote` says so, and tells the reader to set both or clear both. Only when the server has no identity either does git invent the missing half (see DL-044).
- The form carries `novalidate` and adds no validation the server lacks. `PATCH /api/v1/me` trims and stores whatever it receives, and git accepts almost anything as an author. A browser-only email rule would be skipped by the CLI and direct API calls, so it would look like a guarantee and be a suggestion. `type="email"` stays for the keyboard, and `novalidate` stops constraint validation from silently refusing a value the server would accept.

## Rationale

- One page, not two, keeps one answer to "where does this setting go". Sections suit forms this short, where tabs would hide most settings behind a click.
- Picking the default model from a server-provided list reflects that a model name is a value whose typo is expensive to discover, and the server refuses an unusable one on save.
- Logic that sits inside a component cannot be observed by a test, and for seeding that logic is the whole feature. The page folds through `seedField` for the same reason.
- The pending flag fixes the one-screen, two-buttons race that people actually hit.

## Measurements

- An unguarded fold in an `$effect` (a fresh object on every pass) ran 1002 times and then threw `effect_update_depth_exceeded`, the moment the profile arrived, taking the page down. Re-run with `cd web && bun run test`, in `settings.svelte.test.ts`.
- Such a bug passes `scripts/check.sh` when "vitest never loads a Svelte component" is read as "reactivity cannot be tested". The vitest config sets `resolve.conditions: ['browser']`, which `mount` needs; without it `mount` throws `lifecycle_function_unavailable`.

## Consequences

- Account settings have one page with room for another section.
- Two tests mount the reactivity: `settings.svelte.test.ts` runs the fold under runes, and `components/settings.svelte.test.ts` mounts the page to test the button rule, which exists only in the rendered markup. Pure logic is tested in `settings.test.ts`.
- A mounted test has one trap. openapi-fetch captures `globalThis.fetch` when `client.ts` is imported, so the fetch stub must be installed in `vi.hoisted`. A stub installed in a test body is never used and every request goes to the real network.
- A pending-flag test must dispatch `submit` on the form. Clicking a disabled button dispatches nothing and proves nothing about the handler check.
- Links to `/credentials` 404.
- Per-session git identity is unchanged: `store.SessionRequest` carries `GitName` and `GitEmail`, the CLI resolves them locally, and this page covers only the stored profile.

## Known gaps

- The pending flag is not a server-side fix. Two separate clients can still race on the profile row, and preventing that needs a conditional write.
- In local mode `have_key` cannot change until `spov serve` restarts, so storing a key there refreshes the list to the same answer.
