## Context

A job is a session plus a goal and a verdict. `store.Job.SessionID` is non-nullable with a composite foreign key, so the relationship is one to one and the session is the durable half: it outlives the sandbox, and the job row points at it. The page where a person reads what the agent did is therefore the session page, and the job's state, gates and deliverables belong on it. A second route for the same thing would fork the reading experience: the scroll behaviour, the sticky sidebar and the folding of events would have to exist twice.

A transcript grows while someone watches, so the page also has to decide where it opens and when it follows new output. Cancelling a job or ending a session terminates a sandbox, and nothing brings back what it held. A cancelled job ends without a verdict, and anything the agent had not pushed is lost. These acts need their own thought about confirmation.

## Decision

### A job is shown on its session's page

There is no job detail route. `/jobs/` is a list whose rows link to session pages and `/jobs/new` is a creation route (DL-060, DL-061). When a session has a job, its sidebar gains a job section; a session with no job has none, and nothing about its transcript differs.

The page finds the job through `GET /api/v1/jobs?session=<ref>`. `listJobsInput` takes a `session` query parameter (`store.JobFilter.SessionID`), so the page does not list every job and filter in the browser. At most one job matches. State filters on the same endpoint are one comma-separated parameter, because huma keeps only the first value of a repeated query parameter and drops the rest silently; anything that filters on a set must not use the repeated form.

The job resource is a store read, so polling it does not touch a sandbox (DL-018). It polls every 10 s only while asking again could learn something:

- it stops when the job is in a terminal state;
- it stops when the endpoint answered 501, which is a server with no supervisor and would otherwise be asked every ten seconds for as long as the tab is open;
- it keeps polling on any other failure, such as a 502 from a restarting replica or a dropped connection, because stopping would leave the page stale for good;
- `blocked`, `steered` and any state this build does not know count as still changing, since a newer server's unknown state is more likely a new in-flight one than a new terminal one;
- a session that answered once with no job never gains one, because a job's session is inserted in the same transaction as the job.

The session's own row is polled every 5 s only while the session is still `starting` (`sessionSettling`), and not at all after a failed read, so a session that answers 404 is not asked for again. Its gate is a `$derived` boolean too.

The gate is a `$derived` boolean and not a read of the parsed job. The gate is evaluated inside the resource's effect, and reading a freshly allocated object made the effect tear down and re-run on every answer. A re-run loads immediately, so the interval never ticked and the page made one request per round trip. A derived value does not notify its dependents when it recomputes to the same value. `resource.svelte.test.ts` pins this.

### The sidebar

The sidebar is sticky. It carries the session's name and state, then the job section when there is one, then the workspace and the cost. It shows facts and keeps explanations behind an (i) control (`InfoToggle.svelte`):

- The job block's heading is the kind in words ("Pull request job", "Report job") with the job's state mark on the same line, then the time limit ("Stops at 16:40 (2h limit)", or the reason the clock is not counting), the goal, the deliverables and the actions. Deliverables are drawn by their kind (DL-051); the kind decides the rendering, never sniffing the text.
- The goal is folded to about 240 characters (`clip`, at a word boundary) with "Show all", because it is in the transcript whole.
- The verdict is a disclosure headed by one mark and word (`verdictSummary`): "Passed", "Passed, 1 unverified", "Partial", "1 gate failed" or "Unverified". The worst gate decides it, except that a gate spov could not verify beside passing ones still reads as a pass, since a job started without a check is unverified on gate 1 every time. The disclosure opens by itself when a gate failed or the deliverable was partial. Inside, each gate is listed by name (Check, Deliverable, Conduct) with its mark and word from `gateMark`, so "unverified" stays neutral, and its detail beneath (DL-050).
- A credential is one row, the platform and its kind ("Stored token", "App token"). The full `credentialLine` note opens behind the (i). What departs from the usual case stays visible: `credentialTag` adds "every repository" for `access: all`, "inside the sandbox" for a sandbox-held token, and whose credential was used.
- "Cost so far" shows the figure, with how it is worked out behind the same control. The sandbox stays a `details`.

### The verdict is shown gate by gate

The verdict is drawn as its gates, not as its stored text, because which gate decided is the point, and a successful job has a verdict too (it is kept out of `error` so a client cannot render success as failure). `JobView.Gates` is parsed in Go by `jobs.ParseGatesNote`, which sits beside `gatesNote` in `internal/jobs`, and `TestTheGatesSurviveTheRoundTrip` pins the pair to each other. A new column would be a second copy of a fact the row holds, able to disagree with it. Parsing in the browser would couple the web app to a `Fprintf` format across a language boundary, with silent drift. The verdict text is still carried beside the structure, so a line this build cannot parse is shown and not lost.

Three kinds of line in the verdict text are not gates and must not be parsed as one: the summary (a gate's detail verbatim, with the same shape), the retry note (a bullet with no gate shape), and a detail that itself contains `: ` and `(`. `gatesNote` collapses whitespace when it writes, because a gate detail is not always spov's wording: gate 3's embeds the tool name and error type the sandbox chose. A newline in a detail would end the line early, lose the closing parenthesis and make the parser drop the deciding gate from the structured view while the text below still names it.

### The page head and the clock bar

The head is a title, one facts line and a clock bar. The facts line holds the state mark with how long the session has run ("Running for 1h 12m", "Stopped after 0h 52m"), the repositories in mono and the sandbox ID, separated by space.

The clock bar is a 4 px track from "Started 14:02" to "Job stops at 16:40" with a tick and the time at now. `clockBar` in `format.ts` decides it from fields the page already reads (`JobView.clock_started_at`, `clock_used` and `max_duration`; `SessionView.created_at` and `sandbox.timeout_secs`) and needs no API of its own:

- for a running or blocked job it shows the job's wall clock, the part used (including time from before a resume, and the start reads "Resumed" after one) against the limit; the fraction is `(clock_used + now - clock_started_at) / max_duration`, the same arithmetic as `wallClock`'s `endsAt`, so the two cannot disagree about when the job stops;
- while a job is steered the clock is paused, so the bar shows what is used, says "Paused while you steer" and has no now tick;
- for an interactive session it shows the sandbox's timeout, "Sandbox stops at";
- it turns gold inside `WarnWithin` (15 minutes);
- a session that has ended, or a sandbox with no timeout, has no bar.

The lifetime warning is on the hard timeout, because the API has no last-activity time and an idle countdown would be invented.

### The transcript opens at its end and follows the tail

Opening a session shows the end of the transcript. Following the tail is a latch (`web/src/lib/tail.ts`), not a one-off scroll, because the live stream appends and a jump on load is scrolled away by the first arriving event. It sticks to the bottom only while the reader is already within 64 px of it, releases the moment they scroll up, and re-arms when they return to the end. "Jump to latest" is offered whenever the reader is not at the end, measured fresh, and stays for a finished session. It is centred over the transcript column. A page that always follows pulls itself out from under someone reading earlier output.

The latch must not re-anchor on the stream's five-minute reopen. A reader who sits at the end through an orderly `end` and silent reopen must not see a jolt, and a scroll implementation that re-reads on `end` would undo the transcript's read-once rule (DL-058; the guard is `live.test.ts`, "an orderly close reopens without reporting a gap"). The latch is unaffected by layout changes, which only move content inside the column the document already scrolls.

The top navigation is sticky too, because a page that follows a growing transcript carries the reader far down the document and never scrolls back up on its own. The sidebar's sticky offset is `--header-h` plus `--main-pad-y`, one value written once. The header's height is measured at runtime in `Base.astro` and published as `--header-h`, since it wraps on narrow viewports and follows the type scale. A wrong literal puts the sidebar under the navigation, which looks like a z-index bug, and a mismatch between the sticky offset and the natural position makes the sidebar jump as it starts to stick. `--read-w` caps the transcript column and `--log-w` is what its rows cap at (the two are equal); anything that caps the transcript uses `--log-w`. A sticky sidebar needs `self-start`, because a stretched grid item is as tall as the transcript and a sticky element never moves within its own box. Below the `lg` breakpoint the sidebar is ordered first in the grid so the page does not open on "Cost so far".

### Cancel job and End session

The session page has two controls, Cancel job and End session. Each acts only on a second press, and neither is offered anywhere else. List rows stay read-only: you open the thing first and see what you are ending. "Stop" already names the interrupt of a turn, so the new controls use names that cannot be read as that (DL-053).

- **Cancel job** sits at the foot of the sidebar's Job section and calls `DELETE /api/v1/jobs/{id}` (`Service.CancelJob`). `cancellable` offers it for `queued`, `provisioning`, `running`, `blocked` and `steered`. It does not offer it while `delivering`, because the run is over, the verdict is seconds away and a cancel would throw it away. Terminal and unknown states offer nothing. The rule is a `Record` over every job state, so a new state fails `astro check` until it is decided, as `sendability` and `canStop` do (DL-059). The browser's rule is narrower than the server's, which accepts `delivering`; the CLI can still cancel a job stuck in delivery.
- **End session** sits in the sidebar's first section under the session's state and calls `DELETE /api/v1/sessions/{ref}` (`Service.Delete`). `endable` offers it for a `starting` or `running` session that no unfinished job drives, and nothing is offered until the jobs read has answered. A job's session never offers it, because the server's session delete on an unfinished job's session cancels the job (`DeleteSession`), so two buttons would do one thing under two names. Once the job is terminal, a session that is still live can be ended like any other.
- **The first press asks; the second acts** (`ConfirmAct.svelte`). The first press replaces the button in place with a sentence naming what is lost and two buttons: the act ("Yes, cancel" or "Yes, end it") and "Keep it". For a job: its sandbox is terminated, the job ends without a verdict, and work that was not pushed is lost. For a session: its sandbox is terminated and anything not pushed is lost. "Keep it" takes focus, so a stray Enter or Space backs out. Escape backs out. The question disappears if the state changes so that the act does not apply, for example when the job finishes while it is open. There is no modal and no `confirm()`, which looks foreign and is suppressed in some embedded browsers. Typing the name to confirm was rejected as too heavy, and no confirmation at all as too easy next to the safe Stop and Resume buttons.
- **One request at a time.** A pending flag disables both buttons. Afterwards the page re-reads the session and the job. A job that finished while the cancel was in flight answers 409; its outcome stands, the server's message is shown, and the page does not retry. `SessionDetail` holds the failure and not the control, because a refusal re-reads the page and can withdraw the control.
- Both controls sit outside the composer's form, as Stop and Resume do, so nothing in the composer can submit them. CSRF protection is the browser guard alone (DL-061). The server is unchanged: both endpoints, their errors and their audit notes ("cancelled by …") are what the CLI uses.

## Rationale

- One page for one thing: the transcript is the same whether or not a job drove it, and the relationship is one to one in the schema, so a session shows its job without ambiguity.
- Rendering the gates separately is what makes a verdict useful: "failed" says nothing, while "Conduct: failed, the run was refused" says what happened.
- Tail-following is specified as a behaviour because the naive version is worse than none: it either fights the reader or does nothing after the first event.
- The clock bar is the element that belongs to spov. Time against its limit is what costs money, and it has a picture.
- The sidebar is read at a glance while the transcript runs. A sentence that is the same on every session, such as how cost is worked out or what an App token is, is read once and then is in the way.
- The controls are on the session page because that is where you can see what you are about to lose: the transcript, the job's state and the time limit are all there. A row shows a name and a badge. Cleaning up several things at once is slower this way, which is an acceptable cost.
- A second press in place keeps the confirmation next to the thing it confirms, and moving focus to "Keep it" makes the careless keyboard path the safe one.
- No cancel while delivering, because delivery is short and produces the one thing a job exists for.

## Consequences

- The cancellable states are written twice, in Go (`CancelJob` refuses a terminal job) and in the browser (which also leaves out `delivering`). They differ on purpose.
- Changing a Go type under `internal/server`, such as `listJobsInput`, needs `scripts/gen-api-client.sh` (DL-005).
- The web build is the step that catches a template error: `astro check` does not compile Svelte and vitest never loads a component, so `bun run build` has to pass and not just the check and the tests.
- `sessiondetail.svelte.test.ts` and `jobcontrols.test.ts` guard the controls: second press, Escape, no cancel while delivering, End session only once the jobs read has answered, and a refusal shown beside the job without a retry.

## Known gaps

- Row actions, ending several sessions at once and undo do not exist. None is possible without a server change, and none is needed yet.
- The page cannot show an idle countdown, only the hard timeout, until the API reports a last-activity time.
