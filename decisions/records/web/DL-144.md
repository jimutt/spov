## Context

DL-112 reads a subagent card's state from the child's own frames, and falls back to the call that started it when the child has none: a finished call that was not a background call means the child is done. From OpenCode 2.3.0 every `subagent` call returns at once and its input carries no `background` flag, so that fallback calls a child done before its first frame is read.

The page also draws the agent as working only while the main conversation's turn is in flight (DL-111, DL-059). With background subagents the main turn ends while children work, so the page looks idle during the longest part of a delegated task.

## Decision

- A finished `subagent` call says nothing of its child, whatever its input. With no frame of the child's read yet the card is starting, and running once the child has frames with no execution ending. `DelegatedCall.background` and the reading of the `background` input are removed. A call that failed started no child, and its card stays failed. A finished call with no conversation behind it that names no child (a log recorded before parentage, DL-110) has nothing to wait for and stays done.
- Each `LogEvent` carries its conversation's parent (`parent`, the parent's OpenCode id, absent for a root), resolved where the log handler already names the conversation (`conversationNames`). The page adds a conversation for each child the log names that the conversations it read do not list (`withLoggedChildren`), so a subagent started while the page is open is a child at once and the page never reads the conversations again for it; DL-111 assumed a re-read the page did not make. A child a call names that no conversation lists (a log from before parentage) is judged from its own frames in the log all the same, grouped by session once per build.
- `subagentsWorking` (a plain function beside `subagentState`) counts the children, at any depth, whose state is running or starting, from the cards the timelines drew. While the main turn is not in flight and the count is above zero, the composer's status line reads "1 subagent working" or "N subagents working", and a job's sidebar state line adds the same words. A session that has ended counts none, and so does one whose recording has stopped (`recordingStopped`: spov's `spov.recorder.stopped` is the last thing the log holds from anyone but spov, DL-131), since no frame of its children will come.
- Interrupt stays tied to the main conversation's turn (`canStop` is unchanged): it is not drawn while only subagents work, and the page offers no way to stop a subagent. The status line's explanation (`controlsNote`) says a message sent now is read when the agent's next turn starts.
- Sending is unchanged: `sendability` does not read the count.
- A child's report is not a message. At 2.3.0 it reaches the parent as a `synthetic` inbox item whose `metadata.source` is `"subagent"`, naming the child in `metadata.childID` and how it ended in `metadata.state` (`completed`, `cancelled`). The server says so on the wire, from the stored frame (`storedReport`, beside `storedRole`, through `jobs.InboxItemReport`) and from the stored message (`messageReport`), as `report: {child, state}` on `LogEvent` and `MessageView`; the browser never decides it from the text. The page draws a report neither as a message nor as a line, so none of its text is shown: the card already shows the child's conclusion. A report's `state` decides a card whose child has no execution frame read (`completed` done, `cancelled` stopped). A report is never a person's message: it is synthetic, so `messageStatuses`, the echo reconciliation, `personWrote` and the takeover rule pass it by. A session recorded before the field draws as before.

## Rationale

The child's own frames are the only source that says how a child is going, so the fallback should claim nothing. The count is derived from what the page already holds, so it asks the server for nothing. Interrupt is left alone because `POST /sessions/{ref}/interrupt` addresses the main conversation, and what it does to a running child is not measured; offering a control whose effect is unknown would be worse than offering none.

## Measurements

- S-SA3 (local, at 2.3.0): an interrupt of the parent does not stop a running child, whether the parent is idle or its own turn is in flight; the parent's tool is aborted and the child's is not. Interrupting the child's own session stops it (`session.execution.interrupted`, reason `user`), and its report reaches the parent with `state="cancelled"` and starts a parent turn. So Interrupt on the page, which addresses the main conversation, never stops a subagent.
- The fixture the page's tests read (`subagent.fixture.ts`) is S-SA1's 2.3.0 capture passed through the real recorder (`TestWriteTheSubagentFixture`), beside the 2.2.5 foreground and background pairs.

## Consequences

- A session recorded before the pin moved still draws correctly when its children's frames were recorded: its foreground children have their own frames, which decide first. A listed child with no frame recorded (an old session's, or one past a session's storage limit, DL-131) is a card that is starting ("Delegating…") until the session ends, and stopped after; its call's success no longer says done. While the session runs, a recording that has stopped keeps it out of the working count.
- Stopping a running subagent from the page stays unavailable. S-SA3 has since measured that only an interrupt of the child's own session stops it; offering that is a decision of its own.
- `LogEvent` gains `report` and `parent`, and `MessageView` `report`, so the generated document and client change (DL-005). The report's text stays on the wire for other clients.
