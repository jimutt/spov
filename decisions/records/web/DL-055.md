## Context

spov serves one origin and one image. The API and the sign-in surfaces belong to the server, and the browser app is whatever is left. The app is a dashboard over an API that already exists, with live state arriving over server-sent events. It has to ship inside the `spov` binary, so that a local `spov serve` gets the dashboard as well. A Go-only checkout must still build, test and run without a JavaScript toolchain.

## Decision

### Stack

The web app is Astro with static output (`output: 'static'`), no adapter and no server-side rendering. Svelte 5 islands, through `@astrojs/svelte`, do all data fetching in the browser against `/api/v1` with the session cookie. Tailwind comes in through `@tailwindcss/vite`: `@astrojs/tailwind` has no release for Astro 5 or later, so the Vite plugin is the supported route. Bun is the runtime and the package manager, and `web/bun.lock` is committed. The source lives in `web/`.

Static output is chosen by supply: there is no official Bun adapter for Astro, and a community adapter would be one more dependency to track. Re-check only if an official one ships.

`typescript` is pinned to exactly 5.9.3, because TypeScript 7 breaks `astro check` and both OpenAPI generators. One version passes both tools: the peer ranges of `@astrojs/check` and `@astrojs/svelte` include 5.x, and `openapi-typescript` 7.13.0 peers `^5` and excludes 6. The pin is shared with the generated client (DL-005) and the two move together. The Bun pin (1.4.0, the newest stable release) and the places it must change are listed in `AGENTS.md`, as are the dev-proxy rules.

### Embedding

`internal/webui` holds `//go:embed all:dist`. A plain `go build` embeds only a tracked `dist/.gitkeep`, so the Go toolchain never depends on Bun, and serves a "this binary was built without the web UI" page held as a Go string constant. Everything else in `internal/webui/dist/` is gitignored, so build output cannot be committed over the placeholder and a local `bun run build` never dirties a tracked file. Whether a build is real is whether `index.html` exists in the embedded tree (`webui.Built`), and `spov serve` warns at startup when it does not.

`scripts/build-web.sh` builds `web/` and copies the output into `internal/webui/dist/`. CI and goreleaser's before hook run it first, and the container image builds the app in a Bun stage and copies the output over the placeholder. The release build needs Bun because the hook runs the script, and without it a release would ship the placeholder and nothing would say so. `scripts/install-bun.sh` verifies the release archive against a checksum committed beside the version rather than piping an installer into a shell, because that script runs on the path that produces release binaries.

### Routing

`Server.ownsPath` is the split between the server and the web app. The server keeps:

- `/api` and everything under it;
- huma's `/docs`, `/openapi…` and `/schemas…`, read from huma's own configuration, so renaming one cannot silently hand it to the web app;
- the health probes and the OpenCode pin document;
- the login and device surfaces, reserved whether or not the deployment serves them, so local and hosted mode route a path the same way and differ only in the answer.

Everything else is the web app's. An unregistered path under a reserved prefix stays the server's: a mistyped `/api/v1/…` answers as the API instead of returning HTML with a 200. A route added directly to the mux must be added to `ownsPath`, or it is unreachable behind the web app's 404. The failure direction is safe, since an unowned path never reaches the mux and so nothing protected can become public, but it is silent. `TestOwnsPath` asserts the literals.

The web branch is registered on the public mux, outside the authenticated mux, outside the session middleware and outside the browser guard. It must be outside the guard because a completed login arrives as a cross-site top-level GET, which the guard answers with 403. Leaving it unguarded is safe because the branch serves public static bytes, reads no cookie and changes no state. Being outside the session middleware means a logged-in browser does not put a session-store read on every static byte. The guard gives framing and sniffing protection only to the paths it covers, so the handler sets `X-Content-Type-Options: nosniff` and `Content-Security-Policy` itself. The policy is `frame-ancestors 'none'; img-src 'self' data:`, which also keeps a report's images to the server's own origin (DL-063).

The handler serves:

- exact files, and a directory path resolved to its `index.html` (Astro writes `/jobs` as `jobs/index.html`), never a directory listing, which `http.FileServer` would give and which would publish the asset manifest;
- no dotfile at all, which also declines the `/.env` and `/.git` probes any public address attracts (a path under `/.well-known/` would need a carve-out);
- `GET` and `HEAD` only, with a 405 and an `Allow` header otherwise;
- hashed files under `_astro/` with `Cache-Control: immutable`, and HTML with `no-cache`;
- Astro's `404.html` with status 404 for an unknown path, and a bare 404 when the build has no such page.

Embedded files have a zero modification time, so the handler sends no `Last-Modified` and no `ETag`, and `no-cache` HTML is downloaded in full on each navigation. The pages are a few kilobytes and this is left alone; if the app grows, an `ETag` computed when the handler is built is the fix.

A same-origin page needs no CSRF work for reads. A same-origin `fetch` or `EventSource` sends `Sec-Fetch-Site: same-origin`, no `Origin` header and the `HttpOnly; SameSite=Lax` cookie. Same-origin POSTs do send an `Origin` header, so the browser's writes rely on the browser guard alone and no token scheme is added.

### Pages

Each page is a static Astro file with one Svelte island loaded on the client:

| Address | Reads |
|---|---|
| `/` | `GET /api/v1/me`, then the session list over the state stream, and the 60 s `/me/usage` summary; the page renders a signed-out state (DL-060) |
| `/sessions/new` | the session launch form (DL-061) |
| `/session/?id=<ref>` | one session, its transcript and, for a job session, the job (DL-057, DL-058) |
| `/jobs/` and `/jobs/new` | the job list and the job form (DL-060, DL-061) |
| `/usage/` | `/me/usage`, polled every 60 s |
| `/tokens/` | the account's CLI tokens: list and revoke |
| `/settings/` | the account's credentials and defaults (DL-062) |

An address the build has no file for gets the 404 page. The admin users and quota pages are not part of the app; that management stays API-only. The browser-login listing (`/api/v1/me/sessions`) is also API-only and is registered only when the server has a login service.

Session detail is addressed by query string, `/session/?id=<ref>`. Astro builds statically and the handler answers an address it has no file for with the 404 page, so a path-shaped `/sessions/<id>` would need a build-time list of session ids, which cannot exist, or a fallback in the server. The query string keeps the question inside the web app.

The token endpoints are registered unconditionally, not only when the device flow is configured. The OpenAPI document and the generated client are produced from a server built without the device flow, so gating the endpoints would leave `/api/v1/me/tokens` out of both and the Tokens page could not call it. The handlers only read the token store, so without a device flow they answer an empty list and a 404 on revoke. `TestTokensAreServedWithoutTheDeviceFlow` and `TestTheDocumentCarriesTheTokenOperations` pin both halves.

`SessionView.estimated_cost` is computed by the server so that there is one cost implementation: it reuses `billableWithin` with the period opened at the session's own creation. It therefore covers the session's whole life, where `/me/usage` covers the calendar month, and a session started last month shows more than it contributed to that total. The field's doc comment says so. Every cost the app draws is a floor, because `estimated` is always true in the API, and the interface says "at least" and never presents a figure as an invoice.

### Data layer

State is Svelte 5 runes (`$state`, `$derived`). One helper, `resource.svelte.ts`, does fetch on mount, refetch when the tab becomes visible, and abort on unmount, with an optional poll interval that pauses while the document is hidden and an optional `when` gate that holds the first load until a page knows someone is signed in. Alongside it are the typed `openapi-fetch` client (DL-005) and the server-sent-event wrapper. There is no TanStack Query: a dashboard with a handful of endpoints whose liveness arrives over server-sent events needs no query cache.

The transcript is read once per connection and never on a timer, with a backoff on reconnect. That rule is in DL-058.

### One 401 funnel, two clients

An `openapi-fetch` middleware on the `api` client sends every 401 to `/login?next=<current path>`, so no page carries auth handling of its own. The server-sent-event path does not go through `openapi-fetch` and calls the same `redirectToLogin`. `redirectToLogin` does nothing where there is no document to navigate, and where the browser is already in the login flow, which would be a loop.

There are two clients. `api` has the funnel. `probe` is the same client without the middleware, for the landing page and the header identity, which must render a signed-out state and could not if every 401 redirected. It is a separate instance rather than a per-request header so the exemption cannot be left on a request by accident. `next` is always a path and never an origin, so the redirect is not an open redirect. `nav.go` is a seam over `location.assign`, because jsdom does not implement navigation and a test could not otherwise see the funnel fire.

### Errors and secrets

A non-2xx response becomes an `ApiError` carrying the RFC 9457 problem, and one component, `Problem.svelte`, renders it. The page shows the server's own words. What protects the page from a secret in an error body is on the server and in the data: the server scrubs a credential out of an error built from upstream text before it sends it (`scrub` and `redact`), the app renders the body as escaped text, and the browser never receives a stored secret, since credential listings carry names and facts and not values. The app does not sanitise server errors a second time. The field where a credential is typed is never logged, never persisted in the browser and never put in a URL.

### Theme

Dark mode is the three-state form, keyed on a `data-theme` attribute through a Tailwind `@custom-variant`, not the default media query. The page follows the OS until the viewer chooses; choosing Light or Dark in the header toggle pins it in `localStorage` (guarded, so a blocked store falls back to the OS theme). There is no control to return to following the OS short of clearing site data. An inline script in `Base.astro` sets the attribute before first paint and so duplicates the storage key and attribute from `theme.ts` by hand, since an imported module would be deferred; `theme.test.ts` asserts both literals so drift fails a test instead of flashing the wrong theme.

### Dev and CI

`astro dev` proxies every path `ownsPath` reserves to a separate `spov serve`, keyed on anchored regexes because Vite matches a bare string key by prefix and would proxy `/apiary` and `/devices` in dev while production serves them from the web app. The proxy sets `changeOrigin` and rewrites `Origin`, because the browser guard checks `Host`, `Sec-Fetch-Site` and `Origin`.

The `web` CI job runs `bun install --frozen-lockfile`, the drift gate on the generated client, `astro check`, Vitest (`bun run test`, never `bun test`, which skips the Vite pipeline), `scripts/build-web.sh`, a `go build` that proves the embed from a clean checkout and `go test ./internal/webui/` against that real build, since the Go `test` job only ever sees the placeholder. Component tests use a plain Vite config with `resolve.conditions: ['browser']`; with Astro's own `getViteConfig()`, or without the condition, Svelte resolves its server build and `mount` does not exist. There is no browser end-to-end test in CI.

## Rationale

- Serving from the Go binary keeps one container and one origin with no proxy configuration, and the app and the API it calls ship from the same commit.
- The placeholder keeps `go build ./...`, `go test ./...` and every Go-only workflow working without Bun installed.
- Every page calls the public `/api/v1` through the typed client, so the app exercises the API's shape as a real consumer and has no endpoints of its own. The one server-side addition made for it is a computed field, `estimated_cost`.
- Costs are computed once, in Go. A second implementation in TypeScript would drift silently, and drifting cost figures are worse than none.
- The lifetime warning on the session page is on the hard timeout, because the API has no last-activity time and an idle countdown would have to be invented.

## Measurements

- **Dev proxy against a live `spov serve`.** `/api/v1/me` through `astro dev` answers 401, so the guard passed and authentication ran, with `Host` and `Origin` both rewritten. An unrewritten `Origin` alone gives 403, and so does an unrewritten `Host` alone. `/apiary`, `/devices` and `/logins` are not proxied, so dev and production agree on the near-misses the anchored keys exist for.
- **Routing against the running binary.** Unauthenticated `GET /` returns the built dashboard with 200, also as a cross-site top-level navigation. `/api/v1/me`, `/docs` and `/openapi.yaml` answer 401, or 403 when sent cross-site, so the guard still runs ahead of authentication on the server's own surfaces. `/_astro/` and `/.gitkeep` are 404. Hashed assets are immutable, `/` is `no-cache`, and both carry `nosniff` and `frame-ancestors 'none'`. Re-run: `go test ./internal/webui/ ./internal/server/ -run 'TestOwnsPath|WebUI'`.
- **Image build, end to end.** The binary extracted from the finished container image contains the built page, not the placeholder.
- **Type tooling on 5.9.3.** `openapi-typescript` 7.13.0 run from `node_modules` against the project's TypeScript 5.9.3 produces output byte-identical to the same generator run standalone, and `astro check` reports 0 errors. Re-run: `scripts/gen-api-client.sh`, then `cd web && bunx astro check`.
- **Bun 1.4.0.** `web/bun.lock` (`lockfileVersion: 2`) installs with `--frozen-lockfile` unchanged.

## Consequences

- Release builds need a Bun step before `go build`, and CLI binaries carry the dashboard bytes, which are small. CI's build job installs Bun for its goreleaser snapshot, and whatever runner cuts a release must do the same.
- `internal/webui`'s handler (cache headers, the 404 fallback, placeholder detection) is ordinary logic, unit-tested against a fake `fs.FS`, and is not in `scripts/coverage-exclude.txt`.
- Changing the cost model changes what the pages say, since every figure is labelled as an estimate floor.
- Adding a server route outside `/api` means adding it to `ownsPath` and to the dev proxy.
- The funnel depends on every page calling `api`; a page that needs the signed-out state must use `probe` and gate its other loads on the answer, or its first 401 redirects.

## Known gaps

- The app has no way back to following the OS theme once a theme is pinned.
- HTML is revalidated by full download, because embedded files carry no `ETag`.
- There is no browser end-to-end test; the pages are covered by unit and component tests and by `astro check`.
- The session page cannot warn that a sandbox is about to stop for idleness: the API reports the configured idle timeout but not the last activity, so it warns on the hard timeout, and a truthful idle countdown needs a last-activity timestamp on `SessionView`.
