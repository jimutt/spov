## Context

Service accounts and their tokens are managed only through the API (DL-140, DL-141). An administrator has to read their own CLI token out of the OS keyring before the first `curl`, which is more than creating an identity for a pipeline should take. DL-129 put the allowlist on the Settings page for the same reason.

## Decision

The Settings page gains a **Service accounts** section, drawn for an administrator on a hosted server and for nobody else, after the People section. It is its own component, `ServiceAccounts.svelte`, with its logic in `web/src/lib/serviceaccounts.ts`. It uses only the seven routes of DL-140 and DL-141; no route is added or changed for the page. This amends DL-140's and DL-141's "API only".

- **Who sees it.** Settings mounts the component only when `/me` says `admin`, so a non-admin's page never reads the accounts. A local server answers 501 to the list and the section is not drawn, as `Allowlist.svelte` and `OrgSettings.svelte` do.
- **The list.** One row per account: its name, its commit author (name and address), how many usable tokens it has, and when it was last used or "never used". Accounts that are not deleted come first, by name. A deleted account (`disabled_at`) is listed after them with a "deleted" mark and the date, since its name stays taken; it offers no act except **Delete again**, which sends the same delete without a second press and so retries its off-boarding (DL-140). Every value is drawn as text.
- **Creating.** A name field and two optional author fields (name, address). A name that does not have the server's shape (3 to 32 lower-case letters, digits and hyphens, starting with a letter and not ending with a hyphen) is named under the field and never sent (`nameProblem`), so the field's text cannot make a path that reaches another route. A listed account's name is sent only when it has that shape (`accountPath`), and a token's ID only when it is a ULID (`tokenPath`), so not even a value the server returned can make `..` a path segment. Empty author fields are left out of the request, so the server's defaults apply. A refusal (a taken name, the limit of 100) is shown beside the field in the server's words, with the text left in the field.
- **Changing the author** is an inline edit on the row: two fields, Save and Cancel, a `PATCH` carrying only the fields that changed (`authorPatch`). A field emptied is sent, and the server's refusal is shown beside the fields, which stay open.
- **Tokens.** A row expands to its tokens, read from the account's token route only when it is opened and read again after every token act. The route lists every token that is not revoked, expired ones included. Each token shows its label, who issued it (the issuer's label, or "unknown" when the server gives none), when it was created, when it expires, that it has expired, or "never expires" (`expiryText`), and when it was last used. **Revoke** is behind `ConfirmAct.svelte`'s second press.
- **Issuing a token.** A label (required, at most 64 characters) and a lifetime: 365 days (the default), a number of days from 1 to 1095, or no expiry. A lifetime outside the range is named under the field and never sent. The request leaves `expires_in_days` out for the default and sends `no_expiry` for no expiry (`tokenRequest`).
- **The token is shown once.** The create answer's token is held in one component variable and nowhere else: never in `localStorage`, `sessionStorage`, the URL, a log or another component. It is drawn in a panel that says it cannot be shown again and names the two variables a pipeline sets (`SPOV_SERVER`, given as the page's own origin, and `SPOV_SERVER_TOKEN`), without writing the token a second time, with a **Copy** button (`navigator.clipboard.writeText`; where that is missing or refuses, the text stays selectable and the button says so) and a **Done** button. Focus moves to the panel when it appears and back to the token form's label field on Done. While the panel is open the token text is the only place it exists in the DOM.
- **A shown token is cleared only by Done, by leaving the page, or by its account turning out deleted.** The create answer's token is always kept, and its account's tokens are opened to show it, whatever was toggled while the request was in flight, so an issued token is never dropped unseen. While it is shown nothing else can hide it: every row's Tokens toggle, Change author, Delete, Delete again, Revoke and the submits of the create and token forms are disabled, and the panel says to press Done first; its own wording says it stays until Done or until the page is left. A `pagehide` handler on the window clears it, so a page restored from the back/forward cache does not bring it back. Every answer of the list, the resource's own re-reads included, clears the token, the open tokens and an author edit of an account it lists as deleted or does not list (`accountGone`), and the edit is never drawn on a deleted row.
- **Deleting** is behind `ConfirmAct.svelte`'s second press. The confirmation says what deletion does, as DL-140 does it: it cancels the account's jobs, stops its sessions, revokes its tokens and deletes its stored credentials, keeps its history, and the name cannot be used again. When the delete answers 500 the section shows the server's message and reads the list again. Only when that list shows the account deleted (`partialDeletion`) is it a half-finished deletion, with a line saying so and the row's **Delete again** as the retry; a 500 that left the account as it was is only the refusal.
- **One act runs at a time.** The act in flight is named (`acting`), each handler checks it, every act re-reads the list, and only the control whose act is running says "Working…". While one runs, the Tokens toggles, Delete and Revoke are disabled (`ConfirmAct.svelte` takes a `disabled` prop for it, and a `name` for its accessible name), so no confirmation can be opened. The token list's reads are numbered, and only the newest one's answer is drawn. The dates are taken again whenever an answer arrives. Each row's buttons carry the account in their accessible names ("Tokens for release-bot", "Change author of release-bot", "Delete release-bot", "Revoke token ci of release-bot") while their visible text stays short. **Enter** in the create form creates the account and in the token form issues the token; the page spends nothing, so the job form's implicit-submit guard does not apply. The section has no `$effect`, so DL-062's seeding loop cannot arise.
- **On a phone** the section is one column: the create fields, then the rows, each wrapping its name, author, marks and buttons, with the token list and the token panel full width under their row. Every control is drawn once.

The page does not store a forge token or a model key for an account: an account's credentials are stored by the account itself (DL-140). No CLI command is added. `deploy/README.md` keeps the `curl` examples for scripts and points to the page first.

## Rationale

- Everything the page needs is already in the API, so the API stays the one place the rules live and the page is markup and a small amount of logic.
- An administrator already manages who may use the server in Settings (DL-129); identities for pipelines belong beside it.
- Holding the token in one variable that is cleared on Done bounds where the one secret the browser ever shows can end up. Disabling what could hide it, rather than clearing it on those acts, means a token the server issued is never lost before the administrator has had the chance to store it.
- Listing deleted accounts explains why a name is refused, and gives the retry of a half-finished deletion a place to be pressed.

## Consequences

- The section's behaviour is tested in `serviceaccounts.test.ts`, with a mounted test only for the wiring (`serviceaccounts.svelte.test.ts`: the list as text, a create and its refusal, a token issued, shown once and gone after Done or `pagehide`, kept through toggles pressed while it was issued, surviving every disabled control, dropped when its account turns out deleted, a revoke, a delete and its retry after a 500, a 500 that is only a refusal, the token reads out of order, the accessible names and focus) and two in `settings.svelte.test.ts` (the section absent for a non-admin, who never reads the accounts, and drawn for an admin).
- The token is in the page's memory and on screen until Done is pressed or the page is left, and in the clipboard if copied. A browser extension or someone at the screen can read it there; the panel's wording must not suggest otherwise.
- The deletion confirmation's wording must stay true to what `Service.Offboard` ends for a service account (DL-140).
- jsdom draws no CSS, so the tests check markup; the layout at phone and desktop widths is checked only in a browser.
