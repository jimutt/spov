## Context

The session page's clock bar draws a live sandbox against its timeout: started at, stops at, and the share used (DL-057). It counted from the session's `created_at`. A resumed session keeps its row and gets a new run, a new sandbox whose timeout starts again (DL-085, DL-087), so a session resumed hours later showed the first sandbox's start, said its sandbox had stopped at a time already past, and drew a full bar while the new sandbox had most of its time left. The running time beside the state ("Running 0h 07m") and the list row's duration had the same fault.

## Decision

- `SessionView` carries `run_started_at`: the `StartedAt` of the session's newest run, set where the views are decorated from their runs (`withRuns`), on the single session, the listing and the resume answer alike. It is absent when no run is stored.
- The page counts a sandbox's time from it (`runStart` in `web/src/lib/format.ts`, falling back to `created_at`): the clock bar's start, end and share (`clockBar`), the timeout track (`lifetime`), and the running or stopped duration (`age`). A stopped resumed session's duration is its last run's.
- The session's own `created_at`, its order in the list and its estimated cost (whole-life, by runs) are unchanged.

## Rationale

A sandbox's timeout is the run's, so the time to show against it is the run's. Serving the start rather than every run keeps the view small, and the listing's stamp already moves when a new run is stored (its number is hashed), so a live list picks it up.

## Consequences

- `TestAResumedSessionsViewCarriesItsCurrentRunsStart` checks the single view and the listing; `format.test.ts` checks a resumed session's bar and duration.
