## Context

On a phone the session page's slim bar sometimes loses its contents while its raised background stays in place, and the words and buttons come back on the next scroll or when a message arrives. The reporter sees it on the latest Firefox for Android and has not seen it in Chrome. It appears only while the session is live and the real message composer is drawn; a stopped session with no composer has not shown it.

The bar is a sticky element below the page's own header, which scrolls away below `lg` (DL-106). It shares the page with the docked composer (DL-154). The state is not going missing: `Resource` keeps the last body while a request is in flight and on failure (`web/src/lib/resource.svelte.ts`), so `s` never falls back to undefined for a refresh, and a content change would redraw the words rather than remove the buttons and text together.

Two things happen only with a live composer, and both reach the bar. The dock's height is measured and written as `--dock-h` on the page's grid, an ancestor of the bar, so every change in the composer's height restyles the bar's whole subtree; the status line and the box change height with a turn. The bar's own elapsed-time text also changes every minute while the session runs, which a stopped session's does not. Scrolling or a new message restoring the words points at paint as well: Gecko has a history of sticky elements flickering or failing to paint while scrolling, with the moving Android toolbar as a known factor (Mozilla bugs 1585378 and 1813213), and WebKit reports sticky elements vanishing on an overscrolled document (WebKit bug 330140).

## Decision

Two changes, neither of which moves anything on screen:

- `--dock-h` is written on the "Jump to latest" control, the only element that reads it, instead of on the grid. A composer resize therefore no longer invalidates an ancestor of the bar.
- The bar carries Tailwind's `transform-gpu`, a zero-size `translateZ(0)`, so its background and its children are one compositor layer that the browser repaints together.

`sessiondetail.svelte.test.ts` asserts the class, which only stops it being dropped by accident.

The sticky offset, the negative margins that make the bar's natural position meet the header's bottom, the truncation, `lg:hidden`, and the docked composer are DL-106's and DL-154's as they were. The transform is on the bar itself and not on an ancestor, so it changes no containing block, and the bar has no fixed-position descendants.

## Rationale

The report names the one structural difference between the two cases: the composer. Its height is the only value that is written onto the bar's ancestor and changes while a session runs, so keeping that value on its one consumer removes the bar from the invalidation without changing the layout. The compositor promotion is a second, engine-neutral guard for a sticky paint failure: it costs one layer and changes no geometry on either Gecko or WebKit. Moving the bar out of its wrapper, making it fixed, replacing `dvh` with `svh`, or removing truncation would each change behaviour the layout decisions rely on, without evidence that layout is the fault.

## Consequences

- jsdom cannot reproduce compositing, so the guard test proves only that the class is still there. Check the real behaviour on the reporting device by running a turn through a resize of the composer, scrolling both ends of a long transcript, showing and hiding the browser toolbar, opening the keyboard and the details sheet, and receiving messages.
- If the bar still loses its words on Firefox for Android, the live duration update and `sticky` are the next suspects: the next change is a bar fixed below `lg` and hidden until the page header has left, which amends DL-106's layout and needs a browser check. `overscroll-behavior-y` is only a diagnostic, since it also changes pull-to-refresh and rubber-band scrolling.
