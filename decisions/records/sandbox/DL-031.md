## Context

Modal's sandbox network policy has two outbound allowlists, one of CIDRs and one of domains. The SDK treats an absent list as "open". It treats an empty list as "allowlist mode with nothing allowed", which blocks all egress. A sandbox created with no lists (open) cannot be narrowed later: `UpdateNetworkPolicy` refuses it. Modal's domain allowlist (a beta feature) matches the TLS server name (SNI) on port 443; traffic that is not TLS is governed by the CIDR list alone. A wildcard such as `*.example.com` matches subdomains only, not the bare domain.

spov needs a policy that is always explicit, that can be narrowed on a running sandbox, and that is easy to name. It also has to be honest about what egress does and does not protect, because a sandbox runs an agent that has shell access, reads untrusted repositories and acts with a git credential through the proxy sidecar.

## Decision

### A required policy type

`sandbox.EgressPolicy{Preset, CIDRs, Domains}` is a required part of `Spec`. `Spec.Validate` rejects a policy with an empty `Preset`, so forgetting to set one is a validation error and never an open sandbox. An explicit `open` preset makes the permissive choice visible at every call site, where the SDK's nil would hide it.

Both allowlists are always sent at create (`createParams`). "Open" is spelled with the allow-all entries `0.0.0.0/0` and `*`, which is what lets `Handle.SetEgress` (Modal's `UpdateNetworkPolicy`, with both lists) narrow a running sandbox later. `EgressOpen` is the only constructor that produces them, so no caller can express the blocking form by accident. `Fake` records `SetEgress` calls. Production code does not narrow a running sandbox today; the primitive is there for install-then-lock-down flows.

### Presets

| preset | CIDRs | domains |
|---|---|---|
| `open` | `0.0.0.0/0` | `*` |
| `install` | none | git hosts, registries, model APIs, agent services |
| `agent` | none | git hosts, model APIs, agent services |
| `custom` | as the base | the base preset's domains plus extras (`WithDomains`) |

`install` and `agent` therefore block all non-TLS traffic: plain-HTTP registries and `git://` fail by design. A domain that a project's toolchain needs and the preset lacks (a model provider host that is not listed, say) fails visibly inside the sandbox; `sandbox.egress_extra_domains` adds it and turns the policy into `custom`. Extra domains are a setting of the server, applied by `Service.egressFor` to whatever preset a session chooses; a request carries only the preset name, so a project file's list does not reach a hosted server. Extra domains on top of `open` are refused.

The domain lists, which are the meaning of the preset names (changing one changes what a preset allows):

- git hosts: `github.com`, `api.github.com`, `codeload.github.com`, `objects.githubusercontent.com`, `*.githubusercontent.com`
- registries and toolchain downloads (`install` only; `sandbox.RegistryDomains`):
  - Debian: `deb.debian.org`, `security.debian.org`
  - Go: `proxy.golang.org`, `sum.golang.org`, `storage.googleapis.com`, `dl.google.com`, `go.dev`
  - Node and Bun: `registry.npmjs.org`, `nodejs.org`, `bun.sh`, `*.bun.sh`
  - Python and uv: `pypi.org`, `files.pythonhosted.org`, `astral.sh` (python-build-standalone ships from GitHub, already a git host)
  - Rust: `crates.io`, `static.crates.io`, `index.crates.io`, `static.rust-lang.org`, `sh.rustup.rs`
  - Java: `repo1.maven.org`, `repo.maven.apache.org`, `maven-central.storage-download.googleapis.com`, `plugins.gradle.org`, `plugins-artifacts.gradle.org`, `services.gradle.org`, `downloads.gradle.org`, `api.adoptium.net`, `api.sdkman.io`, `download.java.net`
  - .NET: `api.nuget.org`, `nuget.org`, `*.nuget.org`, `builds.dotnet.microsoft.com`, `download.visualstudio.microsoft.com`, `dotnetcli.blob.core.windows.net`, `dot.net`
  - Ruby and PHP: `rubygems.org`, `index.rubygems.org`, `repo.packagist.org`, `packagist.org`
  - mise and its checks: `mise-versions.jdx.dev` (mise's version index, without which a Java install fails) and `tuf-repo-cdn.sigstore.dev` (Sigstore's trust root, which mise reads to verify the GitHub attestations of a precompiled Ruby)
  - Playwright browsers: `cdn.playwright.dev`, `playwright.download.prss.microsoft.com`
- model APIs: `api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`, `openrouter.ai`, `opencode.ai`, `*.opencode.ai`
- agent services (both presets): `mcp.exa.ai`

A first-use toolchain install (see DL-032) needs the `install` hosts; under `agent` it fails and the agent stays on the default version. The lists are exact by intent, so a lookalike domain does not match, and an apex that is itself contacted (`nuget.org`) is listed beside its wildcard.

### Forge hosts are added at launch

At launch `EgressPolicy.WithForgeHosts` adds the host of each platform the session selected (without its port; `forgeHosts` in the server) under `install` and `agent`, so a Forgejo, Gitea or GitLab session reaches its own forge without `egress_extra_domains`. GitHub keeps its fixed list as well as its host. An IP literal or a single-label host is not a domain and is not added, so such a forge is reachable only under `open`. The preset keeps its name, since it means this session's forges; the server's `egress_extra_domains` still make it `custom`. `open` is unchanged. A launch and a recreated credential sidecar resolve the policy the same way (`Service.egressFor` with the session's selections), and the sidecar gets the same list. The presets narrow the main container; the sidecar keeps the policy it was created with, see DL-034.

### Validation

`Validate` refuses a domain that is a URL, carries a path or port, has an inner wildcard, is a bare label, is an IP address (which belongs in the CIDR list) or has a malformed label, because each of those silently matches nothing at the provider and reads as an egress rule that is not working. Domains are lowercased and deduplicated, so two spellings of one host are one entry.

The policy that was asked for must be the policy the sandbox gets. Validation catches a missing preset, not a wrong one, so tests assert the preset at each hop (request, `session.Options`, `Spec`, provider parameters), and each assertion was checked to fail when its hop is severed.

### Web search

OpenCode's built-in web search has two hosted backends, Exa (`mcp.exa.ai`) and Parallel (`search.parallel.ai`), and unless pinned it chooses one per session by a checksum of the session ID. spov pins it to Exa with `websearch: {provider: "exa"}` in the config of every sandbox (`opencode.WebSearchProvider`), so search is deterministic and needs one host, `mcp.exa.ai`, which is the only search host on the presets. `webfetch` is always on and fetches arbitrary URLs; under `install` and `agent` it fails for any host not on the list, which is the intended injection control and is not worked around.

### Defaults and the job default

The default is `open` for interactive sessions and for jobs (`sandbox.egress` in config, `SPOV_SANDBOX_EGRESS` on a server, `egress` in a request). A job's request carries its egress through unchanged, an empty value resolves to the server's `sandbox.egress` (`open` unless the operator changed it), and `agent` and `open` are both selectable. `TestAJobsEgressIsTheCallersChoice` asserts this on the created session's request and not on the preset table, because a preset can be defined and correct and reached by nothing.

Jobs keep open egress by default, deliberately. A job's toolchain is not predictable: `pr` jobs run repository checks that fetch modules, `report` jobs fetch pages, and a fixed allowlist is a guess about every repository. A registry that cannot be reached looks exactly like a task that failed, so a narrow default would make failures that nobody can diagnose. The caller chooses the repository, the goal and the credentials, so the caller chooses this risk too.

**What open egress allows.** The agent can reach anything the sandbox can reach, so it can send anything it can read to any host: the cloned repositories, the workspace, files an injected instruction tells it to find. The forge tokens and model-provider keys are held by the proxy sidecar and not by the agent's container (DL-034), so open egress does not let the agent copy them out, but it does let the agent use them through the proxy for what the credential's scope allows.

**What still bounds a job.** The sandbox boundary (a separate Modal sandbox with no published port, see DL-030), the wall clock and the concurrency and duration quotas (DL-049, DL-009), and the scope of the credentials the session holds (DL-043). These do not depend on egress.

**How to narrow it.** Set `sandbox.egress: install` or `agent` in the user or project config, or send `egress` in the request (`spov jobs create`, the API). `install` keeps toolchain installs working. `agent` allows only the forges, model APIs and search, which suits a job whose dependencies are already in the image. On a hosted server the operator sets the default for requests that name none with `SPOV_SANDBOX_EGRESS`; the CLI always sends its own configured value.

**Egress is never the containment.** The permission hook, the verdict gates and the goal's orientation are guardrails on an honest run, not boundaries, and none of them may be described as safe because egress holds. Even `agent` allows the git forge, so an agent that holds a push token can push a workspace to any repository its credential reaches on an allowed host; narrowing the credential is what bounds that, and egress only narrows what a contained agent can reach when someone asks for it.

## Rationale

- Presets are what users and jobs reason about; raw lists are for the rare custom case.
- Reserving the allow-all lists at create costs nothing, and a sandbox created without them can never be narrowed.
- Domain allowlisting is the strongest lever against a hijacked agent, which is why `install` and `agent` exist. It is a choice and not the default, because a default that breaks builds is a support problem and not a security gain.
- A session that cannot reach its own forge is a broken launch, and an operator should not have to repeat in egress what the platform configuration already says.

## Measurements

- `UpdateNetworkPolicy` on a sandbox created with nil allowlists is refused with: "sandbox was created with open network access; restricting it while running is not currently supported; create the sandbox with an allow-all allowlist (CIDR 0.0.0.0/0, domain *) to start open and restrict it later". A sandbox created with the allow-all entries can be narrowed. An integration test asserts that real outbound HTTPS works from inside a created sandbox. Re-run: `go test -tags integration ./internal/sandbox/ -run Integration -v`.
- An empty allowlist blocks everything, so `EgressOpen` is the only constructor that says "no restriction".

## Consequences

- Extending a preset's domain list is a reviewed change, and `install` and `agent` fail plain-HTTP registries, `git://` and ssh by design.
- Parallel web search and any other search backend are not reachable on the presets. Enabling Parallel means adding `search.parallel.ai` and dropping the pin.
- The open default means a job's blast radius is set by its credentials and the sandbox, not its network. Revisit the default before jobs are launched by a trigger or by people other than the operator of the deployment.

## Known gaps

- Blocked connections cannot be logged on v2 sandboxes, which expose no stdio. An injection tripwire would need a different sandbox kind or an in-sandbox log shipper.
- Hosts that a forge redirects downloads to (GitLab's LFS object storage) are not added by `WithForgeHosts`; under `install` or `agent` a GitLab LFS download may fail until they are added with `egress_extra_domains`.
- A job holds the same kind of git credential as a session, whatever its kind. Giving a `report` job no push token would be a bound that does not depend on egress, and it is not built; it matters more while egress is open.
