## Context

A sandbox has to start in seconds, with OpenCode already installed at the pinned version, without depending on npm or GitHub at launch. An agent asked to build or test a typical repository also needs a toolchain; if it has to install one it spends its first turns on that, and cannot do it at all under a closed egress preset. A survey of hosted agent runners, universal dev images and sandbox platforms found the same baseline: build tools, Python, a Node LTS and, usually, Go. Very large images are being replaced by a curated base plus opt-in extras.

OpenCode has no official container image, needs a glibc userland, and needs `ripgrep` on `PATH`: without `rg` the server downloads it from GitHub at runtime, which stalls a cold start and fails outright under restricted egress. A Dockerfile `ENV` in the image is not inherited by the sandbox entrypoint, so variables reach the entrypoint only through the sandbox's create-time `Env`.

## Decision

### The base image and its name

- The image is built from `debian:trixie-slim` and published once under a name, through Modal's image publish and `Images.FromName`. A launch resolves it by name. Version strings and package names are validated before they are interpolated into a build command.
- System packages (`basePackages`): `bash`, `build-essential`, `ca-certificates`, `curl`, `fd-find` (linked as `fd`), `git`, `jq`, `make`, `openssh-client`, `pkg-config`, `ripgrep`, `sqlite3`, `tar`, `unzip`, `xz-utils`, `zip`, with `/workspace` created.
- The image name is `spov-base-<opencode-version>-<hash>`. The hash covers the base image and every rendered build command (`ImageSpec.extraSuffix`, 32 hex characters), so a change to the recipe, a CLI bump, a toolchain bump, extra apt packages or an add-on is a new image and a corrected recipe cannot reuse a stale one. The image supports `amd64` and `arm64`; any other architecture fails the build.
- Each Dockerfile command is one line, because Modal's parser reads an embedded newline as the start of a new instruction (`TestImageSpecDockerfileCommands`).
- The build is a chain of layers from least to most often changed (`ImageSpec.Layers`), so Modal reuses the cached layers below a change: an OpenCode bump rebuilds only its own layer, and an add-on variant (DL-033) builds only its own layers on a cached base.
  1. system packages and `/workspace`
  2. mise and its settings
  3. the default languages, ending with their version checks
  4. add-ons, one layer each, in sorted order
  5. extra apt packages the base lacks
  6. the forge CLIs and their check
  7. OpenCode and its version check
  `BuildImage`, which `EnsureImage` calls on a miss, passes one `DockerfileCommands` call per layer to Modal. `TestTheBuildIsLayeredLeastChangedFirst` guards the order.
- The build ends with version checks, so a broken toolchain fails the build and not the first sandbox. It fails if `python`, `uv`, `node`, `corepack`, `bun`, `go` or `mise` is missing or reports a version other than the pin, if a forge CLI does not run, or if OpenCode does not report the pinned version.

### OpenCode: the pinned npm package, checked, run in place

- The image fetches OpenCode's platform package straight from npm (`https://registry.npmjs.org/<scope>/cli-<target>/-/cli-<target>-<version>.tgz`), with the target chosen from `dpkg --print-architecture`, and unpacks the package's binary to `/root/.opencode/bin/opencode`. The package layout of an install script is not a stable interface, so spov installs the pinned package itself and verifies it.
- `openCodeReleases` records per version the npm scope, the binary's name inside the package and npm's `dist.integrity` (sha512) for each target. A version with no entry is taken to be published like the current pin's line (`unrecordedRelease`). The pin is always recorded, and `TestEveryRecordedReleaseCoversEveryTarget` fails when an entry misses a target.
- The tarball is checked against its sha512 integrity before it is unpacked, in the build's own shell (`sh` and coreutils only). An unrecorded version reads `dist.integrity` from the registry's metadata in the same step, says so in the build log, and is still checked. That value comes from the same registry as the tarball, so it guards against corruption, not against the registry itself.
- On x64 the image uses the `-baseline` build, which runs on any x86-64 host. A choice made by probing the CPU at build time would reflect Modal's build machine and not the machine that runs the sandbox.
- The build's version check runs the installed binary and compares the last field of its `--version` output, without a leading `v`, with the pin.
- The rendered install is tested in a real shell against stubbed `curl` and `dpkg`: a matching package installs for each architecture, a mismatch is refused before unpacking, an unrecorded version takes the registry's value, and a binary of another version fails the check (`image_install_test.go`). The integration spikes download the same x64 package through the same table and check its integrity when one is recorded. The local client is installed by the person with OpenCode's official installer; spov does not download one.
- The entrypoint execs `/root/.opencode/bin/opencode serve` where the image installs it and copies nothing (`TestEntrypointRunsTheBinaryInPlace`). `PATH` already starts with `/root/.opencode/bin`. One path for the binary means the image check, the entrypoint and the spikes run the same file.
- The exact pinned version is baked in and no moving tag is resolved at sandbox start. That removes npm and GitHub from the launch path, makes a cold start deterministic, and makes a bump explicit.

### Building is an operator command

`spov serve image build` builds and publishes the base image and exits. It belongs under `serve` because it needs the deployment's Modal credentials, as `serve migrate` needs its database.

- It builds the version from the resolved config, so it publishes exactly the name a launch will ask for (`TestImageBuildMatchesWhatALaunchWouldAskFor`). `--opencode-version` builds a different one, which is how a new pin is prepared before anything is switched to it. The order is: build the new version, change the config, restart. The reverse order fails every launch with `resolve image "spov-base-<version>-<hash>": NotFoundError: Image not found`, and the command's help describes `--opencode-version` as the way to prepare a new pin before switching. `--addons`, `--apt` and `--rebuild` build an add-on variant ahead of its first launch or republish a pruned image (DL-016).
- The spec is validated before the provider is touched, since a build takes minutes. Publishing is idempotent (`EnsureImage` returns at once when the image exists), so it is safe before every deploy. A name the image registry marks as pruned is built again without the lookup, and every image the command publishes is recorded in the registry (DL-016).
- A launch never builds the base image. `sandbox.ImageBuilder` is a separate interface that `Provider` does not embed, and the command type-asserts for it, so a deployment that only launches needs neither the capability nor the credentials for it. A launch that built its own image would make one user's first session of a new pin a multi-minute wait on a path whose cost nobody sees. Only an add-on variant is built on demand, see DL-016. A provider that cannot build is refused with an explanation.
- `internal/cli/image.go` is under the coverage gate and tested against a fake; the Modal calls it drives stay in `image_build.go`, which is excluded from the gate and covered by integration tests.
- Recording a new OpenCode build in `openCodeReleases` is the first step of a pin bump (DL-035): record the integrity per target with `npm view <scope>/cli-linux-x64-baseline@<version> dist.integrity` and the arm64 equivalent.

### The default toolchain

The versions are exact and live in Go: `toolchain.Defaults`, `CorepackVersion` and `MiseVersion` in `internal/toolchain/toolchain.go`, and the forge CLI versions in `internal/sandbox/image.go`. They are a bump away from changing, so this record does not restate them.

- Languages, installed through mise as global defaults: Python with uv (the newest release with a year of bug fixes behind it), Node on the Active LTS line with corepack installed from npm and enabled (Node 25 and later do not bundle it), Bun, and Go.
- Go keeps its own default of `GOTOOLCHAIN=auto`, which spov does not set: a repository whose `go.mod` names a newer toolchain gets it downloaded, and an older one runs on the installed Go, since the `toolchain` line is a minimum. `GOPATH/bin` (`/root/go/bin`) is on `PATH`.
- Every default version is exact and every download is checked against a checksum: mise verifies its own downloads, and spov verifies mise against a sha256 per architecture. A bump is a code change and gives a new image name.
- Rust, .NET, Playwright, Java, Ruby, PHP, PostgreSQL and Redis are add-ons, not defaults (DL-033). The image carries one version of each language. Preinstalling several versions per language would multiply the image size.
- Moving Node to a new LTS line or Python to a new release is recurring maintenance, like the OpenCode pin.
- The credential-proxy sidecar's image is separate (DL-034).

### mise is the version layer

mise is installed at its pinned version, checked against its sha256, and installs the default languages at build.

- A sandbox resolves languages through mise's shims, which come first on `PATH` (`opencode.sandboxPath`, built from `toolchain.PathDirs`), because OpenCode's shell is non-interactive and never runs `mise activate`.
- A repository's own version files win inside it: `.tool-versions`, `mise.toml`, `.nvmrc`, `.node-version`, `.python-version`, and, when the matching add-on is present, `rust-toolchain.toml`, `global.json`, `.java-version` and `.ruby-version`; `go.mod` through Go itself, which moves only to a newer toolchain. Recent mise leaves idiomatic version files off, so the image's global settings enable them for node, python, rust, dotnet, ruby and java (`idiomatic_version_file_enable_tools`) and make a bare Java version mean Temurin (`java.shorthand_vendor`). A repository that pins Node 22 gets Node 22 without spov preinstalling it.
- A missing pinned version is installed on first use into mise's data directory in the sandbox, which is gone when the sandbox ends (nothing persists beyond the sandbox, see DL-029). A version that every session needs can be pinned into the variant image with an add-on instead.
- mise trusts `/workspace` (`trusted_config_paths`): a `mise.toml` there can set environment variables and tasks, and the agent can already run arbitrary code in its own sandbox. The agent can run `mise use <tool>@<version>` itself, and the workspace `AGENTS.md` says so.
- Globally installed tools land in fixed `PATH` directories so no `mise reshim` is needed: `/root/go/bin`, uv's `/root/.local/bin`, an npm prefix of `/root/.local/share/npm-global` (set in `/root/.npmrc`), `/root/.cargo/bin` and `/root/.dotnet/tools`.
- mise verifies downloads with its defaults: Node against `SHASUMS256`, Go by checksum, tools from GitHub releases by GitHub attestations, SLSA or cosign.
- A first-use install needs egress. Under the `agent` preset it fails and the agent stays on the default version. Under `install` it works; the hosts it needs (including `mise-versions.jdx.dev` and `tuf-repo-cdn.sigstore.dev`) are `sandbox.RegistryDomains`, listed in DL-031.
- Through the credential-proxy sidecar (`credproxy.MainEnv`) installs work too: mise is built with native roots, and `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` point at the bundle that carries the sidecar's CA.
- corepack: pnpm and yarn follow a repository's `packageManager`; with none, corepack downloads its own default pnpm on first use.

### The forge CLIs

The image carries `tea` (Forgejo and Gitea), `gh` (GitHub) and `glab` (GitLab), because opening a pull request is most of the point of giving an agent a repository. `opencode.CLIForKind` maps a platform kind to its CLI (`gitlab` to `glab`, `gitea` to `tea`), and the workspace `AGENTS.md` tells the agent which CLI belongs to which repository and to open a merge request with `glab mr create`.

- Each CLI is pinned to a version and checked against a sha256 per architecture (`cliSHA256`, beside the versions, as mise's are). The value is the one in the release's own checksums file. `tea` is a plain binary, `gh` a tarball and `glab` a tarball from GitLab's package registry. A bump changes the version and the checksums together and gives a new image name, because a downloaded binary that runs with the agent's access should be the reviewed one.
- Authentication is written by the entrypoint, never baked into a layer, because credentials are per session. What the CLIs hold are placeholders; the real tokens are in the proxy sidecar (DL-034), except on a deployment that runs without the sidecar, where the CLIs hold the real token. Files holding them are mode 0600 and no token appears on the entrypoint script's command line.
  - `tea` has a login entry per Forgejo or Gitea platform, named after the configured platform, in `~/.config/tea/config.yml`.
  - `gh` reads `~/.config/gh/hosts.yml`, assembled from per-host fragments, and never `GH_TOKEN` (DL-021).
  - `glab` reads `~/.config/glab-cli/config.yml`, written whole by `writeGlabConfig` for every GitLab host at once to a temporary name and moved into place: per host the token, `api_protocol: https`, `git_protocol: https` and, for an instance under a base path, `subfolder`; the first host is the default; `check_update`, `telemetry` and `show_whats_new` are off and `no_prompt` is on; values are single-quoted.
- glab reads `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN`, `OAUTH_TOKEN`, `GITLAB_HOST` and `API_PROTOCOL` ahead of its file, so none may be set in the main container; the file is the one source, as with gh. glab also writes a full default config wherever it first runs, so the image's version check runs it with `GLAB_CONFIG_DIR` on a throwaway directory and the image keeps no glab config; an appended file under glab's default would leave gitlab.com unauthenticated. `~/.config/glab-cli` is on the plugin's read deny list. A GitLab token is not renewed, so the refresh script has no glab case.
- Clone URLs carry no secret. The entrypoint writes `/root/.git-credentials` (0600) with git's `store` credential helper. A token in the clone URL would be printed by `git remote -v` to anything running in the sandbox, and `tea` could not match a repository to its login, since it parses the remote and does not expect credentials there.
- The entrypoint generates `/workspace/AGENTS.md` from the same selection that drove the clones, so it cannot drift from what is present and the agent does not have to guess which CLI belongs to which repository (a guess that is wrong half the time with several platforms); its content is described in DL-037. OpenCode discovers `AGENTS.md` by walking up from its working directory, so a file at the workspace root is visible from every cloned repository. It stays short and factual, because it competes for attention with the repositories' own `AGENTS.md` files.
- A stored Forgejo token is the user's own, and the CLI inherits exactly its scope: a token limited to some repositories cannot open a pull request against another, and the failure shows inside the sandbox. A launch checks a stored token against each repository first (DL-043).

## Rationale

- A pre-published image with the exact pin removes npm and GitHub from the launch path, makes a cold start deterministic, and makes a bump a rebuild and republish.
- A pinned, verified download cannot be broken by an upstream script change. Hashing the whole recipe into the name means a changed recipe is a new image. Checking integrity in the build's shell keeps the Go side free of network calls, and the image name stays a pure function of the spec.
- Keeping the build off the launch path makes the operator who changed the pin pay for it once, knowingly. As a command it reads the same config as the server, where a script would re-derive the name and could publish one that nothing looks up.
- `trixie` is Debian stable; the forge CLIs and OpenCode are static binaries. A layer chain makes a bump cheap.
- One mechanism, mise, serves both the defaults and a repository's runtime overrides, and Go needs no manager because `GOTOOLCHAIN=auto` fetches what `go.mod` names.

## Measurements

- Base image build and publish: 26 s for the first build, 23.7 s for a later build, and under 1 s to reuse a published image by name. Re-run: `go test -tags integration ./internal/sandbox/ -run TestIntegrationEnsureImage -v`.
- OpenCode install on Modal: the install step built in about 40 s, and a sandbox was healthy about 3 s after create, reporting the pin. Re-run: `go test -tags integration ./internal/sandbox/ -run 'EnsureImage|EndToEnd' -v`.
- OpenCode run in place from the lazily loaded image layer, six fresh sandboxes in two runs of three, with the GA build: every server answered `/api/info` with the pinned version within 2 to 5 s of create, created and listed a session and logged no error, and the binary's md5 matched in every sandbox. The beta build, a Bun standalone executable that reads its embedded chunks through `/proc/self/exe`, died from the lazy layer with `SyntaxError: Invalid character: '\0'`, and the entrypoint had to copy it (164 MB) on every start. Whole-launch checks pass with the binary in place: `go test -tags integration ./internal/sandbox/ -run TestIntegrationEnsureImage -v ; go test -tags integration ./internal/session/ -run CredentialProxy`.
- Readiness, create to the server's port answering, with the real entrypoint, five fresh sandboxes per image, four runs: medians of 1.85, 1.52, 2.38 and 1.59 s (range 1.43 to 2.91 s) for the trixie image against 1.74 and 1.90 s (range 1.42 to 2.20 s) for a bookworm image. The difference is within run-to-run noise and inside the one-second budget; Modal loads images lazily and boot reads little of the toolchain. Re-run: `SPOV_READINESS_BASELINE=<old image> go test -tags integration ./internal/sandbox/ -run ToolchainImage -v`.
- Size, measured in a prototype before any runtime install: the languages take 652 MB in mise's data directory and `/usr` takes 580 MB; OpenCode takes 196 MB. A build from scratch took 1 min 32 s, and changing only mise's settings rebuilt in 37 s because the layers below were reused. Re-run: `go test -tags integration ./internal/sandbox/ -run ToolchainImage -v`.
- After the move to running in place, the image, end-to-end, lifecycle, connect-token, sidecar, bubblewrap and plugin-loop spikes passed at the GA pin (the plugin loop sends two continuations; no spike calls a model), as did a whole launch through the credential proxy (`go test -tags integration ./internal/session/ -run CredentialProxy`).
- Formatters and language servers: OpenCode 2.0.22 runs no formatter and starts no language server even with the toolchains present. A second OpenCode inside a sandbox, driven by a fake model through its `write` tool, left unformatted Go, TypeScript and Python files as written although `gofmt` was on `PATH`; no language-server process started and nothing was downloaded into OpenCode's cache. The OpenCode config has `formatter` and `lsp` switches; re-decide if a later build changes the default.
- First-use installs under the `install` preset: Node 2.8 to 4.4 s, Python 2.0 to 4.1 s, a Go toolchain about 2 to 6 s, Rust about 13 to 15 s, a .NET SDK about 8 to 10 s, Java 3.5 to 5.8 s, Ruby 7.9 s, and a Playwright 1.62.0 headless shell download 19 s. Node, Python, Go, Rust, .NET, Java (Temurin and OpenJDK) and Ruby installs, `uv pip`, pnpm through corepack, npm, cargo, NuGet, Composer, `gem` and `go get` all work. One NuGet restore once took 1.5 minutes and did not reproduce (3 s on a re-run). Re-run: `go test -tags integration ./internal/sandbox/ -run ToolchainImage -v`.
- Installs through the credential-proxy sidecar in a real launch: Node and Python installs from version files, a Go toolchain download and `uv pip install` work, and a Python request to a host the sidecar decrypts succeeds. Re-run: `go test -tags integration ./internal/session/ -run 'AnAddonVariant|CredentialProxy'`.
- Forge CLI install in the base image under local Docker, with a wrong checksum refused by the build: 31 s. Re-run: `SPOV_CLI_INSTALL=1 go test -tags integration ./internal/sandbox/ -run ForgeCLIsInstall`. The CLI install and pre-authentication were also checked against a real Modal sandbox and a Forgejo forge: the CLIs report their pinned versions, `tea login list` shows the account, its config is 0600, `/workspace/AGENTS.md` renders, and `tea pr list` inside a clone lists the repository's pull requests without `--repo`. The gh config is re-checked with `go test -tags integration ./internal/sandbox/ -run 'GhReadsItsConfigFile|RefreshThroughExecInput'`. The Docker test also checks that glab reads the token, default host and switches back as written.
- The forge CLIs add roughly 30 MB to the image for tea and gh.

## Consequences

- spov owns image maintenance. Bumping OpenCode, mise, a language, a forge CLI or an add-on recipe is a rebuild and republish under a new name.
- An OpenCode bump re-runs the spikes listed under the bump order in `AGENTS.md`, which cover run-in-place. No dedicated guard detects a regression in how Modal loads image layers. If a future OpenCode or Modal release makes a binary fail from the lazy layer, every sandbox's server dies at start, the image and end-to-end spikes fail, the server log shows the `SyntaxError`, and sandboxes never become healthy. The fix is to restore a copy of the binary in the entrypoint. The build's own `--version` check runs in the build container and does not exercise the lazy layer; the integration test that boots a sandbox does.
- After a toolchain, mise, add-on or image bump, run `go test -tags integration ./internal/sandbox/ -run ToolchainImage -v` (with `SPOV_READINESS_BASELINE` naming the replaced image) and `go test -tags integration ./internal/session/ -run 'AnAddonVariant|CredentialProxy'`.
- The unrecorded-version fallback guards against a corrupt download only; recording the pin's integrity is what pins the content.
