## Context

The server runs a handful of programs inside a sandbox's main container and reads what they print: `printenv` for the OpenCode password, the sync export and inspect scripts, the seed, a token refresh, a CA install. The agent is root in that container and can replace any of them. `runProcess` read both output streams with `io.ReadAll`, so a replaced `printenv` that never stops printing was read into the server's memory until the process was killed, and again at each restart, since the password is read whenever a connection is not cached.

## Decision

Every exec reads at most a bound of each output stream, and output over the bound is an error (`sandbox.ErrOutputTooLarge`), never a truncated answer.

- `Exec`, `ExecInput` and `SidecarExecInput` read `sandbox.MaxExecOutput`, 64 KiB.
- `Handle.ExecBounded(ctx, command, stdin, maxOutput)` is `ExecInput` with the caller's bound. Two callers size their own: the password read takes 4 KiB, and the sync export takes the export limit in base64 plus 1 MiB for the JSON around it and the deleted paths (`git.MaxSyncExportBytes/3*4 + 1 MiB`).
- The read stops one byte past the bound (`readBounded`), so the server never holds more than the bound plus a read buffer.
- `sandbox.Fake` and the tests' local shell apply the same bound to a canned result (`sandbox.BoundOutput`), so a test sees what a real sandbox would answer.

The export's own 32 MiB check stays where it is, after the decode. Raising what a sync-back can carry is a separate change that streams the export through the server; a larger bound here would only raise what one export holds in memory.

## Rationale

- An error is the honest answer: a truncated password or a truncated export would fail later and less clearly.
- A bound on the interface, with a default, means a new exec is bounded without its author thinking about it.

## Consequences

- A legitimate command that prints more than 64 KiB on either stream now fails. None of spov's does: the seed, the refresh and the CA install print a line or two, and the inspect prints counts.
- Measured on Modal with SDK v0.10.0 (`TestIntegrationExecOutputBound`, re-run on an SDK bump): a program that writes 512 MiB to either stream ends in under two seconds and the exec answers `ErrOutputTooLarge` with the caller's heap unchanged. The SDK reads a stream only from the first `Read`, through a 64 KiB pipe, so it holds nothing spov did not ask for. `runProcess` closes both streams when it returns, which ends the SDK's reader that a bounded read leaves blocked.
- The bound is on size, not on time: a program that never exits holds its exec until the caller's context ends, as it did before. Every exec needs a deadline of its caller's.
