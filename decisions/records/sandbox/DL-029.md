## Context

spov runs every session in a Modal sandbox. The official Go SDK (`github.com/modal-labs/modal-client/go`) covers sandboxes completely but is pre-1.0 and ships breaking minor releases: moving from v0.8 to v0.10 changed many signatures. The gRPC API under the SDK is explicitly not public. A different backend is plausible later.

A sandbox bills for its whole wall-clock life, on the larger of its requested and actual resources, so a sandbox that nobody ends is the main cost risk of the product. spov sandboxes also sit idle while a person types or a job waits for a model.

## Decision

### One interface, one package

- All Modal access goes through `sandbox.Provider` (`Create`, `Get`, `List`) and a `Handle` for per-sandbox operations (`Info`, `Tunnels`, `Exec`, `Terminate`, `Detach`, connect tokens, egress changes, tags, sidecars and so on; image building sits on separate interfaces). The interface is larger than a handful of methods and spans several files; its role is what matters: it is the only seam between spov and Modal, it stays free of SDK types (`TestNoSDKTypesInPublicAPI`), and `sandbox.Fake` implements it for tests, recording the specs it is given and failing on demand.
- The SDK is imported only in `internal/sandbox` (a depguard rule) and is pinned to an exact version in `go.mod`. An upgrade is: read the SDK changelog, bump, fix that package.
- spov never speaks raw gRPC to Modal and never shells out to the `modal` CLI.
- The Modal implementation uses the Sandbox v2 backend: `Sandboxes.ExperimentalCreate`, `ExperimentalList` and `ExperimentalFromName`. v2 sandboxes are invisible to the v1 `List`. v2 has no GPUs and no NFS, and spov needs neither. When Modal promotes v2 to the default, the `Experimental*` calls are dropped inside the package.
- The Modal app is `Apps.FromName` with `CreateIfMissing`, named by `modal.app` (default `spov`, which must be set), in the environment from config. A Modal credential in the provider's own config wins over the ambient profile.
- `Get` resolves a reference that is either a sandbox ID (`sb-` prefix) or a session name. `Sandboxes.FromID` is a pure constructor that never contacts Modal, so `Get` polls the sandbox once; an unknown reference then surfaces as `ErrNotFound` there instead of as a confusing failure at a later call. Modal reports a malformed sandbox ID as gRPC `InvalidArgument` rather than `NotFound`; both map to `ErrNotFound`, because to a user both mean the reference does not resolve (`ModalProvider.resolveErr`; the by-name case is under Known gaps). `spov attach` and `spov stop` branch on that sentinel.
- `Create` validates the spec first, then waits for the readiness probe for up to three minutes (`readyTimeout`). A sandbox that exists but never becomes ready, or whose sidecar cannot start, is terminated before `Create` returns, with a bound of 60 s on the teardown and the entrypoint's exit code in the error, since a v2 sandbox exposes no stdio. If the teardown itself fails, the error says the sandbox is still running and billing, names it and wraps `ErrStillRunning`.
- `modal.go` and `image_build.go` are thin SDK adapters and are excluded from the coverage gate (`scripts/coverage-exclude.txt`). Their behaviour is covered by integration tests behind the `integration` build tag, which CI compiles but does not run, because they create billable sandboxes.

### Sandbox configuration

`config.Sandbox` carries the sandbox's shape. Each key in the table maps one-to-one to a field of `sandbox.Spec`, follows config layering (user file, project file, `SPOV_SANDBOX_*`), and is validated before any billable call. The section holds other keys too (`image`, `addons`, `apt`, the git access and job duration preferences, `sync`) that belong to other records.

| key | type | default | rule |
|---|---|---|---|
| `cpu` | float | 0.5 | positive |
| `memory_mib` | int | 2048 | positive |
| `cpu_limit` | float | none | zero means no limit; otherwise at least `cpu` |
| `memory_limit_mib` | int | none | zero means no limit; otherwise at least `memory_mib` |
| `regions` | list of strings | none | passed through; empty lets Modal choose |
| `cloud` | string | empty | `aws`, `gcp`, `oci`, `auto` or empty (`sandbox.ValidCloud`) |
| `workdir` | string | empty | an absolute path (`sandbox.ValidWorkdir`); empty keeps the entrypoint's own directory |
| `egress` | string | `open` | a preset name, see DL-031 |
| `egress_extra_domains` | list of strings | none | appended to the preset's domains |
| `inbound_cidrs` | list of strings | none | valid CIDR prefixes |
| `timeout` | duration | 4h | positive, at most 12h |
| `idle_timeout` | duration | 30m | at least 1 minute (`sandbox.MinIdleTimeout`), at most `timeout` |

- `gpu` is recognised and refused with "gpu is not available: spov uses Modal's v2 sandbox backend, which has no GPU support". A silent ignore would look like a feature that does not work.
- The rules live in package `sandbox` (`ValidCloud`, `ValidWorkdir`, `MinIdleTimeout`, `MaxTimeout`, `EgressPolicy.Validate`, and the limit and timeout comparisons in `Spec.Validate`). `config.Validate` checks the file when it is loaded, so a bad file fails before anything is created, and `Spec.Validate` checks again at the provider boundary, so a caller that builds a `Spec` directly cannot bypass it. Cloud, workdir, the idle floor and egress are one function called from both places; the numeric comparisons (limits at least their requests, the 12 h cap, the idle timeout at most the timeout) are written in both, and `config.MaxSandboxTimeout` is a second constant with `sandbox.MaxTimeout`'s value. `validate_test.go` and `spec_test.go` cover each.
- A request that arrives over the API is validated synchronously in `Service.Create` (`validateRequest`), against the same `Spec.Validate` through a probe spec built from the request. A bad value answers 422. It is never accepted with 202 and left to fail minutes later on the event stream, when a session row and a launch goroutine already exist.
- The `workdir` key is the directory the entrypoint starts in. Where a session's agent works is decided by the session's landing directory, see DL-037.
- Not exposed on purpose: volumes, cloud bucket mounts, PTY and Modal's own proxy option.

### Lifetime and cost

- `timeout` has a hard cap of 12 hours (`sandbox.MaxTimeout`; `config.MaxSandboxTimeout` is the same value). It is enforced twice: `config.Validate` when the value is read, and `Spec.Validate` before any create reaches Modal. The default is 4 hours. The cap covers a working day and bounds a leaked sandbox to half a day of billing. Modal's own maximum lifetime is 24 hours. A hosted server's per-user `max_timeout` (8 hours by default) sits below the cap and is clamped to it (`Quotas.withDefaults`), see DL-009. The reconciler terminates a sandbox older than the organisation's maximum session age plus a grace hour, whatever the store says, see DL-004.
- `idle_timeout` is Modal's idle timeout, 30 minutes by default. It ends a sandbox nobody is using; it cannot end one that something keeps touching. What resets the clock is measured below: plain requests do, a held-open stream does not. A connected client therefore keeps a sandbox alive until it leaves, which is why DL-030 has the client's proxy send periodic plain requests and why the floor is one minute. Web-only use has no exit signal and relies on the idle timeout after the tab closes, and on the cap.
- The default size is 0.5 CPU and 2 GiB of memory, set per project or per request. OpenCode mostly waits on a model API, so a small request keeps an idle sandbox cheap. A hard limit (`cpu_limit`, `memory_limit_mib`) lets an organisation have a runaway agent killed by the kernel instead of billed at burst.
- Every sandbox is tagged at creation by `BuildTags`: `spov=1`, `created_at` (RFC 3339), and when known `name`, `user`, `org`, `repos`, `job`, `proxy`. Tags are the only filterable discovery mechanism, so they are how `List` finds spov's sandboxes after the process that created them is gone. A crashed client therefore never leaks an unbounded sandbox: it is bounded by the timeouts from the moment it exists and findable by its tags. `created_at` gives `Info.Age`. `user` and `org` carry the owner's IDs in hosted mode and `local` in local mode.
- Cost is shown, not just bounded. A session reports an estimated cost from its requested size and age (`sandbox.HourlyCost`, `sandbox.EstimatedCost`); because Modal bills the larger of requested and actual resources, the estimate is a floor. `spov fly` prints the hourly estimate at launch, and session and job listings show age so forgotten sessions are visible. The documentation says plainly that an open terminal or browser tab keeps the sandbox billing.
- Ending a sandbox is checked, not assumed. `Handle.Terminate` waits for the sandbox to stop, so the caller knows billing has ended. A teardown that follows a Ctrl-C or a failed launch runs on a context detached from the cancelled one and bounded to a minute (`terminateTimeout` in the CLI, `Launcher.cleanupSandbox` in the launcher), and a failure is reported as "still billing" with the command that stops it, never swallowed. `spov stop --all` continues past a sandbox that will not stop. When the TUI exits, `spov fly` terminates its sandbox unless `--keep` is given; that command's behaviour is in DL-025.
- A job's duration is governed by the job's own wall clock, not by this policy, see DL-049.

### State is ephemeral

A sandbox keeps no state beyond its own life. Anything the agent produced leaves through a git push (or, for a job, through the job's deliverables); when the sandbox ends, OpenCode's data, the toolchain's caches and the working tree end with it. This is the simplest arrangement and leaves no provider keys on shared storage. The consequence is that a session cannot be resumed in a new sandbox. The conversation stays readable from the server's stored log, see DL-017.

## Rationale

- Wrapping the SDK keeps an upgrade to one package, makes everything above the seam testable with no network, and leaves room for another backend.
- Validating each knob from one function before the call is the cheapest place to catch a mistake: every parameter here is fixed at creation and cannot change on a running sandbox, so a wrong value means recreating it.
- Refusing `gpu` loudly is the honest answer to a constraint spov chose with the v2 backend.
- Twelve hours is the cheapest bound on the dominant product risk, a sandbox that keeps billing after its owner has gone.

## Measurements

- Sandbox v2 cold start, from create to a healthy `/api/health` through the tunnel, including the git clone: 3.2 to 4.4 s, on par with v1 (about 3 to 4.5 s in the comparison run). Re-run: `go test -tags integration ./internal/sandbox/ -run Integration -v`.
- Idle clock through a tunnel (a sandbox with an exposed port, which spov does not use): with `IdleTimeout` of 5 minutes, one HTTP request every 30 s kept the sandbox alive until it was killed at 7 m 16 s; one SSE connection to `/api/event` also did (killed at 7 m 26 s), because OpenCode sends an SSE heartbeat about every 16 s; with no traffic the timeout fired at 5 m 46 s.
- Idle clock through the connect endpoint, which is the path spov uses (spike S-A: idle timeout of 2 minutes, observed for 4.5 minutes, four sandboxes in parallel): a no-traffic control dies; a plain request every 30 s keeps the sandbox alive; a held-open stream (`log?follow=true`, or an SSE stream) does not, and dies with the control; a `follow=false` poll every 30 s keeps it alive. Only plain requests reset the clock. Re-run: `go test -tags integration ./internal/sandbox/ -run 'IdleTimeoutCountsConnectTraffic|LogReadingAndIdleTimeout' -v`.
- `Get` on a malformed ID, a well-formed but stale ID and an unknown session name all return `ErrNotFound`. Re-run: `go test -tags integration ./internal/sandbox/ -run GetUnknownSandbox -v`.
- A sandbox whose entrypoint exits at once fails `Create` with "never became ready" and the exit code, and is terminated. Re-run: `go test -tags integration ./internal/sandbox/ -run CreateFailureTerminates -v`.

## Consequences

- Code above `internal/sandbox` sees no SDK type. A new Modal capability enters as a `Provider` or `Handle` method with a `Fake` implementation, and the interface should stay as small as the callers allow.
- Anything that polls a sandbox with plain requests keeps it billing up to the cap; see DL-018 for how reads are kept off the sandbox.
- Because tags are the discovery mechanism, a sandbox created without `BuildTags` is invisible to listing and to the reconciler.
- Exposing `regions` and `cloud` lets a session be placed somewhere more expensive; the cost estimate does not model region.
- `config.Validate` has cross-field rules (a limit at least its request, an idle timeout at most the timeout), each covered in `validate_test.go`.
- The integration tests create billable sandboxes. Each terminates what it creates in `t.Cleanup`.

## Known gaps

- `resolveErr` is meant to return an `InvalidArgument` on the by-name path (a bad environment, say) as a real error and not as a missing sandbox. `isNotFound` also counts `InvalidArgument`, so that path maps it to `ErrNotFound` too, and a bad environment reads as "no such sandbox".
- `store.SandboxConfig` and the API's sandbox view carry a `persist` field that nothing sets or reads.
