## Context

OpenCode listens inside the sandbox on an HTTP port and is guarded by HTTP Basic auth. If that port were published through a Modal tunnel (`EncryptedPorts`), its URL would be public: every request, authenticated or not, would reach the OpenCode process, which has shell access to the workspace and acts with the session's forge access, and the only barrier would be one password valid for the sandbox's whole life.

Modal's sandbox connect tokens move authentication to Modal's edge. OpenCode's terminal UI and web UI speak only Basic auth, so neither can present a connect token itself, and a small proxy has to sit between them and the sandbox.

Edge behaviour that this design rests on (measured, see Measurements): a sandbox with no published port has no tunnel at all, and a connect token still yields a working URL for its port. The edge answers a request with no token `401 "No auth token provided"` without OpenCode seeing it. It accepts the token as `Authorization: Bearer`, as a `_modal_connect_token` query parameter, or as a `_modal_connect_token` cookie. OpenCode reads `Authorization: Basic`, so a Bearer token is consumed by the edge and OpenCode sees no credential; with the token in the cookie the edge leaves `Authorization` alone and both layers work. A token is an RS256 JWT bound to one sandbox and one port that expires 24 hours after issue, and the SDK offers no way to revoke it.

## Decision

### No published ports

A sandbox sets no `EncryptedPorts` (`Spec.Ports` is empty). The only way to OpenCode is a connect-token URL, and Modal's edge rejects every request that lacks a token for that sandbox and port. The sandbox also keeps its generated OpenCode password (32 random bytes, base64url, never empty because OpenCode disables its auth entirely when the password is empty, and never on a command line) as a second layer: a request that reaches the edge with a token still needs the password to reach anything.

### Only the server mints tokens

`POST /api/v1/sessions/{ref}/connect` (`Service.Connect`) is the one place a client obtains credentials, so only the server process holds the Modal credential, locally and hosted alike.

- It is allowed to the session's owner or an admin, and only while the session is running.
- It mints a token for the session's port with `Handle.ConnectToken`. The token's user metadata is `{"user_id", "session_id"}`, which reaches the sandbox as Modal's verified `X-Verified-User-Data` header and must stay under Modal's 512-byte limit (`sandbox.MaxConnectMetadata`); the provider adapter and `Fake` both enforce it.
- It writes a `Mint` audit row: who, which session, when, and `expires_at`. The expiry is the token's `exp` claim, decoded without verifying the signature because only the number is needed (`tokenExpiry`), and clamped to at most `AssumedTokenTTL` (24 hours). A token with no readable expiry is recorded as now plus 24 hours with a warning. The audit row is what makes an unrevocable token acceptable: the reach of a leaked token is known (one sandbox, one port, until `expires_at`) and attributable.
- It is rate limited to `MintsPerMinute` (10) per rolling minute per organisation and session, then answers 429. The count and the reservation happen in one store transaction, and the row is written before the token is minted, because a check-then-act limit overshoots under concurrent callers and for unrevocable tokens that is the difference between a bound and a suggestion. A mint that then fails leaves a reservation that expires with the window, so the limit errs toward refusing.
- It answers `{url, token, user, password, expires_at, idle_timeout_secs}` with `Cache-Control: no-store`. Credentials appear in no log, audit row or store (`store.Mint` stores no token).
- The OpenCode password is generated at launch and held in the launching replica's memory keyed by session. Any other replica recovers it with one exec in the sandbox and keeps it in a bounded per-replica LRU (`passwordCache`, 1,000 entries); a failed recovery is a 502, never a made-up value. The password is never written to the database. `Service.ForgetSession` drops the password and the cached connection on every path that stops a session: delete, failed launch, and the reconciler finding the sandbox gone, and shutdown clears both caches (an idle timeout stops a sandbox without any request to spov, so the reconciler's `Forget` hook is the common case).
- A client never persists what `connect` returns: no connect token or password under the config directory or in the keyring. A new attach mints anew.
- A token that has been returned is valid until it expires or the sandbox is terminated; deleting the session is the revocation. If per-request revocation is ever needed, the answer is a server-side proxy in front of the sandbox, not a change to the client proxy.
- `sandbox.inbound_cidrs`, when set, is applied at create as Modal's inbound allowlist. It suits a fixed office or VPN egress and not roaming clients.

### The client's loopback proxy

`spov attach` (the TUI, or `--web` for OpenCode's web UI in a browser) runs a reverse proxy (`internal/proxy`, `httputil.ReverseProxy`) on `127.0.0.1:<ephemeral port>` for as long as it runs. `session.StartClientProxy` mints once eagerly, so a client with no way in fails at attach and the heartbeat interval is known before the proxy serves, and passes the proxy a mint callback that calls the server. For every request the proxy:

- rewrites the target and `Host` to the connect URL and adds the `_modal_connect_token` cookie;
- removes the client's own `Authorization` header and sets `Authorization: Basic opencode:<password>`, so the proxy's credential always wins: forwarding a client's header would make the proxy a password-checking oracle, and a Bearer header is consumed by the edge, whose 401 would read as an expired token (`TestProxyReplacesAClientsOwnAuthorization`);
- streams responses unbuffered (`FlushInterval: -1`; `ReverseProxy` already flushes event streams and unknown-length bodies, so this covers a streamed response that declares a `Content-Length`);
- uses an upstream transport with HTTP/2 disabled, because an `Upgrade` request cannot be carried over h2. OpenCode's PTY WebSockets authenticate with a short-lived ticket in the URL, so `ReverseProxy`'s own `Upgrade` handling is enough and OpenCode is unmodified;
- re-mints when the edge answers 401, which covers the 24-hour expiry. The edge's 401 carries no `WWW-Authenticate` header and OpenCode's 401 for a wrong password carries `Basic`, so only the first causes a mint. Re-minting is throttled to once per 30 s (`remintInterval`), or 2 s after a failed mint (`remintBackoff`), so a transient control-plane failure is retried and a server answering 401 for its own reasons cannot drive a mint loop. The mint costs an authenticated API call and has a 5 s timeout (`mintTimeout`), separate from the request's, so a health check polling every 250 ms is not stalled behind a hung control plane;
- drops a `Location` response header that names another host, since the upstream is an agent and could otherwise send the browser anywhere (`confineRedirect`; a relative location stays), and answers a failed upstream request with a bare 502 so the edge host is not shown to the client.

The launcher has a proxy of its own while a launch waits for OpenCode's health: it mints straight from the provider, with no metadata, no audit row and no heartbeat, and the server closes it once the launch is healthy (`StartProxy`, `Session.CloseProxy`). The client's proxy is the one a person uses. Server-side mints are distinguishable in tests by their metadata.

The proxy holds every credential; clients hold none. The TUI is started with `--server http://127.0.0.1:<port>` and no `OPENCODE_PASSWORD`, the web UI is reached at the same URL with no password prompt, and neither the token nor the password appears in a URL, terminal output or browser history.

**It refuses any request a web page could have caused.** A loopback port can be found by scanning a few hundred ports, and the target is an agent with shell access to the workspace and live git credentials, so a page open in another tab must not be able to use it. Three checks in `Proxy.guard`:

- `Host` must name the proxy: its own address, or `localhost`, `127.0.0.1` or `::1` with its port. This defeats DNS rebinding, where a rebound name resolves to the port but the browser still sends the attacker's hostname.
- `Sec-Fetch-Site`, when present, must be `same-origin` or `none`. This is the check that matters, because `Origin` alone is not enough: browsers omit `Origin` on cross-site subresource GETs, so an `<img>`, `<script>`, `<iframe>` or top-level navigation aimed at the port would otherwise be forwarded with both credentials attached. Go's HTTP client sends no `Sec-Fetch-*` header, so an absent header is allowed; that is spov's own TUI and health checker. A future non-browser client that does send `Sec-Fetch-Site` would be refused.
- `Origin`, when present, must name the proxy.

A `Set-Cookie` from the sandbox has its `Domain` attribute removed. A cookie scoped to `localhost` is shared with every other service on a loopback port, so a prompt-injected agent could otherwise write cookies into unrelated local tools. Host-only cookies are all the session's page needs.

**Minting is capped** at `maxMints` (64) per proxy. The 401s that drive re-minting come from the sandbox, the untrusted side, and without a cap a compromised agent could cause unrevocable 24-hour tokens to be minted for as long as the session runs. The server's per-session limit is the counterpart for every client together.

**Lifetime.** The proxy lives and dies with the `spov` process that started it: it stops when the TUI exits. With `--web`, `spov` stays in the foreground as the proxy until interrupted. `spov fly --no-attach` and `spov attach --no-tui` print how to reach the sandbox and exit with no proxy left. The web UI is reachable only while it runs and only from that machine; sharing a session with another device is not offered, since the only mechanism would be a token in a URL. Hints printed for a session that is left running name the command that starts a new proxy (`spov attach <name> --web`, or "re-run with --web") and print no URL, since a loopback address is worthless once the printing process ends. Only a `--web` session prints its URL, while it is live.

### The heartbeat

Through the connect endpoint a request every 30 s keeps a sandbox from idling out, and a held-open stream does not. The OpenCode TUI between keystrokes is exactly an idle event stream, so a user who reads for the whole idle window would lose the sandbox. The proxy therefore sends a heartbeat for as long as it runs.

- `GET /api/info` (`proxy.HeartbeatPath`, OpenCode's identity endpoint) goes through the normal upstream path, with the token cookie and Basic auth injected, so it uses the same credentials as real traffic and re-mints on 401.
- The interval is `idle_timeout / 4` clamped to 10 to 30 s (`proxy.HeartbeatFor`), derived from `idle_timeout_secs` in the connect response. `Options.Heartbeat` of zero disables it. The idle timeout must be at least 40 s for this to make sense; the 1 minute floor in config validation ensures it (see DL-029). The request timeout is half the interval.
- A response of 500 or worse, or a transport error, is a failure; a 4xx is not, because a 401 is handled by the re-mint and any other 4xx still proves the sandbox answers. A failure is logged and does not stop the proxy; three in a row surface one warning that the sandbox is not answering. A 404 or 405 reached the sandbox but says the route may have moved, which is warned once (`TestAMovedHeartbeatRouteIsSaidOnce`). A beat in flight when the proxy closes fails because the listener is gone, so the loop checks for shutdown before counting, or quitting the TUI would claim the sandbox died.
- The heartbeat stops when the proxy closes, and nothing else keeps the sandbox alive. Liveness is tied to the proxy rather than to the TUI, so the web UI has the same guarantee and a browser tab left open does not defeat the idle timeout by itself. A session nobody is attached to idles out after its last plain request.

### The server's own connections

The server reaches a sandbox for its own purposes: the conversation recorder, a job's open, pause, report and evidence reads, and steering. If each used `Service.Connect`, each would issue a 24-hour unrevocable token and spend the session's mint budget.

- The server keeps a bounded in-memory LRU of live connections per replica, keyed by session (`connCache`, 256 entries). An evicted or missing entry costs one mint, exactly what every call cost without a cache, so a miss is always correct and a path that needs a fresh credential simply skips the cache. The cache is memory only: persisting it would store a live, unrevocable credential at rest, needing sealing and a migration for something any replica can re-issue.
- Entries are not served within `ConnectionExpiryMargin` (5 minutes) of their expiry, and are dropped on a refusal. `withConnection` runs one act over a cached or fresh connection; if the sandbox answers `ErrSandboxUnauthorized` (a 401 or a 403, since the edge may refuse a token with either) it drops the connection and the password, mints again and runs the act once more. Any other failure is returned as it is, because a sandbox that answered 500 may have done the work. The closure is re-run whole, so everything wrapped in `withConnection` must be safe to repeat; the job actions are, since a conversation is looked up before it is created.
- A refusal drops the cached connection only if it is the one the refused request carried (`forgetIf`), so two callers refused on the same stale token do not discard each other's fresh mint out of the ten-a-minute budget. The session's password is dropped unconditionally, since a 401 does not say which credential was refused and recovering it costs one exec (`TestARefusalDropsOnlyTheTokenItWasRefusedOn`, `TestARefusalDropsBothCredentials`). A second refusal is not retried, and the credential that earned it is not left cached.
- A cache hit is still authorised: `connectReusing` resolves the session through `Service.Get` and refuses one that is not running. The cache saves only the mint. `SetJobLoopPaused` takes the caller's principal (the session's owner for the supervisor's own pause), so its mint is audited against whoever asked.
- `/connect` neither reads nor fills the cache and mints on every request, because `connectMetadata` records which user a token was issued to and two holders of one cached token would make that wrong. `TestTheConnectEndpointIsOutsideTheCache` checks both directions.
- The recorder has a `drop` seam, called from `span` (the one place that holds the token a refusal applied to); only a refusal triggers a drop, not an ordinary break, or every redial would spend a mint.
- One credential per session means the recorder (as `auth.Recorder(orgID)`) and a job's actions (as the owner) share it, so the `Mint` row's metadata names whoever minted first. Nothing reads it. A mint does not correspond to one act, so an act that needs attribution records it where it happens (steering writes its own audit marker, see DL-019).

### The mint budget, shared with steering

Steering sends reach the sandbox through the same cache, so the durable `MintsPerMinute` count does not bound them. A steering act (a message, a model switch, cancelling a queued message, answering an ask) is therefore refused (`mintBudgetLeft`) while it could take the session's remaining budget below `RecordingMintReserve` (3), read from the shared `Mint` rows. Interrupt makes the check only when no connection is cached, since otherwise it spends no mint. Three is the recorder's worst case, since its backoff allows at most three redials in a minute. One send can cost `MintsPerSteer` (2) mints: one on a cache miss and one more if the sandbox refuses the credential. An act is refused once more than five mints (`MintsPerMinute` less the reserve less `MintsPerSteer`) have been spent in the minute. The check is a floor read before the send, not a reservation, so a concurrent mint can overshoot it by at most one. It runs after the session-is-running check and before anything reaches the sandbox. A failed read of the count is an error, neither a refusal nor a pass: failing open would spend the reserve and refusing would blame the caller for spov's outage. `MessagesPerMinute` (6) is an in-memory, per-replica limit that serves as abuse control only. Raising `MintsPerMinute` was rejected, because more minted tokens means more live credentials that cannot be revoked.

## Rationale

- Unauthenticated traffic never reaches OpenCode. A leaked URL is worthless by itself, and a leaked token is bound to one sandbox, one port and 24 hours, where a password would be bound to nothing but the sandbox.
- Keeping the sandbox password costs nothing once the proxy injects it, and makes the edge a second layer instead of the only one.
- Only one process holds the Modal credential, which is the point of a hosted server; a local server gets the same shape.
- Keeping the proxy on the client keeps the heartbeat and the browser guard where the attached client is, and keeps the server off the data path.
- Moving the password from the TUI's environment into the proxy is not an improvement against a hostile local process. The loopback port is reachable by the same processes, such a process now needs only a TCP connect instead of reading the TUI's environment, and it can reach a connect token, which exists on the machine only because of this design. The gain is against remote traffic, not local traffic.
- Reusing the server's connections removes a credential issue from every server-side sandbox call and reduces the number of live unrevocable tokens a deployment has issued. This is a security improvement as well as a cost one.

## Measurements

- Connect-token edge semantics (spike on the pinned OpenCode build): a sandbox with no published port has no tunnel and `CreateConnectToken` still yields a working URL; a tokenless request gets 401 `No auth token provided`; the token is accepted as Bearer, as a query parameter or as a cookie, and only the cookie lets OpenCode's Basic auth through; the token is an RS256 JWT from `oidc.modal.com` with `aud: sandbox-connect`, `sub` the sandbox ID, `prt` the port and `exp` 24 hours after issue; the SDK has no revoke call; an SSE stream (`/api/event`) and a PTY WebSocket upgrade (`/api/pty/:id/connect`, 101) both pass the edge and a stdlib `ReverseProxy` on loopback. Re-run: `go test -tags integration ./internal/sandbox/ -run TestIntegrationConnectToken -v`.
- Idle clock through the connect endpoint (idle timeout of 2 minutes, reproduced twice): a request every 30 s keeps the sandbox alive; a held-open SSE stream does not (the SSE-only sandbox died at 2 m 16 s, the same time as one with no traffic). Re-run: `go test -tags integration ./internal/sandbox/ -run IdleTimeoutCountsConnectTraffic -v`. If Modal starts counting open streams this test fails and the heartbeat should be reconsidered. The same rule is measured for log reads in DL-018.
- A connect token's observed expiry is 24 hours, which `AssumedTokenTTL` mirrors.

## Consequences

- A `spov` process must be running for a person to reach a sandbox's OpenCode directly; `spov attach` is that process for a session started elsewhere.
- Putting a browser on a loopback origin is surface a public tunnel did not have: remote web content can address `127.0.0.1` but could never address a Modal hostname as loopback. The `Host`/`Sec-Fetch-Site`/`Origin` guard and the cookie `Domain` strip exist because of that, and are the parts to re-check when browser behaviour changes. `internal/proxy/proxy_test.go` covers each check. The guard rests on `Sec-Fetch-Site`, which every browser that can reach a loopback port sends and no page can forge.
- Tokens cannot be revoked. Terminating the sandbox is the revocation, and the audit row and the mint limits bound the exposure until then.
- The `withConnection` retry makes any new wrapped act a requirement to be safe to repeat; the helper states this.
- Anything that polls a sandbox keeps it billing; read paths answer from the store instead, see DL-018.

## Known gaps

- Whether Modal enforces `sandbox.inbound_cidrs` on the connect endpoint is not covered by any test in the repository. Treat the option as unverified until a test confirms it.
- The Modal connect-token behaviour above (cookie versus header handling, expiry) is Modal's and can change; `TestIntegrationConnectToken` is the standing check.
- `catchUp`'s per-conversation message read logs a warning instead of returning its error, so a credential refusal there never reaches the recorder's drop. It does no harm today because the session listing just before it fails first on a refused credential.
- The window between a sandbox disappearing and a replica hearing of it leaves a cached connection pointing at nothing; using it fails as a transport error and grants no access.
