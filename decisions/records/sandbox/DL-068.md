## Context

The CLI accepts and validates `sandbox.egress_extra_domains` from the user and project files, and `docs/configuration.md` lists it beside `egress`. But `spov fly` and `spov jobs create` send only the preset's name, and the server adds only its own `EgressExtraDomains` (`egressFor`; DL-031). A user cannot add a domain their toolchain needs from their own config, and the key does nothing on the client.

## Decision

The launch request carries the user's `sandbox.egress_extra_domains` (`egress_extra_domains` on the session and job requests), and the server adds them to the preset beside its own `EgressExtraDomains` and the session's forge hosts (`egressFor`). They are validated as the server's are (a hostname or a leading wildcard, never a scheme or path), refused on `open` egress, where they would do nothing, and bounded to `MaxEgressExtraDomains` (16) per request. A project file may set them like any other sandbox key.

## Consequences

A project that needs one more registry works under `install` or `agent` without the operator. The operator still bounds what a sandbox can reach in total, through the presets and the credential proxy, which adds a credential only on its own hosts. `TestACallersExtraEgressDomainsReachTheSandbox` and `TestFlyRequestCarriesTheConfig` cover both sides.
