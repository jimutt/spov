## Context

For a stored token the proxy adds no credential to a request on a pull request's `merge` path (`credproxy.Platform.allowsAPI`, DL-135). For a GitHub App's token (`Scoped`) it adds the credential on every path (DL-034), and the token a sandbox gets holds `contents: write` and `pull_requests: write`, so `PUT /repos/<owner>/<name>/pulls/<n>/merge` succeeds. Which credential a job runs on then decides whether its agent can merge its own pull request over REST.

## Decision

`Platform.allows` applies the merge rule before it returns for a `Scoped` platform: a request to a GitHub API path `repos/<owner>/<name>/pulls/<n>/<merge>` (the segment as `isMergeSegment` reads it) with any method but GET or HEAD is forwarded with no credential, for an App token as for a stored one. Every other path keeps DL-034's rule for an App token.

## Rationale

- One answer for both kinds of credential: a sandbox does not merge over the REST endpoint.

## Consequences

- This is a guardrail and not a boundary. `POST /graphql` is allowed for both kinds and its body is not read, so the `mergePullRequest` mutation still merges, and either token can push to a branch that is not protected. A project that must hold a merge sets branch protection or a ruleset on the forge. `docs/github-access.md` says so.
- An agent that tries the REST merge sees gh's `401 Requires authentication`, which the generated guide already tells it to report (DL-108).
- `TestAGitHubAppTokenIsNotUsedToMerge` joins `policy_test.go`.
