## Context

DL-130 bounds what an exec makes the server hold: `ExecBounded` reads each output stream into memory up to the caller's bound, and more is `ErrOutputTooLarge`. That is the right shape for an answer the server must read whole, but it makes the server hold everything it passes on. Sync-back (DL-027) is the one caller whose output is not for the server at all: it is an archive the server hands to the CLI. Holding it is why the export was capped at 32 MiB, and DL-130 already named streaming as the way past that cap.

## Decision

`sandbox.Handle` gains `ExecStream(ctx, command, w io.Writer, maxStdout int64) (ExecResult, error)`.

- It reads stdout while the process runs and writes each chunk to `w` as it arrives, through a copy buffer of at most 64 KiB, so the server never holds more than one chunk of it. It reads stdout to its end before `Wait`, where `runProcess` waits first. `ExecResult.Stdout` is empty; the exit code and stderr are as `ExecBounded` reports them, stderr bounded by `MaxExecOutput` and read after stdout ends.
- The bound counts every byte written to `w`. One byte past `maxStdout`, it stops reading, closes both streams and answers `ErrOutputTooLarge`. What was already written stays written; the caller decides what a partial write means.
- A failed write to `w` (the HTTP client went away) ends the read the same way and answers the write's error, wrapped.
- **Stopping the read does not stop the process.** SDK v0.10.0's `ContainerProcess` has no kill. `ExecStream` passes the caller's remaining deadline as `SandboxExecParams.Timeout`, so Modal ends the process at the deadline, and a caller whose program must not outlive an abandoned read arranges that itself (DL-176's script does).
- Like every exec it needs a deadline its caller set (DL-135); `sandbox.Fake` refuses one without (`ErrExecNoDeadline`) and writes its canned stdout to `w` under the same bound and the same error, so a test sees what Modal would answer. `TestEverySandboxExecThisPackageMakesIsBounded` covers the new method, and every `Handle` behind the `integration` tag implements it.
- Stdin is not streamed: `ExecStream` takes none.

**Measured on Modal** by `TestIntegrationExecStream` (SDK v0.10.0, 2026-11-21; re-run on an SDK bump):

1. 1 GiB from `/dev/urandom` reaches the writer whole in 63 to 127 seconds (8 to 16 MiB/s Modal to the server), with the caller's heap up by 0.3 to 0.4 MiB.
2. A writer that fails after 1 MiB ends the read at once. The program goes on writing until the deadline the exec was given (40 seconds there), and Modal ends it then: its later steps never ran and no process of it was left.
3. Idle time: a stream that writes a line every 5 seconds for 3 minutes kept a sandbox with a 1-minute `IdleTimeout` alive, but a 1 GiB stream in the same setting lost its sandbox after 91 seconds ("Sandbox has already shut down"), and the same stream with a 10-minute idle timeout finished. A running exec is therefore not reliable activity. **A streaming export runs `true` every 30 seconds while it streams** (`session.keepAwake`), as S-R1 measured short execs reset the idle clock (DL-021); with it, the 1 GiB stream finished in 99 seconds under the 1-minute idle timeout.

## Rationale

The Modal SDK (v0.10.0) already reads an exec's stdout lazily from the first `Read`, through a 64 KiB pipe, and keeps the output on Modal's side until it is read (DL-130's measurement), so streaming adds no buffer the SDK does not already have.

A separate method, not a mode of `ExecBounded`, keeps DL-130's rule intact for every other caller: an exec that returns bytes holds them, bounded; an exec that writes them elsewhere holds none.

## Consequences

- DL-130's "the server never holds more than the bound plus a read buffer" holds for `ExecStream` with the bound replaced by one copy buffer.
- A program that writes to stdout slowly holds its exec, and the HTTP request feeding it, until the caller's deadline; the deadline is what bounds a stream's time, as for every exec.
