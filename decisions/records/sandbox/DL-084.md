## Context

Resuming a stopped session with its dirty tree, installed packages and caches needs a copy of its filesystem from after the work happened. A sandbox mostly ends without spov watching: its idle timeout or its hard timeout ends it, or it crashes. Snapshotting on a schedule would miss the last stretch of work, and spov cannot snapshot on the way down when nobody is watching.

DL-029's "State is ephemeral" rules this out today: a sandbox keeps no state beyond its own life, and a session cannot be resumed in a new sandbox.

Modal has an experimental create option, `enable_exit_snapshot`, that has Modal take a filesystem snapshot whenever the sandbox ends. Spike S-SR1 (`internal/sandbox/snapshotresume_integration_test.go`, 2026-11-05 and 2026-11-06) measured it:

- An exit snapshot is taken after `Terminate`, after the idle timeout and after the hard timeout. It is ready 6 to 12 s after the end, and a boot from it reaches its first exec in about 2 s.
- It holds the main container's filesystem only. Files written in a sidecar are not in it, and the sidecar does not delay it.
- A restored OpenCode lists its conversations with the same messages, because its SQLite store (WAL included) is on that filesystem.
- It can be fetched later from another process, from the sandbox ID alone (`Sandboxes.FromID`, then `ExperimentalGetExitSnapshot`).
- It still boots after its base image is deleted, and a snapshot of a restored sandbox keeps both generations' work after the first one is deleted.
- Taking snapshots does not reset the idle clock.
- Without the option, `ExperimentalGetExitSnapshot` answers `InvalidError` naming `enable_exit_snapshot=true`.

Modal's documentation (exit snapshots are labelled beta) says one is taken on every exit except a preemption, which CPU sandboxes do not get. The snapshot is kept 30 days, and it stores only the difference from the base image. Modal publishes no storage price.

## Decision

**The spec.** `sandbox.Spec` gains two fields:

- `ExitSnapshot bool`: `ModalProvider.Create` sets `ExperimentalOptions["enable_exit_snapshot"] = true`.
- `ImageID string`: the image ID a snapshot boots from (DL-088). When it is set, `Image` is not resolved, and only names the image the sandbox is recorded against.

Both stay behind `internal/sandbox` with every other Modal type (DL-029). DL-029's tag list gains `run`, the session's run number (DL-085).

**When.** The server sets `ExitSnapshot` for an interactive session's sandbox only when all of these hold:

- the launch runs the credential proxy (`ProxyImage` is set, DL-034);
- snapshots are not switched off in the deployment config (DL-086);
- the server keeps its sessions in Postgres. A server on the memory store, which a local `spov serve` is, forgets its sessions when it exits, so nothing would be left to resume. Persisting a local server's sessions is a follow-up decision, after which local servers take part too;
- the session is not a job's.

So a job's sandbox never gets one, and neither does a sandbox launched with the tokens in the main container (a plain local build, or `SPOV_TOKENS_IN_SANDBOX=1`).

`sandbox.Provider` gains `ExitSnapshot(ctx, sandboxID, wait)`. It returns the snapshot's image ID, `ErrNoExitSnapshot` when the sandbox was created without one, or an error when the snapshot failed or is still pending at `wait`.

If Modal ever refuses the option at create (an `InvalidError` that names it), the launch is not failed. The provider creates the sandbox once more without it, records that the run has no snapshot, and the server logs a warning once per process.

S-SR1 is re-run on every Modal SDK bump (`SPOV_SNAPSHOT_SPIKE=1 go test -tags integration ./internal/sandbox/ -run SSR1 -v -timeout 30m`).

**What is now kept at rest.** This amends DL-029's "State is ephemeral". An interactive sandbox's filesystem outlives it, on Modal's storage, for at most the retention (DL-086): the clones of private repositories, the agent's files and OpenCode's store. It never holds a forge token or a provider key, because a snapshot is only taken under the proxy and the sidecar is not captured. A job's sandbox stays ephemeral.

## Rationale

The exit snapshot is the one copy that exists however the sandbox ended, which is what makes resume work for the common case: a session that idled out overnight.

The proxy condition keeps secrets out of stored images. With the proxy, the main container holds only placeholders, and S-SR1 showed the sidecar's filesystem is not captured. Without it, the forge tokens and model keys are in the main container's environment and files, and a snapshot kept for days would hold them. Such sessions can still resume from the transcript on a hosted server (DL-089).

Falling back to a plain create keeps an experimental option from ever blocking a launch. Losing resume for one session is better than refusing it.

## Consequences

- Every interactive sandbox on a hosted server under the proxy leaves an image behind, which DL-085 collects and DL-086 prunes. Implement DL-084 together with those two, or snapshots pile up for Modal's 30 days.
- The option is experimental and beta. A rename or removal shows as the fallback's warning, and S-SR1 is the check on a bump.
- A sandbox's memory is not in the snapshot, so processes always restart on resume.
- Repository contents now rest on Modal's storage between runs, within the retention. `docs/` that describes what spov keeps must say so.
