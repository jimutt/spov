## Context

The default toolchain (DL-032) leaves out what is larger or more specialised, and some projects need it: Rust, a browser for Playwright, Java, .NET, Ruby, PHP, a database. Two designs were rejected:

- Honouring `devcontainer.json`. Honouring it in part means a repository that works in Codespaces silently half-works in spov, and its features are arbitrary install scripts that assume Docker build semantics.
- Separate `addons` and `tools` keys, spov recipes versus mise installs. That exposes the implementation and leaves no rule for where Rust or Java belongs.

An organisation's Postgres or PHP major is fixed by its production systems and not by Debian's release, and a language version a project needs in every session is better built into the image than downloaded each time. An image should also be named after what it holds, which only an exact version says.

## Decision

### One curated list

`sandbox.addons` is one list of `name[@version]` entries, and `sandbox.apt` is a list of raw Debian packages.

```yaml
sandbox:
  addons: [rust, playwright, java@21, node@22]
  apt: [libvips-dev]
```

- `sandbox.apt` stays separate because it is a different kind of thing: raw packages with no recipe and no version. It feeds `ImageSpec.ExtraPackages`. A name may not start with `-`, so it cannot reach `apt-get` as an option. Packages the base image already installs are dropped (`sandbox.ExtraPackages`), and an `apt` list made only of those boots the base image, so the base is never built on demand.
- Both keys sit beside `sandbox.image`, not under it, because that key holds a custom image name. Setting `image` together with `addons` or `apt` is refused, since a custom image is not built from spov's recipe, and the server refuses add-ons on any image spov did not build.
- Curated only. Each add-on is an entry in the Go table `toolchain.addons`, which owns its layer commands, the versions it accepts, its default version, the environment it sets, any service it starts, and its note in the workspace guide. Whether a recipe uses mise, rustup, apt or an upstream installer is hidden. The current add-ons and their default versions are in `internal/toolchain/addons.go`: dotnet, java (Temurin), php, playwright, postgres, redis, ruby, rust, and the default languages node, python, go, bun and uv.
- Recipe details that a reader would otherwise have to find in the table: `rust` installs through mise, which runs rustup, removes the `rust-docs` component, and defers to a repository's `rust-toolchain.toml`; `playwright` installs Chromium and its system dependencies with `npx playwright install --with-deps chromium`; `dotnet` is the SDK for C# and F# installed through mise's dotnet backend (which runs Microsoft's install script), with `libicu76`, `DOTNET_CLI_TELEMETRY_OPTOUT` and `DOTNET_NOLOGO` set and `~/.dotnet/tools` on `PATH`, and a repository's `global.json` installs the SDK it names on first use; `ruby` installs a precompiled build through mise; `java` is Temurin through mise.
- `toolchain.Parse` is the only way to a `Selection`, and `ImageSpec.Validate` refuses a selection that Parse did not produce, so nothing unvalidated reaches a build command. Parse refuses an unknown name, a version the add-on does not accept, and a name given twice; the error lists the valid names. An unknown name never falls through to mise's registry.
- Validation happens before any build: at config validation, and again in the server, which is the authority (`Service.variantProblems`). A request carries `addons` and `apt` (at most 16 add-ons and 32 packages) in a session or job request, and the server derives the image name from them. A request that names neither add-ons nor apt nor an image gets the server's own `sandbox.addons` and `sandbox.apt`, as its egress preset applies; this is what a session started from the browser gets. Both keys follow config layering, where a later layer replaces the whole list. A client that sends neither gets the base image.
- The image name hashes the canonical form: names sorted and versions resolved (below).
- Docker is not an add-on: Modal's sandbox runtime cannot run it.
- Adding an add-on is a code change with a recipe, a test and a measured build.
- An add-on's environment (for example `PLAYWRIGHT_BROWSERS_PATH`, `DOTNET_NOLOGO`, `COMPOSER_ALLOW_SUPERUSER`) goes in the sandbox's own `Env` (`opencode.EnvConfig.Addons`), not in the entrypoint's exports, so a `sandbox exec`, such as a check or a spike, sees it as OpenCode does.
- How a variant image is built on demand, chosen at launch, registered and pruned is in DL-016.

### Versions

A version is optional. A bare name means spov's tested default, which is exact. `name@version` pins an exact version. A partial version (`java@21`, `node@22`, `dotnet@10`, `rust@stable`, `postgres@14`) resolves to an exact release before the image is named.

Accepted shapes, which are checked and not looked up in a list:

- `postgres@<major>`; `php@<major.minor>`; `redis@<major.minor>` or an exact `redis@<x.y.z>`; `rust` as `stable` or `x.y[.z]`; `java` as a major or a full Temurin version; `playwright` as an exact version only, which installs Chromium into `/ms-playwright`; the other tools as `x[.y[.z]]`.
- Because only the shape is checked, a major released after a spov build works without a spov update. A version the repository lacks fails the image build with apt's or mise's error, so a typo fails at build time and not at validation.

The default languages `node`, `python`, `go`, `bun` and `uv` are add-ons that pin a version into the image. The layer runs `mise use -g <tool>@<version>`, so the variant's global default changes. A repository's own version file still wins inside it. The base version stays installed underneath, unused, because a default cannot be removed. An entry at the base's own version is dropped by Parse, so it builds no variant, and the workspace guide lists the pinned version and says the base's is still installed. Pinning builds the language into an image that later sessions reuse and spares each session the download and the egress it needs.

### Resolving a partial version

The server resolves every partial version to an exact one before it names a variant; an exact version is left alone. The lookups are in `internal/addonindex`, not `internal/toolchain`, which renders commands and makes no calls; `toolchain` says where each add-on resolves (`Selection.Index`).

- mise-installed add-ons (node, python, go, bun, uv, rust, ruby, dotnet, java) resolve against mise's own version index, `https://mise-versions.jdx.dev/<tool>`. The answer is the newest version that extends the partial one, compared numerically, skipping anything with a pre-release marker. Java looks only at `temurin-` JDK builds. `rust@stable` means the newest release. Asking mise's own index means the server and the build agree on what "newest 22" is.
- postgres, php and redis resolve against their repository's `Packages.gz` for amd64: the newest upstream version of the add-on's main package (`postgresql-<major>`, `php<v>-cli`, `redis-server`), without the epoch or Debian revision. That is the version apt would install.
- An answer is untrusted input, because it reaches a build command. It must match a strict exact shape for its add-on and be a release of the requested version. `toolchain.Selection.Resolve` is the one check, for a fresh answer and for one read back from the state file. The index is not signature-checked here, since apt verifies what it actually installs.
- Answers are cached per add-on and partial version, in memory on a hosted server, and in a state file beside `server.json` (`variants.json` in the user's state directory, shared with the image registry) on a local server, which exits after a minute with nothing to do and would otherwise start every launch cold. An answer under an hour old (`Fresh`) is used as it is. An older one is used at once and refreshed in the background, so a launch waits for a lookup only when nothing is cached. A lookup that fails keeps the last answer and logs a warning. One that fails with no answer to keep is not tried again for five minutes (`FailureBackoff`), so an unreachable index costs one launch the lookup's 20 s timeout and not every launch. With no answer at all the launch falls back to the partial version as written. A missing or unreadable state file is a cold cache and never a failed launch. A launch's lookups run in parallel, each bounded at 20 s, and an index is read up to 64 MiB decompressed (PGDG's, the largest measured, was 4.6 MB).
- The server needs egress to `mise-versions.jdx.dev` and the three apt repositories.
- On a hosted server resolution is per process, so two replicas can disagree for up to an hour. That is harmless: each names the image after what it resolved.

A `Selection` carries both versions: the requested one, as Parse canonicalises it, and the resolved one. `Resolved` is empty when the requested version is already exact or could not be resolved, and such a selection renders byte for byte as an unresolved one, so an exact request names the same image whether or not a resolver ran. `Resolved` is set only through `Selection.Resolve`.

- The recipe renders the resolved version: `mise use -g node@22.23.3`, an exact apt pin such as `postgresql-14=14.24-*`, `php8.1-cli=8.1.34-*` or `redis-server=6:7.4.6-*`, and Temurin's full build. The build fails if the resolved version cannot be installed. `ImageSpec.Validate` checks both versions by shape.
- The variant's name hashes the recipe with the resolved versions, so a new patch release gives a new name and a new image. That is what lets a release reach new sessions without a manual rebuild. `ImageSpec.Requested().Name()` is the name of the request with versions as asked, the key under which the newest build of a request is recorded.
- A session records both. `SessionRequest.Addons` keeps what was asked (`node@22`), so a queued job re-derived at launch resolves again. `Session.Booted` keeps the image the sandbox was created from and the add-ons it installs (`node@22.23.3`), written by the launch. The session view shows them as `booted_image` and `installed_addons`, which makes "which Node did that job run on" answerable.
- The workspace guide names the resolved versions.

### Postgres, PHP and Redis come from upstream repositories

These three install from their upstream apt repositories (PGDG for PostgreSQL, `packages.sury.org` for PHP, `packages.redis.io` for Redis), the default version included, so there is one recipe per add-on. The suite is the base image's Debian release (`toolchain.DebianSuite`), tied to the base image by `TestTheAddonRepositoriesFollowTheBaseRelease`.

- Each repository's signing key is downloaded at build time and must match a fingerprint fixed in spov (the public signing-key fingerprints in the `pgdg`, `suryPHP` and `redisIO` values in `addons.go`). The download is imported into a throwaway keyring, and only the key with the pinned fingerprint, with its subkeys, is exported to `/etc/apt/keyrings`. Anything else in the file is never trusted, and a file without that key fails the build. `gpg` and `gpg-agent`, which an import needs (Debian's `gpg` package does not include the agent), are installed in the add-on's layer.
- A fingerprint check survives a re-signed key: pinning the file's hash would break the build whenever a key is renewed (the PHP repository's current key expires in 2028).
- The key is named in its source's `signed-by`, so it verifies that repository only. The repository's source stays in the image on purpose: a later `sandbox.apt` package, or an agent's own `apt-get install php8.1-gd` or `postgresql-14-postgis`, gets the version that matches the add-on.
- PHP packages are named per version (`php8.1-cli`, `-curl`, `-mbstring`, `-xml`, `-zip`, `-sqlite3` and `-pgsql`). Composer comes from the Composer project at a pinned version checked against its sha256: the current line for PHP 7.2 and newer and the 2.2 LTS line for older PHP (`composerFor`). Composer 2.2 LTS is maintained until the end of 2026; after that, PHP older than 7.2 keeps an unmaintained Composer. `COMPOSER_ALLOW_SUPERUSER=1` is set, since sandboxes run as root.
- `redis@8.0` means redis.io's newest 8.0.x. A partial version asks apt for the newest patch (`redis-server=6:7.2.*`), which depends on the repository's version epoch, 6, that the recipe names.
- Changing a recipe changes the image hash, so existing variants are rebuilt on their next launch.

What this trusts and what it costs: three third-party repositories are trusted in any image that asks for their add-on. Each can supply any package to that image, at build time and to an agent's `apt-get` later, and its packages can be newer than Debian's. A change of key requires a spov release with the new fingerprint, and until then a build of that add-on fails.

### Services start before OpenCode

Asking for postgres or redis means wanting it running, and a sandbox has no init system. Installing a service does not run it, and Debian's Postgres defaults to peer authentication, which refuses a `root` client. The entrypoint starts each service add-on in the background as its first step, before the clones and OpenCode (`Entrypoint.writeAddons`), and does not wait for it, so sandbox readiness time is unchanged.

- Postgres: a cluster with trust authentication on the loopback address and the local socket, a `root` superuser role and a `root` database, so a bare `psql` connects. It starts with `pg_ctlcluster <major> main start` for the add-on's major.
- Redis starts from the repository's `/etc/redis/redis.conf`, which binds the loopback addresses only.
- A service that fails to start does not fail the launch. Its output goes to a log under `/tmp`, and the workspace guide gives the connection details, the log path and the restart command. An agent that connects straight after start-up can find the service still starting; the guide says so. Service memory comes out of the sandbox's own allowance.
- spov sets no `DATABASE_URL` or similar variable. A project's own configuration decides how it connects.
- What trust authentication protects and what it does not: the services listen on loopback only, inside a single-tenant sandbox, so only processes already in the sandbox can connect. It gives no protection against them. That is acceptable because those processes are the agent and its tools, which run as root and already hold the project's code. It does not make the database safe to expose, and nothing here exposes it.

### The workspace guide

The generated `/workspace/AGENTS.md` carries a toolchain section rendered by `toolchain.Guide` from the same Go tables the image is built from, so it cannot drift from what is installed. The one hand-written part, the list of system tools, is checked against the image's package list (`TestTheGuideNamesOnlyBasePackages`). The section names:

- the default languages and their versions (a pinned language at its pin, with a note that the base's is still installed);
- each add-on with its resolved version and the note its recipe supplies, including a service's connection details;
- that a repository's version files are honoured and that `mise use <tool>@<version>` installs another version when egress allows;
- that Docker is not available.

It is appended to the file the entrypoint already writes, which exists only when the workspace has repositories. It is guidance and not containment. The rest of the file is described in DL-037. `TestTheGuideNamesExactlyWhatIsInstalled` and `TestTheWorkspaceGuideCarriesTheToolchain` check that every installed language and add-on is named and nothing uninstalled is; the add-on launch spike checks the file inside a real sandbox.

## Rationale

- One concept is easier to explain than two, and a curated recipe is one spov has built and measured, so an unknown name fails at validation and not halfway through a build.
- A fingerprint check keeps a compromised or re-signed key file from widening what is trusted, while still surviving a legitimate renewal.
- Checking a version's shape and not a list means a new major needs no spov release. The cost is a typo failing at build.
- Naming an image after the exact versions it holds is what lets a release reach new sessions, and recording both the request and the result keeps "the newest 22" meaning that while answering what a session ran on.
- Falling back to the partial version when a lookup fails keeps a broken index from stopping anyone's launch.
- Rendering the guide from the image tables saves the agent several exploratory turns without a chance of describing something that is not there.
- Starting a service in the background costs little and saves the agent a turn, and not waiting keeps readiness unchanged.

## Consequences

- A launch can depend on two more external services (mise's index and the apt repositories), only on a cold cache; a failure falls back. The resolver has to track the format of mise's list and of Debian's `Packages` files, and the integration run on a mise bump checks the first.
- A repository that has dropped an older patch cannot rebuild an image named after it. Nothing rebuilds an older resolution on purpose, and a race against a fresh release fails one build, which the next launch retries. Variant images accumulate, one per patch release used, and are pruned, see DL-016. An image built before names followed exact versions is named after the partial version, and DL-016 says how it is used.
- On a toolchain, mise, add-on or image bump, re-run the `ToolchainImage` and `AnAddonVariant|CredentialProxy` tests named above.
- `toolchain.DebianSuite` must name the base image's Debian release, or the upstream repositories are asked for the wrong suite.
- A re-keyed upstream repository fails that add-on's build until the fingerprint in `addons.go` is updated in a release.

## Known gaps

- The browser's session and job forms have no add-on picker; a browser session gets the server's own `sandbox.addons` and `sandbox.apt`. Add-ons are set through config or the API.
- A typo in a version of a shape-checked add-on (for example `postgres@41`) is caught only when the image build fails.
