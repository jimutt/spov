## Context

Organisations keep private package registries (npm, Maven, NuGet, PyPI) and other services a session needs a credential for. spov knows two kinds of secret, forge tokens and model provider keys, both held by the proxy sidecar (DL-034). There is no way to give a sandbox any other credential: nothing passes a secret through, and putting one in the main container would let the agent copy it out. This decision is the generic core the rest of the `routed-credentials` plan builds on.

## Decision

### The credential

A routed credential is a named secret plus a route:

- **Name:** lowercase letters, digits and `-`, starting with a letter, at most 40 characters. It is unique per owner (a user, or the organisation; DL-074).
- **Hosts:** one to 8 exact host names, lowercased. No wildcard, no IP literal, no single-label host, no port: the proxy decrypts only port 443. A host must pass the same check egress domains do (DL-031's `Validate`).
- **Paths (optional):** up to 8 path prefixes. A prefix ending in `/` covers everything below it, and one without covers that exact path, as a provider entry's `Paths` do (`ProviderAPI.allows`). With no prefix, every path on the route's hosts gets the secret. A request whose path carries a percent-escape, a dot segment or an empty segment gets no secret on a route with prefixes, so no encoding can move a request into a covered prefix.
- **Scheme:** how the secret is presented: `bearer` (`Authorization: Bearer <secret>`), `basic` with a username (`Authorization: Basic`), or `header` with a header name, whose value is the secret as it is.
- **Secret:** at most 8 KiB, never empty.

A header scheme may not name a header the proxy owns or that changes how the request is routed or framed: `Host`, `Cookie`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Upgrade`, `TE`, `Trailer`, `Keep-Alive`, `Expect`, any `Proxy-*` header, any `X-Forwarded-*` header and `Forwarded`. The name must be a valid HTTP token.

### In the proxy

The sidecar's configuration gains a `routes` list beside `platforms` and `providers` (`credproxy.Route`), and `SidecarConfig.Validate` checks it:

- A route host may not be a forge host the session holds a credential for, or a provider's API host. Within one session, two routes may not share a host: the proxy picks a credential by host, as it does for forges (DL-034's "one credential per forge host"), and which credential takes a contested host is decided at launch (DL-075).
- A route's hosts are decrypted, added to the per-sandbox CA's permitted names (`CAHosts`, `DecryptHosts`), and added to the session's egress under `install` and `agent`, as forge hosts are (`WithForgeHosts`, DL-031). The preset keeps its name. `open` is unchanged. A recreated sidecar resolves the same list.
- On a request to a route host whose path the route covers, the client's credential headers are removed (`credentialHeaders`, plus the route's own header name for a `header` scheme) and the secret is set in the route's scheme. On a path the route does not cover, the request is forwarded with the client's credential headers removed and no secret, as an anonymous client's would be.
- The response is scrubbed of the secret and, for `basic`, of its Basic encoding, as every credentialed response is (`scrubResponse`). git packs and `application/octet-stream` pass through unread as today, so a package tarball is not buffered. A body over `MaxScrubbed` is refused. A route's `text/event-stream` is read, as a forge's is: the pass-through exception stays for providers only.
- A redirect never carries the secret to another host. `httputil.ReverseProxy` does not follow redirects, so the client follows a redirect itself, and its next request gets a secret only if the new host is itself a route host and the path is covered.
- The proxy logs one line per request that got a routed secret (method, host, path, status, route name), never a header or a body.
- A route's secret is not renewed. A credential changed during a session reaches later sessions, and a recreated sidecar gets the secret as it resolves then (DL-075).

### In the sandbox

The main container holds only a placeholder, in `SPOV_CREDENTIAL_<NAME>` (the name uppercased, `-` as `_`). It is random per sandbox and keeps the secret's recognisable prefix by the same rule as forge placeholders (`credproxy.Placeholder`), because some tools branch on it. A user's own config can name the variable (an `.npmrc` line `//npm.acme.com/:_authToken=${SPOV_CREDENTIAL_ACME_NPM}`, say). A preset also writes the client's config file for it (DL-076). The variable name may not collide with anything `EnvConfig.Secrets` refuses (`TestProviderKeysCannotRedirectTheProxy`), and the name rule above already rules that out.

### Out of scope

Request signing (AWS SigV4), tokens minted from a service account, client TLS certificates, and anything not HTTPS (ssh, databases, plain HTTP). Signing and minted tokens could later be a "token source" in the proxy. Container registries are deferred with the Docker preset (DL-076).

## Rationale

DL-034's mechanism already does everything a routed credential needs for forge tokens and provider keys: a placeholder in the sandbox, decryption limited by name constraints, header replacement, and response scrubbing. A route generalises the provider entry (host, header, optional paths) with a user-chosen host and scheme. That costs no new trust boundary, and the secret never enters the agent's container.

Exact hosts keep the CA's name constraints as narrow as their purpose: a wildcard would let the CA sign for hosts nobody named. Path prefixes let a credential for one repository on a shared host (an Artifactory or Nexus instance holding several teams' repositories) stay off the others. Refusing escapes on a route with prefixes follows the forge policy, where the encoded form is what lets a request slip past a prefix check.

The forbidden headers are the ones that change routing, framing or the proxy's own behaviour. Allowing `Host` would let a route address another virtual host than the one the CA covers, and `Cookie` would invite session credentials, whose lifetime and scope the proxy cannot see.

## Consequences

- Any HTTPS service that takes a static secret in a header can be given to a sandbox without the agent holding the secret.
- A Java client fails on a route host, as it does on forge hosts today, because it does not trust the system bundle. DL-076 adds the CA to Java's trust for the Maven preset's sake, and that covers every Java client.
- A package metadata document over 32 MiB from a route host is refused rather than passed on unscrubbed.
- Tests: `TestARouteSetsItsSecretOnlyOnItsHostsAndPaths`, `TestARouteCannotNameAForbiddenHeader`, `TestARouteHostCannotOverlapAForgeOrProvider`, `TestARoutesEchoedSecretIsScrubbed`, `TestARouteHostJoinsTheEgressAndTheCA`.
