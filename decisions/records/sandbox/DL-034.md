## Context

An agent in a sandbox runs code from the repositories it clones and reads text from the web, so a prompt injection can make it run anything the sandbox allows. Anything the sandbox holds, the agent can read and send out. A git token and a model provider key are credentials that keep working after the sandbox is gone, and a key is billed to its owner. A scoped token narrows the damage, but spov cannot check how widely a Forgejo token or a GitHub personal access token (PAT) was created, and even a narrow token on the right repository can add a deploy key, a webhook or a push mirror that outlasts the session.

So the secrets stay out of the agent's container. Every sandbox gets a second container, a proxy sidecar, which holds the real credentials and adds them to requests for the hosts and endpoints a session is entitled to. The main container holds placeholders. The mechanism is Modal's sidecar feature, a second container in the same sandbox with its own processes, filesystem and egress policy.

## Decision

### Where credentials live

Every sandbox, interactive and job alike, that holds a forge token or a provider key gets a sidecar container named `proxy`. A launch with neither, such as public repositories and no key, has nothing for it to hold and gets none.

- The forge tokens and the model provider keys live only there. The main container holds a random placeholder for each, so the CLIs and OpenCode send their requests. `OPENCODE_PASSWORD` stays in the main container, because OpenCode checks every client against it. The server is reachable only through a connect token (DL-030), and the agent already runs inside that server, so reading the password gives it nothing it lacks, and a leaked password is no use without a connect token. Of spov's secrets, the agent's environment holds only `OPENCODE_PASSWORD`.
- The main container keeps its own egress preset (DL-031). Do not close it to force traffic through the proxy: that would break MCP servers, SDKs, ssh and every non-HTTP protocol for no gain to the secrets. Token safety does not depend on the main container's egress, because a client that bypasses the proxy reaches the forge with no credential.
- Proxy-aware clients are pointed at `http://proxy:3128` through `HTTPS_PROXY`, `HTTP_PROXY` and their lowercase forms; `NO_PROXY` covers `localhost`, `127.0.0.1`, `::1` and `main`; `credproxy.MainEnv` sets them. git, gh, tea, curl, npm, Bun and OpenCode's model calls honour them. A client that ignores them reaches the forge or the provider with a placeholder and gets a 401. What the main container holds in its `SPOV_GIT_TOKEN_*` variables, `.git-credentials`, gh's `hosts.yml` and tea's config is the placeholder, never the real token.
- The sidecar gets the same egress policy as the main container, fixed at creation (an open policy is created with no allowlists, since a sidecar is never narrowed). The SDK cannot change a running sidecar's policy, so a later change to the main container's egress narrows only the main container, and the forge hosts stay reachable through the sidecar. A main container with empty allowlists still reaches its sidecar, so no preset cuts it off from the proxy.
- The sidecar takes a share of the sandbox's own CPU and memory allocation (at least 32 mCPU and 32 MiB).
- A sandbox launched with the proxy carries the tag `proxy=1`. A re-mint of a token for it goes only to the sidecar, even when the sidecar has died, and never to the main container's files; without the tag it goes to the main container's files (DL-021). Where a re-mint goes is decided by the tag, never by whether the sidecar answers, because Modal reports an exited sidecar as not found and falling back would write the token into the main container (`TestADeadProxyNeverSendsTheTokenToTheMainContainer`).

### The proxy

The proxy is spov's own code: `cmd/spov-proxy`, a small static linux/amd64 binary embedded in `spov` the way the web app is, by `scripts/build-proxy.sh` and goreleaser, using the Go standard library only.

- `net/http` takes `CONNECT` and hijacks the connection. A host that is not decrypted is spliced byte for byte. A decrypted host gets `tls.Server` with a `GetCertificate` that issues a leaf from the sandbox's CA, HTTP/1.1 only, and forwards through `httputil.ReverseProxy`, which never follows a redirect: the redirect goes back to the client.
- The policy is plain Go beside it, tested per forge. The standard library was preferred over a proxy product because the policy is the point (the endpoint allowlist, choosing a token, taking a new one mid-session), which no product provides, and because an off-the-shelf proxy would put the policy in configuration outside the Go tests and make a mid-session token update awkward. A dependency such as goproxy would need its redirect, header and certificate-cache defaults audited in the component that matters most.
- It listens only on port 3128 and has no control port. It takes a new token or key only through an exec on the sidecar with the secret on standard input (`spov-proxy set-token <platform>` and `spov-proxy set-key <ENV>`); the credentials sit in a file only the sidecar's owner can read, replaced by a rename so a reader sees the old file or the new one, and the CA key and the configuration are removed from the process's environment once read.
- It dials public addresses only (`PublicDial`): it resolves the host itself and dials the address it checked, and refuses loopback, private, link-local, unspecified and multicast addresses. That covers the main container, the proxy itself and the cloud metadata address, and it means a provider endpoint on a private network cannot be reached through the proxy.
- A re-mint goes to the proxy by that exec and mints with the session's recorded git access.
- It logs one line per credentialed request (method, host, path, status) to the sidecar's own output, never a header or a body.
- Every proxy-aware client depends on the sidecar, OpenCode's model calls included, so a dead sidecar stops model calls as well as git until it is recreated. Paths that run on the server or come in to the sandbox (the second verdict gate and delivery asking the forge, connect, the file read) are unaffected.

### Decryption and the CA

- Each sandbox gets its own CA, made at launch, with X.509 name constraints that permit only the hosts the sidecar decrypts (`credproxy.NewCA`): the session's forge hosts and the API hosts of the providers it holds a key for. Its key could not sign for any other host even if it left the sidecar. It is an ECDSA P-256 CA that cannot sign other CAs and is valid for 26 hours (`CAValidity`), longer than any sandbox lives. The proxy issues one leaf per host, valid for 24 hours and cut to the CA's expiry.
- The CA key goes only to the sidecar. The certificate goes into the main container's system bundle and `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` are set for every process. A client that ships its own roots (uv with rustls, Java) fails on the decrypted hosts only.
- Only forge hosts and provider API hosts are decrypted (`github.com`, `api.github.com`, `uploads.github.com`, each selected Forgejo, Gitea or GitLab host, and each provider's host). Every other `CONNECT` is tunnelled as it is. Decrypting everything would give the proxy all model traffic and make every client trust it for every host; the name constraints keep the CA's reach as small as its purpose.
- A sandbox keeps the CA its launch made for its whole life. The CA's identity belongs to the sandbox and not to one sidecar process: OpenCode, MCP servers and anything else the agent started learned to trust it when they started, and a running process does not pick up a new one. At launch the CA is handed to the server (`keepProxyCA`), which seals it with the credential key (`SPOV_CREDENTIAL_KEY`, AES-256-GCM, bound to the organisation and session) in the table `session_proxy_cas`, which no listing or view reads. Without a credential key, or when that write fails, it is held in the server's memory, which only a single-process server can use for a recreation. The stored CA is deleted when its session stops, and the memory copy when the server forgets the session.
- The key is a secret the server did not otherwise hold. It is no broader than the credentials the server already seals: it can sign only for the session's own hosts, it expires with the sandbox's longest life, and using it needs a position on that sandbox's network path. Sealing it as user credentials are sealed keeps a database dump from yielding it.

### How a request is handled

A credential is added only to a request that arrived through a decrypted `CONNECT` to a host the sidecar decrypts (port 443, unless a forge's configured address names another port), and the decision is made for each request and not for each connection.

- The proxy dials the host named in the `CONNECT` and refuses a request whose `Host` or TLS server name differs from it.
- A plain-HTTP or absolute-form request is forwarded and never gets a credential.
- Every client credential header is removed before the policy runs: `Authorization`, `Proxy-Authorization`, `X-Api-Key`, `X-Goog-Api-Key`, `Cookie`, and GitLab's `Private-Token`, `Job-Token`, `Deploy-Token` and `Sudo`, in any spelling with underscores.
- A request on a forge host that the policy does not allow is forwarded without a credential, as an anonymous client's would be, so a public repository can still be cloned and public dependencies fetched.
- The placeholders keep the real credential's recognisable prefix (`ghs_`, `github_pat_`, `glpat-`, `sk-ant-` and so on), because tools branch on it. A placeholder is random per sandbox and worthless anywhere but this proxy.

### Forge endpoints

A GitHub App token is narrowed by GitHub to the session's repositories and is added on any path of its hosts, because gh also calls GraphQL (`POST /graphql`), whose path names no repository. A sandbox's App token is minted with `contents: write`, `pull_requests: write`, `issues: write` and `metadata: read` (`git.SandboxPermissions`), each capped at what the installation was granted (read from `GET /app/installations/<id>`, since asking for more than the App holds fails the mint; if the installation cannot be read all four are asked). It has no administration, webhook, secrets or workflows permission, so it cannot plant access, and a push that changes `.github/workflows` fails. The server's own tokens (listing repositories, verdict gate 2) are not narrowed.

A stored token (a Forgejo or Gitea token, a GitHub PAT, a GitLab PAT) is added only to an allowed endpoint of one of the session's repositories. The list is an allowlist, because a repository rule alone lets a hijacked agent add a deploy key, a webhook or a mirror that keeps access after the session, and a denylist would miss an admin endpoint. Anything absent is refused. A git access of `all` (DL-043) lifts the repository rule for its platforms and never the endpoint rule.

- Normalisation: owner and repository are compared case-insensitively with any `.git` removed. Percent-encoding, dot segments, empty segments, a trailing slash and absolute-form request lines are refused (GitLab differs, below). Forgejo's base path comes from its configured URL.
- GitHub (`api.github.com`, or `/api/v3` on GitHub Enterprise) and Forgejo or Gitea (`/api/v1`): any method on `contents`, the git data API, `commits`, `pulls` and their reviews and comments, and `issues` and their comments; reads only on branches (branch protection and renaming sit below them, and git creates branches itself), a pull request's `merge`, statuses, check runs and suites, `compare`, raw files, labels and milestones (tea reads the labels before it creates a pull request) and the repository itself; reads of `user`, `version` and `rate_limit`, which the CLIs call before they name a repository. Refused by absence: keys, hooks, collaborators and invitations, transfer, repository settings and deletion, Actions secrets and variables, push mirrors. The list is `repoSections`, with a test per forge in `policy_test.go`.
- git smart HTTP (`info/refs`, `git-upload-pack`, `git-receive-pack`), the LFS batch API, and a same-host LFS object transfer (`info/lfs/objects/<oid>` and its `verify`, which Forgejo's batch response points at).
- GraphQL: a GitHub PAT also gets `POST /graphql`, and a GitLab PAT `POST <base>/api/graphql`. Without it gh cannot open a pull request, a `pr` job could not deliver with a PAT, and users would pick git access `all`, which widens more. GraphQL is not narrowed: a PAT reaches there whatever its owner gave it, merging included. The session page says so, and Settings advises a fine-grained PAT limited to specific repositories, or for GitLab a dedicated account with access to only the projects spov should touch.
- GitLab names a project in its API by its whole path encoded as one segment, or by a numeric ID, and its REST API takes a bearer token while git over HTTPS takes Basic. Under `<base>/api/` the proxy sets `Authorization: Bearer`; elsewhere (git) it sets Basic with the username `oauth2`. A GitLab PAT cannot be limited to projects, so this rule is the narrowing.
  - The segment after `projects/` may be percent-encoded only with `%2F`. It is decoded, split, checked for empty and dot segments and a `.git` suffix, and must equal one of the session's full paths. A numeric ID is allowed only if the launch recorded it: `buildProxy` asks GitLab for each selected project's ID by path (`git.ProjectIDs`, concurrently under one 5 s deadline, and only for a stored token the proxy narrows), and a project it cannot read gets no ID. With git access `all`, any ID or path counts. Sections are matched on raw segments, so no escape can change which project or section is addressed.
  - Only the one segment after `repository/files`, `repository/branches` or `repository/tags` may carry another well-formed escape (never `%25`), and its decoded name may not have an empty or dot part. Anywhere else a `%` gets no credential. A dot in any segment after the section is refused, because GitLab routes `merge.json` as `merge`.
  - Any method on `repository/files` and `repository/commits`. On `merge_requests` and `issues`, writes are an explicit list: create (POST on the collection), edit (PUT on the item, never DELETE), and anything on its `notes` and `discussions`; every other item path is read only, so merge, approve, rebase, pipelines, approval rules and moving or cloning an issue are refused. Reads only: the project, `repository/branches`, `tags`, `tree`, `blobs`, `compare`, `archive`, `labels`, `milestones`, `pipelines`, `jobs` and commit statuses. Reads of `user`, `version`, `metadata` and `personal_access_tokens/self` need no project. Everything else is refused: hooks, members, variables, deploy keys and tokens, access tokens, protected branches, mirrors, transfer, export, runners, releases, packages.
  - A request whose query names `private_token`, `access_token`, `job_token` or `sudo` (any case, split on `&` or `;` as Rack does) gets no credential.
  - git: the path is one of the session's full project paths (with `.git` removed) followed by a git service. Smart HTTP and LFS batch on a session project, and GitLab's same-host LFS transfer paths (`<project>.git/gitlab-lfs/objects/<oid>[/<size>]`); LFS object storage on another host needs no credential. The GitLab policy splits the path itself (`allowsGitLab`) and the other kinds use `cleanSegments`, which refuses every escape.
  - A new glab feature that stops working inside a sandbox is most likely a missing section, as a new gh or tea feature is most likely a missing `repoSections` entry. `TestAGitLabTokenIsUsedOnlyOnTheSessionsProjects` guards the policy.

### One credential per forge host

A session holds at most one credential per forge host. The config may declare several platforms on one host, but only one may be used in a session. `git.Bootstrap` refuses a launch that needs two (`oneCredentialPerHost`, by each platform's host) before any token is minted, naming both, and `credproxy.SidecarConfig.Validate` refuses the same configuration again on the hosts the proxy decrypts, counting GitHub's `api.` and `uploads.` hosts as `github.com`. The proxy picks a credential by host with a linear scan, so a first match among two accounts would be an accident, and git's credential store and gh's `hosts.d` are keyed by host too. Choosing per request would need path-level selection the proxy does not have. Work on repositories from two accounts on one host needs two sessions (`TestASessionHoldsOneCredentialPerHost`).

### Model provider keys

Each forwarded provider key variable (the catalogue's allowlist, DL-013) gets a random placeholder that keeps the key's recognisable prefix (`credproxy.KeyPlaceholder`), so OpenCode sees a key and configures the provider as usual. The real keys reach the sidecar through its ephemeral Modal Secret beside the forge tokens, and a launch with a key and no forge token still gets the sidecar.

- For a request to a provider's own API host the proxy removes the client's credential headers, then sets the provider's own header: `x-api-key` for Anthropic, `x-goog-api-key` for Google Gemini, `Authorization: Bearer` for OpenAI, OpenRouter, Groq, xAI, DeepSeek and Mistral. Setting the one header, and not swapping the placeholder wherever it appears, keeps the agent from putting the placeholder into a header the provider echoes into a response body, which would then be unscrubbed in a stream.
- A key goes only to the host its own provider's catalogue entry names (`prep.Provider.API`, `ProviderAPIs`), never to another provider's, and the proxy refuses a configuration where two providers, or a provider and a forge, share a host. A key whose variable has no entry stays in the main container; every forwarded key has one. The CA's name constraints and the decrypt list add the API hosts of the providers the session holds a key for; the egress presets are unchanged, because the main container already needed those hosts. The catalogue is already the one list of the providers spov supports and the variables it forwards, and hosts and headers kept anywhere else would drift from it.
- A provider entry may list paths (and, per path, a method), and then the key is set only there, a path ending in `/` standing for everything below it; with none, any path on the host gets the key. There is no endpoint allowlist for the usual providers: a key's harm is spend and access to the provider account, inference is both the purpose and the spend, and provider APIs change often enough that an allowlist would break model calls after an OpenCode bump. A client's `?key=` on Gemini and OpenAI organisation and project headers pass through; they can only steer which of the key's own projects is billed. The OpenCode Console sign-in is the entry that lists paths, see DL-015.
- A provider key's variable may not be named like anything that points the sandbox at the proxy or its CA (`HTTPS_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS`, `SPOV_PROXY_CA` and the like): `EnvConfig.Secrets` refuses it, so a stored key cannot redirect traffic (`TestProviderKeysCannotRedirectTheProxy`).
- A key is not renewed: a key changed during a session reaches only later sessions, except where the server writes one in (the Console sign-in). A recreated sidecar is given the keys as they resolve then. The launch log names the provider keys the proxy holds (names only).
- A provider key is a spending credential with no expiry. Held by the proxy, the agent can spend through it while the session runs, since that is what running a model is, but cannot take it away, so the damage is bounded by the session. A tool in the sandbox that calls a provider directly gets a 401. The prep pass runs in the control plane and is unaffected (DL-047).

### Responses are scrubbed

Every response to a credentialed request has the credential replaced with `spov-redacted`, in headers and body, because an upstream can echo it (Forgejo's LFS batch API copies the request's `Authorization` header into each action it returns). The replaced forms are the token and its Basic encoding, or a provider's key. The client's `Accept-Encoding` is dropped from such a request, so the body arrives decoded.

- git pack and binary object responses (`application/x-git-*`, `application/octet-stream`) pass through unread, for any host.
- A `text/event-stream` from a provider's host passes through unread, because buffering it would stop the model's output from streaming; a forge's event stream is still read.
- A body over 32 MiB (`MaxScrubbed`), or one that still arrives encoded, is refused instead of being passed on unchecked. OpenCode streams, so for provider keys this reaches only non-streamed calls the agent makes itself.
- A provider error that quotes a masked fragment of the key (OpenAI's does) is not scrubbed; only the full key is.
- `TestAnEchoedCredentialNeverReachesTheClient` guards this. Do not pass a credentialed response through unread unless it is a git pack or a binary object.

### Building and starting the sidecar

- `ModalProvider.Create` creates the sandbox, then the sidecar, then waits for OpenCode's port; `Spec` carries the sidecar's image and secrets, and the secrets reach it through an ephemeral Modal Secret. The sidecar starts inside `Create` because the entrypoint waits for `proxy:3128` for at most 60 seconds before it clones anything, and exits with code 97 if the proxy never answers, so a failed launch says why.
- The proxy image is `spov-proxy-<hash of the binary and the base image>`. The first time a server needs it, it boots a minimal base, writes the binary in, snapshots the filesystem and publishes the snapshot with no expiry (the default snapshot lifetime is 30 days). It is recorded in the image registry and pruned like other images (DL-016; an older binary's image is deleted after 7 days unused, and one the registry marks deleted is baked again). Later launches reuse it, and a bake that failed is retried on the next launch that needs the image.
- When a sidecar cannot be resolved or started, `Create` terminates the sandbox, and if that succeeded the launcher re-bakes the image without looking its name up (a deleted image's name can still resolve) and runs `Create` once more. The retry is a whole new `Create` because the entrypoint's 60 seconds are less than a bake takes. A terminated sandbox holds its name for about 2 seconds after `Terminate` returns, so the retry waits it out, for at most 30 seconds. A server re-bakes at most once per process, so a Modal outage cannot turn every launch into a bake, and it never retries when the failed sandbox could not be terminated (`sandbox.ErrStillRunning`). Two replicas that bake at once publish identical contents under one name, so no lock is needed (`TestASidecarThatWillNotStartIsRebakedOnce`).
- A missing proxy is loud. If the sidecar cannot be created or does not answer, the launch fails. A plain `go build` embeds only a placeholder instead of the proxy binary: a hosted `spov serve` built that way refuses to start unless `SPOV_TOKENS_IN_SANDBOX=1` is set (`TestAHostedServerRefusesToRunWithoutTheProxy`, DL-010), and a local one starts and launches sandboxes with the tokens and keys in the main container, saying so at startup and on each session page. The credential line on the session page says where each token is held (`proxy` or `sandbox`, unset for an adopted sandbox), which kind it is, and its git access; the launch log says the proxy holds the token and uses it only for the session's repositories.

### A dead sidecar is recreated once

A pass on the reconciler's replica (`Service.CheckSidecars`, once a minute) looks at every running session whose sandbox is tagged `proxy=1`, from Modal's side (`SidecarRunning`). An exited sidecar is simply not found, and neither this lookup nor `Poll` resets the idle clock. Only a sandbox that is itself still running is looked at, and a job's only while it is running, blocked or steered: a provisioning launch and a delivering job's collection each end on their own. A recreation and a token re-mint of the same session never run at once, since each would revoke the other's token.

- The first time a sidecar has exited, the server obtains every platform's credential again (a renewable token is re-minted, a stored one is read again), resolving the tier the launch recorded and not switching to another (DL-042), and resolves the provider keys as they are now. Once they are in hand it tags the sandbox `proxy-recreated=1`, so an attempt that reaches the sandbox counts even if it fails, while a forge that cannot answer is simply tried again the next minute. It then recreates the sidecar under the same name; the main container reaches it at `proxy:3128`, whose address changes. Tags are merged with `Handle.AddTags` and never set with Modal's `SetTags`, which replaces every tag, and nothing is set over a read that lacks `spov=1`. The re-minted tokens the dead sidecar held are revoked, and the renewal pass keys on the new expiry. A recreation writes into the sandbox without the renewal's activity gate, so it resets an idle session's clock once.
- The recreated sidecar reuses the sandbox's CA when its permitted hosts cover every host the new sidecar decrypts (`credproxy.CACovers`). Then nothing in the main container changes: every running process keeps working and a recovery is invisible to the agent. When the CA cannot be had (lost with a restart of a server with no credential key, unreadable, or not covering a host added since, such as a provider key stored after launch), a new CA is made and installed, before the new sidecar starts, by one exec that replaces `MainCAFile` and appends the certificate to the system bundle. Processes started afterwards trust it; a running process, OpenCode included, keeps the trust it started with and its model calls fail until it restarts. Restarting OpenCode after a recovery was rejected: it drops the running turn and any attached client, loses a job plugin's in-memory state, and leaves other processes with the old trust. (`TestAKeptCASurvivesARestartSealed`, `TestARecreationWithNoKeptCAInstallsANewOne`.)
- The second time, the sandbox is ended. A job is ended through the job, with a marker (`jobs.MarkerProxyFailed`) that the verdict fails the job with; an interactive session is stopped with that reason as its error (`TestADeadSidecarIsRecreatedOnceThenTheSessionEnds`).
- An adopted job sandbox tagged `proxy=1` whose sidecar is not running, because the launch stopped before starting one, is terminated, and its session fails as a failed launch.

### What this buys, and what it does not

- The tokens and keys are never in the agent's container, so they cannot be copied out and replayed, whichever way its traffic leaves.
- The endpoint allowlist stops a live agent from using the proxy to plant access (a deploy key, a webhook, a mirror) that outlasts the session.
- Nothing stops a live agent from using the session's repositories through the allowed endpoints, as the credential allows, for as long as the session lives. With egress open, code can still leave the sandbox. A prompt-injected agent can still spend a held provider key while the session runs.
- The sidecar feature is alpha in Modal and is pinned through the SDK (DL-029).

## Rationale

- A sidecar puts the secret in another container and not in another namespace of the agent's own. Nothing about OpenCode, its port or the connect path changes. A namespace-based sandbox inside one container would need socket bridges in both directions and a uid mapping under which a root-owned file would still be readable.
- Both kinds of session get it together. An interactive session holds the same token and faces the same prompt injection from a cloned repository, and two credential paths would mean two ways to debug git in a sandbox.
- Decrypting is needed to add a header to gh's and tea's API calls, and to tell one repository's request or one endpoint from another. The alternative, rewriting git to plain HTTP and having the server open pull requests, would change how `pr` jobs deliver and would still leave gh and tea without a credential.
- An embedded binary baked by hash works from any server and is uploaded once per proxy version. The 78 MB `spov` binary would be a heavy upload and would work only from a linux/amd64 server.
- A hosted server refuses a build without the proxy because a hosted deployment's security should not depend on how its binary happened to be built; locally the user is also the operator and sees the warning.
- Failing closed on a client that ignores the proxy (a 401 on a placeholder) is better than a leak. If a provider's calls were found to bypass the proxy, the first fix would be OpenCode's own provider config (a base URL or fetch setting written by the entrypoint), and the next Modal's transparent relay, which routes all of the main container's traffic through the sidecar. The relay would change the rule that the main container keeps its own egress and would need a decision of its own; S-K1 found no provider that goes direct, so neither is used.
- The narrow decode of GitLab's project segment lets the proxy read the one place GitLab puts the project without the blanket decoding that would let an encoded `..` or `/` elsewhere change what is addressed. GraphQL is allowed for the same reason as on GitHub: the tools need it, and the PAT's owner sets its reach.
- Provider keys are set in the provider's own header and not swapped from the placeholder, for the echo reason above.

## Measurements

- S-I2 (a Modal sidecar): a second container in the same sandbox has its own processes, filesystem and egress policy. With the main container's egress emptied, the main container reaches the sidecar by name and nothing else. A secret in the sidecar's environment is not visible from the main container in any environment, process or file.
- S-I3 (`TestIntegrationCredentialProxyThroughASidecar`, `TestIntegrationSidecarAndIdleTimeout`): a running sidecar, and `Poll` on it once a minute, do not keep a sandbox from idling out; an exec into the sidecar does, as an exec into the main container does, so the sidecar check costs nothing and a re-mint into the sidecar stays gated by recent activity. A sidecar is created in about 0.2 s; the proxy answered about 5 s later, most of it the upload of its 7 MB binary, which the baked image removes. An exec in the main container inherits the proxy variables. With the main container's own egress closed, curl, git and gh reached decrypted GitHub hosts through the proxy and trusted the CA from the system bundle; OpenCode's call to `api.anthropic.com` went through the sidecar, trusted the CA through `NODE_EXTRA_CA_CERTS` and reached Anthropic with the header the proxy set; OpenCode needs `NO_PROXY` to cover localhost for its own server. tea, uv, pip and Node were not measured. Re-run: `go test -tags integration ./internal/sandbox/ -run 'CredentialProxyThroughASidecar|SidecarAndIdleTimeout'`; a gh or tea bump also re-runs the test that drives them through the proxy.
- S-I4 (`TestIntegrationSidecarRecovery`): a sidecar can be recreated under the same name and the main container reaches the new one at `proxy:3128`; an exited sidecar is reported as not found; Modal's `SetTags` replaces every tag; a terminated sandbox holds its name for about 2 s after `Terminate` returns. Re-run: `go test -tags integration ./internal/sandbox/ -run SidecarRecovery`.
- S-I1 (`TestIntegrationBubblewrapInModal`) measured the alternative of a namespace-based sandbox inside one container: it works only with a network namespace from `unshare --user --map-root-user --net` with bwrap inside it (bwrap's own `--unshare-net` fails under gVisor), and needs socket bridges both ways. It is not built. `TestIntegrationSidecarProxy` and the S-I1 test are the sidecar feature's re-check on an SDK bump: `go test -tags integration ./internal/sandbox/ -run 'SidecarProxy|BubblewrapInModal'`.
- Snapshot publish, the path that bakes the proxy image: `go test -tags integration ./internal/sandbox/ -run SnapshotPublish`.
- S-K1 (`TestIntegrationSKModelCallsThroughTheProxy`): every catalogue provider's model call, with the main container's own egress closed. The eight providers measured reached their catalogue host through the sidecar within a few seconds, and the providers' errors quoted the proxy's key and not the placeholder; none bypasses the proxy (ten with the OpenCode providers). It needs no provider key: the proxy sets an invalid key and the provider's 401 or 400 in the audit log shows the route (OpenRouter answers an invalid bearer with "Missing Authentication header"). The spike tries a provider's next model when OpenCode's resolver finds one unavailable, since the resolver ends the turn before any call (a model unavailable at the first pin was removed from the catalogue for that reason).
- S-K2 (`TestIntegrationSKARunningOpenCodeAndANewCA`), the same CA versus a new one after a sidecar recreation: with the same CA, a running OpenCode's model calls and git both continue; with a new CA, git (a new process per command) works but every model call of the running OpenCode fails with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, in the same session and in a new one, and `POST /api/location/reload` does not help. The spike stops the old proxy by its process ID, since `pkill` is absent from the image. Re-run: `go test -tags integration ./internal/sandbox/ -run 'SKModelCallsThroughTheProxy|SKARunningOpenCode'` (`SPOV_SK2_PROVIDER=openrouter` for that provider). The combined scenario `TestScenario5` (run in CI's Postgres job) covers the recreation and the kept CA against the fake provider.
- A whole launch through the sidecar, end to end: `go test -tags integration ./internal/session/ -run CredentialProxy`.
- S-GL1 (`TestIntegrationSGL1GitLabThroughTheProxy`): the pinned glab and git against a disposable GitLab project, through the real credential policy and locally with no Modal. The measured calls fit the allowlist; members, merge, approve, delete and an unselected project went without the credential, and every decrypted request is logged with whether it got the token. S-GL2 ran a `pr` job against a subgroup project and verified its merge request. Re-run: `SPOV_TEST_GLAB=<path to glab> go test -tags integration ./internal/credproxy/ -run SGL1 -v` (needs a GitLab test account).

## Consequences

- An SDK bump re-runs the sidecar spikes above, since the sidecar feature is alpha, and an OpenCode bump or a catalogue change re-runs the per-provider spike. The catalogue carries two fields per provider (its API host and header) to keep current on each OpenCode bump.
- A new gh or tea feature that stops working inside a sandbox is most likely an endpoint missing from `repoSections`; a new glab feature, a missing GitLab section.
- A new forge kind needs a policy in the proxy and an entry in `credproxy.Kinds`, which cannot import `git`; a test keeps the two lists together.
- A stored Forgejo, Gitea or GitLab token reaches only the session's repositories from inside a sandbox, whatever it was given at creation. Scoping the token at the forge is still advised, because the token leaves the server and a narrow token is a second limit.
- A recreation and a token re-mint of one session are serialised, so neither revokes the other's token.

## Known gaps

- A PAT's submodules from other private repositories stop working under git access `repos`.
- A tarball download redirects to `codeload.github.com` with a short-lived token in the URL, which the agent can see.
- git-lfs lock verification (`info/lfs/locks/verify`) and a request GitHub redirects to `/repositories/<id>/...` for a renamed repository get no credential; git-lfs warns and goes on.
- A credential or `sudo` in a form-encoded body is not read by the proxy for GitLab. GitLab reads the header the proxy sets after a body's `private_token`, so such a request authenticates as whatever the body names, never with the real token, which stays in the sidecar.
- An unrecorded numeric GitLab project ID goes out without a credential and fails visibly instead of silently widening access.
- With a new CA made because none was kept, a running OpenCode keeps failing its model calls until it restarts.
