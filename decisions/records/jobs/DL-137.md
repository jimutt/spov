## Context

A `pr` job is told two things spov wrote: the re-asserted goal ends with `branchEpilogue` ("Work on a NEW BRANCH and open a pull request from it", DL-051), and the generated `/workspace/AGENTS.md` has an "Opening pull requests" section that says to use the forge's CLI (DL-037, DL-032).

A caller that drives jobs from a pipeline writes a goal whose own command chooses the branch, pushes and opens the pull request, and that sends a second job to add to the branch of an open pull request. Both of spov's instructions then contradict the goal, and the agent has to pick one.

## Decision

A job request gains `pr_policy`, with the values `spov` (the default, today's behaviour) and `goal`. It chooses whose instructions say how the branch is made and the pull request opened; spov enforces neither. It is valid only on a `pr` job; on any other kind it is a 422. `spov jobs create` takes it as `--pr-policy goal`. The browser's form does not offer it.

With `pr_policy: goal`:

- **The epilogue** is `goalFlowEpilogue` in place of `branchEpilogue`:

  > Never commit or push to the default branch. The goal says which branch to work on and how the pull request is opened: follow it, and when it names a branch that already exists, add to that branch. Right after the pull request is opened or updated, call the spov_pull_request tool with its repository and branch: a pull request you do not record is not part of this job's result. Change only the repositories listed above.

  The GitLab merge-request note is added as before.
- **The guide's section** "Opening pull requests" is replaced by one that says the goal names how this job's pull request is opened, and lists the forge CLIs present as authenticated tools, with no `create` command. The refusal section (DL-108) and the scratchpad section stay. The orientation on the re-asserted goal (DL-039) no longer says the guide tells how to open a pull request.
- **Nothing else changes.** The `spov_pull_request` tool, its refusal of a repository not selected at launch, gate 2 and the plugin's permission allowlist are the same.

The value is stored on the job (`jobs.pr_policy`, empty meaning `spov`, so a request that names `spov` is stored empty), fixed at create, and reaches `opencode.Plugin` and the guide from there, so a continuation and a re-asserted goal carry the same text for the life of the job. A job's view shows it only when it is `goal`.

## Rationale

- A flag keeps the choice with the caller who wrote the goal. Letting a goal's wording override spov's instructions in general would make every guardrail in the epilogue negotiable by text.
- The lines that are guardrails (never the default branch, record the pull request, only the listed repositories) do not conflict with any such goal, so they stay.

## Consequences

- Gate 2 looks a pull request up by its branch (DL-051), so a job that names the branch of an already open pull request passes it whether or not it pushed anything. With `pr_policy: goal` that is the expected shape of a revision round, and a caller that needs to know a round added commits compares the pull request's head itself.
- The epilogue is guidance, as `branchEpilogue` is (DL-039, DL-040); protection of the default branch on the forge remains the control.
- `TestThePullRequestToolMatchesThePlugin` and the guide's tests gain the second flow.
