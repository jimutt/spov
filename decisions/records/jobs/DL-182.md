## Context

OpenCode 2.3.0's shell tool can run a command in the background: the agent asks for it (`background: true`), or a foreground command still running at its timeout is moved there. The tool call returns at once, and the command's result reaches the session later as a synthetic inbox item that starts a new turn (DL-180).

DL-143 holds the loop's continuation only while a subagent of the job runs. A job's turn that ended to wait for a background command was continued at once, and again at every turn end. On a live report job (2026-11-22) whose goal ran `sleep 20; echo build-ok; exit 3` in the background, the plugin continued three times in about thirty seconds. The agent, told each time to keep working, declared the job complete without the result, wrote "unknown" into its report, and the result arrived after delivery had begun. Each continuation was a billed model turn spent waiting.

Measured at 2.3.0 by spike S-OI1:

- a command moved to the background ends its tool call with `session.tool.success` in the calling session, whose `data.metadata` is `{status: "running", shellID, pid, truncated}`; a finished command's success has no `status: "running"`;
- `shell.exited` (`data.id` the shell id, with `exit` and `status`, no session) arrives when it ends;
- its result is an inbox item to the calling session of `type: synthetic` with `payload.metadata.source: "shell"` and the same `shellID`, which starts a turn;
- a command a person runs through the session's shell route (the TUI's `!`) has no tool call, and its result does not start a turn.

## Decision

**The plugin tracks the job session's background commands.** A `session.tool.success` of the job's session whose `data.metadata.status` is `"running"` and whose `data.metadata.shellID` is a string adds that shell id to the running set (`backgroundedShell`). It leaves the set when a synthetic inbox item to the job's session names it (`metadata.source: "shell"` and `metadata.shellID`, `reportedShell`), or when a `shell.exited` or `shell.deleted` frame names it (`data.id`). Each of those also records the id as ended (`endShell`, the newest 500 kept), and a backgrounded success for an ended id is ignored, so a command whose end is read before its call's success (a short one, or one moved to the background just as it finished) never holds the loop. A turn that ends between a command's exit and its result's arrival is continued as usual, and the result's own turn follows; the cost is one continuation. A subagent's own background commands are not tracked: their results go to the subagent's session, not the job's. A person's own shell commands are never tracked.

**The loop holds while one runs.** When the job session's turn ends and a subagent or a background command of the job is running, the plugin sends no continuation and records `continue.waiting` with the number of each (`running` for subagents, as before, and `shells`). The command's result starts the next turn by itself. `waitForSubagents` becomes `waitForBackground`.

**The same bound.** `SubagentWait` (10 minutes, from the turn end that began the hold) bounds this hold too. When it runs out with no turn of the job's started, the plugin drops subagents that sent no frame, as DL-143 says, but keeps every background command: its end is always seen, by its result or by `shell.exited`. The ordinary continuation then goes out with the wait note naming what is still running ("1 subagent and 2 background commands"), and the next turn end may hold again. A paused, stopped or held loop, a failed turn's retry and a stop marker are unchanged.

**Completion still does not wait.** DL-143's rule stands: a declared completion ends the run whatever is still running in the background.

**The agent is told.** `SubagentNote`, in the completion tool's description and every continuation, adds that a background command reports its result the same way and that one still running when the tool is called is ended. The wait note also suggests stopping a background command the agent no longer needs. The generated `/workspace/AGENTS.md` section on subagents, now "Subagents and background commands", also says that a background command's result reaches the agent as a message of its own when the command ends, which starts its next turn, so it need not poll or sleep for it, and that a command still running when the job completes is ended with the sandbox.

## Rationale

A background command is the same shape as a subagent at 2.3.0: the call returns at once and the result arrives as a message that starts a turn. Continuing while one runs does nothing but bill turns and push the agent to declare early. Keeping commands through the bound, rather than dropping them as quiet subagents are dropped, follows from their end being observable; a subagent is dropped only because a missed end frame could otherwise hold it forever.

## Consequences

- A job that waits on a build, a test run or any long command costs no model turns while it waits, up to ten minutes at a time.
- A job that leaves a server running in the background and ends a turn without completing waits up to ten minutes before it is continued, each time. The note tells the agent what is still running; the wall clock (DL-049) bounds the job.
- On an OpenCode bump, S-OI1 re-measures the frames, and S-SA3's background test (`SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SSA3 -v`) runs the hold end to end with the real plugin.
