## Context

A person watching a job can stop the turn the agent is in the middle of, from the web composer's Interrupt button or with `spov jobs interrupt <job>`. Stopping the turn is a call to the sandbox's OpenCode. For a job that call alone strands it:

1. The plugin continues the loop only on `session.execution.succeeded`. An interrupted turn clears `loop.inFlight` and sends no continuation.
2. The supervisor derives `signalTurnEnded` from the interrupted turn, and the state machine has no case for it, so the row does not move.
3. The abandoned-job backstop returns early while the session is live.

The job stays `running` with nothing that will ever continue it, and it holds its sandbox and quota until the sandbox idles out or the wall clock ends it (DL-049, DL-045). The state an interrupt should produce is `steered`: the loop stops continuing, the sandbox stays up, the person owns the session, and leaving takes an explicit act (DL-054).

OpenCode's interrupt call has a `resume` query parameter. It has no server-side default: an absent value behaves as false, and an unknown query parameter is ignored. With `resume` absent or false, a message the person sent just before interrupting stays parked in the inbox.

## Decision

### An interrupt is a sandbox call plus a marker

`POST /api/v1/sessions/{ref}/interrupt` (`Service.Interrupt`) interrupts the conversation's turn and, for a job's session, writes a spov-sourced marker, `jobs.MarkerInterrupted`. It never writes the job row. The supervisor's own pass reads the marker: `signalFor` matches it by name and source, in the branch that runs before other markers are dropped, and yields `signalSteered`. `applyFollow` then writes `steered`, and the guard that fires on that transition holds the plugin's loop (DL-054). `spov jobs interrupt <job>` calls the same endpoint.

Reusing the supervisor's machinery gives each property:

- The marker is a durable store row, so a crash right after writing it is recovered by any replica's next pass.
- There is no half-finished state: the loop is never held under a row that `ResumeJob` refuses, because the same pass does both.
- The supervisor stays the one writer of job states.
- It cannot race the pass. If the handler wrote `steered` itself, a pass already in progress would discard its own conclusion: `applyFollow` refuses `steered -> blocked`, so a park detected in that pass would be dropped with its event already behind the cursor, leaving the job steered over an unanswered permission.

A sandbox cannot forge the marker. `store.Event.Validate` refuses `spov.`-prefixed event names on ingest, and `signalFor` requires `Source == spov`.

The marker is not best-effort, unlike the audit note a message leaves. A stopped turn with no marker behind it is the stranded job this design prevents, so a failed write fails the request, and trying again is safe: a second marker steers a job that is already steered and changes nothing. It is written on a detached context, because the turn has already stopped and a caller hanging up must not decide whether the job is ever taken off it. It is written only after the sandbox call succeeded, so a call the sandbox refused leaves no marker (`TestAMarkerIsNotWrittenForATurnThatWasNotStopped`); and `interrupted: false` still writes one, since false does not mean the turn is still going. After the marker the handler nudges the recorder so `session.execution.interrupted` reaches the store for gate 3's discount (DL-050). The nudge is best-effort and the recorder's poll remains the mechanism.

### Interrupt reads what the person sent, at once

The call sends `resume=true` (`ResumeOnInterrupt`), always stated through `interruptURL`, because an absent value means false. A message the person sent and the agent has not yet read is delivered at once, in a new execution. Items sent as `queue` stay parked, as OpenCode documents; the browser does not send them. The value is a string union: `?resume=1` or `yes` are validation errors, not truthy.

`interrupted: false` is an ordinary success and does not mean the session was idle. On an idle session holding an undelivered `steer` item, `resume=true` delivers that item and starts a turn while reporting `interrupted: false`. Clients must not say the session was idle when they see it.

Only a code check catches a renamed parameter, since OpenCode ignores unknown ones: the contract check covers `resume` (DL-035). At a job's wall clock the supervisor ends the run with its own interrupt (`EndJobRun`), which sends `resume=false` so nothing queued starts afterwards and writes no marker (DL-049).

### On a job, an interrupt is a takeover and holds the loop

Because `resume=true` starts an execution, the plugin holds its loop when it sees `session.execution.interrupted` with `reason: "user"` in the job's own session (recorded as `loop.held`, reason `interrupted`). The execution that answers the person's message then ends without a continuation, before the supervisor's pass writes `steered` (`TestAUserInterruptHoldsTheLoop`). The hold is released by Resume. The message the person sent keeps its own `after` (DL-052), but the interrupt takes the job over whatever it says.

A human's rejection of a tool call raises the same `session.execution.interrupted` event with `reason: "shutdown"`, so any code that reads the event must filter on `reason == "user"`. The plugin holds nothing for a reject.

There is no interrupt-and-send act and no "interrupt that holds queued messages", in the API or the browser. People type the correction and then stop the work that should not continue, and a hold would answer that with silence. With `steer` as the default delivery a message waits only while one step runs, so there is rarely anything left to hold.

### Which states allow it

`jobRefusesAnInterrupt` allows `running` and `steered`, where the turn running is usually the one answering the reader's own message, and answers 409 (`ErrJobNotInterruptible`) naming the state for:

- `blocked`: something is running, but the job's way out is answering the permission or resuming, and stopping the turn would strand the question.
- `queued`, `delivering` and the terminal states.
- `provisioning`: the machine has no `provisioning -> steered` edge, so the marker would do nothing while the caller was told the turn had stopped.

The refused set equals the message refusal's (DL-052), pinned by `TestTheTwoRefusalsCoverTheSameStates`, and the browser's `canStop` mirrors it (DL-059). On an interactive session Interrupt is only the sandbox call: no row, no marker, no loop.

The conversation is chosen as a message's is (`steerInto`): against the store's own rows, and an omitted one is accepted only when the session has exactly one. Taking the caller's word would let a request stop a turn in another session's conversation using the credential of a session they own.

The recorder's mint reserve is checked only when the act would mint (a cache miss on the connection), and then a stop that would spend it is refused with a 429 (`ErrTooManyStops`). A stop is what a person presses when something is wrong, so it is never refused to protect a recording while the connection is cached and costs no mint (`TestTheReserveIsTakenOnlyWhenAStopWouldMint`).

### Gate 3 and the interrupt

An interrupt spov issued and a person's rejection of a tool call leave the same evidence, a tool part with `error.type: "aborted"`, so gate 3 reads spov's own interrupt as the agent being refused unless it can tell them apart (`internal/jobs/interrupted.go`). The rules below are the discount; the gate's other rules are in DL-050.

- A part is discounted as stopped by a person (`stoppedByAHuman`) only when three things hold together: its type is `aborted`; its `time.completed` lies within two seconds (`stopWindow`) of a `session.execution.interrupted` event with `reason: "user"`; and its error message is the interrupt's, "Tool execution interrupted". The timestamps come from the frame's own `created` and the part's `time`, both on the sandbox's clock. Neither the timing nor the message is enough alone (`TestNeitherSignalDiscountsOnItsOwn`), and a refusal of any other type is never discounted (`TestAPolicyRefusalIsNeverDiscounted`). The caution runs one way: a missed discount leaves a false sentence in the verdict ("a tool call was refused"), while a wrong discount blinds the one gate that can veto a success to a real refusal.
- A part a person stopped counts as having run only if it had started, which `time.ran` tells (`anyToolRan`, `TestACallStoppedBeforeItStartedDidNotRun`): `time.completed` is set on an aborted part either way. Gate 3 asks what ran, not what was called, so a run whose calls were all stopped before they started is unverified, not passed.
- A user interrupt clears every permission question asked before it, and only those; a question asked after it belongs to a later turn and is a real park. Without this an interrupt that cut a question short would block the job as "waiting on a permission request nobody answered" (`TestAQuestionTheInterruptEndedDoesNotPark`).
- `interrupted` with reason `shutdown` is read as the sandbox timing out and sets `Verdict.Retry`, unless it lies within two seconds of a call a person declined, whose message is "The user declined this tool call": a rejection raises the same event with that reason (`wasShutDown`, `TestAHumanRejectIsNotASandboxShutdown`). Here the caution runs the other way, since suppressing the retry note needs the corroboration.

## Rationale

- The aborted tool part from an interrupt carries `error.type: "aborted"`, the same value as a human's reject, so the supervisor and the verdict cannot tell the two apart without the marker and the event's `reason`.
- A new state such as `interrupted` would need its own edges, resume behaviour, rendering and backstop handling, to express a distinction nothing downstream acts on. `steered` already means exactly this outcome.
- `resume=true` matches what people do: send the correction, then stop the work.

## Measurements

- **S-LS1** (`go test -tags integration ./internal/sandbox/ -run SLS1`): an absent value and `false` each leave the inbox item and start nothing; `true` on an idle session delivers the pending steer item and starts a turn (`interrupted: false`). `1` and `yes` are 400. Re-measured at OpenCode 2.0.22 with the parameter named `resume`.
- **S-LS2** (`go test -tags integration ./internal/sandbox/ -run SLS2`, build 19151): interrupting a real `shell` call gives a tool part with `state.status` `error`, `error.type` `"aborted"`, message "Tool execution interrupted", `executed` false and `time {created, ran, completed}`. `session.execution.interrupted` (reason `user`) is durable, and its `created` time is 7 ms and 11 ms from the part's `time.completed` across two runs.
- **S-LS3** (`go test -tags integration ./internal/sandbox/ -run TestIntegrationSLS3InterruptVersusReject`, one session, run twice): a human's reject is followed by `session.execution.interrupted` 10 ms later in both runs, with `reason: "shutdown"`. Filtered on `reason: "user"`, the event is 7 to 14 ms from the part spov stopped and 17 to 22 s from the part a human refused. A reject's message is "The user declined this tool call". The two-second window in gate 3 sits two orders of magnitude above the first and one below the second.
- **Inbox ordering** (spike S-Q1, `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SQ1 -v`): `resume=true` delivers a pending message at once in a new execution, and queued items stay parked (DL-019).
- Among the interrupt call sites in the OpenCode bundle measured (build 19378), the user-facing stop paths pass `continue: true`; subagent, undo and every ACP and CLI teardown path pass nothing; none passes false.

## Consequences

- The row changes on the next pass, so the badge lags the action by up to a pass. The turn has already stopped, so the lag is cosmetic.
- A stop that lands on a run that has already finished still holds the job at `steered`, and the abandoned-job backstop delivers it once the sandbox is gone (DL-045). The deliverable is lost, because the sandbox is gone when delivery reads it, but the job does not hold its owner's quota forever (`TestAnInterruptThatLandsOnAFinishedRunHoldsIt`).
- Cutting a turn off can leave a half-written file. Nothing spov says may suggest the agent stops cleanly.
- A job can reach `steered` with no human message in its transcript, because an interrupt alone takes it over.
- `ResumeJob` is reachable from the browser as the way out (DL-054).

## Known gaps

- Pressing ESC in an attached TUI still strands a job: no marker is written. The `reason` an attached TUI's ESC carries is not measured. `session.execution.interrupted` also carries reasons other than `user` (`shutdown`, `inactivity`, and one for a turn replaced by another), so OpenCode itself can interrupt a job's turn with no person involved and strand it the same way; the reason is the signal a wider fix would read.
- No single run measured both an interrupt and a person's reject: the two messages come from different builds, so nothing would catch a build that rewords either, which would only bring back the false "refused" sentence.
- A `permission.asked` landing between the endpoint's `blocked` check and the supervisor's next pass leaves a marker folded from `blocked`, where there is no edge to `steered`, so the supervisor drops it without a warning. The job stays parked on its question, which is what the refusal wanted, but a reader who pressed Interrupt sees no effect and no reason.
