## Context

A job runs unattended, so someone has to say whether it worked. Three obvious signals are wrong. The CLI's exit code is 0 even when a permission was rejected. The turn's own outcome is `stop` even when `permission.evaluate` denied every call, because the agent narrates the denial and finishes. And the agent's final message is a claim, which is exactly what a verdict must not rest on. What a run actually did is in its tool parts, its recorded evidence, and what it left behind that spov can check from outside.

## Decision

A finished job is judged on three gates. The turn's outcome and the CLI's exit code are never evidence. `judge` combines the gates and `recordVerdict` writes the result.

### Gate 1: the check

The repository's own check command exits 0. It runs in the sandbox, the plugin captures its output as evidence, and the recorder stores it (DL-039). The check is a property of the job: it is taken on the create request and persisted on the row (`check_command`), because the launch happens later and possibly on another replica. A check the caller did not give may be proposed by the prep pass (DL-047); that is recorded as `check_proposed`, and every gate 1 outcome says so ("a check spov proposed, not one the caller gave", `withCheckProvenance`). Guessing a check is worse than running none, because a guess that does not exist reports an infrastructure failure on every job, and one that checks the wrong thing passes a gate nobody meant to pass.

- The command runs in the session's directory, `/workspace` by default, so a repository-relative check is written `./<repo>/scripts/check.sh`. `--landing <repo>` moves the session and the check into that repository. There is no `check_dir` field, because a check is a shell command and `cd repo && ./scripts/check.sh` already says it (`TestTheCheckRunsInTheSessionsDirectory`).
- A timeout or an infrastructure failure is distinguished from a failing suite and is `unverified`, not `failed`.
- A shell exit of 127 (not found) or 126 (not executable) means the command could not be run, not that the suite failed. Gate 1 stays `unverified`, worded "the check command could not be run". When the caller set the check, success also becomes unreachable and the job is recorded `failed` with that reason: the caller asked for a gate and did not get one, and 126/127 is deterministic, unlike a transient failure. A check spov proposed does not veto, because failing a job over spov's own guess would be an infrastructure failure on every job (`TestACheckThatCouldNotRunVetoesSuccess`, `TestAProposedCheckThatCouldNotRunDoesNotVeto`, `TestAJobWithNoCheckIsNotVetoed`). A veto and not a new outcome value, because the distinction is already in the detail text and an outcome value would be API surface and a web rendering for it. Validating the path at create time was rejected: spov knows the clone directories but not the sandbox filesystem, so a warning would be a heuristic, and a wrong warning on a working setup is worse than none.
- A job started without a check command has no gate 1, whatever the evidence file says: gate 1 is `unverified` ("the job was started without a check command, so there is no mechanical gate"). This closes the cheapest forgery, since the agent can write the evidence file.
- Once any `user` inbox item exists in the run (an enqueued item of type `user`, whatever its `after`; the opening goal and the plugin's continuations are `synthetic`), a proposed check is `unverified` whatever it returned. Its detail keeps what the check found and adds that a person wrote after spov proposed it. A proposed check is spov's guess at done, drawn from the goal as first written, and a person's message is newer and more authoritative; a correction can make the guess wrong. A check the caller gave is unaffected. A person who wants a check to decide a steered job gives it themselves (`personWrote`, `TestAProposedCheckStopsDecidingOnceAPersonWrote`).
- The plugin's evidence line is flat, `{event, at, ...data}`, and `TestGateOneReadsTheLineShapeThePluginWrites` pins the reader to it with distractor lines present. A reader that expects a nested `data` object leaves gate 1 unverified on every job with no error anywhere, which looks the same as a job with no check.
- A timed-out check kills its process group (`detached: true` plus `process.kill(-pid)`), or the orphan holds the sandbox open for as long as the command would have run (`TestATimedOutCheckStopsWhatItStarted`).
- The check runs before the stop marker goes out, because the supervisor collects the evidence file in the one sandbox visit it makes when it sees the marker (DL-048).

### Gate 2: the deliverable

Gate 2 asks whether the job left what it was for, from spov's side. A `pr` job's deliverables are the pull requests (merge requests on GitLab) the agent recorded, each asked about on its own forge; a `report` job's are the Markdown files collected from the out directory (DL-051). spov asks with its own client and a credential it holds, never `gh` or `tea` inside the sandbox, whose view the agent can shape. Crediting an unchecked pull request would be the claim the agent could otherwise make for itself.

Each member gets a status: `verified` (the forge answered with an open or merged pull request from the branch, or the report was collected), `missing` (the forge says none, or the request was closed without merging), `unverified` (spov could not ask or could not read), or `over_limit` (not collected because of the collection limits). The gate's outcome over the set:

1. `passed`: at least one member is verified and nothing qualifies the result. Every member is verified, nothing was declared `unfinished`, the run was not ended by its wall clock (DL-049), and no report lost a linked image.
2. `partial`: at least one member is verified and something qualifies it: a missing, unverified or over-limit member, a non-empty `unfinished`, a lost image, or an ending at the wall clock.
3. `unverified`: no member is verified and at least one is unverified, or the report listing itself failed.
4. `failed`: no member is verified and none is unverified. That covers a `pr` job that recorded no pull request, a report job whose out directory held no Markdown file, and a set where every member is missing or over the limit.

A member the agent withdrew at a reader's request is named but not judged (DL-051): the rest are judged without it, a set whose every member was withdrawn fails as a job that recorded nothing, and a withdrawal made with no later message from a person is judged as recorded and the detail says so. A pull request found closed without merging is a `missing` member that the detail counts separately ("closed without merging").

The detail names counts and qualifying facts, for example "2 of 3 pull requests verified; 1 could not be checked; the agent left unfinished: migrating the docs". Selecting three repositories and opening one pull request is not incomplete. A report that lost a linked image stays `verified` with `ImagesLost` set, and gate 2 reads it as partial.

- A broken query or a broken read is `unverified`, never `failed`. Delivery is idempotent, so a `failed` caused by a connect failure would be permanent on a job that may well have delivered. "spov could not check" and "the job did not deliver" stay different findings. Collection records `spov.job.collect.failed` and gate 2 reads that as unverified. Only spov's own marker counts; if the sandbox's word counted, a sandbox could talk its way out of gate 2.
- The agent reports what it opened, with `spov_pull_request {repository, branch}`, and spov never guesses a branch from the newest branch or a name pattern. A gate built on a guess is worse than an unverified one because it can be confidently wrong, and "some pull request exists in this repository" is not evidence about this job. A pull request URL reaches the job's `Result` whatever the verdict.
- Gate 2 asks the forge with the job owner's credential, resolved exactly as the launch resolved it and at the tier the launch recorded (`JobOwnerForge`, `FindPullRequestVia`, which takes a resolver rather than a forge; DL-042). "Not the sandbox's credential" means a job cannot influence what the gate sees by editing its environment, and the owner's credential is resolved on the server from the sealed store on a path the job never touches. The deployment's organisation forge is not what the launch used, and may be another account with no access to the repository; asking with it would leave every `pr` job on a user-credential deployment unverified with its pull request open. A deployment with no per-user resolver falls back to the deployment's forge. A nil resolver returns `ErrUnsupported`, which gate 2 reads as "cannot answer" and never as "found none". `jobs.Forge` stays narrow and declared in `internal/jobs` (DL-046). A hosted delivery decrypts the owner's credentials once per job, from the store and not the sandbox. A user who narrows their token after the job gets `unverified`, the safe direction (`TestGateTwoIsWiredToTheJobOwnersForge`).
- The query is a read against the forge at delivery, not against the sandbox, so it resets no idle clock (DL-018).

### Gate 3: conduct

Gate 3 is read on every job. It classifies from stored events and message parts, with no sandbox contact.

- **A refused call** is a tool part with `state.status == "error"` and a non-empty `state.error.type` other than `tool.execution` (`toolPart.Refused`). The refusal has no single marker: the plugin's own deny leaves type `permission.rejected`, and a person's reject through the permission reply endpoint leaves `aborted` with the message "The user declined this tool call". The shape is what gate 3 keys on, and an unrecognised type is still a refusal, so a build that invents a third marker is caught. `tool.execution` is the runtime error of a tool that ran and failed (an edit whose old and new strings are identical, say) and is excluded by that one name, not by switching to an allowlist of refusal types. The agent's narration of a denial is never an input.
- `executed` is OpenCode's `providerExecuted`, false for every locally executed tool, successes included. It is kept only as a guard against a provider-executed part and never separates a refusal from a success. The type requirement is the whole test: dropping it as redundant would turn every ordinary tool failure into a refusal and block working jobs, and nothing else would catch that, since the work got done and the other gates pass. `TestARuntimeToolErrorIsNotARefusal` fails in both directions, treating every type as a refusal and narrowing to the two known ones. The doubt points one way on purpose: missing an unrecognised refusal blinds gate 3 to one blocked run that the other gates can still catch, while treating every untyped error as a refusal blocks working jobs.
- **A refusal vetoes only when no tool call ran** (`anyToolRan`, decided from the tool parts, never from the other gates). The allowlist is narrow on purpose (DL-040), so a run that is refused something, notices and does the work another way is the policy working as designed, and "the run was prevented from working" is different from "a call was refused". Gates 1 and 2 cannot answer that question: gate 1 runs the check in the sandbox outside the permission hook and passes on an already-green repository, and gate 2 can collect an artifact that predates the run. Whether a call ran cannot be inherited from a previous run. `TestARefusedRunIsNotASuccessHoweverWellItFinished` is the case to keep: a run refused everything, holding a passing gate 1 and a passing gate 2, is still blocked. There is no threshold on the refusal count, because any number is indefensible.
- A refusal that did not decide the outcome is recorded as an observation: the gate's outcome is `passed` and its detail says a call was refused and the run continued. A successful job's verdict text does not recite refusals. `conduct: passed` is therefore not a claim that nothing was refused.
- **An unanswered permission always vetoes.** It is a run waiting, not a refusal, and the job is not finished whatever else ran. An internal `Parked` flag on the gate result tells the two apart and deliberately does not reach a client, because `ParseGatesNote` rebuilds the gates from the verdict text and a wire field would be a second copy of a fact that matters only while the gates are combined. `blocked` is rare because only a wholly refused run or a parked one reaches it.
- Requests are paired as the supervisor pairs them (DL-046): an asked frame names its request at `data.id` (`PermissionID`), `permission.replied` at `requestID`, and spov's `MarkerAnswered` names a request a person answered through spov. An asked frame with no readable ID still counts as a park. A person's interrupt clears what was asked before it (DL-053). A turn ending does not clear a request at gate 3, because delivery's own interrupt ends the turn of a job abandoned while blocked (`TestGateThreePairsPermissionsByRequestID`, which builds the measured frame shapes).
- A part spov's own interrupt aborted is discounted (DL-053). `interrupted` with reason `shutdown` is a retry (a sandbox timeout), not a failure.
- With no tool call at all the gate is `unverified` ("the run made no tool calls"), and with calls that were all stopped before they ran it says that instead.

### Combining the gates

`judgeGates` decides in this order:

1. A failed gate 3 with a park, or with no tool call having run, gives `blocked`. A refused run that reached delivery is recorded `failed` with the refusal as its reason, because there is no `delivering -> blocked` edge.
2. A failed gate 1 gives `failed`, even if something was delivered: a pull request that does not build is not the deliverable.
3. A failed gate 2 gives `failed`.
4. A check the caller set that could not be run gives `failed`.
5. Gate 2 `passed` or `partial` gives `succeeded`. A passing check does not carry a success alone: a `pr` job on a forge spov cannot query fails with every member unverified, and a job whose every gate is unverified produced no evidence it did anything and is recorded `failed` (`TestAPassingCheckWithNothingVerifiedIsNotASuccess`).
6. Otherwise `failed`, "finished without a verified deliverable".

A conduct pass never counts toward success: it means nothing was refused, not that the work was done, and letting it carry a pass would turn "refused nothing" into evidence of work. `partial` belongs on the gate, not on the job's state, because it qualifies a success and does not stand beside it. A partial success is `succeeded`, `JobView.partial` is true only for a `succeeded` job whose gate 2 is `partial`, and a failed job with a partial gate 2 reports failed. No state, transition, count or quota changes. A conduct summary is not recited on a success.

### Recording, and what the verdict reads

- The gates live in their own column (`verdict`), not in `Error`, because a succeeded job has a verdict and a client that renders `Error` as a failure would show every success as one. The summary goes to `Error` only when the job did not succeed. `gatesNote` writes one `- gate: outcome (detail)` line per gate and `ParseGatesNote` reads them back (`TestTheGatesSurviveTheRoundTrip`). The verdict summary opens with the notes for a proxy failure, the wall-clock bound, a repeated-denial stop and failed turns (DL-049, DL-048).
- `delivering` is not a resting state. The verdict moves the job past it, and the sandbox is terminated after the verdict is written, so a failed terminate cannot leave a job at `delivering` with its gates unread. A failed terminate is warned about, and the reconciler's reaper is the backstop. Every kind leaves something inspectable on every failure path, because delivery runs on failure too.
- The verdict reads the whole run from the first event, not from the supervisor's cursor, because a refusal early in a long job is what it must not miss. Its event bound (`MaxVerdictEvents`, 20,000) trims the head, never the tail, since gate 1's evidence marker is the last event a job has. It trims on the short-batch path too, which is where every run ends. A run long enough to trim away every message is judged as if no person wrote.
- The verdict waits for the recorder's final read (`CatchUp`, best effort), because the recorder reads `/message` when a turn ends and a job's last turn is the one turn nothing re-reads. A sandbox that is already gone is judged on what was stored.
- Gate 2 reads stored evidence and the forge, so a redelivery runs it again and can improve a member an earlier pass could not check.

### What the gates protect

Gates 1 and 2 are guardrails on an honest run, not protection against a dishonest agent. The plugin's evidence file is inside the sandbox and every job kind has `shell`, so the agent can append a passing check line to it. Matching spov's marker proves spov wrote the event, not the content. On a `pr` job the agent can edit the check script, and an agent with a shell and a forge token can open a pull request from a branch it did no work on. What is closed is the cheapest forgery: no check command, no gate 1. The verdict's value is catching a refused or incomplete run, never a lying one, and it must not be cited as protection against an active adversary. The boundary is the egress policy and the sandbox (DL-031).

## Rationale

- Two independent findings say the same thing: the exit code lies, and so does the turn's outcome. Anything derived from "did it finish" is the wrong shape. What the agent did is in the parts.
- Reading gate 3 from stored rows keeps the rule that read paths do not touch the sandbox (DL-018) and makes the verdict answerable on any replica, including for a sandbox that is already terminated, which is when a verdict is wanted.
- Checking the pull request from spov's side is the cheap half of taking prompt injection seriously: the one place the agent could most usefully lie is whether it delivered.
- Without a gate that can pass for `pr` jobs, a `pr` job with no check could never succeed. An always-failed verdict teaches readers to ignore it. Giving `pr` a gate that can pass fixes that without loosening what success means.
- A successful job must have something verified, and gate 2 carries success because a check that passes in a job that produced nothing is not a delivery. A known unfinished piece of work must be stated rather than hidden, which is why `unfinished` makes a success partial. spov's own failure is never the job's failure.

## Measurements

- S3: a `permission.evaluate` deny leaves a tool part with `executed: false`, `state.status: "error"` and `state.error.type: "permission.rejected"`, and the turn itself finishes `stop`. Re-run: `go test -tags integration ./internal/sandbox/ -run PluginDecidesPermissions`.
- S6: a person's refusal through `POST /api/session/:id/permission/:requestID/reply` with `reject` leaves the same part shape with `state.error.type` `aborted` and the message "The user declined this tool call". Re-run: `go test -tags integration ./internal/sandbox/ -run S6PermissionRepliesAndTheirEffects`.
- Eight stored parts from one real run (glob, glob, shell, read, execute, shell, shell, read) all had `executed=false`: seven `status=completed`, and one read with `status=error` and type `permission.rejected`. So `executed` is false on successes too. Re-take this on an OpenCode bump.
- An edit whose old and new strings were identical produced error type `tool.execution` ("No changes to apply: oldString and newString are identical"). Without the by-name exclusion, gate 3 would record that run as refused and fail a job that had done its work and pushed. Re-run: `go test ./internal/jobs/ -run TestARuntimeToolErrorIsNotARefusal`.
- A timed-out check: `sleep 30` under a 300 ms bound, killing the shell only, resolved the plugin's promise in 303 ms, and the plugin process then stayed alive for 29,958 ms because the orphan held the stdout and stderr pipes. Killing the process group fixes it. Re-run: `go test ./internal/opencode/ -run TestATimedOutCheckStopsWhatItStarted`.
- `sh -c ./missing.sh` exits 127, and a file that is not executable exits 126; neither is a failing suite.
- `permission.asked` carries its request ID at `data.id`, and only `permission.replied` carries `requestID`. Re-run: `go test -tags integration ./internal/server/ -run SF1Asks -v`.

## Consequences

- A `pr` job can succeed on its own evidence, on a deployment that has only user-tier credentials, without a check command.
- `blocked` means what it says, that the run could not proceed. Without that rule it would be reachable by any single refusal, which would make it common and unreadable.
- A mostly-blocked run succeeds if one call ran and a gate passed. That is the accepted cost of having no threshold, bounded by what the gates verify: a report must exist, and a pull request must be open or merged on the forge.
- Every repository-relative check configuration must be written `./<repo>/...` or given `--landing <repo>`; otherwise it fails with a clear reason instead of being silently unchecked.
- A person who steers a job with a proposed check loses that check as a deciding gate, and the job can still succeed on gate 2.
- Gate 3 differs from the supervisor in one case. A turn ending settles an earlier request for the supervisor but not for gate 3, so a job with two requests open, one dropped by a turn end and the other answered, is released and then judged parked. Jobs do not ask at the pinned build (DL-040), so this cannot arise until they do.
- When a pass releases a blocked job to running it also releases the plugin's loop, as Resume does (`releaseLoop`, `TestAnAnswerThatReleasesAJobReleasesItsLoop`; DL-054), so a verdict never fails a job for a park spov released it from.
- The verdict is a second consumer of the stored message shape, which is inferred, and of the event shapes, which were measured. Pin both against captured frames.
- Metrics: `spov_job_gates_total` carries the `partial` result, and `spov_job_deliverables_total{kind,status}` is recorded once per job where the verdict is written (DL-011).

## Known gaps

- The evidence file is the agent's to write, and a proposed check that always passes would carry gate 1; nothing detects either.
- Gate 3 and the supervisor disagree on whether a turn ending settles a permission request, as described in the consequences.
