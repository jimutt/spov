## Context

A job's sandbox ends when the job is delivered (DL-045, DL-050), and gate 2 judges a pull request or the reports collected from `/workspace/out` (DL-050, DL-051). A `sync` job (DL-100) delivers the repository's state instead, and someone takes it later, with `spov jobs apply` or over the API (DL-102). The user chose, on 2026-11-07, to keep the sandbox until then rather than store an export: the state is read from the sandbox itself. A held sandbox bills, so its life and its count have to be bounded as DL-049 bounds a job's.

## Decision

This amends DL-045 (a job's sandbox ends at delivery, and the quotas), DL-049 (a job's sandbox timeout, and the spend bound), DL-050 (gate 2) and DL-051 (the deliverable).

### Delivery stops the agent first

For a sync job, delivery always calls `EndRun` before it reads the repository. That stops the plugin's loop for good and interrupts the turn, with `resume=false`, in the order DL-049 already requires. So the state that is judged is the state that is taken: nothing changes the repository afterwards. For `pr` and `report`, delivery is unchanged.

### Gate 2

Delivery then reads the repository once (`session.InspectSync`): the branch, `HEAD`, the commit count since the base, the changed-file count, and the size the export would have, measured but never transferred. Gate 2 is:

| Outcome | When |
|---|---|
| `passed` | at least one commit since the base or one changed, added or deleted file, within the export's 32 MiB bound |
| `partial` | the same, but the run ended at its wall clock or the agent declared work `unfinished` (DL-050's partial) |
| `failed` | no commit and no change ("the repository is unchanged since the job started"), or changes over the bound ("the changes are N MiB, over the 32 MiB a sync can take"), which can never be applied |
| `unverified` | the sandbox could not be read |

A history rewritten past the base, where the base is no longer an ancestor of `HEAD`, counts as a change when `HEAD` differs from the base. Gates 1 and 3 are unchanged. The result is one deliverable of kind `sync` with the branch, head commit, commit count, file count and size. Its status is `verified`, `over_limit` or `unverified`.

### The job finishes; the sandbox is held

- **The job finishes.** A sync job that ends `succeeded` or `failed` reaches that state as any job does, and `spov jobs wait` returns (DL-103). Its sandbox is not terminated: it is **held** for its state to be taken. A cancelled sync job is not held. Neither is one whose sandbox had already ended.
- **What held means.** A held job is a sync job in `succeeded` or `failed` whose session is still live with a sandbox. It is a derived fact, not a stored state or flag. It ends however the session ends: an apply, a release (DL-102), the sandbox's timeout, a sidecar that dies twice, the reaper, or a person stopping the session through a path DL-102 allows.
- **The view.** `JobView.sync` is `{branch, head_commit, commits, files, bytes, held, held_until, applied_at, released_at}`.
  - `applied_at` is the only new stored time, set by an apply's release (DL-102).
  - `released_at` is the session's `StoppedAt`.
  - `held_until` is display only: the time the launch reached running (`store.Run.RunningAt`) plus the session's sandbox timeout. It may be up to a launch's duration later than Modal's real deadline, and no check depends on it.
- **The loop is stopped and nobody joins.** A held sandbox runs no agent turns. `Service.Connect` refuses a finished job's session, as the CLI's `joinable` already does, so neither a person nor an orchestrator can change the state between judging and taking it. Steering a finished job is already refused.

### How long it is held

- A sync job's sandbox timeout is DL-049's (its clock, the wall-clock margin and the steering headroom) plus a **hold**:
  - 30 minutes by default;
  - set per job with `spov jobs create --hold <duration>`, `sandbox.job_sync_hold` in config, or `hold` in the request;
  - at least 1 minute.
- When the sum is over the caller's `max_timeout`, the steering headroom is cut first (as DL-049 does), then the hold. An explicit `--hold` that cannot fit is refused at create, as an explicit duration is.
- So a sync job that ran to its wall clock still has its full hold left after delivery, unless the limit cut it. The view's `held_until` tells a script its window.
- A held sandbox's idle timeout equals its timeout, as for every job (DL-049), so nobody needs to be attached.

### Counting a held job

- A held job keeps its job slot until it is released. The job quota counts unfinished jobs plus held sync jobs, and the session quota leaves out their sessions, as it leaves out an unfinished job's. This is DL-049's spend bound kept: with the default limit of 2, at most two job sandboxes bill per person, held or running. A third `jobs create` is refused with the quota's 429 until a held job is applied or released.
- `JobState.Counts()` stays a function of the state alone. The quota query (`store.JobCounts` and the create's count) adds the held case explicitly, with a test that the two agree.

### Everything else that sees a held session

- **The reconciler.** It already leaves a live session that records its sandbox alone (`Once`'s live check). A held session is such a session, so it needs no change, and a test pins it. When the sandbox ends at its timeout, the reconciler stops the session as for any ended sandbox, which is the release.
- **Metrics.** The snapshot labels a held session's kind `job`, as `recordStop` does when it ends (DL-011). An apply or release ends it with a new termination reason, `released`, documented in `docs/metrics.md`.
- **The web.** The session page of a held job shows "Held until 14:30" with the apply command. It replaces End session with **Discard held work** (`POST .../release`, behind `ConfirmAct`'s second press), whose copy says the work is lost unless it was applied.

## Rationale

- Judging the live repository needs no copy of the state. The counts and the measured size tell a delivery from an empty or untakeable one.
- Stopping the run before reading is what makes the judged state and the taken state the same, which terminating the sandbox achieved for the other kinds.
- Finishing the job at once keeps the job state machine and the web's state groups as they are. Counting it against the job quota keeps the spend bound, and an orchestrator learns to apply before it starts more.
- A hold of its own, on top of the timeout, guarantees a window after delivery however long the run took.

## Consequences

- A held sandbox bills until it is applied, released or times out. The job page, `spov jobs` and `spov ls` say it is held (a `held` mark beside `succeeded` or `failed`).
- If nobody takes the state before the hold runs out, it is gone, and the view says it was released without an apply.
- An orchestrator with the default job limit can have two sync jobs outstanding: running or held.
- Gate 2 cannot tell a good change from a bad one. That is the check's job, as for a `report`.

## Implementation notes

**Stopping and reading.**
- In `Supervisor.deliver`/`concludeJob` (`internal/jobs/supervisor_run.go:617`, `:663`), for `JobKindSync`, call the `EndRun` seam unconditionally (today only `stopBoundedRun` does) before the deliverable step.
- Add `session.InspectSync(ctx, h, dir, base) (SyncSummary, error)` beside `ExportSync` in `internal/session/sync.go`. One exec, whose script:
  1. reads `HEAD` and the branch;
  2. counts `<base>..HEAD` when the base is an ancestor (else sets `Rewritten`);
  3. counts `git status --porcelain=v1 -z --untracked-files=all`;
  4. measures the export: builds the same bundle and gzipped tar as `ExportSync` into `/tmp`, takes their sizes, and deletes them.

  It returns `{Branch, HeadCommit, Commits, Files, Bytes, Rewritten}` and no contents.
- The supervisor reaches it through a new function seam, wired in `cli/serve.go` to a `Service` method as `svc.OpenJobOut` is for reports. `internal/jobs` may not import `net/http` or the server.

**Gate 2 and the deliverable.**
- `judgeDeliverable` (`internal/jobs/verdict.go:544`) gets a `JobKindSync` branch per the table above, reading the run's end from the same markers the other kinds use for partial (`MarkerBounded`, the `unfinished` declaration).
- `internal/jobs/deliverables.go`: a sync job's collection step calls the seam once and writes one `store.Deliverable` with `Kind: store.DeliverableSync` (new, `store.go:1540`), `Key: "sync"`, `Owner`/`Name`/`Branch`, and new fields `HeadCommit string`, `Commits int`, `Files int` and `Size` (the existing `int64`, reused for the bytes). Its status is `verified`, `over_limit` or `unverified`. It is gated by `MarkerCollected` like reports, so a broken-off pass collects again.
- Migration `00035_sync_jobs.sql` (shared with DL-100) adds `head_commit text not null default ''`, `commits integer not null default 0` and `files integer not null default 0` to `job_deliverables`, and widens its kind check (`00024:18`) to `'sync'`. Update the sqlc queries, the memory store and `storetest`.
- `DeliverableView` (`internal/server/jobapi.go:175`) gains `head_commit`, `commits` and `files`.

**Holding.**
- `concludeJob` calls `s.terminate(ctx, job)` for every finished job. For `JobKindSync` it does not, unless the job was cancelled.
- `applied_at`: one nullable column on `jobs` (`sync_applied_at timestamptz`) in the same migration, set by DL-102's apply.
- Held is derived in the server: `job.Kind == sync && (state == succeeded || state == failed) && session.State.Live() && session.SandboxID != ""`. Put it in one function (`server.jobHeld`) used by the view, the quota and DL-102's routes.
- `Service.Connect` (`internal/server/connect.go:70`) refuses a finished job's session with 409, naming `spov jobs apply`.

**The hold.**
- Add `Hold time.Duration` to the job request (`hold`, seconds, as `max_duration` is), `--hold` to `jobs create`, and `sandbox.job_sync_hold` to config, with `TestTheConfigurationSampleIsComplete`'s sample.
- Resolve it in `jobClock` (DL-049, `internal/server/jobs.go`) for kind `sync` only, with the cut order above. A hold on another kind is refused with a 422.

**Quota.**
- The job quota's count (`createJobWithinQuota`, `store.JobCounts` and its SQL twin) adds held sync jobs. The session count's exclusion of unfinished jobs' sessions extends to held ones.
- `TestJobCountsAgreesWithTheCountsMethod` gains the held case. Add a new `TestAHeldSyncJobKeepsItsJobSlot`.

**Views and metrics.**

- Add a `released` termination reason in `internal/telemetry/labels.go` and its row in `docs/metrics.md`.
