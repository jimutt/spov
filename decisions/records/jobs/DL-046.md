## Context

An autonomous job needs something that watches it: it provisions the sandbox, opens the job, notices when a turn ends, when the run is parked on a permission nobody answered, when a person steps in, and when the plugin says the loop has stopped. The obvious design blocks on `POST /session/:id/wait` and polls `GET /api/session/:id/permission`. Neither works on the pinned OpenCode build, and polling a sandbox would undo the rule that only the recorder reads one (see DL-018) on the longest-lived sandboxes spov runs.

The supervisor also has to live somewhere. `internal/server` is too large to read as a whole, and a single package cannot refuse an import, so every seam inside it is a convention. The job code is two clusters with very different costs to separate: the code hanging off `*Supervisor` reaches everything through function-typed seams, while the code hanging off `*Service` (creating, provisioning, resuming and cancelling a job) shares many helpers with session launch.

## Decision

### The supervisor reads the store

The supervisor is a River worker. River carries durable execution and retries only; progress already flows as rows the recorder writes (see DL-017). The supervisor learns everything from those stored events:

- A turn ending is a stored event whose name ends in `.execution.succeeded`, `.execution.failed` or `.execution.interrupted` (`TurnEnded`).
- A run parked on a decision nobody answered is a stored `permission.asked`, matched to its answer by request ID.
- The loop having stopped is the plugin's stop marker (see DL-048).
- `steered` and the release of `blocked` are decided from stored rows too. A person's message steers the job when it is delivered (DL-052); a permission answer relayed through spov releases a blocked job once nothing else is pending (DL-054). The sandbox's reply frame names no principal, so the supervisor cannot tell a person's answer from the job's own plugin answering, and it infers no release from `permission.replied` alone; it only counts those frames. A job's plugin does not ask at the pinned build (DL-040), so `blocked` is reached only when its permission hook failed to install.

`POST /session/:id/wait` and `GET /api/session/:id/permission` are used nowhere. The recorder reads `/api/event`, because the durable per-session log returns only its watermark.

The supervisor touches the sandbox otherwise only for lifecycle: create, issue the run after readiness, lock egress down, terminate. These are not reads, so `TestNoReadPathTouchesTheSandbox` still holds. The one read exception is the job-end visit that collects reports, evidence and the outcome file (DL-051).

### How a pass reads events

`Supervisor.follow` is a pure fold over stored rows: it writes nothing and touches no sandbox. `signalFor` reads one event. spov's own markers are matched by name and by `source`; the sandbox's `permission.asked` and `permission.replied` are matched by exact name, and a spov marker is never read back as the session's voice. The sandbox chooses frame names, so a suffix rule would let a frame it invents drive the state machine. `TestSignalForNamesTheSupervisorActsOn` pins that `session.permission.asked` and `session.permission.replied` signal nothing. Turn-end events are the one suffix match, and they only count turns.

`Supervisor.applyFollow` writes the result:

1. It re-reads the job row inside a transaction and checks the transition against the state the row has now, not the state the pass started from. A cancellation that lands mid-pass is not resurrected. A row that moved under the pass is left alone with a warning. The store's own state machine refuses the illegal write as a second line of defence (`TestApplyFollowDoesNotResurrectADecidedJob`, `TestApplyFollowRefusesAnIllegalTransition`).
2. It writes the cursor in the same transaction as the state. The cursor is `jobs.cursor` (`Job.Cursor`) and advances over every event, signalling or not, otherwise the uninteresting frames of a busy session would be re-read forever.

The cursor is durable because the supervisor's conclusions are not idempotent. Re-reading an old `permission.asked` or a person's inbox item would re-derive `blocked` or `steered` and undo the act that released the job. Both are legal transitions, so neither the machine nor the store would refuse them. Without a persisted cursor a person could never release a job while the supervisor ran (`TestAHumanReleaseSurvivesTheNextPass`, `TestTheCursorAdvancesOverUninterestingEvents`).

### Gaps

A recording gap is "unknown", not "nothing happened". The gap marker is read back by name and `source`, as are the resume, interrupt and answer markers (see DL-054); a spov-written event that borrows a sandbox frame's name signals nothing (`TestASpovMarkerSignalsNothing`). A gap moves no state, events after it are read normally, so a park that follows a gap is seen, and the pass reports the gap. A state concluded across a gap is still written, and the row's `Error` carries `GapNote` ("recording gap: the state was concluded from an incomplete range, and may be stale"). An `asked` before a gap may have been answered inside it. Suppressing the write would leave a genuinely parked job reading `running` with nothing to prompt anyone to look, which is worse than a stale `blocked` that a person can release (`TestAGapIsUnknownAndMovesNothing`, `TestAStateConcludedAcrossAGapSaysSo`, `TestACleanConclusionCarriesNoGapNote`).

### Opening the job

`openJob` (in `internal/server`) issues the job's first turn with `POST /api/session/:id/synthetic` and `resume: true`, never `/prompt`. Nothing of spov's is ever a `user` inbox item. A prompt would be indistinguishable from a person typing, and every job would enter `steered` on its own first turn. The synthetic arrives as `session.inbox.enqueued` with `item.type: "synthetic"`.

### River configuration

River's defaults are wrong here: `JobTimeout` defaults to one minute and there is no leasing, so a rescued job can run twice. An attempt is one supervisor pass, which ends by snoozing to be redelivered, so the timeout bounds a pass and not the job's life. `NewRiverClient` sets the timeout (`SupervisorJobTimeout`, `config.DefaultLaunchTimeout` of 5 minutes plus 30 minutes, and `TestOnePassHasRoomToProvision` checks it covers a launch), the rescue horizon (`SupervisorRescueAfter`, the timeout plus an hour, because River requires it to exceed the timeout), the queue, `SupervisorMaxAttempts` (3, which snoozes do not consume, where River's default of 25 would keep re-provisioning sandboxes for a job whose goal is broken) and `SupervisorMaxWorkers` (10 per replica, which is a spend ceiling as much as a concurrency one). `JobArgs` carries only the job and organisation IDs, because the row is the truth. Its `InsertOpts` pin the queue and retry budget and make the queue unique by args, so a periodic re-queue cannot race a job already being worked.

The sandbox is tagged with the job ID (`sandbox.JobTags`) and `findJobSandbox` adopts a live one by that tag, so a duplicate delivery re-attaches instead of creating a second billable sandbox (`TestARedeliveredAttemptAdoptsRatherThanLaunchingAgain`). A stopped sandbox is not a candidate; of several live ones the oldest is kept, and the supervisor terminates none (choosing among them is the reconciler's). A listing that fails never becomes a launch (`TestAListingFailureDoesNotBecomeASecondSandbox`). A restarted server finds its jobs the same way, since Modal offers no lifecycle events: `Supervisor.Sweep` re-queues every unfinished job except a delivering one every `SweepInterval` (5 minutes) on the leader, and the queue's uniqueness and the tag make that safe.

River brings its own migrator to the same Postgres. goose owns every spov table and River owns every `river_*` table, and neither migrates the other's. `spov serve migrate` never touches River's tables, `jobs.MigrateRiver` runs at server start and is never pointed at spov's, and wrapping River's DDL in goose files would fork it from the version the library expects. River runs on the same database and inherits its connection handling.

### The package cut

The job supervisor lives in `internal/jobs`, cut at the receiver rather than at the filename. What hangs off `*Supervisor` (the run loop, the job state machine, the three gates, the prep pass, the River worker and the sweeps, with `verdict.go` and `toolparts.go`) is in `internal/jobs`. What hangs off `*Service` (`jobs.go`, `jobrun.go`, `jobapi.go`, and `supervisor_open.go`, despite its name, because every caller of its functions is `jobrun.go`) stays in `internal/server`, and so does job creation.

The supervisor reaches the server only through function-typed fields on `Supervisor`: `Provision`, `Open`, `Adopt`, `Wake`, `OpenOut`, `Evidence`, `Outcome`, `CatchUp`, `Terminate`, `FindPullRequest`, `Prepare`, `Mark`, `Loop`, `EndRun`, `Queue` and `Snooze`. Importing `internal/server` from `internal/jobs` is an import cycle, and the compiler rejects it with "import cycle not allowed". That is stronger than the depguard rules in `.golangci.yml`, which work at import level and cannot police a boundary that is not a package. Pieces both sides need are in their own packages:

- `internal/redact` holds the credential filter (`Error`, `Text`). The server calls it in a dozen files and the supervisor in many places that write an error into a log or the store; two copies would drift.
- `config.DefaultLaunchTimeout` is in `internal/config`, because `ProvisionTimeout` and `SupervisorJobTimeout` derive from it and a duplicated literal would silently break that link.
- `internal/jobs/jobstest` holds the shared test helpers. `SeedJob` and `PathTo` encode the job state machine's legal transitions, so a second copy could let one side seed a route the machine does not permit.

## Rationale

- A supervisor that polls a sandbox reintroduces the idle-clock billing problem on the longest-lived sandboxes spov runs (DL-029). Everything the supervisor needs is already written down by something connected, and a second reader would give a worse answer for more work.
- Adopting by tag instead of trusting a lease turns River's weakest guarantee into something Modal can answer definitively.
- Matching the permission and inbox frames by exact name keeps a sandbox that invents event names from driving job state.
- An endpoint's shape is read from the server's own `/openapi.json` before it is called. A guessed URL makes a 404 ambiguous between a wrong path and no such mechanism, and a guessed body makes a 400 ambiguous between a wrong key and a wrong endpoint. The other published route, `POST /api/session/:id/permission`, creates a request and wants `{action, resources}`; it does not answer one.
- A package boundary is enforced by the compiler; a convention is not. Cutting by receiver took the part with the cheap seam first and left the `*Service` half, which shares helpers with session launch, until something forces a launcher seam out of `Service`. Cutting by filename prefix would have moved `supervisor_open.go`, whose callers are all `*Service`, and left `verdict.go` and `toolparts.go`, which are pure `*Supervisor` code.

## Measurements

- S3 (build 0.0.0-beta-18866): `POST /session/:id/wait` on a session parked on a permission never answers, not slowly but at all.
- S-B: the durable per-session log returns only its watermark.
- S5 (build 0.0.0-beta-18684): `POST /api/session/:id/synthetic {text, resume: true}` answers 200 and arrives as `session.inbox.enqueued` typed `synthetic` with `delivery: "steer"`, and a turn runs and finishes. `permission.asked` carries no `durable` marker and so no `seq`. `POST /api/session/:id/permission/:requestID/reply {reply}` answers 204 and raises `permission.replied` whose `requestID` matches the asked frame's `per_` ID. Re-run: `go test -tags integration ./internal/sandbox/ -run S5SyntheticLoopAndPermissionAnswer`.
- S6 (build 0.0.0-beta-18684): `permission.replied`'s `data` is exactly `{sessionID, requestID, reply}` with no principal. After a 204 reply the turn resumed and finished, so an answer un-parks the run. `Permission.Reply` is `once`, `always` or `reject` (read from the server's `/openapi.json`), and a `reject` raises `permission.replied` with `reply: "reject"`. Re-run: `go test -tags integration ./internal/sandbox/ -run S6PermissionRepliesAndTheirEffects`.
- Nullable `seq` against Postgres: NULLs are distinct in a unique index, so a row without a `seq` drops out of `events_opencode_seq` while a real sequence is still deduplicated. This is the store's side of the ephemeral frames the supervisor reads (see DL-017). A contract case that writes the same `seq` twice pins it. Re-run: `go test -tags integration ./internal/store/postgres/...`.
- Coupling at the package cut (a `go/ast` pass over identifier references in both directions): the rest of `internal/server` referred to about 8 symbols of the 15 job files, which referred to about 30 of the server's, 13 of them `*Service` methods.
- Size of the cut: about 5,700 non-test and 6,100 test lines moved, 29% of `internal/server`. (Approximate.)

## Consequences

- The supervisor's freshness is the recorder's plus the feed's. A job's state can lag reality by that much, which matters for a cost cap and little else. A leader failover pauses the recorder, and so the supervisor's eyes, until a new leader takes over; the gap marker makes that visible.
- A new frame name the supervisor should act on has to be added to the recorder's `ephemeralNames` as well (DL-017); `signalFor` tracks that list.
- Job logic has a two-part answer: supervision is in `internal/jobs`, creation and the HTTP surface are in `internal/server`.
- Three names exist on both sides of the wall: `MarkerGap`, `MarkerEvidence` and `turnEnded`. `internal/server/jobsboundary_test.go` pins each to its counterpart from the side that sees both (`TestTheGapMarkerNamesMatch`, `TestTheEvidenceMarkerNamesMatch`, `TestTurnEndedAgreesAcrossThePackages`), and each fails on planted drift. `oneLine` is duplicated on purpose. `SyntheticRole` and `TurnEnded` are exported for tests only.
- Most of the exported API of `internal/jobs` is what non-test code in `internal/server` and `internal/cli` uses (including the CLI's River wiring: `MigrateRiver`, `NewRiverClient` and the worker); the rest is needed by tests across the boundary. `GateMechanical`, `GateDeliverable` and `GateClassification` appear in a stored verdict and `GapNote` in API text, so those are public in substance.
- A test that reads Go source off disk as text turns a move into a missing-file failure instead of a build error. `TestTheQueueSeamsAreWiredWithRiver` reads `serve_river.go` and the worker this way, and only the full `check.sh` runs it. Check any `os.ReadFile` of a Go file after moving code.
- `scripts/coverage-exclude.txt` must name `internal/jobs` paths. An entry for a path that does not exist excludes nothing and reads like a working entry. `internal/jobs/jobstest/jobstest.go` is listed as test furniture.
- A test that straddles the wall is rewritten with a direct writer rather than widening the API for a test.
- Moving the package back would cost a rename and an import rewrite, unlike splitting the `*Service` half, which would fix an interface shape.

## Known gaps

- `Service` (about 48 methods) and `Deps` (about 30 fields) are untouched by the cut. If the difficulty of reading `internal/server` is mostly that `Service` does too much, the cut does not help with that.
- Job creation, provisioning, resume and cancel stay in `internal/server`, so job code lives in two packages until a launcher seam is forced out of `Service`.
- The sandbox never says who answered a permission, and no principal can be recovered from the frame, so a release is only ever inferred from spov's own answer marker.
