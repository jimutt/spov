## Context

A job produces one or more deliverables: pull requests (merge requests on GitLab) for a `pr` job, Markdown reports for a `report` job. A job can open two pull requests in one repository, and supporting ones in other repositories it was launched with, possibly on other forges. It can write several reports. Selecting three repositories does not mean three pull requests are expected.

The inventory has to exist however the run ends, including at its wall clock, when the agent never calls the completion tool. It has to survive a retried delivery and one bad read among good ones. A listing must show the set without carrying report bodies, which can be 10 MiB each. Every client needs to name each pull request by its repository and forge.

## Decision

**A `pr` job records each pull request as it opens it; a `report` job's reports are the Markdown files in its out directory. spov checks both at delivery and stores the inventory in `job_deliverables` and the collected bytes in `job_files`, apart from the job row.**

### Pull requests

- **The tool.** The plugin registers `spov_pull_request` for `pr` jobs only, with required arguments `repository` and `branch` and an optional `withdrawn`. It writes the evidence line `deliverable.recorded {platform, repository, branch}` and does not end the run. Like the completion tool it declares `options: {codemode: false}`, returns `{content}` and is in no allowlist. The completion tool says nothing about pull requests. `opencode.PullRequestTool` and `opencode.DeliverableEvent` in Go and `CONFIG.pullRequestTool` and `CONFIG.deliverableEvent` in the plugin must agree (`TestThePullRequestToolMatchesThePlugin`). The prompt tells the agent to call the tool right after opening each pull request, and that one it does not record is not part of the result. On GitLab the repository is the whole project path, and the tool's description says merge request there.
- **The repository** is named as the workspace note names it: `owner/name`, or `host/owner/name` when two selected repositories on different forges share the name. The plugin strips a scheme, a `.git` suffix and a trailing slash, matches without regard to case, and records the configured slug. It refuses, with an explanation in its reply, a repository that was not selected at launch. The server drops such a line too (`recordedPullRequests`), because the evidence file is the agent's to write. The selected list is fixed at launch: `git_access=all` widens the sandbox's credentials, not the job's repositories.
- **A member** is one (repository, branch) pair. Recording a pair twice is one member. The branch is trimmed and loses a leading `origin/`.
- **Why record as it goes.** The inventory then exists whenever the run ends. Naming the repository keeps spov from guessing: asking every selected repository about every branch would credit a pull request the agent never meant.
- **Delivery** resolves the job owner's forge for each member's platform (`svc.JobOwnerForge`) and asks it for the pull requests from the branch (`FindPullRequestVia`, which uses the selection whose platform name matches the member's, so the same `owner/name` on two forges is asked on the right one). A forge that answers "none" makes the member `missing`. An error or `git.ErrUnsupported` leaves it `unverified`. Recording reads only stored evidence and never rewrites a stored member, and `checkPullRequests` asks only about members that are neither verified nor withdrawn. Both run on every delivery pass, so a redelivery can improve a member an earlier pass could not check.
- **Any state counts.** GitHub, GitLab and Forgejo/Gitea are asked for pull requests from the branch in every state, from the repository itself and never a fork (the GitHub query fixes the head owner to the repository's owner, and reads the newest 30), and the best answer decides: open, then merged, then closed (`git.bestPullRequest`). Open or merged is `verified`, and a merged one says so in its detail. Closed without merging is `missing` with the detail "closed without merging", counted apart from not found. A merged or closed pull request opened before the job was created, with a minute allowed for the forge's clock, is an earlier job's on a reused branch name and counts as none; an open one counts at any age.
- **Merge requests.** On GitLab the check is `GET /projects/<path>/merge_requests?state=all&source_branch=<branch>` with the owner's credential, and only a merge request whose source and target project are the same counts, so a fork's does not. The number is the IID. A member records its forge's kind when the supervisor records it, from the session's recorded credentials (`job_deliverables.forge`; a later write without one keeps it), and `DeliverableView.forge` carries it. Wording follows the kind: "Merge request !12" on GitLab, "Pull request #12" elsewhere, from `git.ChangeNoun` and `git.ChangeRef`, mirrored by `changeNoun` in `internal/jobs/verdict.go` and by `changeNoun` and `pullRequestName` in `web/src/lib/deliverables.ts`. Change them together. Gate 2's detail says merge requests when every member is GitLab's. The job kind stays `pr` and its label "Pull request"; the form says it opens a pull request, a merge request on GitLab. A `pr` job with a GitLab repository gets `mergeRequestNote` on its goal, saying a pull request there is a merge request, opened with glab and recorded with the same tool. A member recorded without a forge (a session whose credentials were not recorded, such as one adopted after a failed resolution) is worded as a pull request, and a later write does not fill the forge in.
- **Withdrawal.** The agent can call the tool again with `withdrawn: true` for a branch it recorded; a later record of the same branch without the flag takes the withdrawal back. Withdrawing a branch that was never recorded withdraws nothing. A withdrawal is honoured only when a person's `user` inbox item reached the job after the branch was first recorded, by frame time, both on the sandbox's clock (`withdrawalHonoured`); a record with no time honours nothing. The member is then stored with the status `withdrawn`, gate 2 does not ask the forge about it, judges the rest without it and names it ("1 withdrawn at the reader's request"). A set whose every member was withdrawn has nothing verified and fails as a job that recorded nothing. A withdrawal with no later message from a person is judged as recorded, and gate 2's detail says the agent withdrew it unasked, counted from the stored members so the detail and the stored statuses agree. The case this serves is a person correcting a job ("fold the docs into the API branch and close the docs pull request"): without it the closed pull request would stay on the list as missing though everything asked was done. The `withdrawn` status is carried by the store, the API, the web wording and the deliverables metric's `status` label. How gate 2 weighs the members is in DL-050.
- **The outcome file.** The evidence file has a line per permission evaluation, and delivery reads only its first 256 KiB, so a pull request recorded after a few hundred tool calls would be lost. The plugin copies the lines that decide an outcome (`deliverable.recorded`, `completion.declared`, the check and `loop.stopped`) to `/tmp/spov-outcome.jsonl` (`opencode.PluginOutcomePath`). Delivery stores it as `jobs.MarkerOutcome`, and every reader takes a line from either marker; record lines come from the outcome marker when it exists, since it keeps every line however long the run, so a truncated evidence file never has the last word. Gate 1's check is protected the same way. A sandbox gone before delivery (`jobs.ErrSandboxGone`) cannot say what it recorded: that is a failed collection, which gate 2 reads as unverified, never as "recorded no pull request".

### Reports

- **Discovery.** Delivery lists `/workspace/out` (`opencode.OutDir`) through OpenCode's `GET /api/fs/list` and takes every regular file directly in it whose name ends in `.md` (in any letter case), in file-name order. Subdirectories hold supporting files and are not searched for reports. `report.md` is an ordinary report. The directory is the declaration: no tool call is needed, so a run ended by the wall clock still delivers what it wrote. Dotfiles are skipped, and a symlink never appears in the listing.
- **Title.** The first `# ` heading (indented up to three spaces, without closing `#`s or a CRLF's `\r`), cut at 200 characters, else the file name without `.md`.
- **Limits.** One file is at most 10 MiB. Everything one job delivers, reports and images together, is at most 100 MiB in at most 1,000 files. A report is collected whole or not at all: a file over 10 MiB is recorded `over_limit`, and when the total would pass 100 MiB the files are collected in name order and the rest are recorded `over_limit`. Every report is collected before any image so images cannot crowd a report out, and a report's member is written after its images, because a verified member is never rewritten.
- **Images.** Only a PNG, JPEG, GIF or WebP file, at most 10 MiB, that a collected report links by a relative path staying inside `out/` is collected (`jobs.ImageLinks`, `jobs.OutRelative`), typed by its first bytes, never by its name. An image no report links is not collected, and nor are remote images, `data:` URIs, absolute paths and links that leave `out/`. SVG is never collected, because served from spov's origin it could run script in the dashboard. Collection reads links generously, reference definitions and code-block examples included, since a false match costs one read of a file that must still be an image under `out/`.
- **Failures.** A failed listing marks collection failed and gate 2 reads it as unverified. A sandbox that has gone is a failed collection, never an empty directory. A failed read leaves that one member `unverified` and does not stop the others.
- **The prompt.** The report note tells the agent to write each report as its own Markdown file directly in `/workspace/out`, named for its subject, with its title as the first heading, that files elsewhere are not delivered, and how to link images. The write roots (`/workspace/out` and the scratchpad) are unchanged. The entrypoint creates `/workspace/out` at start.
- **Where it reads.** `/api/fs/list` is in `contract.Used`, and the fakes that answer it are wrapped in `contract.Checked`. Collection is one listing and one read per file inside delivery's single sandbox visit, so the rule against reading a sandbox on a path a browser can reach is unchanged (DL-018).
- **A report that lost a shown image is partial.** An image a reader would see is an inline image outside fenced code, or a reference definition such an image uses (`jobs.ShownImages`). Losing one makes the report partial, and losing a link that is only read generously does not; either is named in the report's detail. The causes are: not found, over 10 MiB, unreadable, not a supported type, over the job's total, or not stored. The member stays `verified`, because its text was collected and stays readable and downloadable, with `store.Deliverable.ImagesLost` set (`job_deliverables.images_lost`). Gate 2 counts it as qualifying, as it does an unverified member, so a set that would pass reads partial and the job succeeds partly. The deliverables metric's status label is unchanged. A pass that finds the sandbox gone rewrites unverified members from the stored files without the flag; that set is partial anyway, because the broken collection qualifies gate 2.

### Storage

- `job_deliverables` holds one row per member, keyed `(job_id, key)`. The key is `pr:<platform>:<owner>/<name>:<branch>` or `report:<path>`. A row has a kind (`pr` or `report`), a status (`verified`, `missing`, `unverified`, `over_limit` or `withdrawn`) and a detail line. A pull request row adds platform, forge, repository, branch, number, URL and title. A report row adds its path under `out/`, title and size.
- `job_files` holds the collected bytes, keyed `(job_id, path)`, with content type, size and a `bytea` body. Reports and the images they link both live there, so one file endpoint serves both. A listing never loads a body.
- `jobs.unfinished` holds what the agent declared it left undone, cut to 4,000 characters.
- **Writes only improve.** A status write is ignored when the stored status is `verified`; a file is inserted once (`on conflict do nothing`). A retry collects only what it lacks and a later failure never replaces an earlier success, so delivery is idempotent per member. The memory and Postgres stores implement the same rules, and `storetest` asserts them.
- Postgres's `PutDeliverable` and `PutJobFile` are single statements that select the job by organisation, so a member can never be filed under another organisation's job. Zero rows written means the member or file was kept, or the job is not the organisation's; a `JobExists` read tells the two apart.
- **Collection has its own marker**, `jobs.MarkerCollected`, written when it finishes. Only it stops a later pass collecting again; the evidence marker is written before collection, so a pass that broke off would otherwise never collect again. A later collection that works clears an earlier failure. When a pass cannot read the sandbox it writes a member for every report an earlier pass stored (`storedMembers`), so a stored report is delivered whatever happened afterwards (`TestAPassThatBrokeOffCollectsAgain`).

### Job views, the file endpoint and the clients

- Every job endpoint returns the same `JobView`, carrying `deliverables` (kind, status, detail, and for a pull request its repository, platform, forge, branch, number, URL and title, or for a report its path, title and size), `partial` and `unfinished`, and never a body (`TestJobViewsCarryTheInventoryAndNoBody`). The listing carries the inventory too, bounded by the file count. `deliverables` is always present and is empty before anything is delivered.
- `GET /api/v1/jobs/{id}/file?path=<path>` returns one collected file with its stored content type (a report is `text/markdown; charset=utf-8`), `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`. `download=true` adds `Content-Disposition: attachment`, naming the file `spov-<job>-<path with slashes as dashes>`. The same ownership rules apply as for reading the job, and it reads only the store. The path is matched against stored keys, never joined to a filesystem path. It is a query parameter because huma's path parameters do not span slashes. It is not a huma JSON operation and is documented like the other raw routes. A collected file is stored once and never replaced, so a 200 carries `Cache-Control: private, max-age=31536000, immutable`.
- A report downloaded with `download=true` that links collected images arrives as a zip of the report and those images at their paths, built by the server (`Service.ReportImages`, `Service.WriteReportBundle`, named `spov-<job>-<path>.zip`), streaming one image at a time so a 100 MiB job is never held in memory. The bundle is one link in every client. The browser's rendering of those images is in DL-063.
- `spov jobs show` prints one line per deliverable (status; the pull request's URL and repository, or the report's title, path and size), then `unfinished` and the gates. `spov jobs report <job> [<path>]` prints a report's Markdown: the only report, or a list when there are several. It takes no `--json`; `--json` on `jobs show` prints the API view (DL-023). `spov jobs report --save <dir>` writes the report and the images it links at their paths: the report's path is checked with `jobs.OutRelative` before anything is written, and the image paths come from `jobs.ImageLinks`, which applies the same check. `jobs report` must be in the command tree that `TestEveryNamedCommandExists` checks.
- The session page's job panel lists each pull request as a link with its repository and number, and each report with its title, size, Read and Download. A partial success says so beside the state, and `unfinished` is shown. The jobs page's outcome line names the single pull request or counts several ("3 pull requests", "2 reports"). The number is a field, so nothing parses it out of gate 2's detail.

## Rationale

- Recording as it goes means the inventory exists at the wall clock, on exactly the runs whose partial work most needs finding. A list given to the completion tool would be empty there.
- The directory is the declaration for reports, so an agent cannot forget to register one it wrote.
- The limits are set so that nobody hits them by accident. They bound one job's storage, and the file count stops delivery from turning into thousands of sandbox reads. A report cut off at a byte limit looks complete in a preview, while a member marked over the limit says what happened.
- A merged pull request is the best outcome a pull request can have, so it must verify. The strict rule about withdrawal exists because the evidence is the agent's to write: an agent free to drop members could close a broken pull request and claim a clean success.
- Keying each member makes delivery idempotent per member, not per job. Separating the inventory from the content keeps listings cheap, and keeping bodies out of every view makes a listing's cost independent of report sizes.
- Verified-but-flagged for a report with lost images keeps the text readable and downloadable, while the outcome, not only a detail line, tells the reader that what was delivered lacks parts the agent produced.
- This is a guardrail on an honest run, not a defence against a dishonest agent. An agent can record a pull request from a branch it did no work on, and with the sandbox's shell it could raise a `user` inbox item through its own OpenCode to make a withdrawal count. It could already leave a broken pull request out by never recording it. Keeping a withdrawn member visible as `withdrawn` means nothing leaves the result unseen.
- The file endpoint serves stored bytes the agent produced, so it names the type it stored, forbids sniffing and sandboxes the response.

## Measurements

- **Outcome file.** The evidence file is read to its first 256 KiB (`MaxEvidenceBytes`); the outcome lines are copied beside it so a late record survives. `go test ./internal/jobs/ -run TestTheOutcomeFileOutlivesTheEvidenceBound`.
- **S-D1** (`TestIntegrationSD1ReportFilesShape`, one sandbox, no model, OpenCode 2.0.22) ran in 16.7 s. `go test -tags integration ./internal/sandbox/ -run SD1 -v`. It measured:
  - `/api/fs/read` returns binary files byte for byte, served as `application/octet-stream`, for 16,384 bytes covering every byte value and for 3 MB of random data.
  - Throughput: a 12 MB file came back whole in 7.2 s, about 1.7 MB/s, so 100 MiB takes about a minute inside one delivery pass.
  - `/api/fs/list` with `location[directory]` gives paths relative to that location, a directory's path ends in `/`, and dotfiles are listed (spov skips them). A symlink is left out of the listing altogether, and reading one directly answers 500.
  - A missing out directory answers 500 on listing, the same as a broken read, which is why the entrypoint creates `/workspace/out` at start and delivery reads any listing failure as a broken read.

## Consequences

- A change to a status, a key or a limit touches the plugin, the supervisor, both stores, the API and the web together. The names shared by Go and the plugin (the tool, the evidence event, the outcome path) need a guard test each, as the other shared names do.
- Gate 2 lists pull requests of every state, which can mean more pages on a busy repository than an open-only query.
- The deliverable wording is chosen from the member's recorded forge kind everywhere, so a new forge kind needs a decision in `git.ChangeNoun`, `git.ChangeRef` and their web mirrors.
- Guard tests: `TestThePullRequestToolRecordsASelectedRepository`, `TestTheRecordedPullRequestsReachTheJob`, `TestTheReportsNeverLandInARepository`, `TestAReportJobIsToldWhereToLeaveItsReports`, `TestEveryReportAndItsImagesAreCollected`, `TestAPassThatBrokeOffCollectsAgain`, `TestAWithdrawalNeedsAPersonsMessageAfterTheRecord`, `TestGateTwoLeavesAWithdrawnPullRequestOut`, `TestTheOutcomeLinesAreKeptApart`.

## Known gaps

- Stored content lives as long as the job row, up to 100 MiB per job, so retention is an open question once there are many jobs.
- A pull request is judged by branch, so an agent can record one from a branch it did no work on.
- A running `pr` job gets its plugin when its sandbox is created, so a plugin change reaches only jobs started afterwards; finish running `pr` jobs before upgrading a server across a change to the recording tool.
