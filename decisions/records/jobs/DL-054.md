## Context

`steered` and `blocked` are suspensions of a job, not ends. In `steered` the loop stops continuing, the sandbox stays up and the person owns the session. In `blocked` the agent is parked on a permission question. Leaving either is an explicit act, never automatic (DL-045).

Two independent mechanisms stop a job, and they share no state:

- The plugin's continuation loop fires on every `session.execution.succeeded` and checks only `loop.stopped` and `loop.paused`, never who caused the turn. A human's message starts a turn like any other, so the plugin would continue from it. `loop.paused` is in memory and is set by the plugin's `/spov-goal pause` command or by a hold (DL-052).
- `steered` is the server's reading of a stored inbox item or of its own interrupt marker (DL-053). The plugin never learns of it.

A resume that moved only the row would leave a job reading `running` whose loop is paused, indistinguishable from a long turn. A resume that only released the plugin would leave the row `steered`, so the supervisor would never deliver it.

## Decision

### One act, and `steered` always means a held loop

`POST /api/v1/jobs/{id}/resume` (`Service.ResumeJob`; `spov jobs resume <job>` is an ordinary client of it) clears the plugin's pause and moves the row `steered -> running`. When the supervisor writes `steered` it also pauses the plugin (`pauseLoop`). The server's state therefore always implies the plugin's: `steered` means the loop is held and `running` means it is not.

The reverse is deliberately not so. `/spov-goal pause` typed by a person moves no row, because a pause is a person looking at something, not a takeover, and a job concluded or suspended out from under them is what a pause exists to avoid. The server's row is what other replicas, the listing and the verdict read, so it must never be less true than the sandbox's flag; the flag may be more paused than the row.

- **The command route.** The plugin is released and held through its own command endpoint, `POST /api/session/:id/command {"name":"spov-goal","text":"resume"}` (`sendLoopCommand`), which answers 204 and runs the handler asynchronously. An accepted request means the sandbox took it, not that the plugin acted: a sandbox whose plugin never loaded answers 204 too. A resume clears `loop.paused` and nothing else; `loop.stopped` is final.
- **Pausing on `steered` is best-effort.** A pause that cannot be delivered leaves the row `steered` and warns. `applyFollow` reports the state it wrote, and the pause keys on that, not on the pass's conclusion, because the two differ when the store refuses a conclusion (`TestAPassThatDidNotWriteSteeredPausesNothing`).
- **Order: plugin first, row second.** A steered job's loop is always held, so a resume that cannot release it leaves the row untouched and reports the failure. Both orders can fail. Plugin-first can leave a running loop under a `steered` row after a database failure that follows a successful POST; the caller's retry closes that window, so a failed resume must be retried, and the API says so. Resuming is idempotent.
- **The states.** A job that is neither `steered` nor `blocked` is refused with a 409 naming its state (`ErrJobNotResumable`). A steered job whose sandbox has gone answers 409 with the session-stopped problem type, since `SetJobLoopPaused` returns `ErrSessionNotRunning` and a steered job's release must succeed (`TestResumingASteeredJobWithNoSandboxSaysSo`); a dead sandbox will never take a retry, so that job is left to the backstop (DL-045). A blocked job's release is best-effort, so it resumes whatever the sandbox answers. `SetJobLoopPaused` takes the caller's principal so the connection mint is audited against whoever asked; each resume mints a connect credential and is bounded by `MintsPerMinute`.
- **A resumed job keeps its clock** (DL-049): resuming never adds time. The original goal is re-asserted unchanged, and gate 3 judges steered turns like any other.
- **Typing never resumes.** A `user` item never advances a job to `running`; that is how steering is detected. The gesture "interrupt, then say carry on" leaves the row `steered` on purpose, and `spov jobs resume` is the act that moves it. A job leaves `steered` three ways: resumed, cancelled, or the agent declaring completion (DL-048). The supervisor is the one writer of job states except for two human acts on the HTTP surface, cancel and resume.

### The resume boundary marker

The resume writes a `spov.job.resumed` marker (`MarkerResumed`, spov-sourced so a sandbox cannot forge it, recording who resumed) before it moves the row, and a failed write fails the resume. Without the boundary, the follow pass would still hold a person's "carry on" typed seconds before the resume, read it after the row is `running`, and steer the job straight back, which is the half-state this design removes.

The fold in `follow` applies a steer in place and remembers it. Events arrive in `Pos` order and the stale item is older than the marker, so a flag-then-skip design would read the item first, while the flag is still unset, and steer anyway. Applying in place is also required because a stop marker read after a steer must still be dropped by `nextState`, which it can only be if the state really is `steered` (`TestASteerIsInEffectForTheRestOfThePass`). When `signalResumed` arrives the steer is retracted:

- The retraction is conditional on the state still being the steer's. A declared stop folded between the steer and the marker must survive (`TestADeclaredStopInsideTheSteerWindowSurvivesTheResume`).
- A permission park folded inside the window is remembered and applied against the state the steer interrupted, because there is no `steered -> blocked` edge and its event is already behind the cursor (`TestAParkInsideTheSteerWindowSurvivesTheResume`).
- The held steer is carried across `FollowBatch` edges (`TestTheResumeBoundaryReachesAcrossABatch`, `TestTheResumeBoundaryAcrossOrderings`).

Advancing the cursor to the end of the log inside the resume was rejected: it would discard every unread event in the window, a permission asked or a stop announced among them. The marker discards exactly one class of signal.

### A blocked job resumes too

After a permission reply the turn resumes and finishes, so a person who answers has a running agent under a `blocked` row, where `nextState` moves neither a stop nor a declaration, and the job would strand with its deliverable uncollected. Resume moves `blocked -> running`. A blocked job's loop is held only if a person wrote to it while it was parked, so releasing the plugin is best-effort there: most blocked jobs have nothing to release, and one left held is still ended by its wall clock.

### A stop already announced means delivery

A steered or blocked job whose loop already announced its stop is delivered, not resumed. The handler checks the transcript as `loopStoppedInMessages` does (`jobLoopAnnouncedStop`) and `resumeIntoDelivery` moves the job to `delivering`. Resuming it would put `running` above a stopped loop that nothing will continue. There is no `blocked -> delivering` edge, so a blocked job goes via `running`, in two writes committed together (`TestResumingAJobWhoseLoopAlreadyStoppedDeliversIt`, both states).

### The nudge, and its guards

Clearing `paused` alone leaves the plugin waiting for a `session.execution.succeeded` that may never come on an idle session. The plugin's `resume` handler therefore sends a continuation itself (`nudge`), as a queued synthetic, so a message a person parked runs first (DL-052). No count of continuations ends a run, so the nudge meets no limit (DL-049). It is skipped in two cases:

- `loop.stopped` or `loop.paused`: nothing to restart, or the resume did not take.
- A turn in flight, tracked from `session.execution.started` and `succeeded`, because the running turn sends its own continuation and two would be billed.

`inFlight` is cleared on `session.execution.interrupted` and `failed` as well as on `succeeded`. ESC emits `interrupted`, so a flag cleared only on success would stay true from the moment a job becomes resumable, and every later resume would skip its nudge against a session idle for hours (`TestResumingAfterAnInterruptedTurnStillNudges`). It is scoped to the job's own session, learned from the first execution event, because the plugin is never told which session it belongs to and a subagent's execution events, if OpenCode emits them, must not clear the flag while the parent turn runs (`TestASubagentTurnDoesNotClearTheJobsInFlightFlag`). `pluginresumerun_test.go` drives the real `setup()` and invokes the registered command.

### A blocked job resumes by itself once its permission is answered

Answering a blocked job's permission through spov (`POST /sessions/{ref}/permissions/{id}`, DL-020) releases the job. `permission.replied` names no principal, so the supervisor cannot tell a person's answer from the plugin's. After the sandbox accepts the reply, the server writes the marker `spov.job.answered` (`jobs.MarkerAnswered`, written by `markJobAnswered`, naming the request). `signalFor` matches it by name and source, like `MarkerInterrupted`, as `signalReleased`, and the supervisor moves `blocked -> running`. The supervisor stays the one writer of states. If the server crashes between the reply and the marker, or the marker write fails (it warns), the job stays blocked and Resume still releases it.

- **Only when nothing else is asked.** The release happens only when no other permission asked in the job is unanswered, counted over the whole stored log (`unansweredAsks`): asked, with neither a `permission.replied` nor an answered marker, excluding the request just answered because its replied frame may not be stored yet. A request whose conversation's turn ended without a reply is not unanswered, because an interrupt drops a pending permission without one (`TestAnotherUnansweredRequestKeepsTheJobBlocked`). The count is read only when an answer is folded.
- **Decided at the fold.** If another request is open then and is answered later from an attached TUI, its reply names nobody, so that job still needs Resume. An answer from an attached TUI always needs Resume.
- **A reject releases too.** The agent has its refusal and its message and the run continues. The wall clock counts `blocked` already, so no time is granted or lost. A message to a blocked job is still refused; the page offers the answer.
- **Side effects of a release.** It clears the suspension's note, as Resume does. An answer folded while a steer is held clears the park the steer swallowed, so a later Resume does not block the job again on it. The release also releases the plugin's loop (`releaseLoop`, best-effort), as Resume does for a blocked job, after the wall-clock check so a job that pass ends at its bound is not first nudged on (`TestAnAnswerThatReleasesAJobReleasesItsLoop`). The release sends the plugin's resume command, which posts a short "resumed" note into the conversation as a synthetic read at the agent's next step, sends a continuation if the session is idle, and counts as activity for git-token renewal.

## Rationale

- One act, because two would strand a job, and the ambiguity of a `running` row over a paused loop has no timeout that could tell it from a long turn.
- The plugin is resumed through its own command endpoint, not through a new marker. A marker would need the plugin's event subscription widened, a second forge-resistant match, a transcript note so it does not render as raw text in spov's voice, and a pushable fake event bus in the plugin's runtime test, for no gain. The resume command is a guardrail against a person's own gesture and an accidental marker, not against an agent with a shell: an agent holds the sandbox password in its environment and can post to either endpoint. The permission hook, the gates and this command are guardrails on an honest run, and the sandbox is the unit of containment, not egress (DL-031).
- `blocked` resumes on measured evidence (spike S6): the turn continues after a permission reply, so the realistic flow is answer, then run.
- A suspended job resuming itself after an answer is the explicit act waiting to happen; requiring a second click would mean nothing and leave the job blocked for a person who did not know to press it.
- The resume writes to the sandbox once per human act, on a path no browser or listing polls, so it resets Modal's idle clock exactly when a person has asked the job to keep working (DL-018).

## Measurements

- **Spike S6:** after a permission reply the turn resumes and finishes.
- **Spike S2:** `POST /api/session/:id/command` answers 204 and runs the registered `spov-goal` command.
- **Steer, resume and finish against real Postgres**, where the resume boundary's `Pos` ordering is the store's: `SPOV_TEST_DATABASE_URL=… go test -tags integration ./internal/server/ -run TestIntegrationJobLifecycleSteersResumesAndFinishes`.
- **Not measured:** whether OpenCode emits execution events for child (subagent) sessions. The `inFlight` flag is scoped to the job's own session so the answer does not matter.

## Consequences

- A suspended job can be handed back to its loop. Cancel and resume are the two human writes of job state.
- The supervisor writes to a sandbox on the steering path (the pause). That is one more place a pass can be slow or fail, and the failure is tolerated, not retried.
- Each resume mints a connect credential and writes a `mints` row, so rapid retries hit `MintsPerMinute`.
- A permission answered in an attached TUI, and a second open request answered after the release, still need an explicit Resume.

## Known gaps

- A pause is written after the row, so a resume landing inside `OpenTimeout` (30 s) can be followed by the late pause, leaving `loop.paused` true under a `running` row. The job then idles until its sandbox times out, and `spov jobs resume` refuses it because the row already says `running`; recovery is `/spov-goal resume` in the attached TUI. Reordering only flips the failure's direction.
- The recorder can store a person's item after the marker that should have answered it (a late attach or a gap), which reads as a fresh steer and re-pauses the job.
- A resume of a job whose plugin never loaded reports success and continues nothing.
