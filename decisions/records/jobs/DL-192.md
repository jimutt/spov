## Context

DL-191 stores schedules with a `next_run_at`. Something must notice a due slot and create its job exactly once, across replicas and restarts, without a second way of creating jobs.

## Decision

- `Service.RunSchedules` runs as one more loop on the replica holding the reconciler lock (`serve.go`'s leader block, beside the job sweep; DL-004), every `ScheduleTick` (1 min). Each tick reads up to `MaxSchedulesPerTick` (50) active schedules with `next_run_at <= now`, oldest slot first (`ScheduleStore.Due`, the one schedule query that takes no org, listed in `boundaries_test.go`'s `unscopedQueries`), and fires each; one replica runs the loop, and the unique (schedule, slot) pair below is what keeps a slot from firing twice.
- A fire's slot is the schedule's `next_run_at`. When the slot is more than `ScheduleCatchUp` (1 h) late, only the newest slot at or before now is fired and the ones between are recorded as missed in one history entry (DL-193); so a server that was down fires at most one catch-up per schedule. The walk over missed slots stops after `maxCatchUpSteps` (10,000) and then finds the newest slot from an hour before now, recording "at least N".
- A fire creates the job through the same path as `Service.CreateJob` (`createJob`, which adds the schedule and slot) with the owner's principal, built from the owner's row by `auth.PrincipalOf`, the token authenticator's own rule: a person only while the allowlist still covers them, a service account only while it is not disabled, and never as an admin. An owner no longer allowed is a failed fire (DL-193), and the schedule is paused by off-boarding anyway (DL-193).
- Inside the job create's own transaction (`createJobWithinQuota`, through `jobOrigin.check`) the schedule is read again and held (`ScheduleStore.Lock`, `for update` on Postgres): one deleted, paused (unless the run is manual) or changed since the tick read it (its `updated_at` moved) creates nothing, and the fire is a skip saying so. An off-boarding's `PauseOwned` waits for that lock, so no job is created after it.
- Before the busy check, a fire looks for the job its slot already has among the schedule's newest 20 (`slotJob`) and records it as already run.
- The job records where it came from: `store.Job.ScheduleID` and `ScheduledFor` (columns `schedule_id`, `scheduled_for`, migration with a unique index on the pair where `schedule_id` is set; the memory store refuses the same pair). A second fire of the same slot is refused by the store, and the fire then finds that slot's job and records it as already fired, so a replica that lost the lock mid-fire, or a retried tick, never creates two jobs for one slot.
- After each fire, started or not, `next_run_at` moves to the next slot strictly after both the fired slot and now, in the schedule's zone, in the same transaction as its history entry, through `ScheduleStore.RecordFire`, which writes only the failure count, the next slot and, when pausing, the state and reason, and only while the row still holds the slot the fire read: an edit, a resume or a pause made while the fire ran is kept. A cadence with no next slot pauses the schedule, and one that can no longer be read pauses it with the reason. The started entry's id is a millisecond after the missed entry's, so both stores list them in order.
- "Run now" (DL-194) fires the schedule at the current minute as its slot, through the same path and the same skip rules, and does not move `next_run_at`.

## Rationale

Creating through `CreateJob` keeps one path for every job, so prep (DL-047), quotas (DL-045), the wall clock (DL-049), the verdict (DL-050) and the job's page all apply unchanged. The unique (schedule, slot) pair makes a fire idempotent where it matters, in the store, rather than trusting the lock alone. One catch-up after downtime is what a person would want from a daily report; ten queued reports would not be.

## Consequences

- A schedule fires up to a minute after its slot.
- A fire depends on the leader replica: while no replica holds the lock, nothing fires, and the next holder catches up once.
