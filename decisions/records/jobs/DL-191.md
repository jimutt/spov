## Context

The autonomous jobs (DL-045) with report and pull request outcomes suit work that recurs: a weekly dependency report, a nightly triage, a monthly clean-up. Today each run is started by hand. A hosted server runs all the time and already runs work on one replica (DL-004), so it can start them on a cadence. OpenCode's own automations (2.4) live and die with one sandbox and are turned off in jobs (DL-184), so they are not this.

## Decision

- A schedule is a row of its own (`store.Schedule`, Postgres table `schedules`, the memory store's map), owned like a job: `org_id`, `owner_id`, an id (ULID), a name unique per owner (the same shape as a template's name), and the job it creates each time: the body of `POST /api/v1/jobs` (`server.JobRequest`) stored whole, as a job's session request is. Only kinds `report` and `pr` are accepted; `sync` needs a seed bundle from a local checkout and is refused with 422.
- The cadence is a cron expression in five fields (minute, hour, day of month, month, day of week) or one of `@hourly`, `@daily`, `@weekly`, `@monthly`, parsed with `github.com/robfig/cron/v3`'s standard parser and evaluated in an IANA time zone (`time.LoadLocation`; default `UTC`). Seconds, `@every` and `@yearly` are refused.
- A schedule fires at most once an hour: the minimum gap between consecutive slots over the next 400 slots from the time it is saved must be at least `MinScheduleInterval` (1 h), else 422 naming the shortest gap found. A person may own at most `MaxSchedulesPerUser` (20) schedules, a service account the same; the count and the insert share the owner's job-quota lock.
- Saving a schedule (create or update) checks its job request as `CreateJob` would without creating anything: the request's own validation, the template it names (DL-120), the model and its mode (DL-013, DL-187), the repositories' shape and the caller's credential for them, and the git access (DL-043). A failure is the same 422 a job create gives. The stored request keeps what the caller sent, not what it resolved to, so a later change of the account default applies at the next fire.
- A schedule is `active` or `paused`, with `paused_reason` when paused (by its owner, by DL-193's failures, or by off-boarding). It stores `next_run_at`, the next slot after now in its zone, computed on save and after each fire.
- Hosted only: a local server's store has no schedules and its routes answer 501, since nothing runs while a local server sleeps.

## Rationale

Storing the request whole, as a job stores its session request, means a scheduled run is exactly a job someone could have started by hand, judged by the same gates. Five-field cron covers hourly, daily, weekly and monthly and every custom cadence in between, in the syntax people already know; the zone keeps "09:00 on weekdays" at nine across a daylight-saving change. An hour's floor bounds what a forgotten schedule can spend: each run buys a sandbox and a prep pass.

## Consequences

- `go.mod` gains `github.com/robfig/cron/v3` as a direct dependency (it is already in the module graph).
- A schedule whose template, model or credential disappears is caught at fire time, not save time (DL-193).
