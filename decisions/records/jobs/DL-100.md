## Context

An agent orchestrator outside spov sometimes wants to hand a coding task to spov and get the repository back, as `spov fly` does from a checkout (DL-027, DL-095), rather than a pull request (`pr`) or a report (`report`). DL-027 and DL-095 say jobs never sync. DL-027 and DL-098 also say a seed's bundle travels only in memory with its launch. That cannot hold for a job, which is created now and provisioned later, possibly by another replica (DL-045, DL-046). Agreed with the user on 2026-11-07.

## Decision

This amends DL-027 and DL-095 (jobs never sync), DL-027 and DL-098 (a seed's bundle is never stored), and DL-037 (every job works from `/workspace`).

### The kind

- A third job kind, `sync` (`store.JobKindSync`), beside `pr` and `report`. Like the others, it runs only on a server with a database; a local server refuses every job (DL-046).
- The agent is told, in the kind's deliverable note, that the result is the repository's state at the end: commits on the branch it started on, plus any uncommitted changes. Pushing and opening a pull request are not needed. Its permission allowlist is `pr`'s, which already covers editing the repository, running its tools, and git (DL-040). Every agent-facing text that assumes a pull request says otherwise for this kind: the orientation (`workspaceNote`) and the generated AGENTS.md's job section. In local-bundle mode the AGENTS.md also says the repository has no `origin` and no git credentials.
- The web job form does not offer it, since a browser has no checkout to seed from. `everyKindIsOffered` names it as deliberately absent.

### The seed

- `spov jobs create --kind sync`, run inside a git checkout, sends what `spov fly`'s sync sends (`resolveSyncLaunch`): the branch, the base commit, and a bundle of unpushed commits. The bundle runs from the newest remote-tracking ancestor to `HEAD`, or is the whole history in local-bundle mode.
- It has DL-027's preconditions, checked before the server is asked: a clean checkout, `HEAD` on a branch, a commit. `--repo` may name only the checkout's repository.
- The request carries the seed as `sync`, validated as a session's: one repository, a valid branch, a 40-hex base, and a bundle of at most `git.MaxSyncBundleBytes` (16 MiB).
  - A `sync` job without a seed is refused with a 422, and so is a seed on another kind.
  - `POST /api/v1/jobs` takes the session create's body limit (`MaxSessionBodyBytes`) on its huma operation and in `maxBodyBytesFor`.
- **Local-bundle mode is allowed**: a checkout whose remote matches no configured platform, or has none. The bundle is the whole history and the sandbox has no `origin`, as for `fly` (DL-027).
- **The 16 MiB bound is on what is sent, not the codebase.** The seed holds only the commits the remote lacks, and the sandbox clones the rest. Only local-bundle mode, or a branch with no remote ancestor, sends whole history. That is where a large repository is refused, with the existing advice to push the branch first. Streaming such a seed through object storage instead of the database is left for a later decision.

### Where the bundle waits

- The bundle is stored from create until the launch applies it, in a table of its own, `job_seeds (job_id primary key references jobs on delete cascade, bundle bytea not null, created_at)`. It is not in the job's or the session's request JSON, which listings read.
- It is plain, like the repository it comes from, which the server can already read through its clone. It is written in the job create's transaction.
- The launch (`Service.launch` for a job) reads it into `opts.Sync.Bundle`. It is deleted once the launch has applied the seed and committed the session's `running`. A launch that fails keeps it for a redelivery.
- It is also deleted when the job reaches any terminal state, in the same transaction, so no bundle outlives its job. The journaled memory store has no jobs, so only Postgres and the memory store's contract need it.

### Where it works

- The server sets a sync job's landing to its repository's directory (`git.SingleRepoDir`), as a synced `spov fly` lands. It refuses a `landing` that names anything else with a 422. An orchestrator calling the API directly gets the same landing as the CLI.
- The check therefore runs in the repository, not at `/workspace` (DL-037, DL-050). `--check`'s help says so for this kind, so `--check ./scripts/check.sh` is right for a sync job where a `pr` job writes `./<repo>/scripts/check.sh`.

## Rationale

- Reusing fly's seed means a sync job starts from exactly what a synced session would, unpushed commits included. The same rules about a clean checkout keep the result landable.
- A kind of its own keeps the deliverable explicit: a `pr` job that did not open a pull request would be a failure.
- A job's launch is asynchronous, so the bundle has to wait somewhere. A row of its own, gone by the time the job ends, keeps it out of every listing and bounds how long it is kept.
- Bounding the bundle rather than the repository keeps a large codebase usable, since only what the remote lacks travels.

## Consequences

- `JobKind`'s closed set gains a value, and every switch on it must decide `sync` (the implementation notes list them).
- A job's create request can be 16 MiB, and the server stores it briefly.
- A whole-history seed of a large repository is refused; push the branch, or give the checkout a remote on a configured platform.
