## Context

A sync job's sandbox is held after delivery until its state is taken (DL-101). DL-027's `POST /api/v1/sessions/{ref}/sync-export` and `spov stop --sync` both refuse a job's session. An orchestrator needs to read the state over the API, a person or script needs to land it in a checkout, and either needs to end the hold. A person who interrupted a sync job (`steered`) or found it `blocked` may also want its state without handing it back to its loop.

## Decision

This amends DL-027 (the export refuses a job's session) and DL-023 (the command table, the `--json` commands and completion).

### The routes

**`POST /api/v1/jobs/{id}/sync-export`** exports the state from the sync job's sandbox, in the session export's shape and bound: `branch`, `base_commit`, `head_commit`, `bundle`, `worktree_tar` and `deleted`, at most 32 MiB.
- It is a POST, like the session export: an explicit, per-act read of a sandbox (DL-018, DL-019), and every GET stays a store read.
- It works on a held job, and also on an unfinished sync job whose sandbox is live (`running`, `blocked` or `steered`), so steered or blocked work can be taken. Its result is the repository as it is at the call. On a held job that is the judged state, since nothing runs (DL-101).
- It is repeatable and changes nothing.

**`POST /api/v1/jobs/{id}/release`**, with an optional body `{"applied": bool}`, ends a held job's sandbox (DL-101's release). With `"applied": true` it also sets `applied_at`.
- It answers the job view.
- On a sync job already released it answers 200 with the view, so a retry is harmless.

The status codes, one table for both:

| Case | `sync-export` | `release` |
|---|---|---|
| Held sync job | 200 | 200 |
| Unfinished sync job with a live sandbox (`running`, `blocked`, `steered`) | 200 | 409 (not finished) |
| Sync job `delivering` (being judged) | 409 | 409 |
| Sync job queued or provisioning, no sandbox yet | 409 | 409 |
| Sync job already released, or cancelled | 409 | 200 (released already) |
| A `pr` or `report` job | 404 | 404 |
| Another user's job (not admin) | 404 | 404 |

Both are authenticated as the job's owner or an admin, and both are in the generated API (DL-005).

### The commands

- **`spov jobs apply <id> [--keep] [--json]`**, run inside a checkout of the job's repository:
  1. checks the checkout as `stop --sync` does (`verifySyncCheckout`);
  2. exports;
  3. lands the state with `git.ApplySync`: in place when the checkout is still where the job started, else on `spov/<job's session name>`;
  4. prints the same summary;
  5. on a held job, releases with `applied: true` unless `--keep`.

  On an unfinished job it lands the state and never releases, and says the job is still running. A failed landing releases nothing, and prints the retry (`spov jobs apply <id>`) and `spov jobs release <id>` to discard. `--json` prints the job view after it.
- **`spov jobs release <id> [--json]`** ends the hold without applying, saying the work is discarded.
- **`cancel` keeps its meaning (DL-023): it ends an unfinished job.** On a finished job it stays the 409 it is (DL-045), with a hint that names `spov jobs release <id>` when the job is held. Cancelling an unfinished sync job ends it unheld, as DL-101 says.
- **`spov stop` and the web's End session do not discard a hold by accident.**
  - `spov stop <session>` on a held job's session is refused, naming `spov jobs apply` and `spov jobs release`.
  - `spov stop --all` skips held sessions and lists them, with the same commands.
  - The web offers Discard held work instead (DL-101).
- **DL-023's table gains `apply` and `release` in the `jobs` group**: `apply` lands a job's work and `release` ends a hold, and neither word is used for anything else. Both take `--json`, which joins DL-023's list (`TestTheReadAndCreateCommandsTakeJSON`). Completion for `apply` and `release` offers held sync jobs, an exception to "the acts offer unfinished ones only".

## Rationale

- The API export is what an orchestrator needs to apply the state itself, or somewhere spov is not installed. The same read on a steered or blocked job means its work is never stranded.
- `apply` releasing by default fits the common path, from create to wait to apply, with nothing left billing; `--keep` serves a script that applies in two places.
- Keeping `cancel` for unfinished jobs and `release` for a hold keeps each verb meaning one thing.

## Consequences

- Two routes, two commands. `stop` and the web's End session learn about holds.
- The rule that no page load or listing reads a sandbox still holds, since both routes are POSTs, per act (DL-018).

## Implementation notes

**The export route.**
- The session export is `POST /api/v1/sessions/{ref}/sync-export` (`internal/server/sync.go:48`, operation `export-session-sync`). It finds the sandbox with `s.handle` and runs `session.ExportSync` by exec (`sync.go:93`). It does not go through `withConnection`.
- Add the job route (operation `export-job-sync`) beside the job routes. It resolves the job and its session, checks the caller, applies the table, then does the same `s.handle` and `ExportSync`. Its response type is the session export's, so `server/client` reuses the decoding: add `Client.ExportJobSync(ctx, id)`.
- No sandbox-read inventory needs updating. `TestNoReadPathTouchesTheSandbox` GETs store paths, and a POST is not one.

**The release route.**
- Operation `release-job`. On a held job, end the session the way `Service.DeleteSession` ends a session (`MarkStopped` and terminate; not the job cancel path, since the job is finished), with the `released` termination reason (DL-101). Set `sync_applied_at` when `applied`. Answer the view. Add `Client.ReleaseJob(ctx, id, applied bool)`.

**The stop paths.**
- `Service.DeleteSession` (and so `spov stop`, and the web's End session should it be called) refuses a held job's session with 409, naming the two commands, unless the call comes from the release route.
- `spov stop --all` (`internal/cli/stop.go`) filters held sessions out of what it stops, using `SessionView.job.held` (DL-101), and prints them.

**The CLI (`internal/cli/jobs.go`).**
- `newJobsApplyCmd` and `newJobsReleaseCmd`.
- `apply` reuses `verifySyncCheckout` with the job's session view, which carries `Repos` and `Sync`, and `git.ApplySync` with the session's name for the fallback branch, as `syncSessionBack` does (`internal/cli/sync.go`).
- `cancel`'s 409 on a held job adds the release hint.
- Completion for both (`completion.go`) lists held sync jobs.
- `docs/jobs.md`: the commands, and a "Sync jobs" section.

**Tests to add.**
