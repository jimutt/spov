## Context

spov runs autonomous work as a job: a goal, a repository selection and a kind (`pr` or `report`), carried out by an agent in its own sandbox while nobody is attached. A job outlives the terminal that created it, can run for hours, and spends money unattended. It needs a durable row, a state machine that cannot be driven into an illegal state, a bound on how many a person can have, and a loop that survives a server restart without launching a second sandbox for work already running.

Two facts about the environment shape the design. The agent's continuation (re-prompting, goal re-assertion, permission decisions, yielding to a human) has to sit next to the model, so it runs as a plugin inside the sandbox (DL-039). But the sandbox is not what must survive a failure: a plugin that never loads or crashes must not strand a job.

## Decision

### The job contract

A job is created by `POST /api/v1/jobs`, and the CLI (`spov jobs create`) and the web form (`/jobs/new`) are clients of it with no privileged path. A local server has no supervisor and answers 501 (`ErrJobsNeedAServer`), not 404, so a client does not conclude its URL was wrong; autonomous jobs on a local server are not supported. Any authenticated user may create a job in their own organisation, the same rule as creating a session. A role check is the wrong bound on spend; the job quota is the bound. `spov jobs create` prints the job id and exits, because blocking a shell on something that may run for hours is the wrong default. Following a job is `spov jobs` and the session page.

A job always owns a fresh session and never attaches to an existing one. A job session runs under the job permission policy (DL-040), and joining a live session would change the policy beneath whoever is attached to it. The session row is inserted in the same transaction as the job, `starting` with no sandbox, because `store.Job.SessionID` is not nullable and carries a composite foreign key to the session in the same organisation. The session is named `job-<id>` (lowercased), after the job and not the clock: session names are unique among live sessions, and a name with one-second resolution collides between two jobs started in the same second and surfaces as a name conflict rather than as the real cause.

`CreateJob` resolves the model, the git access (a job never takes the interactive default, DL-043) and the wall clock (DL-049) before any row exists, so a bad request is a refusal and not a failed job. It enqueues the job after the rows commit, so the supervisor is never handed an id that does not resolve. If the enqueue fails, the queued row stays visible and cancellable, the error names the job id and says to cancel it with `spov jobs cancel`, and the restart sweep re-queues it.

### The row

A job row holds the canonical goal, the kind, the owner, the session, the state, an optional check command, the model, the assessment and verdict text, an error text, what the agent declared unfinished, a cursor into the session's event log and the wall-clock ledger. The store follows the pattern of the others: a memory and a Postgres implementation, `org_id` on every query, ULID ids. The goal exists in three copies and the row owns it: the session's first prompt is a rendering of it, and the plugin's in-memory copy is derived and may be stale after a reload. Nothing reads the goal back out of the transcript.

- A job's session, kind and owner are immutable after creation, and its session must exist in the same organisation. Postgres enforces the first by what `UpdateJob` does not write and the second by the composite foreign key; the memory store enforces both; contract cases in `storetest` pin them for both stores. Re-pointing a job at another session on update is how the one-job-per-session rule would be slipped.
- There is one job per session: `unique (org_id, session_id)`. A session running two loops has two things continuing it and neither knows about the other.
- Because a job's session is an ordinary session row, the transcript, the sessions list and the web page work on a job unchanged, and `spov attach <job>` is an ordinary attach with the loop's controls reachable from the terminal UI (DL-025).
- `StartedAt` and `StoppedAt` are stamped by the store (`StampJobTimes`) and are write-once. A job returning to `running` from `blocked` or `steered` keeps the time it first started, and neither `blocked` nor `steered` stamps `StoppedAt`. The same function keeps the wall-clock ledger (DL-049).

### The state machine

A job is in one of nine states.

| State | Meaning |
|---|---|
| `queued` | created, nothing provisioning it yet |
| `provisioning` | the supervisor has taken it and is launching the session |
| `running` | the agent's loop is driving the session |
| `delivering` | the run ended; the pass that collects, judges and concludes it |
| `succeeded`, `failed`, `cancelled` | terminal |
| `steered` | suspended because a human took over; the loop is held and the sandbox stays up |
| `blocked` | parked on something the server will not decide for it |

`steered` and `blocked` are suspensions, not terminal states, and leaving either is explicit: a resume, a release, or a cancel. `blocked` is distinct from `failed` because a human can recover it. At the pinned OpenCode build the plugin decides every permission, so a job reaches `blocked` only when its permission hook failed to install (DL-022); how a person's answer releases it is DL-054. How a human message takes a job over is DL-052. Three words are not interchangeable: a job is suspended when a human took over, parked when it waits on something nobody will answer, and the plugin's `/spov-goal pause` only stops the loop continuing and never moves the row.

The legal moves are the table `jobTransitions`:

- `queued` to `provisioning`, `cancelled`, `failed`;
- `provisioning` to `running`, `failed`, `cancelled`, `blocked`;
- `running` to `delivering`, `blocked`, `steered`, `failed`, `cancelled`;
- `delivering` to `succeeded`, `failed`, `cancelled`;
- `blocked` to `running`, `delivering`, `cancelled`, `failed`;
- `steered` to `running`, `delivering`, `cancelled`, `failed`.

A move to the same state is allowed, because the supervisor records progress as well as state. The transitions live in Go (`store.CanTransition`), the one table a test asserts whole. The alphabet lives in a check constraint on `jobs.state` that names the nine states. Two copies of the transitions, one in the schema and one in code, would be a second thing to keep in step.

`JobStore.Update` reads the current row `for update` inside its own transaction and refuses a move the machine disallows. The supervisor runs behind the leader lock, which makes it singular, so there is no version column. The row lock is for the window in which a restart or failover leaves two replicas both believing they hold the lock: the machine holds across that window.

The supervisor writes every state that follows from what happened in the run. The human acts, cancel and resume, are the only other writers, and they go through the same table. Because only server code writes a state, a failed plugin cannot strand a job outside `steered`: the supervisor writes `steered` from the stored inbox rows, not from anything the plugin reports.

### The plugin may fail without the job failing

If the plugin never loads, nothing re-prompts, the job degrades to a single pass, and the server still classifies the outcome. Nothing on the server's verdict path may depend on a signal only the plugin produces: a missing plugin signal is missing evidence, not a failure. This rules out waiting for a plugin heartbeat and treating the plugin's own state report as authoritative. Two mechanisms keep it true. The end of a run is a signal the plugin announces, never something inferred from silence (DL-048), and a backstop keyed on the session's state concludes a job whose announcement never landed.

Nothing spov sends is ever a `user` inbox item. A prompt over HTTP is indistinguishable from a human typing at the terminal UI (the same `item.type: "user"`, and the item carries no id to correlate), so neither the plugin nor the server sends one. The opening goal and every continuation are synthetic. Otherwise a job's own first prompt would read as a takeover and every job would steer itself.

### The run loop

`Supervisor.Run` is resumable rather than a script. Each attempt re-reads the row and does only what it says is outstanding: `queued` provisions, `provisioning` opens the goal, `running`, `blocked` and `steered` are followed, `delivering` delivers. A redelivery by River therefore resumes work and never provisions a second sandbox.

- The row moves to `provisioning` before the launch, never after, so a crash between the two leaves a row the sandbox tag settles and not a `queued` row a retry would provision again. A refused move means a cancel landed and nothing is launched. The supervisor adopts a sandbox already tagged with the job instead of launching another. The preparation pass runs after the move, so a cancelled job is never paid for (DL-047).
- A `provisioning` job waits on its session with no timeout of its own. The reconciler fails the session past `LaunchTimeout` and the next pass turns that into a failed job. A second timeout in the supervisor would race the sweep and decide with less information.
- A failed launch is the job's failure, recorded on the row and not returned, because River would retry and each retry would provision again. A failed opening turn is returned: the sandbox is up and paid for, the failure is one request into it, and a retry adopts by tag.
- One attempt is one pass: it advances a step and asks River to redeliver after `FollowInterval` (10 s). `JobSnooze` decrements the attempt count, so redelivery consumes none of `SupervisorMaxAttempts` (3), which stay for real infrastructure failures. An attempt that looped until the job finished would hold a worker slot for hours, and `SupervisorMaxWorkers` (10) of them would starve the queue. `SupervisorJobTimeout` is the launch budget plus 30 minutes, not the sandbox ceiling.
- A finished job's sandbox is terminated by the delivery pass after the verdict is written (DL-050), so a failure to terminate cannot leave the job `delivering` with its gates unread.
- Supervisor function seams (`Provision`, `Open`, `Adopt`, `OpenOut`, `Evidence`, `Outcome`, `Mark`) keep the sequencing testable without a launcher, a forge or a sandbox; `spov serve` wires them. The supervisor's River client is not confined to the leader: it is a work queue that leases each job to one worker, and confining it would idle every replica but one. `spov serve` runs the River migration at startup, and a failed migration stops the server, so no replica works a queue whose schema it does not match.

### Every abandoned job is delivered and judged

When a job's session is not live and the plugin never announced a stop, `checkAbandoned` concludes the job. It keys on the session's state, never on elapsed time, and reads only the store. It covers `running`, `blocked` and `steered`, and sends every one of them to `delivering` (`abandonedState`). `delivering` is not a verdict; it is the pass that computes one. A suspended job that produced nothing has no passing gate and is recorded `failed` anyway, and a job that produced something is judged on it. A `pr` job's verdict and link are recovered this way, because gate 2 asks the forge and not the sandbox. A report is not: by the time the backstop fires the session is not live, and neither the report collection nor the evidence read can reach the sandbox.

The target is chosen inside the store transaction, on the locked row, because `movedTo` takes the routing as a function. The caller's copy of the state is stale exactly when the pass wrote nothing. A job the pass itself had just parked would otherwise be routed as a running job though it had stopped running: the store refuses `blocked` to `delivering` when the edge is absent, nothing is written, and the job sits in `blocked` with no sandbox, holding its owner's quota. Both branches (the session row is gone, the session stopped) use the same `abandonedState`. `TestTheAbandonedRoutingIsAnEdgeTheMachineHas` ties the routing to the transition table: a routing the machine refuses writes nothing and warns a true sentence about the wrong problem. `TestADeclarationSurvivesADeadSandbox` covers the interaction with a completion declared before the sandbox died. Interrupt can land on a run that already announced its stop, so a job can reach this path through a person's act as well as through a dead sandbox.

### Cancel

`DELETE /api/v1/jobs/{id}` (`CancelJob`) re-reads the row in a transaction and writes `cancelled`, appending to the job's error text what it was waiting on, then stops the job's session. The row goes first, so a terminate that fails leaves a cancelled job and a sandbox the reconciler reaps (DL-009). Stopping the session records a durable cancel request while it has no sandbox, which a launch in flight reads in the transaction that commits its sandbox, so a supervisor provisioning at that moment does not commit one. A session still `starting` with no sandbox is concluded by the cancel itself, since no launch exists to resolve it. Cancelling a cancelled job is not an error, and cancelling a finished one is a 409. A job that finished between the read and the write has been decided by someone else, and that outcome stands.

`DELETE /api/v1/sessions/{ref}` on a session owned by an unfinished job goes through the same cancellation (`DeleteSession`). A plain session delete would leave the job queued, to run later against a session the caller believed they had stopped. Once the job is finished its session is an ordinary one, and the delete is a plain delete. Cancel is the explicit act that leaves `blocked` or `steered` without a human releasing it.

### The restart sweep

`Supervisor.Sweep` re-queues every unfinished job nothing is working: one whose enqueue failed after commit, or one queued before the River tables were reset. It is safe because the queue is unique by job and the run loop is resumable. It skips `delivering` jobs: that state is not terminal, so `ListLive` returns it, and re-delivering would read the sandbox every five minutes and hold it open to its billing cap. Delivery is also idempotent through its own evidence marker, so a River retry cannot repeat it. The sweep runs every `SweepInterval` (5 minutes), first immediately, under the leader lock beside the reconciler and the recorder.

### The job quota

A person has at most `MaxConcurrentJobs` unfinished jobs, default 2, below the session default of 3. It is separate from the session quota so a queue never locks someone out of their own interactive tooling, and the reverse (DL-009 holds the full rule). It counts every non-terminal state with `JobState.Counts()`, not `Live()`, which excludes `queued` and would let a caller queue any number of jobs; `store.JobCounts` is the same set as a list for SQL, and `TestJobCountsAgreesWithTheCountsMethod` keeps the two in step. `createJobWithinQuota` counts inside the insert's transaction, because two creates on different replicas would otherwise both read one short of the limit. The session count excludes the session of an unfinished job, decided by the job's state and not the existence of a job row, so a billing sandbox under a terminal job falls back to the session quota. The job count takes an advisory lock keyed `job:<owner>`, apart from the session key, so a user's job create and session create do not wait on each other.

### The reconciler and jobs

The reconciler skips the sessions of `queued` jobs only. A queued job may wait longer than any launch budget, and its session is `starting` with no sandbox, which is otherwise indistinguishable by age from an orphaned launch. Once the supervisor takes a job, its session is an ordinary launch again and the orphan sweep is the backstop for a replica that died mid-provision. A job's sandbox is recognised by its `job` tag, never by the session name (DL-004).

## Rationale

The split follows what must survive the sandbox. The server owns the job row, states, restart recovery, the verdict and delivery. The plugin owns continuation, which has to sit next to the model. That line is what makes a plugin reload, a sandbox restart or a leader failover leave the job knowing what it was for.

`steered` is a state of its own because it changes what `running` means: a running job may have a human at the keyboard and not the loop driving. Adding a state to a machine other code already switches on is where this kind of bug lives, so the machine names it.

Making the run loop resumable instead of sequential is the difference between River's retries being a safety net and being a way to buy two sandboxes for one job. A separate job quota is one more field and removes a class of interference between autonomous and interactive work.

Shapes rejected for the end of a run: a quiet-period heuristic has no safe threshold, because a long turn (a full test suite, a slow build) produces no events for minutes and looks exactly like a finished job; a looping attempt that held its worker slot until the job finished would starve the queue; and polling the plugin's evidence file on a timer would keep every job's sandbox alive to the 24-hour cap, since any plain HTTP request to a sandbox resets its idle clock (DL-018).

## Measurements

- **Spikes S1 to S4** (the plugin primitives): a plugin loads from a file, registers a command reachable over HTTP, and starts the next turn from inside the server, and a prompt sent over HTTP is typed `user` exactly like a human's, with no item id to correlate. All four held; S4's finding is the basis of the rule that nothing spov sends is a user item. Re-run: `go test -tags integration ./internal/sandbox/ -run 'PluginSeesTheHumanInbox|PluginLoop'`.
- **S7, the sandbox's file read** (`GET /api/fs/read`), on OpenCode `0.0.0-beta-18684`: the route, the raw-bytes body and `location[directory]` were as inferred, but an absolute path answers 500 and a missing file answers 500, not 404. `readEvidence` therefore splits the path and sends the directory as the location, and both a missing file and a broken read map to "no artifact", the harmless direction. The test asserts the measured behaviour so a build that distinguishes the two fails it. Re-run: `go test -tags integration ./internal/sandbox/ -run S7FsReadShape`.
- **Idle clock (spike S-A):** any plain HTTP request to a sandbox resets Modal's idle clock; a held-open stream does not. This is why the evidence file is read once at delivery and not polled.
- **Job lifecycle against real Postgres with a fake sandbox:** a redelivery resumes and does not re-provision, a cancel landing mid-flight stands, and the stop marker moves a job to `delivering`. Sabotage-checked by making `provisioning` re-provision and by removing the stop signal. Re-run: `SPOV_TEST_DATABASE_URL=... go test -tags integration ./internal/server/ -run JobLifecycle`.
- **The two concurrency limits** (distinct advisory lock keys, session exclusion by job state), which only real Postgres shows: `go test -tags integration ./internal/store/postgres/ -run Quota`.

## Consequences

- A job is the first thing that can spend money unattended. The bounds on it are the job quota, the sandbox timeout and the wall clock (DL-049).
- Only server code writes a job's state, so the concurrent writers are its own replicas. The row lock is what keeps the machine intact across a failover.
- A queued job's session shows as `starting` with no sandbox and is exempt from the orphan sweep for as long as the job stays queued.
- A cancel that fails halfway leaves a sandbox the reconciler reaps on its own schedule, which is the reconciler working as designed.
- The delivery pass runs more often against sessions whose sandbox is gone. It handles that already: a failed collection is a warning, and gate 2 treats it as unverified.
- The API document and its TypeScript client carry the job endpoints, so `scripts/gen-api-client.sh` runs when they change.
- `TestEveryJobStateIsDecided` fails when a new state is added without a decision on whether it can receive a message (DL-052). The web app reads the state alphabet too: `GROUP` in `joblist.ts` fails the type check until a new state is placed (DL-060).

## Known gaps

- Nothing limits how many continuations a job's loop sends; the wall clock is the bound on how long an agent runs (DL-049).
