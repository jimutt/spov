## Context

A job runs inside a sandbox under a plugin that keeps the agent working turn after turn. Something has to say when the run is over. Every way a run can end badly (a person stopping it, a failed send, a repeated denial, failing turns) has its own signal. The way it ends well needs one too, or an agent that has finished keeps taking turns: a job whose work was correct on its first turn once spent forty more turns saying "Already complete", billing the whole time.

Silence cannot be that signal. A long turn, such as a full test suite or a slow build, produces no events for minutes and cannot be told from a finished job by any timeout. A quiet-period heuristic has no safe threshold: it either cuts long jobs off mid-run and reports a partial result as the whole one, or makes every job wait out a delay it did not need. Polling the plugin's evidence file on a timer is no alternative either. Every plain HTTP request to a sandbox resets Modal's idle clock, so polling would keep each job's sandbox alive to its 24 h cap, and `TestNoReadPathTouchesTheSandbox` would fail (see DL-018).

## Decision

A run ends on a signal the plugin sends. The supervisor reads it from stored events (DL-046); it never infers an end from quiet.

### The completion tool

The plugin registers a tool, `spov_complete` (`opencode.CompletionTool`), through `ctx.tool.transform`. A job ends well only when the agent calls it, never by saying so in prose. Calling it sets `loop.stopped` with reason `declared` and takes the ordinary `announceStop` path, so the check, the marker, delivery and the verdict follow as for any other stop.

The channel is a named structure with an argument schema. It cannot be produced by accident, and neither a person typing the words nor the agent quoting them can end a job. Deciding that the goal is met stays with the agent, which is the only party that can.

- Declaring completion ends the run, not the outcome. A job that declares with no deliverable still fails gate 2 (DL-050). The tool is a guardrail on an honest run: an agent that can declare can already end its own job with `/spov-goal stop`.
- The tool takes `summary` (required) and `unfinished` (optional). Both are evidence for a person reading the report. No gate reads `summary`; `unfinished` only makes a success partial. It takes no branch: pull requests are recorded with `spov_pull_request` (DL-051).
- It needs no allowlist entry, and must not be given one. A permission assertion is written by each tool's own `execute`, not by the dispatcher, and spov's asserts nothing, so `permission.evaluate` never fires for it. An entry would name an action that is never evaluated and would fail `TestIntegrationActionVocabulary` (`TestTheCompletionToolIsNotInAnyAllowlist`; see DL-040).
- It declares `options: {codemode: false}`. The toolset splits on that field: `codemode === false` tools are direct calls and the default goes into a codemode catalog reachable only from generated code. Without it the agent said it could not invoke the tool and ran to its limit (`TestTheCompletionToolIsADirectCallNotCodemodeOnly`).
- Its `execute` returns an object carrying `content` and declares no `output` schema. The dispatcher throws on a bare string, the part is stored with `status: "error"`, gate 3 reads that as a refusal, and a job that did its work is judged blocked. The codemode path skips that check, which is why the two faults masked each other (`TestTheCompletionToolReturnsWhatTheDispatcherAccepts`).
- A second mechanism can remove a tool before the model sees it: the toolset is filtered by `options.permission ?? <tool name>` against OpenCode's permission rules, dropping a tool whose last matching rule denies resource `*`. This is also why `edit` is the single write gate: the write and patch tools declare `options.permission` as `edit`. spov sets no such rules.
- The plugin records the tool's registration and any failure to register it, to the evidence file and to stdout, because a cancelled job never collects the file. If registration fails the loop stops after the opening turn, so the job is judged on that rather than running to its clock.
- A declaration with no session ID still sets `loop.stopped` and the reason before it tries to announce, and the event subscription announces at the next turn end (`TestADeclarationWithoutASessionStillStopsTheLoop`).
- The agent is told about the tool in two places, the continuation text and the goal (`goalEpilogue`), because the first turn has no continuation. Both say that stating completion in a reply does nothing (`TestThePromptDoesNotAskTheAgentToAnnounceInProse`).
- The tool name is written in Go (`opencode.CompletionTool`) and in the plugin (`CONFIG.completionTool`). `TestCallingTheCompletionToolEndsTheRun` compares the name the running plugin bound against the prompt text.
- The check runs before the marker on this path. `announceStop` is awaited inside the tool call, so the agent's turn blocks while the check runs; the supervisor collects evidence in the single sandbox visit the marker triggers, and a check still running then would be a check nobody reads.

A declaration does not stop the turn it was made in. The marker is a `resume: false` synthetic, which starts no turn and cannot retract one in flight, so the agent can keep working and declare again. `announceStop` returns early on `loop.announced`, so exactly one marker is sent; without that guard an already delivered job would be redelivered. `continue.skipped` records that the loop refused to continue.

Calling the tool begins delivery within seconds: the supervisor collects the deliverable, then concludes the job and terminates the sandbox. Work done after the declaration can be uncollected or cut off. On a `pr` job an edit can land after the check, so the verdict describes a tree slightly different from the one the run left. The mitigation is the tool's description, which says it must be the last action and that every write, commit and push comes first (`TestTheCompletionToolSaysItMustBeTheLastAction`).

### While a person's message is pending

The tool refuses while a person's message is waiting. The plugin counts the `user` inbox items it has seen enqueued and not yet delivered or cancelled (`inbox.pending`). Above zero, and while the loop has not already stopped, the tool records `completion.deferred` (never `completion.declared`), announces nothing, and answers that a message is waiting and will reach the agent next and that it should act on it and call again (`TestCompletionWaitsForAQueuedMessage`).

- Nothing from the deferred call counts. The check runs only when a later call is accepted, and the deliverables are whatever is recorded by then, so the evidence describes the revised work. Gates 1 and 2 never read `completion.deferred` as a completion because it differs from `declaredCompletionName`.
- The plugin is the only place that sees the completion call and the inbox together; a server-side check would come a pass too late, after delivery began.
- The plugin counts only its own session's inbox, and a succeeded execution clears the count, since every queued item has been delivered by then. A delivery the subscription missed cannot defer completion for the rest of the run.
- A message the run never reached is drawn as not processed. That happens when it arrives after the stop was announced but before the pass that refuses further messages, when the job reaches its wall clock (DL-049) and when the job is cancelled. None of these grants more time or starts another job. The page reads the status from stored events (`messageStatuses` in `timeline.ts`; see DL-058).

### The stop marker

The plugin announces its own stop as a `resume: false` synthetic whose text begins with `SPOV_LOOP_STOPPED` (`opencode.LoopStoppedMarker`) followed by a JSON object with the reason and counts. `resume: false` starts no turn, so the announcement cannot trigger a continuation, and a synthetic is not a `user` item, so it is never read as a person steering. It is sent at most once.

A pause announces nothing. `/spov-goal pause` stops the loop continuing without moving the job row, because a person pauses to look and then resumes.

The supervisor matches the marker on three conditions: the event is `session.inbox.enqueued`, the item is a synthetic (so a person typing the marker steers instead of ending the job, and the agent quoting it in a reply is not an inbox item at all), and the text starts with the marker (so the token inside a longer message does not match). The text is at `data.item.payload.text` in the event frame (`TestTheStopMarkerIsFoundInARealFrameShape`) and at the top level of a stored synthetic message (`TestTheStopMarkerIsFoundInARealMessageShape`).

The marker is a guardrail, not a boundary. The agent has a shell and OpenCode's API on localhost with its password in the environment, so it can post a synthetic and end its own job, just as it can answer its own permission request. The boundary is the egress policy and the sandbox (DL-031). The marker says the loop stopped, never that the job completed honestly, and the verdict does not read it as evidence of completion. Gate 2 checks the deliverable from spov's side for that reason.

### Which states a stop moves

`nextState` moves a `running` job to `delivering` on any stop. A `steered` job moves to `delivering` only on a stop with reason `declared`; blocked jobs move on neither (a blocked job is parked on an unanswered permission, and an unanswered permission vetoes at gate 3).

Without the steered edge, a steered job whose agent declared would stay `steered` until cancelled, delivery (where the deliverable is collected) would never run, and the finished report would die with the sandbox. A declaration is a tool call and a positive assertion that the work is complete. Every other reason (the loop giving out, a failed send, a repeated denial, a pause) says nothing about whether the work is done, and concluding a job out from under a person who is steering is what the steered state prevents. The reason is read from the marker's JSON payload against `opencode.CompletionReason`, the literal the plugin writes. A payload that cannot be parsed is not a declaration (`TestCallingTheCompletionToolEndsTheRun` is the drift guard). Declaring still does not make the job succeed: the gates judge the steered turns like any others.

`followResult.Stopped` folds in a declaration as well as an ordinary stop, so the abandoned-sandbox backstop does not run over a job the same pass just delivered (`TestADeclarationSurvivesADeadSandbox`).

### The backstop and the recovery

If the marker never lands (the send failed, or the recorder was not attached at that moment), the job would sit in `running`. `checkAbandoned` keys on the session's state in the store, which the reconciler maintains from the provider's own view: a job whose session is not live has no sandbox left to wait for. It moves the job to `delivering`, from `running`, `blocked` or `steered`, so the verdict judges what the run left behind (a blocked job's unanswered permission vetoes it at gate 3). A long turn cannot trip it, because a sandbox executing a long suite is still live. It reads the store only (`TestSilenceIsNotCompletion`, `TestTheBackstopLeavesALiveSandboxAlone`).

The recorder writes an inbox item to both the event log and the message store, and on a real run the marker reached the messages and not the events, with the cursor at the end of the log, so the job stayed `running` on a live sandbox that the backstop would not touch. A follow pass on a `running` job that saw no stop event asks `loopStoppedInMessages` whether the stored transcript carries the marker, and treats it as the stop.

- It is a store read: nothing reaches the sandbox and no idle clock resets. It costs one query per follow pass of a running job. It reads the same announcement the plugin sent from a second place, so it is not inference from silence, and it does not replace the backstop, which covers an announcement that landed nowhere.
- The guard is the `running` state, not a gap. The event goes missing two ways: a recorder break, which leaves a gap, and the recorder's opening window, which leaves none. A blocked, steered or delivering job is never reconsidered, so a marker the event stream deliberately did not act on cannot take effect by the back door (`TestTheTranscriptRecoveryIsBoundedByStateNotByAGap`).
- The message must be a synthetic and its text must start with the marker, so a person typing it or the agent quoting it does not count (`TestTheGapRecoveryCannotBeForged`).
- A succeeded job carries no `Error`. The verdict clears `GapNote` on success; otherwise a recovered job would succeed while showing "recording gap … may be stale", a success that reads as a failure.

### Failed turns

A failed turn (`session.execution.failed`) is retried twice, then ends the run.

1. Unless the loop is stopped or held by a person, the plugin records `turn.failed` with the error's message, type and status, and continues the run after 10 seconds, then 30 seconds after the second failure in a row (`opencode.TurnRetryDelays`).
2. The retry is a queued synthetic continuation sent from a timer, so the event loop keeps reading. A takeover, a stop or a new turn before it fires skips it.
3. A third failure in a row ends the run with reason `turn-failed` (`opencode.TurnFailedReason`) and the error in the stop marker. The job is then delivered and judged like any other.
4. A succeeded turn resets the count.

A held loop is left alone: a failure in a turn a person started is theirs to handle. The delays are constants, not configuration. The verdict's summary begins "the run was ended after 3 turns in a row failed: <error>", with the error redacted and bounded as a denied call's is (`failedTurnNote`, `TestTheVerdictQuotesTheFailedTurnsError`). The endings metric counts it as `ended_by="turn-failed"` (`telemetry.EndedTurnFailed`). The plugin's behaviour is covered by `TestFailedTurnsAreRetriedThenEndTheRun`, `TestASucceededTurnResetsTheFailures` and `TestAFailedTurnWhileHeldIsNotRetried`.

## Rationale

- The observed cost of having no completion exit was forty turns of unattended spend after correct work. Every one was billable and none could accomplish anything.
- A tool call is deterministic where prose is not, the same reasoning that makes gate 3 key on a tool part's shape instead of the agent narrating a denial, and that makes a continuation a synthetic instead of a prompt.
- No-progress detection is a bound and classifies a run as having hit a limit, which is a different and less useful fact than having finished. Verifying the deliverable after every turn would be stronger, but it only works where the deliverable is mechanically detectable.
- A provider can fail for a moment (overloaded, a dropped stream) or for good (a spent quota, a revoked key), and the plugin cannot tell which from one failure. Two retries over forty seconds ride out a brief fault; past that, waiting only bills the sandbox while nobody is told. A job whose model is unavailable ends in about a minute, not at its wall clock.
- A completion check that lives in the plugin sees the pending message at the moment of the call; one that lives in the supervisor would run after delivery had begun.

## Measurements

- S10 (OpenCode build 0.0.0-beta-18684): no allowlist entry is needed for a contributed tool. Permission assertions live in each tool's `execute`; the only computed-action site in the bundle is MCP's `<server>_<tool>`; the toolset filter is `options.permission ?? <tool name>` against the permission rules. Re-run: `go test -tags integration ./internal/sandbox/ -run S10 -v`.
- Codemode split: only `codemode === false` tools are direct calls. The first run without it answered "the tool is not in the current Code Mode catalog (`default.*` only)". Re-run: `go test ./internal/opencode/ -run TestTheCompletionToolIsADirectCallNotCodemodeOnly`.
- Dispatcher contract: with `tool.output` undefined the result must carry `content` and no `output`. A bare string throws `J is not an Object` and the part is stored with `status: "error"`. Re-run: `go test ./internal/opencode/ -run TestTheCompletionToolReturnsWhatTheDispatcherAccepts`.
- Stored synthetic message shape: no `content` array, text at the top level, no `role` key (the role comes from `type`), measured against a real capture. Re-run: `go test ./internal/server/ -run TestTheStopMarkerIsFoundInARealMessageShape`.
- A real job did correct work on its first turn, then spent forty more turns saying "Already complete" because nothing told it to stop.
- A job run against a GitLab repository had its first model call fail with `session.execution.failed`, error type `provider.quota`, status 429. The plugin did nothing, and the job sat `running` with no activity for seventeen minutes until it was cancelled.

## Consequences

- Job state follows the plugin's announcements, so a run that finishes ends within a pass of the signal and does not bill to the clock.
- The supervisor depends on the marker's payload shape and on the stored message shape. The message shape is inferred in the same sense `parseMessages` is, and pinned by a test against a real capture.
- Three names are written in Go and in the plugin and drift fails silently: the stop marker, the completion tool name and `declaredCompletionName`. Their guards are `TestTheStopMarkerMatchesThePlugin`, `TestCallingTheCompletionToolEndsTheRun` and `TestTheCompletionEventMatchesThePlugin`.
- A steered job can end without the person who steered it saying so. That is a deliberate narrowing, bounded to a declaration.
- The artifact of a steered job is collected and its sandbox terminated at delivery.
- The completion tool must never be added to `PermissionsForKind`.

## Known gaps

- A short window remains between the stop announcement and the pass that moves the job to `delivering`. A message accepted then is not processed, and is drawn that way.
- Work after a declaration can be lost, as above. Closing the window would take refusing tool calls after a declaration (no measured way to do so) or deferring collection to the end of the turn, which brings back the timing problem the marker avoids.
- The transcript recovery reads no reason and runs only for `running` jobs, so a steered job whose declaration reached the messages but not the events stays steered until cancelled or its clock ends it.
- A stop marker and a declaration are the sandbox's word: the agent can post a marker itself, so neither proves the work was done honestly.
