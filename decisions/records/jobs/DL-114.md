## Context

The browser is not the only reader that takes an inbox item of type `user` to mean "a person". Server-side code does too, over the whole session's log, with no conversation filter:

- `takesOver` and `takeoverDelivered` (`supervisor_follow.go`) steer a job when a `user` item is delivered, and `FindEvent` joins the delivery to its enqueue anywhere in the session (DL-052);
- `personWrote` (`verdict.go`) reads any `user` enqueue as "a person put something in the job's inbox", after which a check spov proposed stops deciding gate 1 (DL-050);
- `withdrawalHonoured` (`deliverables.go`) lets a `user` enqueue after a pull request was recorded honour the agent's withdrawal of it (DL-051).

DL-052's plugin already restricts itself to the job's own session (`TestAnotherSessionsMessageDoesNotHold`: "a subagent's inbox is not the job's"). The supervisor does not. If a subagent's task prompt is a `user` item in the child's own inbox, which the web transcript's behaviour suggests and spike S-SA1 (DL-110) is to confirm, then on every subagent call:

- the supervisor reads its delivery as a person's takeover and moves the job to `steered`, though nobody wrote anything and the plugin (correctly) did not hold the loop;
- the verdict can later say a person wrote, and stop judging by a proposed check;
- an agent's withdrawal of a pull request can be "honoured" by its own subagent's prompt, which is the one thing DL-051's rule exists to prevent.

The same applies to `signalTurnEnded` (a child's `session.execution.succeeded` counts as one of the job's turns) and to `unansweredAsks`, which already pairs asks by request id and conversation and is not affected.

## Decision

The supervisor's readers of "a person's item" and "the run's turn" are restricted to **the job's own conversation**, the one `jobConversation` opens and `store.Primary` (DL-110) returns:

- `follow` loads the session's conversations once per pass and keeps the id of the job's own, and ignores the inbox and execution frames of any other conversation for `takesOver`, `takeoverDelivered` and `signalTurnEnded`. A frame of a child is read for what a job reads *everywhere* (a permission ask, the stop marker's absence, the tool calls gate 3 counts) exactly as before.
- `personWrote` and `withdrawalHonoured` take the events of the job's own conversation only. `Judge` and `recordDeclarations` leave every other conversation's `session.inbox.*` frames out of the events they read (`withoutOthersInbox`), since those two are the only readers of inbox frames there; everything else in the verdict reads every conversation.
- `takeoverDelivered`'s `FindEvent` joins the enqueue within that conversation.

What is **not** restricted, deliberately:

- gate 3 counts tool calls from every conversation: work a subagent did is work the job did (`jobMessages` keeps reading every message);
- `unansweredAsks` and `signalParked`: a child's permission ask holds the job exactly as the job's own does. This is the supervisor's counterpart of the web showing a child's ask in the main view (DL-112);
- the plugin, which already filters by session.

If the job's own conversation cannot be determined (no row yet, a recorder gap before the first frame), the pass reads as it does today for that pass and writes nothing new, since a job opens its conversation with the goal before the agent can spawn anything (`jobConversation`, DL-025's reasoning).

## Rationale

- A person can write to a job only through the API and the CLI, both of which land in the job's conversation (DL-109, DL-110). A `user` item anywhere else was written by the agent, so reading it as a person's is a wrong inference, not a conservative one, and every error it causes moves a job's judgement in the person's favour.
- The restriction is a filter on the conversation, not on the item's content, so it does not need to know what a subagent prompt looks like.
- Repeating the plugin's own rule on the server keeps the two judges agreeing, which `TestThePluginAgreesOnWhatTakesOver` already insists on for the item itself.

## Consequences

- Tests, in the measured shape: a delivered `user` item of a child conversation does not steer; one of the job's own does (`TestFollowSteersOnTheDeliveryOfATakeoverItem` still holds); a withdrawal is not honoured by a child's prompt; a child's turn ending is not a turn of the job. Frames are built from the S-SA1 capture, not invented, for the reason AGENTS.md gives about gate 3.
- S-SA1 measured a child's prompt as a `user` item in its own inbox (DL-110), so the steering, withdrawal and "a person wrote" cases are fixes, not pins.
- `follow` reads the conversation list once per pass: a store read, as the rest of the pass is.
- AGENTS.md's "How a job ends" and "The plugin" sections gain one line naming the rule, and DL-052's table of shared names is unchanged.
