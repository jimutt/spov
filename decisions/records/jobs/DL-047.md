## Context

A job's goal is the weakest input in the system. It comes from a person in a hurry or from a forge label, it says nothing about what kind of work is asked for, and a label applied by a maintainer can carry a prompt injection into the job. The job also has a check command for gate 1 (DL-050), and most callers never pass one. Gate 1 is then unverified, which a job survives: a `report` job succeeds on its artifact and a `pr` job on its pull request. A check is offered where one is obvious and is not required where it is not.

The supervisor (DL-046) opens a job's session with a synthetic message. The question this record answers is what text that message carries and where it comes from.

## Decision

### One pass, before the sandbox exists

One model call runs in the control plane before the job's sandbox is created. It produces an assessment, not a replacement for the goal:

- The job row's `Goal` keeps the original text unchanged. The row owns the canonical text; derived things do not become canonical, and the pass can be re-run without rewriting what was asked.
- `openingText(job)` is the one place the opening text is decided. With no assessment it is the goal verbatim. With one, the original comes first, labelled as the request exactly as given, and the assessment follows, labelled as an automated reading that may be wrong or incomplete, with the request above it stated to win wherever they differ. The assessment is flattened to one line of prose, not a delimiter it could close.
- A rewritten goal is a goal nobody agreed to, and a job that did the wrong thing correctly is worse than one that failed.

`internal/prep` is the control plane's only outbound model call. A provider key is otherwise a value spov carries into a sandbox and never uses.

### A failed pass never fails the job

If the model is unavailable, over budget or answers unusably, or if the row write fails, the job opens on its original text alone. `Supervisor.prepare` returns the job unchanged on every path that is not a recorded success (`TestAFailedPassLeavesTheJobExactlyAsItWas`, `TestAnAssessmentThatCannotBeRecordedIsNotUsed`). A half-applied assessment must not reach a prompt that another replica reads.

The pass is bounded by its own timeout (`prep.Timeout`, 30 seconds, no retries) and skipped on expiry. The reply is capped at `MaxOutputTokens` (8,000), which looks generous for a paragraph and a command because OpenAI's API counts reasoning tokens against it; a reply cut off by the cap before any answer is reported as such. The assessment and any proposed check are stored on the job row (`assessment`, `check_proposed`), because River redelivers and provisioning may run on another replica. A job that already has either skips the pass, so a retry does not pay twice. The write re-reads the row inside its transaction and changes only the fields the pass owns, so it cannot write a stale state back over the job's.

Two log levels stay separate. No provider key found is an ordinary zero-configuration state, noted once at startup. A call that was attempted and failed warns on every job. The startup line names the model and endpoint and never the key (`TestTheStartupLineNamesTheModelAndNeverTheKey`). Without the split, a deployment whose default model was retired would look like one that never configured a key (`TestNoProviderIsANoteAndNotAWarning`).

### The proposed check

The pass may propose the job's check command, only when the caller gave none.

- A caller's check always wins. `prepare` re-checks the current row, not its own copy, before filling `CheckCommand` (`TestACallersCheckIsNeverOverwrittenByAProposedOne`).
- The row records that the check was proposed (`CheckProposed`), and the verdict says so on every gate 1 outcome through `withCheckProvenance` ("a check spov proposed, not one the caller gave") (`TestGateOneSaysWhenTheCheckWasSpovsOwn`). A gate that passed on a command spov chose is weaker evidence than one the caller chose, and a reader must be able to tell which.
- A check stays optional. An empty answer is the ordinary case, and the prompt asks for an empty string instead of a guess. A proposal that cannot be made leaves gate 1 unverified, with no fallback command. `parseAssessment` drops anything that is not a single command: a newline, or more than 512 bytes, makes the check empty.
- Once a person has put a message in the job's inbox, a proposed check is unverified whatever it returned (DL-050; `TestAProposedCheckStopsDecidingOnceAPersonWrote`).

The proposed command is untrusted text that spov then executes. It runs in the sandbox, contained as the agent's own shell is (DL-031), never in the control plane and never with spov's credentials. Nothing about it may become a path by which a job's text reaches the server. A proposed check that always passes (`true`, or a test of a file the job creates first) is worse than none, and nothing detects one. The system prompt is therefore security-relevant text; it forbids such commands and commands that write, push, deploy or delete. Gate 1 is a guardrail on an honest run, not a boundary against a dishonest one.

### The assessment is untrusted text

The pass reads input that may be hostile and writes text that goes into a prompt, so it is a prompt-injection surface by construction. The system prompt tells the model the goal is data, not instruction. The goal is fenced in `<task>` tags and clamped to 16 KiB on a rune boundary (the model is told when it was cut), and the reply is bounded to 4 KiB. The fence is for legibility and is not a boundary. The assessment is contained by:

- carrying the original beside it, never in place of it;
- granting nothing: a job's permissions come from its kind, never from what the pass concluded (DL-040).

It is not sanitisation, and nothing downstream may rely on it as such.

### Provider and model

The client is `github.com/openai/openai-go/v3` behind the `Completer` seam. The wire format is the interface: every other provider is reached by pointing the base URL elsewhere. Anthropic's own API is not spoken; a deployment that wants Claude reaches it through OpenRouter or an OpenAI-compatible gateway. A second SDK would be a second client and type set for a provider already reachable. An aggregator library over the vendor SDKs would be a second pre-1.0 dependency, repeating the cost of breaking minor releases that the Modal SDK already imposes. The SDK carries its major version in its import path, so a breaking change cannot arrive in a minor bump; the seam stays so tests can fake it.

The client does not follow redirects, so the key never leaves over one (`TestARedirectIsNotFollowed`), and an error message has the key scrubbed from it (`TestAnErrorDoesNotCarryTheKey`).

The provider is detected from a three-rung ladder. The first key present decides the endpoint and the model family:

| Key variable | Endpoint | Family | Fallback literal |
|---|---|---|---|
| `OPENROUTER_API_KEY` | `https://openrouter.ai/api/v1` | `anthropic/claude-sonnet-<n>` | `anthropic/claude-sonnet-5` |
| `GEMINI_API_KEY` | Google's OpenAI-compatible endpoint | `gemini-<n>-flash` | `gemini-3.8-flash` |
| `OPENAI_API_KEY` | the SDK's default | `gpt-<n>-luna` | `gpt-5.6-luna` |

Each rung picks the newest non-beta model of its family from the live model list (DL-013) through `List.Newest`, using `OpenRouterFamily`, `GeminiFamily` and `OpenAIFamily`. The key is resolved once at startup and each pass picks the model again with `prep.Reselect`, so it follows the list as it refreshes. A family that matches nothing falls back to the rung's literal in `internal/prep/model.go`. The literals are the last resort and are not the current picks. The pass needs a capable, cheap model, not a particular one, and the family stays true across releases. `TestTheSnapshotHoldsEveryRung` checks each family and literal against the shipped snapshot.

OpenRouter is first because one key reaches Claude, Gemini, GPT and several hundred other models. Gemini is second because its OpenAI-compatible endpoint is documented by Google as in beta, so it is the least stable link and belongs in the fallback part of the order. The ladder stops at three: each further rung is a base URL and a model literal that ages on its own schedule, and a deployment holding only another provider's key sets explicit configuration.

A key is looked up in the environment first, then in the credential store (`spov credentials add`), as `providerKeys` does for a sandbox. A deployment that stored its key still gets a pass, and a deliberate export is not outranked by a forgotten stored key.

Explicit configuration overrides detection. It is deployment-level, under `prep` in the server's configuration, and read only by `spov serve`:

```yaml
prep:
  base_url: https://gateway.example.com/v1
  model: some-model
  key_env: PREP_API_KEY
```

- `model` alone keeps the detected endpoint ("OpenRouter, but a cheaper model").
- `base_url` requires `model`, because spov cannot know a gateway's catalogue and a guessed name either 404s on every job or asks for something nobody chose.
- `key_env` requires `model`, because a key does not say which provider it is for. A `key_env` that names an empty variable is a configuration error, not a reason to fall down the ladder to a key meant for something else.
- A `base_url` without `key_env` sends the detected key to the configured endpoint. That is the "OpenRouter key plus a proxy in front of it" case, and it means a credential travels to a host chosen by configuration. The operator who set `base_url` chose that. A deployment that separates budgets sets `key_env` and gets a key nothing else reads.

The pass is not per-user and not per-job. It is the operator's inference, billed like the database. A per-job model would let the goal text influence which model reads the goal text, which is a worse injection surface than influencing what that model says.

## Rationale

- The opening prompt is the one place a job's framing can be improved before anything expensive happens, and it is cheap there: one short call against one small model, once per job.
- Keeping the original verbatim is what makes the pass safe to add. If the assessment is wrong the agent still has what was asked; if it is right the agent has both.
- Making the pass optional keeps it from becoming a second single point of failure. A component that can fail must not become the thing every job depends on.
- A caller's check beating a proposed one is the rule against a rewritten goal, applied to a command.
- Metadata starts nearly empty on purpose. The pass is where task metadata will be extracted, but no schema for a richer task taxonomy is added until a consumer reads it. The two job kinds, `pr` and `report`, describe delivery, not the shape of the work.
- The prompt is spov-authored text that shapes every job. It belongs in the repository under review, not in configuration, and a bad edit does quiet damage there.

## Measurements

- Dependency cost of `openai-go/v3`: a probe module importing only the chat-completions path linked at 17.6 MB and tidied to exactly four `tidwall` modules, all already present at equal or higher versions through the Modal SDK. The Azure and AWS requires in the SDK's `go.mod` are pruned because nothing imports those constructors.
- The mechanism behind the opening text, `POST /api/session/:id/synthetic` with `resume: true`, was measured in S5 (DL-046). Re-run: `go test -tags integration ./internal/sandbox/ -run S5SyntheticLoopAndPermissionAnswer`.

## Consequences

- The supervisor gains a step before provisioning, which is a new way to be slow. The accepted costs are an egress dependency, a latency floor before a job starts, and a per-job cost outside the sandbox's own. All three are accepted for a short prompt against a small model and are not to grow without revisiting.
- A hard-coded model name is a liveness dependency whose failure is silent: a retired model answers 404 on every pass while a failed pass does not fail the job. The family pick, the fallback literal and the note-versus-warning split are what make that visible. The literals live in one file beside the detection order.
- The provider-key check order means a deployment that already holds a sandbox key gets a working pass with no configuration.

## Known gaps

- Which credential pays is unsettled. The keys are the ones the server holds for sandboxes, so the pass and the sandboxes share one budget unless the operator sets `prep.key_env`. Making the separation the default is unscheduled.
- Nothing detects a proposed check that always passes; only the prompt discourages one.
