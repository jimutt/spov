## Context

A job runs on its own: the plugin in the sandbox sends a continuation whenever a turn succeeds (DL-039). A person can still write to it, from the web composer, from `spov` or from a TUI attached to the sandbox, and those messages mean different things. Sometimes the person adds a hint and wants the job to carry on; sometimes they type "stop" and want the agent to wait for them. Autonomy has to end, when the person asks for that, at a point the agent has actually read the message. The supervisor and the plugin each need to recognise the same event, and a continuation must never overtake a message a person wrote.

A message reaches the agent as an inbox item of type `user` (a human's words) or `synthetic` (spov's own). OpenCode's `delivery` field decides when the agent reads it (DL-019).

## Decision

### Whose words are a `user` item

Nothing spov generates is ever sent as a `user` item: not a continuation, an opening goal, a marker or a pause notice. A message a human typed belongs to that human, and the server relaying it is a courier, so `user` is the right type. The plugin and the server both rely on this, because a spov-authored `user` item would make every job steer itself on its opening turn.

`TestOnlyAHumansOwnWordsReachThePromptEndpoint` is a source test over the repository's non-test Go files. It asserts that the sandbox's prompt route is addressed only from `steer.go`, and that the text posted there is the caller's own, unmodified: a preamble added by the server would put spov's words inside a `user` item. Opening a job still posts a synthetic. Routing a human's words as a synthetic would attribute them to spov in the transcript.

### Each message says what follows it

The prompt carries `metadata: {"spov": {"after": "continue" | "handover"}}` (`steerBody`). It is metadata, never part of the text. On spov's API an omitted `after` means `continue`, and the server always writes the value; on an interactive session it is ignored. OpenCode keeps the metadata on the enqueued item and on the stored message.

In the sandbox, a `user` item takes the job over unless its metadata says `continue`. An item with no spov metadata comes from something that talks to OpenCode directly, in practice a person typing in the attached TUI, which cannot set it. Such an item hands over, so a typed "stop" keeps working.

### Takeover happens on delivery

The takeover is decided when the item is delivered to the agent, not when it is enqueued:

- **The plugin** remembers the ids of takeover items from `session.inbox.enqueued`, and on `session.inbox.delivered` for one of them it holds its loop (`loop.paused`, recorded as `loop.held`). Delivery comes before the execution's `session.execution.succeeded`, so the continuation that would follow is never sent. A cancelled item (`session.inbox.cancelled`) is forgotten and holds nothing. The hold is silent: the plugin tells the agent nothing. An inbox event from another session (a subagent's) does not hold the job's loop.
- **The supervisor** writes `steered` when it reads the delivery of a takeover item. The delivery event carries only the inbox id, so it joins that id to the `session.inbox.enqueued` event of the same item, from the pass itself when it read the enqueue there and otherwise through `ConversationStore.FindEvent` (`takeoverDelivered`), one store read at most per delivered item. An enqueue that was never stored takes nothing over on the supervisor's side. It then sends the one pause notice as it does for any move to `steered` (DL-054).
- A `continue` item holds nothing and moves nothing. The job stays `running` and its wall clock keeps running (DL-049).
- Messages sent after a handover are still read: OpenCode delivers every pending item without stopping between them. The hold stops autonomy, not the person's own messages. A `continue` item behind a handover does not release the hold; only Resume does (DL-054). Until a message is delivered the person can cancel it (DL-019).

The rule for which items take over is written twice, in Go (`takesOver`, `InboxItemAfter`, `InboxID` in `internal/jobs`) and in the plugin (`takesOver`, `trackInbox`, `inboxIDOf`). `TestThePluginAgreesOnWhatTakesOver` runs the plugin's own functions and Go's over the same 18 frames, a captured one among them, including items nested at the depth limit (5) and past it, and the `after` values `continue`, `handover` and a wrongly spelled one. `pluginhold_test.go` drives the real `setup()` under bun or node: a human message mid-turn leaves the turn's end with no continuation, a synthetic item does not hold, a `continue` message does not hold, resume clears the hold and nudges, and a second message records nothing (`TestAHumanMessageHoldsTheLoopAtOnce`, `TestTheLoopsOwnItemsDoNotHoldIt`). `TestFollowSteersOnTheDeliveryOfATakeoverItem` covers the supervisor.

### The supervisor writes the state

The request handler does not pause the loop and does not write `steered`. Writing `steered` from the handler would assert a fact about the sandbox that has not been observed, and would skip the `pauseLoop` guard. A synchronous pause would also leave a held loop under a `running` row that `ResumeJob` refuses to resume (only `steered` and `blocked` resume), and the plugin's `loop.paused` is memory only, so nothing durable would record it after a crash. It would reverse Resume's order too: Resume clears the plugin's pause first, so every crash point leaves the job resumable, and setting a pause first puts every crash point in the one state Resume refuses. And a pause cannot retract the turn already running. A held loop under a `running` row is safe here because the trigger is a stored inbox item that any replica's next pass reads:

- If the server crashes before the pass, the next pass reads the same stored event.
- If the plugin dies, the sandbox is gone, which is the abandoned-sandbox case (DL-045).
- If the recorder missed the item in a gap, the job sits `running` with its loop held until the wall clock delivers and judges it.
- If a person writes to a job that is about to be `blocked`, the loop is held and the supervisor cannot steer a blocked job; Resume sends the plugin's resume for a blocked job too, best-effort, and the wall clock ends a job left held.

The control that stops work is Interrupt (DL-053). The turn already running when a message is delivered is untouched, so the composer copy never says the agent will stop. It may say a job continues after a `continue` message, because it does.

### When a send is refused

`jobRefusesAMessage` refuses a message when it would be enqueued but never delivered, and names the job's state in the 409 (`ErrJobNotSteerable`):

- `blocked`: the agent is parked on a permission question and will not read its inbox. Typing into such a job is answering it, not taking it over; the page offers the answer instead.
- `queued` (no sandbox yet) and every terminal state.
- `delivering`: the run is over.
- `provisioning`: the agent has no goal yet, and the state has no edge to `steered`, so the store would refuse the move.

A `steered` job accepts messages, since talking to a job you took over is the main use. Every job state is decided one way or the other: a state added to the transition table but not to `jobRefusesAMessage` would become steerable by omission. `store.JobStates()` lists them for the check and `TestEveryJobStateIsDecided` enforces it. A job accepts both `steer` and `queue` delivery; takeover is judged at delivery, not by the delivery mode.

### The plugin's continuations are queued

Every continuation the plugin sends, the loop's and Resume's nudge alike, goes out as `ctx.session.synthetic({resume: true, delivery: "queue"})` (`continueRun`), never `ctx.session.prompt`, which would arrive as a human's message and move the job to `steered` on its own turn. Queued synthetics are ordered with queued user items by arrival, so a continuation never goes ahead of a message a person queued, including after an interrupt, when queued items stay parked until the next execution starts and an unqueued nudge would run first. Synthetics that must reach the model mid-turn stay `steer`: the pause notice, the denial note and the plugin's replies. Those sent with `resume: false` start nothing. `TestPluginContinuesWithSyntheticAndNeverPrompt` and `TestTheLoopsOwnItemsDoNotHoldIt` guard this. Anything spov sends into a job's session must stay `synthetic`, or it holds the job's own loop.

## Rationale

- Holding at delivery is the only point that honours "hand over after the agent has read this". At enqueue, the supervisor's pause notice, a steer synthetic, would go ahead of a queued item, so the agent would be told to stop before it had read the message, and the clock would stop while the agent was still working.
- The plugin holds as well as the supervisor because the supervisor's pass comes up to `FollowInterval` (10 s) after the event. In a job whose turns finish in seconds, a continuation can slip into that window. A typed "stop" was followed by two continuations before the pass held the loop, while ESC suspended the job properly.
- The plugin does not read the text. Rejected alternatives: a completion-style tool with which the agent reports that it was told to stop (the agent judging intent, with a schema, a verdict distinction and one more name shared between Go and the plugin); the server matching the text against "stop" (it would fire on "stop using that library" and "don't stop until the tests pass", and a false positive suspends a working job); a shorter follow interval (a short turn can always end first, and it adds a store poll per job).
- Messages behind a handover are processed rather than held in a spov-side queue, or refused while a handover is pending: they are the person's own words, which they can cancel while pending, and a second queue would need its own visibility, cancel and release.
- Item metadata, not text, carries the choice, so the rule that the posted text is the human's own, unmodified, stands.
- An item with no metadata hands over because only a client talking to OpenCode directly sends one, and a person typing in the attached TUI expects that to take the job over. spov's own API always states the choice.
- Continuations are queued because, at `succeeded`, the queue is already drained, but after an interrupt it is not, and only a queued continuation keeps its place behind the person's parked messages.

## Measurements

- **Plugin sees the human inbox** (`TestIntegrationPluginSeesTheHumanInbox`, one sandbox, no model turn, OpenCode build 0.0.0-beta-19151): a prompt posted to `/api/session/:id/prompt` reaches a server plugin's subscription as `session.inbox.enqueued` with `item.type: "user"`, and the plugin recorded `loop.held`. `go test -tags integration ./internal/sandbox/ -run PluginSeesTheHumanInbox`.
- **S-LS1:** an omitted `delivery` resolves to `steer` at OpenCode. `go test -tags integration ./internal/sandbox/ -run SLS1`.
- **S-Q1** (DL-019 has the numbers): delivery precedes `session.execution.succeeded`; OpenCode keeps `metadata` on the enqueued item and the stored message; a steer synthetic goes ahead of queued items; queued synthetics order with queued user items by arrival; OpenCode drains pending items without stopping between them; an interrupt leaves queued items parked until the next execution starts. The plugin hold on a delivered handover: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SQ1PluginHold -v`; the ordering: `SPOV_PROBE=1 go test -tags integration ./internal/server/ -run SQ1 -v`.

## Consequences

- A job in `steered` always has a held loop (DL-054), and a held loop under a `running` row lasts at most one pass.
- The supervisor makes at most one store read per delivered item on a job, to find its enqueue.
- Copy that talks about a message may say it is read once the agent's current step finishes, that a job carries on after a `continue` message and pauses for the reader after a handover. It never says a turn stops.
- A change to the takeover rule changes the Go and plugin copies together, with `TestThePluginAgreesOnWhatTakesOver`. On an OpenCode bump, re-run the plugin-hold and inbox-shape measurements above.
- A new job state fails `TestEveryJobStateIsDecided` until `jobRefusesAMessage` decides it, and the browser's mirror of the rule is in DL-059.
